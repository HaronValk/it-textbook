# VK Cloud, Selectel, Cloud.ru: сравнение сервисов, цены, особенности, миграция между провайдерами

## 1. Введение (зачем это нужно в реальной работе)

Тикет в поддержку:

> **Пользователь:** Иванов (бухгалтерия)
> **ВМ:** WIN11-CL01
> **Что написал:** «Добрый день! Пришёл акт сверки от облачного провайдера за март — 47 300 ₽, в феврале было 31 800 ₽. Новых ресурсов мы не заказывали. Подтвердите, что это наши машины, и посмотрите, нет ли варианта дешевле. Счёт надо оплатить до 25-го.»
> **Срочность:** средняя, срок — до конца недели

Заявка выглядит бухгалтерской, а на самом деле это чистая DevOps-задача: понять, что у нас в облаке, сколько оно стоит, какие есть альтернативы у других российских провайдеров и как переехать, если альтернатива дешевле.

В работе это встречается постоянно. Компании почти никогда не сидят в одном облаке всю жизнь: кто-то уходит из-за цены, кто-то из-за аттестации под 152-ФЗ, кто-то потому что провайдер закрыл зону или поднял тарифы. Инженер, который умеет читать чужой прайс, считать TCO и переносить инфраструктуру без трёхдневного простоя, стоит дороже того, кто умеет только нажимать «Создать ВМ».

После этой главы ты должен уметь: ориентироваться в трёх крупных российских облаках (VK Cloud, Selectel, Cloud.ru), понимать их сильные стороны, собирать сравнение по цене и сервисам, оценивать стоимость владения, а не только цену виртуалки, и планировать миграцию по шагам с DNS, образами, данными и понятным планом отката.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Все три провайдера — это IaaS/PaaS-облака в российских ЦОДах. Технически внутри почти у всех одна и та же база: **OpenStack** (набор open-source-сервисов для виртуализации, сетей, хранилища и образов) плюс надстройки — managed Kubernetes, S3-совместимое объектное хранилище, managed-базы данных, балансировщики, реестр образов.

Что важно понимать про архитектуру:

**Слои.** Снизу — железо и ЦОД, выше — гипервизор и OpenStack (Nova — ВМ, Neutron — сети, Cinder — диски, Glance — образы, Keystone — аутентификация). Ещё выше — управляемые сервисы (Kubernetes, БД, S3, очереди, функции). Ты как DevOps работаешь с верхними двумя слоями через API.

**API и протоколы.** Всё управление — HTTPS на 443, REST. OpenStack API отдаёт JSON, аутентификация — по токену (Keystone). S3-хранилища говорят на протоколе S3 (тоже HTTPS, подпись запросов AWS Signature V4). Kubernetes — стандартный kube-apiserver на 6443. Terraform ходит в те же API через провайдеров.

**Регион и зона.** Регион — город/ЦОД (Москва, Санкт-Петербург и т.д.), зона доступности — независимый сегмент внутри региона. Класть прод в две зоны одного региона — базовая практика, но у российских провайдеров число зон обычно меньше, чем у AWS [ПРОВЕРИТЬ по каждому провайдеру].

**Ключевая российская специфика:**

- оплата в рублях, закрывающие документы, счёт-фактура — критично для бухгалтерии;
- **152-ФЗ** «О персональных данных» и постановление Правительства № 1119 (уровни защищённости УЗ-1…УЗ-4) — если хранишь ПДн, нужен провайдер с подходящим уровнем защиты и аттестованным сегментом; состав аттестации уточняется в договоре и у самого провайдера [ПРОВЕРИТЬ];
- реестр отечественного ПО и требования импортозамещения для госсектора — все три провайдера заявляют соответствие, но конкретный перечень услуг проверяется в реестре [ПРОВЕРИТЬ];
- данные физически в РФ, что снимает часть юридических вопросов, но не отменяет вопрос «в каком ЦОДе и в какой зоне».

Схема сравнения, которую удобно держать в голове:

```text
                     УПРАВЛЯЕМЫЕ СЕРВИСЫ (PaaS)
      ┌──────────────┬───────────────┬────────────────┬──────────────┐
      │ Managed K8s  │ Managed БД    │ Object Storage │ AI / ML      │
      └──────┬───────┴───────┬───────┴────────┬───────┴──────┬───────┘
             │               │                │              │
      ┌──────┴───────────────┴────────────────┴──────────────┴───────┐
      │              IaaS: Compute / VPC / Диски / Образы            │  ← OpenStack
      └──────────────────────────────┬───────────────────────────────┘
                                     │  HTTPS/443, REST, токен Keystone
      ┌──────────────────────────────┴───────────────────────────────┐
      │      ЦОД в РФ: регион → зона доступности → стойка             │
      └──────────────────────────────────────────────────────────────┘

  VK Cloud        = продуктовая разработка, PaaS/ML, быстрый старт
  Selectel        = инфраструктура, выделенное железо, гибрид, колокация
  Cloud.ru        = корпоративный/регулируемый контур, AI, VDI
```

**Позиционирование коротко** (все три пункта — маркетинговые заявления вендоров, проверяй по актуальной документации [ПРОВЕРИТЬ]):

| | VK Cloud | Selectel | Cloud.ru |
|---|---|---|---|
| История | ex-Mail.ru Cloud Solutions | ex-хостер, выделенные серверы, колокация | ex-SberCloud |
| Сильная сторона | PaaS, Kubernetes, ML, медиа-нагрузки | железо, приватное облако, гибрид, сеть | корпоративный контур, комплаенс, AI, VDI |
| Типичный клиент | продуктовые команды, веб, ML | компании с собственным железом | крупный бизнес, госсектор |
| OpenStack API | да [ПРОВЕРИТЬ] | да [ПРОВЕРИТЬ] | да, платформа Evolution [ПРОВЕРИТЬ] |
| S3-совместимое хранилище | есть | есть | есть |
| Managed Kubernetes | есть | есть | есть |
| Terraform-провайдер | `vkcs` | `selectel` | есть [ПРОВЕРИТЬ точное имя] |

**Миграция между провайдерами** — это не «скопировать диск». Это шесть этапов:

1. Инвентаризация: что есть, что из этого нужно, что мёртвое.
2. Целевая архитектура: те же ВМ или уже Kubernetes/PaaS.
3. Подготовка: Terraform для целевого облака, образы, ключи SSH, понижение DNS TTL.
4. Пилот: 1–2 некритичные ВМ, проверка сети и производительности.
5. Переключение: данные → приложение → DNS → проверки.
6. Вывод из эксплуатации и удаление старых ресурсов (иначе платишь за оба облака).

Главные ловушки переезда: **исходящий трафик** (выгрузка 5 ТБ стоит денег и времени), **DNS TTL** (кэши живут часами), **привязка к proprietary-сервисам** (managed-БД, очереди, функции), которые нельзя перенести один-в-один, и **юридический контур** (персональные данные нельзя просто так выгрузить наружу).

## 3. Аналогия из жизни

Переезд из съёмной квартиры в другую. Ты платишь аренду (compute), отдельно — кладовку в подвале (object storage), отдельно — за мебель в рассрочку (диски), отдельно — грузчикам за каждый вынесенный диван (исходящий трафик). У нового хозяина дешевле аренда, но нет лифта, и за грузчиков он берёт больше. Ты заранее меняешь адрес в почте и на работе (DNS): кто-то запишет сразу, кто-то через неделю, и часть писем ещё долго будет лететь на старый адрес. Мебель перевозишь в коробках (образы ВМ), а вот встроенный шкаф-купе (managed-база) перевезти нельзя — на новом месте его придётся собирать заново или ставить готовый.

Где аналогия перестаёт работать: в облаке «мебель» можно клонировать — образ ВМ копируется за минуты, и в новой квартире сразу появляется точная копия, а старую можно ещё сутки не выключать.

## 4. Практика и команды

Базовая предпосылка: управление через OpenStack CLI (одинаково почти для всех трёх провайдеров), `rclone`/`aws-cli` для S3, `terraform` для IaC. Перед любой командой получаешь креды в панели (или через CLI-конфиг) — протокол `openrc`-файла с переменными окружения [ПРОВЕРИТЬ имя файла и переменные у каждого провайдера].

**1. Аутентификация и проверка доступа**

```bash
source ~/openrc-vkcs.sh          # переменные OS_AUTH_URL, OS_USERNAME, OS_PASSWORD [ПРОВЕРИТЬ]
openstack token issue -f value -c id
```

`token issue` — выпуск токена Keystone; если получил строку — креды рабочие. Смотреть: не истёк ли токен, к какому проекту он привязан (в `openstack token issue` есть поля `project_id`, `expires`).

**2. Инвентаризация: что вообще у нас в облаке**

```bash
openstack server list --long
openstack server list -c ID -c Name -c Status -c Networks -c Flavor
```

`--long` — расширенный вывод; `-c` — выбрать колонки. Типичный вывод:

```text
+------+-------------+--------+------------------------------------+-----------+
| ID   | Name        | Status | Networks                           | Flavor    |
+------+-------------+--------+------------------------------------+-----------+
| a1f2 | web-prod-01 | ACTIVE | private-net=10.0.1.14, 203.0.113.7 | c2.m4     |
| b3c4 | db-prod-01  | ACTIVE | private-net=10.0.1.25             | c4.m16    |
+------+-------------+--------+------------------------------------+-----------+
```

Смотреть: количество `ACTIVE` машин, флейворы (отсюда сразу видно «толстые» ВМ, которые жрут бюджет), привязку к сети.

**3. Флейворы — из чего складывается цена ВМ**

```bash
openstack flavor list --sort-column VCPUs
```

Колонки: `VCPUs`, `RAM` (МБ), `Disk` (ГБ). В прайсе платишь обычно за vCPU + RAM, диск часто отдельно. Найди самый дорогой флейвор и спроси себя, нужны ли эти 16 ГБ памяти.

**4. Образы: что можно выгрузить при переезде**

```bash
openstack image list
openstack image save --file ubuntu2204.qcow2 <IMAGE_ID>
```

`image save` выгружает образ в файл (qcow2/raw — как хранится), дальше его можно залить в другое облако. Смотри на размер и статус `active`.

**5. Проверка и конвертация образа перед заливкой**

```bash
qemu-img info ubuntu2204.qcow2
qemu-img convert -f qcow2 -O raw ubuntu2204.qcow2 ubuntu2204.raw
```

`info` показывает формат, виртуальный и реальный размер, backing file. Если в `info` есть `backing file:` — образ зависим от родителя, заливать его в чужое облако нельзя, сначала нужно «сплющить» (`qemu-img convert` это и делает).

**6. Тома и их «судьба» при переезде**

```bash
openstack volume list --long
```

Смотри `Attached to` — тома, привязанные к ВМ, переносятся копированием или через снапшот; ВМ с ephemeral-диском (без тома) придётся пересоздавать из образа.

**7. Оценка объёма данных перед переездом**

```bash
rsync -avz --dry-run --stats /var/www/ user@10.10.10.30:/srv/www/
```

`--dry-run` — только показать, что было бы скопировано; `--stats` — итоговая статистика. Смотреть `Number of files` и `Total transferred file size`: это ваш объём трафика. Умножь на цену исходящего трафика — получишь цену переезда.

**8. Перенос данных в S3-совместимое хранилище**

```bash
rclone config                       # создать remote типа s3 с endpoint провайдера
rclone lsd s3vk:                    # список бакетов
rclone copy /srv/backup s3sel:bkp --checksum --transfers 8 --progress
rclone check /srv/backup s3sel:bkp --checksum
```

`copy` (не `sync`!) — при переезде безопаснее, ничего не удаляет на целевой стороне. `--checksum` — сверка по MD5, а не по размеру/времени. `check` в конце — обязательный шаг приёмки.

**9. Проверка совместимости S3 API**

```bash
aws --endpoint-url https://<s3-endpoint> s3 ls
aws --endpoint-url https://<s3-endpoint> s3 cp ./test.bin s3://bkp/test.bin
```

Многие «S3-совместимые» хранилища не поддерживают часть операций (версионирование, Object Lock, lifecycle-правила, tagging) [ПРОВЕРИТЬ у конкретного провайдера]. Проверяй именно те функции, которыми пользуешься.

**10. Terraform: один код — разные провайдеры**

```bash
terraform init -backend=false
terraform validate
terraform fmt -check
terraform providers
```

`init -backend=false` — скачать провайдеры без подключения к бэкенду (удобно, когда ещё нет кредов); `validate` — синтаксис и типы; `fmt -check` — форматирование; `providers` — какие провайдеры и версии реально используются. Провайдеры в блоке `required_providers`:

```hcl
terraform {
  required_providers {
    vkcs     = { source = "vkcs/vkcs" }          # [ПРОВЕРИТЬ версию]
    selectel = { source = "selectel/selectel" }  # [ПРОВЕРИТЬ версию]
    cloudru  = { source = "cloudru/cloudru" }    # [ПРОВЕРИТЬ точное имя source]
  }
}
```

**11. Перенос ресурса под другого провайдера в state**

```bash
terraform state list
terraform state rm selectel_server.web
terraform import vkcs_compute_instance.web <SERVER_ID>
```

`state rm` убирает объект из state, не удаляя его в облаке; `import` подтягивает существующий ресурс. Так делают «переезд кода» без пересоздания руками. Всегда `terraform plan` после — должен быть пустой diff.

**12. Переключение между кластерами Kubernetes в двух облаках**

```bash
kubectl config get-contexts
kubectl config use-context vkcs-prod
kubectl get nodes -o wide
```

`get-contexts` — список кластеров из kubeconfig; `use-context` — переключиться. При мультиоблаке держи контексты с осмысленными именами (`<провайдер>-<среда>`), иначе однажды сделаешь `kubectl delete` не в том кластере.

**Бонус: калькулятор стоимости на bash**

```bash
#!/usr/bin/env bash
# cost-model.sh — сравнение месячной стоимости типового профиля
set -euo pipefail
HOURS=730; SSD_GB=50; S3_GB=100; EGRESS_GB=200

# ЗАГЛУШКИ. Впиши актуальные цены из калькулятора провайдера [ПРОВЕРИТЬ].
# VM — ₽/час за 2 vCPU / 4 ГБ; SSD — ₽/мес за 1 ГБ; S3 — ₽/мес за 1 ГБ; EG — ₽ за 1 ГБ egress
declare -A VM=([vkcs]=0 [selectel]=0 [cloudru]=0)
declare -A SSD=([vkcs]=0 [selectel]=0 [cloudru]=0)
declare -A S3=([vkcs]=0 [selectel]=0 [cloudru]=0)
declare -A EG=([vkcs]=0 [selectel]=0 [cloudru]=0)

for p in vkcs selectel cloudru; do
  vm=$(awk -v a="${VM[$p]}" -v h=$HOURS 'BEGIN{printf "%.0f", a*h}')
  ssd=$(awk -v a="${SSD[$p]}" -v g=$SSD_GB 'BEGIN{printf "%.0f", a*g}')
  s3=$(awk -v a="${S3[$p]}" -v g=$S3_GB 'BEGIN{printf "%.0f", a*g}')
  eg=$(awk -v a="${EG[$p]}" -v g=$EGRESS_GB 'BEGIN{printf "%.0f", a*g}')
  echo "$p: ВМ=$vm SSD=$ssd S3=$s3 Egress=$eg ИТОГО=$((vm+ssd+s3+eg)) ₽/мес"
done
```

Смысл не в цифрах, а в методе: цена ВМ — это 40–60 % счёта, остальное набегает на дисках, трафике, бэкапах и балансировщиках.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

## 6. Ошибки новичков и безопасность

1. **Сравнивать только цену ВМ.** → К концу месяца счёт в 1,5–2 раза выше ожидаемого из-за дисков, бэкапов, публичных IP, балансировщика и трафика. → Считай полный TCO: compute + storage + egress + бэкап + лицензии + человеко-часы.

2. **Не понизить DNS TTL заранее.** → Половина пользователей после переключения ходит на выключенный сервер, простой растягивается на часы. → TTL 60 за 48 часов до миграции, старый стенд живёт ещё минимум один TTL после переключения.

3. **`rclone sync` вместо `copy` при переезде.** → Удалит файлы на целевой стороне, которых нет в источнике. Первый прогон — только `copy`, `sync` — потом, когда данные уже сверены.

4. **Тащить образ с backing file.** → В новом облаке ВМ не стартует или стартует с чужим базовым слоем. → Всегда `qemu-img info` перед выгрузкой, при наличии `backing file` — конвертировать.

5. **Привязка к proprietary-сервисам.** → Managed-БД, очереди, функции и секреты нельзя перенести, переезд превращается в переписывание приложения. → Держи состояние в переносимых форматах (PostgreSQL-дамп, S3, стандартный Kubernetes), а proprietary — только там, где экономия реально оправдана.

6. **Забыть выключить старое облако.** → Двойная оплата месяц-два, иногда и дольше. → В runbook отдельный пункт «дата вывода из эксплуатации» и напоминание в календаре.

7. **Игнорировать регуляторику.** → Персональные данные уехали в сегмент без нужного уровня защищённости — это уже не техника, а нарушение 152-ФЗ. → До миграции согласовать с ИБ и юристами: категория данных, требуемый УЗ, аттестация ЦОД.

### Безопасность

- **Токены и пароли — только в переменных окружения/Vault, никогда в Git.** В лабораторной все креды учебные (`Lab#2026-vektor`), в бою так нельзя: ключ, попавший в историю коммитов, считается скомпрометированным навсегда, его нужно отзывать, а не «удалять коммитом».
- **Бакеты S3 не должны быть публичными по умолчанию.** Разрешение `anonymous read` на бакет — классическая утечка. Проверяй политику бакета сразу после создания.
- **Security group с `0.0.0.0/0` на 22/3389** — приглашение к брутфорсу; ограничивай по IP и ставь bastion/VPN.
- **Публикация MinIO на 9000 наружу в лабораторной** — небезопасно (HTTP, простой пароль). В лабе порт слушает только localhost и внутреннюю сеть; в продакшене — TLS, отдельный сервисный аккаунт, ротация ключей.
- **Отключение проверок ради «чтобы работало»** (MFA на root-аккаунте, алерты бюджета, шифрование дисков) — типичный shortcut в миграции. В рабочей среде это блокирующее требование, а не пожелание.

## 7. Вопросы на собеседовании

**1. Чем VK Cloud, Selectel и Cloud.ru отличаются по позиционированию и когда что выбрать?**

*Ответ.* Все три — российские IaaS/PaaS-провайдеры на близком технологическом стеке (OpenStack, S3-совместимое хранилище, managed Kubernetes, managed БД), поэтому чисто технически выбор часто сводится к цене и удобству. Разница в фокусе: VK Cloud — продуктовая платформа с сильным PaaS/ML и быстрым стартом для веб- и ML-нагрузок; Selectel исторически вырос из хостинга и колокации, поэтому силён там, где нужен гибрид «своё железо + облако в одном ЦОД, один договор»; Cloud.ru (ex-SberCloud) ориентирован на корпоративный и регулируемый контур — аттестованные сегменты, VDI, AI-сервисы. Выбор делается по трём осям: какие сервисы критичны, какие требования ИБ/152-ФЗ и какая итоговая стоимость владения с учётом трафика и поддержки. Конкретные перечни сервисов и аттестаций надо проверять в актуальной документации [ПРОВЕРИТЬ].

*Что хочет услышать интервьюер:* что ты не путаешь маркетинг с архитектурой, знаешь три оси выбора и не утверждаешь, что «все облака одинаковые».

*Красный флаг:* «Берём самое дешёвое, они всё равно одинаковые» или уверенные цифры цен без оговорки про дату.

**2. Как сравнить стоимость владения между провайдерами, кроме цены ВМ?**

*Ответ.* Считаю полный месячный профиль: ВМ (vCPU+RAM) × 730 часов, диски, снапшоты и бэкапы, объектное хранилище, исходящий трафик, публичные IP, балансировщики, managed-сервисы, реестр образов, плюс поддержка и человеко-часы на эксплуатацию. Отдельно — разовые затраты на переезд (выгрузка данных, время инженера, простой бизнеса). Дальше нормализую: считаю не «₽ за ВМ», а «₽ за 1 vCPU и за 1000 RPS» или «₽ за 1 ТБ данных в месяц», чтобы сравнивать одинаковое с одинаковым. Результат — таблица + скрипт, который можно пересчитать при смене тарифов, а не разовый расчёт в блокноте.

*Что хочет услышать интервьюер:* методику, нормализацию и понимание, что egress и storage часто перевешивают compute.

*Красный флаг:* «Посмотрел цену калькулятора и всё понятно» — без трафика, бэкапов и трудозатрат.

**3. Как мигрировать 20 ВМ и 5 ТБ данных из одного облака в другое с минимальным простоем?**

*Ответ.* Шесть этапов. Инвентаризация (что живое, что можно выключить, карта зависимостей). Целевая архитектура и Terraform для нового облака — инфраструктура поднимается кодом, а не руками. Подготовка: выгрузка образов через API, проверка `qemu-img info` на backing file, понижение DNS TTL до 60 за 48 часов, ключи и секреты в новом хранилище. Данные: `rclone copy --checksum` или rsync в несколько потоков, первый прогон за неделю до окна (основной объём), второй — инкрементальный в окне. Пилот на 1–2 некритичных ВМ, проверка производительности и сети. Переключение: остановка приложения → финальная досинхронизация → переключение DNS → smoke-тесты. Старый стенд живёт минимум один TTL после переключения как план отката, гасится по календарю. Для 5 ТБ отдельно считаю стоимость выгрузки и время при канале: 5 ТБ при 100 Мбит/с — это ~5 суток непрерывной передачи, что часто решает вопрос в пользу «пересоздать из образа, а не копировать».

*Что хочет услышать интервьюер:* этапность, TTL, досинхронизация, план отката и арифметику канала.

*Красный флаг:* «Просто сделаю снапшот и перенесу» — без DNS, без времени на трафик, без отката.

**4. Что такое vendor lock-in и как его снижать?**

*Ответ.* Lock-in — зависимость от уникальных API/форматов провайдера, из-за которой переезд стоит дороже, чем терпеть текущие условия и цены. Проявляется в proprietary managed-БД, очередях, serverless-функциях, форматах образов, IAM-моделях и IaC-провайдерах. Снижаю так: состояние приложения — в переносимых форматах (PostgreSQL-дамп, S3-совместимое хранилище, стандартный Kubernetes-манифест); инфраструктура — в Terraform с минимальной провайдер-спецификой и слоем переменных; уникальные сервисы — только там, где экономия измерима; регулярно проверяю «а сможем ли выгрузить» на практике, а не в теории — например, раз в квартал делаю тестовое восстановление бэкапа в другом окружении.

*Что хочет услышать интервьюер:* понимание, что lock-in — это экономика, а не религия, и наличие конкретных практик проверки переносимости.

*Красный флаг:* «Мы берём только open-source, поэтому lock-in нет» — открытый код сам по себе не отменяет привязку к API и процессам.

**5. Какие требования 152-ФЗ и регуляторики влияют на выбор облака?**

*Ответ.* Если обрабатываются персональные данные, нужно определить категорию ПДн и требуемый уровень защищённости (УЗ-1…УЗ-4 по постановлению Правительства № 1119), затем проверить, что у провайдера есть сегмент с подходящей аттестацией и что в договоре это зафиксировано. Дальше — где физически лежат данные (ЦОД в РФ), кто имеет доступ, как организованы бэкапы и журналирование, есть ли СЗИ в составе услуги. Плюс организационное: модель ответственности (провайдер отвечает за физику и платформу, за данные и доступы — ты), уведомление Роскомнадзора, сроки хранения. Всё это согласуется до миграции, а не после.

*Что хочет услышать интервьюер:* что ты понимаешь границу ответственности и не берёшься сам решать юридические вопросы, а знаешь, кого подключать.

*Красный флаг:* «Мы просто зашифруем, и 152-ФЗ не применяется» — это не отменяет требований закона.
