## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Облако — это HTTP API, к которому прикрутили железо и биллинг.** Всё остальное — обёртки. Консоль в браузере, `aws`/`gcloud`/`az`/`yc`, Terraform, Ansible-модули, Kubernetes-контроллеры — все они в конечном счёте делают подписанные HTTPS-запросы на 443-й порт к REST API провайдера. Отсюда важное следствие: **если вы понимаете, что делает API-метод, вы понимаете сервис**, чем бы он ни назывался в конкретном облаке.

```text
                 Консоль (браузер)   CLI (aws/gcloud/az/yc)   Terraform/Pulumi
                        \                    |                       /
                         \                   v                      /
                          +-------->  HTTPS 443, REST API  <-------+
                                            |
                                            v
                          +-------------------------------------+
                          |  Регион (например, eu-central-1)    |
                          |   зона a     зона b     зона c      |  <- разные ЦОДы
                          +-------------------------------------+
                                            |
                     ВМ, диски, сети, бакеты, БД, балансировщики
```

Регион — географическая площадка (Франкфурт, Москва). Зона доступности (Availability Zone) — изолированный ЦОД внутри региона со своим питанием и сетевым оборудованием. Внутри региона задержка между зонами обычно около 1–2 мс, между регионами — десятки миллисекунд. Отсюда правило: отказоустойчивость делается **в зонах**, а не в регионах; регионы нужны для географии пользователей и юридических требований.

Разные облака называют одно и то же по-разному:

| | AWS | Azure | GCP | Yandex Cloud |
|---|---|---|---|---|
| Регион | `eu-central-1` | `germanywestcentral` | `europe-west3` | `ru-central1` |
| Зона | `eu-central-1a` | зоны внутри региона (AZ-01…) | `europe-west3-a` | `ru-central1-a`, `-b`, `-d` `[ПРОВЕРИТЬ актуальный список зон]` |

**Иерархия ресурсов.** Это второй по важности слой после API — именно здесь новички путаются при миграции, потому что границы аккаунтов, проектов и подписок не совпадают:

```text
AWS:     Account  ── Region ── VPC / EC2 / S3-бакет / RDS
Azure:   Tenant (Entra ID) ── Subscription ── Resource Group ── Resource
GCP:     Organization ── Folder ── Project ── Resource
Yandex:  Organization ── Cloud ── Folder ── Resource
```

В AWS границей биллинга и изоляции служит **аккаунт**; в Azure — **подписка**, а логическая группировка ресурсов — **resource group**; в GCP и Yandex — **проект/каталог (folder)**. Практический вывод: то, что в AWS делают отдельным аккаунтом (dev/prod), в Yandex делают отдельным каталогом или облаком.

**Идентичность (IAM).** Во всех облаках модель похожа: есть субъект (пользователь, сервисный аккаунт, роль) и есть политика — список разрешённых действий над ресурсом. Отличаются детали: в AWS политики — JSON, привязанные к пользователю/группе/роли, с приоритетом явного запрета (`Deny` всегда побеждает); в Azure роли RBAC назначаются на область (подписка → группа ресурсов → ресурс), а аутентификация живёт в отдельном Entra ID; в GCP роль — это набор permissions, который назначается участнику на ресурс.

**Как ВМ получает права без пароля.** Ключевой механизм, который отличает облако от «просто арендованной виртуалки»: у каждой ВМ есть link-local адрес `169.254.169.254` — metadata service. Приложение спрашивает его «кто я», и получает временные креды. AWS требует IMDSv2 (сначала PUT-запрос за токеном), GCP — заголовок `Metadata-Flavor: Google`, Azure — заголовок `Metadata: true`. В Yandex Cloud есть тот же механизм для сервисных аккаунтов. Именно поэтому в правильной архитектуре в коде **нет статических ключей**.

**Таксономия сервисов.** Любое облако устроено одинаково, меняются только названия:

| Категория | AWS | Azure | GCP | Yandex Cloud | VK Cloud / Selectel |
|---|---|---|---|---|---|
| Виртуальные машины | EC2 | Virtual Machines | Compute Engine | Compute | Cloud Servers / Облачные серверы |
| Объектное хранилище (S3) | S3 | Blob Storage | Cloud Storage | Object Storage | Object Storage |
| Блочный диск | EBS | Managed Disks | Persistent Disk | Disks | Диски |
| Сеть (VPC) | VPC | VNet | VPC | VPC | Cloud Networks / Приватные сети |
| Managed Kubernetes | EKS | AKS | GKE | Managed Service for Kubernetes | Cloud Containers / Managed Kubernetes |
| Управляемые БД | RDS | Azure SQL, Flexible Server | Cloud SQL | Managed Service for PostgreSQL/MySQL | Databases |
| Serverless-функции | Lambda | Functions | Cloud Functions | Cloud Functions | `[ПРОВЕРИТЬ набор в VK/Selectel]` |
| Реестр образов | ECR | ACR | Artifact Registry | Container Registry | Container Registry |
| Балансировщик | ALB/NLB | Load Balancer / App Gateway | Cloud Load Balancing | ALB/NLB | LB |
| Секреты и ключи | Secrets Manager / KMS | Key Vault | Secret Manager / KMS | Lockbox / KMS | `[ПРОВЕРИТЬ]` |
| Мониторинг | CloudWatch | Monitor | Cloud Monitoring | Monitoring | Мониторинг |

Сравнение российских провайдеров между собой — в уроке 70, сети в облаке — в уроке 72, S3-совместимые хранилища — в уроке 73. Здесь важен сам навык «перевести категорию в название».

**Одна строка про рынок РФ.** Прямой аккаунт AWS/Azure/GCP у российской компании в 2026 году, мягко говоря, проблематичен из-за ограничений и платежей — поэтому учиться на них удобнее через документацию и локальные эмуляторы, а руками строить в Yandex Cloud / VK Cloud / Selectel / Cloud.ru. Легальный путь для реального проекта — российский провайдер.

## 3. Аналогия из жизни

Облако — это бизнес-центр, где вы арендуете офисы.

**AWS** — старейший и огромнейший БЦ города: 300 корпусов, 200+ услуг, включая свою химчистку и типографию, но навигация по нему — отдельный навык, а на каждом шагу платный турникет. **Azure** — БЦ, принадлежащий компании, которая уже держит у вас бухгалтерию и кадровый учёт (Active Directory, Exchange), поэтому переезд туда для «виндового» бизнеса — просто перейти в соседнее здание по внутреннему переходу. **GCP** — БЦ с лучшими лифтами и аналитикой: туда идут те, кто пришёл считать данные и запускать Kubernetes.

**Регион** — город, где стоит БЦ. **Зона доступности** — отдельное здание в этом городе, не подключённое к соседнему одним кабелем: если в здании «a» пожар, здание «b» продолжает работать, а вот если землетрясение на весь город — встанут все. **IAM** — пропускная система: у вас есть пропуск (identity), в нём написано, в какие двери можно входить (policy), а если дверь заперта явным запретом, никакой начальник вас туда не проведёт. **Роль** — временный гостевой пропуск на два часа, который охранник на ресепшене (STS) выдаёт после проверки, кто вы такой. **Metadata service** — внутренний телефон в офисе, по которому вы звоните на ресепшен и спрашиваете свой гостевой пропуск, не храня его на столе.

Аналогия перестаёт работать вот где: в реальном БЦ арендодатель не заходит в ваш офис и не чинит вашу мебель, а в облаке ответственность разделена — провайдер отвечает за здание, а за то, что вы оставили дверь бакета открытой на улицу, отвечаете вы сами.

## 4. Практика и команды

Ниже — команды трёх гиперскейлеров и Yandex Cloud. Смотрите не на конкретные слова, а на **форму**: у всех CLI одинаковый скелет `группа ресурсов → действие → флаги → формат вывода`.

### 1. Установка AWS CLI v2 (Ubuntu)

```bash
curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o awscliv2.zip
unzip awscliv2.zip
sudo ./aws/install
aws --version
```

`aws --version` → `aws-cli/2.x.x Python/3.x Linux/...`. Смотрите на **major-версию**: пакет `awscli` в apt может быть v1, и синтаксис местами другой. v2 ставится официальным установщиком.

### 2. Профили и конфигурация

```bash
aws configure --profile vektor-local
# AWS Access Key ID: test
# AWS Secret Access Key: test
# Default region name: us-east-1
# Default output format: json

aws configure list --profile vektor-local
```

Лежит в `~/.aws/credentials` (ключи) и `~/.aws/config` (регион, формат). `configure list` показывает, откуда взято каждое значение: env-переменная, профиль или IMDS. **Что смотреть:** если в колонке `source` стоит `env`, то переменные окружения перебивают профиль — классическая причина «почему команда ушла не в тот аккаунт».

### 3. Проверка «кто я»

```bash
aws --profile vektor-local \
    --endpoint-url http://10.10.10.30:4566 \
    sts get-caller-identity
```

Ожидаемый вывод:

```json
{"UserId": "AKIAIOSFODNN7EXAMPLE", "Account": "000000000000", "Arn": "arn:aws:iam::000000000000:user/deploy-bot"}
```

Разбираем ARN: `arn:aws:iam::<аккаунт>:<тип>/<имя>`. Это универсальный идентификатор любого ресурса в AWS. `--endpoint-url` подменяет адрес API — именно так работают локальные эмуляторы. **Что смотреть:** `Account` и `Arn` — если они не те, все дальнейшие команды уйдут не туда.

### 4. S3: создание бакета и объекта

```bash
aws --profile vektor-local --endpoint-url http://10.10.10.30:4566 \
    s3api create-bucket --bucket vektor-docs

echo "Инструкция для поставщика" > README.md
aws --profile vektor-local --endpoint-url http://10.10.10.30:4566 \
    s3api put-object --bucket vektor-docs --key docs/README.md --body README.md

aws --profile vektor-local --endpoint-url http://10.10.10.30:4566 \
    s3api list-objects-v2 --bucket vektor-docs --query 'Contents[].Key' --output text
```

Имена бакетов: только строчные буквы, цифры и дефис, 3–63 символа, глобально уникальны. В регионе, отличном от `us-east-1`, нужно добавлять `--create-bucket-configuration LocationConstraint=<регион>` `[ПРОВЕРИТЬ поведение конкретного эмулятора]`. `--query` — это JMESPath-фильтр, `--output` — `json|text|table`.

### 5. Подписанная ссылка (presigned URL)

```bash
aws --profile vektor-local --endpoint-url http://10.10.10.30:4566 \
    s3 presign s3://vektor-docs/docs/README.md --expires-in 300
```

Выдаёт ссылку вида `http://10.10.10.30:4566/vektor-docs/docs/README.md?X-Amz-Algorithm=...&X-Amz-Expires=300&X-Amz-Signature=...`. Работает без учётной записи, но живёт ровно 300 секунд и подписана под конкретный хост. Это ровно то, что просил поставщик в тикете, — и ровно то, что ломается чаще всего (см. раздел 5).

### 6. «Виртуалки» и теги

```bash
aws --profile vektor-local --endpoint-url http://10.10.10.30:4566 \
    ec2 run-instances --image-id ami-12345678 --instance-type t3.micro --count 1 \
    --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=devops-071}]'

aws --profile vektor-local --endpoint-url http://10.10.10.30:4566 \
    ec2 describe-instances \
    --query 'Reservations[].Instances[].{ID:InstanceId,State:State.Name,Type:InstanceType}' \
    --output table
```

Теги — не украшение: на них строится FinOps (урок 76) и разграничение доступа по условиям в политиках.

### 7. IAM: пользователь и политика

```bash
aws --profile vektor-local --endpoint-url http://10.10.10.30:4566 \
    iam create-user --user-name deploy-bot

aws --profile vektor-local --endpoint-url http://10.10.10.30:4566 \
    iam attach-user-policy --user-name deploy-bot \
    --policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess

aws --profile vektor-local --endpoint-url http://10.10.10.30:4566 \
    iam list-attached-user-policies --user-name deploy-bot
```

Это учебный пример «как НЕ надо». В реальной работе CI/CD получает не IAM-пользователя с ключами, а роль: для GitLab — OIDC-федерация, для пода в Kubernetes — IRSA/Workload Identity.

### 8. GCP: те же действия, другой CLI

```bash
gcloud auth list
gcloud config set project vektor-lab
gcloud compute instances list --format="table(name,zone,status)"
gcloud storage ls
```

`--format` — аналог `--query` + `--output`. Обратите внимание: проект — это граница, и почти любая команда требует, чтобы активный проект был задан.

### 9. Azure: подписки и группы ресурсов

```bash
az login
az account show --output table
az group list --output table
az vm list -d -o table
```

`-d` = `--show-details` (добавляет IP и питание). Ключевое отличие: перед созданием ВМ вы обязаны указать **resource group** — в Azure почти нет «просто ресурсов», всё лежит в группе.

### 10. Yandex Cloud: то же самое по-русски

```bash
yc config list
yc compute instance list
yc vpc subnet list
yc iam service-account list
```

`yc config list` покажет `cloud-id`, `folder-id`, `zone` — это и есть иерархия из раздела 2.

### 11. IaC: сравнение провайдеров Terraform

```hcl
provider "aws" {
  region = "eu-central-1"
}

resource "aws_s3_bucket" "docs" {
  bucket = "vektor-docs"
}
```

```hcl
provider "yandex" {
  cloud_id  = var.cloud_id
  folder_id = var.folder_id
  zone      = "ru-central1-a"
}

resource "yandex_storage_bucket" "docs" {
  bucket = "vektor-docs"
}
```

Структура одинаковая, меняются провайдер и имена ресурсов. Именно поэтому знание AWS-документации переносится: вы ищете не «как в AWS», а «какой ресурс в провайдере соответствует категории».

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

Смысл лабораторной: **потрогать AWS API без аккаунта AWS** (на локальном эмуляторе LocalStack), сравнить CLI трёх облаков и оформить матрицу соответствия сервисов как документ в Git — чтобы в следующий раз отвечать на такие тикеты за пять минут, а не за день.

### Предусловия

- **UBU01** (10.10.10.30, Ubuntu Server 24.04, SSH) — доступен, есть интернет через NAT VMnet8, установлен Docker (главы по контейнерам). Если Docker нет — поставьте `sudo apt update && sudo apt install -y docker.io` и добавьте себя в группу `docker`.
- **GIT01** (10.10.10.50, GitLab CE) — доступен, есть ваша учётная запись и право создавать проекты.
- **WEB01, MON01** — не нужны. **Windows-часть стенда не нужна вообще.**
- Аккаунта в AWS/Azure/GCP у нас нет и не будет — и это нормально: для лабы хватит эмулятора. Реальные `yc`-команды выполняйте только если завели аккаунт в уроке 69.

### Снапшот

В VMware Workstation: правый клик по ВМ → **Snapshot → Take Snapshot**, имя `before-devops-071`. Сделать на **UBU01** и **GIT01**.

Если хотите из терминала хоста:

```bash
vmrun -T ws snapshot "/path/to/UBU01.vmx" before-devops-071
vmrun -T ws snapshot "/path/to/GIT01.vmx" before-devops-071
```

### Шаги

1. **UBU01.** Поднимаем эмулятор AWS API:
   ```bash
   docker run -d --name localstack -p 4566:4566 \
     -e SERVICES=s3,iam,sts,ec2 \

   ```
   Ожидаемо: контейнер в состоянии `Up`. `SERVICES` ограничивает набор сервисов, чтобы контейнер не ел память `[ПРОВЕРИТЬ: в новых версиях список сервисов можно не ограничивать]`. Если Docker Hub недоступен из вашей сети — настройте зеркало реестра в `/etc/docker/daemon.json` или возьмите образ из другого публичного реестра `[ПРОВЕРИТЬ актуальность зеркала]`.

2. **UBU01.** Проверяем, что API жив:
   ```bash
   curl -s http://10.10.10.30:4566/_localstack/health
   ```
   Ожидаемо: JSON, где в `services` у `s3`, `iam`, `sts` стоит `available` или `running`.

3. **UBU01.** Ставим AWS CLI v2 командами из раздела 4 (пункт 1) и проверяем `aws --version` — должно быть `aws-cli/2.x`.

4. **UBU01.** Создаём профиль `vektor-local` (пункт 2 раздела 4). Ключи — любые непустые строки, регион `us-east-1`. Ожидаемо: `aws configure list` показывает `access_key ****` и `region us-east-1`.

5. **UBU01.** `aws ... sts get-caller-identity`. Ожидаемо: JSON с `Account: 000000000000` и ARN. Запишите ARN в черновик — он пойдёт в документ.

6. **UBU01.** Создаём бакет `vektor-docs`, кладём туда `docs/README.md`, выводим список ключей (пункт 4). Ожидаемо: `docs/README.md` в выводе `list-objects-v2`.

7. **UBU01.** Генерируем presigned URL на 300 секунд (пункт 5) и открываем его `curl -v "<url>"`. Ожидаемо: HTTP 200 и текст файла. Затем повторяем тот же `curl` через 6 минут — ожидаемо 403 `AccessDenied` с сообщением про истёкший запрос.

**Как воспроизвести намеренно (UBU01):**

```bash

URL=$(aws --profile vektor-local --endpoint-url http://10.10.10.30:4566 \
  s3 presign s3://vektor-docs/docs/README.md --expires-in 60)

curl -i "$URL"          # ожидаем 403 AccessDenied, "Request has expired"

#    (именно так и было в лабе — endpoint 10.10.10.30 доступен только из VMnet8)
```

**Диагностика по порядку:**

1. Читаем **текст** ошибки, а не только код. `AccessDenied` + «Request has expired» → истёк TTL. `SignatureDoesNotMatch` → не совпал секрет или хост в подписи. `RequestTimeTooSkewed` → разъехались часы. Таймаут/`Connection refused` → проблема сети, а не прав.
2. Проверяем срок: когда ссылка выдана и какой был `--expires-in`.
3. Проверяем, **откуда** её открывают. Наша ссылка ведёт на `http://10.10.10.30:4566` — это адрес в сети VMnet8. Поставщик снаружи туда не попадёт никогда, даже со свежей ссылкой.
4. Проверяем часы на UBU01: `timedatectl` — при расхождении более чем на несколько минут подпись ломается.
5. Проверяем, что объект на месте: `aws ... s3api head-object --bucket vektor-docs --key docs/README.md`.

**Решение:** перегенерировать ссылку с адекватным TTL (например, 24 часа), а главное — честно сказать, что ссылка на внутренний адрес наружу не работает, и выдать файл через сервис с публичным адресом (в нашем стенде это делает WEB01 в DMZ на уровне L2, урок 72). В реальном облаке — presigned URL на публичный endpoint Object Storage.

## 6. Ошибки новичков и безопасность

1. **Искать сервис по имени, а не по категории.** Ищут «Lambda» в Yandex Cloud, не находят и делают вывод «там нет serverless». → Правильно: искать категорию («функции как услуга»), а потом название у провайдера.
2. **Копировать примеры из документации AWS в чужое облако.** Туториалы подразумевают `us-east-1` и реальный аккаунт. → Правильно: всегда проверять, куда указывает endpoint и какой профиль активен (`aws configure list`, `yc config list`).
3. **Использовать IAM-пользователя с постоянными ключами для автоматизации.** Ключ течёт через Git, логи CI, образы. → Правильно: роли и короткоживущие креды (OIDC, instance profile, managed identity, service account).
4. **Работать из root/owner-аккаунта.** Одна ошибка — и снесён весь биллинг-аккаунт. → Правильно: root только для создания аккаунта и включения MFA, дальше — отдельный администратор.
5. **Считать, что «облако само настроит безопасность».** Публичный бакет — самая массовая утечка десятилетия. → Правильно: Block Public Access по умолчанию, шифрование, версионирование, политики как код (урок 65).
6. **Игнорировать зоны доступности.** Всё в одной зоне, «чтобы дешевле». → Правильно: минимум две зоны дляprod-нагрузки, а БД — multi-AZ.
7. **Тыкать в консоль вместо IaC.** Конфигурация дрейфует, никто не помнит, что менялось. → Правильно: изменения через Terraform/Pulumi в Git, консоль — только для чтения.
8. **Тестировать на «почти проде».** В облаке легко создать ресурс, который начнёт тратить деньги молча (NAT Gateway, снапшоты, публичный IP). → Правильно: песочница/отдельный каталог, бюджеты и алерты (урок 76).

**Безопасность (отдельно).** В этой лабораторной мы сознательно работаем с фейковыми ключами `test/test` и эмулятором — это безопасно и не тратит денег, но приучает к плохой привычке: **ключи прямо в команде и в скрипте**. В боевой среде так нельзя: секреты — только из хранилища (Vault, SOPS, Lockbox, Key Vault, Secrets Manager, урок 66), в Git — ни одного ключа, даже «временного». Второе: presigned URL — это фактически пароль в адресной строке, он попадает в логи прокси, браузера и мессенджеров; выдавайте минимальный TTL и не пересылайте ссылки в открытых каналах. Третье: эмулятор LocalStack не является продакшн-средой и не проверяет вашу безопасность — он просто отвечает «ок» на любые креды; не переносите его настройки в реальные облака.

## 7. Вопросы на собеседовании

**1. Чем отличаются модели IAM в AWS, Azure и GCP? Зачем нужны роли, если есть пользователи?**

Ответ: во всех трёх модель «субъект + разрешения на ресурс», но по-разному устроена иерархия. AWS: аккаунт как граница, политики в JSON крепятся к пользователям, группам и ролям, явный `Deny` всегда побеждает; роли дают временные креды через STS и именно поэтому предпочтительны — постоянных ключей в коде быть не должно. Azure: аутентификация в Entra ID отдельно от авторизации; RBAC-роли назначаются на область — группа управления, подписка, resource group, ресурс — и наследуются вниз; для сервисов используются managed identities. GCP: роли (наборы permissions) назначаются участникам на конкретный ресурс в иерархии organization → folder → project; сервисные аккаунты можно олицетворять, а для подов в GKE работает Workload Identity. Общий принцип — least privilege и отсутствие статических ключей.

*Что хочет услышать интервьюер:* что вы понимаете разницу между аутентификацией и авторизацией, знаете про временные креды и не тащите ключи в код.
*Красный флаг:* «IAM — это просто список пользователей с паролями».

**2. У нас сервис на EC2 + S3 + RDS. Что из этого есть в Yandex Cloud и что изменится при миграции?**

Ответ: EC2 → Compute (образы через Packer/Cloud-Init, урок 63), S3 → Object Storage (S3-совместимый API, но другой endpoint и другая схема подписи-совместимости — проверять на клиентах), RDS → Managed Service for PostgreSQL/MySQL. Меняется: IAM (вместо ARN — идентификаторы ресурсов и роли, вместо instance profile — сервисный аккаунт ВМ), сеть (VPC и подсети создаются явно, security groups есть, но набор правил и лимитов другой), часть инстанс-типов отсутствует, цены на egress и резервные копии считаются иначе. Terraform-код придётся переписать на другой провайдер — структура та же, ресурсы другие. Технически проще всего мигрировать stateless-часть: собрать golden image, поднять в новом облаке, переключить DNS.

*Что хочет услышать интервьюер:* что вы не верите в «переехали одной кнопкой» и называете конкретные сцепки — IAM, сеть, IaC, биллинг.
*Красный флаг:* «Всё один в один, просто меняем провайдера».

**3. Что такое регион и зона доступности и как это влияет на отказоустойчивость?**

Ответ: регион — географическая площадка, зона — изолированный ЦОД внутри региона со своим электричеством и сетью. Внутри региона между зонами единицы миллисекунд, между регионами — десятки. Поэтому отказоустойчивость строится на зонах: минимум две, балансировщик распределяет трафик, БД — multi-AZ с автоматическим failover, объектное хранилище реплицируется провайдером. Регионы нужны для приближения к пользователям и для юридических требований (данные в РФ), плюс для сценариев disaster recovery, но это уже другой бюджет и другая сложность.

*Что хочет услышать интервьюер:* понимание, что «зона» — это физическая единица отказа, и что multi-AZ и multi-region решают разные задачи.
*Красный флаг:* «Регион и зона — это одно и то же, просто разные названия».

**4. Как приложение внутри виртуалки получает доступ к API облака, не храня ключей?**

Ответ: через metadata service по адресу `169.254.169.254`. ВМ обращается к нему и получает временные креды роли, привязанной к инстансу. В AWS это instance profile + IMDSv2 (сначала PUT за токеном, потом GET); в GCP — сервисный аккаунт, привязанный к инстансу, с обязательным заголовком `Metadata-Flavor: Google`; в Azure — managed identity с заголовком `Metadata: true`; в Kubernetes-мире — IRSA в EKS или Workload Identity в GKE, где под получает свою роль через OIDC. Плюс: креды живут минуты и ротируются автоматически, утечь из репозитория им просто негде.

*Что хочет услышать интервьюер:* что вы знаете механизм, а не только слово «роль», и понимаете, зачем нужен IMDSv2.
*Красный флаг:* «Положим ключи в переменные окружения systemd-юнита, так же проще».

**5. Как вы будете разбираться с сервисом в незнакомом облаке, который видите впервые?**

Ответ: сначала определяю категорию (это compute, storage, очередь, managed-сервис?), потом читаю в документации четыре обязательных раздела: «What is X» (что это), «Quotas / Limits» (что упрётся первым), «Pricing» (что будет стоить денег) и «IAM permissions required» (какие права нужны). Дальше смотрю API Reference, чтобы понять форму ресурса, и проверяю, поддерживается ли он в Terraform-провайдере. Потом делаю минимальный POC в песочнице — руками через CLI, чтобы увидеть реальные ответы API, и только после этого переписываю в Terraform. Если сервис — аналог известного, я всё равно сверяю ограничения: у «похожих» сервисов они отличаются в разы.

*Что хочет услышать интервьюер:* системный подход «документация → лимиты → цена → права → POC → IaC» вместо «погуглю и скопирую».
*Красный флаг:* «Найду статью на Хабре и повторю команды».
