## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Стек и порты.** Модель OSI вам нужна не для экзамена, а как карта диагностики. Снизу: L1/L2 (Ethernet, MAC, ARP) → **L3 IP** (адресация, маршрут) → **L4 TCP/UDP** (порты, соединения) → **L5–L7** (DNS, TLS, HTTP). На практике в DevOps 90% разборов — это L3+L4+L7. Ключевые порты: 22 SSH, 53 DNS (UDP и TCP), 80 HTTP, 443 HTTPS, 3000/5000/8080 — приложения, 6443 — API Kubernetes, 5432 PostgreSQL, 6379 Redis.

**TCP.** Соединение устанавливается тремя пакетами: `SYN → SYN-ACK → ACK`. Состояния важны при диагностике: `LISTEN` (порт открыт, ждём), `SYN-SENT` (клиент постучал, ответа нет — обычно firewall или маршрут), `ESTABLISHED` (работает), `TIME-WAIT` (60 секунд на Linux после закрытия со стороны инициатора), `CLOSE-WAIT` (приложение не вызвало `close()` — пахнет утечкой дескрипторов). UDP соединений не имеет: отправил датаграмму и молись. Именно на UDP работают DNS и **QUIC** (основа HTTP/3).

**DNS.** Иерархия: корневые серверы → зона `.lab` → зона `corp.vektor.lab`. Клиент задаёт вопрос своему **рекурсивному** резолверу (у нас — `systemd-resolved` на UBU01 или DNS на DC01), тот идёт по цепочке и кэширует ответ на время **TTL**. Основные типы записей: `A` (IPv4), `AAAA` (IPv6), `CNAME` (псевдоним), `MX` (почта), `TXT` (SPF/DKIM/верификации), `NS`/`SOA` (делегирование зоны). В Kubernetes отдельный слой — CoreDNS: сервис получает имя `<service>.<namespace>.svc.cluster.local`, а TTL там маленькие (у CoreDNS по умолчанию 5 секунд [ПРОВЕРИТЬ в вашей версии]), и это постоянная причина «подвисших» соединений при деплое.

**HTTP/1.1 vs HTTP/2 vs HTTP/3.** HTTP/1.1 — текстовый, одно соединение = один запрос за раз (keep-alive помогает, но голова очереди блокирует), отсюда костыли вроде доменных шардов и спрайтов. HTTP/2 — бинарный, **мультиплексирование** потоков в одном TCP-соединении + сжатие заголовков HPACK, но потеря одного TCP-пакета блокирует **все** потоки (TCP head-of-line blocking). HTTP/3 — тот же мультиплексированный HTTP, но поверх **QUIC (UDP 443)**: потери пакетов блокируют только свой поток, есть 0-RTT при повторном подключении. Версия выбирается по **ALPN** в TLS-хендшейке (`h2`, `http/1.1`) или по QUIC.

**TLS.** TLS 1.3 (RFC 8446) укладывает хендшейк в 1 RTT (0-RTT при resumption), TLS 1.2 — в 2 RTT. В хендшейке клиент передаёт **SNI** — имя сайта открытым текстом, чтобы сервер отдал нужный сертификат с общего IP. Дальше сервер присылает цепочку сертификатов, клиент проверяет подпись CA, срок и SAN. Глубоко PKI разберём в уроке 11 — здесь нам хватит умения увидеть хендшейк.

**NAT и маршрутизация.** Маршрутизатор выбирает маршрут по **longest prefix match** (самый специфичный префикс выигрывает), default-route `0.0.0.0/0` — последний вариант. NAT бывает двух видов: **SNAT/masquerade** (подменяем源 адрес: так офис выходит в интернет и так в логах nginx появляется IP шлюза вместо клиентского) и **DNAT** (подменяем адрес назначения — на этом стоят port forwarding и Kubernetes Services через iptables/IPVS). Таблица **conntrack** помнит соединения и делает обратную трансформацию. Проблемы от NAT: сломанный лог-анализ, hairpin-доступ, обрыв долгих соединений при истечении conntrack-таймаута.

```text
 UBU01 10.10.10.30            GW01                       WEB01 10.10.20.10
+----------------+      +------------------+        +---------------------+
| app/curl/dig   |      | eth0 10.10.10.3  |        | eth0 10.10.20.10    |
|                |----->| eth1 10.10.20.1  |------->| nginx :80           |
| route: default |      | ip_forward = 1   |        | ss -tlnp -> :80     |
|  via 10.10.10.2|      | nftables filter  |        | access.log          |
+----------------+      | conntrack        |        +---------------------+
   VMnet8 NAT            +------------------+            VMnet10 (DMZ)
   10.10.10.0/24           маршрутизация                 10.10.20.0/24
                          10.10.10.0/24 <-> 10.10.20.0/24
```

## 3. Аналогия из жизни

«Вектор» — логистическая компания, и сеть устроена как её доставка. **DNS** — это справочник адресов: вы знаете «склад на Ленинградке», а не координаты; справочник может быть устаревшим (TTL истёк — звоните заново). **IP-маршрутизация** — сортировочный центр: у посылки есть конечный адрес, и каждый узел решает, на какую машину её перекинуть (самый точный маршрут приоритетнее общего). **TCP** — курьер с подписью за получение: не отдал — везём снова, поэтому доставка гарантирована, но медленнее. **UDP** — листовки в почтовые ящики: быстро, дёшево, никто не подтверждает получение. **NAT** — ресепшн: наружу все письма уходят с одного адреса компании, а внутри ресепшн по журналу (conntrack) помнит, чья это была посылка. **HTTP/2** — один большой грузовик, который повёз сразу 50 заказов: эффективно, но если грузовик встал в пробку — встали все 50. **HTTP/3** — 50 отдельных курьеров на самокатах: один застрял, остальные едут.

Где аналогия ломается: посылки нельзя терять безнаказанно и переставлять местами, а IP-пакеты теряются, дублируются и приходят не по порядку — и это норма, всю работу по восстановлению порядка делает TCP.

## 4. Практика и команды

**1. Куда уйдёт пакет — маршрут.**
```bash
ip -br a                       # краткий список интерфейсов и адресов
ip route                       # таблица маршрутов
ip route get 10.10.20.10       # какой маршрут выберет ядро именно для этого IP
```
```text
$ ip route get 10.10.20.10
10.10.20.10 via 10.10.10.3 dev ens33 src 10.10.10.30 uid 1000
    cache
```
Смотрим: `via` — следующий хоп (GW01), `dev` — интерфейс, `src` — адрес источника. Нет `via` — значит доставка напрямую в своей подсети. Если в `ip route` нет строки на 10.10.20.0/24 и нет default — пакет уйдёт в никуда, и это первая причина «не открывается».

**2. Проверка L3 простыми средствами.**
```bash
ping -c 3 10.10.20.10
tracepath -n 10.10.20.10      # apt install iputils-tracepath, если нет
mtr -n -c 5 10.10.20.10       # apt install mtr-tiny
```
`mtr` удобнее traceroute: показывает потери по хопам в реальном времени. Если первый же хоп теряет 100% — проблема на шлюзе/маршруте, до приложения дело не дошло.

**3. Кто слушает порт и кто уже подключён — `ss`.**
```bash
ss -tulpn                     # t=tcp u=udp l=listening p=процесс n=без резолва
ss -tan state established     # только установленные
ss -tnp '( dport = :80 )'     # все соединения на порт 80
ss -s                         # сводка: сколько сокетов в каком состоянии
```
```text
$ ss -tulpn
Netid State  Local Address:Port  Process
udp   UNCONN 127.0.0.54:53       users:(("systemd-resolve",pid=612,fd=18))
tcp   LISTEN 0.0.0.0:22          users:(("sshd",pid=701,fd=3))
tcp   LISTEN 127.0.0.53:53       users:(("systemd-resolve",pid=612,fd=13))
```
Ключевое: `0.0.0.0:80` — слушаем все адреса, `127.0.0.1:80` — только локально (снаружи не достучитесь, классическая ошибка в `bind`). Заменил `netstat` — он устарел и медленнее на больших таблицах.

**4. Проверка L4 в одну команду.**
```bash
nc -zv 10.10.20.10 80         # -z не передавать данные, -v рассказать
nc -zvu 10.10.10.30 53        # то же для UDP
```
`Connection to 10.10.20.10 80 port [tcp/http] succeeded!` — TCP-слой жив. `Connection refused` — дошли, но никто не слушает (или слушает на loopback). `Timed out` — пакет едят firewall/маршрут/NAT.

**5. DNS-запросы — `dig`.**
```bash
dig +short web01.corp.vektor.lab          # только ответ
dig +noall +answer web01.corp.vektor.lab  # ответ с TTL и типом
dig @10.10.10.30 web01.corp.vektor.lab A  # спросить конкретный сервер
dig -x 10.10.20.10                        # обратная зона PTR
dig +trace example.com                    # пройти всю цепочку от корня (нужен интернет)
```
```text
$ dig +noall +answer web01.corp.vektor.lab
web01.corp.vektor.lab.  0  IN  A  10.10.20.10
```
Смотрим на флаг `aa` в полном выводе (авторитетный ответ или кэш), на `status: NXDOMAIN` (имени нет), `SERVFAIL` (сервер сломан) и на TTL: `0` — локальная запись резолвера, кэшировать бесполезно.

**6. Как настроен резолвинг на хосте.**
```bash
resolvectl status            # что реально используется как DNS на каждом интерфейсе
resolvectl query web01.corp.vektor.lab
cat /etc/resolv.conf         # на Ubuntu там обычно 127.0.0.53 — заглушка systemd-resolved
```
Если `resolvectl query` отвечает, а `ping` по имени — нет, проблема в nsswitch/приложении, а не в DNS.

**7. HTTP-запрос с диагностикой — `curl`.**
```bash
curl -v http://web01.corp.vektor.lab/            # весь диалог: DNS, connect, заголовки
curl -Iso /dev/null -w 'code=%{http_code} dns=%{time_namelookup} conn=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total} ip=%{remote_ip}\n' http://web01.corp.vektor.lab/
curl --resolve web01.corp.vektor.lab:80:10.10.20.10 -sI http://web01.corp.vektor.lab/   # проверить без DNS
```
Тайминги — лучший способ отличить «медленный DNS» от «медленного приложения»: большой `time_namelookup` — резолвер, большой `time_connect` — сеть/фаервол, большой `time_appconnect` — TLS, большой разрыв между `time_starttransfer` и `time_total` — сервер отдаёт тело медленно.

**8. HTTP/2 и TLS в одном взгляде.**
```bash
curl -v --http2 https://example.com/ 2>&1 | grep -E 'ALPN|HTTP/'
openssl s_client -connect example.com:443 -servername example.com -alpn h2 </dev/null
```
`ALPN, server accepted to use h2` — договорились на HTTP/2. `openssl` печатает всю цепочку сертификатов и протокол (`TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384`). Поддержка HTTP/3 в системном `curl` из Ubuntu зависит от сборки — проверяйте `curl -V | grep HTTP3` [ПРОВЕРИТЬ], часто нужен отдельный бинарник.

**9. Снять трафик — `tcpdump`.**
```bash
sudo tcpdump -i any -nn port 53 -c 4
sudo tcpdump -nn -i any 'host 10.10.20.10 and tcp[tcpflags] & tcp-syn != 0' -c 4
sudo tcpdump -i any -nn -s0 -w /tmp/cap.pcap 'tcp port 80'
tcpdump -nn -r /tmp/cap.pcap | head -30
```
```text
12:05:02.101 IP 10.10.10.30.41522 > 10.10.20.10.80: Flags [S], win 64240, length 0
12:05:02.102 IP 10.10.20.10.80 > 10.10.10.30.41522: Flags [S.], win 65160, length 0
```
Видите `[S]` без `[S.]` в ответ — SYN ушёл, ответа нет: firewall, `ip_forward=0` или неверный маршрут назад. `-nn` (без DNS/PORT-резолва) обязателен: иначе tcpdump сам начнёт генерировать DNS-запросы и вы будете ловить себя.

**10. NAT и состояние соединений на шлюзе.**
```bash
sudo nft list ruleset                 # правила: filter/forward, nat postrouting
sudo conntrack -L | grep 10.10.20.10  # apt install conntrack; активные трансляции
cat /proc/sys/net/netfilter/nf_conntrack_count
```
`conntrack -L` покажет `src=10.10.10.30 dst=10.10.20.10 sport=41522 dport=80` — если вместо клиентского `src` видите адрес шлюза, значит работает SNAT и в логах приложения будет шлюз.

**11. Пересылка пакетов (роутер).**
```bash
sysctl net.ipv4.ip_forward
sudo sysctl -w net.ipv4.ip_forward=1
echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-routing.conf && sudo sysctl --system
```
Без `ip_forward=1` Linux с двумя интерфейсами честно принимает пакеты и молча их выбрасывает — невероятно частая причина «сайт не открывается из офиса, а с шлюза открывается».

**12. Логи как последний рубеж.**
```bash
sudo tail -f /var/log/nginx/access.log
sudo journalctl -u nginx --since "10 min ago"
```
В `access.log` первое поле — IP клиента. Если там `10.10.20.1` при клиенте `10.10.10.30` — вы за SNAT, и реальный IP надо брать из `X-Forwarded-For`.

4. **UBU01.** Проверить L4: `nc -zv 10.10.20.10 80`. Ожидаемо: `succeeded`.
5. **UBU01.** Поднять локальный резолвер с записью для портала. Если DC01 есть и уже отвечает за `corp.vektor.lab` — шаг 5–6 можно сократить до `dig @10.10.10.10 web01.corp.vektor.lab`. Иначе:

Ожидаемо: `systemctl status dnsmasq` — `active (running)`.

7. **UBU01.** Посмотреть DNS в трафике: в одном терминале `sudo tcpdump -i any -nn port 53`, в другом `dig web01.corp.vektor.lab`. Ожидаемо: пара пакетов «запрос `A?` → ответ `A 10.10.20.10`».
8. **UBU01.** Проверить, что маршрут до портала через GW01, а не напрямую: `tracepath -n web01.corp.vektor.lab`. Ожидаемо: первый хоп `10.10.10.3`, второй `10.10.20.10`.
9. **UBU01.** HTTP-запрос с таймингами:
```bash

```
Ожидаемо: `code=200`, все тайминги в миллисекундах.
10. **UBU01.** Снять TCP-хендшейк: `sudo tcpdump -nn -i any 'host 10.10.20.10 and tcp[tcpflags] & tcp-syn != 0' -c 4`, параллельно `curl -s -o /dev/null http://web01.corp.vektor.lab/`. Ожидаемо: `[S]` и `[S.]` — рукопожатие состоялось.

## 6. Ошибки новичков и безопасность

1. **Диагностика «сверху вниз»** (сразу в логи приложения и `curl -v`, пропустив `ping`/`nc`) → копаетесь в nginx, когда пакеты вообще не доходят → всегда проверяйте L3 → L4 → L7.
2. **`ping` не проходит = хост недоступен** → на многих серверах ICMP просто заблокирован → проверяйте `nc -zv` по нужному порту, а не только ping.
3. **`ss -tulpn` без `p` и `sudo`** → не видно процессов → без `sudo` `ss` не покажет чужие сокеты, добавляйте `sudo`.
4. **`tcpdump` без `-nn` и без фильтра** → tcpdump сам генерирует DNS-запросы, вы ловите себя и тонете в выводе → всегда `-nn` и конкретный фильтр `host/port`.
5. **`tcpdump` на проде без `-c` и `-w`** → гигабайты в консоли, убитый терминал и нагрузка → `-c 100` для просмотра, `-w file.pcap -s0` для разбора в Wireshark, и обязательно снимать вместе с окном времени инцидента.
6. **Правка `/etc/resolv.conf` руками на Ubuntu** → systemd-resolved перезапишет файл → используйте `resolvectl dns` или `systemd-resolved` конфиг.
7. **Забыть про `ip_forward` при сборке роутера** → половина сети работает, половина «не видит» друг друга → проверяйте `sysctl` первым делом на любом Linux-шлюзе.
8. **Игнорировать NAT при чтении логов** → «атака с 10.10.20.1» и неверные rate-limit'ы → смотрите `X-Forwarded-For` и `conntrack`, а не только первый столбец `access.log`.

**Безопасность.** В лаборатории мы спокойно запускаем `tcpdump` и открываем 80-й порт в DMZ — это учебный стенд. В боевой среде: `tcpdump` видит **все** пакеты, включая пароли в plain-text HTTP и содержимое токенов — запускать только по инциденту, с осознанным фильтром, не хранить `.pcap` на общих шарах и удалять после разбора. Открытый порт 80 без TLS в DMZ — это передача данных в открытом виде: в реальной работе там TLS-терминация на балансировщике, HSTS и редирект 80→443. `ip_forward=1` на машине с двумя интерфейсами превращает её в маршрутизатор: без правил `nftables` в `forward`-цепочке она может начать пропускать трафик, который пропускать не должна — по умолчанию политика `forward` должна быть `drop`, а разрешения — точечными.

## 7. Вопросы на собеседовании

**1. Пользователь говорит «сайт не открывается». Ваши действия по шагам?**
Ответ: сначала уточняю, что именно видит пользователь (ошибка браузера, таймаут, 502) и у всех ли проблема. Дальше снизу вверх: `ping`/`tracepath` (L3), `nc -zv host порт` и `ss -tlnp` на сервере (L4), `dig` (DNS), `curl -v` с таймингами (L7 и TLS), `tcpdump` на клиенте/шлюзе/сервере, если непонятно, где пакет теряется. Параллельно смотрю логи nginx/приложения и метрики.
*Что хочет услышать интервьюер:* системный порядок слоёв, а не «перезапустил nginx — заработало».
*Красный флаг:* сразу лезть в код приложения или перезапускать сервисы без диагностики.

**2. Чем HTTP/2 лучше HTTP/1.1 и почему появился HTTP/3?**
Ответ: HTTP/1.1 — один запрос на соединение за раз, отсюда очереди и костыли (шардинг, конкатенация). HTTP/2 мультиплексирует потоки в одном TCP-соединении и сжимает заголовки HPACK, но потеря TCP-пакета блокирует все потоки — TCP head-of-line blocking. HTTP/3 убирает это, переезжая на QUIC поверх UDP: потеря блокирует только свой поток, плюс 0-RTT при повторном подключении. Версия согласуется через ALPN.
*Что хочет услышать интервьюер:* понимание HOL blocking и того, что HTTP/3 — это UDP, а значит сетевая диагностика другая.
*Красный флаг:* «HTTP/2 просто быстрее» без объяснения причин; путаница HTTP/3 с WebSocket.

**3. Зачем нужен SNI, если TLS шифрует соединение?**
Ответ: SNI передаётся в ClientHello **открытым текстом**, до установления шифрования. Без него сервер с одним IP и сотней доменов не знает, какой сертификат отдать. Это же свойство — источник утечки: по SNI видно, куда ходит клиент, поэтому появились ECH (Encrypted Client Hello) и DoH/DoT для DNS. В Kubernetes SNI — основа маршрутизации на ingress-контроллерах.
*Что хочет услышать интервьюер:* что SNI — часть ClientHello, а не шифрованного трафика, и практическое применение в ingress.
*Красный флаг:* «SNI шифруется вместе с сертификатом».

**4. Клиент видит в логах nginx IP шлюза вместо реального. Почему и что делать?**
Ответ: между клиентом и nginx работает SNAT (или прокси), подменяющий адрес источника; обратная трансляция выполняется по таблице conntrack. Реальный IP передаётся заголовком `X-Forwarded-For` (или PROXY protocol), который надо настроить на прокси и учитывать в конфиге nginx (модуль realip). Иначе ломаются логи, rate limiting и гео-аналитика.
*Что хочет услышать интервьюер:* понимание разницы SNAT/DNAT и того, что XFF легко подделать, если не ограничить доверенные прокси.
*Красный флаг:* «надо смотреть в conntrack на каждое соединение» как штатное решение.

**5. Что такое состояние TIME-WAIT и почему его много — это проблема?**
Ответ: TIME-WAIT — состояние стороны, закрывшей соединение первой; держится 60 секунд на Linux (2×MSL), чтобы поздние пакеты не попали в новое соединение с тем же 4-tuple. Много TIME-WAIT на клиенте — обычно признак коротких соединений без keep-alive и признак нагрузки, а не аварии; лечится пулом соединений. А вот растущий `CLOSE-WAIT` — тревожный: приложение не закрывает дескрипторы, это утечка и путь к `EMFILE`.
*Что хочет услышать интервьюер:* разницу между TIME-WAIT и CLOSE-WAIT и что первое — норма, второе — баг.
*Красный флаг:* «надо уменьшить tcp_tw_reuse и всё пройдёт» без понимания причины.
