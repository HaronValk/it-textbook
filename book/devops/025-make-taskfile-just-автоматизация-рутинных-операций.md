# Make, Taskfile, Just: автоматизация рутинных операций проекта

## 1. Введение (зачем это нужно в реальной работе)

**Тикет в трекере «Вектора»:**

> **От:** разработчик платёжного сервиса (роль в команде; отдельной ВМ на стенде нет — код живёт в GitLab на GIT01)
> **Кому:** adm.student
> **Тема:** «Один вход в проект вместо десяти команд»
> **Текст:** «У нас в README шесть разных команд: `go build` с длинным `-ldflags`, `go vet`, `go test -race -count=1`, потом ещё скрипт для деплоя. Половину флагов никто не помнит, каждый делает по-своему. Новый разработчик неделю въезжает. Можно сделать одну команду вроде `make ci`, чтобы и локально, и в пайплайне запускалось одно и то же?»
> **Срочность:** средняя

Это самая частая задача DevOps/DX-инженера после настройки самого CI. Проект живёт не в одном человеке, а в команде: у всех разные shell, разные привычки, разный уровень. Пока команды запуска «как надо» живут в головах и в вики, они неизбежно расходятся: локально тесты гоняют с `-race`, в CI без; сборка идёт с `-ldflags` у одного и без у другого; в пайплайне появляется «свой» набор шагов, который никто не проверял локально.

Таск-раннер решает эту проблему: он делает из набора команд **именованный интерфейс проекта**. `make ci`, `task build`, `just test` — это контракт. Он лежит в Git, ревьюится как код, версионируется вместе с проектом и одинаково работает у человека, в контейнере и в runner.

После этой главы ты будешь: понимать, чем Make отличается от Task и Just; писать Makefile с переменными, зависимостями и `.PHONY`; делать `Taskfile.yml` с кешированием по контрольным суммам; писать `justfile` с параметрами; связывать всё это с CI в GitLab и не наступать на классические грабли вроде табов вместо пробелов.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Таск-раннер — это программа, которая читает файл-описание (Makefile / Taskfile.yml / justfile) и по имени цели запускает нужные команды. Сетевых портов и протоколов здесь нет вообще: всё происходит в одном процессе на localhost. «Протокол» тут другой — **контракт автоматизации**: имя цели, аргументы командной строки, переменные окружения, код возврата (0 — успех, ≠0 — провал) и потоки: результат в stdout, логи/ошибки в stderr. Именно по коду возврата CI понимает, что джоба упала.

Место в общей картине (модель OSI тут не про сеть, а про слои инструментов):

```text
┌──────────────────────────────────────────────────────────────────┐
│  Слой 4. CI/CD                GitLab pipeline на GIT01           │
│                               job "ci":  script: task ci         │
├──────────────────────────────────────────────────────────────────┤
│  Слой 3. Таск-раннер          make / task / just                 │
│                               граф зависимостей, переменные,     │
│                               условия «уже собрано — пропустить» │
├──────────────────────────────────────────────────────────────────┤
│  Слой 2. Команды предметной   go build, go test, go vet,         │
│          области              docker build, kubectl apply,       │
│                               ansible-playbook, terraform         │
├──────────────────────────────────────────────────────────────────┤
│  Слой 1. Shell                /bin/sh, /bin/bash, PowerShell     │
│                               (каждая строка рецепта)            │
└──────────────────────────────────────────────────────────────────┘
```

**Make (GNU Make).** Живёт с 1976 года, изначально для сборки C-проектов. Ключевая идея — **цель (target) — это файл**. У цели есть пререквизиты (prerequisites, файлы, от которых она зависит) и рецепт (recipe, команды). Make смотрит на время изменения файлов: если цель новее всех пререквизитов — ничего не делает («is up to date»). Это позволяет пересобирать только то, что реально изменилось. Отсюда всё остальное: `$@` (имя цели), `$<` (первый пререквизит), `$^` (все пререквизиты), шаблонные правила вида `bin/%: cmd/%/main.go`. И главная боль: **рецепт должен начинаться с таба**, а не с пробелов.

**Task (go-task).** Современный раннер на Go, описание — YAML. Никаких табов, зато есть:
- `deps` — задачи, которые выполняются **до** и параллельно;
- `cmds` — последовательный список команд;
- `sources` / `generates` — список файлов на входе и выходе; Task считает по ним контрольную сумму и пропускает задачу, если ничего не менялось («is up to date»), то есть кеширование не по таймстемпам, а по содержимому;
- `status`, `preconditions`, `vars`, `dotenv`, `includes`.

**Just.** Раннер на Rust — по сути «make без файловой семантики». Это просто именованные рецепты с нормальными параметрами (`just deploy staging`), значениями по умолчанию, вариадическими аргументами и shebang-рецептами, где весь рецепт выполняется одним bash-скриптом. Никаких проверок «файл новее файла» — если вызвал, значит выполнилось.

| | Make | Task | Just |
|---|---|---|---|
| Формат | свой синтаксис, **табы** | YAML | свой, пробелы |
| Язык / год | C, 1976 | Go, ~2017 `[ПРОВЕРИТЬ]` | Rust, ~2016 `[ПРОВЕРИТЬ]` |
| Зависимости | граф + таймстемпы файлов | `deps` последовательно-параллельно | `deps` перед рецептом |
| «Уже сделано» | по mtime файлов | по контрольной сумме `sources` | нет |
| Аргументы | `make VAR=x` | `task x VAR=y`, `CLI_ARGS` | полноценные параметры рецепта |
| Windows | через WSL/MSYS2 | нативный бинарник | нативный бинарник |
| Порог входа | высокий | низкий | средний |

Про лицензии и доступность: все три — свободное ПО (GPLv3 у Make и Just, MIT у Task). Дистрибутивы качаются с GitHub Releases; если из офиса прямой доступ нестабилен, легальная альтернатива — внутреннее зеркало/Nexus или установка через `go install` с настроенным `GOPROXY` `[ПРОВЕРИТЬ актуальный GOPROXY в вашей сети]`.

## 3. Аналогия из жизни

Представь кухню ресторана. Повар-стажёр приходит, и ему говорят: «ну, суп варится как обычно, посмотри, как Игорь делает». Через месяц Игорь уволился — и суп стал другим, потому что «как обычно» никто не записал.

**Кулинарная книга** — это таск-раннер. В ней есть название блюда (`build`), список того, что должно быть готово заранее (`deps`/пререквизиты), и пошаговый рецепт (`cmds`/рецепт).

**Make** — это книга с таймером и холодильником: перед готовкой она проверяет, не осталось ли у тебя вчерашней заготовки, и если она свежее, чем продукты, — второй раз не варит. Проблема в том, что страницы книги нужно набирать особым шрифтом (табами), иначе повар не поймёт.

**Task** — та же книга, но написанная на стандартном бланке (YAML) и с чек-листом: если набор продуктов не изменился с прошлого раза, блюдо не готовится повторно, экономим время.

**Just** — это просто меню с рецептами и параметрами: «стейк, прожарка medium». Никакой проверки заготовок — заказали, значит готовим.

Аналогия ломается на одном: на кухне повар видит, что суп уже сварен. Make этого не видит — он смотрит только на дату изменения файла, поэтому «суп» может быть испорчен, но с более новым временем, и Make честно скажет «up to date».

## 4. Практика и команды

**1. Установка инструментов на UBU01 (Ubuntu Server 24.04).**

```bash
sudo apt-get update
sudo apt-get install -y make git
go install github.com/go-task/task/v3/cmd/task@latest
export PATH="$PATH:$(go env GOPATH)/bin"
task --version
```

Разбор: `go install` кладёт бинарник в `$(go env GOPATH)/bin` (обычно `~/go/bin`), поэтому PATH надо расширить и прописать это в `~/.bashrc`. Для `just` в Ubuntu 24.04 пакет может быть в `universe` — `sudo apt-get install -y just` `[ПРОВЕРИТЬ в вашем релизе]`; альтернатива — бинарник с GitHub Releases или `cargo install just`. Типичный вывод:

```text
Task version: v3.x.y (h1:...)
just 1.x.y
```

Смотреть: версия выше минимально поддерживаемой (у Task v3, у Just — release notes).

**2. Минимальный Makefile.**

```make
SHELL := /bin/bash
BIN   := payments-api
VERSION ?= $(shell git describe --tags --always --dirty 2>/dev/null || echo dev)

.PHONY: help build test lint ci

help: ## Показать список целей
	@grep -hE '^[a-zA-Z0-9_-]+:.*?## ' $(MAKEFILE_LIST) \
		| awk 'BEGIN {FS = ":.*?## "}; {printf "\033[36m%-12s\033[0m %s\n", $$1, $$2}'

build: ## Собрать бинарник
	go build -ldflags "-X main.version=$(VERSION)" -o bin/$(BIN) ./cmd/api

test: ## Прогнать тесты
	go test ./... -count=1

lint: ## go vet
	go vet ./...

ci: lint test build ## Полный прогон как в CI
	@echo "CI OK, version=$(VERSION)"
```

Разбор: `SHELL := /bin/bash` — иначе рецепты пойдут в `/bin/sh`; `:=` — немедленное вычисление, `?=` — «если не задано снаружи»; `.PHONY` объявляет цели, которые не являются файлами; `@` перед командой гасит эхо; `$$1` — экранированный `$1` для awk (Make съел бы одиночный `$`).

**3. Запуск целей Make.**

```bash
make help
make build
make -n build        # dry-run: показать команды, не выполняя
make -j4 ci          # параллельно, где возможно
make VERSION=1.2.3 build
make -C ~/vektor/payments-api test   # выполнить в другом каталоге
```

Вывод `make help`:

```text
build        Собрать бинарник
ci           Полный прогон как в CI
lint         go vet
test         Прогнать тесты
```

Смотреть: цели видны без чтения Makefile — это и есть «документация, которая не расходится с кодом».

**4. Автоматические переменные и шаблонные правила.**

```make
bin/%: cmd/%/main.go
	go build -o $@ $<
```

`$@` — имя цели (`bin/payments-api`), `$<` — первый пререквизит (`cmd/payments-api/main.go`), `$^` — все пререквизиты, `$*` — «стебель» шаблона (`payments-api`). Смотреть: правило сработает только если исходник новее бинарника.

**5. Диагностика табов и переводов строк (главная боль Make).**

```bash
cat -A Makefile | head -20
```

Вывод:

```text
SHELL := /bin/bash$
build: ## Собрать^M$
^Igo build -o bin/payments-api ./cmd/api$
```

Смотреть: `^I` — это таб (правильно), строка из пробелов (`    go build...`) — ошибка `missing separator`, `^M` в конце — файл сохранён в CRLF (правится `dos2unix Makefile` или `sed -i 's/\r$//' Makefile`).

**6. Taskfile.yml.**

```yaml
version: '3'

vars:
  BIN: payments-api
  VERSION:
    sh: git describe --tags --always --dirty 2>/dev/null || echo dev

dotenv: ['.env']

tasks:
  default:
    desc: Список задач
    cmds:
      - task --list

  lint:
    desc: go vet
    cmds:
      - go vet ./...

  test:
    desc: Прогнать тесты
    cmds:
      - go test ./... -count=1

  build:
    desc: Собрать бинарник
    deps: [lint]
    sources:
      - ./cmd/**/*.go
      - go.mod
    generates:
      - ./bin/{{.BIN}}
    cmds:
      - go build -ldflags "-X main.version={{.VERSION}}" -o ./bin/{{.BIN}} ./cmd/api

  ci:
    desc: Полный прогон как в CI
    cmds:
      - task: lint
      - task: test
      - task: build
```

Разбор: `version: '3'` — версия схемы Taskfile (обязательна); `deps` выполняются до `cmds`, причём параллельно; `sources`/`generates` включают кеш по контрольной сумме; `{{.BIN}}` — шаблон Go-темплейта (тема урока 24); `dotenv` подхватывает `.env`.

**7. Запуск задач Task.**

```bash
task --list
task build
task --force build
task --dry build
task ci
```

Первый `task build` собирает, второй печатает:

```text
task: Task "build" is up to date
```

Смотреть: `--force` игнорирует кеш, `--dry` показывает, что будет выполнено. Если «up to date» при изменённом коде — значит `sources` не покрывает нужные файлы.

**8. justfile.**

```make
set dotenv-load

default: help

# Показать список рецептов
help:
    @just --list

# Собрать бинарник
build target="payments-api":
    go build -o bin/{{target}} ./cmd/api

# Прогнать тесты
test *args:
    go test ./... -count=1 {{args}}

# go vet
lint:
    go vet ./...

# Полный прогон как в CI
ci: lint test build

# Релиз через shell-скрипт (весь рецепт — один bash)
release version:
    #!/usr/bin/env bash
    set -euo pipefail
    echo "release $version"
    ls -l bin/
```

Разбор: параметр с дефолтом `target="payments-api"`; `*args` — вариадические аргументы; `@` перед командой убирает эхо; shebang-рецепт выполняется как один скрипт, поэтому `cd` и `set -e` внутри работают как ожидается.

**9. Запуск рецептов just.**

```bash
just --list
just build
just test -run TestVersionNotEmpty
just --dry-run ci
```

Вывод:

```text
Available recipes:
    build target='payments-api' # Собрать бинарник
    ci                          # Полный прогон как в CI
    help                        # Показать список рецептов
    lint                        # go vet
    test *args                  # Прогнать тесты
```

Смотреть: `just --list` строится из комментариев `#` над рецептом — та же идея самодокументации.

**10. Проверка кода возврата — контракт с CI.**

```bash
make test; echo "exit=$?"
just ci || echo "CI упал, чиним"
```

Смотреть: любой ненулевой код должен останавливать пайплайн. Если рецепт заканчивается `; true` или `|| true` — CI будет зелёным при сломанных тестах.

**11. Вызов раннера из GitLab CI (`.gitlab-ci.yml`).**

```yaml
stages: [test]

ci:
  stage: test
  image: golang:1.23   # [ПРОВЕРИТЬ актуальный тег в вашем зеркале образов]
  before_script:
    - go install github.com/go-task/task/v3/cmd/task@latest
    - export PATH="$PATH:$(go env GOPATH)/bin"
  script:
    - task ci
```

Разбор: пайплайн не дублирует шаги, а вызывает ту же цель, что и разработчик локально. Единственное отличие CI — установка раннера в `before_script`.

**12. Сравнение по времени и «шумности».**

```bash
time make ci
time task ci
time just ci
```

Смотреть: где кеш реально экономит время (Task с `sources`), а где каждый запуск делает всё заново (Just). На маленьком проекте разница в секундах, на сборке контейнеров — в минутах.

### Сломай и почини

> **Пользователь:** разработчик платёжного сервиса
> **ВМ:** UBU01
> **Что написал:** «Сделал `make build` — вылетает `Makefile:8: *** missing separator. Stop.` Вчера всё работало, я только дописал пару строк в vim с рабочего ноутбука и скопировал файл на сервер. Срочность средняя, но релиз сегодня.»
> **Срочность:** средняя

**Воспроизведи поломку.** На UBU01 в своём проекте замени табы в рецептах на пробелы и добавь CRLF:

```bash
sed -i 's/^\t/    /' Makefile
sed -i 's/$/\r/' Makefile
make build
```

Ожидаемо: `Makefile:8: *** missing separator. Stop.`

**Диагностика по шагам** (именно в этом порядке):

1. Прочитать текст ошибки: `missing separator` — почти всегда «не таб» или «CRLF».
2. `cat -A Makefile | head -20` — ищем `^I` (таб) в начале строк рецептов и `^M` в конце строк.
3. `make -n build` — если падает так же, дело в парсинге файла, а не в командах.
4. Проверить, что правится тот файл: `pwd; ls -l Makefile`.
5. Убедиться, что не подключён другой `Makefile`/`GNUmakefile`: Make ищет их в порядке `GNUmakefile`, `makefile`, `Makefile`.

**Решение:**

```bash
sed -i 's/\r$//' Makefile        # убрать CRLF
sed -i 's/^    /\t/' Makefile    # вернуть табы в начало строк
make -n build && make build
```

Если строк много и вложенность важна — надёжнее открыть в vim (`:set list`, `:set noexpandtab`) и поправить руками.

**Ответ пользователю:** «Проблема не в коде, а в форматировании Makefile: рецепты должны начинаться с символа табуляции, а при копировании с Windows-редактора табы превратились в пробелы и добавились символы перевода строки CRLF. Исправил, `make build` проходит. На будущее: в репозитории лежит `.editorconfig` с `indent_style = tab` для `Makefile` — забирай, и такая ситуация больше не повторится.»

**Закрытие заявки:** комментарий с причиной, что сделано, и ссылкой на коммит с фиксом + `.editorconfig`. Метка `регрессия предотвращена`.

## 6. Ошибки новичков и безопасность

1. **Пробелы вместо табов в Makefile.** → `missing separator`, ничего не собирается, человек ищет проблему в коде. → Проверяй `cat -A`, держи `.editorconfig` с `indent_style = tab` для `Makefile`.
2. **Нет `.PHONY`.** → Появился файл или каталог с именем цели (`build`, `test`) — Make говорит «up to date» и ничего не делает. → Объявляй все «нефайловые» цели в `.PHONY`.
3. **Каждая строка рецепта — отдельный shell.** `cd dir` в одной строке не действует на следующую; `export VAR=1` тоже. → Пиши `cd dir && command` в одной строке или используй `.ONESHELL:`.
4. **`sources`/`generates` описаны неполно.** → Task кеширует по неверным файлам: правишь код, а задача «up to date». → Включай все входные файлы, включая `go.mod`, `go.sum`, Dockerfile; при сомнении — `task --force`.
5. **Дублирование логики: команды и в Makefile, и в `.gitlab-ci.yml`.** → Локально зелено, в CI красно (и наоборот). → В пайплайне только вызов `make ci` / `task ci`, все флаги — в таск-файле.
6. **Незапиненные версии раннера.** → На runner'е скачалась новая версия Task/Just — пайплайн неожиданно упал. → Устанавливай фиксированную версию (`task@v3.x.y`), кешируй бинарник в образе.
7. **`|| true` и `; exit 0` в рецептах.** → Тесты падают, но CI зелёный; проблема всплывает в проде. → Никогда не глуши код возврата без явной причины и комментария.
8. **Огромные `make deploy` без подтверждения.** → Одна неверная переменная — и выкатка ушла не в тот стенд. → Разделяй `deploy-staging` и `deploy-prod`, добавляй `preconditions`/интерактивное подтверждение.

### Безопасность

- **Секреты в таск-файлах и `.env`.** Makefile, `Taskfile.yml`, `justfile` коммитятся в Git: пароли, токены, ключи там видеть нельзя. `.env` — только в `.gitignore`, реальные секреты — в переменных CI/CD (masked/protected) на GIT01.
- **`curl ... | sh` при установке инструментов.** Мы так ставили Task/Just ради лабы. В боевой среде это выполнение произвольного кода с правами пользователя: скачивай бинарник, проверяй контрольную сумму или ставь из доверенного внутреннего репозитория.
- **Таск-файл как вектор атаки.** `make`/`task` из чужого репозитория выполняют то, что в нём написано, — не запускай `make` из незнакомого проекта на своей машине без просмотра файла, а в CI — только из доверенных веток.
- **`sudo` внутри рецептов.** Даёт любому, кто может запустить задачу, root. В нормальной среде такие задачи вынесены в отдельные роли Ansible/CI-джобы с ограниченным доступом и подтверждением.

## 7. Вопросы на собеседовании

**Вопрос 1. Зачем нужен таск-раннер, если можно написать bash-скрипт?**
Ответ: скрипт решает одну задачу, раннер даёт единый именованный интерфейс и граф зависимостей. Причины: самодокументируемость (`--list`), одинаковый вход для локальной машины, контейнера и CI, управление зависимостями между шагами (сначала lint, потом test, потом build), переменные и кеширование, кроссплатформенность (Task/Just — нативные бинарники). Скрипты при этом никто не отменяет: раннер их вызывает.
*Что хочет услышать интервьюер:* понимание DX и воспроизводимости, а не «мне нравится Make».
*Красный флаг:* «просто удобнее, чем помнить команды» без упоминания CI и единого источника правды.

**Вопрос 2. Чем Make отличается от Task и Just, что выберешь?**
Ответ: Make — про файлы и таймстемпы, граф целей, минимум зависимостей, стандарт де-факто; но табы, слабые аргументы и кроссплатформенность только через WSL. Task — YAML, кеш по контрольным суммам `sources`/`generates`, `deps`, `includes`, нативный бинарник. Just — рецепты с полноценными параметрами и shebang-рецептами, без файловой семантики. Выбор: legacy/Go-проекты и совместимость — Make; новый проект с кешированием и команда без make-опыта — Task; нужны удобные аргументы и «просто команды» — Just. Главное — один инструмент на проект.
*Что хочет услышать:* критерии выбора, а не религия.
*Красный флаг:* «Make устарел, всегда беру Task» без аргументов.

**Вопрос 3. Зачем нужен `.PHONY` и что будет без него?**
Ответ: `.PHONY: build test` помечает цели как не связанные с файлами. Без него, если в каталоге есть файл или папка с именем цели, Make сравнит таймстемпы и скажет «is up to date». Классика: каталог `bin/` и цель `bin`, или файл `build`. Это же правило делает поведение предсказуемым для целей `help`, `clean`, `test`.
*Что хочет услышать:* понимание файловой модели Make.
*Красный флаг:* «это устаревший синтаксис, можно не писать».

**Вопрос 4. Как сделать, чтобы локально и в CI выполнялось одно и то же?**
Ответ: одна цель (`ci`) — единственный источник правды, пайплайн вызывает только её; все флаги, переменные и порядок шагов описаны в таск-файле, который лежит в репозитории и ревьюится; версия раннера закреплена и одинаково ставится локально и в образе CI; в CI нет «своих» дублирующих скриптов; секреты приходят из переменных CI, а не из файла. Дополнительно — контейнер с закреплённым образом как среда исполнения.
*Что хочет услышать:* «CI — тонкий вызывающий слой».
*Красный флаг:* «в пайплайне напишем те же команды руками, так проще».

**Вопрос 5. Что такое «up to date» в Task и зачем это нужно?**
Ответ: механизм пропуска уже выполненной работы. `sources` — входные файлы, `generates` — выходные; Task считает контрольную сумму и, если входы не менялись и выходы существуют, печатает `Task "x" is up to date` и не выполняет `cmds`. Экономит минуты на сборке и тестах, но требует аккуратного перечисления файлов; `--force`/`--status` помогают отлаживать. У Make аналог — сравнение mtime, у Just аналога нет.
*Что хочет услышать:* понимание, что кеш — источник и экономии, и багов «не пересобралось».
*Красный флаг:* «всегда запускаю с `--force`, чтобы наверняка» — значит, кеш настроен неверно.
