## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Shell — это интерпретатор в пользовательском пространстве (user space). Сам по себе он ничего не «считает»: он читает строку, разбивает её на слова, ищет бинарник в `$PATH` и делает `fork()` + `execve()`. Всё остальное — работа внешних программ.

**Коды возврата.** Каждый процесс по завершении отдаёт родителю число 0–255. 0 — успех, всё остальное — ошибка. В shell это `$?`. Договорённость, которую надо знать: 1 — общая ошибка, 2 — ошибка использования (неверный ключ), 126 — нет прав на файл, 127 — команда не найдена, 128+N — процесс убит сигналом N (130 = Ctrl+C, 143 = SIGTERM).

**Конвейер (pipe).** Между процессами shell создаёт системный вызов `pipe(2)` и подменяет файловые дескрипторы: stdout левого процесса становится stdin правого. Это ровно те fd 0/1/2, которые ты разбирал в уроке 6. Программы в конвейере работают **параллельно**, а не по очереди.

**В чём подвох.** По умолчанию код возврата конвейера — это код **последней** команды. `cat broken.log | grep ERROR` вернёт 1 (grep не нашёл), а вот `grep ERROR broken.log` в конвейере с `sort` вернёт 0 от `sort`, даже если `grep` упал с ошибкой чтения файла. Именно это лечит `set -o pipefail`.

```text
 bash-скрипт (pid 4242, user space)
 ┌──────────────────────────────────────────────────────────────────┐
 │ set -Eeuo pipefail   ← политика: -e падать, -u ловить опечатки,  │
 │                        pipefail: статус конвейера = статус       │
 │                        САМОЙ ПРАВОЙ команды, упавшей с != 0      │
 │ trap ... EXIT        ← уборка (rm временных, снять lock)         │
 │ trap ... ERR         ← репорт: строка, код (нужен set -E)        │
 │ getopts              ← разбор -c / -n / -o в $OPTARG, $OPTIND    │
 └───────────────┬──────────────────────────────────────────────────┘
                 │ fork()+execve()  и  pipe(2) между соседями
     ┌───────────┴──────┐
     ▼                  ▼
  awk access.log ──pipe──▶ sort ──pipe──▶ head ──pipe──▶ jq
   fd1 → fd0          fd1 → fd0        fd1 → fd0      fd0 → stdout
   exit 0             exit 0           exit 0         exit 0
   ┌─────────────────────────────────────────────────────────────┐
   │ лучшее место для проверки ошибок — СТЫК, а не конец цепочки │
   └─────────────────────────────────────────────────────────────┘
```

**Инструменты обработки.** `sed` — потоковый редактор: читает построчно, применяет к строке набор команд (чаще всего `s/что/на что/флаги`), пишет в stdout. `awk` — маленький язык с полями: строку режет на `$1..$NF`, умеет ассоциативные массивы и блоки `BEGIN`/`END`. `jq` — фильтр для JSON: у него своя мини-грамматика (`.a.b`, `select()`, `map()`), и он **валидирует** JSON, то есть ловит битые данные. `yq` — то же самое для YAML/XML/TOML, но у него есть **две несовместимые реализации** (об этом ниже).

Где это в модели OSI: нигде. Это уровни 5–7 в бытовом смысле, но технически — прикладной уровень поверх системных вызовов ОС. Понимание нужно не для OSI, а для того, чтобы знать: `curl … | jq` упадёт на HTML-странице ошибки от прокси, потому что это не JSON.

## 3. Аналогия из жизни

Представь ресторанную кухню. Шеф (bash) не готовит сам — он выкрикивает задания поварам (внешние команды). Между станциями стоит конвейер: один повар нарезает, второй обжаривает, третий выкладывает на тарелку (это `pipe`). У каждой станции есть лампочка «готово/брак» (код возврата). По умолчанию шеф смотрит только на лампочку **последней** станции: если мясо сгорело на гриле, но на тарелку его всё равно положили, шеф считает блюдо готовым — это и есть конвейер без `pipefail`. С `pipefail` шеф обходит всю линию и видит первую красную лампочку. `trap` — это пожарная тревога и вечерняя уборка: срабатывает независимо от того, чем закончилась смена. `getopts` — бланк заказа с галочками («с соусом», «без лука»), а `jq`/`awk`/`sed` — повара-универсалы: один режет по словам, другой по символам, третий перекладывает из формата в формат.

Аналогия перестаёт работать в одном месте: на реальной кухне повара работают по очереди, а в конвейере все процессы запускаются одновременно и просто ждут друг друга на чтении из трубы.

## 4. Практика и команды

### 4.1. Шапка любого серьёзного скрипта

```bash
#!/usr/bin/env bash
set -Eeuo pipefail
IFS=$'\n\t'
```

- `-e` — выйти при первой ошибке. **Не срабатывает**, если команда стоит в `if`/`while`/`until`, слева от `&&` или `||`, после `!`, или (без `pipefail`) не последняя в конвейере.
- `-u` — обращение к незаданной переменной это ошибка (ловит опечатки). Дефолт задаётся как `${VAR:-значение}`.
- `-o pipefail` — статус конвейера = статус самой правой упавшей команды.
- `-E` (он же `errtrace`) — `trap ... ERR` наследуется функциями и подоболочками. Без него ошибка внутри функции может пройти мимо.
- `IFS=$'\n\t'` — убираем пробел из разделителей, чтобы `for f in $list` не рвал имена файлов с пробелами.

### 4.2. Коды возврата

```bash
grep -q 'ERROR' /var/log/nginx/access.log; echo "rc=$?"
rc=0; grep -q 'ERROR' access.log || rc=$?
if ! command -v jq >/dev/null 2>&1; then echo "jq не установлен" >&2; exit 3; fi
```

`grep -q` ничего не печатает, только код: 0 — нашёл, 1 — нет, 2 — ошибка (например, нет файла). Три разных смысла у одного grep — поэтому в скриптах проверяют именно `rc`, а не текст.

### 4.3. trap: уборка и репорт об ошибке

```bash
TMPDIR=$(mktemp -d)
cleanup() { rm -rf -- "$TMPDIR"; echo "[$(date -Is)] уборка выполнена" >&2; }
trap cleanup EXIT
trap 'echo "[$(date -Is)] ОШИБКА: строка $LINENO, код $?" >&2' ERR
trap 'echo "прервано пользователем" >&2; exit 130' INT TERM
```

`EXIT` срабатывает всегда — и при успехе, и при падении, и при Ctrl+C. Поэтому все временные файлы, локи и фоновые процессы снимают там. `ERR` — только при ненулевом коде. `$LINENO` внутри одинарных кавычек вычисляется в момент срабатывания, поэтому даёт нужную строку.

### 4.4. getopts: аргументы командной строки

```bash
usage() { echo "usage: $0 -c config.yaml [-n 5] [-o out.json] [-v]" >&2; }

CONFIG=./config.yaml; TOPN=""; OUT=""; VERBOSE=0
while getopts ":c:n:o:vh" opt; do
  case "$opt" in
    c) CONFIG="$OPTARG" ;;
    n) TOPN="$OPTARG" ;;
    o) OUT="$OPTARG" ;;
    v) VERBOSE=1 ;;
    h) usage; exit 0 ;;
    :) echo "ключ -$OPTARG требует значения" >&2; exit 2 ;;
    \?) echo "неизвестный ключ -$OPTARG" >&2; usage; exit 2 ;;
  esac
done
shift $((OPTIND - 1))
```

Двоеточие **перед** строкой опций (`":c:n:o:vh"`) включает «тихий» режим — тогда неизвестный ключ и отсутствующее значение приходят в `case` как `?` и `:`, и ты сам печатаешь сообщение. `getopts` не умеет длинные опции (`--config`); для них берут `getopt` (внешняя утилита) или ручной `while [ $# -gt 0 ]`.

### 4.5. sed: точечная правка потока

```bash
sed -n '1,5p' access.log                 # только первые 5 строк
sed -E 's/^([0-9.]+) .*/\1/' access.log  # только IP в начале строки
sed -i.bak 's/old-host/new-host/g' nginx.conf
sed -E 's/\r$//' win-файл.txt > unix-файл.txt
```

`-n` — не печатать всё подряд (тогда нужен явный `p`). `-E` — расширенные регулярки (`+`, `?`, `|`, группы без обратных слэшей). `-i.bak` — правка на месте с сохранением копии; без `.bak` откатиться будет нечем.

### 4.6. awk: подсчёт по полям

```bash
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -5
awk -F'"' '{split($3, a, " "); print a[2]}' access.log | sort | uniq -c | sort -rn
awk -F'"' '{split($3,a," "); if (a[2] ~ /^5[0-9][0-9]$/) n++} END {print n+0}' access.log
awk 'END {print NR+0}' access.log
```

Формат `combined` у nginx: `$remote_addr - $remote_user [$time_local] "$request" $status $bytes "$referer" "$ua"`. Казалось бы, статус — `$7`. Но если в URL попадётся пробел (а он может быть закодирован не всегда), поля **съедут**, и `$7` станет мусором. Поэтому надёжнее резать по кавычке (`-F'"'`): тогда `$2` — всегда запрос, `$3` — `статус размер`. `n+0` — страховка: без неё на пустом входе `print n` выведет пустую строку, а не 0.

Типичный вывод `uniq -c | sort -rn`:

```text
   9120 10.10.10.100
   4471 10.10.20.10
    231 10.10.10.101
```

Смотрим на первый столбец (частота) и на то, нет ли в топе одного адреса, который даёт 90% трафика — это либо сканер, либо сломанный клиент.

### 4.7. jq: чтение и сборка JSON

```bash
jq -r '.log.path' config.json
jq -c '.items[] | select(.status >= 500) | {ip, url}' resp.json
jq -e '.server_errors > 0' report.json >/dev/null; echo "rc=$?"
jq -n --arg host "$(hostname)" --argjson n 37 '{host: $host, errors: $n}'
jq -R -s 'split("\n") | map(select(length > 0))' < список.txt
```

`-r` — «сырой» вывод без кавычек (для подстановки в переменную). `-c` — компактно, одной строкой (для логов). `-e` — выставить код возврата 1, если результат `false`/`null` — так JSON-проверку можно ставить в `if`. `--arg` подставляет строку, `--argjson` — уже готовый JSON (число, массив), без второго `jq` не соберёшь вложенный массив. `-R -s` — читать сырой текст целиком и превратить его в одну строку.

### 4.8. yq: YAML как данные

```bash
yq '.log.path' config.yaml
yq -r '.alerts[].threshold' config.yaml
yq -i '.log.top_n = 10' config.yaml
yq -o=json '.' config.yaml
yq --version
```

**Важно:** существуют две несовместимые `yq`. Та, что нужна для Kubernetes и CI, — **mikefarah/yq** (Go), версия 4.x, команда `yq eval` (по умолчанию = `yq`). Другая — Python-обёртка над jq (kislyuk/yq), у неё другой синтаксис и флаг `-y` для вывода YAML. Проверяй `yq --version`: у mikefarah будет строка вида `yq (https://github.com/mikefarah/yq/) version v4.x`. `-i` правит файл на месте — как `sed -i`, без бэкапа; в Git-репозитории это нормально, вне его — опасно.

Установка mikefarah-версии (в apt Ubuntu её может не быть, там лежит другая) `[ПРОВЕРИТЬ актуальность имён файлов в релизе]`:

```bash
sudo wget -qO /usr/local/bin/yq https://github.com/mikefarah/yq/releases/latest/download/yq_linux_amd64
sudo chmod +x /usr/local/bin/yq
yq --version
```

Из РФ GitHub может быть нестабилен — тогда `sudo snap install yq` (это тоже mikefarah) или зеркало/пакет из репозитория дистрибутива. Скачивать бинарник и сразу запускать его от `sudo` — так себе практика; в боевой среде сначала проверяют контрольную сумму из релиза.

### 4.9. Чтение файла построчно

```bash
while IFS= read -r line; do
  printf 'строка: %s\n' "$line"
done < list.txt
```

`IFS=` сохраняет ведущие пробелы, `-r` отключает обработку `\`. Вариант «в одну строку» — `mapfile -t arr < list.txt`.

### 4.10. Проверка скрипта

```bash
bash -n logreport.sh      # синтаксис, без выполнения
shellcheck logreport.sh   # стиль + реальные баги
bash -x logreport.sh -c config.yaml   # трассировка; PS4='+$LINENO: ' для номеров строк
```

`shellcheck` — обязательный шаг. Он ловит незакавыченные переменные, `for i in $(ls)`, `[ $a = $b ]` без кавычек и десятки других классических ошибок.

### 4.11. Временные файлы и блокировки

```bash
TMP=$(mktemp -d) || exit 1
exec 9>"$TMP/report.lock"; flock -n 9 || { echo "уже выполняется" >&2; exit 4; }
```

`mktemp` создаёт файл/каталог с уникальным именем и правами 600 — не угадываемым в `/tmp`. `flock` не даёт двум копиям скрипта (например, крону и ручному запуску) работать одновременно.

> **Пользователь:** дежурный администратор
> **ВМ:** UBU01
> **Что написал:** «Отчёт отработал с кодом 0, а в нём `"server_errors": 0` и `"total_requests": 0`. Хотя я точно знаю, что за ночь на WEB01 была куча 502. Скрипт врёт.»

**Как воспроизвести.** На WEB01 принудительно ротировать лог:
```bash

ls -la /var/log/nginx/
```
`access.log` станет пустым (0 байт), данные уедут в `access.log.1.gz`. Скопируй пустой лог на UBU01 поверх старого и запусти скрипт. Получишь ровно этот симптом: JSON есть, код 0, нули.

**Диагностика по порядку.**
1. `jq '.total_requests' out/report.json` — если 0, проблема на входе, а не в `jq`.
2. `wc -l access.log` на UBU01 и `ls -la access.log` — 0 строк и 0 байт.
3. `head -3 access.log` — пусто.
4. На WEB01: `ls -la /var/log/nginx/` — видим `access.log.1.gz` сегодняшней датой.
5. `zcat /var/log/nginx/access.log.1.gz | wc -l` на WEB01 — тысячи строк. Причина найдена: **пустой вход ≠ нет ошибок**.
6. Дополнительно: `grep -c ' 5[0-9][0-9] ' access.log` вернул бы 0 и код 1 — если бы ты использовал `grep` в конвейере без `pipefail`, ошибка потерялась бы совсем.

**Решение.** Добавить в скрипт два изменения:

```bash
read_log() { case "$1" in *.gz) zcat -- "$1" ;; *) cat -- "$1" ;; esac; }

total=$(read_log "$LOG_PATH" | awk 'END {print NR+0}')
if [ "$total" -eq 0 ]; then
  echo "[$(date -Is)] ОШИБКА: 0 строк во входе $LOG_PATH — лог ротирован? не считаю это успехом" >&2
  exit 3
fi
```

И заменить остальные обращения к `"$LOG_PATH"` в пайплайнах на `read_log "$LOG_PATH" |`. Код 3 — отдельный, чтобы дежурный и будущий мониторинг отличали «нет данных» от «есть данные, ошибок нет» (0) и «есть ошибки» (2).

**Ответ пользователю:** «Причина — ночная ротация логов: скрипт читал уже опустевший `access.log`. Исправил: теперь он понимает `.gz`-архивы и возвращает отдельный код 3, если на входе ноль строк, вместо ложного „всё хорошо“. Проверено на ротированном логе, отчёт строится по `access.log.1.gz`.»

## 6. Ошибки новичков и безопасность

1. **`set -e` и вера, что он ловит всё.** → Скрипт «зелёный» после падения внутри `if`, `&&`-цепочки или подоболочки. → Правильно: `set -Eeuo pipefail` плюс явные проверки через `if ! cmd; then …` там, где ошибка ожидаема.
2. **Незакавыченные переменные.** `rm -rf $DIR/` при пустом `$DIR` удалит `/`. → Всегда `"$VAR"`, а перед `rm -rf` — проверка `[ -n "$DIR" ] && [ -d "$DIR" ]`.
3. **Парсинг JSON регулярками.** `grep '"status": 500'` ломается на смене форматирования и вложенных объектах. → `jq`, который проверяет структуру.
4. **`sed -i` без бэкапа и `yq -i` без Git.** → Одна опечатка в регулярке — и конфиг нечитаем. → `sed -i.bak`, `yq -i` только в файле под версионным контролем.
5. **`cat файл | grep` и `for f in $(ls)`.** → Лишний процесс и поломка на именах с пробелами. → `grep pattern файл`, `for f in ./*; do` или `while IFS= read -r`.
6. **Пустой вход трактуется как «всё хорошо».** → Ложнозелёный мониторинг (см. лабу). → Явный `exit 3` при нуле строк.
7. **`[ "$a" > "$b" ]` для чисел.** → `>` внутри `[ ]` — это перенаправление вывода в файл, а не сравнение; получишь файл с именем числа. → Для чисел `-gt`/`-lt` или `(( a > b ))`; для строк `[[ "$a" > "$b" ]]`.
8. **`[ cond ] && cmd` последней строкой функции.** → Функция вернёт 1, и `set -e` убьёт скрипт на ровном месте. → `if [ cond ]; then cmd; fi`.

### Безопасность

- **Секреты в скрипте и в аргументах.** `./deploy.sh --token abc123` видно в `ps aux` любому пользователю машины. В Git секреты попадают навсегда (история). Правильно: переменные окружения из файла с правами 600, `curl -K`, менеджер секретов, `.gitignore` + `git-secrets`/`gitleaks`.
- **`curl … | bash`.** Ты запускаешь код с сервера без проверки. На учебном стенде допустимо, в боевой среде — скачай, проверь контрольную сумму/подпись, и только потом запускай.
- **Временные файлы в `/tmp` с предсказуемым именем.** Классический симлинк-хак. Только `mktemp`.
- **Широкие права ради удобства.** `chmod 777` на каталог отчётов означает, что любой процесс на сервере может подменить JSON, который потом читает мониторинг. На стенде мы так не делаем; в бою — владелец-сервис и `750`.
- **`sudo` внутри скрипта.** Скрипт, который сам просит `sudo`, нельзя безопасно запускать из CI. В боевой среде скрипт запускается от сервисного пользователя с узким набором прав (см. урок 8 про sandboxing в systemd).

## 7. Вопросы на собеседовании

**1. Что делает `set -euo pipefail` и в каких случаях `-e` не спасает?**

`-e` завершает скрипт при ненулевом коде возврата команды, `-u` превращает обращение к незаданной переменной в ошибку, `-o pipefail` меняет статус конвейера на статус самой правой упавшей команды (по умолчанию берётся только последняя). Не срабатывает `-e` в условиях `if`/`while`/`until`, в левой части `&&`/`||`, после `!`, и в командах внутри `$(...)`, если ошибка там не влияет на итоговый статус — плюс `-e` не наследуется в подоболочки функций без `-E`/`errtrace`. Поэтому в реальных скриптах явные проверки всё равно нужны.

*Что хочет услышать интервьюер:* что ты знаешь про pipefail и исключения `-e`, а не просто вставляешь магическую строку из интернета. *Красный флаг:* «set -e решает все проблемы с ошибками».

**2. Как гарантировать выполнение очистки, если скрипт упал или его прервали?**

`trap 'cleanup' EXIT` — срабатывает при любом выходе: успех, ошибка, сигнал. Отдельно `trap '...' INT TERM` для реакции на Ctrl+C и SIGTERM (в обработчике — вернуть `exit 130`/`143`), и `trap '...' ERR` вместе с `set -E` для репорта о том, где именно упали (`$LINENO`, `$?`). В `cleanup` — удаление `mktemp`-каталога, снятие `flock`, удаление PID-файла; он должен быть идемпотентным.

*Что хочет услышать интервьюер:* понимание, что `EXIT` покрывает все пути выхода. *Красный флаг:* «поставлю cleanup в конце скрипта».

**3. Как безопасно обработать JSON в bash-скрипте?**

Только через `jq`, не через `grep`/`sed` и тем более не через `eval`. Значения извне передаются как `--arg`/`--argjson`, а не подстановкой в текст фильтра — иначе получишь инъекцию фильтра. Для проверок используется `jq -e` (код возврата 1 на `false`/`null`), для встраивания в другие команды — `-r`, для логов — `-c`. Ошибки парсинга `jq` отдаёт ненулевым кодом, что вместе с `pipefail` останавливает скрипт.

*Что хочет услышать интервьюер:* `--arg` и `-e`. *Красный флаг:* `eval "$(jq ...)"` или `jq ".field == \"$USER_INPUT\""`.

**4. `awk` или `sed` — когда что?**

`sed` — когда работа построчная и нужна замена/удаление/выбор строк по шаблону: конфиги, простые правки, `s///`. `awk` — когда нужны поля, арифметика, агрегация и состояние между строками: подсчёт по колонкам, топ-N, суммы, `BEGIN`/`END`, ассоциативные массивы. Правило большого пальца: одна строка — `sed`, статистика по колонкам — `awk`. Если появляется третий уровень сложности (парсинг CSV с кавычками, JSON) — берут специализированный инструмент, а не `awk`.

*Что хочет услышать интервьюер:* что ты не тащишь `awk` туда, где нужен `jq`, и наоборот. *Красный флаг:* «awk умеет всё, я им парсю YAML».

**5. Чем ограничен `getopts` и как валидировать аргументы?**

`getopts` — встроенная команда bash, поддерживает только короткие опции (`-c`), склеивание (`-vh`) и значения (`-c file` или `-cfile`). Длинных опций (`--config`) нет — нужен внешний `getopt` или ручной цикл. Валидация: после `shift $((OPTIND-1))` проверяем, что обязательные переменные заданы и непусты, что `-n` — целое (`[[ "$N" =~ ^[0-9]+$ ]]`), что файлы читаемы (`-r`), и печатаем `usage` в stderr с кодом 2 при ошибке использования.

*Что хочет услышать интервьюер:* различие `getopts`/`getopt` и код возврата 2 для «неверное использование». *Красный флаг:* разбор аргументов через `$1`, `$2` без обработки ошибок.
