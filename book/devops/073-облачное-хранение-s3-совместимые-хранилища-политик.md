# Облачное хранение: S3-совместимые хранилища, политики жизненного цикла, шифрование, версионирование

## 1. Введение (зачем это нужно в реальной работе)

Тикет в поддержку: «Пользователь: ivanov (Иван Иванов, бухгалтерия) / ВМ: портал на WEB01 / Что написал: „Открываю вложение к платежу за прошлый месяц — портал отдаёт 404, файл пропал. Это платёжка, она нужна аудитору сегодня“ / Срочность: высокая».

За такими заявками почти всегда стоит одно из трёх: объект удалила политика жизненного цикла, объект перезаписали и старой версии нет, потому что версионирование не включили, или доступ закрыла политика бакета. Объектное хранилище — это то место, куда в современной инфраструктуре складывают всё «плоское»: бэкапы, логи, артефакты сборок, вложения пользователей, образы ВМ, выгрузки из 1С. Оно дешевле диска виртуалки, к нему можно обратиться из любого контейнера по HTTP, и оно масштабируется без переформатирования. После этой главы ты должен уметь: поднять S3-совместимое хранилище на стенде, создать бакет, включить версионирование, написать политику жизненного цикла, настроить шифрование и запретить в бакет нешифрованные загрузки, выдать временный доступ ссылкой и — главное — восстановить «пропавший» файл за минуты, а не за сутки. Плюс понимать, чем это отличается в Яндекс Облаке и почему в РФ к хранению персональных данных прилагается 152-ФЗ.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**S3 (Simple Storage Service)** — это HTTP REST API и модель данных, а не конкретный продукт. Изначально придуман Amazon, но реализаций много: MinIO, Ceph RGW, SeaweedFS, Garage, а в РФ — Yandex Object Storage, VK Cloud Object Storage, Selectel, Cloud.ru. Все они понимают один и тот же протокол, поэтому `aws-cli` или `mc` работают одинаково, меняется только endpoint.

**Модель данных.** Нет привычных папок. Есть плоское пространство ключей внутри бакета: объект = ключ (строка, например `attachments/2026/03/invoice-42.pdf`) + тело + метаданные + ETag (обычно MD5 тела или хеш multipart-загрузки) + version-id (если включено версионирование). Слэши в ключе — просто символы; «префикс» — это фильтр по началу строки. Отсюда правило: файловая система для «много мелких файлов с переименованием» — не объектное хранилище. Бакет — контейнер верхнего уровня, имя обычно уникально в пределах региона/аккаунта.

**Протокол.** HTTP/1.1 поверх TLS (443 в облаке; в лабе мы поставим 9000 без TLS — и это отдельно оговорим). Методы: `PUT` (загрузить), `GET` (скачать), `HEAD` (метаданные), `DELETE`, `POST` (multipart). Аутентификация — подпись **AWS Signature V4**: HMAC-SHA256 от канонического запроса ключом, производным от secret key. Пароль по сети не летит. Большие файлы (>100 МБ) грузятся multipart-ом: `CreateMultipartUpload` → `UploadPart` → `CompleteMultipartUpload`, поэтому в правилах жизненного цикла есть отдельный пункт «прервать незавершённые multipart-загрузки» — иначе они молча жрут деньги.

**Согласованность.** У AWS S3 с декабря 2020 и у MinIO — strong read-after-write: после успешного `PUT` следующий `GET` увидит объект. У более старых/самописных реализаций могла быть eventual consistency — уточняй у провайдера.

**Версионирование.** Включил — каждая перезапись создаёт новую версию с уникальным version-id, а `DELETE` без указания версии ставит **delete marker** (объект «удалён», старые версии живы). Приостановка версионирования (`Suspend`) сохраняет старые версии, новые пишутся с version-id `null`. Выключить и «почистить историю» можно только удалением всех версий.

**Жизненный цикл (lifecycle).** Набор правил в JSON: фильтр (префикс/тег), действие (`Expiration` — удалить текущую версию, `NoncurrentVersionExpiration` — удалить старые версии, `Transition` — переложить в холодный класс, `AbortIncompleteMultipartUpload`). Провайдер применяет правила фоновым сканером, обычно раз в сутки — то есть «удалится в течение ~24–48 часов», а не мгновенно.

**Шифрование.** Варианты: `SSE-S3` (ключ у провайдера, «шифруем, но ключ не наш»), `SSE-KMS` (ключ в KMS/Vault, есть аудит и ротация), `SSE-C` (клиент присылает ключ в заголовке каждого запроса, провайдер его не хранит — потерял ключ, потерял данные), client-side (шифруем до загрузки). Отдельно — шифрование в транзите: TLS. Плюс `Object Lock` (WORM): бакет с версионированием, где объект нельзя удалить/перезаписать до истечения срока в режимах `GOVERNANCE` (можно снять с правами) и `COMPLIANCE` (нельзя никому до срока). Это защита от шифровальщиков и «случайных `rm -rf`».

**Доступ.** IAM-политики (кто), bucket policy (что разрешено/запрещено с этим бакетом, может запрещать даже владельцу), ACL (устаревшее), presigned URL (временная подписанная ссылка), public access (явно включается, по умолчанию всё закрыто).

```text
       UBU01 10.10.10.30            WEB01 10.10.20.10
       (mc, aws-cli, бэкапы)        (портал: вложения пользователей)
                 \                          /
                  \   S3 API, TLS, SigV4   /
                   \                      /
              ┌─────────────────────────────────┐
              │  S3-совместимый сервис          │
              │  HARBOR01 10.10.10.55:9000      │
              │  (лаба: MinIO, TLS нет :(       │
              │   прод: TLS 443 + KMS)          │
              │                                 │
              │  buckets:                       │
              │   vektor-portal-attachments     │  versioning ON
              │     ├─ attachments/  (365 дн.)  │  lifecycle
              │     ├─ tmp/          (1 день)   │
              │     └─ noncurrent    (30 дн.)   │
              │   vektor-backups  (Object Lock) │
              └─────────────────────────────────┘
                     scанер lifecycle: раз в сутки
```

Место в модели OSI: прикладной уровень (L7), как HTTP. Проблемы «не грузится» ищут так же, как любой HTTP: DNS → TCP 443/9000 → TLS → код ответа (403 — права, 404 — нет ключа, 400 — подпись/параметры).

## 3. Аналогия из жизни

Объектное хранилище — это камера хранения на вокзале. Бакет — конкретная камера хранения (или целый склад), ключ — номер ячейки (`attachments/invoice-42.pdf`), содержимое — чемодан. Ты не можешь «зайти в ячейку и переставить вещи»: только положить чемодан целиком, забрать целиком, заменить целиком. Номерка сплошная, но в ней есть слэши, чтобы людям было привычнее. Версионирование — это стеллаж: положил новый чемодан в ту же ячейку, старый не выкинули, а убрали на полку с биркой (version-id); если ты «удалил» чемодан, на полке остался ярлык «здесь ничего нет» (delete marker), а сам чемодан на полке. Жизненный цикл — это уборщик с обходным листом: «всё из ячейки `tmp/` старше суток — в утиль, всё со стеллажа старше 30 дней — в утиль», и он ходит раз в сутки, а не по твоему звонку. Шифрование `SSE-C` — ты приносишь свой замок и каждый раз приносишь ключ; забыл ключ дома — чемодан твой, а открыть нечем. Object Lock — чемодан прикован к полке болгаркой до даты в накладной. Аналогия перестаёт работать в одном месте: у камеры хранения есть физический лимит по объёму, а объектное хранилище практически эластично — «место кончилось» ты увидишь скорее в счёте, чем в ошибке.

## 4. Практика и команды

Всё выполняем на стенде: MinIO поднимется на **HARBOR01** (10.10.10.55) — он уже Ubuntu Server с Docker для Harbor. Новых машин по правилам трека не заводим; в продакшене под S3-хранилище выделяют отдельный хост или берут managed-сервис.

**1. Запуск S3-совместимого сервиса (HARBOR01)**

```bash
sudo mkdir -p /srv/minio/data
sudo docker run -d --name minio \
  -p 9000:9000 -p 9001:9001 \
  -e MINIO_ROOT_USER=vektor-admin \
  -e MINIO_ROOT_PASSWORD='Lab#2026-vektor' \
  -v /srv/minio/data:/data \
  --restart unless-stopped \
  quay.io/minio/minio:latest server /data --console-address ":9001"
```

- `-p 9000` — S3 API, `-p 9001` — веб-консоль.
- `MINIO_ROOT_USER/PASSWORD` — это «root» хранилища, в боевой среде такие креды живут в Vault (урок 66) и не переиспользуются нигде.
- `--console-address` — явно задаём порт консоли, чтобы не уехал на случайный.
- Образ тянется из `quay.io`; из РФ возможны сложности с доступом — легальная альтернатива: официальный Docker Hub-образ `minio/minio` или зеркало вашего реестра HARBOR01 [ПРОВЕРИТЬ актуальное состояние community-версии MinIO: в 2025 политика проекта менялась].

**2. Установка клиентов и алиас (UBU01)**

```bash
curl -O https://dl.min.io/client/mc/release/linux-amd64/mc
chmod +x mc && sudo mv mc /usr/local/bin/mc
mc alias set vektor http://10.10.10.55:9000 vektor-admin 'Lab#2026-vektor'
mc admin info vektor
```

`mc` — CLI MinIO, удобнее для админских операций (lifecycle, retention). `mc admin info` печатает версию, uptime, объём и число нод — первое, что смотрим при «хранилище недоступно».

**3. Создание бакета и включение версионирования**

```bash
mc mb vektor/vektor-portal-attachments
mc version enable vektor/vektor-portal-attachments
mc version info vektor/vektor-portal-attachments
```

Ожидаемый вывод последней команды: `vektor-portal-attachments is versioning enabled`. Без этого шага всё, что ты перезаписал, потеряно навсегда — именно так теряются «случайно затёртые» платёжки.

**4. Политика жизненного цикла**

```bash
mc ilm rule add vektor/vektor-portal-attachments --prefix "tmp/" --expire-days 1
mc ilm rule add vektor/vektor-portal-attachments \
  --expire-days 365 \
  --noncurrent-expire-days 30 \
  --expire-delete-marker \
  --abort-incomplete-multipart-days 3
mc ilm rule ls vektor/vektor-portal-attachments
```

Ключи: `--prefix` — к какому префиксу применяется правило; `--expire-days` — удалить текущую версию через N дней; `--noncurrent-expire-days` — удалить неактуальные версии; `--expire-delete-marker` — не копить delete markers (иначе `ls --versions` распухает); `--abort-incomplete-multipart-days` — убрать зависшие multipart-загрузки. Синтаксис `mc ilm rule` новый; в старых сборках `mc` было `mc ilm add --expiry-days` — смотри `mc ilm rule add --help` [ПРОВЕРИТЬ под свою версию].

**5. Загрузка и проверка версий через AWS CLI**

```bash
EP=http://10.10.10.55:9000
aws --endpoint-url $EP s3 cp /etc/hosts s3://vektor-portal-attachments/attachments/invoice-2026-03.txt
aws --endpoint-url $EP s3 cp /etc/hostname s3://vektor-portal-attachments/attachments/invoice-2026-03.txt
aws --endpoint-url $EP s3api list-object-versions \
  --bucket vektor-portal-attachments --prefix attachments/invoice-2026-03.txt
```

`--endpoint-url` подменяет адрес сервиса (по умолчанию AWS). В выводе `list-object-versions` смотри `Versions[].VersionId`, `IsLatest`, `Size` — так видно, что обе загрузки живы.

**6. Восстановление старой версии**

```bash
aws --endpoint-url $EP s3api get-object \
  --bucket vektor-portal-attachments \
  --key attachments/invoice-2026-03.txt \
  --version-id <VersionId-старой-версии> /tmp/restored.txt
mc cp --version-id <VersionId> \
  vektor/vektor-portal-attachments/attachments/invoice-2026-03.txt \
  vektor/vektor-portal-attachments/attachments/invoice-2026-03.txt
```

Первая команда просто скачивает нужную версию, вторая — делает её текущей (перезаписывает ключ содержимым версии). Это и есть «восстановление за 30 секунд».

**7. Шифрование клиентским ключом (SSE-C)**

```bash
sudo openssl rand -out /root/sse-c.key 32
aws --endpoint-url $EP s3api put-object \
  --bucket vektor-portal-attachments --key secure/secret.txt \
  --body /etc/hostname \
  --sse-customer-algorithm AES256 \
  --sse-customer-key fileb:///root/sse-c.key
aws --endpoint-url $EP s3api head-object \
  --bucket vektor-portal-attachments --key secure/secret.txt
```

`--sse-customer-algorithm AES256` — алгоритм, `--sse-customer-key` — сам ключ (файл, `fileb://` означает «бинарный файл»). При `head-object` без ключа сервис ответит ошибкой вида «object was stored using a form of Server Side Encryption…» — значит, шифрование реально работает. Ключ `/root/sse-c.key` в лабе лежит открыто; в бою он в KMS/Vault и с бэкапом, иначе данные нечитаемы.

**8. Запрет нешифрованных загрузок (bucket policy)**

```bash
cat > /root/deny-unencrypted.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyUnencryptedUploads",
    "Effect": "Deny",
    "Principal": {"AWS": ["*"]},
    "Action": "s3:PutObject",
    "Resource": "arn:aws:s3:::vektor-portal-attachments/*",
    "Condition": {"Null": {
      "s3:x-amz-server-side-encryption": "true",
      "s3:x-amz-server-side-encryption-customer-algorithm": "true"
    }}
  }]
}
EOF
aws --endpoint-url $EP s3api put-bucket-policy \
  --bucket vektor-portal-attachments --policy file:///root/deny-unencrypted.json
```

Условие `Null: true` означает «заголовка нет». Два условия подряд — это AND: запрещаем `PUT`, если нет ни SSE-S3/KMS-заголовка, ни SSE-C-заголовка. Политику храним в Git — это configuration as code (урок 65).

**9. Временная ссылка для пользователя (presigned URL)**

```bash
aws --endpoint-url $EP s3 presign \
  s3://vektor-portal-attachments/attachments/invoice-2026-03.txt \
  --expires-in 900
```

Отдаёт URL с подписью в query string, действует 900 секунд. Так отдают файл человеку без учётки в хранилище и без публичного бакета. Максимум для SigV4 — 7 дней (`--expires-in 604800`).

**10. Object Lock (WORM) для бэкапов**

```bash
mc mb vektor/vektor-backups
mc version enable vektor/vektor-backups
mc retention set --default GOVERNANCE 30d vektor/vektor-backups
mc retention info vektor/vektor-backups
```

`--default GOVERNANCE 30d` — 30 дней объект нельзя удалить/перезаписать; снять защиту можно только учёткой с правом `s3:BypassGovernanceRetention`. Режим `COMPLIANCE` не снимается вообще до истечения срока — только так, и осознанно.

**11. Диагностика объекта**

```bash
mc stat vektor/vektor-portal-attachments/attachments/invoice-2026-03.txt
mc ls --versions vektor/vektor-portal-attachments/attachments/
mc du vektor/vektor-portal-attachments
```

`stat` показывает ETag, размер, metadata, version-id; `ls --versions` — все версии и delete markers; `du` — объём (считается долго на больших бакетах). В консоли MinIO (`http://10.10.10.55:9001`) то же самое доступно мышкой: бакет → объект → вкладка с версиями.

**12. Тот же API в облаке (Яндекс Облако)**

```bash
yc storage bucket create --name vektor-portal-attachments --default-storage-class standard
yc storage bucket update --name vektor-portal-attachments --versioning
aws --endpoint-url https://storage.yandexcloud.net s3api get-bucket-versioning \
  --bucket vektor-portal-attachments
```

`--default-storage-class` — класс хранения по умолчанию (`standard`), `--versioning` — включить версионирование; endpoint — `https://storage.yandexcloud.net`, а lifecycle удобнее задавать тем же `put-bucket-lifecycle-configuration` с `Transition` в холодный/ледяной класс. Точные флаги `yc` сверяй по `yc storage bucket update --help` [ПРОВЕРИТЬ]. Одна строка про РФ: персональные данные по 152-ФЗ нужно хранить в РФ-регионе, у российских провайдеров это выбор региона при создании бакета [ПРОВЕРИТЬ актуальные требования].

   Ожидаемо: `An error occurred (AccessDenied)` — политика работает. Затем повтори с `--sse-c` — успех.

## 6. Ошибки новичков и безопасность

1. **Не включил версионирование «потому что и так работает»** → любая перезапись или `rm` необратимы, восстановление только из бэкапа. Правильно: версионирование включается сразу при создании бакета с данными, которые кто-то может затереть.
2. **Lifecycle-правило с `--expire-days` на весь бакет без префикса** → уносит продакшн-данные, как в лабе. Правильно: правило всегда с узким префиксом, проверка через `mc ilm rule ls` и MR в Git.
3. **`--expire-delete-marker` без `--noncurrent-expire-days`** → delete markers копятся (и `ls --versions` нечитаем), либо наоборот: включили удаление всех неактуальных версий через 1 день и потеряли историю. Правильно: пара «delete marker + noncurrent 30+ дней» под реальные требования.
4. **Бакет публичный «чтобы быстро отдать файл»** → утечка. Правильно: `presigned URL` с коротким TTL или проксирование через приложение.
5. **SSE-C-ключ рядом с бэкапом в том же бакете** → шифрование превращается в театр. Правильно: ключ в Vault/KMS (урок 66), отдельный контур доступа, ротация.
6. **`mc admin` root-креды раздаются приложениям** → одна утечка = весь стенд. Правильно: root только для администрирования, приложениям — отдельные сервисные учётки с политикой на конкретный префикс.
7. **S3 без TLS «в лабе же» и привычка тянуть это в прод** → SigV4 защищает от подделки запроса, но тело и метаданные видны в сети. Правильно: TLS-терминация (nginx/reverse-proxy перед MinIO) или облачный endpoint с HTTPS по умолчанию.
8. **Оставили `--abort-incomplete-multipart-days` без внимания** → зависшие multipart-загрузки годами занимают место и деньги. Правильно: правило 3–7 дней обязательно.

**Безопасность отдельно.** В боевой среде нельзя: держать бакет с персональными данными вне РФ-региона (152-ФЗ), оставлять `Principal: "*"` в `Allow`, выдавать presigned URL на дни, использовать `COMPLIANCE`-режим Object Lock без юридического обоснования (снять его нельзя даже админу), запускать MinIO с root-паролем из документации (`minioadmin`), хранить ключи шифрования на том же диске, где данные. Все «упрощения» лабы — HTTP, пароль стенда `Lab#2026-vektor`, ключ в `/root` — в проде недопустимы.

## 7. Вопросы на собеседовании

**1. Чем объектное хранилище отличается от файлового и блочного и когда вы выберете S3?**
Ответ: блочное (диск ВМ) — сырые блоки, ФС сверху, для ОС и БД; файловое (NFS/SMB) — иерархия, блокировки, частичная запись, для общих папок; объектное — плоское пространство ключей по HTTP, объект пишется целиком, есть метаданные, версии, lifecycle, неограниченное масштабирование и дешёвое хранение. S3 выбирают для бэкапов, логов, артефактов, статики, вложений, датасетов; не выбирают для БД, для файлов с частой частичной перезаписью и для сценариев с жёсткими POSIX-блокировками.
*Что хочет услышать интервьюер:* понимание границ применимости и «боли» (переименование, append, latency).
*Красный флаг:* «S3 — это просто папка в облаке».

**2. Как работает версионирование и как вы восстановите файл, который перезаписали месяц назад?**
Ответ: при включённом версионировании каждая перезапись создаёт новую версию с version-id; `DELETE` создаёт delete marker, данные остаются. Восстановление: `list-object-versions` → найти нужный version-id → `get-object --version-id` → перезаписать ключ содержимым версии (или снять delete marker). Ключевой момент: срок жизни старых версий задаётся `NoncurrentVersionExpiration`, и если он меньше месяца — восстановить нечего.
*Что хочет услышать интервьюер:* что версии не бесплатны, их срок надо осознанно настраивать, и что `rm` в S3 — это не `rm`.
*Красный флаг:* «у нас же бэкапы есть» без понимания RPO/RTO и без проверки, что lifecycle не удалил историю.

**3. Клиент жалуется, что из бакета пропадают файлы через сутки. Ваши действия?**
Ответ: гипотеза №1 — lifecycle. Смотрю `get-bucket-lifecycle-configuration`/`mc ilm rule ls`: правила, префиксы, сроки, noncurrent-политика, `AbortIncompleteMultipartUpload`. Гипотеза №2 — версионирование выключено и объект перезаписывается приложением с тем же ключом. Гипотеза №3 — приложение/скрипт сам делает `DELETE` (смотрю логи доступа/access logging, наличие delete markers, время удаления). №4 — срок жизни presigned URL/политика доступа (но это 403, не пропажа). Дальше: восстановление из версий, исправление правила через Git, алерт на аномальное удаление.
*Что хочет услышать интервьюер:* системный порядок проверок и то, что сначала сохраняем данные, потом чиним конфиг.
*Красный флаг:* сразу «перезальём файлы» без выяснения причины.

**4. Какие способы шифрования есть у S3 и что вы выберете для персональных данных?**
Ответ: SSE-S3 (ключ провайдера), SSE-KMS (свой ключ в KMS/Vault, аудит и ротация), SSE-C (ключ клиента на каждый запрос, провайдер не хранит), client-side (шифруем до загрузки). Плюс TLS в транзите всегда. Для ПДн: SSE-KMS с ключом в управляемом KMS, отдельный ключ на бакет/домен данных, ограниченные права на `kms:Decrypt`, аудит доступа, РФ-регион по 152-ФЗ; клиентское шифрование — если не доверяем провайдеру как таковому.
*Что хочет услышать интервьюер:* разницу «шифрование включено» и «ключ у меня, и я знаю, кто его использует».
*Красный флаг:* «включил галку шифрования — значит безопасно», без темы ключей и доступа.

**5. Зачем нужен Object Lock и какие у него подводные камни?**
Ответ: WORM-защита от удаления/изменения — против шифровальщиков, инсайдеров, для требований аудита и регуляторов. Требует версионирования, задаётся на бакет (default retention) или на объект. Режимы: `GOVERNANCE` (снимается правами `BypassGovernanceRetention`) и `COMPLIANCE` (не снимается никем до срока). Подводные камни: необратимость (в `COMPLIANCE` данные нельзя удалить даже при ошибке), нельзя включить «назад» без последствий, растёт объём хранения, и это не заменяет бэкап — от потери аккаунта/бакета не спасает.
*Что хочет услышать интервьюер:* что WORM — это про неизменяемость, а не про резервное копирование, и что цена ошибки необратима.
*Красный флаг:* «включим COMPLIANCE на всё, на всякий случай».
