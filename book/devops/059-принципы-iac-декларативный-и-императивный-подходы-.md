# Принципы IaC: декларативный и императивный подходы, идемпотентность, дрейф конфигурации

## 1. Введение (зачем это нужно в реальной работе)

**Заявка #4471**
- **Пользователь:** sidorov (Алексей Сидоров, склад)
- **ВМ:** WEB01 (портал отгрузок, 10.10.20.10)
- **Что написал:** «Утром на портале были новые тарифы, после обеда опять старые. Мы уже дважды перезапускали — то новые, то старые. Клиенты путаются, срочно».
- **Срочность:** высокая

Ты открываешь WEB01 и видишь: в `/etc/nginx/sites-available/portal.conf` кто-то вчера «на минутку» поправил `root` руками, а сегодня утром кто-то другой прогнал старый скрипт развёртывания и вернул файл к прежнему виду. Конфиг на сервере больше не совпадает с тем, что лежит в Git. Никто не знает, какая версия «правильная». Вот это и есть **дрейф конфигурации** — и это одна из главных причин, по которым в 2026 году инфраструктуру описывают кодом, а не руками.

Дальше в работе ты будешь сталкиваться с этим каждый день: сервер, настроенный «по памяти», после переустановки выглядит иначе; «временная» правка на проде живёт три года; на тесте работает, на проде нет — потому что окружения разъехались. IaC (Infrastructure as Code, «инфраструктура как код») — это дисциплина, которая лечит именно эти болезни.

После главы ты должен уметь: объяснить разницу между императивным и декларативным подходом и привести примеры инструментов; написать идемпотентный скрипт и понять, почему `>>` в скрипте — это мина; обнаружить дрейф конфигурации штатными средствами (Ansible `--check --diff`, `terraform plan`, `kubectl diff`); вернуть систему к описанному состоянию и не потерять при этом чужие изменения.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Два подхода.**

**Императивный** — ты пишешь *как*: последовательность шагов. «Создай пользователя. Скачай файл. Скопируй в `/etc`. Перезапусти сервис». Это bash-скрипт, `kubectl run`, ручные клики в веб-панели. Проблема: скрипт не знает, в каком состоянии система была до него. Запустил второй раз — получил дубли или ошибку.

**Декларативный** — ты пишешь *что* должно быть в итоге: «порт 80 слушает nginx, файл `/var/www/portal/index.html` имеет такое содержимое, владелец www-data». Как этого добиться — забота инструмента. Terraform, Kubernetes-манифесты, ArgoCD, cloud-init — декларативны.

**Идемпотентность** — свойство операции: сколько раз её ни выполни, результат один и тот же, а побочных эффектов при повторе нет. `systemctl start nginx` идемпотентна (второй запуск ничего не делает). `echo ... >> file` — нет (каждый запуск добавляет строку). `useradd ivanov` — нет (второй запуск упадёт с ошибкой «user already exists»).

**Сходимость (convergence)** — чуть более мягкое понятие, чем идемпотентность: инструмент за один прогон может не дойти до нужного состояния, но за несколько прогонов обязательно дойдёт. Ansible именно такой: он «сходится» к описанному состоянию.

**Дрейф (drift)** — расхождение между тем, что описано в коде (desired state), и тем, что реально работает (actual state). Причины: ручные правки «по-быстрому», обновления пакетов сбоку от IaC, восстановление из бэкапа, аварийный хотфикс ночью, кто-то поменял настройку в веб-консоли облака.

**Петля сверки (reconciliation loop)** — то, что отличает настоящий декларативный инструмент от «скрипта с проверками»:

```text
        Git / репозиторий IaC
        (единственный источник истины)
                   │  desired state
                   ▼
          ┌─────────────────┐
          │   IaC-инструмент │
          │  Terraform /     │
          │  Ansible /       │
          │  ArgoCD / Flux   │
          └─────────────────┘
             │          ▲
     apply / │          │ observe (read-only)
     sync    ▼          │
          ┌─────────────────┐
          │  Реальная система│
          │  ВМ, nginx, k8s  │
          └─────────────────┘
                   │
        drift: ручная правка «мимо» кода
                   ▼
              расхождение
```

Цикл такой: **прочитать факт → сравнить с желаемым → показать разницу (plan/diff) → применить только разницу**. У Terraform это `refresh` + `plan` + `apply`, у Ansible — сбор фактов + задачи, у ArgoCD — периодический опрос кластера (по умолчанию раз в 3 минуты `[ПРОВЕРИТЬ]`).

**Где это живёт в стеке.** IaC — уровень над ОС и железом. Агентов обычно нет: Ansible ходит по SSH (TCP 22), облачные провайдеры и GitLab/ArgoCD — по HTTPS (443), Kubernetes API — 6443. Именно поэтому IaC-инструменты не «ставятся на сервер», а работают *снаружи* и управляют серверами через их штатные интерфейсы.

**Кто есть кто (запомни расклад):**

| Инструмент | Подход | Профиль |
|---|---|---|
| Bash/PowerShell-скрипт | императивный | универсально, но всё пишешь сам |
| Ansible | процедурный с декларативными модулями (гибрид) | конфигурация ОС и сервисов |
| Terraform / OpenTofu | декларативный | провижининг ресурсов (ВМ, сети, DNS, облака) |
| Kubernetes + `kubectl apply` | декларативный | состояние workloads |
| ArgoCD / Flux | декларативный (GitOps) | доставка состояния из Git в кластер |
| Packer | декларативный (шаблон образа) | «золотые» образы ВМ |

Важно: «декларативный» не значит «без порядка». В Terraform зависимости задаются через `depends_on` или неявно (ссылка на атрибут другого ресурса), в Kubernetes — через readiness-пробы и операторы. Декларативность — про *что*, а не про *отсутствие логики*.

## 3. Аналогия из жизни

Сборка шкафа из IKEA.

**Императивно** — это когда друг диктует тебе по телефону: «Возьми винт A, вкрути в деталь 3, потом возьми полку...». Пропустил звонок на середине — и не знаешь, на каком ты шаге. Позвонил заново с начала — вкрутил те же винты второй раз, только дырки уже заняты.

**Декларативно** — это картинка готового шкафа на первой странице инструкции: двери, три полки, ручки справа. Ты смотришь на картинку и на то, что уже собрано, и делаешь только недостающее. Собрал — картинка совпала, делать больше нечего.

**Идемпотентность** — «затяни винт до упора». Ты можешь крутить ключ сколько угодно, результат один: винт затянут. Противоположность — «поверни ключ на два оборота»: сделал дважды — и уже перетянул.

**Дрейф** — пока ты уходил за пиццей, кот свалил шкаф и открутил одну полку. Внешне шкаф стоит, но он больше не соответствует картинке. Хороший декларативный инструмент (в жизни — твой взгляд на картинку и на шкаф) заметит это при следующей сверке.

Где аналогия ломается: у настоящей системы с reconciliation loop есть «руки» — она сама себя чинит по расписанию, без тебя. Шкаф сам полку не прикрутит.

## 4. Практика и команды

**1. Императивный скрипт — и его провал на втором запуске**

```bash
#!/usr/bin/env bash
set -euo pipefail
echo 'net.ipv4.ip_forward = 1' >> /etc/sysctl.d/99-vektor-lab.conf
sysctl --system >/dev/null
```

`>>` — дописывание в конец файла. Первый прогон: одна строка. Второй: две одинаковые. Пятый: пять. Работает, но файл мусорится, а если параметр изменился — старое значение останется ниже нового и перезапишет его при разборе. Разбор ключей bash: `set -e` — выйти при ошибке, `-u` — ругаться на неинициализированные переменные, `-o pipefail` — ошибка в любом звене пайплайна валит весь пайплайн.

**2. Тот же скрипт, но идемпотентный**

```bash
#!/usr/bin/env bash
set -euo pipefail
grep -qxF 'net.ipv4.ip_forward = 1' /etc/sysctl.d/99-vektor-lab.conf \
  || echo 'net.ipv4.ip_forward = 1' >> /etc/sysctl.d/99-vektor-lab.conf
sysctl --system >/dev/null
```

`grep -q` — тихо, только код возврата; `-x` — совпадение всей строки, а не подстроки; `-F` — искать как есть, без regexp. `||` означает «дописывать, только если ещё нет». Прогон дважды — вторая строка не появляется.

**3. Маскировка императивной команды под идемпотентную (Ansible)**

```yaml
- name: Инициализировать БД приложения
  ansible.builtin.command: /usr/local/bin/init-db.sh
  args:
    creates: /var/lib/portal/db.initialized
```

Модуль `command` по природе не идемпотентен — всегда «changed». `creates` говорит: запускай, только если файла нет. Есть зеркальный `removes`. Альтернатива — `changed_when` / `failed_when`.

**4. Ansible: прогон-черновик с показом разницы**

```bash
ansible-playbook -i inventory.ini site.yml --check --diff
```

`--check` — dry-run (ничего не меняем), `--diff` — показать unified diff того, что изменилось бы. Типичный вывод:

```text
TASK [Put index.html] ********************************
--- before: /var/www/portal/index.html
+++ after: /home/<user>/.ansible/tmp/...
@@ -1,3 +1,3 @@
- <h1>Тарифы, версия 2</h1>
+ <h1>Тарифы, версия 3</h1>

PLAY RECAP *******************************************
web01  : ok=4  changed=1  unreachable=0  failed=0
```

Смотрим на `changed=1` и на сам diff. Пустой `changed` — дрейфа нет.

**5. Ansible: реальный прогон и доказательство идемпотентности**

```bash
ansible-playbook -i inventory.ini site.yml
ansible-playbook -i inventory.ini site.yml
```

Второй прогон обязан дать `changed=0`. Если не дал — где-то `command`/`shell` без `creates`, либо шаблон отдаёт меняющееся содержимое (например, `{{ ansible_date_time }}` в конфиге). **`changed=0` на повторном прогоне — главный тест на идемпотентность в Ansible.**

**6. Terraform: план с машинно-читаемым кодом возврата**

```bash
terraform plan -detailed-exitcode -out=tfplan
echo $?
```

Коды: `0` — изменений нет, `1` — ошибка, `2` — изменения есть. Это готовый детектор дрейфа для CI: джоба по расписанию запускает план и падает с `2`, если реальность разъехалась с кодом.

**7. Terraform: обновить state под реальность, ничего не меняя**

```bash
terraform plan  -refresh-only
terraform apply -refresh-only
```

Когда кто-то поменял ресурс в веб-консоли облака, `state` устарел. `-refresh-only` перечитывает реальность и обновляет state **без применения** конфигурации. Дальше обычный `plan` покажет честную разницу.

**8. Terraform: посмотреть, что вообще под управлением**

```bash
terraform state list
```

Список адресов ресурсов в state. Если ресурс существует в реальности, но его нет в выводе — он вне IaC, то есть потенциальный дрейф. Подробно `state`, `import` и backend — в уроке 61.

**9. Kubernetes: diff между манифестом и живым кластером**

```bash
kubectl diff -f k8s/portal-deploy.yaml; echo $?
```

Показывает unified diff; код возврата `1` — отличия есть, `0` — нет. Это самый быстрый способ поймать «кто-то поправил деплой через `kubectl edit`».

**10. Kubernetes: декларативное применение**

```bash
kubectl apply --server-side -f k8s/portal-deploy.yaml
kubectl get deploy portal -o yaml | grep -n 'image:'
```

`apply` идемпотентен: повторный запуск без изменений в файле даёт `unchanged`. `--server-side` переносит merge-логику на API-сервер и корректнее работает с большими объектами и конфликтами полей.

**11. GitOps: сравнить кластер с Git и синхронизировать**

```bash
argocd app diff portal
argocd app sync portal
```

`diff` — дрейф между Git и кластером, `sync` — привести кластер к Git. Ключевая идея GitOps: **никто не делает `kubectl apply` руками**, единственный путь изменений — коммит в Git.

**12. Проверка целостности файлов пакетов (дрейф на уровне ОС)**

```bash
sudo dpkg --verify nginx
# RHEL/Astra: sudo rpm -Va
```

`dpkg --verify` сверяет файлы пакета с его же md5-суммами из базы. Вывод вида `??5?????? /etc/nginx/nginx.conf` — файл изменён относительно поставки. Пустой вывод — всё как в пакете. Быстрый способ найти «следы ручных правок» на сервере без IaC.

**13. etckeeper: git внутри `/etc`**

```bash
sudo apt install -y etckeeper
sudo etckeeper init
sudo etckeeper commit "baseline before portal rollout"
sudo etckeeper vcs log --oneline | head
sudo etckeeper vcs diff HEAD
```

`etckeeper` версионирует `/etc` в git и автоматически коммитит изменения при работе apt. Даёт ответ на вопрос «что здесь менялось и когда» — даже если формального IaC ещё нет.

**14. Проверка дрейфа в CI одной строкой**

```bash
git diff --exit-code || { echo "IaC-репозиторий изменён вне ревью"; exit 1; }
```

`--exit-code` возвращает `1`, если есть незакоммиченные изменения. Ставится в пайплайн, который сам генерирует конфиги: «сгенерировали → ничего не поменялось» значит, что ручные правки в шаблонах не просочились.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

- **UBU01** (10.10.10.30, Ubuntu Server 24.04) — рабочая машина, где ты пишешь код. SSH-клиент, `git`, `ansible-core` (ставится в шаге 1).
- **WEB01** (10.10.20.10, Ubuntu Server, nginx, DMZ 10.10.20.0/24) — целевой сервер. Должен пинговаться с UBU01; SSH с UBU01 на WEB01 по ключу. Если WEB01 ещё не развёрнут — сначала пройди тему L2 про веб-сервер в DMZ и маршрутизацию GW01.
- На WEB01 у твоего пользователя должен быть `sudo` (в лабе удобно `NOPASSWD`, но это **учебное упрощение**; в бою так не делают — см. «Безопасность»).
- Windows-часть стенда для этой лабы не нужна.

### Снапшот

В VMware Workstation на **UBU01** и **WEB01**: правый клик по ВМ → *Snapshot* → *Take Snapshot…* → имя `before-devops-059`. Питание ВМ при снапшоте лучше выключить или хотя бы не делать снапшот в момент записи на диск.

### Шаги

1. **UBU01.** Ставим инструменты и создаём репозиторий:
   ```bash
   sudo apt update && sudo apt install -y ansible git
   mkdir -p ~/iac-lab/files && cd ~/iac-lab && git init
   ```
   Ожидаемо: `Initialized empty Git repository in /home/<user>/iac-lab/.git/`.

2. **UBU01.** Демонстрируем неидемпотентность. Создай `imperative.sh` из пункта 4.1 (с `>>` в `/etc/sysctl.d/99-vektor-lab.conf`) и запусти дважды:
   ```bash
   chmod +x imperative.sh && sudo ./imperative.sh && sudo ./imperative.sh
   cat /etc/sysctl.d/99-vektor-lab.conf
   ```
   Ожидаемо: две одинаковые строки `net.ipv4.ip_forward = 1`. Это баг.

3. **UBU01.** Чистим и делаем идемпотентно:
   ```bash
   sudo sed -i '/ip_forward = 1/d' /etc/sysctl.d/99-vektor-lab.conf
   ```
   Замени содержимое скрипта на версию из п.4.2, запусти трижды — в файле всегда ровно одна строка. Ожидаемо: `grep -c` возвращает `1`.

4. **UBU01.** Готовим декларативное описание портала. `files/portal.conf`:
   ```nginx
   server {
       listen 80;
       server_name portal.vektor.lab;
       root /var/www/portal;
       index index.html;
       location / { try_files $uri $uri/ =404; }
   }
   ```
   И `files/index.html`:
   ```html
   <h1>Портал отгрузок. Тарифы, версия 3</h1>
   ```

5. **UBU01.** Пишем `inventory.ini` и `site.yml` (плейбук из раздела «Практика», с `file`, `copy`, хендлером `nginx -t && systemctl reload nginx`). В `inventory.ini` подставь **своего** пользователя на WEB01:
   ```ini
   [web]
   web01 ansible_host=10.10.20.10 ansible_user=ВАШ_ПОЛЬЗОВАТЕЛЬ
   ```

6. **UBU01.** Сухой прогон:
   ```bash
   ansible-playbook -i inventory.ini site.yml --check --diff
   ```
   Ожидаемо: `changed` больше нуля, в diff видно создание файлов. На WEB01 пока **ничего** не изменилось — проверь `ls /var/www/portal` (должно быть пусто или «нет каталога»).

7. **UBU01.** Реальный прогон и сразу второй:
   ```bash
   ansible-playbook -i inventory.ini site.yml
   ansible-playbook -i inventory.ini site.yml
   ```
   Ожидаемо: первый — `changed=3` (или около), второй — `changed=0`. Это и есть доказанная идемпотентность.

8. **UBU01.** Проверяем снаружи:
   ```bash
   curl -s -H 'Host: portal.vektor.lab' http://10.10.20.10/
   ```
   Ожидаемо: `<h1>Портал отгрузок. Тарифы, версия 3</h1>`. DNS не нужен — подставляем заголовок `Host`.

9. **UBU01.** Коммитим — теперь Git источник истины:
   ```bash
   git add -A && git commit -m "portal: nginx vhost + index v3, idempotent playbook"
   ```

10. **WEB01.** Создаём **дрейф** — имитируем ночной хотфикс «руками»:
    ```bash
    sudo mkdir -p /var/www/portal-old
    sudo cp /var/www/portal/index.html /var/www/portal-old/
    sudo sed -i 's#root /var/www/portal;#root /var/www/portal-old;#' /etc/nginx/sites-available/portal.conf
    sudo nginx -t && sudo systemctl reload nginx
    ```
    Ожидаемо: `nginx -t` проходит, портал отдаёт то же самое — но конфиг уже другой.

11. **UBU01.** Обнаруживаем дрейф, не заходя на WEB01:
    ```bash
    ansible-playbook -i inventory.ini site.yml --check --diff | tail -15
    ```
    Ожидаемо: `changed=1`, в diff строка `-root /var/www/portal-old;` / `+root /var/www/portal;`.

12. **UBU01.** Устраняем дрейф прогоном плейбука и фиксируем в журнале:
    ```bash
    ansible-playbook -i inventory.ini site.yml
    curl -s -H 'Host: portal.vektor.lab' http://10.10.20.10/
    ```
    Ожидаемо: `changed=1`, затем `changed=0`, курл отдаёт версию 3. Запись в `stand-log.md` — по разделу «Что изменилось на стенде».

## 6. Ошибки новичков и безопасность

1. **`>>` в предположении «файл же новый».** → Дубли строк, конфликтующие значения, конфиг растёт как снежный ком. → Правильно: `grep -q ... ||`, либо сразу Ansible `lineinfile` с `regexp`.

2. **`ansible.builtin.shell` вместо `command` и без `creates`/`changed_when`.** → Задача всегда `changed`, идемпотентность не проверяется, а в продакшене скрипт может перезапустить сервис миллион раз. → Правильно: сначала искать готовый модуль (`copy`, `template`, `service`, `user`), а `command` — только с `creates` или `changed_when`.

3. **Верить `--check` без `--diff`.** → Видишь `changed=1` и не знаешь, что именно меняется; а иногда «check» показывает изменение, которого в реальном прогоне не будет (модули вроде `command` ведут себя в check-режиме иначе). → Правильно: всегда `--check --diff` и читать diff глазами.

4. **«Поправлю на проде руками, потом закоммичу».** → Классический дрейф: коммит не делается никогда, а следующий прогон IaC затирает правку. → Правильно: изменение только через коммит, даже в инциденте; в аварии — правка руками с **немедленным** переносом в Git и пометкой в инцидент-тикете.

5. **`terraform apply -auto-approve` без чтения плана.** → Применяешь не то, что хотел; в худшем случае — удаление ресурса (`2 to destroy`). → Правильно: план читается всегда, для прода — ручное подтверждение, для CI — сохранённый `-out=tfplan` и применение именно этого файла.

6. **Считать `changed=0` доказательством корректности.** → Инструмент может «не видеть» дрейф: файл не под управлением, ресурс создан в обход IaC (`kubectl run` мимо манифестов), проверка не покрывает этот слой. → Правильно: `changed=0` доказывает идемпотентность, но не полноту покрытия. Отдельно вести инвентарь «что под IaC, а что нет».

7. **Не различать `plan -refresh-only` и обычный `plan`.** → Путаница: кажется, что инфраструктура «уехала», а на самом деле устарел state. → Правильно: сначала refresh-only, потом обычный план.

8. **Секреты в открытом виде в репозитории IaC.** → Пароль от БД в `group_vars/all.yml` уезжает в историю Git навсегда. → Правильно: Vault/SOPS/age, внешние секрет-сторы (тема урока 66).

### Безопасность

- **`host_key_checking = False` в `ansible.cfg`** — удобно в лабе, недопустимо в бою: отключает проверку SSH-ключей хоста и открывает дверь MITM. В лабе — только на время, с явной пометкой в `stand-log.md`.
- **`NOPASSWD: ALL` для пользователя деплоя** — в лабе экономит ввод пароля; в рабочей среде это фактически root без пароля. Правильно: узкий sudoers на конкретные команды (`systemctl reload nginx`), отдельный сервисный аккаунт.
- **Приватные ключи и токены в Git** — даже в приватном репозитории. Только секрет-сторы, короткоживущие токены, ротация.
- **Давать IaC-пайплайну полные права на прод** — компромисс CI-раннера равен компромиссу всей инфраструктуры. Правильно: отдельные окружения и роли, ручное подтверждение на prod, least privilege.
- **Удалять «лишние» файлы при разборе дрейфа.** Сначала выяснить, чьё это изменение. В лабе `rm -rf /var/www/portal-old` безопасен; на рабочем сервере за таким `rm` может стоять чей-то незакоммиченный хотфикс.

## 7. Вопросы на собеседовании

**1. Чем декларативный подход отличается от императивного? Приведите примеры и скажите, когда императив уместен.**

Ответ: императивный описывает последовательность действий («как»), декларативный — целевое состояние («что»). Примеры императива: bash-скрипт, `useradd`, `kubectl run`. Декларатива: Terraform (`resource "..."`), Kubernetes-манифесты, Ansible-задачи с модулями `copy`/`service`, ArgoCD. Декларативный инструмент сам вычисляет разницу между фактом и желаемым и применяет только её — отсюда идемпотентность и устойчивость к повторным запускам. Императив уместен там, где нужна сложная процедурная логика: миграции данных, одноразовые операции, сценарии с ветвлениями и внешними API без провайдера; ещё — в bootstrap, когда декларативный инструмент ещё нечем запустить. На практике часто гибрид: императивный bootstrap, дальше декларативная конфигурация.

*Что хочет услышать интервьюер:* чёткое «как/что», примеры из разных слоёв (провижининг vs конфигурация), понимание, что декларативность ≠ отсутствие зависимостей.
*Красный флаг:* «декларативный — это когда YAML» или «Ansible — полностью декларативный».

**2. Что такое идемпотентность и почему она критична? Приведите неидемпотентную команду и способ её исправить.**

Ответ: операция идемпотентна, если повторное выполнение даёт тот же результат без побочных эффектов. Критична потому, что IaC-код запускается многократно: при каждом деплое, в CI, при аварийном восстановлении. Неидемпотентный пример — `echo '...' >> /etc/sysctl.conf` или `useradd ivanov` (второй запуск падает). Исправление: проверка состояния перед действием (`grep -qxF ... ||`), либо переход на инструмент с декларативным модулем (`ansible.builtin.lineinfile` с `regexp`, `ansible.builtin.user`). В Ansible признак — `changed=0` при повторном прогоне. Отдельно упомяну сходимость: Ansible может сходиться за несколько прогонов, но каждый прогон не должен ломать уже достигнутое.

*Что хочет услышать интервьюер:* понимание «почему», а не заученное определение; конкретный пример и конкретное лекарство; проверка `changed=0`.
*Красный флаг:* путает идемпотентность с «детерминированностью» или говорит, что `command` в Ansible идемпотентен по умолчанию.

**3. Что такое дрейф конфигурации, как его обнаружить и как предотвратить?**

Ответ: дрейф — расхождение фактического состояния системы с описанным в коде. Причины: ручные правки, изменения через веб-консоли, обновления пакетов в обход IaC, восстановление из бэкапа. Обнаружение: `ansible-playbook --check --diff`, `terraform plan -detailed-exitcode` (код 2 = есть расхождения) в джобе по расписанию, `kubectl diff`, `argocd app diff`, `dpkg --verify` для файлов пакетов, etckeeper для истории `/etc`. Предотвращение: единственный путь изменений — коммит в Git (GitOps-модель), запрет прямого доступа к прод-серверам у большинства инженеров, auto-sync с self-heal в ArgoCD, регулярный drift-check в CI с алертом.

*Что хочет услышать интервьюер:* что дрейф — это процесс, а не разовая авария; что есть автоматическая детекция по расписанию, а не «когда заметим»; связка с Git как источником истины.
*Красный флаг:* «дрейфа не будет, если всё делать правильно» — без механизма обнаружения.

**4. Ansible — декларативный или императивный инструмент?**

Ответ: гибрид, и точнее — процедурный инструмент с декларативными модулями. Плейбук задаёт порядок выполнения задач (это императив: сверху вниз, роли, `handlers` в конце), а каждая задача через модуль описывает состояние (`state: present`, `mode: '0644'`). Поэтому идемпотентность в Ansible — свойство **модуля**, а не инструмента: `copy` идемпотентен, `command`/`shell` — нет, пока не добавишь `creates`/`changed_when`. Сравнение: Terraform декларативен на уровне всего графа ресурсов, Ansible — на уровне отдельной задачи.

*Что хочет услышать интервьюер:* понимание, что «декларативность» живёт на уровне модуля, и что за идемпотентность `shell`-задач отвечает автор плейбука.
*Красный флаг:* категоричное «Ansible декларативный» без оговорок либо «Ansible — это просто скрипты по SSH».

**5. Вам нужно срочно поправить прод в 3 часа ночи. Ваши действия с точки зрения IaC?**

Ответ: сначала — стабилизировать сервис. Разрешён аварийный хотфикс руками, но он обязательно фиксируется: сразу после стабилизации делаю коммит в IaC-репозиторий (или issue с точным diff), чтобы состояние из кода совпало с реальностью. Параллельно — `--check --diff`, чтобы понять, не затрёт ли IaC мою правку при следующем плановом прогоне; на время инцидента auto-sync/автоприменение можно приостановить (`argocd app set --sync-policy none`, отключить джобу), иначе через 3 минуты всё вернётся. Дальше — постмортем: почему понадобилась ручная правка, что в процессе IaC этому помешало (долгий пайплайн, отсутствие параметра, плохой alerting), и как это исправить в коде. Правило: аварийный доступ руками есть, но у него есть цена — обязательный коммит и разбор.

*Что хочет услышать интервьюер:* прагматизм без догматизма — доступ руками не отменяется, но обратный путь в Git обязателен; понимание, что auto-sync может «откатить» хотфикс.
*Красный флаг:* «всегда только через пайплайн, даже в аварию» (нет плана на 3 утра) или «поправлю руками и забуду».
