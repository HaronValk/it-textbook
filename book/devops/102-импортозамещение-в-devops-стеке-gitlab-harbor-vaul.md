## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Импортозамещение в ИТ** — это не «поставить русское вместо иностранного». На практике это три разных процесса, которые постоянно путают:

1. **Реестр российского ПО** (ведёт Минцифры). Продукт в реестре — значит, его можно закупать за счёт бюджета и он проходит согласование в госкомпаниях. Наличие в реестре *ничего не говорит* о качестве и совместимости. `[ПРОВЕРИТЬ актуальный адрес реестра: reestr.digital.gov.ru]`
2. **Сертификация ФСТЭК/ФСБ** — для средств защиты информации. Если твой секрет-сервер должен защищать ГИС или КИИ, ему нужен сертификат, а криптография — по ГОСТ.
3. **Технологическая независимость** — когда ты меняешь продукт не из-за закона, а потому что вендор ушёл, поднял цену или сменил лицензию на неудобную.

Второй важный момент — **лицензии**. Запомни три аббревиатуры: MIT/Apache 2.0 (делай что хочешь), SSPL/BUSL (open source с ограничениями — нельзя строить на этом облачный сервис, а иногда и просто нельзя использовать в компании без юриста) и «проприетарная с уходом вендора». GitLab Community Edition — MIT, Harbor — Apache 2.0, а вот Vault и Terraform с августа 2023-го под BUSL 1.1. Именно поэтому появились форки **OpenBao** (от Vault) и **OpenTofu** (от Terraform) под эгидой Linux Foundation — API и синтаксис совместимы, лицензия снова свободная.

Третий момент — **API-совместимость**. Миграция проходит дёшево, когда новый продукт говорит на том же протоколе:

```text
┌──────────────────────── DevOps-стек «Вектор» и кандидаты на замену ────────────────────────┐
│ Слой              Сейчас (стенд)          Кандидат (RU / open source)      Протокол/API    │
├────────────────────────────────────────────────────────────────────────────────────────────┤
│ ОС серверов       Ubuntu 24.04            Astra Linux SE, РЕД ОС, ALT     systemd, dpkg   │
│ Оркестратор       k8s upstream (k8s-*)    Deckhouse Kubernetes Platform   Kubernetes API  │
│ Git + CI/CD       GitLab CE (GIT01)       GitFlic, GitVerse               Git (SSH 22/443)│
│ Реестр образов    Harbor (HARBOR01)       Harbor CE, Deckhouse Registry   Registry API v2 │
│ Секреты           Vault (UBU01:8200)      OpenBao, отеч. хранилища        HTTP API 8200   │
│ IaC               Terraform               OpenTofu                        HCL             │
│ Облако            —                       Yandex Cloud, VK Cloud, Cloud.ru S3/VM API       │
│ Криптография      OpenSSL                 КриптоПро CSP, ViPNet CSP       ГОСТ TLS        │
└────────────────────────────────────────────────────────────────────────────────────────────┘

Поток «как это работает сегодня»:

разработчик ──git push (22/443)──► GIT01 (GitLab CE)
                                     │  CI-раннер собирает образ
                                     ▼
                          HARBOR01 (Registry API v2, 443) ──trivy scan (урок 98)
                                     │  docker pull
                                     ▼
                          k8s-cp01 (API 6443) / k8s-w01 / k8s-w02
                                     │  читает секреты
                                     ▼
                          UBU01:8200 (Vault / OpenBao, HTTP API)
```

Ключевая мысль: **самые безболезненные замены — те, где совпадает протокол**. Vault → OpenBao: клиент `vault` работает без изменений. Terraform → OpenTofu: тот же HCL, тот же state. Harbor → Harbor CE: вообще ничего менять не надо. А вот GitLab → GitFlic — это смена API CI-пайплайнов, и вот там начинается настоящая работа.

## 3. Аналогия из жизни

Представь, что ты меняешь всю сантехнику в девятиэтажке, где живут люди.

Трубы текут (лицензия кончилась), но отключить воду на весь дом нельзя — разработчики работают. Значит: сначала составляешь схему стояков (инвентаризация), потом закупаешь трубы нужного диаметра и **проверяешь резьбу** (совместимость API), потом меняешь по одному стояку, начиная с того, где меньше всего жильцов (пилот на некритичном сервисе). Обязательно держишь наготове заглушки и старые трубы — если новая резьба не подошла, откатываешься за час, а не за неделю. И предупреждаешь жильцов: «в четверг с 10 до 14 воды не будет».

Где аналогия ломается: трубы не выпускают новую версию раз в квартал с breaking changes в API и не требуют переписать половину конфигурации. ПО требует.

## 4. Практика и команды

### 4.1. Понять, на чём вообще стоит стенд

```bash
cat /etc/os-release
```

Типичный вывод:

```text
PRETTY_NAME="Ubuntu 24.04 LTS"
ID=ubuntu
VERSION_ID="24.04"
```

Смотрим `ID` и `VERSION_ID`: от них зависит, есть ли нужный пакет в репозитории Astra Linux или РЕД ОС и какой версии. Это первая строка твоего инвентаря.

### 4.2. Версия и редакция GitLab

```bash
sudo gitlab-rake gitlab:env:info
sudo gitlab-ctl status
```

Сокращённый вывод:

```text
System information
System:         Ubuntu 24.04
GitLab information
Version:        17.x.x
Revision:       ...
Edition:        Community Edition
```

Что смотреть: `Edition`. `Community Edition` — MIT, живём спокойно. `Enterprise Edition` без купленной лицензии — это EE-код с функциями CE и баннером «trial истёк»; `gitlab-ctl status` покажет, какие сервисы (`puma`, `sidekiq`, `postgresql`, `redis`, `gitaly`) реально подняты.

### 4.3. Harbor: узнать версию и настройки через API

```bash
curl -sk https://10.10.10.55/api/v2.0/systeminfo | jq '{harbor_version, registry_url, auth_mode, with_trivy}'
```

Разбор: `-s` — тихо, без прогресс-бара; `-k` — не проверять сертификат (в лабе он самоподписанный, **в проде так нельзя**); `jq` — вытащить нужные поля из JSON. `[ПРОВЕРИТЬ точный набор полей в вашей версии Harbor]`

Вывод:

```json
{
  "harbor_version": "v2.x.x",
  "registry_url": "10.10.10.55",
  "auth_mode": "db_auth",
  "with_trivy": true
}
```

Смотрим `with_trivy` — встроенный сканер включён или нет (пригодится для урока 98).

### 4.4. Список проектов и образов в реестре

```bash
curl -sk -u admin:'Lab#2026-vektor' \
  'https://10.10.10.55/api/v2.0/projects?page_size=100' | jq -r '.[].name'

curl -sk -u admin:'Lab#2026-vektor' \
  'https://10.10.10.55/api/v2.0/projects/devops/repositories?page_size=100' | jq -r '.[].name'
```

`-u` — basic auth. **Пароль в командной строке виден в `ps`** — в боевой среде используй `--netrc-file` или переменную окружения. Это ровно тот класс ошибок, который ловит Gitleaks (урок 98).

### 4.5. Проверить образ в реестре: digest и слои

```bash
skopeo inspect --tls-verify=false docker://10.10.10.55/devops/web:1.0
```

Если `skopeo` нет: `sudo apt install -y skopeo`. Вывод (сокращённо):

```json
{
  "Name": "10.10.10.55/devops/web",
  "Digest": "sha256:...",
  "RepoTags": ["1.0"],
  "Architecture": "amd64",
  "Os": "linux"
}
```

Главное здесь — `Digest`. В манифестах деплоя надо пинить образ по digest, а не по `:latest`, иначе после переезда на другой реестр ты не докажешь, что это тот же самый бинарь.

### 4.6. Перенести образ между реестрами (сама суть миграции)

```bash
skopeo copy --all \
  --src-tls-verify=true --dest-tls-verify=false \
  docker://docker.io/library/nginx:1.27 \
  docker://10.10.10.55/mirror/nginx:1.27
```

`--all` — тащить все артефакты: мультиархитектурные манифесты и подписи. Без него ты молча потеряешь ARM-сборку или аттестацию cosign (урок 97).

### 4.7. Инвентаризация образов прямо из манифестов

```bash
grep -rhoE 'image:[[:space:]]*[^[:space:]]+' deploy/ | sed 's/image:[[:space:]]*//' | sort -u
```

Это и есть твой список «что придётся перетащить». На реальном проекте таких строк сотни, и половина из них — с Docker Hub, который может быть недоступен.

### 4.8. Поднять OpenBao рядом с Vault

```bash
docker run -d --name openbao-dev --cap-add=IPC_LOCK \
  -e BAO_DEV_ROOT_TOKEN_ID=root \
  -p 127.0.0.1:8201:8200 \
  quay.io/openbao/openbao:latest server -dev -dev-listen-address=0.0.0.0:8200
```

Разбор: `--cap-add=IPC_LOCK` — разрешить `mlock` (чтобы секреты не ушли в swap); `-dev` — режим разработки: **хранилище в памяти, root-токен в открытом виде, всё пропадает при рестарте**. Только для лабы. `-p 127.0.0.1:8201:8200` — слушаем только localhost и на другом порту, чтобы не конфликтовать с Vault. `[ПРОВЕРИТЬ актуальный тег образа и его расположение: quay.io/openbao/openbao]`

### 4.9. Проверить совместимость API старым клиентом

```bash
VAULT_ADDR=http://127.0.0.1:8201 VAULT_TOKEN=root vault status
docker exec -e BAO_ADDR=http://127.0.0.1:8200 -e BAO_TOKEN=root openbao-dev bao secrets list
```

Если `vault status` против OpenBao отвечает `Sealed: false` — совместимость на уровне API есть, и это главный аргумент в плане миграции: приложениям менять код не придётся.

### 4.10. Записать и прочитать секрет

```bash
export VAULT_ADDR=http://127.0.0.1:8201 VAULT_TOKEN=root
vault kv put secret/vektor/db password='Lab#2026-vektor'
vault kv get -format=json secret/vektor/db | jq -r '.data.data.password'
```

`kv put` — запись в KV v2; `-format=json` и `jq` — чтобы вытащить одно поле в скрипте, не парся человекочитаемый вывод.

### 4.11. Kubernetes: тянуть образ из Harbor по токену

```bash
kubectl create secret docker-registry harbor-pull -n default \
  --docker-server=10.10.10.55 \
  --docker-username='robot$devops+ci' \
  --docker-password="$HARBOR_TOKEN"

kubectl run pull-test --image=10.10.10.55/devops/web:1.0 \
  --overrides='{"spec":{"imagePullSecrets":[{"name":"harbor-pull"}]}}'
```

Имя robot-аккаунта в Harbor имеет вид `robot$<проект>+<имя>`. Если реестр переедет, поменяется только `--docker-server` и токен — сам манифест пода останется прежним.

### 4.12. OpenTofu вместо Terraform

```bash
tofu version
tofu init -lockfile=readonly
tofu plan
```

`tofu` — форк с тем же HCL и тем же форматом state. `-lockfile=readonly` полезен, чтобы на первом прогоне **не перезаписать** `.terraform.lock.hcl` чужими хешами провайдеров. `[ПРОВЕРИТЬ флаги вашей версии OpenTofu]`

### 4.13. Deckhouse: посмотреть, что предлагает платформа

```bash
kubectl get nodes -o wide
kubectl get pods -n d8-system
```

Deckhouse ставит свои системные компоненты в namespace `d8-system`, а CLI-утилита называется `d8`. `[ПРОВЕРИТЬ имя CLI и namespace в актуальной документации deckhouse.io]` Полноценную установку на стенде мы не делаем — для неё нужен отдельный кластер и ресурсы; в лабе мы фиксируем её как кандидата и критерии оценки.

6. Проверь, не истёк ли срок действия у оставшихся роботов (`Expiration`), и не поменялся ли пароль в CI-переменной GIT01 (`Settings → CI/CD → Variables`).

**Решение.** Создай нового робота `robot$devops+ci` с правами `pull` (и `push`, если он же пушит из CI), скопируй токен, обнови masked-переменную `HARBOR_TOKEN` в проекте GIT01, обнови secret в k8s:

```bash
kubectl delete secret harbor-pull -n default
kubectl create secret docker-registry harbor-pull -n default \
  --docker-server=10.10.10.55 \
  --docker-username='robot$devops+ci' --docker-password="$NEW_TOKEN"
kubectl rollout restart deployment/hr-portal
```

**Что ответить пользователю:** «Портал собирается из нашего внутреннего реестра образов. Ночью истёк служебный доступ, из-за этого новые копии не запускались. Доступ перевыпустил, портал поднимается, через 5–10 минут проверьте, пожалуйста. Причину зафиксировал, поставлю срок действия токена на мониторинг».

**Закрытие заявки:** категория «инфраструктура, реестр образов», в решении указать причину и профилактику (алерт на срок жизни робота + healthcheck pull в CI).

## 6. Ошибки новичков и безопасность

**1. «Большой взрыв».** Ошибка: заменить GitLab, реестр и секреты в одну ночь. → К чему: утром не работает ничего, а причину искать в трёх новых системах одновременно. → Как правильно: по одному слою за раз, начиная с наименее связанного с людьми (обычно реестр), с планом отката на каждый шаг.

**2. Выбор по реестру, а не по задаче.** Ошибка: «в реестре отечественного ПО есть продукт X, берём его». → К чему: продукт не умеет Registry API v2, и весь пайплайн переписывается с нуля. → Как правильно: сначала матрица требований (API, протоколы, интеграции, объём), потом сверка с реестром.

**3. Игнорирование лицензий upstream.** Ошибка: «мы же self-hosted, какая разница, что там за лицензия». → К чему: BUSL/SSPL может запрещать использование в коммерческом сервисе; юристы приходят через год. → Как правильно: перед внедрением смотреть `LICENSE` в репозитории и фиксировать вывод в `plan.md`.

**4. Секреты в CI-переменных без маскирования.** Ошибка: токен реестра в открытой переменной и в логах джобы. → К чему: утечка, и её потом находят Gitleaks'ом в истории Git. → Как правильно: masked + protected переменные, короткий TTL у роботов, ротация (урок 96).

**5. Dev-режим в проде.** Ошибка: OpenBao запущен с `-dev`. → К чему: секреты в памяти, root-токен `root`, всё исчезает при рестарте. → Как правильно: нормальное хранилище (Raft/file), инициализация, unseal-ключи в сейфе, а не в `docker-compose.yml`.

**6. Не проверить bus factor форка.** Ошибка: поставить малоизвестный форк «потому что без лицензионных ограничений». → К чему: через год нет патчей безопасности. → Как правильно: смотреть, под чьей опекой проект (Linux Foundation, CNCF — хороший знак), частоту коммитов, число мейнтейнеров.

**7. Миграция без фиксации digest.** Ошибка: перетащить образы по тегу `:latest`. → К чему: после переезда в проде другой бинарь, и никто не знает какой. → Как правильно: `skopeo copy --all` + пиннинг по digest + SBOM (урок 97).

**8. Забыть про криптографию.** Ошибка: считать, что «заменили Vault на OpenBao» закрывает требования регулятора. → К чему: если система в области действия 187-ФЗ/152-ФЗ с требованиями ФСТЭК, нужен сертифицированный СКЗИ и ГОСТ-TLS, а это отдельный слой (урок 101). → Как правильно: уточнять у ИБ класс защищённости до выбора продукта.

### Безопасность

В боевой среде **нельзя**: хранить пароль Harbor/`root`-токен в истории bash, в `docker-compose.yml` в Git или в открытых CI-переменных; запускать Vault/OpenBao в dev-режиме; отключать `--tls-verify` «навсегда, потому что так проще»; выдавать роботу права `push` там, где нужно только `pull`; оставлять срок жизни робота «бессрочно». Всё это не «стиль», а прямые находки аудита. Правильный минимум: TLS с валидным сертификатом (внутренний CA — норм), короткоживущие токены, минимальные права, отдельный робот на каждый пайплайн, логи доступа к реестру и секретам.

## 7. Вопросы на собеседовании

**Вопрос 1. Чем OpenBao отличается от Vault и почему он вообще появился?**

Ответ: В августе 2023 HashiCorp перевела Vault, Terraform, Consul и ряд других продуктов с MPL 2.0 на BUSL 1.1 — лицензию, которая ограничивает коммерческое использование и позволяет вендору менять условия. Сообщество форкнуло код последней MPL-версии: так появился OpenBao, переданный под опеку Linux Foundation. Он совместим по HTTP API и CLI с Vault, поэтому приложениям и скриптам обычно не нужно меняться — меняется установка и путь миграции данных (нужен аккуратный перенос хранилища и переинициализация/unseal). Похожая история — Terraform → OpenTofu (тот же HCL, тот же state), Redis → Valkey.

*Что хочет услышать интервьюер:* что ты понимаешь разницу между «форк из-за лицензии» и «новый продукт», и что совместимость API — это то, что делает миграцию дешёвой.

*Красный флаг:* «OpenBao — это наш российский Vault» (это не российский продукт) или «просто переставил бинарь, всё работает» без упоминания миграции данных и unseal-ключей.

**Вопрос 2. Как бы вы спланировали миграцию self-hosted GitLab на отечественный аналог?**

Ответ: Пять фаз. (1) Инвентаризация: версия и редакция, количество проектов и групп, объём Git-данных, активные пайплайны, runner'ы, интеграции (registry, webhooks, LDAP), кто и как использует API. (2) Классификация: что переносится 1:1 (git-репозитории), что переписывается (`.gitlab-ci.yml` → другой синтаксис), что теряется (например, специфичные функции CI). (3) Пилот на 2–3 некритичных репозиториях с зеркалированием push в оба места. (4) Полная миграция по группам с freeze-периодом и объявленным окном. (5) Вывод старого GitLab из эксплуатации через месяц read-only. Отдельно: план отката на каждом шаге, потому что «переехали и сломали CI» — это остановка всей разработки.

*Что хочет услышать интервьюер:* инвентаризация → пилот → волны → критерии отказа → откат. И понимание, что дороже всего не перенос репозиториев, а смена CI.

*Красный флаг:* «сделаем `git clone --mirror` и всё» — про CI, runner'ы, права и интеграции ни слова.

**Вопрос 3. Что такое реестр российского ПО и как он влияет на выбор инструмента?**

Ответ: Это государственный реестр отечественных программ для ЭВМ и баз данных, который ведёт Минцифры. Для госкомпаний и бюджетных организаций закупка ПО вне реестра ограничена или запрещена; наличие в реестре — формальное условие закупки. Важно: реестр не оценивает техническое качество и совместимость, поэтому инженерное решение всё равно принимается по требованиям (API, протоколы, поддержка, сообщество), а реестр — это фильтр для закупки. Плюс отдельно существует сертификация ФСТЭК/ФСБ для средств защиты информации — это другой список и другие требования.

*Что хочет услышать интервьюер:* что ты не путаешь реестр ПО, сертификацию ФСТЭК и открытый исходный код, и что ты не выбираешь инструмент только по галочке в реестре.

*Красный флаг:* «если в реестре — значит безопасно» или наоборот «реестр — это фикция, можно игнорировать».

**Вопрос 4. Почему смена лицензии HashiCorp вообще важна для компании, мы же ставим Vault на свои серверы?**

Ответ: BUSL ограничивает не развёртывание как таковое, а предоставление продукта третьим лицам как сервиса, и даёт вендору право менять условия в будущих версиях. На практике это значит: юридический риск при использовании в продукте, невозможность зафиксировать условия навсегда, риск цен и риск того, что следующая версия окажется недоступной. Инженерное следствие — либо остаться на последней MPL-версии (без патчей), либо перейти на форк (OpenBao/OpenTofu), либо купить коммерческую лицензию. Решение принимается совместно с юристами и ИБ, а не только командой.

*Что хочет услышать интервьюер:* что лицензия — это инженерный риск (нет патчей, непредсказуемость), а не только юридическая формальность.

*Красный флаг:* «open source же, какая разница» или «обойдём лицензию».

**Вопрос 5. Что такое Deckhouse и зачем он нужен, если есть upstream Kubernetes?**

Ответ: Deckhouse Kubernetes Platform от «Флант» — российская платформа управления Kubernetes, построенная вокруг готового набора модулей: ingress, мониторинг, логирование, политики, реестр, обновления. Ключевые отличия от «голого» k8s: единый способ включения модулей через CRD-ресурсы, предсказуемые обновления кластера, готовые интеграции с отечественной инфраструктурой и сертификаты (ФСТЭК) для части поставок. Цена — привязка к вендору и его модель подписки. В upstream k8s ты собираешь всё сам и отвечаешь за совместимость версий аддонов; в Deckhouse часть этой работы уже сделана за тебя.

*Что хочет услышать интервьюер:* понимание trade-off «готовое решение vs гибкость и vendor lock-in», а не рекламный пересказ сайта.

*Красный флаг:* «Deckhouse — это дистрибутив Kubernetes, он лучше обычного» без единого слова о подписке, привязке и требованиях к ресурсам. `[ПРОВЕРИТЬ текущий состав модулей и условия лицензирования в документации]`
