# Как учиться DevOps без коммерческого опыта: pet-проекты, документация в Git, портфолио на GitHub/GitLab

## 1. Введение (зачем это нужно в реальной работе)

Тикет в поддержку «Вектора», 09:14:

> **Мария Петрова / WIN10-CL02 / «Не могу зайти на \\FS01\HR — пишет "нет доступа". У Ивана из бухгалтерии всё открывается. Мне надо сегодня закрыть табель, помогите!» / Средняя**

Ты открываешь оснастку, видишь, что petrova не входит в `GG-HR`, добавляешь её в группу, просишь перелогиниться, закрываешь заявку. 12 минут. Навык есть — а доказать его на собеседовании нечем: в резюме «администрирование Windows Server», и всё.

Разница между «я это умею» и «я это умею, вот подтверждение» — это и есть весь смысл портфолио. В DevOps почти нет сертификатов, которые сами по себе что-то доказывают, зато есть очень дешёвый способ показать мышление: репозиторий, где лежит твой стенд, описанный как код, с историей коммитов, инструкциями и разбором того, что сломалось. Нанимающий тимлид за 5 минут чтения README понимает про тебя больше, чем из получасового разговора.

После этой главы ты будешь уметь: превращать любую свою работу (даже учебную заявку в техподдержку) в pet-проект; вести документацию как код в Git, а не в Word на рабочем столе; собирать репозиторий, который не стыдно дать ссылкой; и понимать, что именно смотрит интервьюер, когда открывает твой GitLab.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Pet-проект ≠ учебная лаба.** Лаба из туториала проверяет, что ты повторил за автором. Pet-проект проверяет, что ты сам поставил задачу и сам её решил. Держи формулу, по которой строится 90% хороших портфолио-репозиториев:

- **Проблема** — что болело (реальная заявка, реальный косяк, «надоело руками»).
- **Ограничения** — что нельзя было (только бесплатные версии, одна ВМ, нет денег на облако).
- **Решение** — код, конфиги, пошаговая инструкция.
- **Доказательство** — как проверить, что работает (скриншот метрики, вывод команды, лог CI).
- **Ретроспектива** — что не получилось и что бы сделал иначе. Это самый ценный блок, его почти никто не пишет.

**Git внутри.** Git — распределённая система контроля версий (VCS). Ключевое слово «распределённая»: у каждого клона лежит полная история, а не только последняя версия файлов. Внутри Git хранит четыре типа объектов: `blob` (содержимое файла), `tree` (каталог — список имён и ссылок), `commit` (снимок дерева + автор + дата + ссылка на родителя) и `tag`. Каждый объект адресуется хешем его содержимого — поэтому «переписать историю» означает «создать другие объекты с другими хешами», а не «отредактировать строчку».

Ветка в Git — это не копия каталога, а просто файл-указатель на коммит (в `.git/refs/heads/`). `HEAD` — указатель на текущую ветку. Отсюда весь синтаксис: `main~1` — «родитель последнего коммита в main».

```text
┌──────────────┐   git add    ┌──────────────┐  git commit  ┌──────────────┐
│ Working tree │ ───────────► │    Index     │ ───────────► │  Repository  │
│ (файлы на    │              │ (staging,    │              │ (.git, объек-│
│  диске)      │ ◄─────────── │  что войдёт  │              │  ты, ветки)  │
└──────────────┘ git restore  │  в коммит)   │              └──────┬───────┘
                              └──────────────┘                     │
                                                     git push      │ git pull
                                                                   ▼
                              ┌────────────────────────────────────────────┐
                              │ Remote: GitLab CE на GIT01 (10.10.10.50)   │
                              │ или bare-репозиторий /srv/git/*.git        │
                              │         │                                  │
                              │         ▼  pipeline (.gitlab-ci.yml)       │
                              │   runner: build → test → deploy            │
                              └────────────────────────────────────────────┘
```

**Транспорт.** Git умеет работать по HTTPS (443), по SSH (22) и по `git://` (9418 — не используем, там нет аутентификации). В корпоративной среде стандарт — SSH-ключи: `git@10.10.10.50:group/repo.git`. Для GitHub/GitLab это те же 22/443.

**Документация как код (docs-as-code).** Принцип: документация живёт в том же репозитории, что и код, в формате Markdown, проходит ревью через merge request и версионируется тегами. Тогда инструкция не устаревает молча — она устаревает в конкретном коммите, и видно, кто это сделал и почему.

**Структура портфолио-репозитория.** Универсальный каркас, который узнаёт любой тимлид:

```text
vektor-stand-docs/
├── README.md            # проблема, схема, quickstart, что проверять
├── docs/
│   ├── stand.md         # описание стенда: машины, сети, адреса
│   ├── adr-001-git-hosting.md   # Architecture Decision Record: почему так
│   └── troubleshooting.md
├── runbooks/
│   └── fs01-hr-access.md        # пошаговое решение конкретной заявки
├── scripts/
│   └── check-access.sh
├── .gitignore
├── CHANGELOG.md
└── LICENSE
```

**Где хостить.** GitHub — мировой стандарт, публичные репозитории бесплатны, у него же бесплатные минуты CI для публичных проектов `[ПРОВЕРИТЬ актуальные лимиты]`. GitLab — стандарт в крупных РФ-компаниях, чаще в self-managed виде: именно поэтому у тебя на стенде появляется GIT01. Есть и отечественные варианты (GitFlic, Gitea/Forgejo как self-hosted) — их актуальный статус и условия `[ПРОВЕРИТЬ]`. Практический вывод: не привязывайся к одной платформе, держи репозиторий с двумя remote (личный GitHub + учебный GitLab), команды одинаковые.

Что реально смотрит интервьюер, открыв твой репозиторий: (1) запускается ли это по README за 5 минут; (2) осмысленна ли история коммитов; (3) объясняешь ли ты trade-off, а не только «сделал по гайду». Всё остальное — украшения.

## 3. Аналогия из жизни

Портфолио DevOps-инженера — это лётная книжка пилота, а не диплом в рамочке. В лётной книжке записано: дата, тип самолёта, маршрут, часы налёта, кто проверял. Туда же попадают и неприятности — уход на второй круг, срабатывание сигнализации, разбор с инструктором. Никто не требует от пилота «коммерческого опыта», чтобы начать книжку: первый час налёта — тоже час налёта, если он записан и подтверждён.

Твой Git-репозиторий работает так же: каждый коммит — запись в книжке с датой и автором, каждый runbook — разбор полёта, каждый тег — «этап сдан». Поэтому «у меня нет коммерческого опыта» перестаёт быть приговором: есть налёт часов, просто он на учебном стенде.

Аналогия ломается в одном месте: в лётной книжке часы подделать нельзя, а репозиторий можно набить чужими проектами — и это выясняется на первом же техническом вопросе.

## 4. Практика и команды

Дальше всё выполняется на UBU01 (`10.10.10.30`). Если на Windows-части стенда Git тоже есть — те же команды работают в Git Bash, а GUI-путь в VS Code: панель **Source Control** (Ctrl+Shift+G).

**1. Установка и личность автора.** Без `user.name`/`user.email` Git не даст коммитить — это первое, обо что спотыкаются.
```bash
sudo apt update && sudo apt install -y git
git --version
git config --global user.name "adm.student"
git config --global user.email "adm.student@corp.vektor.lab"
git config --global init.defaultBranch main
git config --global --list
```
`--global` = в `~/.gitconfig`, для всех репозиториев пользователя. `init.defaultBranch main` избавит от предупреждения про `master` в каждом новом репозитории. Вывод `--list` — три строки, проверь, что email именно тот (он попадёт в каждый коммит навсегда).

**2. Инициализация и состояние.**
```bash
mkdir -p ~/work/vektor-stand-docs && cd ~/work/vektor-stand-docs
git init
git status -sb
```
```text
## No commits yet on main
```
`-s` — короткий формат, `-b` — показать ветку. Дальше в этой строке появится `## main...origin/main [ahead 1]` — это и есть индикатор «локально есть, на сервере нет».

**3. `.gitignore` — раньше первого коммита.** Создай файл:
```text
# секреты и локальное окружение
.env
*.key
*.pem
secrets/
# мусор
*.log
.venv/
node_modules/
__pycache__/
# terraform
.terraform/
*.tfstate
*.tfstate.backup
```
Проверить, что правило сработало: `git check-ignore -v .env` → выведет строку из `.gitignore`, которая его отбросила.

**4. Индекс: точечное добавление.** `git add -A` берёт всё, `-p` — по кускам, интерактивно.
```bash
git add README.md .gitignore
git add -p scripts/check-access.sh
```
```text
@@ -1,3 +1,4 @@
 #!/usr/bin/env bash
+# проверка доступа к \\FS01\HR для пользователя
```
Ключи `y/n/s/q` — принять кусок / пропустить / разбить на более мелкие / выйти. Это единственный способ делать осмысленные коммиты, когда правок много.

**5. Коммит по Conventional Commits.**
```bash
git commit -m "docs(readme): описание стенда «Вектор» и quickstart"
```
Формат `тип(область): сообщение`, типы: `feat`, `fix`, `docs`, `chore`, `refactor`, `ci`. Не «update», а «что и зачем изменилось». Бонус: по таким сообщениям потом автоматически генерируется CHANGELOG.

**6. История и просмотр коммита.**
```bash
git log --oneline --graph --decorate --all
git show 8f2c1a4 --stat
```
```text
* 8f2c1a4 (HEAD -> main, tag: v0.1) docs(runbook): доступ к \\FS01\HR для petrova
* 3b7d90e chore: структура репозитория и .gitignore
* 5a1c0ff docs(readme): описание стенда «Вектор» и quickstart
```
Смотри на «ровность»: три коммита с разными типами читаются как история мышления. Один коммит «init» на 40 файлов — не читается.

**7. Поиск по содержимому и по истории.** Главный инструмент при разборе «а когда это сломалось».
```bash
git grep -n "GG-HR"
git log -S"Lab#2026-vektor" --oneline --all
```
`git grep` ищет в текущем дереве (быстрее `grep -r`, уважает `.gitignore`). `git log -S"строка"` (pickaxe) показывает коммиты, где число вхождений строки изменилось — так находят «кто добавил этот пароль».

**8. Удалённый репозиторий: bare на UBU01.**
```bash
sudo mkdir -p /srv/git && sudo chown $USER:$USER /srv/git
git init --bare /srv/git/vektor-stand-docs.git
cd ~/work/vektor-stand-docs
git remote add origin /srv/git/vektor-stand-docs.git
git remote -v
git push -u origin main
```
`--bare` — репозиторий без рабочего каталога, только объекты и ссылки; так выглядит любой серверный репозиторий (на GIT01 ровно то же внутри GitLab). `-u` связывает локальную `main` с `origin/main`, дальше хватит `git push`. `remote -v` покажет два URL: fetch и push.

**9. Ветка под задачу и слияние.**
```bash
git switch -c runbook/fs01-hr-access
# ...правим файлы...
git add runbooks/fs01-hr-access.md && git commit -m "docs(runbook): доступ к \\FS01\HR"
git switch main
git merge --no-ff runbook/fs01-hr-access
```
`switch -c` = создать ветку и перейти (старый синоним `checkout -b`). `--no-ff` запрещает «слияние перемоткой» и создаёт явный merge-коммит — по истории видно, что была отдельная задача.

**10. Теги — вехи портфолио.**
```bash
git tag -a v0.1 -m "Первый runbook + README стенда"
git push origin --tags
git tag -l
```
Аннотированный тег (`-a`) — полноценный объект с автором и сообщением, легковесный (`git tag v0.1`) — просто указатель. Для портфолио используй `-a`.

**11. Клонирование как проверка «а правда ли воспроизводимо».**
```bash
cd /tmp && git clone /srv/git/vektor-stand-docs.git check && cd check
ls -R | head -20 && git log --oneline
```
Если после клона в чистое место проект не читается — README врёт. Это ровно то, что сделает интервьюер.

**12. Если секрет уже попал в коммит.**
```bash
git rm --cached .env
git commit -m "chore: убрать .env из индекса"
```
`--cached` убирает файл только из индекса, на диске оставляет. **Важно:** файл остаётся в истории — для реальной очистки нужен `git filter-repo` (отдельный инструмент, ставится через `pipx install git-filter-repo` `[ПРОВЕРИТЬ]`) или BFG Repo-Cleaner, и обязательная ротация самого секрета.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия
- **UBU01** (`10.10.10.30`, Ubuntu Server 24.04) включена, SSH с твоего ПК работает, учётка та же, что на сисадминском треке (дальше подставляй свой логин вместо `$USER`).
- **GIT01** (`10.10.10.50`, GitLab CE + runner) — по плану урока 3 может быть ещё не развёрнут. Это нормально: лабораторная работает на bare-репозитории в `/srv/git`, а когда GIT01 появится (глава про GitLab CI), ты просто добавишь второй remote и запушишь туда. Не поднимай GitLab ради этой главы — она про практику Git и документацию, а не про установку GitLab.
- Windows-часть стенда не нужна.

### Снапшот
VMware Workstation: выбери ВМ **UBU01** → меню **VM → Snapshot → Take Snapshot** → имя `before-devops-005`. Если GIT01 у тебя уже есть — такой же снапшот и на нём.

Через CLI (опционально, `vmrun` входит в поставку Workstation) `[ПРОВЕРИТЬ путь к vmrun для твоей версии]`:
```bash
vmrun -T ws snapshot "/path/to/UBU01.vmx" before-devops-005
```

### Шаги
1. Зайди на UBU01: `ssh $USER@10.10.10.30`. Проверь Git: `git --version`. Если команда не найдена — `sudo apt update && sudo apt install -y git`. **Ожидаемо:** строка вида `git version 2.43.x` `[ПРОВЕРИТЬ точную версию в 24.04]`.
2. Настрой личность и ветку (команды из п.4.1). **Ожидаемо:** `git config --global --list` показывает три строки, включая `user.email=adm.student@corp.vektor.lab`.
3. Создай каркас: `mkdir -p ~/work/vektor-stand-docs/{docs,runbooks,scripts} && cd ~/work/vektor-stand-docs && git init`. **Ожидаемо:** `Initialized empty Git repository in /home/$USER/work/vektor-stand-docs/.git/`.
4. Создай `.gitignore` (содержимое из п.4.3) и `README.md` по шаблону ниже. **Ожидаемо:** `git status -sb` показывает `## No commits yet on main` и два untracked-файла.
```markdown
# Стенд «Вектор» — документация и runbook'и

Учебный стенд вымышленной логистической компании «Вектор» (VMware Workstation).
Цель репозитория — держать инфраструктуру и инструкции как код.

## Что внутри
- `docs/stand.md` — машины, сети, домен, учётки
- `runbooks/` — пошаговые решения типовых заявок
- `scripts/` — проверки и автоматизация

## Quickstart (5 минут)
1. `git clone <url> && cd vektor-stand-docs`
2. Прочитать `docs/stand.md`
3. Проверить: `bash scripts/check-access.sh`

## Ограничения
Только evaluation/бесплатные версии ПО. Пароли — учебные, в репозиторий не попадают.
```
5. Первый коммит: `git add README.md .gitignore && git commit -m "docs(readme): описание стенда и quickstart"`. **Ожидаемо:** `1 file changed...` (плюс `.gitignore`).
6. Создай bare-репозиторий и запушь (команды из п.4.8). **Ожидаемо:** `branch 'main' set up to track 'origin/main'`, затем `git log --oneline` — один коммит.
7. Ветка под заявку: `git switch -c runbook/fs01-hr-access`. Создай `runbooks/fs01-hr-access.md`: симптом («нет доступа к \\FS01\HR»), диагностика (`whoami /groups`, проверка членства в `GG-HR`), решение (добавить в группу, `klist purge` / перелогин), проверка, откат. **Ожидаемо:** файл на месте, `git status -sb` — `## runbook/fs01-hr-access`.
8. Коммит и слияние: `git add runbooks/ && git commit -m "docs(runbook): доступ к \\FS01\\HR для petrova"`, затем `git switch main && git merge --no-ff runbook/fs01-hr-access`. **Ожидаемо:** в выводе `Merge made by the 'ort' strategy` `[ПРОВЕРИТЬ название стратегии в твоей версии Git]`.
9. Поставь тег и запушь всё: `git tag -a v0.1 -m "Первый runbook + README стенда" && git push origin main --tags`. **Ожидаемо:** `* [new tag] v0.1 -> v0.1`.
10. Проверь воспроизводимость: `cd /tmp && git clone /srv/git/vektor-stand-docs.git check && cd check && ls -R`. **Ожидаемо:** видны `README.md`, `docs/`, `runbooks/`, `scripts/`.
11. Добавь в `README.md` строку со ссылкой на runbook, закоммить (`docs(readme): ссылка на runbook FS01`) и запушь. **Ожидаемо:** `git log --oneline --graph` — четыре коммита и один merge.
12. Открой `~/stand-log.md` на своём ПК и запиши изменения (список — в разделе «Что изменилось на стенде»).

1. Где именно утечка: `git grep -n "Lab#2026"` — находит в текущем файле.
2. Когда попала: `git log -S"Lab#2026-vektor" --oneline --all` — покажет коммит `docs(runbook): уточнил пароль`.
3. Что ещё задето: `git log -p -- runbooks/fs01-hr-access.md | grep -n "Lab#"` — видно, в каких коммитах строка присутствует.
4. Есть ли в тегах: `git tag --contains <sha>` — если да, тег тоже придётся пересоздать.

**Решение (в правильном порядке):**
1. **Сначала ротация.** В реальной среде пароль меняют немедленно: он уже считается скомпрометированным, независимо от того, успел кто-то его увидеть или нет. На стенде «ротация» = зафиксируй в stand-log, что поступил бы именно так.
2. Убери секрет из файла: замени на `{{ FS01_PASSWORD }}` и допиши в README, что значения берутся из менеджера паролей (см. урок 4).
3. Перепиши историю. Для трёх коммитов самый честный и быстрый путь — удалить bare-репозиторий и запушить заново «чистую» историю:
```bash
# правим файл, коммитим исправление
git commit -am "fix(runbook): убрать пароль из документа"
# затем чистим историю
git filter-repo --path runbooks/fs01-hr-access.md --invert-paths   # [ПРОВЕРИТЬ установку и флаги]
git tag -d v0.1 && git tag -a v0.1 -m "Первый runbook (без секретов)"
git push --force origin main --tags
```
`--force` перезаписывает ветку на сервере — в одиночном репозитории допустимо, в командном это отдельное согласование.
4. Поставь защиту от повторения: pre-commit-хук со сканером секретов (gitleaks `[ПРОВЕРИТЬ]`) или встроенный Secret Detection в GitLab CI `[ПРОВЕРИТЬ название функции]`, плюс Push Protection в GitHub `[ПРОВЕРИТЬ доступность на бесплатном плане]`.

**Что ответить пользователю:** «Пароль уже сменил. Из документа и из истории Git убрал, тег пересоздал, force push сделал. Добавил pre-commit-хук, который валит коммит, если в диффе похоже на секрет. Ссылку можно отправлять — проверь через `git grep`: пусто».

**Как закрыть заявку:** в комментарии — что сделано, время, и отдельным пунктом «профилактика: сканер секретов в pre-commit». Заявку закрывать только после проверки `git grep` по свежему клону.

## 6. Ошибки новичков и безопасность

1. **Коммит «update» на 200 файлов** → ревьюер не видит логики, история бесполезна как доказательство. Правильно: один коммит — одно смысловое изменение, Conventional Commits.
2. **Секрет в открытом виде** → утечка, и она навсегда в истории и в форках. Правильно: `.gitignore` до первого коммита, сканер секретов, менеджер паролей.
3. **README-стена текста без quickstart** → никто не разберётся, репозиторий закрывают через 30 секунд. Правильно: проблема → схема → 3 шага запуска → что должно получиться.
4. **Копипаста туториала без ссылки и понимания** → на первом вопросе «а почему тут так?» рассыпается. Правильно: ссылка на источник + абзац «что я изменил под свой стенд и почему».
5. **Нет `.gitignore`** → в репозиторий уезжают `.venv/`, `node_modules/`, `.terraform/`, а с ними `*.tfstate` — а в state бывают пароли и ключи.
6. **`git push --force` в общую ветку** → у коллег ломается история, их коммиты теряются. Правильно: force только в свою ветку и только после согласования.
7. **Портфолио из одних скриншотов** → проверяющий не может ничего запустить. Правильно: каждая картинка дублируется командой, которую можно выполнить.
8. **Публикация внутренних данных реального работодателя** → от NDA до увольнения. Правильно: вымышленные домены (`corp.vektor.lab`), вымышленные учётки, либо приватный репозиторий и обезличенные скриншоты.

**Безопасность.** Всё, что попало в публичный репозиторий, считается публичным навсегда: форки, кэши поисковиков, зеркала. Удаление коммита не отменяет утечку — отменяет её только ротация секрета. Второй момент: пароль стенда `Lab#2026-vektor` учебный именно потому, что он лежит в открытом виде в описании стенда. В боевой среде такой подход недопустим: там пароли живут в хранилище секретов (Vault, GitLab CI Variables с маской `[ПРОВЕРИТЬ]`, Kubernetes Secret + внешний KMS), а в Git попадает только ссылка на переменную.

## 7. Вопросы на собеседовании

**1. «Коммерческого опыта нет. Что вы реально делали руками и где это посмотреть?»**
Ответ: назови 2–3 проекта по формуле «проблема → решение → доказательство». Пример: «Развернул стенд из 8 ВМ в VMware: AD-домен, файловый сервер, DMZ за nftables. Всё описано как код в GitLab — README, runbook'и, ADR по решениям. Проблема была в том, что инструкции для коллег жили в переписке и устаревали; решил docs-as-code в одном репозитории, проверка — клон в чистую папку открывается за 5 минут».
*Что хочет услышать:* конкретику и признание границ («это учебный стенд, в проде я бы сделал X»).
*Красный флаг:* «делал всё по курсам» без единого своего решения и без ссылки.

**2. «Что для вас docs-as-code и зачем документация в репозитории, а не в Confluence?»**
Ответ: документация лежит рядом с кодом/конфигами в Markdown, изменения идут через merge request, ревьюятся и версионируются вместе с состоянием. Плюс: инструкция не отрывается от версии конфига; минус: нужна дисциплина и CI-проверки (линтер Markdown, сборка статического сайта). Confluence хорош для вики-контента, но он не знает, к какому коммиту относилась инструкция.
*Что хочет услышать:* понимание trade-off, а не «Git во всём лучше».
*Красный флаг:* «документация мне не нужна, код говорит сам за себя».

**3. «В репозиторий попал API-ключ. Ваши действия?»**
Ответ: сначала ротация ключа (он скомпрометирован), затем убрать из файла и из истории (`git filter-repo`/BFG), force push, пересоздать теги, уведомить команду, добавить сканер секретов в pre-commit и CI. Отдельно — проверить логи использования ключа.
*Что хочет услышать:* что ротация идёт первой, до всех git-операций.
*Красный флаг:* «просто удалю коммит и запушу заново» — без ротации.

**4. «Как вы организуете ветки и сообщения коммитов в своём проекте?»**
Ответ: trunk-based для маленьких проектов — короткие ветки `тип/краткое-имя`, вливание через merge request с `--no-ff`, сообщения по Conventional Commits, теги `v0.x` как вехи. Для одного человека это выглядит как оверхед, но это тренировка процесса, который нужен в команде.
*Что хочет услышать:* что процесс выбран осознанно, а не скопирован.
*Красный флаг:* «у меня всё в main, ветки не нужны» без объяснения почему.

**5. «Как вы докажете, что ваш проект воспроизводим?»**
Ответ: клонирую в чистый каталог на чистой ВМ и прохожу README шаг за шагом; в идеале — CI (`.gitlab-ci.yml`, GitHub Actions), который это делает автоматически при каждом push; версии ПО фиксирую (пин версий в requirements/apt/образе), а не «поставь последнюю».
*Что хочет услышать:* «проверяю на чистом окружении», а не «у меня работает».
*Красный флаг:* «на моей машине запускается» как финальный аргумент.
