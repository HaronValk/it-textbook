# Serverless и функции: Cloud Functions, API Gateway, события, ограничения и применимость

## 1. Введение (зачем это нужно в реальной работе)

**Заявка #4127.** От: Сидоров А., склад. ВМ: WIN10-CL02. Что пишет: «Открываю страницу "Отгрузки за день", нажимаю "Сформировать" — полминуты крутится и вылетает 504 Bad Gateway. Если тут же нажать второй раз — открывается за секунду. С утра всегда так, пока народ не начал работать». Срочность: средняя.

Это классический симптом функции в облаке: первый вызов после паузы «поднимает» контейнер (cold start), а слишком короткий таймаут на шлюзе или слишком маленький лимит памяти превращают это в ошибку.

Serverless — не «без серверов», а «серверы не твоя проблема». Ты отдаёшь провайдеру код в виде функции, он сам решает, где её запустить, сколько копий держать и как патчить ОС. Ты платишь за число вызовов и время работы, а не за простой.

Почему это встречается постоянно: отчёты, вебхуки от платёжных систем, обработка загруженных файлов, ночные cron-задачи, лёгкие API для внутренних сервисов — всё это в 2026 году чаще всего пишут функциями. После главы ты должен уметь: написать и задеплоить функцию, повесить на неё API Gateway, настроить событийный триггер (таймер, бакет, очередь), понимать количественные лимиты платформы и аргументированно говорить, когда serverless брать **нельзя**.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**FaaS (Function as a Service)** — исполнение кода по событию в управляемом провайдером изолированном контейнере. Ключевое свойство: функция **stateless** — между вызовами не гарантируется ни память, ни диск, ни то, что тебя вызовут на том же инстансе.

Под капотом почти у всех (AWS Lambda, Yandex Cloud Functions, VK Cloud Functions, Google Cloud Functions, Azure Functions) одна схема: образ рантайма → инициализация (init-фаза, дорогая) → вызов `handler(event, context)` → ответ. Инстанс живёт «тёплым» несколько минут и может обслужить несколько вызовов подряд, потом уничтожается.

Слои и протоколы: клиент приходит по HTTPS (TCP/443, L7 в модели OSI). Внутри провайдер вызывает функцию не по сети, а через свой control plane. Наружу функция обычно не имеет входящего IP вообще — к ней можно достучаться только через триггер или API Gateway. Исходящий доступ в интернет часто требует NAT-шлюза или вообще закрыт — уточняй по доке конкретного провайдера `[ПРОВЕРИТЬ]`.

```text
                     ┌───────────────────────────────────────┐
 Клиент (браузер,    │  API Gateway  (L7, HTTPS :443)        │
 1С, curl, вебхук    │  маршрутизация по путям, TLS, CORS,   │
   платёжки) ───────►│  rate limit, JWT-авторизация          │
                     └───────────────┬───────────────────────┘
                                     │ invoke (внутренний вызов)
                     ┌───────────────▼───────────────────────┐
                     │  Function: версия + тег (stable/canary)│
                     │  ┌─────────────────────────────────┐  │
                     │  │ контейнер-рантайм               │  │
                     │  │ handler(event, context)         │  │
                     │  └─────────────────────────────────┘  │
                     │  лимиты: RAM, timeout, размер /tmp    │
                     └───┬───────────────────┬───────────────┘
                         │                   │
              сервисный аккаунт        только исходящая сеть
              (IAM-роль на ресурсы)
                         │                   │
              ┌──────────▼─────┐   ┌─────────▼──────────┐
              │ Object Storage │   │ Managed DB / очередь│
              └────────────────┘   └────────────────────┘

 Источники событий (триггеры): таймер(cron) | очередь | бакет S3 | HTTP | шина событий
```

**API Gateway** — отдельный управляемый слой. Зачем он, если есть функция: стабильный домен и TLS-сертификат, маршрутизация нескольких функций по путям, валидация запроса, авторизация (JWT/API-ключ), лимиты и кеш, преобразование запроса в `event` и обратно. У Yandex Cloud спецификация шлюза задаётся OpenAPI 3.0 с расширением `x-yc-apigateway-integration`. У AWS аналог — API Gateway, у GCP — API Gateway/Apigee, в VK Cloud — своя надстройка над функциями `[ПРОВЕРИТЬ]`.

**Триггеры (события)** бывают синхронные (клиент ждёт ответ) и асинхронные (таймер, объект в бакете, сообщение в очереди — провайдер вызывает функцию и **повторяет вызов при ошибке**). Отсюда главное правило: асинхронные функции обязаны быть **идемпотентными**.

**Лимиты — часть архитектуры, а не досадная мелочь.** Типовой набор (числа проверяй в доке провайдера, они меняются):
- максимальное время выполнения — обычно от 60 с до 15 минут (у AWS Lambda 900 с; у Yandex Cloud Functions — порядка 10 минут `[ПРОВЕРИТЬ]`);
- память — от 128 МБ до нескольких ГБ (Lambda: 128–10240 МБ);
- размер пакета с кодом и размер `/tmp` — десятки-сотни МБ;
- размер тела HTTP-запроса/ответа через шлюз (у Lambda синхронный вызов — до 6 МБ, асинхронный — 256 КБ `[ПРОВЕРИТЬ]`);
- квота на число одновременных вызовов (concurrency) — при её превышении вызовы ставятся в очередь или отбиваются 429.

## 3. Аналогия из жизни

Личное такси вместо собственной машины. Платишь за поездку, а не за бензин, страховку, парковку и техосмотр. Поездок нет — расходов нет. Машин в парке столько, сколько нужно городу прямо сейчас: в час пик их сто раз больше, чем ночью, и тебе не надо об этом думать.

Дальше совпадают и минусы. Машину иногда подают долго — это cold start: первый вызов после простоя ждёт, пока контейнер поднимется. В багажник много не положишь — это лимиты по памяти и размеру запроса. Нельзя оставить в салоне зимнюю куртку до следующей поездки — это stateless: состояние надо хранить в базе или объектном хранилище. Если поездка длиннее трёх часов, такси просто не поедет — это execution timeout.

Аналогия ломается в одном месте: такси не переиспользует для тебя тот же самый салон, а FaaS вполне может отдать твой следующий вызов в тот же «тёплый» инстанс — и код, который случайно положил что-то в глобальную переменную, будет работать «через раз».

## 4. Практика и команды

Ниже — боевые команды Yandex Cloud (самый ходовой в РФ провайдер с FaaS) и локальные аналоги на нашем стенде. Для облачных команд нужен `yc` CLI и **триал-аккаунт**: Cloud Functions тарифицируется по вызовам, на учебных объёмах это копейки, но бесплатный грант когда-то кончается — следи за бюджетом (это тема урока 76).

**1. Создать функцию**

```bash
yc serverless function create --name vektor-report --description "Отчёт по отгрузкам"
```

Вывод содержит `id` и `name`. `id` пригодится в спецификации шлюза.

**2. Задеплоить версию кода**

```bash
yc serverless function version create \
  --function-name vektor-report \
  --runtime python312 \
  --entrypoint handler.main \
  --memory 256m \
  --execution-timeout 10s \
  --source-path ./src \
  --service-account-id <ID_СА> \
  --environment LOG_LEVEL=info
```

`--entrypoint handler.main` = файл `handler.py`, функция `main`. `--runtime python312` — идентификатор рантайма, точные имена (`python312`, `nodejs18`, `golang121`) смотри в доке `[ПРОВЕРИТЬ]`. `--service-account-id` — под кем функция пойдёт в Object Storage и БД.

**3. Вызвать и посмотреть результат**

```bash
yc serverless function invoke --name vektor-report --data '{"report":"sklad","date":"2026-03-01"}'
```

В ответе `statusCode` и `body`. Это ровно тот `event`, который увидит `handler`.

**4. Версии и теги (сине-зелёный деплой)**

```bash
yc serverless function version list --function-name vektor-report
yc serverless function set-tag --name vektor-report --tag stable --version-id <ID_ВЕРСИИ>   # [ПРОВЕРИТЬ]
```

Тег — это алиас на версию. API Gateway ссылается на тег `stable`, ты публикуешь новую версию, тегом переключаешь трафик. Откат = переключить тег обратно (секунды, без пересборки).

**5. Описать API Gateway спецификацией (файл в Git)**

```yaml
openapi: 3.0.0
info:
  title: vektor-api
  version: 1.0.0
paths:
  /report:
    post:
      x-yc-apigateway-integration:
        type: cloud_functions
        function_id: <ID_ФУНКЦИИ>
        tag: stable
        service_account_id: <ID_СА>
  /report/{id}:
    get:
      parameters:
        - name: id
          in: path
          required: true
          schema: {type: string}
      x-yc-apigateway-integration:
        type: cloud_functions
        function_id: <ID_ФУНКЦИИ>
        tag: stable
        service_account_id: <ID_СА>
```

Параметр пути `{id}` попадёт в `event.pathParameters.id`. Сервисному аккаунту нужна роль вида `functions.functionInvoker` `[ПРОВЕРИТЬ]`.

**6. Создать шлюз и проверить**

```bash
yc serverless api-gateway create --name vektor-gw --spec api.yaml
curl -s -X POST https://<ID_ШЛЮЗА>.apigw.yandexcloud.net/report -d '{"date":"2026-03-01"}'
```

**7. Триггер по расписанию (cron)**

```bash
yc serverless trigger create timer \
  --name vektor-nightly \
  --cron-expression "0 0 2 * * ?" \
  --invoke-function-name vektor-report \
  --invoke-function-tag stable \
  --invoke-function-service-account-id <ID_СА>          # [ПРОВЕРИТЬ: набор флагов]
```

Формат cron здесь Quartz-подобный, 6 полей, первое — секунды (проверь в доке `[ПРОВЕРИТЬ]`). Ошибка «каждый день в 2:00» → задача бежит ежедневно, но с retry-штормом, если функция падает.

**8. Триггер на появление объекта в бакете**

```bash
yc serverless trigger create object-storage \
  --name vektor-upload \
  --bucket-id <ID_БАКЕТА> \
  --events s3:ObjectCreated:* \
  --invoke-function-name vektor-report \
  --invoke-function-service-account-id <ID_СА>          # [ПРОВЕРИТЬ]
```

Так делают обработку загруженных актов и сканов: файл упал в `s3://vektor-inbox/` → функция его разобрала → положила результат в `s3://vektor-out/`.

**9. Локальный аналог: функция как контейнер и образ в HARBOR01**

```bash
docker build -t harbor01.corp.vektor.lab/vektor/fn-report:0.1.0 .
docker login harbor01.corp.vektor.lab
docker push harbor01.corp.vektor.lab/vektor/fn-report:0.1.0
```

**10. Локальный аналог: деплой с лимитами (k8s)**

```bash
kubectl create namespace serverless
kubectl -n serverless apply -f deployment.yaml
kubectl -n serverless get pods -l app=fn-report
```

В манифесте обязательно `resources.limits` — это и есть эмуляция «памяти на функцию».

**11. Замер холодного старта и конкурентности**

```bash
for i in $(seq 1 30); do
  curl -s -o /dev/null -w "%{http_code} %{time_total}\n" \
    -X POST http://127.0.0.1:8080/api/v1/report -d '{"date":"2026-03-01"}' &
done; wait
```

Смотри распределение времени: первый запрос в разы дольше остальных — это и есть cold start. В реальной платформе тебе те же цифры покажет трейсинг.

**12. Логи и метрики**

```bash
kubectl -n serverless logs deploy/fn-report --tail=50
yc logging read --folder-id <ID_КАТАЛОГА> --limit 20          # [ПРОВЕРИТЬ]
```

Без логов функция — чёрный ящик: `print()` в Yandex Cloud Functions попадает в логи автоматически, но только если у функции есть сервисный аккаунт с правом писать в Cloud Logging.

### Шаги

1. **UBU01.** Клонируй репозиторий: `git clone http://git01.corp.vektor.lab/vektor/serverless-lab.git && cd serverless-lab`. Ожидаемо: пустой репозиторий с `README.md`. Всё, что делаем дальше, коммитим — это IaC-подход.

2. **UBU01.** Создай `handler.py` — саму «функцию»:

```python
import os, time

def main(event, context):
    delay = float(os.getenv("SIMULATE_WORK_SECONDS", "0"))
    if delay:
        time.sleep(delay)
    return {"ok": True,
            "request_id": context["request_id"],
            "path": event.get("path"),
            "body": (event.get("body") or "")[:200]}
```

Ожидаемо: файл на месте, `python3 -c "import handler"` не падает.

3. **UBU01.** Создай `runtime.py` — минимальный «рантайм платформы» (HTTP-сервер, который один раз импортирует модуль и потом вызывает `main`):

```python
import importlib.util, json, os, time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

FILE  = os.getenv("HANDLER_FILE", "/app/handler.py")
ENTRY = os.getenv("HANDLER_ENTRY", "main")
MAX_EXEC = float(os.getenv("MAX_EXEC_SECONDS", "10"))

t0 = time.monotonic()
spec = importlib.util.spec_from_file_location("handler", FILE)
mod = importlib.util.module_from_spec(spec)
spec.loader.exec_module(mod)                 # init-фаза = «холодный старт»
fn = getattr(mod, ENTRY)
COLD_MS = int((time.monotonic() - t0) * 1000)

class H(BaseHTTPRequestHandler):
    def do_POST(self):
        body = self.rfile.read(int(self.headers.get("Content-Length") or 0))
        event = {"httpMethod": "POST", "path": self.path,
                 "headers": dict(self.headers), "body": body.decode("utf-8", "replace")}
        started = time.monotonic()
        try:
            result, code = fn(event, {"request_id": os.urandom(8).hex()}), 200
        except Exception as e:
            result, code = {"error": str(e)}, 500
        took = time.monotonic() - started
        if took > MAX_EXEC:
            result, code = {"error": "execution timeout"}, 504
        out = json.dumps({"result": result, "cold_start_ms": COLD_MS,
                          "duration_ms": int(took * 1000)}).encode()
        self.send_response(code)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(out)))
        self.end_headers()
        self.wfile.write(out)
    def log_message(self, *a): pass

ThreadingHTTPServer(("0.0.0.0", 8080), H).serve_forever()
```

Ожидаемо: `COLD_MS` считается один раз на контейнер — ровно как холодный старт в облаке.

4. **UBU01.** Создай `Dockerfile`:

```dockerfile
FROM python:3.12-slim
RUN useradd --uid 10001 --create-home app
WORKDIR /app
COPY runtime.py handler.py ./
ENV HANDLER_FILE=/app/handler.py HANDLER_ENTRY=main MAX_EXEC_SECONDS=5
USER 10001
EXPOSE 8080
CMD ["python", "runtime.py"]
```

Ожидаемо: образ собирается, процесс работает не от root.

5. **UBU01.** Собери и запушь образ в HARBOR01:

6. **UBU01.** Задеплой функцию в кластер (`deployment.yaml`): namespace `serverless`, Deployment `fn-report` с `replicas: 1`, `resources.limits: {cpu: 500m, memory: 128Mi}`, `readinessProbe` на `/`, Service `fn-report` на порт 8080. Затем `kubectl apply -f deployment.yaml`. Ожидаемо: `kubectl -n serverless get pods` → `Running`, 1/1 Ready.

8. **UBU01.** Добавь API Gateway — nginx с маршрутом и таймаутом (`nginx.conf` в ConfigMap, отдельный Deployment `gw` + Service):

## 6. Ошибки новичков и безопасность

1. **Хранить состояние в памяти или на диске функции.** → Второй вызов попадает на другой инстанс, данные «теряются», отчёты дублируются. → Состояние только в БД или Object Storage, `/tmp` считать одноразовым.
2. **Делать функцию неидемпотентной при асинхронном триггере.** → Провайдер повторит вызов при ошибке, платёж или отгрузка проведётся дважды. → Ключ идемпотентности в записи, проверка «уже обработано» перед действием.
3. **Запихивать в функцию долгую работу: выгрузку 1С на 40 минут, большой PDF, парсинг гигабайта.** → Упирается в timeout, деньги горят, пользователь видит 504. → Долгое — на ВМ/контейнер/Managed-сервис, функция только ставит задачу в очередь.
4. **Ставить память «на глаз», без профилирования.** → Ровно наш кейс с OOMKilled: сервис падает под нагрузкой. → Замерять пиковое потребление, брать с запасом 1.5–2×, проверять под конкурентной нагрузкой.
5. **Не ограничивать конкурентность и размер батча у триггера на очередь.** → Всплеск событий поднимает сотни инстансов и счёт за месяц. → Настроить reserved/max concurrency, ограничить батч.
6. **Тянуть в образ всё, включая pandas и tensorflow, «на всякий случай».** → Образ на 800 МБ, cold start 20–30 секунд, пользователи жалуются на «медленный сайт». → Минимальный рантайм, слои для общих зависимостей, тёплые инстансы для критичных путей.
7. **Не настраивать логи и трейсинг.** → Функция упала, а ты не знаешь ни `event`, ни стека. → Структурные логи, `request_id` в каждом сообщении, алерты на долю ошибок.
8. **Путать 429 и 5xx.** → 429 значит «платформа ограничила concurrency», а не «код сломался». → Смотреть метрики платформы, а не только логи приложения.

### Безопасность

Нельзя: держать пароли, токены платёжного API и ключи доступа в переменных окружения версии или в коде. Переменные окружения видны всем, у кого есть право смотреть функцию, и остаются в истории версий. Правильно — секрет в Lockbox/Vault, а в функцию приходит ссылка на секрет или временный токен (у нас это тема урока 66).

Нельзя: давать функции сервисный аккаунт с ролью администратора каталога «чтобы работало». Принцип наименьших привилегий: только `storage.objectViewer` на конкретный бакет, только `ymq.writer` на конкретную очередь.

Нельзя: делать функцию публичной (`allow-unauthenticated`) для внутреннего API. Публичный эндпоинт без авторизации — это открытые данные и счёт за чужой трафик. Авторизацию вешай на API Gateway (JWT, API-ключ), а не на код функции.

И отдельно: не логируй тело запроса целиком, если там персональные данные или номера карт. Логи живут долго и читаются широко.

## 7. Вопросы на собеседовании (3–5 вопросов с ответами)

**1. Что такое serverless и чем FaaS отличается от обычного контейнера в Kubernetes?**

Ответ: Serverless — модель, где провайдер полностью управляет инфраструктурой: масштабированием, патчингом ОС, выделением ресурсов, а оплата идёт за фактические вызовы и время работы. FaaS — конкретная реализация: ты загружаешь функцию, платформа сама решает, сколько инстансов держать, может масштабировать до нуля и запускает код по событию. Контейнер в Kubernetes — это ты сам управляешь Deployment, репликами, HPA, образом, обновлениями; масштаб до нуля обычно требует отдельного компонента (KEDA, Knative). Ключевые отличия FaaS: контракт `handler(event, context)`, жёсткий execution timeout, stateless-гарантия, оплата по вызовам, отсутствие входящего сетевого адреса.

*Что хочет услышать интервьюер:* что ты понимаешь разницу между «платформа всё делает» и «я всё делаю», и что FaaS — это надстройка, а не магия.

*Красный флаг:* «serverless — это когда нет серверов» и неспособность назвать хотя бы один лимит.

**2. Что такое cold start, почему он возникает и как с ним бороться?**

Ответ: Cold start — задержка первого вызова после простоя, когда платформа создаёт контейнер, тянет образ, поднимает рантайм и выполняет init-код (импорты, подключение к БД). Занимает от десятков миллисекунд до десятков секунд в зависимости от рантайма, размера образа и VPC-подключений. Борьба: уменьшить размер образа и число зависимостей; вынести инициализацию тяжёлых клиентов в lazy-инициализацию или переиспользуемый контекст; использовать provisioned/тёплые инстансы (у AWS — provisioned concurrency, у Яндекса — аналогичный механизм `[ПРОВЕРИТЬ]`); держать критичные пути на «тёплом» минимуме или уходить на serverless-контейнеры; для пользовательских запросов — не показывать спиннер, а отдавать кеш.

*Что хочет услышать интервьюер:* что ты знаешь про init-фазу, про переиспользование контекста и умеешь измерять, а не гадать.

*Красный флаг:* «cold start — это когда сервер выключен» или предложение «просто добавь sleep, чтобы прогрелось».

**3. Как сделать асинхронную обработку на функциях и почему идемпотентность обязательна?**

Ответ: Клиент кладёт сообщение в очередь (Yandex Message Queue, SQS, RabbitMQ), на очередь навешивается триггер, который вызывает функцию. Триггер доставляет сообщения по модели at-least-once: при ошибке или таймауте сообщение вернётся в очередь и вызов повторится, иногда не один раз. Поэтому обработчик обязан быть идемпотентным: проверять по ключу (номер заказа, `message_id`), не обработан ли уже этот объект, и фиксировать факт обработки в БД в той же транзакции, что и бизнес-изменение. Плюс dead-letter queue для сообщений, которые падают стабильно, ограничение `maxReceiveCount` и алерт на рост DLQ.

*Что хочет услышать интервьюер:* понимание at-least-once vs exactly-once и того, что ретраи — не баг, а контракт.

*Красный флаг:* «функция выполнится ровно один раз» и отсутствие упоминания DLQ.

**4. Когда serverless брать НЕ надо?**

Ответ: Когда задача длится дольше платформенного таймаута (тяжёлый ETL, рендер видео, длинные отчёты); когда нужен постоянный «тёплый» процесс с предсказуемой латентностью (высокочастотный API, трейдинг); когда нужны большие локальные диски или GPU; когда приложение держит долгие соединения (WebSocket, пул соединений к БД на тысячи клиентов); когда нагрузка стабильно высокая и круглая — тогда всегда включённый контейнер дешевле, чем миллионы вызовов; когда жёсткие требования по размещению данных или по контролю над средой исполнения.

*Что хочет услышать интервьюер:* что ты считаешь деньги и латентность, а не просто «модно».

*Красный флаг:* «serverless всегда дешевле» без оговорок про характер нагрузки.

**5. Зачем нужен API Gateway, если функция уже умеет принимать HTTP?**

Ответ: Шлюз даёт стабильную точку входа: собственный домен и TLS, маршрутизацию нескольких функций по путям и методам, авторизацию и валидацию запроса до вызова функции (не платим за отклонённые запросы), rate limiting и квоты по клиентам, CORS, кеширование, преобразование запроса в `event` и ответа обратно, единые логи и метрики на весь API. Плюс возможность менять бэкенд (функция → контейнер → ВМ) без изменения URL для клиентов. В Yandex Cloud шлюз описывается OpenAPI-спецификацией, которая лежит в Git и ревьюится как код.

*Что хочет услышать интервьюер:* что шлюз — это слой политики и контракта, а не просто прокси.

*Красный флаг:* «шлюз не нужен, функция сама всё умеет» — обычно значит, что человек не сталкивался с авторизацией и лимитами на проде.
