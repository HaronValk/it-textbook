## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Рабочее место DevOps — это стопка слоёв. Понимание стопки снимает 80% проблем «а почему у меня не работает».

```text
┌──────────────────────── ноутбук (Windows 11) ─────────────────────────┐
│  Windows Terminal / VS Code            ← «окно», эмулятор терминала   │
│   └── WSL2: Ubuntu 24.04               ← лёгкая ВМ с настоящим ядром   │
│        └── zsh + плагины               ← оболочка: история, алиасы     │
│             └── tmux                   ← мультиплексор: сессии живут   │
│                  └── ssh               ← клиент, ~/.ssh/config, agent  │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │ TCP 22, SSH-2: обмен ключами, шифр
                        ┌──────────▼──────────┐
                        │ UBU01 10.10.10.30   │ sshd, tmux-сервер, код
                        └─────────────────────┘
```

**Терминал ≠ оболочка.** Терминал (Windows Terminal, GNOME Terminal, kitty) — программа, которая рисует текст и передаёт нажатия. Оболочка (bash, zsh) — программа, которая эти нажатия интерпретирует и запускает команды. Их путают постоянно.

**WSL2** (Windows Subsystem for Linux 2) — не эмуляция и не «переводчик» системных вызовов, как WSL1, а настоящая лёгкая виртуальная машина с ядром Linux, которой управляет Hyper-V-платформа Windows. Для тебя это значит: `apt`, `systemd`, Docker, сеть — ведут себя как на обычном Linux. Файлы Windows видны внутри как `/mnt/c/...` — но они медленные, потому что доступ идёт через сетевую ФС. Правило: код и git-репозитории держи в Linux-разделе (`~/projects`), а не в `/mnt/c`.

**SSH** — протокол прикладного уровня (поверх TCP, порт 22). Схема аутентификации по ключу: у тебя приватный ключ (никогда не покидает машину), на сервере в `~/.ssh/authorized_keys` лежит публичный. Сервер при подключении даёт «задачу», клиент подписывает её приватным ключом — пароль по сети не летит вообще. Хост сервера запоминается в `~/.ssh/known_hosts`; если отпечаток изменился, ssh орёт `REMOTE HOST IDENTIFICATION HAS CHANGED` — это защита от подмены сервера.

**Приоритет настроек SSH:** параметры в командной строке → `~/.ssh/config` (личный) → `/etc/ssh/ssh_config` (системный). Внутри конфига работает принцип «первое совпадение выигрывает», поэтому общие блоки (`Host *`) пишут в конце файла.

**tmux** — клиент-сервер: сервер tmux живёт на машине (локально или на UBU01) и держит процессы, а терминал — лишь «окно просмотра». Закрыл ноутбук — сессия на сервере продолжает работать. Это и есть ответ ivanov'у.

**Менеджер паролей** — это база, зашифрованная мастер-паролем (KeePassXC — формат `.kdbx`, `pass` — GPG + git). Смысл: один сильный пароль ты помнишь, остальные 200 — нет, и они нигде не лежат открытым текстом.

## 3. Аналогия из жизни

Рабочее место DevOps — это мастерская столяра. Терминал — дверь в мастерскую. WSL2/UBU01 — сам верстак с нормальными инструментами: без него ты работаешь перочинным ножом на коленке. zsh с алиасами — разметка на стене и подписанные ящики: не ищешь стамеску 10 минут, а берёшь сразу. tmux — это верстак, который не разбирают на ночь: заготовка остаётся лежать в струбцинах, даже если ты ушёл пить чай. `~/.ssh/config` — список «к кому и с каким пропуском идти», вместо того чтобы каждый раз объяснять охране, кто ты. Менеджер паролей — сейф у входа: ключи от мастерской не валяются под ковриком.

Аналогия ломается в одном: в мастерской инструментом может воспользоваться любой, кто вошёл, а в DevOps доступ персональный — он подтверждается твоим ключом, и «стоять у верстака» не даёт прав на сервер.

## 4. Практика и команды

### 1. Поставить WSL2 и проверить версию (хост, PowerShell)

```powershell
wsl --install -d Ubuntu-24.04
wsl --list --verbose
wsl --set-default-version 2
```

`--install` включает компоненты, ставит ядро и дистрибутив по умолчанию; `-d <имя>` — конкретный дистрибутив (список доступных: `wsl --list --online`; точное имя `Ubuntu-24.04` [ПРОВЕРИТЬ] — бери из вывода). `--verbose` (`-v`) показывает версию WSL и состояние `Running/Stopped`. Смотреть надо на колонку `VERSION`: там обязана быть `2`.

```text
  NAME            STATE           VERSION
* Ubuntu-24.04    Running         2
```

Если стоит `1` — `wsl --set-version Ubuntu-24.04 2`.

### 2. Убедиться, что внутри настоящий Linux (WSL или UBU01)

```bash
cat /etc/os-release
uname -r
```

`os-release` даёт `PRETTY_NAME="Ubuntu 24.04.x LTS"`, `uname -r` — версию ядра (в WSL2 вида `5.15.x`/`6.x` [ПРОВЕРИТЬ]). Это базовый рефлекс: прежде чем что-то ломать, посмотри, что за система.

### 3. Базовый набор пакетов

```bash
sudo apt update && sudo apt install -y zsh tmux git curl htop neovim
```

`apt update` обновляет индекс пакетов (не сами пакеты!), `install -y` — без подтверждения. `htop` — монитор процессов, `neovim` — редактор. На UBU01 всё это нужно ровно так же, как в WSL.

### 4. Сделать zsh оболочкой по умолчанию

```bash
chsh -s "$(which zsh)"
```

`chsh` меняет логин-шелл в `/etc/passwd`; `$(which zsh)` подставляет полный путь (`/usr/bin/zsh`) — без него `chsh` ругнётся. Применится после перелогина; в WSL — после `wsl --shutdown` и повторного открытия.

### 5. Минимальный `~/.zshrc`

```bash
# ~/.zshrc
HISTFILE=~/.zsh_history
HISTSIZE=50000
SAVEHIST=50000
setopt HIST_IGNORE_ALL_DUPS SHARE_HISTORY INC_APPEND_HISTORY
PROMPT='%F{green}%n@%m%f:%F{blue}%~%f$ '
alias ll='ls -lah'
alias gs='git status -sb'
alias k='kubectl'
export EDITOR=nvim
```

`SHARE_HISTORY` дописывает историю сразу, поэтому команды из разных tmux-панелей не теряются. `HIST_IGNORE_ALL_DUPS` чистит дубли. `PROMPT` — `%n` пользователь, `%m` хост, `%~` текущий путь.

### 6. oh-my-zsh — вручную, а не через `curl | sh`

```bash
git clone --depth=1 https://github.com/ohmyzsh/ohmyzsh.git ~/.oh-my-zsh
cp ~/.oh-my-zsh/templates/zshrc.zsh-template ~/.zshrc
```

Официальный установщик — это `curl ... | sh`, то есть «скачай неизвестный скрипт и выполни». На учебном стенде лучше клонировать репозиторий и посмотреть глазами. `--depth=1` — без истории, быстрее и легче.

### 7. tmux: сессии, окна, панели

```bash
tmux new -s work          # новая сессия с именем work
tmux ls                   # список сессий
tmux attach -t work       # вернуться в неё
tmux kill-session -t work # убить
```

Внутри: префикс по умолчанию `Ctrl+b`, затем `c` — новое окно, `,` — переименовать, `%` — панель вертикально, `"` — горизонтально, стрелки — переключение, `d` — detach (выйти, оставив всё работать). Проверка «жизни»: запусти `htop`, нажми `Ctrl+b d`, зайди снова через `tmux attach -t work` — `htop` на месте.

```bash
# ~/.tmux.conf
set -g mouse on
set -g history-limit 50000
set -g base-index 1
setw -g pane-base-index 1
set -sg escape-time 10
bind r source-file ~/.tmux.conf \; display-message "config reloaded"
```

`mouse on` — скролл и выбор панелей мышью (удобно, в боевой работе иногда отключают), `escape-time 10` убирает задержку после Esc (важно для Neovim).

### 8. SSH-ключ

```bash
ssh-keygen -t ed25519 -C "adm.student@vektor.lab" -f ~/.ssh/id_ed25519_vektor
```

`-t ed25519` — современный алгоритм (короче и быстрее RSA), `-C` — комментарий-метка, `-f` — путь. На вопрос о passphrase отвечай **да**, парольную фразу придумай. Вывод:

```text
Your identification has been saved in /home/adm.student/.ssh/id_ed25519_vektor
Your public key has been saved in /home/adm.student/.ssh/id_ed25519_vektor.pub
The key fingerprint is:
SHA256:AbCd... adm.student@vektor.lab
```

Смотри на fingerprint — по нему ключ опознают.

### 9. Положить публичный ключ на UBU01

```bash
ssh-copy-id -i ~/.ssh/id_ed25519_vektor.pub adm.student@10.10.10.30
```

`ssh-copy-id` создаёт `~/.ssh`, дописывает ключ в `authorized_keys` и ставит права. На Windows-клиенте этой утилиты нет — там вручную:

```bash
cat ~/.ssh/id_ed25519_vektor.pub | ssh adm.student@10.10.10.30 \
  'mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys'
```

### 10. `~/.ssh/config` — главный файл ленивого инженера

```text
Host ubu01
    HostName 10.10.10.30
    User adm.student
    IdentityFile ~/.ssh/id_ed25519_vektor
    IdentitiesOnly yes
    ServerAliveInterval 30
    ServerAliveCountMax 3

Host 10.10.10.*
    User adm.student
```

Теперь `ssh ubu01` вместо `ssh -i ~/.ssh/id_ed25519_vektor adm.student@10.10.10.30`. `ServerAliveInterval 30` шлёт keepalive каждые 30 секунд и не даёт NAT-у роутера выкинуть «мёртвое» соединение. Права на файл: `chmod 600 ~/.ssh/config`, иначе ssh предупредит `Bad owner or permissions`. Посмотреть, что реально применилось: `ssh -G ubu01 | head -20`.

### 11. ssh-agent — чтобы не вводить passphrase 50 раз

```bash
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519_vektor
ssh-add -l
```

На Windows (OpenSSH-клиент штатный):

```powershell
Get-Service ssh-agent | Set-Service -StartupType Automatic
Start-Service ssh-agent
ssh-add $env:USERPROFILE\.ssh\id_ed25519_vektor
```

`ssh-add -l` печатает отпечатки загруженных ключей. Пусто — значит ключ не подхватился, и ssh будет спрашивать passphrase каждый раз.

### 12. VS Code Remote-SSH и Neovim

GUI: `Ctrl+Shift+P` → `Remote-SSH: Connect to Host` → `ubu01` → откроется окно, файловая система — уже серверная. Расширение: «Remote - SSH» (`ms-vscode-remote.remote-ssh`). Из терминала:

```bash
code --remote ssh-remote+ubu01 /home/adm.student
```

Синтаксис `--remote` [ПРОВЕРИТЬ под вашу версию VS Code]. **Важный нюанс:** Remote-SSH, запущенный из Windows, читает `C:\Users\<вы>\.ssh\config`, а не WSL-ный. Если хочешь один конфиг — либо задай `remote.SSH.configFile` в настройках, либо работай через расширение «WSL».

Neovim на сервере — когда правок мало и не хочется поднимать IDE:

```bash
nvim ~/.ssh/config
```

```lua
-- ~/.config/nvim/init.lua
vim.o.number = true
vim.o.tabstop = 2
vim.o.shiftwidth = 2
vim.o.expandtab = true
vim.o.ignorecase = true
vim.o.smartcase = true
```

### 13. Менеджер паролей

KeePassXC (графический, кроссплатформенный, файл `.kdbx`) — на ноутбук, база в папке, которая **не** синхронизируется в Git. Консольный вариант на Linux:

```bash
sudo apt install -y pass
gpg --full-generate-key                 # ECC (sign+encrypt) [ПРОВЕРИТЬ набор опций]
pass init "adm.student@vektor.lab"
pass insert vektor/ubu01
pass show -c vektor/ubu01               # -c: в буфер обмена, не на экран
pass ls
```

`pass` хранит записи как GPG-файлы в `~/.password-store`, каталог можно версионировать через `pass git init`. Пароль в терминал не печатается — это принципиально: всё, что попало на экран, попадает в буфер и в лог.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

- **UBU01** (10.10.10.30, Ubuntu Server 24.04) развёрнут, SSH работает, у тебя есть учётная запись `adm.student` (если на твоём стенде логин другой — подставляй его везде). Машина осталась с сисадминского трека.
- **Хост**: Windows 10/11, в BIOS включена виртуализация (VT-x/AMD-V), свободно ~10 ГБ диска и ~4 ГБ RAM для WSL2.
- GIT01, HARBOR01 и k8s-узлы ещё **не развёрнуты** — это следующие шаги трека. Репозиторий dotfiles делаем локально, запушим на GIT01, когда он появится (см. урок 5 про портфолио).
- Windows-часть стенда (DC01, FS01) в этом треке может отсутствовать — она здесь не нужна.

### Снапшот

В VMware Workstation на **UBU01**: меню `VM` → `Snapshot` → `Take Snapshot`, имя `before-devops-004`. Если по ходу лабораторной ты меняешь ещё какие-то ВМ — снапшот на них тоже.

Хост снапшотом VMware не покрывается: изменения WSL откатываются через `wsl --unregister Ubuntu-24.04` (**уничтожает данные внутри дистрибутива**) или просто тем, что твои конфиги лежат в git-репозитории `~/dotfiles` и восстанавливаются повторным клонированием.

### Шаги

1. **Хост.** `wsl --install -d Ubuntu-24.04`, перезагрузись, создай пользователя. Ожидаемо: `wsl -v` показывает `VERSION 2`, в PowerShell `wsl` открывает приглашение Ubuntu.
2. **WSL.** `cat /etc/os-release` → `PRETTY_NAME="Ubuntu 24.04..."`. Значит, окружение живое и это Ubuntu, а не что-то иное.
3. **WSL.** `sudo apt update && sudo apt install -y zsh tmux git curl htop neovim`. Ожидаемо: `Setting up tmux ...`, без ошибок `E: Unable to locate package`.
4. **WSL.** `chsh -s "$(which zsh)"`, затем `wsl --shutdown` и снова `wsl`. Ожидаемо: приглашение сменилось, `echo $SHELL` → `/usr/bin/zsh`.
5. **WSL.** Настрой `~/.zshrc` из раздела 4 (или склонируй oh-my-zsh вручную). Проверка: `ll` работает как `ls -lah`, `Ctrl+R` находит старую команду.
6. **WSL.** Создай `~/dotfiles`, перенеси туда `.zshrc` и `.tmux.conf`, сделай симлинки: `ln -sf ~/dotfiles/zshrc ~/.zshrc`, `ln -sf ~/dotfiles/tmux.conf ~/.tmux.conf`, `git init && git add . && git commit -m "dotfiles: zsh + tmux"`. Ожидаемо: `git log --oneline` показывает один коммит.
7. **UBU01** (через `ssh adm.student@10.10.10.30`). `sudo apt install -y tmux zsh htop neovim`. Ожидаемо: пакеты встали.
8. **UBU01.** `tmux new -s work`, внутри запусти `htop`, нажми `Ctrl+b`, затем `d`. Ожидаемо: вернулся в обычный шелл, вывод `[detached (from session work)]`.
9. **UBU01.** Закрой SSH-сессию совсем (`exit`). Зайди снова и выполни `tmux attach -t work`. Ожидаемо: `htop` на том же месте, с теми же секундами uptime — процесс не умирал.
10. **Клиент (WSL).** `ssh-keygen -t ed25519 -C "adm.student@vektor.lab" -f ~/.ssh/id_ed25519_vektor` с passphrase, затем `ssh-copy-id -i ~/.ssh/id_ed25519_vektor.pub adm.student@10.10.10.30`. Ожидаемо: `Number of key(s) added: 1`.
11. **Клиент.** Создай `~/.ssh/config` с блоком `Host ubu01`, `chmod 600 ~/.ssh/config`. Проверь `ssh ubu01` (спросит passphrase — пока нормально) и `ssh -G ubu01 | head`.
12. **Клиент.** `eval "$(ssh-agent -s)"`, `ssh-add ~/.ssh/id_ed25519_vektor`, `ssh-add -l`. Затем `ssh ubu01` — passphrase уже не спрашивает.
13. **UBU01 (осторожно, вторая сессия открыта!)** Создай `/etc/ssh/sshd_config.d/60-vektor.conf`:

    ```text
    PasswordAuthentication no
    PubkeyAuthentication yes
    PermitRootLogin prohibit-password
    ```

    Проверь `sudo sshd -t` (молчание = синтаксис ок), затем `sudo systemctl restart ssh`. В отдельном окне проверь, что вход по ключу работает.
14. **VS Code.** `Ctrl+Shift+P` → `Remote-SSH: Connect to Host` → `ubu01`. Открой `/home/adm.student`, создай файл, сохрани. Ожидаемо: файл виден на UBU01 через `cat`.
15. **Хост.** Установи KeePassXC, создай базу `vektor-lab.kdbx` с мастер-паролем, положи туда пароль `adm.student` от UBU01 и passphrase от ключа. Базу — в папку вне git.
16. **Запись в `stand-log.md`**: что настроено, какие ключи и где лежат.

**Как воспроизвести.** На клиенте: `chmod 644 ~/.ssh/id_ed25519_vektor`. Это классическая поломка — права снимаются при копировании файла через мессенджер, распаковке архива или `scp` с чужой машины.

**Диагностика по шагам.**

1. `ssh -vvv ubu01` — смотрим подробный лог. В нём будет:

   ```text
   @@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
   @         WARNING: UNPROTECTED PRIVATE KEY FILE!          @
   @@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
   Permissions 0644 for '/home/adm.student/.ssh/id_ed25519_vektor' are too open.
   debug1: No more authentication methods to try.
   adm.student@10.10.10.30: Permission denied (publickey).
   ```

2. `ls -l ~/.ssh/` — подтверждаем права `-rw-r--r--` вместо `-rw-------`.
3. `ssh-add -l` — если ключ в агенте есть, а падает всё равно, значит проблема не в правах, а в самом ключе: продолжаем.
4. `cat ~/.ssh/id_ed25519_vektor.pub` и на UBU01 `cat ~/.ssh/authorized_keys` — сравниваем строку `ssh-ed25519 AAAA...` символ в символ (частая история: ключ добавлен с обрезанным хвостом или добавлен `.pub` дважды).
5. На UBU01 `sudo tail -n 20 /var/log/auth.log` — там видно, принял ли sshd ключ и с каким отпечатком (`Accepted publickey for adm.student ... SHA256:...`).

**Решение.**

```bash
chmod 600 ~/.ssh/id_ed25519_vektor
chmod 700 ~/.ssh
ssh-add -D && ssh-add ~/.ssh/id_ed25519_vektor
ssh ubu01
```

Если `authorized_keys` битый — перезалить публичный ключ через `ssh-copy-id` из-под второй учётной записи или через консоль VMware.

**Ответ пользователю.** «Проблема была в правах на файл ключа: SSH принципиально отказывается использовать приватный ключ, если его может прочитать кто-то ещё. Исправил права на `600` (доступ только владельцу), проверил вход — работает. Пароль на сервере отключён специально, вход только по ключу; если будешь копировать ключ на другой компьютер — копируй и сразу выставляй права `600`, иначе повторится».

**Закрытие заявки.** Категория «Доступы / SSH», решение в базе знаний, отметка «пользователь подтвердил». И запись в `stand-log.md`: «на клиенте восстановлены права 600 на ключ».

## 6. Ошибки новичков и безопасность

1. **Приватный ключ без passphrase + разложен по всем серверам.** → Утечка одного ноутбука = компрометация всего парка. → Passphrase обязательна, ключ живёт только на рабочей машине, на серверы идёт `.pub`.
2. **Копирование ключа через мессенджер/почту.** → Права `644`, ключ в чужом облаке, в истории чата. → `ssh-copy-id`, менеджер секретов, `scp` внутри защищённого канала.
3. **`StrictHostKeyChecking=no` «чтобы не мешало».** → Отключается проверка подлинности сервера, MITM становится тривиальным. → Разбираться с `known_hosts` руками, а не отключать проверку.
4. **Пароли в `~/.zsh_history`, в `.env` в репозитории, в выводе `echo $PASSWORD`.** → Секрет навсегда в истории шелла и в git-истории (даже если файл удалить). → Менеджер паролей, `pass show -c`, переменные окружения из защищённого файла, `.gitignore` до первого коммита.
5. **Работа без tmux на удалённом сервере.** → Разрыв VPN/Wi-Fi убивает `apt upgrade`, миграцию БД, сборку. → Долгие операции только внутри `tmux`/`screen`.
6. **`PasswordAuthentication yes` на сервере, доступном из сети.** → Брутфорс по словарю, компромисс слабого пароля. → Ключи + `fail2ban`, пароли только как временный резерв.
7. **Проекты в `/mnt/c/Users/...` в WSL.** → Скорость I/O в разы ниже, права файлов ведут себя странно, Docker-билды ползут. → Код в `~/projects` внутри Linux-ФС.
8. **Сто плагинов oh-my-zsh «для красоты».** → Шелл стартует 2–3 секунды, на каждом `ssh` это бесит. → Минимум плагинов, замер через `time zsh -i -c exit`.

**Безопасность.** В боевой среде: приватные ключи не покидают защищённый носитель, доступ выдаётся по принципу минимальных прав, а не «дам root на всякий случай»; отключение `PasswordAuthentication` делается только после проверки входа по ключу во второй открытой сессии — иначе можно остаться без доступа к серверу; база KeePassXC не хранится в общем сетевом каталоге и не коммитится в Git; экспорт из менеджера паролей — в зашифрованном виде. На стенде мы сознательно делаем просто (один ключ, пароль стенда `Lab#2026-vektor`), но помечаем: в реальной работе так нельзя.

## 7. Вопросы на собеседовании

**1. Чем аутентификация по SSH-ключу лучше пароля и зачем отключать `PasswordAuthentication`?**

Ответ: пароль передаётся на сервер (пусть и внутри шифрованного канала) и хранится в виде хеша, который можно подобрать; ключ — приватный материал, который вообще не покидает машину клиента, сервер проверяет лишь подпись. Ключ ed25519 не поддаётся словарному перебору, а пароли — да, поэтому боты круглосуточно бьют по 22 порту. Отключаем `PasswordAuthentication`, потому что один слабый пароль у сотрудника обнуляет всю защиту; плюс это убирает шум брутфорса из логов. Отключать — только убедившись, что у всех есть ключи и есть резервный доступ через консоль.

*Что хочет услышать:* понимание асимметричной криптографии, осознание, что ключ не передаётся, и практика «не блокируй себе доступ».

*Красный флаг:* «ключ тоже можно подобрать» или «мы просто ставим сложный пароль на root и всё нормально».

**2. Зачем tmux, если в терминале есть вкладки?**

Ответ: вкладки терминала живут на клиенте и умирают вместе с SSH-соединением. Сервер tmux живёт на удалённой машине и держит процесс независимо от того, есть ли у меня связь. Закрыл ноутбук, отвалился VPN — `tmux attach -t work` и всё на месте. Плюс одна сессия = окна и панели: логи, `htop`, редактор и shell одновременно, и это одинаково работает на любом клиенте. Ещё бонус — совместный доступ к сессии для парной отладки.

*Что хочет услышать:* что tmux — про надёжность долгих процессов, а не про красоту.

*Красный флаг:* «tmux нужен, чтобы удобнее было» без понимания, где живёт сервер сессии.

**3. Как работает `~/.ssh/config` и в каком порядке применяются настройки?**

Ответ: файл читается сверху вниз, срабатывает первое совпавшее правило по `Host` — поэтому общие настройки (`Host *`) пишут в конце. Приоритет: параметры командной строки → пользовательский конфиг → системный `/etc/ssh/ssh_config`. Внутри блока задаются `HostName`, `User`, `Port`, `IdentityFile`, `ProxyJump`, keepalive-параметры. Проверить, что реально применилось, можно через `ssh -G <host>`.

*Что хочет услышать:* «первое совпадение выигрывает» и знание `ssh -G`.

*Красный флаг:* путаница в порядке приоритетов или незнание, что конфиг вообще существует.

**4. Где хранить секреты на рабочей машине и почему не в Git?**

Ответ: в менеджере паролей — KeePassXC с `.kdbx` или `pass` на GPG. В Git секретов быть не должно: история коммитов неизменяема, и после `git rm` секрет остаётся в старых коммитах и в форках/кэшах CI; вычищать приходится `git filter-repo` и всё равно считать скомпрометированным, менять пароль. Для приложений — переменные окружения из защищённого файла или vault (HashiCorp Vault, а в облаке — managed-сервис секретов), в репозитории только `.env.example` с пустыми значениями.

*Что хочет услышать:* «секрет в Git = секрет утёк», плюс понимание, что делать с уже утёкшим.

*Красный флаг:* «у нас приватный репозиторий, значит можно».

**5. WSL2 — это виртуализация или эмуляция? Что это меняет на практике?**

Ответ: WSL2 — настоящая лёгкая ВМ на Hyper-V с реальным ядром Linux, а не трансляция системных вызовов, как WSL1. Поэтому работают `systemd` (включается в `wsl.conf`), Docker, iptables, привычные пакеты. Практические следствия: свой сетевой стек с NAT и пробросом localhost, отдельная файловая система, а `/mnt/c` — сетевой мост в Windows, поэтому медленный; код держим в Linux-разделе. Ресурсы ограничиваются через `.wslconfig` на хосте.

*Что хочет услышать:* разницу WSL1/WSL2 и практические следствия (сеть, файлы, Docker).

*Красный флаг:* «WSL2 — это просто терминал с Linux-командами».
