## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Всё, о чём пойдёт речь, живёт на стыке «пользовательские программы ↔ ядро Linux». К сетевой модели OSI это не относится напрямую: сигналы и `kill` — это системные вызовы внутри ядра, а не сетевые пакеты. Хотя имена у `kill` и `ss`/`tcpdump` похожи, путать их нельзя.

```text
┌──────────────────────────────────────────────────────────────────────┐
│ Пользовательское пространство                                        │
│   Процесс = код + память + таблица fd + учётные данные (UID/GID)      │
│              + набор namespaces + членство в cgroup                   │
├──────────────────────────────────────────────────────────────────────┤
│ Ядро Linux                                                            │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ │
│  │ Планировщик  │ │ Namespaces   │ │ cgroups v2   │ │ VFS / fd     │ │
│  │ CPU, nice    │ │ 8 видов      │ │ cpu, memory, │ │ fd → inode   │ │
│  │              │ │ изоляции     │ │ io, pids     │ │              │ │
│  └──────────────┘ └──────────────┘ └──────────────┘ └──────────────┘ │
│  Сигналы: kill(2) → доставка → обработчик / действие по умолчанию     │
└──────────────────────────────────────────────────────────────────────┘
```

**Процесс.** Ядро хранит на каждый процесс структуру (`task_struct`), а пользователю отдаёт её проекцию в `/proc/PID/`. У процесса есть PID (номер), PPID (родитель), PGID (группа процессов), SID (сессия), состояние (`R` — работает, `S` — спит, `D` — непрерываемый сон на вводе-выводе, `T` — остановлен, `Z` — зомби). Потоки — это те же задачи в `/proc/PID/task/`.

**Сигналы.** Асинхронные уведомления от ядра процессу. Основные: `SIGTERM` (15) — «завершись красиво», `SIGKILL` (9) — «умри немедленно, обработчик не вызывается», `SIGINT` (2) — Ctrl+C, `SIGHUP` (1) — исторически «повис телефонный провод», сейчас «перечитай конфиг» либо «умри», `SIGSTOP` (19) / `SIGCONT` (18) — пауза/продолжить, `SIGUSR1/2` (10/12) — «на усмотрение приложения». Процесс может перехватить любой сигнал, кроме `SIGKILL` и `SIGSTOP`. Процесс в состоянии `D` не реагирует даже на `-9`, пока ядро не отпустит его из системного вызова.

**Права.** У процесса есть реальный (RUID), эффективный (EUID) и сохранённый UID. Проверки доступа идут по EUID. Классический `setuid root` — грубый инструмент: бинарь получает всё могущество root. Современная замена — **capabilities**: набор дискретных привилегий (`cap_net_bind_service` — bind на порт <1024, `cap_net_raw` — raw-сокеты и т. д.). Docker и Kubernetes по умолчанию режут capabilities до минимума именно из-за этого.

**Namespaces.** Восемь видов изоляции видимости: `mnt` (точки монтирования), `pid` (номера процессов), `net` (интерфейсы, порты), `ipc` (очереди сообщений), `uts` (hostname), `user` (UID внутри ≠ снаружи), `cgroup` (видимость иерархии), `time` (смещения часов). В net-namespace контейнера `eth0` — это `veth`-пара, и «порт 80» внутри и снаружи — разные порты.

**cgroups.** Изоляция ресурсов, а не видимости. В cgroup v2 (unified, по умолчанию в Ubuntu 22.04+/24.04) контроллеры `cpu`, `memory`, `io`, `pids`, `cpuset` лежат в `/sys/fs/cgroup/`. Лимит памяти → OOM-killer внутри cgroup, а не убийство всей машины. Именно cgroups — механизм, которым Docker и Kubernetes реализуют `--memory` и `limits`.

**Файловые дескрипторы.** Таблица `fd → struct file → inode`. Один файл может быть открыт много раз разными fd. Лимит `RLIMIT_NOFILE` (мягкий/жёсткий) ограничивает число открытых fd на процесс — отсюда `Too many open files`. `ulimit` меняет лимит в текущей оболочке, `/etc/security/limits.conf` — для PAM-сессий, `LimitNOFILE=` в юните systemd — для сервисов (детали в уроке 8).

## 3. Аналогия из жизни

Представьте заводской цех. Рабочий — это **процесс**: у него есть табельный номер (**PID**), бригада (**PGID**) и смена (**SID**). Сигнал — это записка от мастера: `SIGTERM` — «доделай деталь и уходи домой», `SIGKILL` — «охрана выводит с территории прямо сейчас, инструмент бросай», `SIGHUP` — «перечитай инструкцию заново», `SIGSTOP` — «замри на месте». Если рабочий застрял в станке и не может отпустить руку (**состояние D**), его не уведёт никакая охрана, пока он не высвободится. **Namespaces** — это стены цехов: в своём цехе рабочий видит только свои станки и не знает, сколько их всего на заводе. **cgroups** — это лимиты: не больше 4 кВт и 200 кг материала в час на цех. **Файловые дескрипторы** — это руки рабочего: пока держишь инструмент, не можешь взять новый, а рук конечное число. Где аналогия ломается: у реального рабочего можно отнять инструмент силой в любой момент, а у процесса `SIGKILL` стирает всю его память без единой возможности что-то сохранить — никакой «охраны», которая аккуратно всё разложит по полкам, просто нет.

## 4. Практика и команды

**1. Посмотреть процессы в терминах планировщика**

```bash
ps -eo pid,ppid,pgid,sid,stat,ni,cmd --sort=-%cpu | head -n 15
```

`-e` — все процессы, `-o` — свой список колонок, `--sort=-%cpu` — по убыванию CPU. Пример вывода:

```text
    PID    PPID    PGID     SID STAT  NI CMD
   1187       1    1187    1187 Ss     0 nginx: master process /usr/sbin/nginx
   1188    1187    1187    1187 S      0  \_ nginx: worker process
   2041    1980    2041    1980 S+     0 sleep 600
```

`Ss` = спит + лидер сессии, `S+` = на переднем плане. `PGID`/`SID` критичны: сигнал, посланный группе, уйдёт всем членам.

**2. Дерево процессов и поиск**

```bash
pstree -p
pgrep -a nginx
```

`pstree -p` показывает иерархию с PID — видно, кто чей ребёнок. `pgrep -a` ищет по имени и сразу печатает командную строку. Важно: сервисы из systemd живут в своём cgroup/слайсе, а не под вашим shell.

**3. Заглянуть внутрь процесса**

```bash
cat /proc/2041/status
cat /proc/2041/limits
```

Выдержка из `status`: `Uid: 1000 1000 1000 1000` (real, effective, saved, fs), `Threads: 1`, `CapEff: 0000000000000000` (у непривилегированного — нули), `VmRSS` — резидентная память. В `limits` смотрите строку `Max open files` — мягкий и жёсткий лимиты.

**4. Сигналы: сначала вежливо**

```bash
kill -TERM 2041          # просьба корректно завершиться
kill -HUP  1187          # nginx: перечитать конфиг
kill -STOP 2041; kill -CONT 2041
kill -l                  # полный список сигналов и номеров
```

`kill` без ключа = `-TERM`. `kill -l` выводит таблицу. Привычка «сразу `-9`» — главный маркер новичка: `SIGKILL` не даёт приложению закрыть соединения и дописать логи.

**5. Убить всю группу процессов**

```bash
kill -- -2041
```

Минус перед PGID означает «всей группе». Без минуса вы попадёте только в один процесс, и его дети останутся сиротами (их усыновит PID 1).

**6. Отвязать процесс от терминала**

```bash
setsid sleep 600 &
nohup ./script.sh > /var/log/script.log 2>&1 &
```

`setsid` создаёт новую сессию — процесс не получит `SIGHUP` при закрытии SSH. `nohup` игнорирует `SIGHUP` и перенаправляет вывод. В нормальной эксплуатации для этого есть systemd, а не `nohup` (урок 8).

**7. Лимиты в оболочке и на живом процессе**

```bash
ulimit -a
ulimit -n 4096
sudo prlimit --pid 1188 --nofile=65536:65536
prlimit --pid 1188
```

`ulimit -n` меняет `RLIMIT_NOFILE` **только в текущей оболочке и её потомках**, уже запущенные процессы не трогает. `prlimit` умеет менять лимит работающему процессу (на понижение — без вопросов, на повышение — нужен `CAP_SYS_RESOURCE`/root, и жёсткий лимит поднять обратно уже нельзя).

**8. Считать файловые дескрипторы**

```bash
ls -l /proc/2041/fd | wc -l
lsof -p 2041 | wc -l
lsof -p 2041 | grep -c report.log
lsof -i :8080
```

`/proc/PID/fd` — прямая проекция таблицы fd. `lsof -p` даёт имена файлов и сокетов; `-i :8080` показывает, кто держит порт (это не замена сетевой диагностике из урока 9, но быстрый способ найти PID).

**9. Права и umask**

```bash
umask
umask 027
sudo install -d -o root -g www-data -m 750 /srv/vektor-app
getfacl /srv/vektor-app
sudo setfacl -m u:nobody:r-x /srv/vektor-app
```

`umask 027` = новые файлы `640`, каталоги `750`. `install -d` создаёт каталог сразу с нужными владельцем и правами. ACL (`getfacl`/`setfacl`) дают точечный доступ, не ломая базовые права и не раздавая `777`.

**10. Sudo по минимуму**

```bash
sudo -l
sudo visudo -cf /etc/sudoers.d/vektor-lab
```

Файл `/etc/sudoers.d/vektor-lab`:

```text
<ваш_пользователь> ALL=(root) NOPASSWD: /usr/bin/systemctl status, /usr/bin/systemctl restart vektor-app
```

Разрешаем ровно две команды вместо полного root. `visudo -cf` проверяет синтаксис, не применяя.

**11. Capabilities вместо setuid-root**

```bash
PY=$(readlink -f "$(command -v python3)")
sudo setcap cap_net_bind_service=+ep "$PY"
getcap "$PY"
getpcaps $$
sudo setcap -r "$PY"      # снять обратно
```

`+ep` — effective + permitted. Это позволяет биндить порт 80 без root. Ставить capability на интерпретатор — учебная демонстрация и плохая практика (см. раздел 6); в проде — порт >1024 и reverse-proxy.

**12. Namespaces**

```bash
lsns
sudo unshare --pid --fork --mount-proc bash
# внутри: ps -ef   → видно только bash и ps
exit
sudo unshare --uts bash -c 'hostname lab-ns && hostname'
```

`lsns` показывает namespace-ID по типам. `unshare` создаёт новый namespace для запускаемой команды; `--fork` обязателен для PID-namespace (первый процесс внутри становится PID 1), `--mount-proc` монтирует свежий `/proc`. Для непривилегированных user-namespace в Ubuntu 24.04 может действовать ограничение `kernel.apparmor_restrict_unprivileged_userns` [ПРОВЕРИТЬ] — поэтому в лабе используем `sudo`.

**13. cgroups v2**

```bash
stat -fc %T /sys/fs/cgroup          # ожидаем cgroup2fs
systemd-cgtop -m
sudo systemd-run --scope -p MemoryMax=100M -p CPUQuota=50% bash
# внутри: cat /sys/fs/cgroup$(cat /proc/self/cgroup | cut -d: -f3)/memory.max
```

`systemd-cgtop` — «top по cgroup». `systemd-run --scope` кладёт команду в отдельный cgroup с лимитами. Подробности юнитов — урок 8, здесь важен сам механизм лимитов.

**14. Посмотреть лимиты cgroup напрямую**

```bash
systemctl status nginx | grep -i cgroup
cat /sys/fs/cgroup/system.slice/nginx.service/memory.max
cat /sys/fs/cgroup/system.slice/nginx.service/pids.current
```

`memory.max` = `max` означает «без лимита». `pids.current` — сколько процессов/потоков сейчас в cgroup (защита от fork-бомб).

**Как воспроизвести поломку (на WEB01).** Разворачиваем учебный «портал» с утечкой fd:

```bash
sudo install -d -o "$USER" -g "$USER" -m 750 /srv/vektor-app /var/log/vektor
sudo tee /srv/vektor-app/mini-backend.py >/dev/null <<'EOF'
#!/usr/bin/env python3
import http.server, socketserver

LEAK = []  # намеренная утечка дескрипторов

class H(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path.startswith("/report"):
            for _ in range(5):
                LEAK.append(open("/var/log/vektor/report.log", "a"))
        body = b"ok\n"
        self.send_response(200)
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)
    def log_message(self, *a):
        pass

socketserver.TCPServer.allow_reuse_address = True
with socketserver.TCPServer(("0.0.0.0", 8080), H) as srv:
    srv.serve_forever()
EOF
chmod 750 /srv/vektor-app/mini-backend.py
sudo touch /var/log/vektor/report.log && sudo chown "$USER" /var/log/vektor/report.log
bash -c 'ulimit -n 64; exec /srv/vektor-app/mini-backend.py' &
```

Затем `curl http://127.0.0.1:8080/report` раз 12–15 подряд. На 13-м запросе приложение начнёт отдавать ошибку.

**Диагностика по шагам.**

1. `ss -ltnp | grep 8080` — процесс на порту ещё жив (сетевые детали — урок 9). Значит, это не падение сервиса, а ошибка внутри.
2. `PID=$(ss -ltnp | grep 8080 | grep -oP 'pid=\K[0-9]+'); ps -o pid,ppid,pgid,stat,cmd -p $PID` — смотрим состояние и командную строку.
3. `ls /proc/$PID/fd | wc -l` — если число близко к 60–64, гипотеза подтверждается.
4. `cat /proc/$PID/limits | grep 'open files'` — видим `64 64`: лимит занижен вручную.
5. `lsof -p $PID | grep -c report.log` — видим десятки открытых одинаковых файлов: это и есть утечка.
6. `curl -sv http://127.0.0.1:8080/report 2>&1 | tail -n 20` — в ответе `OSError: [Errno 24] Too many open files`.

**Решение.** Утечку лимитом не лечат. Порядок: (а) временно поднять лимит, чтобы сервис дожил до фикса — `sudo prlimit --pid $PID --nofile=4096:4096` (уже открытые fd не закроются, но новые появятся); (б) починить код — заменить `LEAK.append(open(...))` на `with open("/var/log/vektor/report.log", "a") as f: f.write("")`; (в) перезапустить сервис с нормальным лимитом: `kill -TERM $PID`, затем `bash -c 'ulimit -n 4096; exec /srv/vektor-app/mini-backend.py' &`; (г) в проде — `LimitNOFILE=4096` в юните systemd (урок 8), а не `ulimit` в шелле.

**Ответ пользователю:** «Мария, добрый день. Проблема была на стороне сервиса отчётов: он не освобождал открытые файлы и упирался в лимит. Исправили и перезапустили, отчёты скачиваются. Если повторится — сразу напишите, у нас теперь есть наблюдение за этим».

**Закрытие заявки:** в комментарии указать причину (`fd leak → RLIMIT_NOFILE`), что сделано, и сослаться на будущую задачу «добавить метрику открытых fd в MON01».

## 6. Ошибки новичков и безопасность

1. **`kill -9` первой командой** → приложение не успевает закрыть соединения и сбросить буферы, в логах дыры, клиенты получают обрывы → сначала `SIGTERM`, ждём 10–30 секунд, потом `-9` и только как крайняя мера.
2. **Пытаться убить зомби** → `kill -9` по `Z` не делает ничего, а новичок думает, что «не работает kill» → зомби уже мёртв, он ждёт `wait()` от родителя; чинить нужно родителя (перезапустить его) или его код.
3. **`chmod 777` «чтобы точно работало»** → любой процесс в системе может писать в каталог → `750`/`640` + группа + точечный `setfacl`.
4. **`sudo su -` и жизнь под root** → одна опечатка в `rm -rf` стоит сервера, все действия неатрибутированы → `sudo` на конкретные команды через `/etc/sudoers.d/`, `visudo -cf` для проверки.
5. **`setcap` на интерпретатор (`python3`, `bash`)** → любой скрипт, запущенный этим интерпретатором, получает привилегию; фактически это дыра размером с root → capability ставить на конкретный бинарь или (правильнее) слушать порт >1024 и проксировать через nginx.
6. **`ulimit -n` в шелле для сервиса** → после рестарта или перезахода лимит теряется, а юнит systemd его вообще не увидит → `LimitNOFILE=` в юните, `prlimit` только как временная мера.
7. **Путать namespaces и cgroups** → «я же поставил лимит памяти, почему приложение видит всю память машины?» → namespace меняет видимость, cgroup — потребление; `free` внутри контейнера часто честно показывает память хоста.
8. **Убивать PID 1 в контейнере** → контейнер не умирает или умирает вместе со всем → PID 1 в своём namespace особенный, для корректной обработки сигналов нужен `tini`/`dumb-init` или приложение с обработчиком.

**Безопасность.** В боевой среде нельзя: давать контейнерам `--privileged` и `--pid=host` без крайней необходимости (это фактически выход из изоляции на хост); отключать `seccomp`/AppArmor «потому что приложение не стартует»; расширять capabilities пакетом вместо одной; писать в `/proc/sys/*` и `/sys/fs/cgroup/*` скриптами «на всякий случай». Отдельно: `kill` не имеет никакой аутентификации — любой процесс с тем же EUID может убить ваш; именно поэтому процессы разных сервисов разносят по пользователям и cgroup.

## 7. Вопросы на собеседовании

**1. Чем SIGTERM отличается от SIGKILL и почему `kill -9` — плохая первая реакция?**

`SIGTERM` (15) — это уведомление, которое приложение может перехватить: закрыть соединения, дописать файлы, снять блокировки, выйти с кодом 0. `SIGKILL` (9) обрабатывать нельзя вообще: ядро освобождает память и fd без участия процесса, никакого graceful shutdown нет. `-9` оправдан, когда процесс завис в пользовательском пространстве и не реагирует на `TERM` после разумного таймаута; если процесс в состоянии `D`, `-9` тоже не сработает до выхода из системного вызова. В Kubernetes то же самое: `terminationGracePeriodSeconds` — это окно для `SIGTERM`, и `-9` прилетает после него автоматически.

*Что хочет услышать интервьюер:* понимание разницы «вежливо vs принудительно», таймаута и того, что `-9` не всегда помогает.
*Красный флаг:* «всегда убиваю `-9`, так быстрее».

**2. Что такое namespaces и cgroups, в чём принципиальная разница и как это используется в контейнерах?**

Namespaces изолируют **видимость**: в pid-namespace процесс видит только свою ветку дерева, в net-namespace — только свои интерфейсы, в mnt — свою таблицу монтирования, в uts — свой hostname, в user — свой маппинг UID. cgroups изолируют **потребление ресурсов**: cpu, memory, io, pids, cpuset, и живут в `/sys/fs/cgroup`. Контейнер — это комбинация: namespaces дают иллюзию отдельной машины, cgroups не дают ему съесть хост. Плюс `chroot`/pivot_root для корневой ФС, capabilities и seccomp для сокращения поверхности атаки. Kubernetes `requests`/`limits` транслируются в cgroup-лимиты, а `shareProcessNamespace` — в общий pid-namespace.

*Что хочет услышать интервьюер:* чёткое разделение «видимость vs ресурсы» и привязку к Docker/Kubernetes.
*Красный флаг:* «namespace — это лимит памяти» или «cgroup — это контейнер».

**3. Приложение падает с `Too many open files`. Как диагностировать и что делать?**

Сначала найти процесс: `ss -ltnp` или `pgrep -a`, взять PID. Посмотреть `ls /proc/PID/fd | wc -l` и `cat /proc/PID/limits | grep 'open files'` — сравнить текущее число с лимитом. Затем `lsof -p PID` и посмотреть, чего именно много: одинаковые файлы, сокеты в `CLOSE_WAIT`, пайпы. Если это утечка в коде — чинить код, лимит лишь отложит падение. Если лимит просто мал для нагрузки — поднять `LimitNOFILE` в юните systemd и перезапустить (а не `ulimit` в шелле). Хорошая практика — метрика `process_open_fds` в мониторинге и алерт на 80% от лимита.

*Что хочет услышать интервьюер:* порядок «PID → fd → лимит → причина → фикс», понимание, что лимит не лечит утечку.
*Красный флаг:* «поставил `ulimit -n 100000` и всё заработало».

**4. Почему в контейнере нужен tini или dumb-init?**

В контейнере первый процесс получает PID 1 в своём pid-namespace. У PID 1 в Linux особое поведение: ядро игнорирует сигналы, для которых не установлен обработчик, — то есть дефолтное действие «умереть по SIGTERM» не применяется. Если приложение само не ставит обработчик (java, node, python часто не ставят корректно в этой роли), `docker stop` будет ждать `terminationGracePeriodSeconds` и потом придёт `SIGKILL`. Второй момент — осиротевшие дочерние процессы: их должен кто-то «пожинать» (`wait`), иначе копятся зомби. `tini`/`dumb-init` — крошечные init-процессы: они форвардят сигналы и убирают зомби.

*Что хочет услышать интервьюер:* знание про особенность PID 1 и про reaping зомби, а не просто заученное слово.
*Красный флаг:* «tini нужен для безопасности» (нет, для корректного завершения и зомби).

**5. Чем capabilities лучше setuid-root и как это применяется в Kubernetes?**

`setuid root` выдаёт бинарю весь набор привилегий root — компрометация приложения означает полный контроль над системой. Capabilities дробят привилегии: `cap_net_bind_service` даёт только bind на привилегированные порты, `cap_net_raw` — raw-сокеты, `cap_sys_time` — смену часов. В Kubernetes `securityContext.capabilities` позволяет сбросить все (`drop: ["ALL"]`) и добавить одну нужную (`add: ["NET_BIND_SERVICE"]`), а `allowPrivilegeEscalation: false` и `runAsNonRoot: true` закрывают остальное. Часто правильный ответ — вообще не давать capability, а слушать порт 8080 и проксировать через ingress.

*Что хочет услышать интервьюер:* принцип минимальных привилегий и конкретику применения в k8s.
*Красный флаг:* «capabilities — это то же самое, что sudo».
