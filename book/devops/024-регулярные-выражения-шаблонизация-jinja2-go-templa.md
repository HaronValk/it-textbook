## 2. Теория «под капотом»

### Регулярные выражения

Регулярное выражение (regex) — формальный язык описания множества строк. Движков два типа:

- **POSIX** (BRE — базовые, ERE — расширенные). Это то, что внутри `grep`, `sed`, `awk`. В BRE метасимволы `(`, `)`, `{`, `}`, `+`, `?` надо экранировать (`\(`, `\{`), в ERE — нет.
- **PCRE** (Perl-совместимые). Есть в `grep -P`, Python `re`, PHP. Умеет lookahead/lookbehind, backreferences, ленивые квантификаторы.
- **RE2** (Go, Google). Линеен по времени, без backreferences и lookaround — зато не подвержен «катастрофическому бэктрекингу» (ReDoS). Это осознанный компромисс: в инфраструктурном коде важнее предсказуемость, чем полнота.

Ключевые конструкции: `^` `$` (якоря), `.` (любой символ кроме перевода строки), `[abc]`, `[^abc]`, `\d \w \s`, квантификаторы `* + ? {n,m}` (жадные — съедают максимум), `*?` (ленивые, только PCRE/Python), группы `( )`, именованные группы `(?P<name>…)`, backreference `\1`, альтернация `|`.

### Шаблонизация

Шаблон — текст с «дырками». Движок подставляет значения, вычисляет условия и циклы, выдаёт готовый файл. Правило номер один: **шаблон и данные живут в Git, сгенерированные файлы — не редактируются руками**.

```text
   ИСТОЧНИК ПРАВДЫ              ШАБЛОН                        РЕНДЕР
   inventory/web01.yml  +  templates/nginx-site.conf.j2  ──►  out/*.conf
        (данные)                (структура)                     (файлы)
                                                                   │
   GIT ◄── commit ── ПРОВЕРКА ◄── ДЕПЛОЙ ◄── ВАЛИДАЦИЯ ◄──────────┘
   (история)          curl        scp+reload    nginx -t
                                     WEB01
```

**Jinja2** (Python) — синтаксис: `{{ переменная }}` — вывод, `{% if %}` / `{% for %}` / `{% endfor %}` — логика, `{%- ... -%}` — обрезка пробелов вокруг тега, `~` — конкатенация строк, фильтры через `|` (`| upper`, `| default`, `| replace`), тесты `is defined`, наследование `{% extends %}` + `{% block %}`, переиспользование `{% include %}` и `{% macro %}`. Критично: по умолчанию неопределённая переменная рендерится в пустую строку — то есть шаблон молча выдаст `server_name ;` и ты узнаешь об этом в проде. Лечится `undefined=StrictUndefined` или `--strict`.

**Go templates** (`text/template`, `html/template`) — синтаксис: `{{ .Field }}` — поле структуры или ключ map, `{{ .Values.image }}` — цепочка, `{{ if }}…{{ else }}…{{ end }}`, `{{ range }}…{{ end }}`, `{{ printf "%s:%d" }}`, `{{ template "имя" . }}`, `{{ define "имя" }}`. В отличие от Jinja2, в Go нет фильтров «из коробки» — вместо них функции, которые надо зарегистрировать (`FuncMap`), либо библиотека Sprig (её использует Helm). Пробелы управляются так же: `{{-` и `-}}`. `html/template` автоматически экранирует вывод — защита от XSS в веб-шаблонах; для конфигов берут `text/template`.

Где это в общей картине: сеть тут не при чём (всё на прикладном уровне, L7), а вот слоёв ОС касается напрямую — шаблон генерирует файл в `/etc`, systemd перечитывает юнит, nginx — конфиг. И самое главное место: **CI/CD-пайплайн**. Рендер — это стадия pipeline, такая же, как сборка или тесты.

## 3. Аналогия из жизни

Представь юридический отдел. Есть **типовой договор** — красивый бланк с пустыми полями: `{ФИО}`, `{сумма}`, `{дата}`. Это шаблон. Есть **карточка клиента** в CRM — там лежит, что Иванов, 150 000, 12.03. Это данные. Секретарь берёт бланк, подставляет данные из карточки — получается готовый договор. Это рендер. Меняется форма договора (добавили пункт) — правишь бланк один раз, и все будущие договоры выходят правильными. Это и есть смысл шаблонизации.

А **регулярное выражение** — это корректор, который умеет находить в стопке бумаг «все номера договоров вида ВК-2026-XXXX» и говорить: вот тут номер битый, тут поля не заполнены, а тут срок истёк.

Где аналогия ломается: бланк не умеет сам решать, что делать, если поле пустое — секретарь хотя бы заметит и спросит. Jinja2 без `StrictUndefined` просто подставит пустоту и промолчит.

## 4. Практика и команды

Все примеры — на стенде: логи nginx лежат на WEB01, генерация — на UBU01 (10.10.10.30). Пользователя Linux на WEB01 подставь своего; ниже в примерах — `adm`.

### 4.1. `grep -E` — найти 5xx в логе

```bash
grep -cE '" (5[0-9]{2}) ' /var/log/nginx/access.log
```

`-c` — только счётчик, `-E` — расширенные регулярки. Формат combined у nginx: `… "GET /hr/ HTTP/1.1" 502 173 …`, поэтому шаблон `" (5[0-9]{2}) ` цепляет статус вместе с кавычкой и пробелом. Вывод: `17`. Смотрим: число больше нуля — есть проблема, дальше копаем.

### 4.2. `grep -o` — вытащить сами запросы

```bash
grep -oE '"(GET|POST|HEAD) [^"]+"' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -5
```

`-o` печатает только совпавшую часть. `[^"]+` — «любые символы, кроме кавычки, один и больше» — так мы не вылезаем за границу поля. Вывод:

```text
    412 "GET /hr/ HTTP/1.1"
     87 "GET /buh/ HTTP/1.1"
     12 "GET /sklad/ HTTP/1.1"
```

Смотрим: какой сайт грузят чаще — это будущий кандидат на отдельный сервер.

### 4.3. `grep -P` — PCRE, если очень надо

```bash
grep -oP '^(?:\S+ ){2}\K[0-9.]+' /var/log/nginx/access.log | head -3
```

`-P` включает Perl-совместимый движок, `(?:…)` — группа без захвата, `\K` — «начать вывод отсюда». Вывод: `10.10.20.5`. Смотрим: помни, что `-P` есть не везде (в busybox и на некоторых сборках нет) — в скриптах для переносимости лучше `awk`.

### 4.4. `sed -E` — заменить с группами

```bash
sed -E 's/^([0-9]{1,3}(\.[0-9]{1,3}){3}).*/\1/' /var/log/nginx/access.log | head -3
```

`-E` — ERE, `\1` — ссылка на первую группу (весь IP), группа 2 — последний октет. `.` экранируем как `\.`, иначе он «любой символ». Осторожно с `sed -i`: он меняет файл на месте, поэтому сначала всегда прогоняй без `-i` и смотри вывод.

### 4.5. `awk` — регулярка как условие фильтрации

```bash
awk '$9 ~ /^5/ {print $1, $7, $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head
```

`$9 ~ /^5/` — «поле 9 начинается с 5». Поля combined-лога: 1 — IP, 6 — метод, 7 — путь, 8 — версия протокола, 9 — статус. Вывод: `14 10.10.20.5 /buh/ 502`. Смотрим: видно, кто и куда ломится с ошибками.

### 4.6. Python `re` — именованные группы и `groupdict`

```python
import re

PATTERN = re.compile(
    r'^(?P<ip>\S+) \S+ \S+ \[(?P<ts>[^\]]+)\] '
    r'"(?P<method>[A-Z]+) (?P<path>\S+) [^"]*" (?P<status>\d{3})'
)

line = '10.10.20.5 - - [12.03.2026:10:15:02 +0300] "GET /buh/ HTTP/1.1" 502 173'
m = PATTERN.match(line)
print(m.groupdict() if m else "no match")
# {'ip': '10.10.20.5', 'ts': '12.03.2026:10:15:02 +0300',
#  'method': 'GET', 'path': '/buh/', 'status': '502'}
```

`\S+` — не-пробел, `[^\]]+` — «до закрывающей скобки», `?P<имя>` — именованная группа, чтобы не путаться в `\1..\9`. `re.compile` один раз — быстрее при тысячах строк. `match` цепляет с начала строки, `search` — где угодно.

### 4.7. Go `regexp` — RE2 и его границы

```go
re := regexp.MustCompile(`^(?P<ip>\S+) .*" (?P<status>\d{3}) `)
for _, m := range re.FindAllStringSubmatch(line, -1) {
    fmt.Println(m[re.SubexpIndex("ip")], m[re.SubexpIndex("status")])
}
```

`MustCompile` паникует при ошибке компиляции — удобно для статичных регулярок (в рантайме с пользовательским вводом бери `Compile`). `SubexpIndex` — доступ к группе по имени. **Важно:** RE2 не поддерживает `(?=…)`, `(?<=…)` и `\1` в самом шаблоне — при попытке будет ошибка компиляции. Переносишь PCRE-регулярку в Go — проверь, не сломалась ли она.

### 4.8. Jinja2-шаблон конфига nginx

```jinja
# templates/nginx-site.conf.j2
server {
    listen {{ site.listen }};
    server_name {{ site.name }};
    root {{ site.root }};
    index index.html;

    access_log /var/log/nginx/{{ site.name }}.access.log;
    error_log  /var/log/nginx/{{ site.name }}.error.log;

    location / {
        try_files $uri $uri/ =404;
    }
}
```

Каждое поле — из данных. Обрати внимание: имя логов тоже шаблонизируется, иначе все три сайта пишут в один файл и разбирать его потом невозможно.

### 4.9. `render.py` — строгий рендер с данными из YAML

```python
from pathlib import Path
import yaml
from jinja2 import Environment, FileSystemLoader, StrictUndefined

env = Environment(
    loader=FileSystemLoader("templates"),
    undefined=StrictUndefined,   # падаем, если переменной нет
    trim_blocks=True,            # убрать перевод строки после {% %}
    lstrip_blocks=True,          # убрать отступ перед {% %}
)
tpl = env.get_template("nginx-site.conf.j2")
data = yaml.safe_load(Path("inventory/web01.yml").read_text())

out = Path("out")
out.mkdir(exist_ok=True)
for site in data["sites"]:
    (out / f"{site['name']}.conf").write_text(tpl.render(site=site), encoding="utf-8")
    print("rendered:", site["name"])
```

`StrictUndefined` — самая важная строка: вместо тихого `server_name ;` получишь `jinja2.exceptions.UndefinedError` и упавшую стадию pipeline. `trim_blocks`/`lstrip_blocks` убирают мусорные пустые строки из вывода. `safe_load` (а не `load`) — обязателен, иначе YAML может исполнить произвольный код.

### 4.10. Jinja2 из командной строки — быстро проверить шаблон

```bash
python -m jinja2 --strict -D site.name=hr.vektor.lab -D site.root=/var/www/hr.vektor.lab/html \
  templates/nginx-site.conf.j2
```

`-D имя=значение` передаёт переменную, `--strict` включает строгий режим. Удобно для одноразовой проверки; точный список ключей смотри в `python -m jinja2 --help` `[ПРОВЕРИТЬ]`. Для реальной генерации лучше свой скрипт из 4.9 — он воспроизводимее.

### 4.11. Ansible `template` — то же, но сразу с доставкой

```bash
ansible web01 -i inventory/hosts.ini -b -m ansible.builtin.template \
  -a "src=templates/nginx-site.conf.j2 dest=/etc/nginx/sites-available/hr.vektor.lab.conf backup=yes validate='/usr/sbin/nginx -t -c %s'"
```

`-b` — become (sudo), `backup=yes` — сохранить предыдущую версию рядом, `validate` — прогнать `nginx -t` на временном файле и **не класть** конфиг, если он битый. Ansible и есть главный потребитель Jinja2 в инфраструктуре; поднимается на UBU01 пакетом `ansible` из репозитория Ubuntu `[ПРОВЕРИТЬ актуальную версию]`.

### 4.12. Go template — тот же конфиг на другом движке

```go
package main

import (
	"os"
	"text/template"
)

type Site struct{ Name, Root string }

func main() {
	const tpl = `{{- range . }}
server {
    listen 80;
    server_name {{ .Name }};
    root {{ .Root }};
}
{{ end -}}`
	sites := []Site{
		{"hr.vektor.lab", "/var/www/hr.vektor.lab/html"},
		{"buh.vektor.lab", "/var/www/buh.vektor.lab/html"},
	}
	t := template.Must(template.New("site").Parse(tpl))
	if err := t.Execute(os.Stdout, sites); err != nil {
		panic(err)
	}
}
```

`{{- range . }}` — цикл по слайсу, `.Name` — поле элемента (внутри `range` точка — это элемент). `{{-` и `-}}` съедают пробелы — без них получишь лишние пустые строки. Отличие от Jinja2: нет `|`, фильтры — это зарегистрированные функции.

### 4.13. Helm — Go-шаблоны поверх Kubernetes

```yaml
# templates/cm.yaml
{{- range .Values.sites }}
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-{{ .name | replace "." "-" }}
data:
  site.conf: |
    server {
        listen 80;
        server_name {{ .name }};
    }
{{- end }}
```

```bash
helm template web ./chart -f values.yaml > out/k8s.yaml
```

`replace` — функция Sprig (Helm подключает её автоматически). `helm template` рендерит локально, без кластера — это твой основной инструмент отладки чартов и тестов в CI.

### 4.14. Валидация перед деплоем

```bash
sudo nginx -t          # синтаксис + доступность файлов
sudo nginx -T | grep -n "server_name"   # весь итоговый конфиг после include
```

`-t` проверяет конфиг и не перезапускает nginx; `-T` выводит полностью собранный конфиг со всеми `include` — то, что nginx реально применит. Это и есть «диагностика вслепую» по одному взгляду.

## 6. Ошибки новичков и безопасность

1. **Жадные квантификаторы без нужды.** `.*"` съест всё до *последней* кавычки в строке → неверный разбор лога. → Используй `[^"]*` или ленивый `.*?` (где движок позволяет).
2. **Регулярка для парсинга JSON/YAML.** `grep` по JSON ломается на вложенности и экранировании. → Структурированные данные — структурными инструментами: `jq`, `yq` (глава 23), а regex — для логов и текста.
3. **Рендер без `StrictUndefined`.** Шаблон молча подставляет пустые значения → валидный по синтаксису, но неработающий конфиг. → Строгий режим + валидация в пайплайне.
4. **Генерация сразу в `/etc`.** Один битый рендер — и сервис не поднимется, а откатывать нечем. → Рендер в `out/`, `nginx -t` на копии, `backup=yes`, атомарная замена.
5. **Правка сгенерированного файла руками.** Через день шаблон перезапишет правку, и начнётся «то работает, то нет». → Правится inventory или шаблон, всегда и только.
6. **Копипаста шаблона под каждый сайт.** Возвращает ту же проблему, от которой уходили. → Один шаблон + список в данных + цикл.
7. **`sed -i` без предварительного просмотра.** Массовая порча файлов за одну команду. → Сначала без `-i`, глазами, потом с `-i.bak`.
8. **Опечатка в имени сайта проходит `nginx -t`.** Синтаксис валиден, но конфиг неверен. → Проверяй не только синтаксис, но и содержание: `curl -H "Host: …"` по каждому имени в списке.

### Безопасность

- **Секреты в шаблонах и values.** Пароли и токены не кладутся в Git ни в шаблоне, ни в inventory — только через переменные окружения, Ansible Vault или внешний секрет-стор. В учебном стенде пароль один и он явно помечен как учебный; в реальной среде так нельзя.
- **SSTI (Server-Side Template Injection).** Если Jinja2-шаблон собирается из пользовательского ввода — это путь к исполнению кода на сервере. Шаблоны пишет только инженер, данные приходят отдельно.
- **ReDoS.** Регулярки с вложенными квантификаторами (`(a+)+$`) на длинном вводе кладут CPU. В Go это невозможно (RE2), в Python — вполне. Не применяй «умные» регулярки к неограниченному пользовательскому вводу.
- **`autoescape` в `html/template` и Jinja2.** Для HTML-шаблонов экранирование обязательно, иначе XSS. Для конфигов — наоборот, `text/template`.
- **Права на файлы.** Конфиги nginx — `0644 root:root`, каталог `sites-enabled` не должен быть доступен на запись кому попало. Иначе шаблонизация превращается в вектор локального повышения привилегий.
- **Отключение `nginx -t` «чтобы быстрее».** Ровно один раз сэкономишь секунду — и получишь лежащий веб-сервер.

## 7. Вопросы на собеседовании

**1. Чем регулярные выражения в Go отличаются от PCRE и что это значит на практике?**

Go использует RE2: гарантированно линейное время работы, нет backreferences, lookahead и lookbehind, зато нет и ReDoS. На практике: регулярку, написанную для `grep -P` или Python, нельзя механически перенести — часть конструкций просто не скомпилируется, придётся переписать через дополнительные проходы (например, сначала разрезать строку, потом применять регулярку к части). Зато если正则 применяется к пользовательскому вводу в высоконагруженном сервисе — RE2 безопаснее.

*Что хочет услышать интервьюер:* понимание компромисса «функциональность против предсказуемости» и что инженер не тащит PCRE-привычки в Go вслепую.
*Красный флаг:* «да они одинаковые, везде же regex».

**2. Что произойдёт в Jinja2, если переменной нет, и как сделать строго?**

По умолчанию подставится пустая строка — рендер «успешен», конфиг битый. Строгий режим: `Environment(undefined=StrictUndefined)` в Python-коде, `--strict` в CLI, в Ansible — переменная `ANSIBLE_UNDEFINED_VAR_BEHAVIOR`/настройка `error_on_undefined_vars` `[ПРОВЕРИТЬ точное имя опции в твоей версии]`. Дополнительно: `assert`/валидация схемы inventory до рендера и `nginx -t` после.

*Что хочет услышать интервьюер:* что инженер делает «тихие» ошибки шаблонов громкими и ловит их в pipeline, а не в проде.
*Красный флаг:* «Jinja2 же выдаст ошибку».

**3. Как безопасно раскатить изменение конфига на 10 серверов?**

Пайплайн: правка inventory/шаблона → PR и ревью → рендер в CI → валидация (`nginx -t`, `--check` у Ansible) → `diff` с текущим состоянием → канареечный деплой на один узел → проверка (health-check, `curl`) → раскатка на остальные → запись в changelog. Обязательно: бэкап предыдущей версии, возможность отката в одну команду, идемпотентность (повторный запуск не меняет ничего).

*Что хочет услышать интервьюер:* «рендер → валидация → поэтапный выкат → откат», а не «залил и перезапустил».
*Красный флаг:* «сделаю `scp` на все и `systemctl restart`».

**4. Если у тебя 50 почти одинаковых конфигов — что сделаешь?**

Один параметризованный шаблон + данные в YAML/JSON (или values-файл в Helm) + генератор. Наследование в Jinja2 (`extends`/`block`) — когда есть общая база с вариациями; `include` и `macro` — для переиспользуемых фрагментов (например, общий блок `location /health`). В Helm аналог — `_helpers.tpl` с `define` и `include`. Ключевое: данные ≠ структура, и то и другое в Git.

*Что хочет услышать интервьюер:* DRY осознанно, без фанатизма — «три копии лучше преждевременной абстракции, но пятьдесят — уже нет».
*Красный флаг:* «сделаю 50 файлов, зато наглядно».

**5. Как тестировать шаблоны?**

Golden files (эталонный отрендеренный файл в репозитории + `diff` в CI), тесты на «шаблон падает при отсутствующей переменной», `helm template`/`helm lint` в CI для чартов, `ansible-playbook --check --diff` для плейбуков, molecule для ролей `[ПРОВЕРИТЬ актуальность инструмента]`, и обязательно smoke-тест после деплоя (`curl` с нужным `Host`). Хорошая практика — рендерить и валидировать артефакт в CI ещё до того, как он попадёт на сервер.

*Что хочет услышать интервьюер:* шаблон — это код, значит он тестируется, ревьюится и версионируется.
*Красный флаг:* «шаблоны тестировать нечем, смотрим глазами».
