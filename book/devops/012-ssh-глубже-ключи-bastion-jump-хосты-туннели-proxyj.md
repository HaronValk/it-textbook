# SSH глубже: ключи, bastion/jump-хосты, туннели, ProxyJump, SSH CA

## 1. Введение (зачем это нужно в реальной работе)

**Заявка №412**

> **Пользователь:** Алексей Сидоров (склад), ВМ WIN10-CL02

Классика. Сервер в DMZ, из офисной сети напрямую недоступен, пароль никто не выдавал, а «сделайте нормально» — это и есть работа DevOps-инженера: не открыть 22-й порт в DMZ настежь, а построить нормальную схему доступа.

SSH — тот инструмент, которым ты будешь пользоваться каждый день до конца карьеры. И если на L1 это «скопировал ключ, зашёл, вышел», то на DevOps — это целый слой инфраструктуры: как инженеры попадают на серверы, как выдаются и отзываются ключи, как администрировать машины без публичных адресов, как прокидывать порты в закрытые сегменты и как автоматизировать всё это так, чтобы Ansible, CI-раннер и Terraform работали без человека.

После этой главы ты будешь уметь: генерировать и грамотно защищать ключи; настраивать `~/.ssh/config` так, чтобы `ssh web01` работал через bastion одной командой; поднимать локальные и удалённые туннели; харднить `sshd` и — главное — настраивать SSH CA, чтобы выдавать временные доступы пачками и отзывать их одним движением, а не правкой `authorized_keys` на двухстах серверах.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

SSH (Secure Shell) — прикладной протокол, работает поверх TCP, стандартный порт 22. В модели OSI это L7, но он «оборачивает» собой всё, что через него ходит: терминал, файлы, порты, X11.

Протокол SSH-2 состоит из трёх слоёв, и это важно понимать, потому что ошибки на каждом слое выглядят по-разному:

1. **Transport layer** — шифрование канала. Здесь происходит обмен ключами Диффи–Хеллмана (обычно Curve25519), согласование алгоритмов (kex, cipher, MAC), аутентификация **хоста** по его host key. После этого весь трафик шифруется. Ошибка на этом слое — `Connection refused`, `Connection timed out`, `Host key verification failed`.
2. **User authentication layer** — проверка **пользователя**: пароль, публичный ключ, клавиатурное взаимодействие (2FA), GSSAPI/Kerberos (актуально для AD-инфраструктуры). Ошибка здесь — `Permission denied (publickey)`.
3. **Connection layer** — мультиплексирование: в одном TCP-соединении живут несколько «каналов» (channels): сессия shell, `scp`/`sftp`, проброс портов, agent forwarding. Именно поэтому `ssh -L` работает «внутри» уже установленного соединения.

**Ключи.** Приватный ключ (файл без расширения) остаётся у тебя, публичный (`*.pub`) кладётся в `~/.ssh/authorized_keys` на сервере. Аутентификация — это подпись challenge приватным ключом; приватный ключ по сети **никогда** не передаётся. Рекомендуемый тип сейчас — `ed25519` (короткий, быстрый, нет проблем с параметрами, как у RSA). RSA (`rsa-sha2-256/512`) остаётся для legacy-систем. ECDSA — реже, DSA — выбросить.

**Host key и TOFU.** У каждого sshd есть свой host key. Клиент при первом подключении запоминает его в `~/.ssh/known_hosts` — модель «Trust On First Use». Отсюда классика: переустановил сервер, ключ сменился — `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED`. Это защита от MITM, и «просто удалить строчку» — плохая привычка, если ты не понимаешь, почему ключ сменился.

**Bastion / jump host.** Промежуточная машина в периметре, единственный вход во внутренний сегмент. На стенде это GW01 (10.10.10.3 в офисной сети, 10.10.20.1 в DMZ).

```text
        Офисная сеть VMnet8 10.10.10.0/24        │      DMZ VMnet10 10.10.20.0/24
                                                  │
  [клиент: WSL2/десктоп]                          │
        │  ssh student@10.10.10.30   ─────────────┼──► UBU01 10.10.10.30   (напрямую)
        │                                         │
        │  ssh web01  ──┐                         │
        ▼               │                         │
  ┌─────────────────┐   │  ProxyJump (один TCP,   │
  │  GW01 (bastion) │◄──┘  внутри — direct-tcpip) │
  │ 10.10.10.3      │                             │
  │ 10.10.20.1      │──── ssh student@10.10.20.10 ┼──► WEB01 10.10.20.10 (только через GW01)
  └─────────────────┘                             │
        ▲                                         │
        └── ssh -L 8080:127.0.0.1:80 web01 ───────┘   локальный туннель до nginx на WEB01
```

**ProxyJump vs ProxyCommand.** `ProxyCommand` (старый способ) запускает локальный процесс `ssh` и гоняет трафик через его stdin/stdout — два отдельных TCP-соединения, медленнее, ломается на длинных путях. `ProxyJump` (`-J`) — нативная функция OpenSSH: клиент открывает соединение до bastion и просит его открыть канал `direct-tcpip` до целевого хоста. Один TCP, работает с multiplexing, чище в конфиге.

**Туннели.**
- **Локальный (`-L`)**: `клиент:port → [ssh-сервер] → цель:port`. Слушает на твоей машине. Классика для «достучаться до БД/вебморды в закрытом сегменте».
- **Удалённый (`-R`)**: `сервер:port → [твой клиент] → цель:port`. Слушает на удалённой стороне. Нужен, когда за NAT сидишь ты.
- **Динамический (`-D`)**: поднимает SOCKS5-прокси на локальной стороне, дальше браузер/`curl` ходят через него куда угодно.

**SSH CA (Certificate Authority).** Вместо `authorized_keys` на каждом сервере — один файл с публичным ключом CA (`TrustedUserCAKeys`). CA подписывает **сертификат** пользователя: в нём зашиты ключ пользователя, набор **принципалов** (каким логинам можно логиниться), срок жизни, серийный номер и ограничения (запрет форвардинга, forced command, source-address). Сервер проверяет подпись CA и срок — и всё. Отзыв — либо короткий TTL (выдали на 8 часов), либо KRL (`RevokedKeys`) / `AuthorizedPrincipalsFile`. Host-сертификаты решают ту же проблему с той стороны: клиент один раз доверяет host-CA (`@cert-authority` в `known_hosts`) и больше не видит вопросов TOFU.

В продакшене CA-ключ живёт не на ноутбуке, а в HashiCorp Vault (ssh secrets engine), step-ca, Teleport или в облачном IAM (PCA/OS Login). Инженер идёт в Vault, тот подписывает его ключ на 15 минут — и всё.

## 3. Аналогия из жизни

Представь завод с проходной. **SSH-ключ** — это личная печать сотрудника: предъявил печать — прошёл. **Bastion(GW01)** — та самая проходная: единственное место, где вообще проверяют документы, и через неё лежит путь во все цеха (DMZ). **Туннель `-L`** — служебный коридор, по которому ты из проходной идёшь не в цех, а сразу к конкретному станку (порту 80 на WEB01), и наружу этот коридор не выходит. **SSH CA** — отдел кадров, который выдаёт **временные** пропуска: не «печать на всю жизнь», а бумажка «Петров, цех №2, до 18:00». Ушёл человек — не надо обходить 200 цехов и выламывать печати из дверей: просто пропуск истекает через 8 часов.

Аналогия ломается в одном: на проходной охранник смотрит в лицо и сверяет с фотографией, а SSH не смотрит никуда. В SSH **владение приватным ключом = личность**. Украли файл — украли тебя, и никакой «фотографии» в системе нет, поэтому ключ с паролем и коротким сроком жизни — не паранойя, а минимум.

## 4. Практика и команды

Все команды ниже выполняются на стенде «Вектор». Клиент — твоя Linux-машина (WSL2 или десктоп-ВМ, см. урок 4), локальный пользователь `student`. Серверы стенда — UBU01 (10.10.10.30), WEB01 (10.10.20.10), GW01 (10.10.10.3 / 10.10.20.1).

### 4.1. Генерация ключа

```bash
ssh-keygen -t ed25519 -a 100 -C "student@vektor-devops" -f ~/.ssh/id_ed25519_vektor
```

- `-t ed25519` — тип ключа (современный дефолт, 256 бит, эквивалент ~3000-битного RSA по стойкости);
- `-a 100` — число KDF-раундов при шифровании приватного ключа паролем (дефолт 16; больше — медленнее подбор);
- `-C` — комментарий, попадёт в `.pub` и будет виден в логах;
- `-f` — путь. Если файл существует, команда откажется перезаписывать.

Вывод: `Your identification has been saved in ...`, `Your public key has been saved in ...`, `The key fingerprint is: SHA256:... student@vektor-devops`. **Смотри:** fingerprint сразу запиши — он нужен для сверки при выдаче доступа.

Парольную фразу задавай обязательно. Пустая — это ключ, который утечёт вместе с ноутбуком.

### 4.2. Посмотреть, что получилось

```bash
ssh-keygen -lf ~/.ssh/id_ed25519_vektor.pub      # отпечаток и тип
ssh-keygen -y -f ~/.ssh/id_ed25519_vektor        # публичная часть из приватного
ssh-keygen -p -f ~/.ssh/id_ed25519_vektor        # сменить пароль на ключе
```

`-l` — показать fingerprint, `-f` — файл. Вывод: `256 SHA256:9xQ... student@vektor-devops (ED25519)`. **Смотри:** `256` — длина в битах, тип в скобках. `-y` выручает, когда потерял `.pub` (его можно восстановить из приватного, наоборот — нельзя).

### 4.3. Копирование ключа на сервер

```bash
ssh-copy-id -i ~/.ssh/id_ed25519_vektor.pub student@10.10.10.30
```

Утилита заходит по паролю и аккуратно дописывает ключ в `~/.ssh/authorized_keys`, создавая каталог с правами 700. Вывод: `Number of key(s) added: 1`, дальше `Now try logging into the machine`. **Смотри:** если пишет `All keys were skipped because they already exist` — ключ уже там.

### 4.4. Проверка прав (главная причина «Permission denied»)

```bash
ssh student@10.10.10.30 'ls -ld ~ ~/.ssh ~/.ssh/authorized_keys'
```

Ожидаемо: `drwxr-x--- ... /home/student`, `drwx------ ... .ssh`, `-rw------- ... authorized_keys`. **Смотри:** sshd игнорирует `authorized_keys`, если файл или каталог доступны на запись группе/остальным, а также если домашний каталог доступен на запись другим. Это называется strict modes, отключается через `StrictModes no` — и отключать этого нельзя.

### 4.5. Подробная диагностика соединения

```bash
ssh -vvv student@10.10.10.30
```

`-v`/`-vv`/`-vvv` — уровень отладки на клиенте. В выводе смотри по порядку: `debug1: Connecting to 10.10.10.30 port 22` (дошли ли до TCP), `debug1: kex: algorithm: sntrup761x25519-sha512` (какие алгоритмы согласовали — примерно так выглядит в OpenSSH 9.x, набор зависит от версии), `debug1: Authentications that can continue: publickey,password` (что сервер вообще разрешает), `debug1: Offering public key: ... ED25519 SHA256:...` и `Server accepts key` или `no such identity`.

Дополнительно на сервере: `sudo journalctl -u ssh -n 50 -t sshd` — там будет причина отказа со стороны sshd.

### 4.6. Конфиг клиента: `~/.ssh/config`

```sshconfig
Host gw01
    HostName 10.10.10.3
    User student
    IdentityFile ~/.ssh/id_ed25519_vektor

Host web01
    HostName 10.10.20.10
    User student
    ProxyJump gw01
    IdentityFile ~/.ssh/id_ed25519_vektor
    ServerAliveInterval 30
    ServerAliveCountMax 3

Host ubu01 mon01
    User student
    IdentityFile ~/.ssh/id_ed25519_vektor
    IdentitiesOnly yes
```

`ProxyJump gw01` — имя из этого же файла; `ServerAliveInterval 30` — keepalive каждые 30 с (спасает от обрыва NAT-сессий); `IdentitiesOnly yes` — предлагать только указанный ключ, а не все подряд из агента (иначе на серверах с `MaxAuthTries 3` тебя выкинет раньше, чем дойдёт до нужного ключа). Права на файл: `chmod 600 ~/.ssh/config`.

Проверить, что ssh реально применил: `ssh -G web01 | grep -Ei 'hostname|user|proxyjump|identityfile'` — выводит итоговый конфиг без подключения.

### 4.7. ProxyJump вручную

```bash
ssh -J student@10.10.10.3:22 student@10.10.20.10
```

`-J [user@]host[:port]` — цепочка прыжков, можно перечислять через запятую (`-J a,b`). Раньше писали `ssh -o ProxyCommand='ssh -W %h:%p gw01' ...` — работает, но это два TCP и лишний процесс. Порт `:22` можно опускать.

### 4.8. Локальный туннель до веб-сервера в DMZ

```bash
ssh -N -L 127.0.0.1:8080:127.0.0.1:80 web01
# в другом терминале:
curl -sI http://127.0.0.1:8080
```

- `-L [bind]:port:host:port` — что слушать локально и куда forwarding'ить **с точки зрения ssh-сервера**;
- `-N` — не выполнять удалённую команду (только туннель);
- явный `127.0.0.1` в bind — критично: без него часть версий может слушать на всех интерфейсах, и туннель увидят соседи по сети.

Вывод `curl`: `HTTP/1.1 200 OK`, `Server: nginx/...`. **Смотри:** заголовок `Server` — так ты убеждаешься, что попал именно на WEB01, а не на что-то локальное.

### 4.9. Динамический туннель (SOCKS5) и удалённый форвард

```bash
ssh -N -f -D 127.0.0.1:1080 web01
curl --socks5-hostname 127.0.0.1:1080 -sI http://10.10.20.10
ssh -N -R 127.0.0.1:9000:127.0.0.1:22 student@10.10.10.30
```

`-D` — SOCKS5 на локальной стороне, дальше трафик идёт через WEB01; удобно, когда надо «пожить» внутри сегмента из браузера. `-f` — уйти в фон. `-R 127.0.0.1:9000:127.0.0.1:22` — на UBU01 откроется `127.0.0.1:9000`, ведущий обратно на SSH твоего клиента; так заходят на машину за NAT. По умолчанию remote-форвард слушает только loopback; `GatewayPorts yes` на сервере расширит это на все интерфейсы — в проде почти всегда ошибка.

### 4.10. SSH-агент

```bash
eval "$(ssh-agent -s)"
ssh-add -t 8h ~/.ssh/id_ed25519_vektor
ssh-add -l
```

`-t 8h` — агент забудет ключ через 8 часов (ровно рабочая смена). `ssh-add -l` покажет загруженные ключи и их отпечатки. **Смотри:** `The agent has no identities` — ключ не загружен, отсюда странные `Permission denied` при работающем `authorized_keys`.

Форвардинг агента (`ssh -A`) — не включай: любой с root на промежуточной машине может использовать твой агент, пока сессия жива.

### 4.11. Харднинг sshd (на UBU01)

```bash
sudo tee /etc/ssh/sshd_config.d/99-vektor-hardening.conf >/dev/null <<'EOF'
PermitRootLogin prohibit-password
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
PermitEmptyPasswords no
X11Forwarding no
AllowAgentForwarding no
MaxAuthTries 3
LoginGraceTime 30
AllowUsers student
EOF
sudo sshd -t && sudo systemctl reload ssh
```

`sshd -t` — проверка синтаксиса **до** перезагрузки (не пропускай, иначе рискуешь остаться без sshd). `sshd -T` — вывести итоговый конфиг после всех include. На Ubuntu 24.04 в `/etc/ssh/sshd_config.d/` уже может лежать `50-cloud-init.conf` с `PasswordAuthentication yes` — файлы читаются по алфавиту, и `99-` перебивает `50-`. Проверяй `sudo sshd -T | grep -i passwordauth`.

### 4.12. SSH CA: создаём CA и подписываем пользовательский ключ

```bash
# на клиенте, ОДИН раз. Приватный ключ CA — 600, в идеале не на ноутбуке
mkdir -p ~/ssh-ca && chmod 700 ~/ssh-ca
ssh-keygen -t ed25519 -f ~/ssh-ca/ca_user -C "VEKTOR user CA" -a 100

# подписываем свой публичный ключ на 8 часов, логин разрешён как student
ssh-keygen -s ~/ssh-ca/ca_user -I "student-$(date +%F)" -n student -V +8h \
  ~/.ssh/id_ed25519_vektor.pub
# появился ~/.ssh/id_ed25519_vektor-cert.pub
```

`-s` — какой CA подписывает; `-I` — Key ID (человекочитаемый идентификатор, попадёт в логи аудита — пиши туда ФИО и дату); `-n` — принципалы (список логинов, под которыми можно зайти); `-V +8h` — срок жизни; `-z` — серийный номер (для KRL).

```bash
ssh-keygen -L -f ~/.ssh/id_ed25519_vektor-cert.pub
```

Вывод (структура):
```text
        Type: ssh-ed25519-cert-v01@openssh.com user certificate
        Public key: ED25519-CERT SHA256:AAA...
        Signing CA: ED25519 SHA256:BBB... (using ssh-ed25519)
        Key ID: "student-2026-04-01"
        Serial: 0
        Valid: from 2026-04-01T09:00:00 to 2026-04-01T17:00:00
        Principals:
                student
        Critical Options: (none)
        Extensions:
                permit-pty
```

На сервере (UBU01, WEB01, MON01) — один раз:

```bash
sudo install -m 644 ~/ssh-ca/ca_user.pub /etc/ssh/ca_user.pub   # scp/cat с клиента
echo 'TrustedUserCAKeys /etc/ssh/ca_user.pub' | \
  sudo tee /etc/ssh/sshd_config.d/98-vektor-ca.conf
sudo sshd -t && sudo systemctl reload ssh
```

После этого строку своего ключа из `authorized_keys` можно удалить — вход работает по сертификату. Проверка: `ssh -v web01` покажет `Offering public key: ... ED25519-CERT ...` и `Server accepts key`.

### 4.13. Host-сертификаты

```bash
# CA для хостов (на клиенте, отдельным ключом!)
ssh-keygen -t ed25519 -f ~/ssh-ca/ca_host -C "VEKTOR host CA" -a 100

# на WEB01: подписываем ЕГО host key, имена = по которым к нему ходят
sudo ssh-keygen -s ~/ssh-ca/ca_host -I web01 -h -n web01,10.10.20.10 -V +52w \
  /etc/ssh/ssh_host_ed25519_key.pub
echo 'HostCertificate /etc/ssh/ssh_host_ed25519_key-cert.pub' | \
  sudo tee -a /etc/ssh/sshd_config.d/98-vektor-ca.conf
sudo sshd -t && sudo systemctl reload ssh
```

`-h` — подписываем host key; `-n` — имена, под которыми хост легитимен (если ходишь по IP — IP обязан быть в списке, иначе снова получишь предупреждение). У клиента в `~/.ssh/known_hosts`:

```text
@cert-authority *.vektor.lab,10.10.20.* ssh-ed25519 AAAAC3Nza...== VEKTOR host CA
```

Теперь переустановка WEB01 не вызывает паники: новый host key подписан тем же CA — клиент молча принимает.

Утилита отзыва: `ssh-keygen -k -f ~/ssh-ca/revoked_keys` (+ `RevokedKeys /etc/ssh/revoked_keys` в sshd_config). Практичнее — короткий TTL.

## 5. Лабораторная работа

### Предусловия

- **UBU01** (10.10.10.30) — доступен по SSH, есть локальный пользователь `student` с sudo.

## 6. Ошибки новичков и безопасность

1. **Приватный ключ без пароля и один на всё.** → Утёк ноутбук — утёк доступ ко всей инфраструктуре, включая прод. → Парольная фраза + `ssh-agent` с `-t`, отдельные ключи под разные контуры (личный, CI, деплой).
2. **`authorized_keys` в Git, приватный ключ в репозитории, ключ в `~/.ssh` с правами 644.** → Ключ считается скомпрометированным мгновенно (сканеры GitHub находят такое за минуты); sshd ещё и молча проигнорирует такой `authorized_keys`. → `.gitignore` на `*.pem`, `id_*`, проверка `git secrets`/pre-commit, права 600 на ключи и 700 на `~/.ssh`.
3. **Отключил пароли, не проверив ключ.** → `Permission denied` и отсутствие доступа к серверу вообще; в облаке — пересоздание ВМ. → Держи вторую открытую сессию, проверяй `sshd -t`, а после `reload` — новый вход **до** закрытия старого; имей консоль (VMware/ILO) как резерв.
4. **`PermitRootLogin yes` + пароль.** → Прямой подбор рута с любого IP, ботнеты сканируют 22-й порт круглосуточно. → `prohibit-password` (или `no`), вход только обычным пользователем + `sudo`, `fail2ban`/nftables-лимиты.
5. **`StrictHostKeyChecking no` в конфиге «чтобы не спрашивало».** → Ты отключил защиту от MITM: любой прокси может подсунуть свой ключ и читать трафик. → Один раз принять ключ, дальше `@cert-authority` с host-сертификатами или нормальный `known_hosts`-менеджмент.
6. **`ssh -A` на все хосты подряд.** → Пока сессия жива, root промежуточной машины (или вредонос в чужом `~/.ssh/rc`) использует твой агент и заходит от твоего имени куда угодно. → Вместо агент-форвардинга — `ProxyJump`; если очень надо — `ssh-add -c` (спрашивать подтверждение на каждое использование).
7. **`-L 0.0.0.0:5432:...` или `GatewayPorts yes`.** → База в закрытом сегменте становится доступна всем, кто видит твою машину. → Всегда явный `127.0.0.1` в bind, `GatewayPorts no`, `PermitOpen` в sshd для ограничения целей.
8. **SSH CA с бессрочными сертификатами и без учёта.** → Ты просто заменил одну свалку ключей на другую, только теперь отзыв невозможен. → TTL от 15 минут до 8 часов, `-I` с ФИО и датой, KRL или `AuthorizedPrincipalsFile` для точечного отзыва, CA-ключ — в Vault/HSM, а не в `~/ssh-ca` на ноутбуке.

**Безопасность отдельно.** В лабораторной ты сознательно кладёшь CA-ключ в домашний каталог на клиенте и оставляешь `TrustedUserCAKeys` доступным на запись владельцу-руту — для стенда нормально, в бою нет: приватный ключ CA = право выписать себе доступ к любому серверу, его место — офлайн-носитель, HSM или Vault, а не рабочая машина с браузером и мессенджерами. Точно так же `AllowUsers student@10.10.10.0/24` — учебное упрощение: в реальной среде нужна привязка к группам AD/LDAP, 2FA (`AuthenticationMethods publickey,keyboard-interactive`) и централизованный аудит всех входов (журнал sshd → SIEM), потому что «кто и когда заходил на 200 серверов» руками по `journalctl` не отвечается.

## 7. Вопросы на собеседовании

**1. Чем ProxyJump отличается от ProxyCommand и что быстрее?**

Ответ: `ProxyJump` (`-J`) — встроенный механизм OpenSSH: клиент подключается к bastion и просит открыть канал `direct-tcpip` до целевого хоста внутри уже установленного SSH-соединения. Один TCP, один набор ключей, работает с multiplexing (`ControlMaster`), чистая семантика в `~/.ssh/config`. `ProxyCommand` — запуск произвольного процесса и проброс его stdio; исторически писали `ssh -o ProxyCommand='ssh -W %h:%p bastion'`, это два отдельных TCP-соединения, больше накладных расходов и больше точек отказа. `ProxyCommand` остаётся нужен для нестандартных случаев: `nc`, `cloudflared`, `aws ssm start-session`.

*Что хочет услышать интервьюер:* что ты понимаешь разницу между «пробросом канала внутри SSH» и «запуском процесса», и что `-J` — дефолтный выбор.

*Красный флаг:* «Это одно и то же, просто разные флаги».

**2. Зачем нужен SSH CA, если есть authorized_keys?**

Ответ: `authorized_keys` не масштабируется: выдача доступа = правка файла на каждом сервере, отзыв = обход всех серверов, аудит = разбор файлов вручную. С CA сервер доверяет одному публичному ключу (`TrustedUserCAKeys`), а доступ выдаётся подписью сертификата: принципалы (под какими логинами можно зайти), TTL (например, 8 часов), Key ID для аудита, ограничения через critical options (`force-command`, `source-address`, `no-port-forwarding`). Отзыв — либо истечение TTL, либо KRL/`AuthorizedPrincipalsFile`. То же самое для хостов: host-сертификаты + `@cert-authority` в `known_hosts` убирают TOFU и «REMOTE HOST IDENTIFICATION HAS CHANGED» при пересоздании ВМ. Реализуется через Vault, step-ca, Teleport или облачные сервисы.

*Что хочет услышать интервьюер:* масштабирование, короткоживущие креды, аудируемость, отзыв; понимание, что CA-ключ — критичный секрет.

*Красный флаг:* «CA — это просто удобнее, безопасность та же» (без упоминания TTL, отзыва и защиты CA-ключа).

**3. Объясни разницу между `-L`, `-R` и `-D`. Приведи по одному рабочему кейсу.**

Ответ: `-L` слушает на клиенте и форвардит через сервер: «достучаться из своей машины до БД/вебморды в закрытом сегменте» (`ssh -L 127.0.0.1:8080:127.0.0.1:80 web01`). `-R` слушает на удалённой стороне и форвардит к клиенту: «дать доступ к машине за NAT / показать коллеге локально поднятый сервис» (`ssh -R 127.0.0.1:9000:127.0.0.1:22 ubu01`). `-D` поднимает SOCKS5-прокси на клиенте: «браузер/`curl` внутрь сегмента, адреса выбираются динамически» (`ssh -N -D 127.0.0.1:1080 web01` + `curl --socks5-hostname`). Везде помнить про bind на 127.0.0.1 и `GatewayPorts`/`PermitOpen` на сервере.

*Что хочет услышать интервьюер:* чёткое «где слушает» + практический кейс + осознание риска «открыл наружу».

*Красный флаг:* путаница в направлении форварда и «-D это то же, что -L, только для HTTP».

**4. Как захарднить sshd и не потерять доступ самому?**

Ответ: `PermitRootLogin prohibit-password`, `PasswordAuthentication no`, `PubkeyAuthentication yes`, `KbdInteractiveAuthentication no`, `AllowUsers`/`AllowGroups`, `MaxAuthTries 3`, `LoginGraceTime` 30, `X11Forwarding no`, `AllowAgentForwarding no`, `ClientAliveInterval`/`ClientAliveCountMax`, `fail2ban` или nftables-лимит на 22-й порт, регулярные обновления OpenSSH. Порядок безопасного применения: снапшот/бэкап конфига → отдельный файл в `sshd_config.d/` → `sshd -t` → `systemctl reload ssh` → **проверка нового входа во второй сессии, не закрывая первую** → и только потом закрытие. Резерв — консоль гипервизора/облака.

*Что хочет услышать интервьюер:* понимание, что порядок действий важнее списка директив, и что «проверил на живой сессии» — обязательный шаг.

*Красный флаг:* «Перезапустил sshd, всё отвалилось, переустановил сервер».

**5. Чем опасен agent forwarding и что использовать вместо него?**

Ответ: при `ssh -A` на удалённом хосте появляется unix-сокет агента; пока сессия жива, любой, кто имеет доступ к этому сокету (в первую очередь root удалённого хоста, а также вредоносный код в чужом `~/.ssh/rc` или через `ForwardAgent` на shared-хосте), может использовать твой агент и логиниться от твоего имени на машины, куда у тебя есть доступ. Ключ не крадут — крадут возможность им подписывать. Альтернативы: `ProxyJump` (не нужен агент на промежуточной машине вовсе), отдельные короткоживущие ключи/сертификаты на каждый хост, `ssh-add -c` (подтверждение на каждое использование), `IdentityAgent` с ограничением. В инфраструктуре с CA агент почти не нужен: сертификат на 1–8 часов выдаётся под задачу.

*Что хочет услышать интервьюер:* что ты понимаешь механизм (сокет, права) и что у тебя есть архитектурная замена, а не только «не используй -A».

*Красный флаг:* «Агент форвардит только публичный ключ, это безопасно».

- **man.openbsd.org** — онлайн-версии тех же man-страниц (актуальные для OpenBSD-ветки OpenSSH). Поиск: `man.openbsd.org ssh-keygen`.
- **ubuntu.com** — *Ubuntu Server documentation*, раздел про OpenSSH server и hardening. Поиск: `ubuntu server openssh documentation`.
- **learn.microsoft.com** — *OpenSSH for Windows* (полезно, если часть парка на Windows; помни, что multiplexing там не поддерживается — `[ПРОВЕРИТЬ]` для конкретной версии). Поиск: `microsoft openssh for windows`.
- **developer.hashicorp.com** — *Vault → SSH secrets engine* (выдача подписанных сертификатов и OTP). Поиск: `vault ssh secrets engine signed certificates`.
- **smallstep.com/docs** — *step-ca*, SSH certificate authority (альтернатива Vault для небольшой инфраструктуры). Поиск: `step-ca ssh certificate`.
- **kubernetes.io** — если дальше будешь связывать SSH с кластером: раздел про доступ к узлам и `kubectl debug`/`node-shell`. Поиск: `kubernetes node access debugging`.

Конкретные номера версий OpenSSH, дефолты в `sshd_config` на Ubuntu 24.04 и Debian 12 перед лабой сверяй через `man sshd_config` и `sshd -T` на своей машине — они меняются от релиза к релизу.
