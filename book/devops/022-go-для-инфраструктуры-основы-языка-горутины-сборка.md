## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Что такое Go.** Компилируемый статически типизированный язык с garbage collector'ом. Исходники компилируются в машинный код заранее, а не исполняются интерпретатором. Единица сборки — **пакет** (`package`), программа начинается с `package main` и функции `main()`. Внешние зависимости описываются в `go.mod` (модуль + версии), их контрольные суммы — в `go.sum`. Это аналог `pyproject.toml` + lock-файла из урока 21.

**Горутины и планировщик.** Горутина — это не поток ОС. Это лёгкая задача, которую рантайм Go сам раскладывает по потокам. Схема планировщика называется **GMP**:

```text
G — goroutine       лёгкая задача (стартовый стек ~2 КБ, растёт по необходимости)
M — machine         реальный поток ОС (их создаёт рантайм, обычно <= число ядер + запас)
P — processor       контекст выполнения, «право работать»; их ровно GOMAXPROCS (по умолчанию = числу ядер)

  очередь G   очередь G   очередь G
      │           │           │
      ▼           ▼           ▼
    [P0]        [P1]        [P2]     ← локальные очереди
      │           │           │
      ▼           ▼           ▼
    [M0]        [M1]        [M2]     ← потоки ОС
      └───────────┴───────────┘
        одна разделяемая память процесса
```

Из схемы следуют две вещи. Первая: горутина дёшева — переключение происходит в пространстве пользователя, без syscall, поэтому их могут быть десятки тысяч. Вторая: все горутины живут в **одной общей памяти**, и если две горутины пишут в одну переменную без синхронизации — это **гонка данных (data race)**, и результат непредсказуем. Инструменты синхронизации: `sync.Mutex`, `sync.RWMutex`, `sync/atomic`, `sync.WaitGroup`, и каналы (`chan T`) — типизированные очереди, через которые горутины передают данные вместо того, чтобы лезть в общую переменную.

**Отмена работы.** `context.Context` — стандартный способ сказать «эта работа больше не нужна»: таймаут, отмена по сигналу, закрытие соединения. Тот, кто запустил горутину, обязан иметь способ её остановить, иначе она утечёт.

**Сборка.** `go build` вызывает компилятор и линковщик. Ключевые свойства:

- `CGO_ENABLED=0` — отключает вызовы C-кода. Без этого бинарник линкуется динамически с системной `libc` и не запустится в пустом контейнере (`scratch`, `distroless`).
- `-trimpath` — убирает абсолютные пути сборочной машины из бинарника (воспроизводимость, меньше утечек информации).
- `-ldflags "-s -w"` — выкидывает отладочную информацию (бинарник меньше; для отладки `delve` не используй `-s -w`).
- `-ldflags "-X main.version=..."` — подставляет строковую переменную во время сборки.
- `GOOS` / `GOARCH` — кросс-компиляция. Важно: **на ноутбуке под Windows/macOS `go build` по умолчанию соберёт бинарник под ноутбук**, а не под Linux-сервер.

**Exporter и Prometheus.** Prometheus работает по **pull-модели**: он сам периодически ходит по HTTP на `/metrics` каждого таргета (по умолчанию раз в 60 с, в лабе — 15 с) и забирает текстовый формат exposition. Exporter — это HTTP-сервис, который переводит «родной» API (склад, база, 1С) в метрики. Четыре типа метрик: `counter` (только растёт), `gauge` (туда-сюда), `histogram` и `summary` (распределения). Отдельная встроенная метрика `up` (1/0) показывает, удалось ли вообще соскрейпить таргет.

```text
        UBU01 10.10.10.30                      MON01 10.10.10.40
 ┌───────────────────────────────┐      ┌────────────────────────────────┐
 │ vektor-exporter (:9101)       │      │ prometheus (:9090)             │
 │                               │      │                                │
 │  poller-горутина (раз в 1 с)  │      │ scrape_configs:                │
 │        │ Set(gauge)           │◀─────│  - job_name: vektor-exporter   │
 │        ▼                      │ HTTP │    targets: ['10.10.10.30:9101']
 │  registry ──► /metrics (text) │ pull │    scrape_interval: 15s        │
 └───────────────────────────────┘      └──────────────┬─────────────────┘
                                                       │ PromQL
                                                       ▼
                                            дашборд + алерты
```

**Оператор.** Оператор = **CRD** (свой тип объекта в API Kubernetes, например `Queue`) + **контроллер**, который в цикле `Reconcile` сравнивает «что просят» (`spec`) с «что есть на самом деле» и приводит второе к первому. Цикл **level-triggered** и **идемпотентный**: он не «выполняет команду один раз», а бесконечно сверяет состояние, поэтому переживает падения, перезапуски и ручные правки. Отличие от Helm: Helm отрендерил манифесты и ушёл; оператор продолжает следить.

## 3. Аналогия из жизни

Представь кухню ресторана «Вектор».

**Бинарник** — это кухня «под ключ»: ты привёз один ящик, открыл — и всё работает. Не надо на месте искать плиту (интерпретатор), сковородки (библиотеки) и рецепты по всему городу. Поэтому Go-сервис так удобно класть в контейнер: внутри пусто, кроме одного файла.

**Горутины** — повара. Их может быть тысяча, а плит всего четыре (ядра). Диспетчер (планировщик Go) переключает поваров так, чтобы плиты не простаивали. Переключение повара — это «отложил нож, взял следующий заказ», а не «уволил и нанял нового» (поток ОС). Дёшево.

**Каналы** — лоток раздачи: один повар кладёт, другой берёт, и им не нужно хватать один котёл руками. Если же они всё-таки полезут в общий котёл одновременно — это гонка данных, суп испорчен, и никто не заметит, пока не попробует гость.

**`context`** — сигнал «стоп-кухня». Закрыли смену — все бросают задачи и уходят, а не доваривают суп до утра. Забыл передать сигнал — повар остался один в тёмном цехе и варит в пустоту: это утечка горутины.

**Exporter** — повар-обходчик с термометром: раз в 15 секунд обходит цех и пишет мелом на доске «температура, глубина очереди». **Prometheus** — менеджер, который сам приходит и списывает показания с доски. Не обходчик звонит менеджеру, а менеджер приходит (pull).

**Оператор** — старший смены с планом: «к отгрузке должно работать три кассы». Он не «один раз открыл кассы», а ходит по залу, сравнивает факт с планом и открывает/закрывает, пока не совпадёт.

Аналогия ломается в одном месте: повара физически не могут одновременно держать один нож, а горутины делят память процесса и при этом **не получают никаких предупреждений** от планировщика — зато гонку ловит `go test -race`.

### 13. Оператор: ядро — функция Reconcile (учебный фрагмент)

```go
func (r *QueueReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
	var q vekv1.Queue
	if err := r.Get(ctx, req.NamespacedName, &q); err != nil {
		return ctrl.Result{}, client.IgnoreNotFound(err) // объект удалили — это не ошибка
	}

	want := q.Spec.Workers // desired

	var dep appsv1.Deployment
	if err := r.Get(ctx, types.NamespacedName{Name: q.Name + "-workers", Namespace: q.Namespace}, &dep); err != nil {
		return ctrl.Result{}, client.IgnoreNotFound(err)
	}
	have := *dep.Spec.Replicas // actual

	if have != want {
		dep.Spec.Replicas = &want
		if err := r.Update(ctx, &dep); err != nil {
			return ctrl.Result{}, err
		}
	}
	return ctrl.Result{RequeueAfter: 30 * time.Second}, nil // периодически перепроверяемся
}
```

Это скелет: в рабочем коде добавляются статус (`q.Status`), `finalizer`, обработка `IsNotFound` для Deployment (создать, а не молча выйти), лимиты. Собирается через `kubebuilder` или `operator-sdk` — оба генерируют CRD, RBAC и менеджер контроллера.

   	defer stop()

   	go poll(ctx, time.Second) // фоновая горутина, живёт до отмены ctx

   	mux.Handle("/metrics", promhttp.Handler())
   	mux.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
   		w.WriteHeader(http.StatusOK)
   		_, _ = w.Write([]byte("ok\n"))
   	})

   	srv := &http.Server{Addr: ":9101", Handler: mux}
   	go func() {
   		log.Printf("exporter слушает :9101, версия %s", version)
   		if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
   			log.Fatalf("http: %v", err)
   		}
   	}()

   	<-ctx.Done()
   	log.Println("получен сигнал, останавливаемся")
   	shCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
   	defer cancel()
   	_ = srv.Shutdown(shCtx)
   }

   func poll(ctx context.Context, every time.Duration) {
   	t := time.NewTicker(every)
   	defer t.Stop()
   	for {
   		select {
   		case <-ctx.Done():
   			return // без этого горутина утекла бы
   		case <-t.C:
   			n, err := fetchQueueDepth(ctx)
   			if err != nil {
   				pollErrors.Inc()
   				continue
   			}
   			queueDepth.Set(n)
   			lastPoll.SetToCurrentTime()
   		}
   	}
   }

   func fetchQueueDepth(ctx context.Context) (float64, error) {
   	// здесь был бы HTTP-запрос к API склада; пока имитация
   	if err := ctx.Err(); err != nil {
   		return 0, err
   	}
   	time.Sleep(50 * time.Millisecond)
   	return float64(rand.Intn(100)), nil
   }

## 6. Ошибки новичков и безопасность

1. **Забыть `select { case <-ctx.Done() }` в цикле.** → горутина живёт после остановки сервиса, память и соединения текут, при частых рестартах сервис падает по OOM. → Всегда прокидывай `ctx` и предусматривай выход.
2. **Общий счётчик без синхронизации.** → гонка данных, «невозможные» значения метрик, случайные паники. → `sync/atomic` для счётчиков, `sync.Mutex` для структур, прогон `go test -race` в CI.
3. **`CGO_ENABLED` не выставлен.** → бинарник линкуется динамически, в `scratch`/`distroless` и на минимальном хосте падает с `no such file or directory`. → `CGO_ENABLED=0` в Makefile/CI, проверка `ldd`.
4. **Сборка на ноутбуке и копирование на сервер.** → `Exec format error` (наша поломка). → Собирать в CI на linux/amd64 runner'е или явно задавать `GOOS`/`GOARCH`, а в пайплайн добавить `file`-проверку.
5. **Тяжёлый сбор метрик прямо в HTTP-обработчике `/metrics`.** → скрейп дольше `scrape_timeout` (по умолчанию 10 с), таргет `up=0`, дашборды пустеют, Prometheus притормаживает. → Тяжёлые опросы выносить в фоновую горутину, в обработчике отдавать уже посчитанные значения из registry.
6. **Метки с высокой кардинальностью** (`user_id`, `request_id`, IP, e-mail). → миллионы временных рядов, Prometheus съедает RAM и падает. → В лейблы только ограниченные множества (env, service, status_code), детали — в логи.
7. **`go get` без фиксации версии и без `go.sum` в репозитории.** → сборка невоспроизводима, в проект может приехать скомпрометированный модуль. → Коммитить `go.mod` и `go.sum`, прогонять `govulncheck`, в закрытом контуре — свой `GOPROXY`/`go mod vendor`.
8. **Игнорировать лимиты CPU в контейнере.** → `GOMAXPROCS` берётся из числа ядер хоста, а не из лимита, планировщик создаёт лишние потоки, сервис троттлится `[ПРОВЕРИТЬ под свою версию Go — поведение менялось]`. → Выставлять `GOMAXPROCS`/`automaxprocs` осознанно.

**Безопасность.** Не оставляй `/metrics` на `0.0.0.0` без ограничений: там видно внутренние имена сервисов, размеры очередей, иногда — версии и ошибки бэкенда. В проде — доступ только из сети мониторинга (network policy/фаервол), на публичных стендах — reverse-proxy с аутентификацией. Никогда не клади в лейблы пароли, токены и персональные данные: метрики обычно хранятся месяцами и доступны широкому кругу. Сервис запускай не от root (порт > 1024, привилегии не нужны). Оператору в Kubernetes не давай `cluster-admin`: только те verbs и ресурсы, которые реально нужны, иначе скомпрометированный контроллер снесёт кластер целиком.

## 7. Вопросы на собеседовании

**1. Чем горутина отличается от потока ОС?**
Горутина — задача рантайма Go со стартовым стеком порядка 2 КБ, который растёт по необходимости; переключение происходит в пространстве пользователя без syscall, поэтому горутин могут быть десятки тысяч. Поток ОС — единица планирования ядра, дорогая по созданию и переключению. Рантайм раскладывает горутины по потокам через планировщик GMP: G — горутина, M — поток ОС, P — контекст выполнения, их `GOMAXPROCS` (по умолчанию число ядер). Горутины делят общую память, значит нужна синхронизация; сами по себе они не ускоряют одну задачу, а позволяют не блокироваться на I/O.
*Что хочет услышать интервьюер:* понимание M:N, `GOMAXPROCS`, дешевизны и того, что параллелизм ограничен ядрами.
*Красный флаг:* «горутина — это лёгкий поток, просто так называется», без упоминания общей памяти и планировщика.

**2. Как собрать по-настоящему статический бинарник и зачем это DevOps-инженеру?**
`CGO_ENABLED=0 go build -trimpath -ldflags="-s -w"`; проверить `file` и `ldd` — должно быть `statically linked` / `not a dynamic executable`. Это даёт один файл, который запускается в `scratch` или `distroless` без пакетов и `libc`, уменьшает размер образа, поверхность атаки и убирает проблему несовместимых версий glibc. Дальше — кросс-компиляция матрицей `GOOS`/`GOARCH` и multi-stage `Dockerfile`: сборка в `golang`, копирование бинарника в пустой базовый образ. `-trimpath` убирает пути сборочной машины, `-X` подставляет версию, которую видно в метрике `build_info`.
*Что хочет услышать интервьюер:* связку «статический бинарник → маленький безопасный контейнер» и знание подводных камней CGO.
*Красный флаг:* «просто `go build`, Go же всегда статический» — без CGO это не гарантировано.

**3. Что такое exporter и как он работает с Prometheus?**
Exporter — HTTP-сервис, который опрашивает «родную» систему и отдаёт метрики на `/metrics` в текстовом формате exposition. Prometheus работает по pull-модели: сам ходит на таргеты по расписанию `scrape_interval`, сохраняет сэмплы с меткой времени и считает `up`. Типы метрик: counter (только растёт, суффикс `_total`), gauge (произвольное значение), histogram и summary (распределения). Имена — в базовых единицах (секунды, байты), лейблы — с ограниченной кардинальностью. Для batch-джоб, которые живут меньше интервала скрейпа, есть Pushgateway — исключение из pull-модели.
*Что хочет услышать интерфейс:* что pull — осознанный выбор (Prometheus сам знает, какие таргеты живы), и что exporter — тонкий переводчик, а не место для бизнес-логики.
*Красный флаг:* «exporter пушит метрики в Prometheus» или путаница counter/gauge.

**4. Что такое оператор Kubernetes и чем он отличается от Helm-чарта?**
Оператор — это CRD (свой тип объекта в API) плюс контроллер, который в цикле `Reconcile` приводит фактическое состояние к желаемому. Цикл level-triggered и идемпотентный: он не «выполняет команду один раз», а постоянно сверяет `spec` и реальность, поэтому восстанавливается после сбоев и ручных правок. Внутри — informers/watch, workqueue, при нескольких репликах — leader election, отдельный статус-сабресурс, finalizer'ы для очистки внешних ресурсов, RBAC по минимуму. Helm лишь рендерит манифесты и уходит; он не умеет реагировать на дрейф и управлять внешними системами. Оператор нужен, когда есть сложный жизненный цикл (базы данных, кластеры, бэкапы), а не «на всякий случай».
*Что хочет услышать интервьюер:* понимание reconcile-паттерна и трезвость про стоимость оператора.
*Красный флаг:* «оператор = чарт с хуками» или «оператор нужен для любого приложения».

**5. Как ловить утечки горутин и гонки данных?**
Утечка — это горутина, которая заблокирована на канале, без `ctx` или забыла `cancel()`. Профилактика: прокидывать `context` везде, где есть I/O, `defer cancel()`, `sync.WaitGroup` или `errgroup` для ожидания, таймауты на HTTP-клиентах, ограничение параллелизма через семафор или пул воркеров. Диагностика: `go test -race` и `go run -race` для гонок; `net/http/pprof` и `go tool pprof` — смотреть `goroutine` профиль, искать растущее число горутин с одинаковым стеком. Гонки ловятся только там, где реально исполнился конфликтующий код, поэтому `-race` гоняют в CI на тестах, а не «один раз локально».
*Что хочет услышать интервьюер:* связку «context + WaitGroup + pprof + race detector» и понимание, что `-race` не доказывает отсутствие гонок.
*Красный флаг:* «поставить `time.Sleep` и посмотреть» или «в Go гонок не бывает».
