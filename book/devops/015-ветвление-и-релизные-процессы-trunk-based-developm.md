## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Что физически такое ветка.** Ветка в Git — это не папка и не копия файлов. Это файл в `.git/refs/heads/<имя>`, внутри которого лежит SHA-1 (или SHA-256) одного коммита. `HEAD` — указатель на текущую ветку или напрямую на коммит (detached HEAD). Тег — файл в `.git/refs/tags/`. Всё остальное — граф коммитов (DAG), где каждый коммит ссылается на родителей. Поэтому «создать ветку» = записать одну строку, а «переключиться» = переписать HEAD и разложить файлы из дерева коммита.

**Способы соединения истории:**
- *fast-forward (ff)* — целевая ветка просто переставляется на новый коммит, нового коммита не появляется. История линейная.
- *three-way merge* — создаётся merge-коммит с двумя родителями. Видно, где была ветка.
- *rebase* — коммиты ветки «переигрываются» поверх новой базы, получаются новые SHA. История линейная, но исходные коммиты исчезают из видимости (спасает `reflog` — урок 14).
- *squash* — все коммиты ветки сжимаются в один.

**Три модели ветвления.** Это соглашения, а не функция Git; Git их не проверяет.

```text
Trunk-Based Development (TBD)
main  ──●──●──●──●──●──●──●──●──●──●──►   всегда зелёный, всегда готов к деплою
        \    /   \        /
         ●──●     ●──●──●                 ветки живут часы, не дни

GitHub Flow
main  ──●──────────●──────────●────────►  один долгоживущий ствол
         \        /  \        /
       feature   PR   feature  PR          ветка → PR → ревью → merge → deploy

GitFlow
main    ──●───────────────●─────────●───►  только релизы (теги) и hotfix
           \             / \       /
release     ●──●──●──●──●    ●──●──●       стабилизация, только фиксы
           /             \  /
develop ──●──●──●──●──●──●──●──●──●──●──►  интеграционная ветка
             \  /           \  /
            feature        feature
```

**Trunk-Based Development.** Одна долгоживущая ветка (`main`/`trunk`). Изменения вливаются минимум раз в день, ветки живут часы. Незаконченная функциональность прячется за фича-флагом (переменная окружения или конфиг, а не ветка). Требует зрелого CI: каждый коммит в транк должен собираться и проходить тесты. Ветки `release/*` в TBD допустимы только для сопровождения старых версий — фиксы идут в транк и оттуда черри-пикаются.

**GitHub Flow.** Тоже один ствол, но обязателен pull request: ветка → пуш → PR → ревью → merge → деплой. Хорошо ложится на веб-сервисы с непрерывным деплоем.

**GitFlow.** Пять типов веток: `main` (только релизы), `develop` (интеграция), `feature/*`, `release/*`, `hotfix/*`. Плюс — можно параллельно поддерживать несколько версий; минус — тяжёлый, медленный, история замусорена merge-коммитами. Классика для коробочного ПО и проектов с релизами раз в квартал; для SaaS чаще избыточен.

**Семантическое версионирование (SemVer 2.0.0).** Формат `MAJOR.MINOR.PATCH`:
- MAJOR — несовместимое изменение публичного API;
- MINOR — новая функциональность без поломок;
- PATCH — исправление без новой функциональности;
- `0.y.z` — начальная разработка, публичного API ещё нет, разрешено ломать что угодно;
- предрелиз: `1.4.0-rc.1`, `1.4.0-beta.2` (считается *меньше* `1.4.0`);
- метаданные сборки: `1.4.0+20260412` — на сравнение версий не влияют;
- `1.10.0` **больше** `1.9.0` — сравниваются числа, а не строки.

**Где это в модели OSI.** Git по SSH — TCP/22, по HTTPS — TCP/443, то есть прикладной уровень L7. Отсюда и типовые проблемы: закрытый 22 на файрволе, просроченный сертификат или корпоративный прокси, режущий TLS — это урок 9 и 11. Сам GitLab на GIT01 (10.10.10.50) отдаёт и 443, и 22 для git-over-ssh; развернём его в уроке 17.

**Связка «тег → артефакт → прод».** CI запускается по событию (`push`, `tag`), собирает образ и публикует его в Harbor (HARBOR01, 10.10.10.55) с тем же номером, что в теге. Номер версии — единственный ключ, по которому дежурный понимает, что крутится в кластере. Поэтому тег — это контракт, а не заметка.

## 3. Аналогия из жизни

Представь редакцию журнала. `trunk` — это основной текст номера, над которым ежедневно работает вся редакция: каждый журналист приносит свою правку, её сразу вклеивают в макет, и макет в любой момент готов уйти в типографию. `feature/*` — черновик статьи, который живёт день-два и вклеивается в макет; если статья не готова, её место занимает «заглушка» — это и есть фича-флаг. `release/1.1` — номер, который уже сверстан и проходит корректуру: там правят только опечатки, новых статей не добавляют. `hotfix` — срочная вклейка «Извините, допущена опечатка» в уже напечатанный тираж. `MAJOR.MINOR.PATCH` — номер выпуска на обложке: сменился год подписки (MAJOR) — новая нумерация; появилась новая рубрика (MINOR) — выпуск вперёд; исправлены опечатки (PATCH) — тоже вперёд, но без анонсов.

Ломается аналогия на откате: тираж не отзовёшь, а деплой откатить можно — но номер выпуска, как и тег, уже «напечатан», и второй раз печатать под ним другой текст нельзя.

## 4. Практика и команды

Все примеры — на UBU01 (10.10.10.30), пользователь `$USER`.

**1. Базовая настройка, чтобы модели не «разъезжались».**

```bash
git config --global init.defaultBranch main
git config --global pull.ff only
git config --global fetch.prune true
git config --global user.name  "$USER"
git config --global user.email "$USER@corp.vektor.lab"
```

`init.defaultBranch main` избавляет от `master` в новых репозиториях; `pull.ff only` не даёт `git pull` молча создать merge-коммит (типичная причина «мусорной» истории); `fetch.prune true` удаляет локально ветки, снятые с сервера. Проверить: `git config --global --list`.

**2. Короткоживущая ветка.**

```bash
git switch -c feature/health-endpoint
# ...правки...
git add health.txt && git commit -m "feat: эндпоинт /health"
```

`switch -c` = создать и сразу переключиться (`checkout -b` — старый эквивалент). Имя ветки — `<тип>/<короткое-имя>`, тип по Conventional Commits (подробно в уроке 16).

**3. Список веток и upstream.**

```bash
git branch -vv
git branch -a --sort=-committerdate
```

Вывод:
```text
* main                 3f2a1c9 [origin/main] chore: релиз 1.1.0
  feature/report-export 8b1d0e2 [origin/feature/report-export: впереди 2]
```
Смотрим: с какой удалённой веткой связана локальная и насколько разошлись. `[gone]` в квадратных скобках означает, что ветку на сервере удалили — её пора снести и локально.

**4. Карта истории.**

```bash
git log --graph --oneline --decorate --all -20
```

```text
* 3f2a1c9 (HEAD -> main, tag: v1.1.1, origin/main) fix: деление на ноль
*   9c4b771 Merge branch 'release/1.1'
|\
| * 55aa012 (release/1.1) chore(release): 1.1.0
|/
* 1d0f3ab feat: экспорт отчёта
```
Это первая команда при разборе любого «релиз не тот». Видно, где стоит тег и какие ветки на каких коммитах.

**5. Перебазирование перед вливанием.**

```bash
git switch feature/health-endpoint
git rebase main
```

Переписывает коммиты ветки поверх актуального `main` — история остаётся линейной, ff-merge становится возможным. Конфликты решаются по одному коммиту (`git rebase --continue`), прервать — `git rebase --abort`. Интерактивный вариант (`-i`, squash, fixup) — урок 14. Правило: ребейзить можно только свою, ещё не опубликованную ветку.

**6. Вливание: ff против merge-коммита.**

```bash
git switch main
git merge --ff-only feature/health-endpoint   # TBD / GitHub Flow
git merge --no-ff release/1.1.0               # GitFlow: точка релиза видна в графе
```

`--ff-only` откажется вливать, если история разошлась, — заставит сначала сделать rebase. `--no-ff` всегда создаёт merge-коммит: в GitFlow это нужно, чтобы по графу было видно, где именно собирался релиз.

**7. Теги по SemVer.**

```bash
git tag -a v1.1.0 -m "релиз 1.1.0: экспорт отчётов"
git tag -l 'v*' --sort=-v:refname
git show v1.1.0 --stat
```

`-a` создаёт аннотированный тег (объект с автором, датой и сообщением) — именно такие нужны для релизов; `-l` — фильтр по шаблону, `--sort=-v:refname` сортирует по версии (а не по алфавиту), иначе `v1.10.0` окажется выше `v1.9.0`. Легковесный тег (`git tag v1.1.0` без `-a`) — просто указатель, для релизов не годится.

**8. Где мы относительно релиза.**

```bash
git describe --tags --long --dirty
```

```text
v1.1.0-3-g8b1d0e2
```
Читается: 3 коммита после тега `v1.1.0`, текущий коммит `8b1d0e2`. Суффикс `-dirty` — есть незакоммиченные правки. Этой строкой удобно подписывать сборку.

**9. Публикация и уборка.**

```bash
git push -u origin feature/health-endpoint
git push origin --follow-tags
git push origin --delete feature/health-endpoint
git branch -d feature/health-endpoint
```

`--follow-tags` пушит коммиты и все *аннотированные* теги, достижимые из них (удобнее, чем `--tags`, который тащит вообще всё). `--delete` убирает ветку на сервере; локальную `-d` удалит только если она влита — иначе `-D`.

**10. Pull request без GitLab — `request-pull`.**

```bash
git request-pull main origin feature/report-export
```

```text
The following changes since commit 3f2a1c9...:
  chore: релиз 1.1.0
are available in the Git repository at:
  /srv/git/vektor-web.git feature/report-export
for you to fetch changes up to 1d0f3ab...:
  feat: экспорт отчёта
```
Формирует текст для ревьюера: диапазон коммитов и diffstat. Ревьюер делает `git fetch && git diff main..origin/feature/report-export`. Полноценные MR появятся в уроке 17 на GIT01.

**11. Вошёл ли фикс в релиз.**

```bash
git merge-base --is-ancestor 8b1d0e2 v1.1.1 && echo "вошёл" || echo "НЕ вошёл"
git tag --contains 8b1d0e2
git branch --contains 8b1d0e2
```

`merge-base --is-ancestor` возвращает 0/1 и ничего не печатает — это главный инструмент проверки «есть ли коммит в этой ветке». `--contains` показывает, в каких тегах и ветках коммит присутствует.

**12. Release notes из истории.**

```bash
git shortlog -sn --no-merges v1.0.1..v1.1.0
git log --oneline --no-merges v1.0.1..v1.1.0
```

Первый — авторы и число коммитов между релизами, второй — сами изменения. Так собирается CHANGELOG; с Conventional Commits его можно генерировать автоматически (урок 16).

**13. Защита ствола серверным хуком.**

```bash
cat > /srv/git/vektor-web.git/hooks/update <<'EOF'
#!/usr/bin/env bash
# update <refname> <oldrev> <newrev>
set -euo pipefail
ref="$1"; old="$2"; new="$3"

case "$ref" in
  refs/heads/main|refs/heads/develop)
    if [ "$old" != "0000000000000000000000000000000000000000" ] \
       && ! git merge-base --is-ancestor "$old" "$new"; then
      echo "push отклонён: переписывать историю $ref запрещено" >&2
      exit 1
    fi ;;
esac

case "$ref" in
  refs/tags/*)
    t="${ref#refs/tags/}"
    if ! printf '%s' "$t" | grep -Eq '^v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)(-[0-9A-Za-z.-]+)?$'; then
      echo "тег '$t' не SemVer (ожидается vX.Y.Z[-pre])" >&2; exit 1
    fi ;;
esac
exit 0
EOF
chmod +x /srv/git/vektor-web.git/hooks/update
```

Хук `update` срабатывает на каждый ref и отклоняет push ненулевым кодом. Здесь два правила: запрет не-fast-forward в `main`/`develop` (защита от `--force`) и проверка формата тега. Это кустарная замена protected branches в GitLab/Gitea — там то же самое настраивается галочками (уроки 17–18).

> **Что написал:** «Выпустили v1.1.0, я срочно пофиксил баг, влил в `main`, поставил тег `v1.1.1`. А на стенде версия всё ещё 1.1.0, и `git describe` показывает `v1.1.1-2-g...`. Разбирайтесь.»
> **Срочность:** высокая

**Воспроизведение.** В `web-dev1`: `git switch -c release/1.1 v1.0.0`, поправить `VERSION` на `1.1.0`, коммит, `git merge --no-ff release/1.1` в `main`, `git tag -a v1.1.0`. Затем «забыть» сделать merge обратно — и совершить hotfix не в релизной ветке, а прямо в `main`: `git switch main`, правка, коммит `fix: срочный фикс`, `git tag -a v1.1.1` **на этом же коммите** `main`, `git push origin main --follow-tags`. Теперь прод собирается из `release/1.1`, а фикс лежит в `main`.

**Диагностика по шагам.**
1. `git log --graph --oneline --decorate --all -20` — видно, что `release/1.1` и `main` разошлись, тег `v1.1.1` стоит на коммите вне релизной ветки.
2. `git tag -n` и `git show v1.1.1 --stat` — что вообще в этом теге.
3. `git tag --contains <SHA фикса>` — пусто или только `v1.1.1`, значит в `v1.1.0` фикса нет.
4. `git merge-base --is-ancestor <SHA фикса> release/1.1; echo $?` — `1`, фикс не в релизной ветке. Причина найдена.
5. `git describe --tags release/1.1` — подтверждает, что собирается `v1.1.0`.
6. Проверить, уехал ли артефакт `v1.1.1` в Harbor/на стенд: `docker image ls | grep 1.1.1` на HARBOR01 (появится в уроке про реестр) или в логах CI.

**Решение.** Если образ `v1.1.1` никуда не публиковался — можно исправить тег:

```bash
git switch release/1.1
git cherry-pick <SHA фикса>          # переносим фикс в релизную ветку
git push origin release/1.1
git tag -d v1.1.1 && git push origin :refs/tags/v1.1.1
git tag -a v1.1.1 -m "hotfix 1.1.1" && git push origin --follow-tags
```

Если артефакт уже ушёл в прод — тег **не трогаем**, выпускаем `v1.1.2` тем же способом (cherry-pick + новый тег). Плюс обязательный шаг: `git switch main && git merge --no-ff release/1.1`, чтобы фикс не потерялся при следующем релизе.

**Ответ пользователю:** «Фикс не попал в релизную ветку — прод собирается из `release/1.1`, а коммит был только в `main`. Перенёс фикс черри-пиком, выпустил v1.1.1 (v1.1.2), артефакт пересобран, на стенде версия обновилась. Впредь правки для релиза идут через `hotfix/*` от тега, а не напрямую в `main`.»

**Закрытие заявки:** тип «Ошибка релиза», решение «cherry-pick в релизную ветку + новый тег», в описании — ссылка на коммит и новый тег.

## 6. Ошибки новичков и безопасность

**1. Долгоживущие ветки.** `feature/x` живёт три недели → конфликты при каждом merge, «пятничный» релиз из неизвестно чего. *Правильно:* ветка живёт часы-дни, незаконченное — за фича-флагом.

**2. Ребейз опубликованной ветки.** `git rebase main` на ветке, которую уже скачали коллеги → их локальные копии разъехались, кто-то делает `--force` и теряет чужие коммиты. *Правильно:* ребейзить только свою, ещё не запушенную ветку; опубликованную — merge.

**3. `git pull` по умолчанию.** Создаёт merge-коммиты «Merge branch 'main' of ...» в истории. *Правильно:* `pull.ff only` или `pull.rebase true`, обдуманно.

**4. Легковесные теги для релизов.** `git tag v1.0.0` без `-a` → нет автора и даты, `--follow-tags` его не отправит, CI по тегу может не сработать. *Правильно:* `git tag -a` с осмысленным сообщением.

**5. Переиспользование номера версии.** Удалили тег `v1.1.1` и поставили заново на другой коммит, артефакт уже в проде → «какая версия на самом деле» не восстановить, кеши и подписи ломаются. *Правильно:* новый номер (`v1.1.2`), старое не трогать.

**6. Семантика «на глаз».** Ломающее изменение в PATCH → у клиента отваливается интеграция после «безопасного обновления». *Правильно:* MAJOR для совместимости-breaking, и это фиксируется в ревью (урок 16).

**7. Релиз с ноутбука.** `git push`, потом «руками собрал на своей машине и залил на сервер» → артефакт невоспроизводим, версия не связана с коммитом. *Правильно:* только CI по тегу, артефакт — из репозитория, тег = тег образа.

**8. Нет защиты ствола.** Любой может `push --force` в `main` и переписать историю. *Правильно:* protected branch на сервере (хук сейчас, GitLab — урок 17), плюс подпись тегов.

### Безопасность

- **Force-push в основную ветку** в боевой среде — это подмена кода в проде: пропадают чужие фиксы и, что хуже, могут «вернуться» удалённые уязвимости. Защита ветки и запрет force — базовое требование, а не паранойя.
- **Секреты в репозитории.** Токен или пароль, попавший в коммит, остаётся в истории навсегда — даже после `git rm`. Ротация обязательна, чистка истории (`filter-repo`) — с согласованием со всей командой.
- **Подпись тегов и коммитов** (GPG или Sigstore). Тег — точка доверия: если злоумышленник может поставить `v1.2.0` на свой коммит, цепочка поставки скомпрометирована. В стенде мы это не настраиваем — в проде для релизных тегов нужно.
- **Неизменяемость артефактов.** Реестр должен запрещать перезапись тега образа (`immutable tags` в Harbor). Иначе «тот же v1.1.0» завтра окажется другим кодом.
- В лабораторной мы намеренно разрешаем всем push в `main` и держим bare-репозиторий в `/srv/git` без аутентификации на уровне Git — на учебном стенде это допустимо, в рабочей среде так делать нельзя: нужны права по ролям (Maintainer/Developer/Reporter) и аудит.

## 7. Вопросы на собеседовании

**Вопрос 1. Чем Trunk-Based Development отличается от GitFlow и что бы вы выбрали для нашего сервиса?**

*Ответ.* TBD — одна долгоживущая ветка, короткие ветки на часы, вливание минимум раз в день, незаконченное скрыто фича-флагами; релиз — с транка, ветки `release/*` только для сопровождения старых версий. GitFlow — пять типов веток, `develop` как интеграционная, отдельные `release/*` и `hotfix/*`, merge-коммиты. TBD требует зрелого CI и культуры маленьких изменений, зато даёт высокую частоту деплоя и низкий lead time. GitFlow удобен, когда нужно параллельно поддерживать несколько версий и релизы редкие и тяжёлые (коробочный продукт, on-premise, где клиент обновляется раз в год). Для SaaS с ежедневными деплоями GitFlow — лишний оверхед, я бы выбрал TBD или GitHub Flow.

*Что хочет услышать интервьюер:* что выбор модели диктуется продуктом и зрелостью CI, а не модой; что кандидат знает цену обеих схем.
*Красный флаг:* «GitFlow устарел, всегда только trunk» без обсуждения контекста.

**Вопрос 2. Как вы выпускаете срочный hotfix в trunk-based модели?**

*Ответ.* Если прод собирается с транка — фикс идёт обычным коротким PR в `main`, проходит CI, выпускается патч-версия `x.y.Z+1`. Если прод закреплён за релизной веткой (`release/1.1`), фикс делается веткой от тега этой версии, вливается в релизную ветку, ставится новый PATCH-тег, собирается артефакт, и **обязательно** тот же коммит попадает в `main` (merge или cherry-pick), иначе следующий релиз потеряет исправление. Проверяю через `git merge-base --is-ancestor`. Публикация — только через CI по тегу, руками ничего не собираю.

*Что хочет услышать интервьюер:* что кандидат помнит про «обратный» перенос в транк и проверяет попадание фикса.
*Красный флаг:* «закоммичу прямо в main и запушу».

**Вопрос 3. Что такое SemVer и как понять, какую цифру поднимать? Как связать это с коммитами?**

*Ответ.* `MAJOR.MINOR.PATCH`: MAJOR — несовместимое изменение контракта (API, схемы, формата файла), MINOR — новая функциональность обратно совместимо, PATCH — исправление. `0.y.z` — период, когда API нестабилен. Предрелизы (`-rc.1`) меньше финальной версии, метаданные сборки (`+sha`) на порядок не влияют. Связка с Conventional Commits: `feat:` → MINOR, `fix:` → PATCH, `feat!:` или `BREAKING CHANGE:` в теле → MAJOR, остальное (`chore`, `docs`, `ci`) версию не двигает. Дальше автоматизация: парсер коммитов считает следующую версию и CI ставит тег. Важное правило — номер версии публикуется один раз и не переиспользуется.

*Что хочет услышать интервьюер:* понимание, что breaking change — это про контракт для потребителя, и что версия ставится автоматикой по правилам, а не «на глаз».
*Красный флаг:* «MINOR — когда много изменений, PATCH — когда мало».

**Вопрос 4. У нас три поддерживаемые версии продукта. Как организовать ветки?**

*Ответ.* Долгоживущие ветки `release/1.x`, `release/2.x`, `release/3.x`, созданные от соответствующих тегов; новые фичи — только в `main`, фиксы — в `main` и затем cherry-pick в поддерживаемые релизные ветки (или сначала в самую старую, потом merge вперёд). Каждая ветка защищена, теги ставятся по SemVer с PATCH-инкрементом. Политика поддержки (сколько версий и как долго) фиксируется письменно, чтобы не поддерживать всё бесконечно. CI собирает артефакт на каждый тег, а не на каждую ветку.

*Что хочет услышать интервьюер:* что кандидат умеет ограничивать число поддерживаемых версий и знает направление переноса фиксов.
*Красный флаг:* «заведу отдельный репозиторий под каждую версию».

**Вопрос 5. Как TBD выживает, если фича делается три месяца?**

*Ответ.* Ветка — не место для ожидания. Код вливается в транк частями под фича-флагом: сначала пустой каркас, потом логика за флагом, включение — конфигом на конкретных пользователей. Флаг удаляется сразу после полного раската, иначе они накапливаются и превращаются в техдолг. Дополнительно — `branch by abstraction`: интерфейс вводится в транк, старая и новая реализации сосуществуют, переключение — в одну строку. Это позволяет не держать долгие ветки и не блокировать релизы.

*Что хочет услышать интервьюер:* знание фича-флагов как инженерной практики и готовность чистить их после раската.
*Красный флаг:* «держу ветку, пока не доделаю».
