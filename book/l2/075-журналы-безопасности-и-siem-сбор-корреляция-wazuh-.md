# Журналы безопасности и SIEM: сбор, корреляция, Wazuh/ELK — первое развёртывание

## 1. Введение (зачем это нужно в реальной работе)

Тикет в поддержку «Вектора»:

> **Пользователь:** ivanov (бухгалтерия)
> **ВМ:** WIN11-CL01
> **Что написал:** «Утром не смог войти — система сказала, что учётка заблокирована. Ночью меня за компьютером не было. Может, это Галина Петровна что-то делала с моим профилем? Посмотрите, пожалуйста.»
> **Срочность:** средняя

Раньше, на уровне L1, ответ был бы таким: «разблокировал учётку, пароль сбросил, проблема решена». На L2 такой ответ неприемлем, потому что остаётся главный вопрос: **а почему её заблокировали?** Может, тридцать раз кто-то подбирал пароль с чужого компьютера в 3 часа ночи, и тогда сброс пароля — это просто выдача ключа от квартиры грабителю.

Чтобы ответить, нужны логи с нескольких машин, собранные в одном месте, с нормальным временем и возможностью искать по ним за неделю назад. Одиночный просмотр «Журнала событий» на одной ВМ это не даёт: логи перезаписываются, разбросаны по 50 машинам, и связать событие на DC01 с событием на WIN11-CL01 глазами невозможно. Именно поэтому в компаниях ставят SIEM — систему, которая собирает журналы со всех узлов, приводит их к общему виду, ищет в них закономерности и складывает на хранение.

После этой главы ты будешь уметь: включить и настроить аудит так, чтобы нужные события вообще появлялись; выгрузить их локально для быстрой проверки; развернуть на своём стенде Wazuh (бесплатный open-source SIEM) и подключить к нему Windows- и Linux-хосты; написать собственное правило корреляции; и, наконец, диагностировать ситуацию «агент есть, а логов нет» — самый частый вид заявки по SIEM в реальной поддержке.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Сначала о том, откуда вообще берутся логи безопасности.**

В Windows журналы — это файлы `.evtx` в `C:\Windows\System32\winevt\Logs`, которыми управляет служба `EventLog`. Нам важны каналы: **Security** (входы, права, изменения учёток, доступ к файлам), **System** (службы, драйверы, ядро), **Application** (приложения, в т.ч. 1С), плюс прикладные каналы вроде `Microsoft-Windows-PowerShell/Operational`. Ключевая особенность: **в Security пишутся только те события, для которых включён аудит**. По умолчанию там почти пусто. Поэтому первое действие админа — не «поставить SIEM», а включить политики аудита (через `auditpol` или GPO). Это печально известная грабля: собрали SIEM, а в нём тишина, потому что аудит не включён.

В Linux три источника: **journald** (`journalctl`, бинарный журнал systemd), **rsyslog** (текстовые файлы `/var/log/auth.log`, `/var/log/syslog` в Ubuntu) и **auditd** (`/var/log/audit/audit.log`, ядровый аудит, аналог Windows Security по смыслу). Плюс сами демоны пишут свои логи — `sshd`, `sudo`, `nftables`.

**Способы доставки.** Есть два подхода:
1. **Агент** — маленькая служба на хосте, которая сама читает журналы и шлёт их на сервер по своему протоколу (у Wazuh это TCP 1514, регистрация агента — 1515). Плюс: работает через NAT, шифрование, буферизация при обрыве связи. Минус: надо ставить и обслуживать на каждой машине.
2. **Agentless / pull** — сервер сам забирает логи: Windows Event Forwarding (WEF/WEC) по протоколу WS-Management (5985/5986), syslog с сетевого оборудования по UDP 514, `winlogbeat`/`filebeat` — это уже агентный сбор, но от Elastic.

**Что делает SIEM после сбора.** Схема:

```text
   источники                    SIEM (MON01, 10.10.10.40)
┌──────────────┐
│ DC01   (агент)│──┐         ┌──────────────────────────────────────┐
│ FS01   (агент)│──┤ 1514/TCP│ 1. СБОР      remoted: приём, буфер    │
│ WIN11-CL01    │──┼────────▶│ 2. ДЕКОДЕРЫ  evtx → JSON, поля:        │
│ UBU01  (агент)│──┤         │    user, srcip, eventid, logon_type  │
│ WEB01  (агент)│──┘        │ 3. ПРАВИЛА   одиночные + корреляция    │
└──────────────┘            │    (frequency/timeframe)             │
                            │ 4. ОБОГАЩЕНИЕ гео-IP, инвентарь, MITRE│
                            │ 5. ИНДЕКС    OpenSearch :9200         │
                            │ 6. ВИЗУАЛ    Dashboards :443          │
                            └──────────────────────────────────────┘
                                 агенты: 1514/1515, API: 55000,
                                 dashboard: 443, индексер: 9200
```

**Ключевое понятие — корреляция.** Одиночное событие «неудачный вход» (Windows 4625, sshd «Failed password») — это шум, таких сотни в день, на них никто не реагирует. Корреляция — это правило вида «5 и более неудачных входов с одного IP за 120 секунд → алерт уровня 10». Только после этого событие становится инцидентом. Именно поэтому SIEM ≠ «сборщик логов»: сбор без правил это просто дорогой архив.

**Wazuh vs ELK.** Wazuh — open-source (лицензия GPLv2), внутри у него свой менеджер правил и свой индексер на форке OpenSearch, и своя веб-консоль. ELK (Elasticsearch + Logstash + Kibana) — это универсальная платформа поиска по логам; чтобы из неё получился SIEM, нужны либо платная подписка Elastic Security, либо Wazuh в связке с ELK (историческая архитектура Wazuh 3.x и опция в 4.x). Для учебного стенда Wazuh «всё-в-одном» — самый быстрый путь: одна команда, всё на одной ВМ. Elastic Stack лицензируется по Elastic License 2.0 / SSPL — для внутреннего использования бесплатно, но это не open-source в строгом смысле.

**Реалии РФ 2026.** В крупных компаниях и особенно в КИИ ты чаще встретишь отечественные SIEM: MaxPatrol SIEM (Positive Technologies), Kaspersky KUMA, R-Vision SIEM [ПРОВЕРИТЬ актуальный состав линейки]. Логика работы у них та же — сбор, нормализация, корреляция, кейсы. Освоив Wazuh, ты не «изучишь MaxPatrol», но поймёшь принципы, а они переносимы. Отдельно напомню: для субъектов КИИ и операторов персональных данных хранение и защита журналов — это не блажь, а требование (187-ФЗ, 152-ФЗ, приказы ФСТЭК) — подробнее в уроке 78.

## 3. Аналогия из жизни

Представь большой офисный бизнес-центр. На каждом этаже стоит вахтёр, который пишет в тетрадку: «в 9:12 вошёл Иванов, пропуск действителен», «в 9:15 неизвестный пытался пройти по чужому пропуску — отказ». Это **агенты и локальные журналы**. Тетрадки лежат на этажах, в каждой свой почерк, и чтобы что-то найти, надо обойти 12 этажей.

**SIEM** — это единая служба охраны в подвале, куда все вахтёры по рации передают записи, секретарь приводит их к единому бланку («время, этаж, кто, что, результат»), а аналитик смотрит на большом экране. И у аналитика есть инструкция: «если за 2 минуты трое разных людей не прошли по пропуску на один и тот же турникет — звонить начальнику смены и блокировать турникет». Это **корреляция**. А отдельная полка с бланками за последние 90 дней — это **хранение и ретенция**.

Где аналогия ломается: вахтёр физически видит нарушителя и может его задержать, а лог лишь фиксирует факт — SIEM ничего не блокирует, он только сообщает, и решение всегда принимает человек (или отдельная система реагирования, которую надо настраивать отдельно).

## 4. Практика и команды

**1. Посмотреть текущие политики аудита (Windows).**

```cmd
auditpol /get /category:*
```

Ключ `/get` — показать, `/category:*` — все категории. В выводе у каждой подкатегории стоит `No Auditing` / `Success` / `Failure`. Смотреть надо на `Logon/Logoff`, `Account Logon`, `Account Management`, `Detailed Tracking`, `Object Access`, `Policy Change`. Если везде `No Auditing` — Security-журнал почти пуст, и никакой SIEM не поможет.

**2. Включить аудит входов и создания процессов.**

```cmd
auditpol /set /subcategory:"Logon" /success:enable /failure:enable
auditpol /set /subcategory:"Account Logon" /success:enable /failure:enable
auditpol /set /subcategory:"Process Creation" /success:enable
auditpol /set /subcategory:"Account Management" /success:enable /failure:enable
```

`/subcategory` — точное имя подкатегории (регистр не важен, кавычки обязательны из-за пробела), `/success:enable` — писать успешные события, `/failure:enable` — неуспешные. Для отладки на стенде можно и то и другое; в бою `Process Creation` только `success`, иначе объём логов вырастает в разы. Важно: 4688 не покажет командную строку, пока не включена политика «Include command line in process creation events» (Computer Configuration → Administrative Templates → System → Audit Process Creation). Это делается через GPO, а не через `auditpol`.

**3. Посмотреть параметры журнала и увеличить размер.**

```cmd
wevtutil gl Security
wevtutil sl Security /ms:1073741824
```

`gl` = get log (показывает `maxSize`, `retention`, `isEnabled`), `sl` = set log, `/ms:` — максимальный размер в байтах (здесь 1 ГБ). По умолчанию в клиентских Windows Security часто 20 МБ — при включённом аудите логи перезаписываются за пару часов, и расследовать ночной инцидент днём будет не по чему.

**4. Быстро вытащить события из журнала без PowerShell.**

```cmd
wevtutil qe Security /q:"*[System[(EventID=4625)]]" /c:5 /rd:true /f:text
```

`qe` = query events, `/q:` — XPath-фильтр, `/c:5` — первые 5 событий, `/rd:true` — в обратном порядке (свежие сверху), `/f:text` — текстовый формат (есть ещё `/f:xml`, `/f:json`). Удобно, когда PowerShell на хосте ограничен политикой.

**5. То же через PowerShell, но с разбором полей.**

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625; StartTime=(Get-Date).AddHours(-24)} -MaxEvents 20 |
  Select-Object TimeCreated,
    @{n='User';e={$_.Properties[5].Value}},
    @{n='SrcIP';e={$_.Properties[19].Value}},
    @{n='LogonType';e={$_.Properties[10].Value}}
```

`-FilterHashtable` работает на стороне службы журнала и в разы быстрее, чем `Where-Object`. `Properties[N]` — поля события по порядку; для 4625 это, соответственно, имя учётки, IP источника и тип входа. Что смотреть: серия событий с одного `SrcIP` по многим `User` — это перебор (brute-force), а с одного `SrcIP` по одной учётке с `LogonType=3` — похоже на «распылённый» подбор или работу червя.

**6. Ключевые Event ID, которые надо знать наизусть.**

```text
4624 успешный вход (LogonType: 2 локально, 3 по сети, 10 RDP, 5 служба)
4625 неуспешный вход (пароль/учётка/IP источника — в полях)
4648 вход с явно указанными учётными данными (частый признак lateral movement)
4672 вход с правами администратора
4688 создан процесс (с командной строкой — только если включена GPO)
4720 создана учётка; 4726 удалена; 4732 добавлен в группу
4740 учётка заблокирована; 4767 разблокирована
4768/4769 Kerberos TGT/TGS; 4771 ошибка Kerberos pre-auth
1102 журнал безопасности очищен  ← почти всегда красный флаг
7045 (System) установлена служба   ← частый признак закрепления
4104 (PowerShell/Operational) блок скрипта
5140/5145 (Object Access) доступ к сетевой папке
```

Это не «список для зубрёжки», а рабочий минимум: по этим ID строятся 80 % правил в любой SIEM.

**7. Linux: журнал systemd.**

```bash
journalctl -u ssh --since "2 hours ago" -p warning --no-pager
```

`-u ssh` — юнит (в Ubuntu 24.04 служба называется `ssh`, не `sshd`), `--since` понимает и даты, и относительные интервалы, `-p warning` — уровень важности и выше, `--no-pager` — не открывать пейджер (важно в скриптах). Смотреть на строки `Failed password for invalid user` и `Connection closed by authenticating user`.

**8. Linux: текстовый лог и подсчёт.**

```bash
sudo grep "Failed password" /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn | head
```

Здесь `grep` фильтрует строки, `awk` берёт поле с IP-адресом (в формате rsyslog он стоит в конце строки), `uniq -c` считает повторы, `sort -rn` сортирует по убыванию. Типичный вывод — `  347 203.0.113.45`. Триста сорок семь попыток с одного адреса за сутки — это уже не «шум», а инцидент.

**9. Linux: аудит ядра (auditd).**

```bash
sudo ausearch -m USER_LOGIN -sv no -ts today
sudo aureport --auth --summary -ts today
```

`ausearch` ищет по типу сообщения (`-m`), `-sv no` — только неуспешные (`success=no`), `-ts today` — с начала суток. `aureport --auth --summary` даёт сводку: сколько всего попыток аутентификации, сколько неуспешных, топ пользователей. Если auditd не установлен: `sudo apt install auditd audispd-plugins`.

**10. Проверить состояние менеджера Wazuh и список агентов.**

```bash
sudo /var/ossec/bin/wazuh-control status
sudo /var/ossec/bin/agent_control -l
```

Первая команда показывает, живы ли `wazuh-remoted`, `wazuh-analysisd`, `wazuh-db` и остальные демоны менеджера. Вторая — список агентов с ID, именем и статусом (`Active` / `Disconnected` / `Never connected`). Именно сюда смотрят первым делом по заявке «агент не работает».

**11. Проверить, как Wazuh разобрал конкретную строку лога.**

```bash
sudo /var/ossec/bin/wazuh-logtest
```

Интерактивный тест: вставляешь строку лога — получаешь, каким декодером она разобрана, какие поля извлечены, какое правило сработало и с каким уровнем. Незаменимо при написании своих правил: видно, почему правило «не ловится».

**12. Своё правило корреляции.**

```xml
<!-- /var/ossec/etc/rules/local_rules.xml -->
<group name="local,sshd,">
  <rule id="100100" level="10" frequency="5" timeframe="120">
    <if_matched_sid>5710</if_matched_sid>
    <same_source_ip />
    <description>Brute-force SSH: 5+ failed logins from one IP in 120s</description>
    <mitre>
      <id>T1110</id>
    </mitre>
  </rule>
</group>
```

`id` — своё правило должно быть в диапазоне 100000–120000 (зарезервировано для локальных), `level` — критичность 0–15, `frequency` + `timeframe` — сколько раз за сколько секунд, `if_matched_sid` — на какое базовое правило «нанизываемся» (5710 — неудачный SSH-вход [ПРОВЕРИТЬ номер в своей версии]), `same_source_ip` — требовать совпадения IP. После правки: `sudo systemctl restart wazuh-manager`. Правила читаются в порядке возрастания ID, и `local_rules.xml` подключён последним — поэтому твоё правило может переопределить встроенное.

**13. Посмотреть алерты и лог менеджера.**

```bash
sudo tail -f /var/ossec/logs/alerts/alerts.log
sudo tail -f /var/ossec/logs/alerts/alerts.json
sudo tail -f /var/ossec/logs/ossec.log
```

`alerts.log` — человекочитаемый, `alerts.json` — тот же поток в JSON (по нему удобно грепать по полям), `ossec.log` — служебный лог менеджера: там видно подключения агентов, ошибки декодирования, проблемы с индексером.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

Нужны: **MON01** (Ubuntu Server 24.04, 10.10.10.40, роль мониторинга), **DC01** (10.10.10.10, AD/DNS/DHCP), **UBU01** (10.10.10.30), **WIN11-CL01** (DHCP), **FS01** (10.10.10.20). Все машины введены в домен, кроме UBU01 и MON01 (Linux в домен не вводим — это отдельная тема).

Важно по ресурсам: на MON01 уже стоит Zabbix, а Wazuh «всё-в-одному» требует заметно больше. Официальные требования Wazuh к алл-ин-уан установке — порядка 4 vCPU / 8 ГБ RAM [ПРОВЕРИТЬ в актуальной документации]. Поэтому: выключи MON01, выставь **4 vCPU, 8 ГБ RAM, диск 60 ГБ**, включи обратно. Если ОЗУ хоста не хватает — останови Zabbix-контейнеры/службы на время лабы (`sudo systemctl stop zabbix-server`) и верни после. Это учебный компромисс: в продакшене менеджер, индексер и дашборд ставят на разные ВМ.

### Снапшот

На MON01, DC01, FS01, UBU01 и WIN11-CL01: VMware Workstation → правый клик по ВМ → **Snapshot → Take Snapshot**, имя `before-l2-075`. (Через CLI VMware Workstation снапшоты не делает — только GUI.) Дополнительно запиши в `stand-log.md` строку «before-l2-075: перед установкой Wazuh».

### Шаги

1. **MON01.** Проверь сеть и время:
   ```bash
   ip -4 a show ens33
   timedatectl
   ```
   Ожидаемо: `10.10.10.40/24`, шлюз `10.10.10.2`, время московское. Если время уезжает — настрой синхронизацию с DC01 (он держит время домена):
   ```bash
   sudo apt install -y chrony
   sudo sed -i 's/^pool .*/server 10.10.10.10 iburst/' /etc/chrony/chrony.conf
   sudo systemctl restart chrony && chronyc sources -v
   ```
   Ожидаемо: в `chronyc sources` напротив `10.10.10.10` появится `^*` (выбран источником).

2. **MON01.** Скачай установщик Wazuh:
   ```bash
   cd /tmp
   curl -sO https://packages.wazuh.com/4.x/wazuh-install.sh
   curl -sO https://packages.wazuh.com/4.x/wazuh-install-files.tar
   ls -lh wazuh-install*
   ```
   Второй файл (`wazuh-install-files.tar`) содержит сертификаты и будущие пароли — если его нет, установщик сгенерирует сам. Ожидаемо: оба файла скачались без ошибок (MON01 выходит в интернет через NAT VMnet8).

3. **MON01.** Запусти установку «всё-в-одном»:
   ```bash
   sudo bash wazuh-install.sh -a -i
   ```
   `-a` = all-in-one (indexer + manager + dashboard), `-i` = игнорировать проверку ресурсов [ПРОВЕРИТЬ актуальность ключа]. Ожидаемо: 10–20 минут вывода, в конце блок `INFO: Installation finished` и сообщение с URL дашборда и логином `admin`.

4. **MON01.** Достань пароль администратора:
   ```bash
   sudo tar -O -xvf wazuh-install-files.tar wazuh-install-files/wazuh-passwords.txt | grep -A2 "'admin'"
   ```
   Ожидаемо: строка с паролем для пользователя `admin`. Сохрани её в `stand-log.md` (это учебный пароль стенда).

5. **С хоста.** Открой `https://10.10.10.40` в браузере, прими предупреждение о самоподписанном сертификате, войди как `admin`. Ожидаемо: дашборд Wazuh с разделами `Agents management`, `Security events`, `MITRE ATT&CK`.

## 6. Ошибки новичков и безопасность

1. **«Включим аудит всего и сразу» →** объём логов вырастает в разы, диск индексера переполняется за сутки, менеджер начинает отбрасывать события, и ты теряешь как раз то, что нужно. *Правильно:* начинать с Logon/Account Logon/Account Management/Process Creation, остальное — по задаче, и обязательно считать суточный объём заранее.

2. **Не включён аудит →** SIEM стоит, дашборд красивый, событий ноль. Полдня диагностики «сломанного SIEM» уходит на пустой журнал. *Правильно:* при подключении любого Windows-хоста первым делом `auditpol /get /category:*`.

3. **Расхождение времени →** события приходят с разницей в часы, корреляция «5 за 120 секунд» не срабатывает, при разборе инцидента таймлайн не складывается. *Правильно:* NTP/chrony/w32time на всех узлах до установки агентов, всё в одной таймзоне (лучше UTC в SIEM, а отображение — локальное).

4. **Без тюнинга правил →** 3000 алертов в день, через неделю никто не смотрит, реальный инцидент тонет. *Правильно:* подавлять известный шум (сканирование уязвимостей из урока 74, сервисные учётки, бэкапы), порог уровня для нотификаций поднимать, а не «отключать алерты».

5. **Хранить логи на том же диске, что и всё остальное →** диск забит, вместе с логами умерли и сервисы. *Правильно:* отдельный том под индексер, ротация индексов, контроль `df -h` в мониторинге (Zabbix на MON01 уже есть).

6. **Открыть дашборд в интернет «чтобы смотреть из дома» →** публично доступная консоль с паролем `admin` = компрометация всех логов компании. *Правильно:* дашборд только во внутренней сети/VPN, MFA, отдельная учётка вместо `admin`, ограничение по IP.

7. **Чистить журнал для экономии места →** событие 1102 «журнал очищен» само по себе красный флаг для любого ИБ-специалиста, а если чистил не ты — уничтожены доказательства. *Правильно:* увеличивать размер, архивировать, выгружать в SIEM, но не очищать.

8. **Писать `frequency` без `same_source_ip` →** правило «5 неудачных входов за 120 секунд» срабатывает на пятерых сотрудников, забывших пароль утром в понедельник. *Правильно:* всегда думать, по какому полю группировать.

### Безопасность

На стенде мы делаем несколько небезопасных вещей ради простоты: держим Wazuh на той же ВМ, что и Zabbix; используем учётку `admin` с паролем из установщика; дашборд слушает все интерфейсы. **В боевой среде так нельзя:** менеджер, индексер и дашборд разводят по разным хостам (компрометация дашборда не должна давать доступ к хранилищу логов), административный доступ к SIEM — только из выделенной сети с MFA, учётка `admin` отключается после первичной настройки, все действия в самой SIEM логируются отдельно. Отдельно: журналы содержат персональные данные (имена, IP, иногда содержимое командных строк) — они подпадают под 152-ФЗ, доступ к ним регламентируется, срок хранения определяется приказом, а не «пока место есть». И третье: SIEM — это цель для атакующего №1 после DC. Если злоумышленник получил домен, он первым делом попытается отключить или «подчистить» SIEM (вспомни событие 1102 и остановку службы агента из лабы). Поэтому защита SIEM — это отдельная задача: сегментация, отдельные учётки агентов, неизменяемое (WORM) хранилище или отправка копии алертов во внешний коллектор.

## 7. Вопросы на собеседовании

**Вопрос 1. Чем SIEM отличается от простого сборщика логов?**
*Ответ:* Сборщик (rsyslog, filebeat, WEF) только транспортирует и складывает. SIEM добавляет: нормализацию (приведение событий разных форматов к общим полям), обогащение (инвентарь, гео-IP, репутация), корреляцию (правила «N событий за T времени»), приоритизацию по критичности, хранение с ретенцией и интерфейс для расследования. Ценность SIEM не в том, что он хранит логи, а в том, что он превращает поток в небольшое число инцидентов. Хороший ответ — добавить, что без тюнинга SIEM вырождается обратно в сборщик, только дорогой.
*Что хочет услышать интервьюер:* что ты понимаешь разницу между «собрать» и «обнаружить», и что ты не считаешь установку SIEM самоцелью.
*Красный флаг:* «SIEM — это программа, которая находит хакеров» без понимания роли правил и ложных срабатываний.

**Вопрос 2. Какие события Windows вы бы точно отправляли в SIEM и почему?**
*Ответ:* 4625 (неуспешные входы — база для детекта перебора), 4624 (успешные, с разбором LogonType: 3 и 10 особенно интересны), 4648 (явные учётные данные — lateral movement), 4672 (вход с админскими правами), 4688 (создание процессов, с командной строкой), 4720/4726/4732 (управление учётками и группами), 4740 (блокировки), 4768/4769/4771 (Kerberos — атаки на AD типа Kerberoasting), 1102 (очистка журнала), 7045 из System (установка службы — признак закрепления), 4104 из PowerShell/Operational. Отдельно замечу: 4688 бессмысленен без включённой GPO о командной строке, об этом часто забывают.
*Что хочет услышать интервьюер:* не заученный список, а понимание, что за атака детектируется каждым событием, и знание про LogonType и GPO.
*Красный флаг:* «собираем всё, разберёмся потом» или путаница между 4624 и 4625.

**Вопрос 3. Что нужно, чтобы корреляция „5 неудачных входов за 120 секунд“ работала корректно?**
*Ответ:* во-первых, синхронизация времени на всех узлах — иначе окно timeframe не сложится; во-вторых, нормализованное поле IP источника, по которому группируем (`same_source_ip` в Wazuh), иначе правило будет ловить пятерых разных сотрудников; в-третьих, включённый аудит на источнике; в-четвёртых, понимание, что считать «источником» при RDP за шлюзом (там IP будет шлюза, и группировать надо по имени пользователя). Ещё нужно продумать порог: пять попыток — это может быть забывчивый сотрудник, поэтому дополнительно смотрим на количество разных учёток с одного IP.
*Что хочет услышать интервьюер:* понимание, что корреляция — это не только XML-правило, а ещё и данные, время и продуманные поля группировки.
*Красный флаг:* «просто написать правило, Wazuh сам разберётся».

**Вопрос 4. Агент в дашборде Active, но события с хоста не приходят. Ваши действия?**
*Ответ:* сначала проверить, что события вообще генерируются локально — на Windows `auditpol /get /category:*` и `Get-WinEvent -LogName Security -MaxEvents 5`, на Linux `journalctl -n 5`. Потом проверить конфиг сбора `<localfile>` на агенте (правильный ли канал, не закомментирован ли блок), затем локальный лог агента `ossec.log` на ошибки декодирования и ошибки соединения. Дальше — на менеджере `wazuh-control status` (жив ли `wazuh-analysisd`, `wazuh-remoted`), `agent_control -l`, лог менеджера, наличие места на диске под индексер. И отдельно — время: если оно уехало, события могут быть, но не попадать в выбранное окно поиска.
*Что хочет услышать интервьюер:* системный порядок «источник → транспорт → менеджер → индексер → интерфейс», а не «перезапустил, заработало».
*Красный флаг:* сразу «переустановить агент» без диагностики.

**Вопрос 5. Какие ограничения у open-source SIEM вроде Wazuh в реальной эксплуатации?**
*Ответ:* ресурсы — индексер требователен к RAM и диску, на 50 хостах это уже отдельный сервер, а не «ещё одна ВМ»; отсутствие вендорской поддержки и SLA — при инциденте разбираешься сам или через сообщество; тюнинг правил полностью на тебе, «из коробки» много шума и часть детектов придётся писать руками; интеграция с отечественными системами и требованиями по сертификации (для КИИ и ГИС часто нужны сертифицированные ФСТЭК средства) — Wazuh здесь не подходит, нужны MaxPatrol SIEM, KUMA и подобные [ПРОВЕРИТЬ актуальный статус сертификации под конкретное требование]. Плюс отдельная задача — защита самого SIEM и ретенция логов под требования 152-ФЗ/187-ФЗ.
*Что хочет услышать интервьюер:* трезвость — ты не фанат «поставим опенсорс и всё будет», а понимаешь стоимость владения и регуляторику.
*Красный флаг:* «open-source лучше всего, платные SIEM не нужны».

Поиск: `auditpol command line reference`, `event 4688 command line audit policy`, `wevtutil qe examples`.
- **Elastic** — домен `elastic.co/guide`. Разделы «Winlogbeat», «Filebeat», «Elastic Security». Поиск: `winlogbeat install windows`, `elastic security detection rules`. Помни про лицензию Elastic License 2.0 / SSPL.
- **Ubuntu** — домен `ubuntu.com/server/docs` (или `documentation.ubuntu.com`). Разделы: «Logging», «Service management with systemd», «Time synchronisation». Поиск: `ubuntu journalctl logging documentation`, `ubuntu chrony configuration`. [ПРОВЕРИТЬ актуальный URL документации Ubuntu Server 24.04]
- **Red Hat / auditd** — домен `access.redhat.com` (документация RHEL по audit). Статья «Audit system architecture» и справочник `ausearch`/`aureport`. Поиск: `rhel auditd ausearch aureport examples`.
- **MITRE ATT&CK** — домен `attack.mitre.org`. Техники `T1110` (Brute Force), `T1078` (Valid Accounts), `T1059` (Command and Scripting Interpreter), `T1562.002` (Impair Defenses: Disable Windows Event Logging). Поиск: `mitre attack T1110 brute force`.
- **NIST** — домен `csrc.nist.gov`. Публикация SP 800-92 «Guide to Computer Security Log Management» [ПРОВЕРИТЬ номер и актуальность редакции]. Поиск: `NIST SP 800-92 log management`.
- **CIS** — домен `cisecurity.org`. CIS Benchmarks для Windows Server 2022 и Ubuntu 24.04, разделы про auditing/logging — связка с уроком 72. Поиск: `CIS benchmark windows server 2022 audit policy`.

Отечественные SIEM (MaxPatrol SIEM, Kaspersky KUMA, R-Vision SIEM) — смотри вендорскую документацию на их официальных сайтах; конкретные URL и состав модулей меняются, поэтому здесь их не привожу, `[ПРОВЕРИТЬ]` перед использованием в резюме.
