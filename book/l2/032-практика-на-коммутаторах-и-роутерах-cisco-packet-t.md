# Практика на коммутаторах и роутерах: Cisco Packet Tracer / EVE-NG / GNS3, MikroTik в виртуальной лаборатории

## 1. Введение (зачем это нужно в реальной работе)

**Заявка в поддержку.** Иван Иванов (бухгалтерия, WIN11-CL01): «После того как в кабинете переставили розетки, половина сетевых папок открывается через раз, а иногда сеть вообще пропадает на пару минут. У Петровой при этом всё нормально. Сделайте что-нибудь, у нас закрытие месяца». Срочность: средняя.

Ты идёшь в серверную, смотришь на коммутатор… а на нём нет ни консольного порта под рукой, ни документации, кто и зачем воткнул лишний патч-корд. Проверять гипотезы «на живом» коммутаторе в рабочее время бухгалтерии — плохая идея: одно неверное `switchport` — и без сети весь отдел. Правильный путь L2-инженера: **сначала воспроизвести сегмент в симуляторе, найти причину на копии, и только потом идти к боевому железу с готовым решением**.

Именно для этого нужна виртуальная сетевая лаборатория. В этой главе ты:
- поймёшь разницу между **симулятором** (Packet Tracer) и **эмулятором** (GNS3, EVE-NG) и когда какой брать;
- поднимешь на стенде «Вектор» машину **SIM01** с GNS3-сервером и соберёшь в ней копию офисного сегмента;
- научишься запускать в лаборатории **настоящий RouterOS** (MikroTik CHR) и настраивать на нём коммутатор с VLAN и роутер с NAT;
- сможешь связать эмулируемую сеть с реальным стендом (DC01, FS01) и снимать с неё pcap для Wireshark;
- узнаешь, какие образы можно использовать легально, а какие — нет.

После главы ты сможешь за 20 минут собрать «песочницу» под любую сетевую гипотезу и приносить на разбор не «мне кажется, там петля», а конфиг, pcap и вывод команд.

## 2. Теория «под капотом»

### Симулятор vs эмулятор

**Симулятор (Cisco Packet Tracer)** — программа, которая *изображает* работу устройств. Внутри нет настоящей Cisco IOS: есть упрощённая модель, которая считает кадры и пакеты по расписанию событий. Отсюда плюсы (работает на слабом ноутбуке, 30 устройств в одной картинке, наглядный режим Simulation) и минусы (часть команд не поддерживается, поведение STP/ARP/таймеров идеализировано, реальные баги не воспроизводятся). Файлы — `.pkt`. Распространяется Cisco через программу NetAcad / Skills for All; из РФ доступ к ней затруднён — это легальная, но не всегда доступная опция.

**Эмулятор (GNS3, EVE-NG)** — это оркестратор виртуальных машин. Он не изобретает поведение устройств, а запускает **настоящие образы** (RouterOS, VyOS, FRR, Linux) в QEMU/KVM и соединяет их виртуальными линками. Внутри такого «роутера» крутится реальная ОС: с реальными таймерами, реальным ядром, реальными багами. Отсюда требования к железу и отдельный вопрос — где брать образы.

| | Packet Tracer | GNS3 | EVE-NG CE |
|---|---|---|---|
| Тип | симулятор | эмулятор | эмулятор |
| Где живёт | приложение на хосте | сервер (VM) + клиент на Windows | готовый appliance (VM), работа через браузер |
| Ресурсы | 1–2 ГБ RAM | 4–8 ГБ RAM на сервер | 4–8 ГБ RAM |
| Образы | встроены | свои (QEMU/Docker/IOU) | свои (QEMU/Docker/IOU) |
| Реализм | учебный | реальный | реальный |
| Лицензии | NetAcad | образы — твоя ответственность | образы — твоя ответственность |

### Что важно знать про железо и виртуализацию

GNS3/EVE-NG внутри себя запускают QEMU. Чтобы это не тормозило, серверу нужна **вложенная виртуализация**: в VMware Workstation у ВМ SIM01 надо включить *Processors → Virtualize Intel VT-x/EPT or AMD-V/RVI*. Без этого QEMU работает в программной эмуляции — в 5–10 раз медленнее, и лаба «умирает».

Второй момент: VMware Workstation конфликтует с включённым Hyper-V / WSL2 / Device Guard на хосте (использует медленный режим совместимости). Если лаба тормозит — проверь `bcdedit` и компоненты Windows.

### Порты и доступы, которые понадобятся

| Сервис | Порт | Учётка по умолчанию |
|---|---|---|
| GNS3 server (API + web) | TCP 3080 | нет (локально) |
| EVE-NG web | TCP 80 | admin / eve |
| EVE-NG SSH | TCP 22 | root / eve |
| MikroTik Winbox | TCP 8291 | admin, **пароля нет** |
| MikroTik SSH / API | 22 / 8728 | admin |

Линки между узлами внутри GNS3 — это либо UDP-туннели между процессами QEMU (порты выделяются начиная с 10000 `[ПРОВЕРИТЬ]`), либо виртуальные коммутаторы внутри сервера.

### Схема стенда после этой главы

```text
┌──────────────────────── Хост-ПК (Windows 11) ───────────────────────────┐
│  VMware Workstation                                                     │
│  ┌───────────────┐   ┌───────────────┐   ┌────────────────────────────┐ │
│  │ DC01          │   │ UBU01         │   │ SIM01 (Ubuntu 24.04)       │ │
│  │ 10.10.10.10   │   │ 10.10.10.30   │   │ 10.10.10.60                │ │
│  └──────┬────────┘   └──────┬────────┘   │  ┌──────────────────────┐  │ │
│         │   VMnet8 10.10.10.0/24        │  │ GNS3 server :3080    │  │ │
│  ───────┴───────────────────┴────────────┼──┤ QEMU/KVM             │  │ │
│                                          │  │  ├ CHR-SW (bridge)   │  │ │
│                                          │  │  ├ CHR-R1 (router)   │  │ │
│                                          │  │  └ VPCS-1, VPCS-2    │  │ │
│                                          │  └──────────────────────┘  │ │
│  ┌──────────────────────────────┐        └────────────────────────────┘ │
│  │ GNS3 GUI / Wireshark / Winbox│  ← обычные Windows-программы          │
│  └──────────────────────────────┘                                       │
└─────────────────────────────────────────────────────────────────────────┘

Внутри проекта GNS3:

 VPCS-1 ──ether2 [VLAN 10]──┐
                            ├── CHR-SW ──ether1 (trunk 10,20)── CHR-R1 ──ether1── Cloud(VMnet8)
 VPCS-2 ──ether3 [VLAN 20]──┘                                     ether2
```

По OSI всё это — уровни 1–3: линк = «кабель» (L1), CHR-SW = L2-коммутация с тегами 802.1Q, CHR-R1 = L3-маршрутизация и NAT.

## 3. Аналогия из жизни

Packet Tracer — это **авиасимулятор-аркада** в торговом центре: джойстик, красивая картинка, можно отработать «где шасси, где закрылки». Для первых шагов и экзамена — отлично, но пилот, который учился только на нём, при первом же боковом ветре в реальном полёте удивится.

GNS3 и EVE-NG — это **полноразмерный процедурный тренажёр с настоящей кабиной и реальными системами**: всё, что ты нажимаешь, реально срабатывает, включая ошибки и перегрев. Именно поэтому в такой тренажёр заливают «топливо» — реальные образы ОС, — и именно поэтому он требует нормального «ангара» (памяти и вложенной виртуализации).

Аналогия перестаёт работать в одном месте: тренажёр не воспроизводит **физику и кремний** — плохой патч-корд, оптику с грязным коннектором, поведение ASIC под нагрузкой, PoE-бюджет, — поэтому реальные «глюки на линии» всё равно ищутся руками и тестером, а не в GNS3.

## 4. Практика и команды

**1. Оценка ресурсов хоста перед запуском (Windows, PowerShell).**
```powershell
Get-CimInstance Win32_Processor | Select-Object Name,NumberOfCores,VirtualizationFirmwareEnabled
Get-CimInstance Win32_ComputerSystem | Select-Object TotalPhysicalMemory
Get-PSDrive C | Select-Object Used,Free
```
`VirtualizationFirmwareEnabled` = True — VT-x включён в BIOS. `TotalPhysicalMemory` в байтах: 32 ГБ ≈ 34 359 738 368. Смотри: под SIM01 отдавай не больше половины RAM хоста, иначе DC01 и FS01 начнут свопиться.

**2. Проверка GNS3-сервера с UBU01 (Linux).**
```bash
curl -s http://10.10.10.60:3080/v2/version
```
Ответ вида `{"version": "2.2.x", "local": false}` — сервер жив и отвечает по REST API v2. Если пусто — `ss -tlnp | grep 3080` на SIM01 и `systemctl status gns3` (имя юнита уточни: `systemctl list-units | grep -i gns3` `[ПРОВЕРИТЬ]`).

**3. Список проектов через API (без GUI).**
```bash
curl -s http://10.10.10.60:3080/v2/projects | jq -r '.[] | "\(.name)\t\(.status)"'
```
Удобно для автоматизации: проверить, что проект `vektor-seg` существует и остановлен (`closed`), прежде чем лезть в GUI.

**4. Packet Tracer: базовая проверка коммутации (CLI коммутатора 2960).**
```text
enable
show vlan brief
show interfaces status
```
`show vlan brief` — какие VLAN есть и какие порты в них (access-порты). `show interfaces status` — статус (`connected`/`notconnect`), VLAN, скорость/дуплекс. Смотри: порт «в VLAN 1» там, где ожидался VLAN 10 — самая частая причина «у соседа работает, у меня нет».

**5. Packet Tracer: MAC-таблица и STP.**
```text
show mac address-table
show spanning-tree vlan 10
```
В MAC-таблице один MAC не должен «прыгать» между портами. В STP смотри `Root ID` (кто корень) и `Root Port` — если корнем стал коммутатор в переговорке, топология построена неверно.

**6. MikroTik: состояние бриджа (коммутатора) и VLAN.**
```text
/interface bridge print
/interface bridge vlan print
/interface bridge port print
```
`bridge vlan print` показывает для каждого VLAN список `tagged`/`untagged` портов. Именно здесь видно, что порт забыли добавить в список tagged для VLAN 20.

**7. MikroTik: адреса и маршруты.**
```text
/ip address print
/ip route print
```
`/ip address print` — интерфейс, адрес, флаги (`D` — dynamic). `/ip route print` — маршруты, флаг `A` = active, `S` = static. Нет активного default — наружу не пойдёшь.

**8. MikroTik: диагностика L2 — таблица MAC-адресов.**
```text
/interface bridge host print
```
Вывод: MAC, VID (VLAN), интерфейс, возраст записи. Если один и тот же MAC виден на двух портах — почти наверняка петля.

**9. MikroTik: проверка связности и пути.**
```text
/ping 10.10.10.10 count=4
/tool traceroute 10.10.10.10
/ip neighbor print
```
`/ip neighbor print` (MNDP) — кто виден на канале: соседи, их MAC и версия RouterOS. Быстрый способ понять, что линк на самом деле есть.

**10. MikroTik: бэкап и перенос конфига.**
```text
/export
/export file=chr-r1-2026-02
```
`/export` печатает всю конфигурацию в CLI (её удобно копировать в `stand-log.md` или в Git); с `file=` создаёт скрипт в `/file` — восстановление одной командой `/import`.

**11. EVE-NG: проверка appliance (если выберешь его вместо GNS3).**
```bash
curl -I http://10.10.10.60/
ssh root@10.10.10.60
# на appliance:
/opt/unetlab/wrappers/unl_wrapper -a fixed   # чинит права на лабы [ПРОВЕРИТЬ]
```
`curl -I` должен вернуть `HTTP/1.1 200` или `302`. `unl_wrapper -a fixed` — пересчёт прав, лечит «лаба не запускается после копирования».

**12. Захват трафика из эмулятора (GNS3, GUI).**
Правый клик по линку → *Start capture* → файл `.pcap` попадает в проект; открываешь в Wireshark, фильтр:
```text
vlan.id == 20 && arp
```
Видно, тегируется ли кадр, какой VLAN-id реально в кадре и кто шлёт ARP. Это прямой мост к уроку 29 (анализ в Wireshark).

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия
Стенд L2 в состоянии после уроков 29–31: DC01 (10.10.10.10, AD/DNS/DHCP), FS01 (10.10.10.20), UBU01 (10.10.10.30, SSH), WIN11-CL01, WIN10-CL02. Все в VMnet8, DHCP от DC01.

Новая машина этой главы — **SIM01**: Ubuntu Server 24.04 LTS, 10.10.10.60 (вне пула DHCP 10.10.10.100–150), 4 vCPU, 6 ГБ RAM, 40 ГБ диск, роль — сервер GNS3. Она не входит в корпоративную часть стенда и служит только лабораторией. Внутри лаборатории используем **свою** адресацию: VLAN 10 → 172.16.32.0/24, VLAN 20 → 172.16.40.0/24, транзит в офис — 10.10.10.61 на CHR-R1.

Если EVE-NG нравится больше — ставь его вместо GNS3 на **ту же** SIM01 (10.10.10.60). Два appliance одновременно на домашнем хосте не поднять.

Образы: **MikroTik CHR** (бесплатный, скачивается с mikrotik.com) и встроенные в GNS3 **VPCS**. Образы Cisco IOS требуют действующего контракта — их мы не используем (см. раздел 6).

### Снапшот
VMware Workstation → ВМ → *VM → Snapshot → Take Snapshot*, имя `before-l2-032` — на **DC01** и **UBU01** (они участвуют в проверке). FS01 не меняем, но снапшот сделать не помешает. Для новой SIM01 сделай снапшот `before-l2-032` сразу после установки ОС и сети, до установки GNS3.

### Шаги

1. **Хост, проверка ресурсов.** PowerShell из п.4.1. Ожидаем: VT-x = True, свободной RAM ≥ 8 ГБ. Если меньше — снижай SIM01 до 4 ГБ и запускай не более 3 узлов.
2. **Создание SIM01.** В VMware: *Create a New Virtual Machine → ISO Ubuntu Server 24.04*, 4 vCPU, 6 ГБ, 40 ГБ, сеть VMnet8. В свойствах ВМ: *Processors → Virtualize Intel VT-x/EPT*. Ожидаем: установка проходит, ВМ грузится.
3. **Сеть и имя.** На SIM01 — статический адрес через netplan:
```yaml
# /etc/netplan/01-sim01.yaml
network:
  version: 2
  ethernets:
    ens33:
      dhcp4: false
      addresses: [10.10.10.60/24]
      routes:
        - to: default
          via: 10.10.10.2
      nameservers:
        addresses: [10.10.10.10]
```
`sudo netplan apply`. Ожидаем: `hostname` = SIM01, `ip a` показывает 10.10.10.60, `ping 10.10.10.10` идёт. Имя интерфейса уточни через `ip -br link`.
4. **Установка GNS3-сервера.** Проще всего — официальный GNS3 VM (OVA с gns3.com), импортировать в VMware и прописать ему тот же 10.10.10.60. Альтернатива — `sudo apt install gns3-server` на нашем Ubuntu `[ПРОВЕРИТЬ]` (версия пакета в 24.04 может отставать от клиента).
5. **Проверка сервера с UBU01.** `curl -s http://10.10.10.60:3080/v2/version`. Ожидаем JSON с версией — сервер доступен по сети, не только с хоста.
6. **Клиент на Windows.** Установить GNS3 GUI, *Edit → Preferences → Server → Host* = `10.10.10.60`, порт 3080. Ожидаем: в списке серверов зелёная галочка, вкладка *Servers Summary* показывает IP и версию.
7. **Импорт CHR.** Скачать с mikrotik.com раздел *Cloud Hosted Router* → образ `chr-7.x.img`. В GNS3: *Preferences → QEMU VMs → New*, имя `MikroTik-CHR`, RAM 256 МБ, 1 vCPU, адаптер `e1000`, консоль `telnet`. Ожидаем: шаблон появился в списке и запускается пустой RouterOS (логин `admin`, пароль пустой).
8. **Сборка топологии.** Проект `vektor-seg`: 2 × MikroTik-CHR (`CHR-SW`, `CHR-R1`), 2 × VPCS (`VPCS-1`, `VPCS-2`), 1 × Cloud (интерфейс VMnet8). Линки: VPCS-1–ether2 CHR-SW, VPCS-2–ether3 CHR-SW, ether1 CHR-SW–ether2 CHR-R1, ether1 CHR-R1–Cloud. Ожидаем: все узлы зелёные после Start.
9. **CHR-SW как коммутатор с VLAN.**
```text
/interface bridge add name=br-seg vlan-filtering=yes
/interface bridge port add bridge=br-seg interface=ether2 pvid=10
/interface bridge port add bridge=br-seg interface=ether3 pvid=20
/interface bridge port add bridge=br-seg interface=ether1
/interface bridge vlan add bridge=br-seg vlan-ids=10 tagged=ether1
/interface bridge vlan add bridge=br-seg vlan-ids=20 tagged=ether1
/interface bridge print
```
Ожидаем: `vlan-filtering: yes`, порты в бридже.
10. **CHR-R1 как роутер (router-on-a-stick + NAT).**
```text
/interface vlan add name=vlan10 interface=ether2 vlan-id=10
/interface vlan add name=vlan20 interface=ether2 vlan-id=20
/ip address add address=172.16.32.1/24 interface=vlan10
/ip address add address=172.16.40.1/24 interface=vlan20
/ip address add address=10.10.10.61/24 interface=ether1
/ip route add gateway=10.10.10.2
/ip firewall nat add chain=srcnat out-interface=ether1 action=masquerade
/ip address print
```
Ожидаем: три адреса со флагом `A`, маршрут `AS`.
11. **Клиенты (VPCS).** В консоли VPCS-1: `ip 172.16.32.10/24 172.16.32.1`, VPCS-2: `ip 172.16.40.20/24 172.16.40.1`, затем `save`. Ожидаем: каждая машина пингует свой шлюз.
12. **Проверка маршрутизации и выхода в офис.** С VPCS-1: `ping 172.16.40.20` (должно **не** работать — разные VLAN), `ping 10.10.10.10` (должно работать через NAT). С DC01: `ping 10.10.10.61`. Ожидаем: изоляция VLAN сохранена, офис доступен.
13. **Захват и разбор.** *Start capture* на линке CHR-SW–CHR-R1, с VPCS-1 `ping 172.16.32.1`, открыть pcap в Wireshark с фильтром `vlan.id == 10`. Ожидаем: кадры тегированы, VLAN-id 10.
14. **Фиксация.** `/export` с обоих CHR → в файл, дописать в `stand-log.md`.

### Проверка

- [ ] SIM01 отвечает: `ping 10.10.10.60` с UBU01 и с хоста.
- [ ] `curl -s http://10.10.10.60:3080/v2/version` возвращает JSON с версией.
- [ ] В GNS3 проект `vektor-seg` существует, все 5 узлов запущены.
- [ ] На CHR-SW `vlan-filtering: yes`, `ether2` pvid 10, `ether3` pvid 20, `ether1` tagged в VLAN 10 и 20.
- [ ] VPCS-1 ↔ VPCS-2 не пингуются (VLAN-изоляция работает).
- [ ] VPCS-1 пингует 10.10.10.10, на DC01 в ARP-таблице виден 10.10.10.61, а не 172.16.32.10 (NAT работает).
- [ ] pcap содержит кадры с `vlan.id == 10`.
- [ ] Конфиги `/export` сохранены, запись в `stand-log.md` сделана.

**Диагностика по порядку:**
1. С VPCS-2: `ping 172.16.40.1` — не идёт. Локальный шлюз недоступен → проблема не в «1С», а в L2.
2. `ping 172.16.32.10` с VPCS-2 — тоже не идёт, хотя VLAN 10 живой. Значит, вопрос не в клиенте.
3. На CHR-SW: `/interface bridge port print` — порт `ether3` в бридже, pvid 20. Локально всё верно.
4. `/interface bridge vlan print` — вот она: VLAN 20 не помечен на `ether1`. Трафик склада не может уйти в транк.
5. Подтверждаем capture: *Start capture* на `ether1`, с VPCS-2 `ping 172.16.40.1`, в Wireshark фильтр `vlan.id == 20`. Кадров нет вообще — трафик режется на egress.
6. Контрольная проверка «с другой стороны»: с CHR-R1 `/interface vlan print` — интерфейс vlan20 есть и up, но пакетов нет.

**Решение.** Вернуть тег:
```text
/interface bridge vlan set [find vlan-ids=20] tagged=ether1
```
Проверить: с VPCS-2 `ping 172.16.40.1`, `ping 10.10.10.10`, `/interface bridge host print` на CHR-SW — MAC VPCS-2 в VID 20 на ether3.

**Ответ пользователю:** «Алексей, проблема была в настройке транка между коммутаторами: трафик склада не передавался дальше первого коммутатора, поэтому не открывались ни папка, ни 1С. Исправил, проверил — склад снова видит общие ресурсы. Если повторится — сразу звоните, это правится за пару минут».

**Закрытие заявки:** категория «Сеть / Коммутация», решение — «исправлена конфигурация VLAN на транке», корневая причина — «VLAN 20 отсутствовал в списке tagged на аплинке», профилактика — «сохранить конфиг в Git и добавить проверку `bridge vlan print` в чек-лист изменений».

### Что изменилось на стенде

- Добавлена ВМ **SIM01** — Ubuntu 24.04 LTS (или GNS3 VM), 10.10.10.60, 4 vCPU / 6 ГБ / 40 ГБ, VMnet8, роль — сервер эмуляции (GNS3 на порту 3080 либо EVE-NG на 80/22).
- В GNS3 создан проект **`vektor-seg`**: CHR-SW (bridge, VLAN 10/20), CHR-R1 (vlan10/vlan20 + NAT), VPCS-1, VPCS-2, Cloud→VMnet8.
- Адресация лаборатории (добавлена этой главой, в корпоративной части стенда не используется): 172.16.32.0/24 — VLAN 10, 172.16.40.0/24 — VLAN 20, транзит CHR-R1 = **10.10.10.61/24** (вне DHCP-пула DC01).
- На DC01/FS01/UBU01 изменений нет; на DC01 видна ARP-запись 10.10.10.61.

- Ранее созданные GW01 (10.10.10.3 / 10.10.20.1) и WEB01 не затрагивались — их темы идут в уроках 35 и 38.

### Откат

## 6. Ошибки новичков и безопасность

1. **Тянуть в лабу образы Cisco IOS «из интернета».** → Нарушение лицензии и риск получить образ с закладкой. → Правильно: легальные образы — MikroTik CHR (бесплатный), VyOS, FRR, Linux, Arista/Nokia в их free-программах `[ПРОВЕРИТЬ актуальность условий]`. IOS — только при наличии контракта.
2. **Забыть про вложенную виртуализацию.** → QEMU в режиме эмуляции, лаба «висит», таймеры STP плывут. → Включить *Virtualize Intel VT-x/EPT* и проверить, что Hyper-V/WSL2 не мешают VMware.
3. **Соединить лабораторию с VMnet8 «как есть», да ещё с DHCP-сервером внутри.** → Rogue DHCP начнёт раздавать адреса WIN11-CL01/WIN10-CL02, в офисном сегменте появится второй шлюз, пользователи «потеряют сеть». → Только статическая адресация в лабе, никаких DHCP-серверов на bridged-интерфейсе; в идеале — отдельный host-only сегмент, а не VMnet8.
4. **Оставить CHR с пустым паролем admin.** → Winbox открыт всем в сети, RouterOS превращается в чужой роутер. → Первым делом `/user set admin password=...` (на стенде — учебный пароль) и закрыть input-chain файрволом; в лабе, доступной из VMnet8, это обязательно.
5. **Packet Tracer как единственная практика.** → На собеседовании сыпятся вопросы про реальные таймеры, поведение при сходимости STP, отсутствующие команды. → PT — для базы и схем, GNS3/EVE-NG — для реальной диагностики.
6. **Копировать MAC-адреса и клонировать запущенные ВМ.** → Дубли MAC, «мигающая» таблица коммутации, непонятные потери. → В GNS3 не клонировать запущенные QEMU-узлы, при переносе проекта перегенерировать MAC.
7. **Оставить EVE-NG с дефолтным root/eve.** → Полный контроль над appliance по SSH. → Сменить пароли сразу после установки, не публиковать appliance в интернет.
8. **Работать без снапшота.** → Испорченный конфиг не откатить, а «пересобрать» — полдня. → Снапшот `before-l2-<номер>` до любых действий, конфиги — в файл после.

**Безопасность.** Всё, что делает лабу удобной, в боевой среде — дыра: bridge лабораторной сети в офисный VLAN без контроля, NAT «наружу» из тестового сегмента, отключённый файрвол на тестовом роутере, дефолтные пароли appliance. Правило: эмулятор живёт в отдельном сегменте, наружу — только то, что нужно, пароли — до первого запуска. Отдельно: не запускай симулятор с bridged-адаптером на рабочем ноутбуке в кафе — это открытый порт 3080 на всю локальную сеть.

## 7. Вопросы на собеседовании

**1. Чем симулятор отличается от эмулятора и что выберешь для диагностики инцидента?**
Ответ: симулятор (Packet Tracer) моделирует поведение устройств упрощённо, без реальной ОС — годится для обучения и быстрых схем. Эмулятор (GNS3, EVE-NG) запускает настоящие образы ОС в QEMU/KVM, поэтому воспроизводит реальные таймеры, баги и версии ПО. Для инцидента — эмулятор; для «показать схему коллеге» — можно и PT.
*Что хочет услышать:* понимание, что PT не покажет реальное поведение, и что образы — отдельная тема с лицензиями.
*Красный флаг:* «PT и GNS3 — одно и то же, просто интерфейс разный».

**2. Как связать эмулируемую сеть с реальной и какие риски?**
Ответ: узел Cloud (GNS3) / Cloud-сеть (EVE-NG), привязанный к физическому или VM-интерфейсу хоста; в моей лабе — VMnet8 на SIM01. Риски: широковещательный шторм и STP-петля выйдут в прод, rogue DHCP, утечка внутренней адресации. Меры: статика, точечный firewall, отдельный VLAN/сегмент, NAT, никаких broadcast-протоколов наружу.
*Что хочет услышать:* что ты думаешь о последствиях до того, как нажать Start.
*Красный флаг:* «просто соединяю бриджем и всё».

**3. MikroTik: как сделать из роутера коммутатор с VLAN и в чём разница между bridge VLAN filtering и /interface vlan?**
Ответ: `/interface bridge` с `vlan-filtering=yes` — это L2-коммутация: `bridge port` задаёт pvid (access), `bridge vlan` — tagged/untagged список портов (транк). `/interface vlan` — это L3-интерфейс поверх физического/бриджевого, чтобы повесить IP на конкретный VLAN (router-on-a-stick). Первое — про кадры, второе — про пакеты.
*Что хочет услышать:* чёткое разделение L2/L3.
*Красный флаг:* «в RouterOS VLAN настраивается только через /interface vlan».

**4. Лаба тормозит, узлы не стартуют. Что проверяешь?**
Ответ: хост — RAM и вложенная виртуализация (VT-x), конфликт Hyper-V/WSL2; сервер — количество и вес узлов, `top`/`ps` по qemu, свободный диск под образы; сеть — не включён ли лишний захват трафика и не раздулся ли pcap. Оптимизация: меньше узлов, 256 МБ на CHR, лёгкие VPCS вместо полноценных ОС, не держать запущенными все проекты.
*Что хочет услышать:* системный порядок проверки, а не «перезагрузил — заработало».
*Красный флаг:* «GNS3 всегда тормозит, это нормально».

**5. Почему нельзя просто скачать образ Cisco IOS и как тогда строить лабу легально?**
Ответ: образы IOS — лицензируемое ПО, право использования даёт контракт с Cisco (обычно через Smart Account); скачивание с торрентов — нарушение лицензии и риск вредоносного кода. Легально: PT через NetAcad (доступность из РФ ограничена), эмуляторы с открытыми/бесплатными образами — MikroTik CHR (free-лицензия с ограничением скорости `[ПРОВЕРИТЬ актуальные условия]`), VyOS, FRR, Linux, free-программы вендоров. Синтаксис Cisco учится по документации и PT.
*Что хочет услышать:* что ты не потащишь в компанию «серую» лабу и знаешь альтернативы.
*Красный флаг:* «да все так делают, образы есть на торрентах».
