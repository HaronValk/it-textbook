# Управление дисками в Linux: LVM, ext4/XFS, fstab, расширение томов, мониторинг

## 1. Введение (зачем это нужно в реальной работе)

**Тикет #4821. Пользователь:** sidorov (склад) — работает через интеграцию с тестовым сервером. **ВМ:** UBU01 (10.10.10.30). **Что написал:** «Выгрузка накладных на сервер падает с ошибкой `upload failed: No space left on device`. Второй день, склад не может закрыть смену». **Срочность:** высокая.

Через полчаса выясняется: место на диске действительно закончилось, но `du` показывает, что папка почти пустая. Классика. Именно такими заявками и живёт L2: «диск полный», «сервер не загрузился после правки fstab», «надо расширить раздел, перезагрузка запрещена», «приложение тормозит на записи».

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Диск в Linux — это многослойный пирог. Каждый слой можно менять независимо, и большинство аварий происходит на стыке слоёв.

```text
+------------------------------------------------------------------+
| Приложение: пишет /srv/app/upload.csv                            |
+------------------------------------------------------------------+
| VFS — виртуальная файловая система ядра (единый интерфейс)       |
+------------------------------+-----------------------------------+
| ext4: журнал, фикс. inode,   | XFS: allocation groups,           |
| блоки 4К, 5% резерв root     | динамические inode, параллелизм   |
+------------------------------+-----------------------------------+
| LV lv_app (3G)               | LV lv_logs (10G)                  |
+------------------------------+-----------------------------------+
|        VG vg_data — общий пул: 10G (/dev/sdb) + 5G (/dev/sdc)    |
+------------------------------------------------------------------+
| PV /dev/sdb (10G)            | PV /dev/sdc (5G)                  |
+------------------------------------------------------------------+
| Блочный слой ядра: драйвер vmw_pvscsi, /dev/sd*, udev            |
+------------------------------------------------------------------+
| VMware Workstation: виртуальные диски .vmdk на вашем ПК          |
+------------------------------------------------------------------+
```

**LVM** (Logical Volume Manager) — прослойка через device-mapper. PV (physical volume) — диск или раздел, отданный в LVM. VG (volume group) — пул, собранный из PV; его размер = сумма PV. LV (logical volume) — «кусок» пула, который выглядит для ОС как обычный блочный диск `/dev/vg_data/lv_app`. PE (physical extent) — минимальная единица нарезки, по умолчанию 4 МиБ. Главная сила: LV можно расширять «в горячем режиме» и добавлять новые диски в VG без переразметки.

**Файловая система** решает, как данные лежат поверх блока: ext4 (журналируемая, inode фиксируются при `mkfs`, можно уменьшать только offline), XFS (несколько allocation groups — параллельная запись в разные зоны, inode динамические, уменьшать нельзя вообще). В РФ-реалиях важно: ext4 — дефолт Ubuntu, XFS — дефолт RHEL-семейства (РЕД ОС, ALT), обе живы и востребованы.

**Монтирование**: ядро через VFS привязывает ФС к каталогу. `/etc/fstab` читается при загрузке, `systemd-fstab-generator` превращает каждую строку в unit вида `srv-app.mount`. Ошибка в fstab = сервер уходит в emergency mode. Формат строки: `устройство точка_монтирования тип опции dump pass`, где `pass` = порядок fsck (0 — не проверять, 1 — корень, 2 — остальные ext4; для XFS ставят 0).

**Порты тут ни при чём** — это локальный стек ядра. Сеть появляется только когда вы монтируете NFS/SMB (это главы 48 и 58 трека).

## 3. Аналогия из жизни

Представьте склад компании «Вектор». **PV** — это физические стеллажи, которые привезли и поставили в помещение. **VG** — всё свободное пространство склада целиком, без разметки «этот стеллаж под бухгалтерию». **LV** — зона, которую вы отгородили и подписали «Отдел закупок, 3 метра». **Файловая система** — стеллажи и полки внутри зоны: ext4 аккуратно нумерует каждую ячейку заранее и ведёт журнал приёмки, XFS ставит несколько бригад грузчиков, которые работают в разных концах зоны параллельно и не мешают друг другу. **fstab** — табличка на входе: «зона закупок — второй поворот налево, ключ у кладовщика». Если табличку перепутать, утром склад не откроется вообще.

Аналогия перестаёт работать в одном месте: у реального диска есть отказы, задержки и лимит одновременно открытых файлов — и именно эти детали и создают 90% инцидентов.

## 4. Практика и команды

Все команды — на **UBU01** (10.10.10.30), через SSH под своей учёткой с `sudo`.

**1. Посмотреть текущую картину дисков**
```bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,LABEL,MOUNTPOINTS
```
`-o` — список колонок. Смотрим: какие есть диски (`disk`), разделы (`part`), есть ли `lvm` в FSTYPE, куда смонтировано. Это первая команда при любой заявке про диск.
```text
NAME        SIZE TYPE FSTYPE      MOUNTPOINTS
sda          20G disk
├─sda1        1G part vfat        /boot/efi
└─sda2       19G part LVM2_member
  └─ubuntu--vg-ubuntu--lv 19G lvm ext4  /
sdb          10G disk
```

**2. Занятое место и inode**
```bash
df -hT
df -i
```
`-h` — человекочитаемо, `-T` — с типом ФС, `-i` — inode вместо байт. Смотреть на `Use%`. Если `df -h` показывает 100%, а `df -i` — 100% при свободных байтах, значит кончились inode (на ext4 их количество задано при создании ФС и не меняется).

**3. Кто реально занял место**
```bash
sudo du -xhd1 /srv/app | sort -h
```
`-x` — не уходить на другие ФС, `-h` — человекочитаемо, `-d1` — глубина 1 (только первый уровень). Дальше спускаемся в самый жирный каталог. `sort -h` сортирует по размеру.

**4. Крупные файлы и «удалённые, но открытые»**
```bash
sudo find /srv -xdev -type f -size +500M -exec ls -lh {} \;
sudo lsof +L1 2>/dev/null | grep -i deleted
```
`+L1` в lsof — файлы с числом ссылок меньше 1, то есть уже удалённые, но удерживаемые процессом. Это ответ на загадку «df полный, du пустой».

**5. LVM: посмотреть пулы и тома**
```bash
sudo pvs; sudo vgs; sudo lvs
```
`pvs` — физические тома и сколько на них свободно внутри VG (`PFree`), `vgs` — пулы (`VFree` — сколько ещё можно нарезать), `lvs` — логические тома. Смотреть `VFree`: если он не нулевой, расширять LV можно прямо сейчас.
```text
  VG      #PV #LV #SN Attr   VSize   VFree
  vg_data   2   2   0 wz--n- <15.00g  2.00g
```

**6. Создать LVM-том с нуля**
```bash
sudo wipefs -a /dev/sdb
sudo pvcreate /dev/sdb
sudo vgcreate vg_data /dev/sdb
sudo lvcreate -L 2G -n lv_app vg_data
```
`wipefs -a` стирает старые подписи ФС/RAID — обязательный шаг, иначе `pvcreate` откажется. `-L 2G` — размер, `-n` — имя. Путь тома: `/dev/vg_data/lv_app`.

**7. Создать файловые системы**
```bash
sudo mkfs.ext4 -L app /dev/vg_data/lv_app
sudo mkfs.xfs  -L logs /dev/vg_data/lv_logs      # нужен пакет xfsprogs
```
`-L` — метка, удобно для людей и для fstab `LABEL=app`. На Ubuntu XFS может отсутствовать: `sudo apt install -y xfsprogs`.

**8. Смонтировать и проверить**
```bash
sudo mkdir -p /srv/app /srv/logs
sudo mount /dev/vg_data/lv_app /srv/app
findmnt /srv/app
df -hT /srv/app
```
`findmnt` показывает смонтированное в виде дерева и сразу печатает опции — быстрее, чем `mount | grep`.

**9. Прописать в fstab по UUID и проверить**
```bash
sudo blkid /dev/vg_data/lv_app
sudo cp /etc/fstab /etc/fstab.bak
sudo nano /etc/fstab
```
```text
UUID=6f1c...e2 /srv/app  ext4 defaults,nofail 0 2
UUID=a83d...71 /srv/logs xfs  defaults,nofail 0 0
```
```bash
sudo systemctl daemon-reload
sudo findmnt --verify --verbose
sudo mount -a
```
`nofail` — сервер загрузится, даже если том недоступен (иначе emergency mode). `mount -a` монтирует всё из fstab: если команда прошла без ошибок — синтаксис верный. Обязательно проверяйте до перезагрузки и держите вторую SSH-сессию открытой.

**10. Расширить том без перезагрузки**
```bash
sudo vgextend vg_data /dev/sdc                 # добавили диск в пул
sudo lvextend -r -L +1G /dev/vg_data/lv_app    # +1 гигабайт
sudo lvextend -r -l +100%FREE /dev/vg_data/lv_logs
```
`-r` (resize) — сразу подтянуть ФС через fsadm: для ext4 вызовется `resize2fs`, для XFS — `xfs_growfs`. Без `-r` вы расширите только том, а `df` не изменится. `-l` — в extent'ах, `+100%FREE` — забрать весь остаток пула. Вручную то же самое: `resize2fs /dev/vg_data/lv_app` или `xfs_growfs /srv/logs` (именно точка монтирования, не устройство).

**11. Параметры ФС и свободное место для root**
```bash
sudo tune2fs -l /dev/vg_data/lv_app | grep -Ei 'Block count|Inode count|Reserved'
sudo xfs_info /srv/logs
```
ext4 по умолчанию держит 5% блоков «под root» — на большом томе это десятки гигабайт, которые не видит обычный пользователь. Меняется через `tune2fs -m 1`.

**12. Мониторинг нагрузки на диск и ошибок ядра**
```bash
sudo apt install -y sysstat
iostat -x 1 3
vmstat 1 5
sudo journalctl -k --since "1 hour ago" | grep -iE 'i/o error|ext4|xfs|sd[b-z]'
```
`iostat -x` — расширенная статистика: смотрим `%util` (загрузка устройства), `await` (средняя задержка, мс) и `r/s`,`w/s`. `vmstat` — колонки `bi/bo` (блоки ввода/вывода) и `wa` (время ожидания I/O). `journalctl -k` — сообщения ядра; `I/O error` и `remounting filesystem read-only` — признак проблем со слоем хранения.

**Аналоги в Windows** (для сравнения, пригодится на L1-заявках): `Get-Volume`, `Get-Partition`, `Get-Disk`, `Resize-Partition`, GUI — `diskmgmt.msc`. Понятия те же, инструменты другие.

### Сломай и почини
**Пользователь:** sidorov (склад) / **ВМ:** UBU01 (10.10.10.30) / **Что написал:** «Выгрузка накладных на сервер падает: `upload failed: No space left on device`. Второй день, склад не может закрыть смену» / **Срочность:** высокая.

**Как воспроизвести поломку** (на UBU01, от `sudo`):
```bash
sudo dd if=/dev/zero of=/srv/app/hold.img bs=1M count=2900 status=none
sudo python3 -c "import time; f=open('/srv/app/hold.img','rb'); time.sleep(7200)" &
sudo rm -f /srv/app/hold.img
df -hT /srv/app     # 100%
du -sh /srv/app     # почти ноль
```

**Диагностика по порядку:**
1. `df -hT` — `/srv/app` занят на 100%, тип ext4. Проблема подтверждена.
2. `df -i /srv/app` — inode свободны. Значит, дело не в количестве файлов.
3. `sudo du -xhd1 /srv/app` — суммарно десятки мегабайт. **Расхождение df и du** — ключевая улика.
4. `sudo lsof +L1 | grep -i hold` — видим удалённый файл `hold.img` размером ~2.9G, удерживаемый процессом `python3` (PID).
5. `ps -fp <PID>`, `sudo ls -l /proc/<PID>/fd | grep hold` — убеждаемся, что это тот самый процесс и файл, а не системный демон.
6. `sudo journalctl --since "2 days ago" | grep -i 'no space'` — подтверждаем время начала инцидента.

**Решение:**
```bash
sudo kill <PID>
df -hT /srv/app     # место освободилось
```
**Ответ пользователю:** «Проблема найдена: место на сервере занимал удалённый файл, который удерживал зависший процесс. Освободили ~2.9 ГБ, выгрузка работает. Причина — отсутствие контроля свободного места; ставим триггер на 80% и разносим выгрузки и логи по разным томам».
**Закрытие заявки:** категория «Диски/место», корневая причина — «удалённый файл, удерживаемый процессом + нет мониторинга порога», действие — «профилактика: триггер Zabbix, logrotate, отдельный LV под uploads».

## 6. Ошибки новичков и безопасность

1. **fstab по `/dev/sdb1` вместо UUID** → после добавления диска или изменения порядка устройство переименуется, сервер уйдёт в emergency mode → всегда `UUID=` или `LABEL=`, проверка через `blkid`.
2. **Правка fstab без проверки и без второй сессии** → незагружающийся сервер → `mount -a` + `findmnt --verify` до перезагрузки, `nofail` для некритичных томов, резервная копия файла. Если уже сломались: в emergency mode — `mount -o remount,rw /`, правим fstab, `systemctl reboot`.
3. **`lvextend` без `-r`** → том вырос, а `df` показывает старый размер → всегда `lvextend -r` (или руками `resize2fs`/`xfs_growfs`).
4. **Попытка уменьшить XFS** → «операция не поддерживается», в худшем случае потеря данных → XFS только растёт; если нужно уменьшить — создаём новый том, копируем, переключаем.
5. **`mkfs` не на том устройстве** → мгновенная потеря данных → перед `mkfs` всегда `lsblk -f` и `wipefs -n`, работать по путям `/dev/vg_data/lv_*`, а не `/dev/sdX`.
6. **Смотреть только `df -h`** → пропускаем исчерпание inode → всегда рядом `df -i`.
7. **Удалил файл — место не освободилось** → причина в открытом файловом дескрипторе → `lsof +L1`, перезапуск сервиса, а не «перезагрузим сервер».
8. **Нет мониторинга места** → узнаём о проблеме от пользователя в 18:40 в пятницу → триггер на 80%/90%, алерт на почту/в Telegram.

### Безопасность
- **`mkfs`, `wipefs`, `parted` необратимы.** В боевой среде перед любой операцией — бэкап и подтверждение от владельца сервиса. На стенде страхует снапшот, в продакшене снапшота нет.
- **LVM-снапшот — не резервная копия.** Он живёт на тех же дисках; умрёт вместе с массивом.
- **`noexec,nosuid,nodev`** для томов с пользовательскими данными (`/srv/app`) — снижает риск запуска занесённого бинарника.
- **Не расширяйте права на `/srv/*` «чтобы работало»** (chmod 777). Правильно — группа и ACL, как в главе 51.
- **Шифрование**: LVM без LUKS = данные читаются при изъятии диска. Для ноутбуков и серверов с ПДн это критично (152-ФЗ), в лабе не делаем — это отдельная тема.
- **Не отключайте fsck и не ставьте `pass=0` корню** — молчаливые ошибки ФС лечатся только с потерей данных.

## 7. Вопросы на собеседовании

**1. «На сервере `df` показывает 100%, а `du` по тому же разделу — 20%. В чём дело?»**
Ответ: три классические причины. (а) Удалённые файлы, удерживаемые процессом: место не освобождается, пока дескриптор открыт — ищем `lsof +L1` и перезапускаем процесс. (б) Файлы в смонтированных поверх каталогах — `du` не видит скрытое под точкой монтирования, помогает `mount --bind / /mnt/root` и проверка оттуда. (в) Зарезервированные блоки ext4 (5% под root) — `tune2fs -m`. Плюс проверка `df -i`: возможно, кончились inode.
*Что хочет услышать интервьюер:* что вы знаете про открытые дескрипторы, а не просто «почистите логи».
*Красный флаг:* «перезагрузим сервер» как первый ответ.

**2. «Как расширить корневой LVM-раздел на работающем сервере без перезагрузки?»**
Ответ: проверить свободное место в VG (`vgs`, `VFree`), если мало — добавить диск и `vgextend`. Затем `lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv`. Ключ `-r` вызывает `resize2fs` для ext4 или `xfs_growfs` для XFS онлайн. Для корня на ext4 это безопасно, ФС остаётся смонтированной; `df` меняется сразу. Если раздел был создан как обычный (не LVM) — сначала `growpart`, потом `pvresize`, и только затем `lvextend`.
*Что хочет услышать:* порядок «диск → PV → VG → LV → ФС» и знание `-r`/`pvresize`.
*Красный флаг:* «нужно загрузиться с live-CD» для LVM-корня.

**3. «Чем ext4 отличается от XFS и что выберете для файлового сервера и для базы?»**
Ответ: ext4 — журналируемая ФС с фиксированным числом inode, умеет уменьшаться offline (`resize2fs` после `e2fsck -f`), эталонно стабильна, дефолт Ubuntu. XFS — allocation groups (параллельная запись), динамические inode, отлично работает с большими файлами и высокой параллельной нагрузкой, но уменьшать нельзя, только расти. Для файлового сервера с разнородными мелкими файлами — скорее ext4 (или XFS, если много параллельных клиентов); под PostgreSQL/MySQL и большие объёмы — XFS. В РФ: РЕД ОС и ALT по умолчанию используют XFS, Ubuntu — ext4.
*Что хочет услышать:* понимание, что выбор зависит от профиля нагрузки, и что XFS не уменьшается.
*Красный флаг:* «XFS быстрее, поэтому всегда XFS» без аргументов.

**4. «Что будет, если в `/etc/fstab` опечатка? Как подстраховаться?»**
Ответ: при загрузке `systemd-fstab-generator` создаст `.mount`-юнит, он упадёт, корневая ФС может уйти в `emergency mode` — сервер недоступен, нужен консольный доступ (в VM — через консоль VMware, в железе — IPMI/KVM). Подстраховка: правку делать с открытой второй SSH-сессией, проверять `mount -a` и `findmnt --verify` до перезагрузки, для некритичных томов добавлять `nofail` и `x-systemd.device-timeout=10`, хранить `/etc/fstab.bak`. Восстановление: в emergency mode `mount -o remount,rw /`, правим файл, `systemctl reboot`.
*Что хочет услышать:* что вы понимаете механизм (fstab → systemd units), а не просто «проверю глазами».
*Красный флаг:* «fstab не критичен, всегда загрузится».

**5. «Как вы мониторите диски и что настроите в Zabbix?»**
Ответ: два уровня. Метрики ОС: `vfs.fs.size[/,pfree]` по каждому важному тому с триггерами <20% (warning) и <10% (high), обязательно `vfs.fs.inode[/,pfree]`, скорость роста (`Change per second`) для прогноза «когда кончится». Метрики производительности: `%util`, `await`, `iops` (через `iostat`/Zabbix agent), плюс `vm.dirty_ratio`. Логи — `journalctl -k` на `I/O error` и переход ФС в read-only. Плюс отдельно — SMART-статус физических дисков (`smartctl`) на железе; в VMware SMART недостоверен, там смотрим на алерты гипервизора.
*Что хочет услышать:* не только «свободное место», но и inode, тренд и деградацию I/O.
*Красный флаг:* «поставим алерт на 90%, этого хватит».
