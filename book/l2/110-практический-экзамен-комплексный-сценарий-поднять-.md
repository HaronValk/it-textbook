# Практический экзамен: комплексный сценарий «Поднять инфраструктуру компании с нуля» на виртуалках

## 1. Введение (зачем это нужно в реальной работе)

Тикет в учебной системе от Петровой (HR, WIN10-CL02):

> «Мария Петрова / WIN10-CL02 / Нужен внутренний портал с документами для сотрудников: чтобы открывался из офиса, чтобы вы узнавали о падении раньше нас, и чтобы был второй контроллер домена — если один упадёт, чтобы домен жил. Срок — завтра. / Срочность: высокая»

За этой формулировкой — весь L2-трек целиком: сеть, маршрутизация, DNS, домен, файлы, веб-сервис, мониторинг и приёмка. На собеседованиях L2 и на испытательном сроке ровно это и проверяют: не «знаете ли вы команду `dcdiag`», а умеете ли вы за отведённое время спроектировать, поднять, проверить и задокументировать контур так, чтобы он не развалился через час. Работодателю нужен человек, который может пройти путь «план → снапшот → развёртывание → проверка → документ → откат».

После этой главы вы сможете: разложить задачу «поднять инфраструктуру» по слоям, написать критерии приёмки и защитить их руками, диагностировать отказ по уровням (сеть → маршрут → порт → сервис → клиент), не сломать стенд насмерть и уложиться в таймбокс. Это генеральная репетиция перед собеседованием и перед первым боевым проектом.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Любая инфраструктура «с нуля» строится слоями. Нижний слой не работает — верхний бессмысленно проверять.

```text
        VMware NAT 10.10.10.2 (выход в интернет)
                    |
[VMnet8 10.10.10.0/24]                    [VMnet10 10.10.20.0/24]
  DC01  .10  (AD DS, DNS, DHCP)            WEB01  .10  (nginx :80)
  DC02  .11  (AD DS реплика, DNS)              |
  FS01  .20  (SMB :445, печать)                |
  SRV1C01 .25 (учебная 1С)                     |
  UBU01 .30, ASTRA01 .31                       |
  MON01 .40 (Zabbix server :10051, агенты :10050)
  WIN11-CL01 / WIN10-CL02 (DHCP 10.10.10.100-150)
                    \                          /
                     +---- GW01 .3 --- .1 ----+
                        (маршрут + nftables)
```

Слой 0 — гипервизор и виртуальные сети: VMnet8 даёт офису NAT, VMnet10 — изолированную DMZ. Слой 1 — адресация и имена: DHCP (UDP 67/68) выдаёт адрес, шлюз и DNS; DNS (UDP/TCP 53) превращает имена в адреса. Слой 2 — домен: LDAP 389, Kerberos 88, SMB 445, RPC 135 + динамические порты, репликация между DC01 и DC02. Слой 3 — сервисы: HTTP 80 на WEB01, Zabbix на MON01. Слой 4 — маршрутизация и фильтрация между офисом и DMZ на GW01 (ядро Linux, `net.ipv4.ip_forward=1`, nftables в таблицах `filter` и `nat`).

Ключевая мысль экзамена: между офисом и DMZ по умолчанию **нет** маршрута. Трафик из `10.10.10.0/24` в `10.10.20.0/24` должен пройти три проверки: у клиента есть маршрут через шлюз, у GW01 включена пересылка, в nftables разрешён `forward`. Ломается обычно одно из трёх — и диагностика идёт строго по этому порядку.

Второй важный принцип — **критерии приёмки**. «Работает» — не критерий. Критерий: «с WIN11-CL01 по имени `web01.corp.vektor.lab` открывается страница с кодом 200, в Zabbix хост в статусе Enabled и есть свежие данные, при остановке nginx через 5 минут появляется проблема». Это можно проверить и показать.

## 3. Аналогия из жизни

Вы сдаёте заказчику новый офис. Сначала проверяют фундамент и электрику (сеть и адресация), потом подключают воду и отопление (DNS, DHCP — без них «жизни» нет), ставят охрану на входе (маршрутизатор и файрвол), затем сдают помещения арендаторам (AD, файлы, портал), ставят камеры и датчики дыма (мониторинг) и только после этого подписывают акт приёмки с чек-листом. И отдельно — аварийный выход и план эвакуации (снапшоты и откат). Аналогия перестаёт работать в одном месте: в офисе нельзя «отмотать» день назад, а в виртуалке — можно, и это меняет всю тактику рискованных изменений.

## 4. Практика и команды

**1. Снапшот машины без GUI** (все команды — с хоста, в PowerShell):
```powershell
& "C:\Program Files (x86)\VMware\VMware Workstation\vmrun.exe" -T ws list
& "C:\Program Files (x86)\VMware\VMware Workstation\vmrun.exe" -T ws snapshot "D:\VM\GW01\GW01.vmx" before-l2-110
```
`-T ws` — тип продукта Workstation; `list` — список запущенных ВМ; `snapshot <vmx> <имя>` — снять снапшот. Путь к `vmrun.exe` зависит от версии и разрядности — `[ПРОВЕРИТЬ]` у себя. Смотреть: команда завершилась без вывода = успех.

**2. Проверка адресации и маршрутов на Linux (GW01):**
```bash
ip -br a
ip r
```
`-br` — сокращённый вывод, `a` — адреса. Ожидаемо: два интерфейса с `10.10.10.3/24` и `10.10.20.1/24`, в таблице маршрутов `default via 10.10.10.2` и строка `10.10.20.0/24 dev <if2>`. Смотрим: не перепутаны ли сети на адаптерах.

**3. Включение пересылки пакетов:**
```bash
echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-vektor-forward.conf
sudo sysctl --system
sysctl net.ipv4.ip_forward
```
Без `ip_forward=1` ядро примет пакет и молча выбросит. Вывод `net.ipv4.ip_forward = 1` — включено. Файл в `sysctl.d` нужен, чтобы настройка выжила после ребута.

**4. Посмотреть правила nftables и счётчики:**
```bash
sudo nft list ruleset
sudo nft -a list chain inet filter forward
```
`-a` — показать handles (по ним удаляют/правят правила). Смотрим на `policy drop` и на счётчики `counter packets N bytes M`: счётчик растёт — правило работает, стоит на нуле — трафик до него не доходит.

**5. Минимальный рабочий ruleset для GW01** (записать в `/etc/nftables.conf`):
```bash
#!/usr/sbin/nft -f
flush ruleset

table inet filter {
  chain input {
    type filter hook input priority filter; policy drop;
    iif lo accept
    ct state established,related accept
    ip protocol icmp accept
    tcp dport 22 accept
  }
  chain forward {
    type filter hook forward priority filter; policy drop;
    ct state established,related accept
    ip saddr 10.10.10.0/24 ip daddr 10.10.20.10 tcp dport 80 accept
  }
}
table inet nat {
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    ip saddr 10.10.20.0/24 oifname "<vmnet8-if>" masquerade
  }
}
```
Имена интерфейсов подставьте свои из `ip -br a`. Применить: `sudo nft -f /etc/nftables.conf && sudo systemctl enable --now nftables`. `ct state established,related` обязателен — иначе ответные пакеты не вернутся.

**6. Проверка порта с Linux:**
```bash
nc -zv 10.10.20.10 80
ss -tulpn | grep -E ':(80|443|10050|10051) '
```
`nc -z` — только подключиться, без данных; `-v` — рассказать. Ожидаемо `succeeded!`. `ss -tulpn` показывает, кто слушает порт (`-t` TCP, `-u` UDP, `-l` listen, `-p` процесс). Если порт слушает только `127.0.0.1` — снаружи не достучитесь, это частая причина.

**7. Проверка доступности с Windows-клиента:**
```powershell
Test-NetConnection web01.corp.vektor.lab -Port 80
Test-NetConnection 10.10.20.10 -Port 80
Resolve-DnsName web01.corp.vektor.lab
```
Смотрим `TcpTestSucceeded : True` и `IPAddress`. Сравнение «по имени» и «по IP» — базовый приём разделения проблем DNS и проблем сети.

**8. Здоровье домена:**
```cmd
dcdiag /test:dns /v
repadmin /replsummary
netdom query fsmo
```
`dcdiag` проверяет DC, `/test:dns` — только DNS-тесты, `/v` — подробно. `repadmin /replsummary` показывает расхождение репликации (в норме `largest delta` — минуты, не часы). `netdom query fsmo` — кто держит роли FSMO. Смотреть: нет ли ошибок по DNS и репликации.

**9. DHCP и выданные адреса:**
```powershell
Get-DhcpServerv4Scope
Get-DhcpServerv4Lease -ScopeId 10.10.10.0
Get-DhcpServerv4OptionValue -ScopeId 10.10.10.0
```
Первая — список областей (пул 10.10.10.100–150), вторая — активные аренды, третья — опции (шлюз 003, DNS 006). Смотреть: клиенты в пуле, а не «где-то».

**10. Файловые права и доли:**
```powershell
Get-SmbShare
Get-SmbShareAccess -Name Buh
icacls \\FS01\Buh
```
`Get-SmbShareAccess` — права на уровне шары, `icacls` — NTFS. Итоговое право = пересечение обоих. Классика: в шаре доступ есть, в NTFS нет — «папка не открывается».

**11. Проверка агента и сервера мониторинга (MON01):**
```bash
systemctl status zabbix-server --no-pager
zabbix_get -s 10.10.10.30 -k agent.ping
```
`zabbix_get` спрашивает агента на UBU01 (порт 10050) по ключу `agent.ping`; ответ `1` — агент жив. Смотреть: версия Zabbix и путь конфига агента (`zabbix-agent2` → `/etc/zabbix/zabbix_agent2.conf`) `[ПРОВЕРИТЬ актуальную LTS-версию]`.

**12. Веб-сервис:**
```bash
sudo nginx -t
curl -I http://10.10.20.10
sudo journalctl -u nginx -n 20 --no-pager
```
`nginx -t` — проверка синтаксиса конфига без перезапуска; `curl -I` — только заголовки (ждём `HTTP/1.1 200 OK`); журнал покажет, доходят ли запросы вообще. Нет строк в access-логе при «не открывается» — проблема не в nginx, а до него.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

Экзамен на 3 часа: этап 1 — сеть и маршрут (40 мин), этап 2 — сервисы (50 мин), этап 3 — проверка и сдача (40 мин), документ (30 мин). Всё, что ломаем, восстанавливаем из конфигов и снапшота.

### Предусловия
Нужны: DC01 (.10, AD DS + DNS + DHCP), FS01 (.20), WIN11-CL01 и WIN10-CL02 (DHCP), UBU01 (.30), ASTRA01 (.31) — стенд L1. И машины L2, поднятые в предыдущих главах: DC02 (.11), GW01 (10.10.10.3 / 10.10.20.1), WEB01 (10.10.20.10, nginx), MON01 (.40). Если GW01/WEB01/MON01/DC02 ещё не созданы — вернитесь к главам модуля L2, где они вводятся; в экзамене нельзя строить на отсутствующем фундаменте. Минимальная замена на месте: одна ВМ Debian 12 с двумя адаптерами (VMnet8 + VMnet10) вместо GW01.

### Снапшот
С хоста, при выключенных или работающих ВМ (лучше — при выключенных):
```powershell
vmrun -T ws snapshot "D:\VM\GW01\GW01.vmx" before-l2-110
vmrun -T ws snapshot "D:\VM\WEB01\WEB01.vmx" before-l2-110
vmrun -T ws snapshot "D:\VM\MON01\MON01.vmx" before-l2-110
vmrun -T ws snapshot "D:\VM\DC02\DC02.vmx" before-l2-110
vmrun -T ws snapshot "D:\VM\WIN10-CL02\WIN10-CL02.vmx" before-l2-110
```
Пути и `vmrun.exe` — подставьте свои `[ПРОВЕРИТЬ]`.

### Шаги
1. **Инвентаризация.** На хосте: `vmrun -T ws list` — все нужные ВМ запущены. Записать в `stand-log.md` дату, список ВМ и их адреса. Ожидаемо: 10 строк.
2. **План адресации и критерии приёмки.** В `exam-report.md` таблица: имя, IP, роль, порты, кто зависит. Ниже — 6 критериев приёмки (портал по имени с двух клиентов, репликация без ошибок, шара `Buh` только для GG-Buh, DHCP-аренды в пуле, Zabbix видит 3 хоста, алерт на падение nginx). Ожидаемо: файл с планом до первого клика.
3. **Сеть с нуля на GW01.** `sudo nft flush ruleset` (правила только в памяти — это безопасный сброс), затем `ip -br a`, `ip r`, `sysctl net.ipv4.ip_forward`. С WIN11-CL01: `Test-NetConnection 10.10.20.10 -Port 80` → `TcpTestSucceeded : False`. Ожидаемо: DMZ недоступна, как и должно быть.
4. **Поднять маршрут.** Записать `/etc/nftables.conf` из п.5 раздела 4, `sudo nft -f /etc/nftables.conf`, `sudo systemctl enable --now nftables`. Повторить тест с WIN11-CL01 → `True`. Ожидаемо: доступ появился ровно к `10.10.20.10:80`, остальное в DMZ закрыто.
5. **Веб-сервис с нуля на WEB01.** Убрать дефолтный сайт из `sites-enabled`, создать `/etc/nginx/sites-available/vektor-portal.conf` с `root /var/www/vektor-portal;` и `server_name web01.corp.vektor.lab;`, симлинк в `sites-enabled`, `sudo nginx -t`, `sudo systemctl reload nginx`. Ожидаемо: `syntax is ok` и `test is successful`, `curl -I http://10.10.20.10` → `200 OK`.
6. **Имя в DNS.** На DC01: `Resolve-DnsName web01.corp.vektor.lab`. Если не разрешается — `Add-DnsServerResourceRecordA -Name web01 -ZoneName corp.vektor.lab -IPv4Address 10.10.20.10`, `Clear-DnsClientCache`. Ожидаемо: имя резолвится в `10.10.20.10` с обоих клиентов.
7. **Домен и репликация.** На DC02: `dcdiag /test:dns`, на DC01: `repadmin /replsummary`, `netdom query fsmo`, `w32tm /query /status`. Ожидаемо: ошибок нет, FSMO на DC01, расхождение времени — секунды (не больше 5 минут, иначе Kerberos отвалится).
8. **Файлы и права.** На FS01: `Get-SmbShare`, `Get-SmbShareAccess -Name Buh`. На WIN11-CL01 под `ivanov`: `net use \\FS01\Buh` → успех. На WIN10-CL02 под `petrova`: `dir \\FS01\Buh` → «Отказано в доступе». Ожидаемо: доступ ровно у GG-Buh, у HR — нет. Это **положительный** результат проверки.
9. **DHCP.** На DC01: `Get-DhcpServerv4Lease -ScopeId 10.10.10.0` — обе клиентские ВМ имеют аренды из 100–150. `Get-DhcpServerv4OptionValue -ScopeId 10.10.10.0` — опции 003 и 006 указывают на 10.10.10.2 и 10.10.10.10. Ожидаемо: значения верные.
10. **Мониторинг.** На MON01 убедиться, что хосты GW01, WEB01 и DC01 в статусе Enabled и с данными; `zabbix_get -s 10.10.10.30 -k agent.ping` → `1`. Ожидаемо: свежие метрики не старше 1–2 минут.
11. **Смоделированный отказ.** На WEB01: `sudo systemctl stop nginx`. Через 3–5 минут в Zabbix — проблема «порт 80 недоступен». `sudo systemctl start nginx` — проблема закрывается. Ожидаемо: цикл алерт → восстановление пройден целиком.
12. **Приёмка и документ.** Пройти чек-лист ниже, записать в `exam-report.md` фактические выводы команд (скриншотами или цитатами), в `stand-log.md` — что изменено. Ожидаемо: отчёт, по которому другой человек воспроизведёт стенд.

### Сломай и почини
> **Пользователь:** Петрова (HR) / **ВМ:** WIN10-CL02 / **Что написала:** «Портал `web01.corp.vektor.lab` не открывается, браузер пишет, что сайт не найден. У Иванова в бухгалтерии всё открывается, я проверяла. Срочно, у меня отчёт.» / **Срочность:** средняя

**Как воспроизвести поломку.** На WIN10-CL02 под администратором поставить статический DNS:
```powershell
Set-DnsClientServerAddress -InterfaceAlias "Ethernet" -ServerAddresses 8.8.8.8
Clear-DnsClientCache
```
Клиент выпадает из доменного разрешения имён — при этом IP-связность и портал по IP работают.

**Диагностика по порядку:**
1. Воспроизвести у себя: `Test-NetConnection web01.corp.vektor.lab -Port 80` → ошибка разрешения имени; `Test-NetConnection 10.10.20.10 -Port 80` → `True`. Значит, сеть, маршрут и nginx целы, проблема в имени.
2. `Resolve-DnsName web01.corp.vektor.lab` на WIN10-CL02 → «не удалось найти». На WIN11-CL01 то же имя резолвится.
3. `ipconfig /all` на WIN10-CL02 → «DNS-серверы: 8.8.8.8». Вот корень.
4. `nslookup web01.corp.vektor.lab 10.10.10.10` → отвечает `10.10.20.10`. DNS-сервер здоров, клиент настроен мимо него.
5. На DC01 `Get-DhcpServerv4OptionValue -ScopeId 10.10.10.0` → опция 006 = 10.10.10.10. Значит, дело не в DHCP, а в ручной/унаследованной настройке клиента.
6. `Get-DnsClientServerAddress -InterfaceAlias "Ethernet"` — подтвердить статику.

**Решение:**
```powershell
Set-DnsClientServerAddress -InterfaceAlias "Ethernet" -ResetServerAddresses
ipconfig /renew
ipconfig /flushdns
Resolve-DnsName web01.corp.vektor.lab
```
**Ответ пользователю:** «Мария, добрый день. Портал был доступен, но на вашем компьютере был вручную прописан внешний DNS-сервер, поэтому внутренние имена не находились. Вернул автоматическое получение настроек, сейчас портал открывается и доменные ресурсы работают. Если повторится — напишите, разберёмся, откуда взялась настройка.» **Закрытие:** тип «Неправильная конфигурация клиента», категория «DNS», в решении — причина, действие, проверка (портал открывается по имени), профилактика (проверить, не раскатывается ли статика скриптом или GPO).

Или в VMware Workstation: правый клик по ВМ → Snapshot Manager → выбрать `before-l2-110` → Go To. После откатa вписать в `stand-log.md`, какие изменения отменены — иначе через неделю вы не вспомните, почему на стенде старый конфиг.

## 6. Ошибки новичков и безопасность

- **Начал строить без плана адресации** → два узла с одним IP, DHCP отдаёт адрес занятому хосту → «плавающие» отказы. Правильно: сначала таблица адресов и критерии приёмки, потом команды.
- **Забыл `ip_forward=1`** → с GW01 пингуется всё, из офиса в DMZ — ничего. Правильно: проверять пересылку до настройки файрвола, а не после.
- **Правила nftables не сохранены в файл** → после ребута firewall пуст, стенд «открыт». Правильно: `/etc/nftables.conf` + `systemctl enable nftables` сразу.
- **Меняет без снапшота**, «потому что быстро» → нечего откатывать. Правильно: снапшот до, имя по шаблону, запись в `stand-log.md`.
- **Проверка «пингом»** → сеть жива, сервис мёртв, инцидент в проде. Правильно: проверять сервис на его порту и по имени (`curl -I`, `Test-NetConnection -Port`).
- **Мониторинг «зелёный», но пустой** → агент стоит, ключи не опрашиваются, алертов нет. Правильно: `zabbix_get` руками и обязательный тест «остановил сервис — увидел проблему».
- **Разъехались часы** → Kerberos рвётся при расхождении больше 5 минут, вход в домен «внезапно» ломается. Правильно: проверять `w32tm /query /status` и `timedatectl` в каждом чек-листе.
- **Секреты в конфигах и в отчёте** → учебный пароль стенда попадает в общий документ. Правильно: в отчёте — `***`, реальные секреты только в менеджере секретов.

**Безопасность.** На стенде мы упрощаем: единый пароль `Lab#2026-vektor`, `policy drop` с минимумом разрешений, мониторинг без TLS. В боевой среде так нельзя: пароли — уникальные и в хранилище, доступ к Zabbix — через аутентификацию и закрытый периметр (никакого «Zabbix в интернет»), веб-сервер в DMZ — только 80/443 наружу и минимум наружу из него, правила firewall — через change management с ревью. Никогда не отключайте файрвол «чтобы проверить» на проде: это делается на копии или через временное правило с таймером и записью в тикете.

## 7. Вопросы на собеседовании (5 вопросов с ответами)

**1. «Вам дали пустой гипервизор и сказали: подними инфраструктуру офиса на 50 человек. С чего начнёте?»**
Ответ: с плана и слоёв — адресация и сетевые сегменты, затем контроллер домена с DNS и DHCP, потом файловые и прикладные сервисы, потом маршрутизация и фильтрация между сегментами, затем мониторинг, бэкап и документация. Параллельно — критерии приёмки по каждому слою.
*Что хочет услышать:* порядок и понимание зависимостей, а не список любимых команд.
*Красный флаг:* сразу «поставлю Windows и заджойню» без единого слова про адресацию, DNS и проверку.

**2. «Как докажете, что инфраструктура жива и что вы ничего не сломали?»**
Ответ: чек-лист приёмки, который проходит руками: разрешение имён с двух клиентов, открытие сервиса по имени и порту, репликация (`repadmin /replsummary`, `dcdiag`), корректные права на шару для «своего» и «чужого» пользователя, алерт в мониторинге на смоделированный отказ. Плюс `stand-log`/журнал изменений и снапшот до работ.
*Что хочет услышать:* проверка сервисов, а не «пинг прошёл»; отрицательные тесты тоже считаются проверкой.
*Красный флаг:* «ну, я посмотрел — всё открывается».

**3. «Из офисной сети не открывается внутренний сайт, а из DMZ он открывается. Ваши действия?»**
Ответ: идти по слоям. Есть ли маршрут до DMZ у клиента (`ip r`, `tracert`), включён ли `ip_forward` на шлюзе, разрешён ли `forward` в nftables и растут ли счётчики, слушает ли nginx нужный адрес (`ss -tulpn`), доходят ли запросы в access-лог. Сравнение «по имени» и «по IP» отделяет DNS от сети.
*Что хочет услышать:* последовательность с отсечением слоёв и умение читать логи и счётчики.
*Красный флаг:* «перезагружу шлюз» или «отключу файрвол и посмотрю».

**4. «Зачем второй контроллер домена и что проверите после его ввода?»**
Ответ: отказоустойчивость — при падении DC01 вход в домен и DNS продолжают работать; репликация и распределение ролей FSMO. Проверю: `dcdiag /v` на обоих, `repadmin /replsummary`, `netdom query fsmo`, что DC02 в DNS-клиентах и отвечает на запросы, синхронизацию времени, отсутствие ошибок в журналах репликации.
*Что хочет услышать:* понимание, что второй DC — не «копия для красоты», а реплика с проверяемым состоянием.
*Красный флаг:* «просто добавил сервер в домен».

**5. «Вы за час до сдачи заказчику сломали конфиг роутера. Что делаете?»**
Ответ: сначала остановить поток изменений и зафиксировать состояние, откатиться на снапшот или предыдущую версию конфига, проверить по чек-листу, что вернулось, сообщить о риске сдвига срока и причине, оформить запись в журнале и короткий постмортем — что сделал, почему не поймал раньше, какая проверка это предотвратит.
*Что хочет услышать:* откат как штатная процедура, прозрачная коммуникация и выводы, а не героизм в одиночку.
*Красный флаг:* «буду чинить до утра и никому не скажу».
