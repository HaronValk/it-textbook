# Сайты и подсети AD: топология репликации, привязка клиентов к ближайшему DC

## 1. Введение (зачем это нужно в реальной работе)

**Заявка №4711.** Пользователь: ivanov (бухгалтерия) / ВМ WIN11-CL01. Что написал: «Добрый день! С утра вход в систему идёт минуты три вместо обычных секунд. Папки на FS01 открываются, принтер печатает, интернет есть. Коллега petrova на своём компьютере заходит мгновенно. Что с доменом?» Срочность: средняя.

Дальше вы открываете `nltest` на клиенте — и видите, что компьютер вообще не понимает, в каком он сайте, а значит, ищет контроллер домена «где-нибудь в домене», а не «рядом». Вот это и есть тема главы.

Сайты (Sites) в Active Directory — это единственный механизм, которым вы говорите домену: «вот эти IP-подсети стоят в одном здании с быстрым каналом, а вот эти — за медленным WAN». От этого зависит две вещи, и обе видны в работе каждый день:

- **Репликация.** Внутри сайта контроллеры домена обмениваются изменениями сразу и без сжатия. Между сайтами — по расписанию, сжато и экономно. Неправильные сайты = либо репликация «через полстраны в кольце», либо отставание на часы.
- **Поиск контроллера домена клиентом (DC Locator).** Windows при входе ищет DC в своём сайте. Если сайт определён неверно или клиента некуда привязать — он пойдёт через медленный канал, и вход растянется на минуты.

После этой главы вы должны уметь: читать и строить топологию сайтов и подсетей, создавать site links с осмысленными cost/interval/schedule, объяснять, что делают KCC и ISTG, и диагностировать по `nltest`, `repadmin` и DNS, почему клиент ходит не туда. Это ровно тот уровень, на котором L2 перестаёт «перезагружать компьютер» и начинает чинить причину.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

### Где это лежит в AD

Объекты сайтов живут не в домене, а в **разделе конфигурации** леса: `CN=Sites,CN=Configuration,DC=corp,DC=vektor,DC=lab`. Значит, они реплицируются на все DC леса и видны всем. Там три вида объектов:

- **site** (`CN=<имя сайта>,CN=Sites,...`) — контейнер для «площадки».
- **subnet** (`CN=10.10.10.0/24,CN=Subnets,CN=Sites,...`) — объект с атрибутом `siteObject`, ссылающимся на сайт. Именно по нему DC понимает, в каком сайте находится IP.
- **siteLink** (`CN=IP,CN=Inter-Site Transports,CN=Sites,...`) — правило репликации между сайтами: состав сайтов, cost, интервал, расписание.

Плюс внутри каждого сайта есть `CN=Servers` со списком DC и объектов `NTDS Settings` — это уже само содержимое сайта.

### Схема

```text
        Лес corp.vektor.lab (Configuration NC)
        ┌───────────────────────────────────────────────┐
        │ CN=Sites                                      │
        │  ├─ CN=Vektor-Office   (сайт)                 │
        │  │    └─ CN=Servers: DC01, DC02               │
        │  ├─ CN=Vektor-DMZ      (сайт)                 │
        │  │    └─ CN=Servers: (пока пусто)             │
        │  ├─ CN=Subnets                                │
        │  │    ├─ 10.10.10.0/24 → siteObject=Vektor-Office
        │  │    └─ 10.10.20.0/24 → siteObject=Vektor-DMZ
        │  └─ CN=Inter-Site Transports                 │
        │       └─ CN=IP                                │
        │            ├─ DEFAULTIPSITELINK (cost 100, 180 мин)
        │            └─ LINK-Office-DMZ  (cost 200, 30 мин) │
        └───────────────────────────────────────────────┘
```

### Как клиент находит «свой» DC

Процесс называется **DC Locator** (реализован в службе Netlogon). Упрощённо:

```text
1. Клиент (10.10.10.117) включает сеть и хочет войти в домен
2. Netlogon спрашивает DNS: SRV _ldap._tcp.dc._msdcs.corp.vektor.lab
3. Получает список DC, шлёт одному из них CLDAP-ping (UDP 389):
   «какой сайт у IP 10.10.10.117?»
4. DC ищет подсеть в AD и отвечает: «Vektor-Office»
5. Клиент спрашивает DNS уже про свой сайт:
   SRV _ldap._tcp.Vektor-Office._sites.dc._msdcs.corp.vektor.lab
6. Получает DC этого сайта, пингует их (доступен? GC? KDC? writable?)
7. Выбирает один, кэширует и идёт к нему за Kerberos-билетом
```

Если в сайте DC нет — срабатывает **next closest site**: клиент идёт в сайт, связанный самым дешёвым (по cost) site link. Если и подсеть не найдена — клиент остаётся без сайта и получает «любой» DC домена. Именно это и даёт «вход 3 минуты» в филиалах.

Есть ещё **automatic site coverage**: если в сайте нет ни одного DC, контроллеры соседнего (по стоимости линка) сайта сами регистрируют в DNS SRV-записи от имени «пустого» сайта. То есть клиенты в DMZ не останутся без домена — их обслужит офисный DC. Регистрация происходит не мгновенно, Netlogon пересчитывает покрытие периодически [ПРОВЕРИТЬ: точный интервал пересчёта].

### Репликация: внутри сайта и между сайтами

| Параметр | Внутри сайта | Между сайтами |
|---|---|---|
| Кто строит топологию | KCC на каждом DC | ISTG (один DC на сайт на транспорт) |
| Форма | кольцо (+ доп. связи при >3 DC) | дерево по site links |
| Сжатие | нет | да, существенное [ПРОВЕРИТЬ: порядка 10–15 % объёма] |
| Триггер | уведомление, секунды | расписание, по умолчанию каждые 180 мин |
| Транспорт | RPC over IP | RPC over IP (SMTP — только для отдельных разделов, требует CA) |

- **KCC** (Knowledge Consistency Checker) — служба внутри AD, которая автоматически создаёт объекты подключений (`NTDS Settings` → connection objects). Руками их трогать почти никогда не нужно.
- **ISTG** (Inter-Site Topology Generator) — один DC в сайте, назначенный выбирать bridgehead-серверы для межсайтовой репликации. Это тот самый DC, через который сайт «соединён с миром».
- **Bridge all site links** включён по умолчанию: IP-транспорт считается полностью связным, и KCC сам строит транзитивные маршруты. Site link bridges нужны, только если вы это отключили.

### Порты, которые надо помнить

| Протокол | Порт | Зачем |
|---|---|---|
| DNS | 53 TCP/UDP | SRV-записи DC Locator |
| CLDAP (ping) | 389 UDP | определение сайта клиента |
| LDAP / LDAPS | 389 / 636 TCP | каталог |
| Kerberos / kpasswd | 88 / 464 TCP+UDP | аутентификация, смена пароля |
| Global Catalog | 3268 / 3269 TCP | поиск по лесу |
| RPC Endpoint Mapper | 135 TCP | репликация, ADUC, GPO |
| RPC динамический | 49152–65535 TCP | сам обмен репликацией |
| SMB | 445 TCP | SYSVOL, NETLOGON |
| W32Time | 123 UDP | время (без него Kerberos ломается) |

## 3. Аналогия из жизни

Представьте сеть МФЦ «Мои документы». Город поделён на районы — это **сайты**. У каждого района есть список улиц и домов — это **подсети**. Человек с прописки на улице Ленина идёт в МФЦ своего района: он же не поедет через весь город. Внутри района документы между окошками передают по коридору за минуту — это **внутрисайтовая репликация**. Между районами раз в три часа ездит фура по расписанию, и бумаги перед отправкой утрамбовывают в коробки — это **межсайтовая репликация со сжатием**. Диспетчер, который решает, из какого района и в какой поедет фура, — это **ISTG**. Если в новом микрорайоне МФЦ ещё не открыли, жители едут в соседний, до которого «дешевле добраться» — это **next closest site**. А если человек потерял прописку (подсеть не заведена в AD), он звонит в колл-центр и его отправляют в случайное отделение — вот вам «вход три минуты».

Аналогия перестаёт работать в одном: в жизни «ближайший» — это географически, а в AD «ближайший» — это тот, чей IP попадает в подсеть вашего сайта, и никакая физика тут не учитывается.

## 4. Практика и команды

Все команды PowerShell выполняются на DC01 под `VEKTOR\adm.student` в консоли с правами администратора домена. Модуль `ActiveDirectory` там уже есть — он ставится вместе с ролью AD DS.

**1. Посмотреть сайты (PowerShell и GUI).**
```powershell
Get-ADReplicationSite -Filter *
```
Ключей нет, `-Filter *` — все объекты. Типичный вывод (сокращённо):
```text
Name                     Description
----                     -----------
Default-First-Site-Name
```
Смотрим: сколько сайтов и как они называются. GUI: `dssite.msc` (Active Directory Sites and Services) → узел **Sites**.

**2. Посмотреть подсети и их привязку.**
```powershell
Get-ADReplicationSubnet -Filter * -Properties Site | Select-Object Name, Site
```
`-Properties Site` нужен, потому что ссылка на сайт — не свойство по умолчанию. Вывод:
```text
Name           Site
----           ----
10.10.10.0/24  Vektor-Office
```
Смотрим: **у каждой рабочей подсети есть объект**. Пусто — значит клиенты «без прописки».

**3. Создать сайт.**
```powershell
New-ADReplicationSite -Name "Vektor-DMZ" -Description "DMZ, 10.10.20.0/24"
```
`-Description` — просто комментарий для людей. Новый сайт **не попадает автоматически ни в один site link** — это ключевой момент.

**4. Создать подсеть и привязать к сайту.**
```powershell
New-ADReplicationSubnet -Name "10.10.20.0/24" -Site "Vektor-DMZ" -Description "DMZ segment"
```
`-Name` — строго в формате CIDR, `-Site` — имя существующего сайта. Одна подсеть = один сайт, «размазать» нельзя.

**5. Посмотреть site links.**
```powershell
Get-ADReplicationSiteLink -Filter * | Select-Object Name, Cost, ReplicationFrequencyInMinutes, SitesIncluded
```
Вывод:
```text
Name                 Cost ReplicationFrequencyInMinutes SitesIncluded
----                 ---- ------------------------------ -------------
DEFAULTIPSITELINK     100                            180 {Default-First-Site-Name}
```
Смотрим cost и интервал. Умолчания: 100 и 180 минут, расписание 24×7.

**6. Создать линк и настроить его.**
```powershell
New-ADReplicationSiteLink -Name "LINK-Office-DMZ" `
  -SitesIncluded "Vektor-Office","Vektor-DMZ" `
  -Cost 200 -ReplicationFrequencyInMinutes 30 `
  -InterSiteTransportProtocol IP
```
`-SitesIncluded` — перечисление сайтов; `-Cost` — «цена» маршрута (чем меньше, тем предпочтительнее); `-ReplicationFrequencyInMinutes` — как часто ISTG будет ставить задачи репликации; `-InterSiteTransportProtocol` — `IP` или `SMTP`. Расписание (окна доступности) удобнее задавать в `dssite.msc`: свойства линка → **Change Schedule**. Параметр `Set-ADReplicationSiteLink -ReplicationSchedule` в модуле есть не во всех версиях [ПРОВЕРИТЬ].

**7. Убедиться, кто в каком сайте.**
```powershell
Get-ADDomainController -Filter * | Select-Object Name, Site, IPv4Address
```
```text
Name Site          IPv4Address
---- ----          -----------
DC01 Vektor-Office 10.10.10.10
DC02 Vektor-Office 10.10.10.11
```
Сайт DC определяется его собственным IP, а не тем, куда его «мысленно» поставили.

**8. Определить сайт клиента и найденный DC (на клиенте).**
```cmd
nltest /dsgetsite
nltest /dsgetdc:corp.vektor.lab /force
```
```text
Vektor-Office
The command completed successfully

           DC: \\DC01.corp.vektor.lab
      Address: \\10.10.10.10
 DC Site Name: Vektor-Office
Our Site Name: Vektor-Office
        Flags: PDC GC DS LDAP KDC TIMESERV WRITABLE DNS_DC ...
```
`/force` — не брать из кэша и опросить заново. Смотрим: **Our Site Name** и **DC Site Name** должны совпадать. Если Our Site Name пустой — подсеть клиента не заведена. `nltest /dsgetdc:corp.vektor.lab /site:Vektor-DMZ` позволяет спросить «а кого бы дали клиенту из DMZ».

**9. Проверить, что DC реально анонсирует себя в DNS.**
```powershell
dcdiag /test:Advertising /v:DC01
```
Тест Advertising проверяет, что все SRV-записи (`_ldap._tcp`, `_kerberos._tcp`, site-specific) зарегистрированы. Строка `... passed test Advertising` — хорошо. Если failed — DC не найдут клиенты.

**10. Посмотреть SRV-записи конкретного сайта.**
```cmd
nslookup -type=SRV _ldap._tcp.Vektor-Office._sites.dc._msdcs.corp.vektor.lab 10.10.10.10
```
```text
_ldap._tcp.Vektor-Office._sites.dc._msdcs.corp.vektor.lab  SRV service location:
          priority       = 0
          weight         = 100
          port           = 389
          svr hostname   = dc01.corp.vektor.lab
```
Смотрим: есть ли записи для сайта и какие DC в них перечислены. Для сайта без DC записи появятся, только когда сработает automatic site coverage. Подробнее про DNS — глава 19.

**11. Здоровье репликации.**
```cmd
repadmin /replsummary
repadmin /showrepl DC02
repadmin /queue DC01
```
`/replsummary` — сводка: сколько партнёров, сколько ошибок (`largest delta`, `fails/total`). `/showrepl` — по каждому партнёру: тип (`<cw-...>` — внутрисайтовая, `<auto-...>` — межсайтовая), время последней успешной репликации, ошибки. `/queue` — что стоит в очереди на отправку.

**12. Пересчитать топологию и увидеть bridgehead.**
```cmd
repadmin /kcc DC01
repadmin /bridgeheads DC01 /verbose
```
`/kcc` заставляет KCC немедленно пересобрать подключения (полезно после правок сайтов). `/bridgeheads` показывает, какой DC выбран ISTG и через кого идёт межсайтовая репликация.

**13. События KCC в журнале.**
```powershell
Get-WinEvent -LogName "Directory Service" -MaxEvents 100 |
  Where-Object Id -in 1311,1566,1865 | Select-Object TimeCreated,Id,Message
```
ID 1311 — «KCC обнаружил проблемы в конфигурации каталога» (обычно сайт без линка). ID 1566 — «все DC сайта по этому транспорту недоступны». ID 1865 — [ПРОВЕРИТЬ формулировку]. Это первое, что смотрят, когда «репликация встала после правки сайтов».

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

Нужны: **DC01** (10.10.10.10, AD DS + DNS, сайт `Default-First-Site-Name`), **DC02** (10.10.10.11, второй DC, репликация с DC01 проверена в уроке 17), **WIN11-CL01** (в домене, пользователь `ivanov`), **WIN10-CL02** (в домене, `petrova`). Все — в подсети 10.10.10.0/24. Учётка `VEKTOR\adm.student`, пароль `Lab#2026-vektor`.

Если DC02 ещё не развёрнут — сначала пройдите урок 17, без второго DC нечего смотреть в топологии. Машины DMZ (GW01, WEB01) для этой лабы не нужны — сайт DMZ мы создаём «на бумаге», заранее под будущий сегмент VMnet10.

### Снапшот

В VMware Workstation на каждой затрагиваемой ВМ: правый клик по вкладке ВМ → **Snapshot → Take Snapshot**, имя `before-l2-018`. Машины: DC01, DC02, WIN11-CL01, WIN10-CL02. Пока снапшоты снимаются — ВМ лучше выключить или хотя бы не менять в них ничего.

### Шаги

1. **DC01.** Открыть PowerShell от администратора. Зафиксировать исходное состояние:
   ```powershell
   Get-ADReplicationSite -Filter *
   Get-ADReplicationSubnet -Filter *
   Get-ADReplicationSiteLink -Filter *
   ```
   Ожидаемо: один сайт `Default-First-Site-Name`, **ни одной подсети**, один линк `DEFAULTIPSITELINK`. Именно так выглядит стенд после установки — и именно поэтому клиенты пока «безадресные».

2. **DC01.** Переименовать дефолтный сайт в осмысленный:
   ```powershell
   Rename-ADObject "CN=Default-First-Site-Name,CN=Sites,CN=Configuration,DC=corp,DC=vektor,DC=lab" -NewName "Vektor-Office"
   ```
   Ожидаемо: `Get-ADReplicationSite -Filter *` показывает `Vektor-Office`.

3. **DC01.** Создать сайт DMZ:
   ```powershell
   New-ADReplicationSite -Name "Vektor-DMZ" -Description "DMZ, 10.10.20.0/24"
   ```
   Ожидаемо: в `dssite.msc` под узлом Sites два сайта, у `Vektor-DMZ` внутри пустой `Servers`.

4. **DC01.** Завести обе подсети:
   ```powershell
   New-ADReplicationSubnet -Name "10.10.10.0/24" -Site "Vektor-Office"
   New-ADReplicationSubnet -Name "10.10.20.0/24" -Site "Vektor-DMZ"
   ```
   Ожидаемо: `Get-ADReplicationSubnet -Filter * -Properties Site` показывает обе с правильными сайтами.

5. **DC01.** Проверить, что DC «переехали» в переименованный сайт:
   ```powershell
   Get-ADDomainController -Filter * | Select-Object Name,Site
   ```
   Ожидаемо: DC01 и DC02 оба в `Vektor-Office`.

6. **DC01.** Создать межсайтовый линк:
   ```powershell
   New-ADReplicationSiteLink -Name "LINK-Office-DMZ" `
     -SitesIncluded "Vektor-Office","Vektor-DMZ" `
     -Cost 200 -ReplicationFrequencyInMinutes 30 `
     -InterSiteTransportProtocol IP
   ```
   Ожидаемо: `Get-ADReplicationSiteLink -Filter *` показывает новый линк с cost 200.

7. **DC01.** Перезапустить Netlogon, чтобы DC перерегистрировал DNS-записи под новое имя сайта, и запустить KCC:
   ```powershell
   Restart-Service Netlogon
   repadmin /kcc DC01
   repadmin /bridgeheads DC01 /verbose
   ```
   Ожидаемо: в выводе `/bridgeheads` фигурирует DC01 как ISTG сайта `Vektor-Office`; ошибок нет.

8. **WIN11-CL01.** Проверить привязку клиента:
   ```cmd
   nltest /dsgetsite
   nltest /dsgetdc:corp.vektor.lab /force
   ```
   Ожидаемо: `Vektor-Office`, а в выводе `/dsgetdc` строки **Our Site Name** и **DC Site Name** обе равны `Vektor-Office`.

9. **WIN11-CL01.** Смоделировать «клиента из DMZ»:
   ```cmd
   nltest /dsgetdc:corp.vektor.lab /site:Vektor-DMZ /force
   ```
   Ожидаемо: DC в сайте DMZ нет, поэтому вернётся DC01 (или DC02) из `Vektor-Office`, а в выводе будет видно несовпадение запрошенного и фактического сайта. Это и есть работа next closest site.

10. **WIN11-CL01.** Проверить SRV-записи:
    ```cmd
    nslookup -type=SRV _ldap._tcp.Vektor-Office._sites.dc._msdcs.corp.vektor.lab 10.10.10.10
    nslookup -type=SRV _ldap._tcp.Vektor-DMZ._sites.dc._msdcs.corp.vektor.lab 10.10.10.10
    ```
    Ожидаемо: для `Vektor-Office` — записи DC01 и DC02. Для `Vektor-DMZ` — сначала пусто, а через некоторое время (или после `Restart-Service Netlogon` на DC01) появятся записи DC01: сработала automatic site coverage.

11. **DC01.** Убедиться, что репликация жива:
    ```cmd
    repadmin /replsummary
    repadmin /showrepl DC02
    ```
    Ожидаемо: `0 fails` в сводке, в `/showrepl` партнёр DC01 с типом внутрисайтовой связи и свежим временем.

12. **Все ВМ.** Записать изменения в `stand-log.md`: переименование сайта, новый сайт, подсети, линк, кто где живёт.

## 6. Ошибки новичков и безопасность

1. **Создать сайт и забыть про подсети.** → Клиенты в этом сегменте не определяют свой сайт, DC Locator работает наугад, вход медленный. → Всегда после создания сайта сразу заводите объекты подсетей всех сегментов этого офиса.
2. **Создать сайт и не добавить его ни в один site link.** → Сайт изолирован: KCC не построит межсайтовую репликацию, в журнале Directory Service полезут 1311/1566. → Сразу добавляйте сайт в линк (`-SitesIncluded`) или создавайте новый линк.
3. **Один сайт на всю компанию с филиалами на медных каналах.** → KCC строит «кольцо» репликации через WAN, изменения ходят по кругу, клиенты филиала логинятся через慢 канал. → Разделяйте сегменты на сайты, задавайте cost и расписание.
4. **Удалить или переименовать `DEFAULTIPSITELINK` «для порядка».** → Ломается маршрут по умолчанию между сайтами, которые вы не описали явно. → Оставьте его, добавляйте свои линки рядом.
5. **Задать подсеть слишком широко (`10.0.0.0/8`).** → Она «съест» все остальные сегменты, включая филиальные, и привяжет их к одному сайту. → Подсети — по фактической адресации, максимально точно.
6. **Переименовать сайт и не перерегистрировать DNS.** → Часть SRV-записей остаётся со старым именем, часть клиентов ищет DC по несуществующему сайту. → После переименования: `Restart-Service Netlogon` на каждом DC, затем `dcdiag /test:Advertising`.
7. **Считать `cost` и `interval` «скоростью репликации».** → Cost — это приоритет маршрута, интервал — период планирования; данные всё равно идут пакетом. → Не ждите «мгновенной» межсайтовой репликации, если она нужна — проектируйте иначе.
8. **Править `NTDS Settings` и connection objects руками.** → KCC вернёт своё через 15 минут, а половина ручных правок останется мусором. → Ручные подключения — только осознанно и с записью в журнал изменений.

### Безопасность

- **Не ставьте обычный (writable) DC в DMZ.** Компрометация веб-сервера в DMZ даст атакующему сетевой доступ к контроллеру домена — это прямой путь к захвату домена. Если в сегменте действительно нужна аутентификация AD, рассматривайте RODC (read-only DC) в отдельном сайте и отдельный файрвол-периметр, а лучше — отдельный лес. У нас `Vektor-DMZ` сознательно без DC.
- **Сайты не являются средством безопасности.** Это про топологию и трафик. Разделение «DMZ-сайт» не заменяет nftables на GW01 и не даёт никаких прав.
- **Правки в AD Sites — это изменение конфигурации леса.** Ошибка здесь влияет на весь домен: репликация и вход пользователей. В рабочей среде — только через согласование, с бэкапом System State и записью в change log. Прямое редактирование через `adsiedit.msc` без понимания атрибутов — гарантированный способ уронить репликацию.
- **Пароли.** На стенде пароль общий учебный (`Lab#2026-vektor`). В реальной работе так нельзя, и в этой главе это важно: получив доступ к любому DC через «дешёвый» маршрут, атакующий получает и все хэши.

## 7. Вопросы на собеседовании (3–5 вопросов с ответами)

**Вопрос 1. Что такое сайт AD и чем он отличается от домена и подразделения (OU)?**

Ответ: Сайт — это объект в разделе конфигурации, описывающий физическую топологию сети: набор подсетей с быстрыми связями. Домен — административная граница (своя база, свои политики паролей), OU — контейнер внутри домена для делегирования и применения GPO. Сайт не даёт прав и не хранит пользователей: он влияет только на репликацию и на то, какой DC выберет клиент.
*Что хочет услышать интервьюер:* чёткое разделение «логика (домен/OU) vs физика (сайт/подсеть)».
*Красный флаг:* «Сайт — это как OU, только для филиалов».

**Вопрос 2. Как Windows-клиент находит ближайший контроллер домена?**

Ответ: Через DC Locator в службе Netlogon. Клиент по DNS находит DC домена, шлёт CLDAP-ping (UDP 389) — DC по IP определяет его подсеть и возвращает имя сайта. Затем клиент запрашивает site-specific SRV-записи `_ldap._tcp.<site>._sites.dc._msdcs.<domain>`, проверяет доступность DC в своём сайте и выбирает один. Если в сайте DC нет — срабатывает next closest site по стоимости site link. Если подсеть не заведена — сайт не определяется, и клиент получает любой DC домена.
*Что хочет услышать интервьюер:* знание SRV-записей и того, что определение сайта делает DC по CLDAP, а не сам клиент.
*Красный флаг:* «Клиент смотрит свою маску подсети локально и по ней выбирает DC» — так не работает.

**Вопрос 3. Чем внутрисайтовая репликация отличается от межсайтовой и кто этим управляет?**

Ответ: Внутри сайта KCC строит кольцевую топологию подключений, данные идут без сжатия по уведомлению (секунды). Между сайтами ISTG выбирает bridgehead-серверы, данные сжимаются и передаются по расписанию site link (по умолчанию каждые 180 минут), с учётом cost. KCC есть на каждом DC, ISTG — один на сайт на транспорт.
*Что хочет услышать интервьюер:* понимание, что ISTG — не «главный DC», а роль генератора топологии.
*Красный флаг:* «Между сайтами репликация идёт мгновенно, просто сжато».

**Вопрос 4. В филиале нет контроллера домена. Что будет при входе пользователя и как это проверить?**

Ответ: Клиент не найдёт DC в своём сайте; сработает next closest site, и он пойдёт в DC соседнего сайта через WAN — вход будет медленным, зависит от расписания и качества канала. Плюс, если в сайте нет и Global Catalog, может понадобиться UGMC (кэширование членства в универсальных группах) — иначе часть входов вообще не пройдёт. Проверяется `nltest /dsgetsite` и `nltest /dsgetdc:<domain> /force` на клиенте: Our Site Name будет своим, а DC Site Name — чужим.
*Что хочет услышать интервьюер:* что кандидат знает про fallback и умеет это измерить, а не «переустановить винду».
*Красный флаг:* «Если DC нет, пользователь не сможет войти» — сможет, если есть кэш и связь.

**Вопрос 5. Как убедиться, что сайты настроены правильно после изменений?**

Ответ: На DC — `Get-ADReplicationSubnet`/`Get-ADReplicationSiteLink` (привязки и параметры), `dcdiag /test:Advertising` (SRV-записи), `repadmin /kcc` и `/bridgeheads` (топология), `/replsummary` и `/showrepl` (нет ошибок). На клиенте — `nltest /dsgetsite` и `nltest /dsgetdc`. В DNS — `nslookup -type=SRV` для `_sites`-записей. В журнале Directory Service — отсутствие 1311/1566.
*Что хочет услышать интервьюер:* что проверка идёт с двух сторон — со стороны DC и со стороны клиента.
*Красный флаг:* «Достаточно посмотреть в dssite.msc — там же видно».
