## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Три разных документа, которые путают новички:**

- **Runbook** — пошаговая процедура для инженера: «что сделать с сервисом, чтобы он ожил». Пишется в расчёте на человека, который устал, ночью, и не знает вашу инфраструктуру.
- **How-to** — инструкция для пользователя: «нажмите Пуск → …». Без PowerShell, без объяснения причин.
- **Статья об инциденте / RCA** — что случилось, почему, что сделали, чтобы не повторилось (см. урок 2 модуля).

**Markdown** — текстовый формат разметки: обычный `.md`-файл с `#`, `*`, таблицами и блоками кода. Его рендерят почти все инструменты (GitLab, GitHub, VS Code, Obsidian). Два важных факта: существует строгая спецификация **CommonMark**, а **GFM** (GitHub Flavored Markdown) добавляет таблицы, чек-листы `- [ ]`, зачёркивание; GitLab использует своё расширение — GLFM, надмножество GFM. Практический вывод: **пишите в GFM-подмножестве** — тогда файл одинаково откроется везде. YAML-заголовок («front matter») в начале файла понимают Obsidian, MkDocs, Hugo, но сам GitHub его не рендерит — покажет таблицей.

**Git** — распределённая система контроля версий. Модель данных простая и её спрашивают на собеседовании:

- **blob** — содержимое одного файла;
- **tree** — каталог (список имён и ссылок на blob'ы/tree);
- **commit** — снимок всего дерева + автор, дата, сообщение и ссылка на родителя. Отсюда SHA-1/SHA-256 хеш коммита;
- **ref / ветка** — просто подвижный указатель на коммит;
- **HEAD** — где вы сейчас.

Ключевое отличие от «сохранения файла на шаре»: коммит — это **неизменяемый снимок**, а не набор правок. Поэтому можно вернуться на любой коммит и сравнить любые два.

Схема учебного стенда для этой главы:

```text
     WIN11-CL01 (DHCP)                        UBU01 (10.10.10.30)
     C:\kb  — рабочая копия                   /srv/git/kb.git — bare-репозиторий
        │                                       (только внутренности Git,
        │  git add / git commit                без рабочих файлов)
        │  (локально, офлайн)                     │
        │                                         │
        │  git push ── SSH, TCP 22 ─────────────► │ обновляет refs/heads/main
        │  git pull ◄──────────────────────────── │
        │                                         │
        │  публикация how-to                     │
        ▼                                         ▼
   \\FS01\Obshchee\KB\*.md  ──читают пользователи──►  (в реальной работе —
   внутренние runbook'и на шару НЕ выкладываем        GitLab/Wiki с правами)
```

С точки зрения модели OSI Git-транспорт по SSH — это прикладной уровень (L7) поверх TCP/22; Markdown вообще не про сеть, это формат файла. Важно понимать: **bare-репозиторий** (`git init --bare`) не имеет рабочей копии — в него можно безопасно пушить, тогда как push в ветку, которая «выchecked-out» в обычном репозитории, Git отклонит.

## 3. Аналогия из жизни

База знаний — это кухня ресторана. **How-to** — меню для гостя: «борщ, 350 ₽, подаётся с хлебом». **Runbook** — технологическая карта повара: граммовки, температура, время, что делать, если соус расслоился. **Git** — журнал, в который повар записывает каждое изменение рецепта: кто поменял соль на 5 г, когда и зачем; старые страницы при этом не вырываются, а остаются доступными. **Шаблон** — это форма бланка с уже расчерченными графами, чтобы новый повар не забыл указать порции и аллергены.

Где аналогия ломается: рецепт проверяют на вкус один раз, а runbook надо перепроверять регулярно — инфраструктура меняется, и инструкция, которая работала год назад, может стать опасной.

## 4. Практика и команды

Ниже — рабочий минимум L2. Windows-команды — в PowerShell или Git Bash, Linux — на UBU01.

**1. Настройка Git после установки** (обязательно, иначе коммиты будут «безымянными»):

```powershell
git config --global user.name "adm.student"
git config --global user.email "adm.student@corp.vektor.lab"
git config --global init.defaultBranch main
git config --global core.editor "code --wait"
git config --global --list
```

`--global` пишет в профиль пользователя; `init.defaultBranch main` задаёт имя первой ветки (без этого Git выдаст предупреждение и создаст `master`); `core.editor "code --wait"` — редактор коммит-сообщений через VS Code.

**2. Создание репозитория и bare-репозитория на сервере**:

```bash
sudo mkdir -p /srv/git && sudo chown $USER:$USER /srv/git
git init --bare /srv/git/kb.git
ls /srv/git/kb.git
```

Ожидаемый вывод `ls`: `HEAD  config  description  hooks  info  objects  refs`. Файлов `.md` там нет — это нормально, содержимое лежит внутри `objects`.

**3. Клонирование**:

```bash
# на UBU01 (локальный путь)
git clone /srv/git/kb.git ~/kb
# на WIN11-CL01 (по SSH)
git clone ssh://adm.student@10.10.10.30/srv/git/kb.git C:\kb
```

В выводе — `warning: You appear to have cloned an empty repository` (для свежего bare-репо это ожидаемо).

**4. Ежедневный цикл: status → add → commit**:

```powershell
git status
git add runbooks/fs01-print-spooler.md
git commit -m "runbook: перезапуск спулера на FS01" -m "Добавлены предусловия и проверка после рестарта."
```

`git status` показывает три зоны: untracked / modified / staged. `-m` второй раз — тело сообщения (заголовок до 72 символов, потом пустая строка). Смотреть надо именно на список «Changes to be committed» перед коммитом.

**5. История и сравнение**:

```bash
git log --oneline --graph --decorate -10
git show HEAD
git diff              # рабочая копия vs индекс
git diff --staged     # индекс vs последний коммит
```

Коммит против коммита: `git diff v1.0..HEAD -- runbooks/`. `--decorate` показывает теги и ветки — удобно печатать в отчёт.

**6. Ветки и слияние с ревью** (аналог merge request без сервера):

```bash
git switch -c kb/howto-buh
# ...правки...
git commit -am "howto: подключение к \\FS01\Buh"
git push -u origin kb/howto-buh
```

`git commit -am` индексирует только **отслеживаемые** файлы — новые так не добавить. `-u` связывает локальную ветку с удалённой, дальше хватит `git push`.

**7. Ревью и merge на «серверной» стороне** (UBU01):

```bash
cd ~/kb && git fetch
git log --oneline main..origin/kb/howto-buh
git diff main..origin/kb/howto-buh
git switch main
git merge --no-ff origin/kb/howto-buh
git push origin main
```

`--no-ff` создаёт отдельный merge-коммит — по истории видно, что изменение проходило ревью.

**8. Теги — фиксация «эталонной» версии инструкции**:

```powershell
git tag -a v1.0 -m "KB: первый согласованный набор runbook/howto"
git push origin v1.0
```

Аннотированный тег (`-a`) хранит автора и сообщение, легкий — только указатель. Теги сами не пушатся, нужен явный `git push origin <tag>`.

**9. Кто и когда сломал строку — blame и история файла**:

```bash
git blame -L 1,20 -- runbooks/fs01-print-spooler.md
git log --follow -p -- runbooks/fs01-print-spooler.md
```

В `blame` слева — короткий SHA, автор, дата. `--follow` продолжает историю при переименовании файла.

**10. Поиск по базе знаний** (главный навык L1/L2 — не писать заново, а найти):

```bash
grep -rn --include='*.md' -i "spooler" ~/kb
```

```powershell
Get-ChildItem C:\kb -Recurse -Filter *.md | Select-String -Pattern "spooler" -List
```

`-r` рекурсивно, `-n` с номерами строк, `--include` ограничивает типы файлов, `-i` игнорирует регистр. В PowerShell `-List` возвращает по одному совпадению на файл.

**11. Отмена: revert vs reset**:

```bash
git revert <sha>          # создаёт новый коммит, отменяющий изменения
git reset --hard <sha>    # ЛОКАЛЬНО: выбросить всё, что после <sha>
```

`revert` безопасен для общих веток, `reset --hard` на общей ветке — способ снести коллегам работу. `--hard` удаляет изменения **и в рабочих файлах**, восстановить можно только через `git reflog`.

**12. Рендер Markdown в читаемый вид** (опционально):

```bash
sudo apt install -y pandoc     # пакет из репозитория Ubuntu [ПРОВЕРИТЬ: включён universe]
pandoc -f gfm -s runbooks/fs01-print-spooler.md -o /tmp/print.html
```

`-f gfm` — читать как GitHub-flavored Markdown, `-s` — самостоятельный HTML со стилями. PDF через `--pdf-engine=xelatex` потребует ещё и TeX — на стенде это лишние гигабайты.

**GUI-пути:** VS Code — `Ctrl+Shift+V` (предпросмотр Markdown), панель Source Control (`Ctrl+Shift+G`) для add/commit/push. Установка Git for Windows: `winget install --id Git.Git -e --source winget` [ПРОВЕРИТЬ точный ID пакета в вашей версии winget] либо установщик с git-scm.com (свободная лицензия GPL, скачивается свободно; если в вашей сети доступ к сайту нестабилен — берите пакет из доверенного зеркала или корпоративного репозитория).

## 6. Ошибки новичков и безопасность

- **Держать знания в голове и в личных заметках** → каждое повторное обращение = потерянный час и раздражённый пользователь → пишите runbook сразу после первого решения, пока помните.
- **Инструкция без предусловий** («просто перезапустите службу») → на чужой машине шаг ломает прод → в шаблоне обязательные блоки «Предусловия», «Проверка», «Откат».
- **Секреты в репозитории** → пароль от `adm.student` или ключ попадает в историю и в бэкапы, вычистить сложно → секреты только в хранилище (Bitwarden/Vault/менеджер паролей), в KB — отсылка «пароль в хранилище, запись `FS01-admin`».
- **Огромная статья «Всё про FS01»** → её никто не читает и не обновляет → один файл = одна процедура, имя файла = действие.
- **Коммиты «fix», «update», «asdf»** → через месяц невозможно понять, что изменилось → формат `область: что сделано` + тело с причиной.
- **Прямой push в `main` без ветки** → конфликты и потерянная работа коллег → ветка + merge/merge request.
- **Runbook написан, но не проверен** → на инциденте выясняется, что команда не работает → раз в квартал «прогон» хотя бы одного runbook на стенде, поле `last_reviewed`.
- **DR-инструкция хранится только на том сервере, который восстанавливают** → при пожаре документация сгорает вместе с ним → одна копия всегда вне контура (Git на другом хосте, распечатка у дежурного).

**Безопасность.** Репозиторий — это тоже актив: давайте права по принципу минимально необходимого (в GitLab — роль Developer, а не Maintainer), включайте двухфакторную аутентификацию, не кладите в KB персональные данные клиентов (152-ФЗ) и внутренние пароли. Отключение проверки SSH-ключей хоста (`StrictHostKeyChecking no`) ради удобства — прямой путь к MITM. Учебный пароль `Lab#2026-vektor` и открытая шара `Obshchee` — удобство стенда; в боевой среде так нельзя: внутренние runbook'и живут в вики с разграничением доступа.

## 7. Вопросы на собеседовании

**1. Чем runbook отличается от статьи в базе знаний и как вы решаете, что пора документировать?**

Ответ: runbook — пошаговая процедура для инженера с предусловиями, проверкой и откатом; статья KB может быть объяснением, how-to для пользователя или разбором инцидента. Документирую по триггерам: повторное обращение (второй одинаковый тикет за месяц), действие, которое делается редко и по памяти (восстановление контроллера домена), передача знания новичку, инцидент с простоем. Правило: если объяснял одно и то же дважды — пиши.
*Что хочет услышать интервьюер:* что вы думаете о следующем инженере и о своём времени, а не «начальник заставил».
*Красный флаг:* «Пишу, когда есть свободное время» — значит, никогда.

**2. Как вы обеспечиваете актуальность базы знаний?**

Ответ: у каждого документа есть владелец и дата последней проверки; шаблон содержит поле `last_reviewed`; при изменении инфраструктуры правка документации входит в Definition of Done задачи; раз в квартал — ревизия топ-10 runbook'ов и обязательный «прогон» на стенде; устаревшее не удаляем молча, а помечаем «устарело» и ссылаемся на замену. Плюс поиск по KB встроен в процесс: перед диагностикой инженер обязан проверить, есть ли статья.
*Что хочет услышать:* процесс, а не «стараюсь».
*Красный флаг:* «У нас KB ведёт один человек» — единая точка отказа.

**3. Что такое коммит и ветка в Git? Чем `commit` отличается от `push`?**

Ответ: коммит — неизменяемый снимок дерева файлов с автором, сообщением и ссылкой на родителя, идентифицируется хешем; ветка — просто подвижный указатель на коммит. `commit` фиксирует изменения локально, `push` передаёт объекты и обновляет ссылки на удалённом репозитории по SSH/HTTPS. Merge-конфликт возникает, когда обе стороны изменили одни и те же строки относительно общего предка.
*Что хочет услышать:* понимание распределённости («локально можно коммитить без сети») и модели данных.
*Красный флаг:* «Git — это облако для файлов» или «ветка — это копия папки».

**4. В репозиторий случайно закоммитили пароль администратора. Ваши действия?**

Ответ: сначала **меняем сам пароль/ключ** — он уже скомпрометирован, история тут вторична. Затем чистим историю (`git filter-repo` или BFG Repo-Cleaner), force-push, просим коллег переклонировать, инвалидируем кэши CI, проверяем, не попал ли секрет в артефакты и бэкапы. Потом профилактика: pre-commit-хук со сканером секретов, `.gitignore`, секреты — в хранилище, доступ к репозиторию — по минимальным правам.
*Что хочет услышать:* порядок «ротация → очистка → профилактика».
*Красный флаг:* «Просто сделаю revert» — пароль останется в истории.

**5. Как вы документируете инцидент после решения?**

Ответ: короткая запись по шаблону: симптом и влияние (кто и сколько пострадал), таймлайн, гипотезы и что проверили, корневая причина (не «перезапустили спулер», а «драйвер печати копил задания после смены формата бумаги»), действия по устранению, что сделали, чтобы не повторилось, и ссылка на обновлённый runbook. Для крупных инцидентов — отдельный RCA-документ без поиска виноватых.
*Что хочет услышать:* что вы отделяете симптом от причины и доводите до профилактики.
*Красный флаг:* «Пишу «решено» в тикете и всё».
