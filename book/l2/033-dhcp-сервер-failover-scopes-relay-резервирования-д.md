# DHCP-сервер: failover, scopes, relay, резервирования, диагностика конфликтов

## 1. Введение (зачем это нужно в реальной работе)

Понедельник, 9:12. В тикете от Марии Петровой (WIN10-CL02, HR) написано: «Доброе утро! Вчера всё работало, сегодня компьютер пишет «Обнаружен конфликт IP-адресов», нет доступа к \\FS01\HR и к 1С. У Иванова тоже утром интернет отваливался. Срочно, у нас отчёт». Через десять минут — тикет от Алексея Сидорова (склад): «Терминал на складе не получает адрес, горит «Сеть без доступа к интернету»».

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

DHCP — прикладной протокол поверх UDP (модель OSI: L7, транспорта — UDP). Порты: **сервер слушает UDP/67**, **клиент — UDP/68**. В DHCPv6 (не наш основной сценарий) — UDP/546 клиент и 547 сервер.

Обмен классический, четыре шага **DORA**:
1. **DHCPDISCOVER** — клиент без адреса шлёт broadcast `255.255.255.255` с источником `0.0.0.0`.
2. **DHCPOFFER** — сервер предлагает адрес.
3. **DHCPREQUEST** — клиент просит именно этот адрес (broadcast, чтобы все DHCP-серверы в сегменте узнали, чьё предложение принято).
4. **DHCPACK** — сервер подтверждает и передаёт параметры (опции): шлюз (3), DNS (6), домен (15), время аренды (51).

Ключевое понятие — **scope (область)**: диапазон адресов под одну подсеть плюс опции для неё. Внутри scope живут:
- **exclusion range (исключение)** — адреса, которые сервер не выдаёт никогда (статический диапазон под серверы, принтеры, коммутаторы);
- **reservation (резервирование)** — привязка конкретного адреса к MAC (Client ID) клиента; адрес выдаётся только этому устройству;
- **lease (аренда)** — запись «адрес X выдан клиенту Y до времени Z». Состояния аренды: активна, истекла, освобождена, отклонена (declined — сервер обнаружил, что адрес уже занят).

**Проверка конфликтов.** Перед выдачей адреса Windows DHCP (если включён `ConflictDetectionAttempts`) делает ICMP-эхо (ping) на адрес. Ответил кто-то — адрес помечается как занятый (declined) и клиенту не предлагается. По умолчанию попыток 0, то есть проверки нет.

**Relay (ретранслятор).** DHCPDISCOVER — broadcast, он не проходит через маршрутизатор. Если подсеть без своего DHCP-сервера, на её шлюзе поднимают relay: он принимает broadcast, подставляет в поле **giaddr** (gateway IP address) свой адрес интерфейса, смотрящего в эту подсеть, и отправляет запрос **unicast** на DHCP-сервер. Сервер выбирает scope **по giaddr**, а не по адресу источника, и отвечает ретранслятору, тот раздаёт клиенту. Дополнительно relay может вставлять **option 82** (relay agent information) — по нему потом можно политиками различать порт/коммутатор клиента (RFC 3046).

**Авторизация в AD.** DHCP-сервер — член домена; чтобы он начал выдавать адреса, его объект должен быть авторизован в AD (`Add-DhcpServerInDC`). Неавторизованный сервер в домене адреса не выдаёт — это защита от «левого» DHCP, который раздаст свой шлюз и уведёт трафик.

**Failover.** Начиная с Windows Server 2012 два DHCP-сервера объединяются в отношение failover и реплицируют scopes, резервирования и аренды по **TCP/647** (плюс аутентификация общим секретом). Два режима:
- **Load balance** — оба сервера активны, делят пул в заданной пропорции (например 50/50). Хорошо, когда оба сервера рядом и доступны.
- **Hot standby** — один активный, второй в горячем резерве; резервному оставляют `ReservePercent` адресов (по умолчанию 5%), чтобы он мог выдавать адреса при падении основного, а перекрытия не возникало. `MaxClientLeadTime` (по умолчанию 1 час) — насколько «вперёд» резервный может продлевать аренды, выданные основным.

```text
    VMnet8 10.10.10.0/24                        VMnet10 10.10.20.0/24 (DMZ)
 ┌────────────────────────────────┐          ┌──────────────────────────────┐
 │ DC01 10.10.10.10  DHCP+DNS     │          │ WEB01 10.10.20.10            │
 │ DC02 10.10.10.11  DHCP (L2)    │◄───┐     │ (нужен адрес по DHCP)        │
 │ WIN11-CL01 / WIN10-CL02: DHCP  │    │     └───────────▲──────────────────┘
 │ пул 10.10.10.100–10.10.10.150  │    │                 │ DHCPDISCOVER (broadcast)
 └────────────────────────────────┘    │                 │
              ▲ unicast UDP/67          │                 │
              │ giaddr = 10.10.20.1     │                 │
        ┌─────┴────────────────────────┴─────────────────┴──────┐
        │ GW01: 10.10.10.3 (VMnet8) / 10.10.20.1 (VMnet10)      │
        │ роль: маршрутизатор + DHCP relay (dhcrelay)           │
        └───────────────────────────────────────────────────────┘

 Failover hot standby:  DC01 (Active) ──TCP/647──► DC02 (Standby, резерв 5%)
                        State: Normal → PartnerDown → Normal
```

## 3. Аналогия из жизни

Представь стойку выдачи ключей в большой гостинице. **Scope** — это список номеров одного корпуса. **Lease** — формуляр: «номер 512 выдан гостю Иванову до пятницы»; если гость не продлил, номер считается свободным и его могут отдать другому. **Reservation** — именная бронь: номер 101 всегда за постоянным клиентом, даже если он не приехал. **Exclusion** — номера, где живёт персонал и техника, их не продают вообще. **Relay** — швейцар в дальнем корпусе с рацией: сам ключей не хранит, но передаёт заявку на главную стойку и относит ключ гостю. **Failover** — вторая стойка в соседнем холле: пока первая работает, вторая только переписывает себе формуляры, а если первая закрылась — начинает выдавать ключи сама, но только из тех номеров, что оставили ей в резерве.

Аналогия ломается в одном месте: администратор гостиницы не может постучать в номер и проверить, что там пусто, — а DHCP именно это и делает (ping перед выдачей адреса, conflict detection).

## 4. Практика и команды

Все команды PowerShell выполняются на DC01 (или с `-ComputerName DC02`), если не указано иное.

**1. Посмотреть области и их состояние**
```powershell
Get-DhcpServerv4Scope -ComputerName DC01 | Format-Table ScopeId,Name,StartRange,EndRange,State,SubnetMask
```
`ScopeId` — идентификатор области (это адрес подсети), `State` — Active/Inactive. Вывод:
```text
ScopeId     Name        StartRange     EndRange       State  SubnetMask
10.10.10.0  Office-LAN  10.10.10.100   10.10.10.150   Active 255.255.255.0
```

**2. Утилизация пула (главный метрик здоровья DHCP)**
```powershell
Get-DhcpServerv4ScopeStatistics -ComputerName DC01
```
Ключевые поля: `Free` (свободно), `InUse` (выдано), `Reserved`, `PendingOffer`, `PercentageInUse`. Смотреть на `PercentageInUse`: 85%+ — пора расширять пул, а не ждать заявки «не получает адрес».

**3. Кто что занял**
```powershell
Get-DhcpServerv4Lease -ComputerName DC01 -ScopeId 10.10.10.0 |
  Sort-Object LeaseExpiryTime | Format-Table IPAddress,ClientId,HostName,AddressState,LeaseExpiryTime
```
`ClientId` — MAC клиента, `AddressState` — Active/Declined/Expired/Inactive. `Declined` = конфликт или «битая» аренда.

**4. Исключения и резервирования**
```powershell
Add-DhcpServerv4ExclusionRange -ComputerName DC01 -ScopeId 10.10.10.0 `
  -StartRange 10.10.10.100 -EndRange 10.10.10.105
Get-DhcpServerv4Reservation -ComputerName DC01 -ScopeId 10.10.10.0
Add-DhcpServerv4Reservation -ComputerName DC01 -ScopeId 10.10.10.0 `
  -IPAddress 10.10.10.120 -ClientId 00-0C-29-AA-BB-CC -Name "WIN11-CL01" -Description "ivanov, бухгалтерия"
```
`-ClientId` — MAC без разделителей тоже принимается (`000C29AABBCC`). `-Name`/`-Description` — только для людей, на выдачу не влияют.

**5. Проверка конфликтов и журнал аудита**
```powershell
Set-DhcpServerSetting -ComputerName DC01 -ConflictDetectionAttempts 2
Set-DhcpServerAuditLog -ComputerName DC01 -Enable $true -Path "C:\Windows\System32\dhcp"
Get-Content C:\Windows\System32\dhcp\DhcpSrvLog-Wed.log -Tail 20
```
Файл журнала — `DhcpSrvLog-<ДеньНедели>.log`, по строке на событие. Коды: 10 — новая аренда, 11 — продление, 12 — освобождение, 13 — адрес **отклонён** (конфликт), 14 — аренда истекла. Ищи конфликты:
```powershell
Select-String -Path C:\Windows\System32\dhcp\DhcpSrvLog-*.log -Pattern "^13,"
```

**6. Опции области (то, что реально ломает «интернет»)**
```powershell
Get-DhcpServerv4OptionValue -ComputerName DC01 -ScopeId 10.10.10.0
Set-DhcpServerv4OptionValue -ComputerName DC01 -ScopeId 10.10.10.0 `
  -Router 10.10.10.2 -DnsServer 10.10.10.10 -DnsDomain corp.vektor.lab
```
Опция 003 (Router) — шлюз по умолчанию, 006 — DNS, 015 — домен для поиска. 80% «нет интернета» после правок сети — это неверная 003.

**7. Авторизация сервера в AD**
```powershell
Get-DhcpServerInDC
Add-DhcpServerInDC -DnsName dc02.corp.vektor.lab -IPAddress 10.10.10.11
```
Выполняется на самом DHCP-сервере; требует прав администратора предприятия (Enterprise Admins) или делегирования. Неавторизованный сервер молча не выдаёт адреса.

**8. Настройка и проверка failover**
```powershell
Get-DhcpServerv4Failover -ComputerName DC01
Add-DhcpServerv4Failover -ComputerName DC01 -Name "DC01-DC02" `
  -PartnerServer DC02.corp.vektor.lab -ScopeId 10.10.10.0,10.10.20.0 `
  -ServerRole Active -ReservePercent 5 -MaxClientLeadTime 01:00:00 `
  -EnableAuth $true -SharedSecret "Lab#2026-vektor" -Force
Invoke-DhcpServerv4FailoverReplication -ComputerName DC01 -Name "DC01-DC02" -Force
```
`-ServerRole Active` = режим hot standby, этот сервер активный (партнёр станет Standby автоматически). Для балансировки вместо `-ServerRole`/`-ReservePercent` задают `-LoadBalancePercent 50`. `Invoke-...Replication` гонит изменения немедленно, не дожидаясь периода репликации.

**9. Клиент на Windows**
```powershell
ipconfig /all
ipconfig /release
ipconfig /renew
Get-NetIPConfiguration -Detailed
Get-NetAdapter | Format-Table Name,MacAddress,Status
```
В `ipconfig /all` смотри поля **DHCP Enabled**, **Lease Obtained/Expires**, **DHCP Server** (по нему видно, кто реально выдал адрес — DC01 или DC02), **Default Gateway**, **DNS Servers**. `/release` освобождает аренду, `/renew` запрашивает заново.

**10. Клиент и сервер на Linux (UBU01, GW01)**
```bash
ip -br a                                  # какие интерфейсы и адреса реально есть
networkctl status ens33                   # состояние линка и DHCP по интерфейсу
journalctl -u systemd-networkd -n 50 --no-pager
sudo tcpdump -i any -n -vv 'udp port 67 or udp port 68'
```
Ubuntu Server 24.04 по умолчанию управляется netplan + systemd-networkd; `dhclient` вручную на таком хосте запускать не надо — будет конфликт двух менеджеров. `tcpdump` по портам 67/68 — самый быстрый способ понять, доходит ли DISCOVER до сервера и приходит ли OFFER обратно.

**11. Relay на Debian (GW01)**
```bash
sudo apt install isc-dhcp-relay
sudo nano /etc/default/isc-dhcp-relay     # SERVERS="10.10.10.10"  INTERFACES="ens34"
sudo systemctl restart isc-dhcp-relay
journalctl -u isc-dhcp-relay -f
```
`SERVERS` — адрес DHCP-сервера, `INTERFACES` — интерфейс, смотрящий в «глухую» подсеть (в нашем случае DMZ). Альтернатива для ручной отладки: `sudo dhcrelay -i ens34 10.10.10.10` (не забудь потом убить процесс). На Cisco аналог — `ip helper-address` на SVI, на MikroTik — `/ip dhcp-relay`.

**12. Старый способ посмотреть области (пригодится в чужом окружении)**
```cmd
netsh dhcp server \\DC01 show scope
netsh dhcp server \\DC01 scope 10.10.10.0 show clients
```
`netsh` работает и на серверах, где нет модуля DhcpServer в PowerShell.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия
Стенд L1 + L2 в состоянии «домен работает»: DC01 (10.10.10.10, AD DS, DNS, DHCP с областью 10.10.10.0/24, пул 10.10.10.100–10.10.10.150), FS01 (10.10.10.20), WIN11-CL01 и WIN10-CL02 (получают адреса по DHCP), UBU01 (10.10.10.30), ASTRA01 (10.10.10.31). Для этой главы добавляются две машины уровня L2 из таблицы: **DC02** (10.10.10.11, Windows Server 2022, введён в домен, статический IP, DNS = 10.10.10.10) и **GW01** (Debian 12, два адаптера: VMnet8 → 10.10.10.3, VMnet10 → 10.10.20.1). WEB01 (10.10.20.10) уже стоит в DMZ и используется в лабораторной как клиент relay — на время опыта переведём его на DHCP и потом вернём статику. Если DC02 или GW01 ещё нет — создай их по описанию стенда (это часть предусловия, а не темы).

### Снапшот
В VMware Workstation: выключить/приостановить ВМ → **VM → Snapshot → Take Snapshot**, имя `before-l2-033`. Сделать для **DC01, DC02, GW01, WEB01, WIN11-CL01, WIN10-CL02**. Для включённых ВМ снапшот тоже снимается (память не сохраняем, только диск — так меньше размер).

### Шаги

1. **DC01 — зафиксировать исходное состояние.** `Get-DhcpServerv4Scope`, `Get-DhcpServerv4ScopeStatistics`, `Get-DhcpServerv4Lease -ScopeId 10.10.10.0`. Ожидаемо: одна область Active, 5–10 аренд, `PercentageInUse` небольшой. Записать вывод в `stand-log.md`.

2. **DC01 — включить аудит и проверку конфликтов.** `Set-DhcpServerAuditLog -Enable $true -Path "C:\Windows\System32\dhcp"`, `Set-DhcpServerSetting -ConflictDetectionAttempts 2`. Проверить: `Get-DhcpServerSetting` показывает `ConflictDetectionAttempts : 2`. Ожидаемо: в `C:\Windows\System32\dhcp\` появляется файл `DhcpSrvLog-<день>.log`.

3. **DC01 — исключение под статику.** `Add-DhcpServerv4ExclusionRange -ScopeId 10.10.10.0 -StartRange 10.10.10.100 -EndRange 10.10.10.105`. Ожидаемо: `Get-DhcpServerv4ExclusionRange -ScopeId 10.10.10.0` показывает диапазон; в статистике `Free` уменьшилось на 6. Смысл: «голову» пула отдаём под технику.

4. **DC01 — резервирование под WIN11-CL01.** На WIN11-CL01 выполнить `Get-NetAdapter | Format-Table Name,MacAddress`, взять MAC. На DC01: `Get-DhcpServerv4Lease -ScopeId 10.10.10.0 | Where-Object HostName -like "*WIN11*"` — узнать текущий адрес, затем **удалить эту аренду**: `Remove-DhcpServerv4Lease -IPAddress 10.10.10.101` (подставь свой). Потом `Add-DhcpServerv4Reservation -ScopeId 10.10.10.0 -IPAddress 10.10.10.120 -ClientId <MAC> -Name "WIN11-CL01"`. Ожидаемо: `Get-DhcpServerv4Reservation` показывает запись. На WIN11-CL01: `ipconfig /release; ipconfig /renew` → адрес 10.10.10.120.

5. **DC01 — создать область для DMZ.** `Add-DhcpServerv4Scope -Name "DMZ" -StartRange 10.10.20.100 -EndRange 10.10.20.110 -SubnetMask 255.255.255.0 -State Active`, затем `Set-DhcpServerv4OptionValue -ScopeId 10.10.20.0 -Router 10.10.20.1 -DnsServer 10.10.10.10 -DnsDomain corp.vektor.lab`. Ожидаемо: в `Get-DhcpServerv4Scope` две области. Если консоль помечает область как «неприменимую» — это нормально: интерфейса в 10.10.20.0/24 у DC01 нет, адреса пойдут только через relay.

6. **DC01 — маршрут до DMZ.** Сервер должен уметь ответить на giaddr 10.10.20.1: `New-NetRoute -DestinationPrefix 10.10.20.0/24 -NextHop 10.10.10.3 -InterfaceIndex (Get-NetAdapter | Where-Object Status -eq Up | Select-Object -First 1 -ExpandProperty ifIndex)`. Проверить `Get-NetRoute -DestinationPrefix 10.10.20.0/24` и `Test-NetConnection 10.10.20.1` (пинг на GW01 может не отвечать — это нормально, главное маршрут есть).

7. **DC02 — установить и авторизовать роль DHCP.** `Install-WindowsFeature DHCP -IncludeManagementTools`, затем (после перезапуска консоли/сессии) — `Add-DhcpServerSecurityGroup`, `Restart-Service DHCPServer`, `Add-DhcpServerInDC -DnsName dc02.corp.vektor.lab -IPAddress 10.10.10.11`. Ожидаемо: `Get-DhcpServerInDC` показывает **две** записи.

8. **DC01 — настроить failover.** Команда из раздела 4 (п.8) с `-ServerRole Active -ReservePercent 5 -ScopeId 10.10.10.0,10.10.20.0`. Ожидаемо: `Get-DhcpServerv4Failover -ComputerName DC01` показывает отношение `DC01-DC02`; на DC02 в `Get-DhcpServerv4Scope -ComputerName DC02` появились обе области (в режиме hot standby они неактивны, но конфигурация есть).

9. **DC01 — проверить репликацию.** Создать резервирование `10.10.10.121` с произвольным MAC, затем `Invoke-DhcpServerv4FailoverReplication -Name "DC01-DC02" -Force`. Ожидаемо: `Get-DhcpServerv4Reservation -ComputerName DC02 -ScopeId 10.10.10.0` показывает ту же запись.

10. **GW01 — поднять relay.** `ip -br a` (уточнить имена: офисный и DMZ-интерфейсы), `apt install isc-dhcp-relay`, прописать `SERVERS="10.10.10.10"` и `INTERFACES="<DMZ-интерфейс>"` в `/etc/default/isc-dhcp-relay`, `systemctl restart isc-dhcp-relay`. Проверить, что nftables не режет UDP 67/68 на DMZ-интерфейсе (`nft list ruleset`), при необходимости добавить `udp dport 67 accept` в input.

11. **WEB01 — проверить relay на живом клиенте.** В `/etc/netplan/` взять файл конфигурации (`ls /etc/netplan/`), временно поставить `dhcp4: true` на интерфейс DMZ, `sudo netplan apply`, `ip -br a`. Ожидаемо: адрес из 10.10.20.100–110, шлюз 10.10.20.1, DNS 10.10.10.10 (`ip route`, `resolvectl status`). Параллельно на DC01 `Get-DhcpServerv4Lease -ScopeId 10.10.20.0` показывает новую аренду, а в логе — событие 10.

12. **Проверка переключения failover.** На DC01: `Stop-Service DHCPServer -Force`. На WIN11-CL01: `ipconfig /release; ipconfig /renew`. ## 6. Ошибки новичков и безопасность

1. **Два DHCP-сервера в одной подсети без failover.** → Клиенты получают адреса то от одного, то от другого, в пулах появляются дубликаты и конфликты. → Правильно: один сервер, либо failover, либо явное разделение пула (split-scope) с разными диапазонами.
2. **Резервирование адреса, который уже выдан другой машине.** → Резервирование не применяется, пока старая аренда жива; клиент продолжает получать «чужой» адрес. → Сначала удалить аренду (`Remove-DhcpServerv4Lease`), потом создавать резервирование, потом `/release` + `/renew` на клиенте.
3. **Статика серверов внутри пула вместо exclusion.** → DHCP рано или поздно выдаст адрес FS01 кому-то ещё. → Все статические адреса — в исключения или вне пула.
4. **`ConflictDetectionAttempts` = 5–10 «чтобы надёжнее».** → Каждая выдача удлиняется на секунды, при массовом включении после сбоя клиенты получают адреса минутами. → 1–2 попытки достаточно.
5. **Relay без маршрута до giaddr на DHCP-сервере.** → DISCOVER доходит, ответить сервер не может; в логах сервера аренда есть, у клиента — нет. → Проверять маршрут до подсети giaddr и `tcpdump` на ретрансляторе.
6. **Забыли авторизовать DHCP в AD.** → Сервер молча не выдаёт адреса, ищут проблему в клиентах и коммутаторах. → `Get-DhcpServerInDC` — одна из первых проверок.
7. **Слишком короткий lease (например 1 час) на весь офис.** → Постоянный фон DORA-трафика и нагрузка на сервер; при падении DHCP офис встаёт за час. → Офис — 8 дней (по умолчанию), гостевые/переговорные сети — короткий lease.

### Безопасность
- **Нельзя ставить DHCP на контроллер домена в продакшене** (в лабе мы это делаем осознанно: DC02 — вторая ВМ и удобная площадка). Роль DHCP на DC расширяет поверхность атаки на тир-0 и нарушает тиринг из урока 25. Правильно: отдельный сервер-член домена.
- **Нельзя оставлять неавторизованный/неучтённый DHCP в сети.** «Левый» DHCP-сервер (роутер из дома, тестовый ноутбук) раздаёт свой шлюз и DNS — это готовый MITM. Защита: DHCP snooping на коммутаторах, где он есть; контроль авторизации в AD; сегментация.
- **Проверка конфликтов пингом** — это ICMP, который многие хосты и файрволы режут; не полагайся на неё как на гарантию. В боевой среде конфликты ловят по журналу событий 13 и по ARP-мониторингу.
- **Пароль failover-отношения (shared secret)** — это учётные данные: не хранить в заметках на общем диске, не переиспользовать доменный пароль (на стенде мы используем единый учебный пароль только потому, что это стенд).
- **Журнал аудита DHCP содержит MAC-адреса и имена хостов** — это персональные данные в смысле 152-ФЗ при связке с ФИО; не выкладывай логи в открытые чаты.

## 7. Вопросы на собеседовании

**Вопрос 1. Клиент не получает адрес по DHCP. Опиши, как будешь разбираться.**
Ответ: иду по слоям. L1–L2: линк, кабель/виртуалка, состояние адаптера (`Get-NetAdapter`, `ip -br a`). L3: есть ли адрес 169.254.x.x (APIPA — значит DISCOVER ушёл, OFFER не пришёл). Дальше смотрю, жив ли DHCP-сервер и авторизован ли (`Get-DhcpServerInDC`), есть ли свободные адреса (`Get-DhcpServerv4ScopeStatistics`), правильные ли опции, не режет ли firewall UDP 67/68, есть ли relay и маршрут до giaddr. Снимаю `tcpdump` на клиенте и на сервере — видно, на каком шаге DORA обрывается. Смотрю `DhcpSrvLog-*`.
*Что хочет услышать:* системный порядок «физика → адресация → сервис → логи», а не «перезагрузил и заработало».
*Красный флаг:* «сразу переустановлю драйвер сетевой» / «включу статический адрес и закрою тикет».

**Вопрос 2. Зачем нужен DHCP relay и что такое giaddr?**
Ответ: DISCOVER — broadcast, маршрутизатор его не пропускает, поэтому в подсети без своего DHCP-сервера на шлюзе поднимают relay. Он принимает broadcast, ставит в поле giaddr адрес своего интерфейса, смотрящего в эту подсеть, и отправляет запрос unicast на сервер. Сервер выбирает scope именно по giaddr (а не по source IP) и отвечает ретранслятору. Плюс relay может вставлять option 82, по которому на сервере строятся политики «какому порту/коммутатору какие опции».
*Что хочет услышать:* «scope выбирается по giaddr», «unicast между relay и сервером», «нужен маршрут в обе стороны».
*Красный флаг:* «relay просто пробрасывает broadcast дальше» — неверно, broadcast через L3 не ходит.

**Вопрос 3. Как сделать DHCP отказоустойчивым в Windows?**
Ответ: два сервера-члена одного домена, роль DHCP на обоих, оба авторизованы в AD, между ними TCP/647. Создаётся отношение failover с именем, общим секретом и списком scope. Режимы: load balance (делят пул, например 50/50, оба активны) и hot standby (один активный, второй в резерве с `ReservePercent`, по умолчанию 5%, и `MaxClientLeadTime`). Реплицируются scope, опции, резервирования и аренды; проверка — `Get-DhcpServerv4Failover`, форсировать — `Invoke-DhcpServerv4FailoverReplication`. Failover ≠ бэкап: конфигурацию всё равно нужно сохранять (`Export-DhcpServer`).
*Что хочет услышать:* требования (домен, авторизация, порт), разницу режимов и что hot standby не даёт выдавать весь пул резерву.
*Красный флаг:* «просто поставлю второй DHCP с тем же пулом» — это гарантированные конфликты.

**Вопрос 4. Чем reservation отличается от exclusion и от статики на клиенте?**
Ответ: exclusion — диапазон, который сервер **никогда** не выдаёт (под серверы, принтеры, статику). Reservation — привязка адреса к MAC: адрес остаётся в пуле, но выдаётся только этому устройству; остальные его не получат. Статика на клиенте — адрес настроен руками, DHCP о нём не знает вообще; если он попал в пул — будет конфликт. Практика: серверы/сетевое оборудование — статика + exclusion; рабочие места с требованием фиксированного адреса — reservation, клиент при этом остаётся на DHCP.
*Что хочет услышать:* понимание, что reservation управляется централизованно, а статика — нет.
*Красный флаг:* «это одно и то же, просто разными кнопками».

**Вопрос 5. В сети появился конфликт IP. Как найдёшь виновника и что сделаешь с адресом?**
Ответ: на пострадавшем клиенте `ipconfig /all` и `arp -a` — смотрю MAC второго устройства; `arping`/скан подсети, чтобы найти хост по MAC, дальше по MAC ищу порт на коммутаторе (MAC-таблица) или ВМ в гипервизоре. На DHCP: аренда на этот адрес (кому законно выдан), состояние Declined, в журнале — событие 13. Решение: вернуть нарушителя на DHCP, затем Reconcile/удаление отклонённой аренды, чтобы адрес вернулся в пул, и продление аренды у легального клиента. Профилактика: проверка конфликтов на сервере, exclusion под статику, DHCP snooping.
*Что хочет услышать:* «сначала нашёл второго участника конфликта, потом чистил состояние на сервере».
*Красный флаг:* «просто перевыдам клиенту другой адрес» — конфликт останется в сети.
