# Принципы мониторинга: метрики, логи, трейсы, алерты, SLI/SLO

## 1. Введение (зачем это нужно в реальной работе)

Заявка в поддержку «Вектора»:

> **Пользователь:** petrova (HR), ВМ WIN10-CL02
> **Что написала:** «С утра папка `\\FS01\HR` то открывается, то нет. Сейчас открылась. Как вы вообще узнаёте, что у вас что-то сломалось? Или только когда мы напишем?»
> **Срочность:** Средняя

Вот это «как вы узнаёте» — и есть тема главы. Пока сервис работает, никто не звонит; ломается — звонят пользователи, а не система. Задача L2 — перевернуть это: система замечает первой, а ты приходишь на готовый сигнал с контекстом, а не начинаешь с нуля.

Мониторинг встречается в работе каждый день, потому что любая заявка «то работает, то не работает» — это либо отсутствие метрики, либо отсутствие алерта, либо алерт, который все привыкли игнорировать. Ты будешь смотреть на графики, читать логи, считать доступность и доказывать руководству, что сервис действительно лежит 40 минут, а не «наверное, что-то было».

После этой главы ты должен уметь: объяснить разницу между метрикой, логом и трейсом и выбрать нужный инструмент под задачу; снять базовые метрики с Linux и Windows без установки чего-либо; прочитать лог и найти в нём причину; сформулировать SLI и SLO для конкретного сервиса; посчитать бюджет ошибок; спроектировать алерт так, чтобы он не превратился в спам.

Конкретные системы (Zabbix, Prometheus, Grafana, Graylog/Loki) — в уроках 89–91. Сегодня — принципы, на которых они все стоят.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

### Три столпа наблюдаемости

**Наблюдаемость (observability)** — способность понять внутреннее состояние системы по её внешним данным. Данных три вида:

| | Метрика | Лог | Трейс |
|---|---|---|---|
| Что это | Число + время + метки | Текст/JSON о событии | Цепочка вызовов одного запроса |
| Объём | Маленький, дешёвый | Большой, дорогой | Средний |
| Отвечает на | «Что и насколько?» | «Что именно произошло?» | «Где именно тормозит?» |
| Пример | CPU 87 %, 12:04:31 | `sshd: Failed password for ivanov` | запрос 420 мс: 30 мс app → 380 мс SQL |
| Хранение | TSDB (time-series DB) | Файлы, Elasticsearch, Loki | Jaeger/Tempo |

Метрика говорит «плохо», лог — «почему», трейс — «где в цепочке». В 90 % работы L2 хватает метрик и логов; трейсы нужны, когда приложение состоит из нескольких сервисов (веб-фронт → API → 1С → БД) и непонятно, кто из них виноват.

### Как данные попадают в систему

```text
   [объект: DC01, FS01, UBU01, WIN11-CL01]
          │            │            │
   агент/exporter   syslog       synthetic-проба
   (pull/push)      (UDP 514)    (ping / TCP / HTTP)
          │            │            │
          ▼            ▼            ▼
   ┌─────────────────────────────────────┐
   │  сбор + нормализация + метки        │  (host, service, env, severity)
   └─────────────────────────────────────┘
          │                    │
          ▼                    ▼
   ┌──────────────┐     ┌─────────────┐
   │ TSDB/хранилище│     │ лог-хранилище│
   └──────────────┘     └─────────────┘
          │                    │
          └────────┬───────────┘
                   ▼
        ┌────────────────────┐
        │ правила алертов    │──► канал: TG / e-mail / SMS / звонок
        │ (порог + for +     │
        │  severity + runbook)│
        └────────────────────┘
                   ▼
             дежурный L1/L2 → реакция → постмортем
```

Ключевые протоколы и порты (пригодятся в 89–91): **SNMP** — 161/udp (опрос), 162/udp (traps); **syslog** — 514/udp (реже 6514/tcp с TLS); **Zabbix** — 10051/tcp (сервер), агент 10050/tcp; **node_exporter** — 9100/tcp, **windows_exporter** — 9182/tcp; **Prometheus** — 9090/tcp; **Grafana** — 3000/tcp; **Loki** — 3100/tcp; **Elasticsearch** — 9200/tcp; **OTLP (трейсы)** — 4317/tcp (gRPC), 4318/tcp (HTTP). По модели OSI: пинг — L3, проверка TCP-порта — L4, HTTP-проба и syslog — L7.

### Pull vs push, black-box vs white-box

**Pull**: сервер сам опрашивает агентов раз в 15–60 с (Prometheus). Плюс: сразу видно, если цель пропала. **Push**: агент сам отправляет данные (Zabbix active, syslog, метрики приложений). Плюс: работает через NAT и из DMZ.

**White-box** — смотрим изнутри (агент на хосте: загрузка CPU, длина очереди). **Black-box** — снаружи, как пользователь (пинг, TCP-коннект, HTTP 200). Только black-box отвечает на вопрос «сервис реально доступен?», поэтому нужны оба.

### Методики выбора метрик

**Четыре золотых сигнала** (из практики Google SRE): задержка (latency), трафик (traffic/нагрузка), ошибки (errors), насыщение (saturation — насколько ресурс близок к пределу).

**RED** — для сервисов: **R**ate (запросов/с), **E**rrors (доля ошибок), **D**uration (время ответа).

**USE** — для ресурсов: **U**tilization (занятость), **S**aturation (очередь), **E**rrors (ошибки). Для диска: %util, длина очереди, ошибки ввода-вывода.

### SLI, SLO, SLA и бюджет ошибок

- **SLI (Service Level Indicator)** — измеримый показатель: «доля успешных TCP-коннектов к FS01:445», «p95 времени ответа API».
- **SLO (Service Level Objective)** — цель по SLI: «доступность 99,5 % за календарный месяц».
- **SLA** — юридический договор с заказчиком с санкциями. SLO всегда строже SLA, иначе штрафы неизбежны.
- **Error budget (бюджет ошибок)** = 100 % − SLO. Это не «сколько можно ломаться», а разрешение рисковать: если бюджет цел — можно катить изменения; кончился — замораживаем изменения и чиним надёжность.

| SLO за 30 дней | Допустимый простой |
|---|---|
| 99 % | 7 ч 12 мин |
| 99,5 % | 3 ч 36 мин |
| 99,9 % | 43 мин |
| 99,95 % | 21 мин |

### Алерты

Правило простое: **алерт должен быть про симптом, который видит пользователь, а не про причину**. «CPU 95 %» — не алерт, это повод посмотреть график. «FS01:445 недоступен 3 проверки подряд» — алерт.

Обязательные атрибуты: **условие** (метрика, порог), **длительность `for`** (сколько времени условие держится), **severity** (Critical / Warning / Info), **владелец**, **канал**, **runbook** (что делать по шагам). Без `for` любой короткий пик будит дежурного в 4 утра.

## 3. Аналогия из жизни

Представь больницу. **Метрики** — это приборы у койки: пульс, давление, температура, снимаются каждые 5 минут и складываются в график. **Логи** — история болезни: «в 14:20 введён препарат, в 14:35 — аллергическая реакция». **Трейсы** — маршрутный лист пациента: приёмный покой (5 мин) → анализ крови (40 мин) → УЗИ (15 мин) → кабинет врача; видно, что 40 минут ушло на кровь. **Алерт** — сигнал на пост дежурной сестры: «давление ниже 90/60 дольше двух минут». **SLO** — «пациент из приёмного покоя должен попасть к врачу за 60 минут»; **бюджет ошибок** — сколько минут в месяц мы имеем право выбиваться из этого норматива.

Аналогия ломается в одном: приборы в больнице не врут и измерения выбирает врач, а в ИТ метрику выбираешь ты — и очень легко измерять не то, что болит у пользователя.

## 4. Практика и команды

### Linux: снять базовую картину

**1. `uptime` — нагрузка и время работы**
```bash
uptime
# 12:04:31 up 12 days,  3:11,  2 users,  load average: 0,42, 0,55, 0,61
```
Три числа — средняя длина очереди на 1/5/15 минут. Значение сравнивай с числом ядер (`nproc`): 4,00 на 4 ядрах = полная загрузка, выше — очередь.

**2. `vmstat 2 5` — срез за 5 интервалов по 2 с**
```bash
vmstat 2 5
# procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
#  r  b   swpd   free  buff cache   si   so    bi    bo   in   cs us sy id wa st
#  1  0      0 812340 41200 921400    0    0    12    84  410  820  4  1 94  1  0
```
`r` — процессы в очереди (насыщение CPU), `si/so` — своп (любое стабильное значение ≠ 0 это плохо), `wa` — ожидание ввода-вывода, `us+sy` — реальная загрузка процессора.

**3. `free -m` — память**
```bash
free -m
#               total   used   free   shared  buff/cache  available
# Mem:           3936   1120    780       12        2036       2540
# Swap:          2047      0   2047
```
Смотри `available` (а не `free`) и `Swap used`. Растущий swap = не хватает RAM.

**4. `df -h` и `df -i` — место и inode**
```bash
df -h / /var
# Filesystem      Size  Used Avail Use% Mounted on
# /dev/sda2        24G   19G  3,6G  85% /
df -i /
# /dev/sda2      1572864  21044 1551820   2% /
```
85 % — уже Warning: логи и бэкапы добьют за пару дней. `df -i` спасает от классики «место есть, а файлы не создаются» (закончились inode).

**5. `iostat -xz 2 3` — диск (пакет `sysstat`)**
```bash
sudo apt update && sudo apt install -y sysstat
iostat -xz 2 3
# Device  r/s   w/s  rkB/s  wkB/s await r_await w_await aqu-sz %util
# sda    1,20 14,60  30,4  210,8  3,12    1,10    3,40   0,05   4,1
```
`await` (средняя задержка операции, мс): до 10–20 мс для локального диска норм, 100+ — болото. `%util` около 100 % = диск забит.

**6. `ss` — кто слушает и сколько соединений**
```bash
sudo ss -tulpn | grep -E ':(22|445|3128)\b'
# tcp  LISTEN 0 128 0.0.0.0:22  0.0.0.0:*  users:(("sshd",pid=812,fd=3))
ss -s
# TCP: 84 (estab 21, closed 40, orphaned 0, timewait 12)
```
`timewait` в тысячах — приложение не переиспользует соединения; `Recv-Q`/`Send-Q` с ненулевым значением у LISTEN — переполнение очереди accept.

**7. `journalctl` — журнал systemd**
```bash
sudo journalctl --since "1 hour ago" -p warning --no-pager | tail -20
sudo journalctl -u ssh --since today --no-pager | grep -iE "failed|invalid" | tail -5
# May 12 12:41:07 ubu01 sshd[3311]: Failed password for invalid user admin from 10.10.10.100 port 51022 ssh2
```
`-p` — уровень (emerg…debug), `-u` — юнит, `-f` — «хвост» в реальном времени, `--since/--until` — окно. Это первый инструмент поиска причины.

**8. `dmesg` — ядро и железо**
```bash
sudo dmesg -T | grep -iE "oom|killed process|error" | tail -10
```
`-T` — человеческое время. Строка `Out of memory: Killed process` объясняет «сервис сам упал» лучше любых догадок.

**9. `curl -w` — мини-трейс HTTP-запроса**
```bash
curl -s -o /dev/null -w "dns=%{time_namelookup} connect=%{time_connect} ttfb=%{time_starttransfer} total=%{time_total} code=%{http_code}\n" http://10.10.10.30:8080/
# dns=0,000112 connect=0,000431 ttfb=0,002041 total=0,002113 code=200
```
Разбивка по фазам — бедняцкий трейс: `connect` большой → сеть/фаервол; `ttfb` большой при быстром `connect` → тормозит приложение; `total` сильно больше `ttfb` → медленно отдаётся тело.

### Windows: то же самое

**10. `Get-Counter` — счётчики производительности**
```powershell
Get-Counter -Counter '\Processor(_Total)\% Processor Time',
  '\Memory\Available MBytes','\LogicalDisk(C:)\% Free Space',
  '\PhysicalDisk(_Total)\Avg. Disk sec/Transfer' -SampleInterval 5 -MaxSamples 3 |
  ForEach-Object { $_.CounterSamples | Select-Object Path, CookedValue }
# \\dc01\memory\available mbytes    2540
# \\dc01\physicaldisk(_total)\avg. disk sec/transfer  0,004
```
`-SampleInterval` — период, `-MaxSamples` — сколько раз. Ключевые счётчики также: `\System\Processor Queue Length` (>2 на ядро — плохо), `\Memory\Pages/sec` (>1000 — свопинг), `\LogicalDisk(_Total)\Avg. Disk Queue Length`. **Важно:** на русской Windows имена счётчиков локализованы — реальные имена смотри через `Get-Counter -ListSet Processor`.

**11. `typeperf` — сбор в файл на длительное время**
```cmd
typeperf "\Processor(_Total)\% Processor Time" "\Memory\Available MBytes" -si 15 -sc 40 -f CSV -o C:\perf\dc01-baseline.csv
```
`-si` интервал в секундах, `-sc` количество выборок (40 × 15 с = 10 минут), `-o` файл. Так снимают baseline: «как выглядит норма», без которого невозможно отличить аномалию.

**12. `Get-CimInstance Win32_LogicalDisk` — диски**
```powershell
Get-CimInstance Win32_LogicalDisk -Filter "DriveType=3" |
  Select-Object DeviceID,
    @{n='FreeGB';e={[math]::Round($_.FreeSpace/1GB,1)}},
    @{n='SizeGB';e={[math]::Round($_.Size/1GB,1)}}
```
`DriveType=3` — локальные диски (2 — сменные, 4 — сетевые). Альтернатива — WMI-счётчик `Win32_PerfFormattedData_PerfDisk_LogicalDisk`, но CIM проще.

**13. `Get-WinEvent` — журналы событий**
```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625; StartTime=(Get-Date).AddHours(-24)} -MaxEvents 5 |
  Select-Object TimeCreated, @{n='User';e={$_.Properties[5].Value}}, @{n='IP';e={$_.Properties[19].Value}}
```
`4625` — неудачный вход, `4624` — успешный, `4740` — блокировка учётки, `7031/7036` — падение/смена состояния службы. `-FilterHashtable` фильтрует на стороне службы журнала и работает на порядки быстрее, чем `Where-Object`. Номера `Properties[5]`/`[19]` проверяй через `$_.ToXml()`: раскладка полей у событий разная.

**14. Синтетическая проверка порта с замером**
```powershell
(Measure-Command { $c = [Net.Sockets.TcpClient]::new(); $c.Connect('10.10.10.20',445); $c.Close() }).TotalMilliseconds
# 2,41
```
Это и есть SLI «доступность + задержка» в чистом виде — можно крутить циклом и считать процент успехов.

**15. Посчитать бюджет ошибок**
```bash
python3 -c "print('SLO 99.5% → бюджет', round(30*24*60*0.005,1), 'минут в месяц')"
# SLO 99.5% → бюджет 216.0 минут в месяц
```

### Шаги

1. **UBU01.** Готовим рабочую папку и ставим sysstat.
   ```bash
   mkdir -p ~/mon && cd ~/mon
   sudo apt update && sudo apt install -y sysstat
   sar -u 1 3   # если пусто — включить ENABLED="true" в /etc/default/sysstat
   ```
   *Ожидаемо:* три строки с `%user %system %idle`.

2. **UBU01.** Поднимаем временный HTTP-сервис для замеров задержки.
   ```bash
   cd /tmp && nohup python3 -m http.server 8080 --bind 0.0.0.0 > /tmp/http8080.log 2>&1 &
   ss -tulpn | grep 8080
   ```
   *Ожидаемо:* `LISTEN 0.0.0.0:8080`. **Недопустимо в бою:** сервер без аутентификации на все интерфейсы. Здесь безопасно, потому что VMnet8 изолирован на твоём ПК — это чисто учебная заглушка.

3. **DC01.** Снимаем мини-трейс до UBU01 (в Windows Server 2022 `curl.exe` есть из коробки).
   ```powershell
   curl.exe -s -o NUL -w "dns=%{time_namelookup} connect=%{time_connect} ttfb=%{time_starttransfer} total=%{time_total} code=%{http_code}`n" http://10.10.10.30:8080/
   ```
   *Ожидаемо:* `code=200`, `total` — единицы миллисекунд. Запиши числа в `sli-slo.md` как эталон LAN.

4. **DC01.** Снимаем baseline счётчиков производительности в файл.
   ```powershell
   New-Item -ItemType Directory -Force C:\perf | Out-Null
   typeperf "\Processor(_Total)\% Processor Time" "\Memory\Available MBytes" "\PhysicalDisk(_Total)\Avg. Disk sec/Transfer" -si 5 -sc 24 -f CSV -o C:\perf\dc01-baseline.csv
   ```
   *Ожидаемо:* файл с 24 строками. Это «норма» DC01, с ней будешь сравнивать в уроках 89–90.

5. **FS01.** То же для файлового сервера + свободное место на дисках данных.
   ```powershell
   typeperf "\Processor(_Total)\% Processor Time" "\Memory\Available MBytes" "\Server\Logon Total" -si 5 -sc 24 -f CSV -o C:\perf\fs01-baseline.csv
   Get-CimInstance Win32_LogicalDisk -Filter "DriveType=3" | Select DeviceID,@{n='FreeGB';e={[math]::Round($_.FreeSpace/1GB,1)}}
   ```
   *Ожидаемо:* CSV и список дисков с остатком в ГБ.

6. **UBU01.** Пишем пробу доступности FS01 (SLI «доступность SMB»): 60 проверок с интервалом 5 с.
   ```bash
   cd ~/mon
   cat > probe.sh <<'EOF'
   #!/usr/bin/env bash
   HOST=10.10.10.20; PORT=445
   LOG=~/mon/probe-$(date +%F).log
   for i in $(seq 1 60); do
     if timeout 2 bash -c "echo > /dev/tcp/$HOST/$PORT" 2>/dev/null; then
       echo "$(date +%FT%T) OK" >> "$LOG"
     else
       echo "$(date +%FT%T) FAIL" >> "$LOG"
     fi
     sleep 5
   done
   EOF
   chmod +x probe.sh && ./probe.sh
   ```
   *Ожидаемо:* ~5 минут работы, файл `probe-<дата>.log` со 60 строками `OK`.

7. **UBU01.** Считаем SLI и бюджет ошибок.
   ```bash
   LOG=$(ls -t ~/mon/probe-*.log | head -1)
   awk '{print $2}' "$LOG" | sort | uniq -c
   T=$(wc -l < "$LOG"); O=$(grep -c ' OK$' "$LOG")
   awk -v o="$O" -v t="$T" 'BEGIN{printf "availability=%.3f%% (SLO 99.5%%)\n", o*100/t}'
   ```
   *Ожидаемо:* `60 OK` и `availability=100.000%` — бюджет цел.

8. **UBU01.** Ищем в логах реальные события за последний час.
   ```bash
   sudo journalctl -u ssh --since "1 hour ago" --no-pager | grep -iE "failed|invalid|error" | tail -10
   sudo journalctl --since "1 hour ago" -p warning --no-pager | tail -10
   ```
   *Ожидаемо:* либо пусто, либо понятные строки (например, попытки входа). Свяжи: если бы в логе были `Failed password` пачками, это коррелировало бы с метрикой — так работает корреляция «метрика + лог».

9. **UBU01.** Оформляем `sli-slo.md` — каталог сервисов (минимум два сервиса).

**Диагностика по шагам.**
1. **Есть ли след в данных?** На UBU01: `grep FAIL ~/mon/probe-*.log` — видим окно, например 12:41–12:46. Вывод: система *видела* проблему, но не *сказала*.
2. **Сервис реально падал или сеть?** На FS01: `Get-Service LanmanServer` и `Get-WinEvent -FilterHashtable @{LogName='System'; ProviderName='Service Control Manager'; StartTime=(Get-Date).AddHours(-2)}` — событие 7036/7031 подтверждает остановку службы, а не проблему сети.
3. **Почему не сработал алерт?** Открыть `alerts.md`: правило есть, но реализации нет — канал уведомлений отсутствует. Это и есть корневая причина: **проблема не в FS01, а в мониторинге**.
4. **Что бы дало диагностику быстрее?** Если бы алерт сработал, дежурный за секунды увидел бы `FAIL` и пошёл по runbook: `ss -tulpn` на FS01 → служба → лог 7031. MTTR — минуты, а не «пока пользователь напишет» (MTTD — время до обнаружения — было бесконечным).
5. **Почему остановилась служба?** Проверить журнал приложений FS01 на ошибки, `Get-CimInstance Win32_OperatingSystem | Select LastBootUpTime` (не перезагружался ли), вспомнить, не было ли обновлений/работ коллеги. В учебном сценарии причина — наш ручной `Stop-Service`; в реальности это чаще всего обновление, падение из-за нехватки RAM или ручная ошибка админа без change-запроса.

**Решение.**
- Добавить в `alerts.md` конкретное правило: `3 последовательных FAIL по 445` → Critical, `for 15 с`, ответственный дежурный L2.
- Реализовать вывод алерта хотя бы в файл и консоль, чтобы проверить логику; полноценный канал (TG/e-mail, Zabbix) — урок 89.
- Внести в каталог сервисов запись: FS01/SMB, SLO 99,5 %, владелец — L2.
- Зафиксировать в журнале стенда факт остановки службы, чтобы это не выглядело как «само сломалось».

## 6. Ошибки новичков и безопасность

1. **Мониторить всё подряд.** → Сотни графиков, из которых никто не смотрит, и алерты, которые все отключили. → Начинай с четырёх золотых сигналов и того, что реально болит у пользователей (`\\FS01\Buh`, вход в домен, 1С).
2. **Порог без длительности `for`.** → Один пик CPU на 15 секунд будит дежурного ночью. → Всегда «условие + сколько держится»: `> 90 % в течение 10 минут`.
3. **Алерт без владельца и runbook.** → Дежурный L1 получает «Disk full» и не знает, что делать. → В карточке алерта: кто реагирует, что проверить, как чинить, куда эскалировать.
4. **Мониторинг причин вместо симптомов.** → «CPU 90 %» — не инцидент, если сервис отвечает за 20 мс. → Алерт на «сервис недоступен / p95 вырос / доля ошибок выросла», а ресурсы — как диагностика второго уровня.
5. **Средние вместо перцентилей.** → Средний ответ 200 мс при том, что 5 % запросов идут по 5 секунд. → Смотри p95/p99 в SLI.
6. **Нет baseline.** → Невозможно отличить норму от аномалии: «а сколько было вчера в это время?». → Храни историю (ретеншн минимум 30 дней) и снимай эталон после изменений.
7. **Мониторинг без присмотра за самим мониторингом.** → Сервер Zabbix упал, и все «зелёные». → Dead man's switch: алерт на *отсутствие* данных, а не только на плохие значения.
8. **SLO из головы и обещание SLA до измерений.** → Обещал 99,9 %, а реально 98,7 % — платишь штрафы. → Сначала измерь месяц, потом договаривайся; SLA всегда мягче SLO.

### Безопасность
- Не открывай SNMP с community `public` и доступ по SNMP из офисной сети в интернет — это фактически анонимное чтение конфигурации.
- Экспортёры (`node_exporter`, `windows_exporter`) на `0.0.0.0` без ограничений отдают метрики всем — в бою только на localhost или в закрытом сегменте с фаерволом.
- syslog по 514/udp не шифруется и не аутентифицируется: логи легко подделать. Для боевых систем — TLS (6514) или отдельный management-сегмент.
- `python3 -m http.server` в лабораторной — это файлораздача без пароля; допустима только в изолированной VMnet8 на учебном стенде.
- Логи не должны содержать пароли, номера карт и ПДн: чисти формат вывода до того, как включать централизованный сбор (урок 91).
- Пароль стенда `Lab#2026-vektor` и единый на всё — только для лаборатории; в реальной среде так нельзя.

## 7. Вопросы на собеседовании

**1. Чем метрика отличается от лога и трейса? Когда что применять?**
*Ответ:* метрика — числовое значение с метками времени, дешёвая и хорошо агрегируется, отвечает «что и насколько плохо»; лог — дискретное событие с контекстом, отвечает «что именно произошло и почему»; трейс — цепочка вызовов одного запроса с длительностями каждого шага, отвечает «где именно тормозит». Начинаю с метрик и алертов по ним, при срабатывании иду в логи, а трейсы включаю, когда система распределённая и непонятно, какой сервис виноват.
*Интервьюер хочет услышать:* понимание стоимости хранения и порядка расследования (метрика → лог → трейс), а не заученные определения.
*Красный флаг:* «это одно и то же, просто разные инструменты».

**2. Что такое SLI, SLO, SLA и бюджет ошибок? Приведите пример.**
*Ответ:* SLI — измеряемый показатель (доля успешных коннектов к FS01:445 = 99,62 % за 30 дней). SLO — внутренняя цель по этому показателю (99,5 %). SLA — договор с заказчиком и санкции за нарушение, всегда мягче SLO. Бюджет ошибок = 100 % − SLO; при 99,5 % за 30 дней это 216 минут. Пока бюджет цел — можно выпускать изменения; кончился — замораживаем релизы и занимаемся надёжностью.
*Интервьюер хочет услышать:* что SLO — инструмент управления риском и приоритетами, а не красивая цифра в отчёте.
*Красный флаг:* «SLA и SLO — это синонимы» или SLO без указания окна измерения.

**3. Как построить алерт, чтобы он не спамил?**
*Ответ:* алерт на симптом, влияющий на пользователя; порог + обязательный `for` (например, 3 неудачные проверки подряд или 10 минут выше порога); severity, чтобы различать «звонить ночью» и «разобрать утром»; дедупликация и группировка однотипных; приглушение на время плановых работ; у каждого алерта владелец и runbook; регулярный разбор — какие алерты срабатывали и что из них было полезно.
*Интервьюер хочет услышать:* «алерт — это действие, а не уведомление» и работа с alert fatigue.
*Красный флаг:* «настроим побольше, лишние отключим».

**4. Что такое золотые сигналы и метод USE?**
*Ответ:* четыре золотых сигнала Google SRE — latency, traffic, errors, saturation; они универсальны для сервисов. RED (Rate, Errors, Duration) — упрощение для request-driven сервисов. USE (Utilization, Saturation, Errors) — для ресурсов: CPU, память, диск, сеть. На практике: сервисы мониторю по золотым сигналам/RED, а когда срабатывает — иду в USE смотреть, какой ресурс упёрся.
*Интервьюер хочет услышать:* что ты умеешь быстро выбрать 5–7 метрик, а не 200.
*Красный флаг:* путаница «насыщение = загрузка»: utilization — сколько занято, saturation — сколько ждёт в очереди.

**5. Как организуете мониторинг файлового сервера FS01 на 50 пользователей?**
*Ответ:* black-box — синтетическая проверка доступности `FS01:445` каждую минуту (SLI «доступность», SLO 99,5 %). White-box — свободное место и inode на томах, `Avg. Disk sec/Transfer`, очередь диска, `Available MBytes`, загрузка CPU, число сессий/открытых файлов, состояние службы «Сервер» и «Диспетчер очереди печати». Логи — System (7031/7036), Security (4625/4740), SMB-события аудита доступа к `\\FS01\Buh`. Алерты: недоступность 3 проверки подряд — Critical; диск < 10 % — Warning с `for` 30 мин; задержка диска > 20 мс 15 минут — Warning. Обязательно контроль бэкапов: «задача завершилась» — отдельный алерт. Всё сводится на дашборд и в каталог сервисов с владельцем.
*Интервьюер хочет услышать:* покрытие и доступности, и производительности, и логов, и бэкапов; приоритет — то, что чувствует пользователь.
*Красный флаг:* только `ping` и свободное место.
