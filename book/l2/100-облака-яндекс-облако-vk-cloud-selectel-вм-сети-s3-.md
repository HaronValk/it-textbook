# Облака: Яндекс Облако, VK Cloud, Selectel — ВМ, сети, S3, IAM, стоимость

## 1. Введение (зачем это нужно в реальной работе)

**Заявка #4712.** Пользователь: ivanov (WIN11-CL01, бухгалтерия). Текст: «На FS01 свободно 3 ГБ, а мне надо сдать квартальный архив первички — это 40 ГБ. И 1С-стенд у нас один, если он падает — мы стоим. Нам же обещали "облако"? Когда оно будет?» Срочность: средняя, но с дедлайном по отчётности.

Этот тикет — типичный вход в облачную тему для L2. Не «переведи всё в облако завтра», а «у нас кончилось место, и нам нужна предсказуемость». Дальше начинается работа: посчитать, сколько стоит хранить 40 ГБ в объектном хранилище против покупки диска в FS01; понять, что вообще можно вынести в облако, а что нельзя (1С с базой в РФ и с персональными данными — отдельная история); проверить, кто и по какому ключу будет туда писать.

Почему это встречается постоянно: почти любая компания сейчас гибрид — часть сервисов в офисе на VMware, часть в облаке. L2 должен уметь завести ВМ в консоли провайдера, настроить сеть и security group, выдать приложению доступ к S3 по ключу, объяснить бухгалтерии, почему ссылка на файл «протухла», и не допустить, чтобы тестовая ВМ за выходные нажгла денег. После главы ты будешь понимать модель «облако = API + биллинг», научишься работать одинаково с Яндекс Облаком, VK Cloud и Selectel (они похожи на 80%), поднимешь S3-совместимое хранилище на своём стенде и научишься считать стоимость до того, как её посчитает бухгалтер.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Облако — это чужой гипервизор, доступный по HTTPS-API. Ты не подключаешься к консоли гипервизора, ты шлёшь HTTP-запрос «создай ВМ с такими параметрами» и получаешь JSON с ID. Всё остальное — обёртки: веб-консоль, CLI (`yc`, OpenStack-клиент), Terraform (урок 99). Отсюда главный вывод: **любое действие в консоли можно сделать командой, и наоборот**. Если что-то сломалось — смотри не «почему не нажимается кнопка», а ответ API.

Модель уровней: **IaaS** (виртуальные машины, сети, диски — Яндекс Облако Compute, VK Cloud Cloud Servers, Selectel Cloud Servers), **PaaS** (managed PostgreSQL, managed Kubernetes), **SaaS** (почта, 1С-аренда). L2 живёт в основном в IaaS.

Иерархия ресурсов примерно одинаковая у всех трёх провайдеров:

```text
   yc / terraform / aws cli / mc
              │  HTTPS 443 (REST API)
   ┌──────────▼───────────┐
   │  IAM: КТО и КАКАЯ РОЛЬ│  пользователь / сервисный аккаунт / ключ
   └──────────┬───────────┘
              │
┌─────────────▼─────────────────────────────────────────────────────┐
│ Аккаунт (облако)                                                  │
│  └ Folder / Project  ← здесь права, квоты и бюджет                │
│      ├─ VPC 10.10.20.0/24   (подсеть привязана к зоне)            │
│      │    ├─ Security Group: 443 ← 0.0.0.0/0, 22 ← 10.10.10.0/24  │
│      │    ├─ VM web01: диск + внутренний IP (+ публичный IP)      │
│      │    └─ VM db01 : только внутренний IP                       │
│      ├─ Object Storage: bucket fs01-archive (S3 API, HTTPS 443)   │
│      └─ Billing: счётчики vCPU·час, ГБ RAM·час, ГБ·мес, egress    │
└───────────────────────────────────────────────────────────────────┘
```

Ключевые отличия провайдеров, которые важно знать на L2:

| | Яндекс Облако | VK Cloud | Selectel |
|---|---|---|---|
| Основа | собственная платформа | OpenStack | OpenStack |
| Единица изоляции | cloud → folder | проект | проект |
| CLI | `yc` | OpenStack CLI / API | OpenStack CLI / API |
| S3 | Object Storage, S3 API | Object Storage (Ceph) | Object Storage (Ceph) |
| ВМ | Compute Cloud | Cloud Servers | Cloud Servers |

OpenStack-происхождение значит: в VK Cloud и Selectel ты встретишь слова Nova (вычисления), Neutron (сети), Cinder (диски), Glance (образы) — это внутренние имена сервисов, в консоли они обычно скрыты.

Протоколы и порты, которые нас касаются: 443 (API и S3), 22 (SSH в Linux-ВМ), 3389 (RDP в Windows-ВМ), 53 (DNS), 169.254.169.254 — link-local адрес **сервиса метаданных**, по нему ВМ сама узнаёт свой ID, IP, имя и может получить токен. Он не маршрутизируется в сеть и доступен только изнутри ВМ.

Object Storage — это S3 API: плоское пространство ключей внутри бакета, доступ по `https://<endpoint>/<bucket>/<key>`. Запрос подписывается AWS Signature V4 (ключ доступа + секрет). Отсюда три способа дать доступ: (1) политика бакета/роль IAM, (2) presigned URL — ссылка с подписью и таймером, (3) публичный бакет (почти всегда зло).

Биллинг считает **метрики**: vCPU·час, ГБ RAM·час, ГБ диска·мес, час публичного IP, ГБ исходящего трафика, ГБ·мес хранения, количество запросов. Остановленная ВМ обычно перестаёт тарифицироваться по vCPU/RAM, но диск и статический IP продолжают капать `[ПРОВЕРИТЬ у каждого провайдера]`.

## 3. Аналогия из жизни

Облако — это бизнес-центр со сдачей помещений. **Подсеть** — этаж с коридором: машины на одном этаже видят друг друга без лифта. **Security group** — охрана на входе с бумажкой, где написано «кого пускать»: правила только разрешают, всё остальное по умолчанию закрыто. **Публичный IP** — вывеска с адресом на фасаде: без неё тебя снаружи не найдут. **S3-бакет** — камера хранения с квитанциями: ты кладёшь коробку, получаешь номер ячейки, а **presigned URL** — разовый пропуск, на котором от руки написано «действителен 15 минут». **IAM** — пропускная система для сотрудников: уборщице не выдают ключ от серверной, а подрядчику выдают на 3 часа. **Биллинг** — счётчики на каждом входе: за свет, за воду, за лифт, отдельно за вынос мусора (исходящий трафик).

Аналогия ломается в одном: в бизнес-центре стену нельзя построить за минуту, а в облаке новую подсеть и правило охраны ты создаёшь одним API-вызовом — и так же быстро забываешь про них навсегда, пока не придёт счёт.

## 4. Практика и команды

**1. Профиль CLI и контекст (Яндекс Облако).** CLI хранит профили: облако, каталог, зона по умолчанию. Почти все «загадочные» ошибки — работа не в том каталоге.

```bash
yc init          # спрашивает OAuth-токен, облако, каталог, зону
yc config list
# folder-id: b1gxxxxxxxxxxxxxxxx
# compute-default-zone: ru-central1-a   [ПРОВЕРИТЬ набор зон]
```
Смотреть: `folder-id` (там создаются ресурсы и висят права) и зону: ресурсы в разных зонах друг друга по внутренним адресам не видят.

**2. Инвентаризация ВМ.**

```bash
yc compute instance list
# +----------------+--------+---------------+---------+--------------------+
# |       ID       | NAME   |     ZONE      | STATUS  |       FQDN         |
# +----------------+--------+---------------+---------+--------------------+
# | fhm0abcd...    | web01  | ru-central1-a | RUNNING | web01....internal  |
# +----------------+--------+---------------+---------+--------------------+
```
Смотреть: `STATUS` (RUNNING/STOPPED/PROVISIONING), зону, FQDN. Дальше — детали в JSON, это основной способ быстро найти сеть и диски:

```bash
yc compute instance get --name web01 --format json | jq '.network_interfaces[].primary_v4_address'
```

**3. Жизненный цикл ВМ.** `yc compute instance stop web01`, `start web01`, `delete web01`. В консоли то же самое: `Compute Cloud → Виртуальные машины → ⋮`. Смысл для L2: остановка ≠ удаление, но и не «бесплатно» — диск остаётся и тарифицируется `[ПРОВЕРИТЬ]`.

**4. Сети и security groups.**

```bash
yc vpc subnet list
yc vpc security-group list
yc vpc security-group get --name sg-web --format yaml | grep -A4 egress
```
Смотреть: CIDR подсети, `default security group` (обычно разрешает только внутреннее общение), правила по портам и источникам. Правило `22/tcp from 0.0.0.0/0` — красная тряпка.

**5. IAM: сервисный аккаунт и ключ.** Приложению не дают твой пароль — ему дают сервисный аккаунт с ролью и ключ.

```bash
yc iam service-account create --name sa-backup
yc iam role list | grep -i storage
yc resource-manager folder add-access-binding <folder-id> \
  --role storage.editor --subject serviceAccount:<sa-id>
yc iam key create --service-account-name sa-backup --output sa-backup.key.json
```
Смотреть: имя роли (`storage.editor` — запись в бакеты, `storage.viewer` — только чтение), область выдачи (каталог или весь cloud), и что `sa-backup.key.json` — секрет, который нельзя коммитить. Точные имена ролей `[ПРОВЕРИТЬ]` в доке провайдера.

**6. AWS CLI против любого S3.**

```bash
aws --endpoint-url https://storage.yandexcloud.net s3 ls
aws --endpoint-url https://storage.yandexcloud.net s3 cp backup.tar.gz s3://fs01-archive/2026/q1/
aws --endpoint-url https://storage.yandexcloud.net s3 presign s3://fs01-archive/2026/q1/backup.tar.gz --expires-in 3600
```
Ключи берутся из профиля `~/.aws/credentials`. `--expires-in` — секунды жизни ссылки. Endpoint у VK Cloud и Selectel другой `[ПРОВЕРИТЬ в доке провайдера]`, а команды те же — в этом вся прелесть S3 API.

**7. `mc` — клиент MinIO, работает с любым S3.**

```bash
mc alias set vektor http://10.10.10.30:9000 adm.student 'Lab#2026-vektor'
mc mb vektor/fs01-archive
mc mirror /srv/backup vektor/fs01-archive --overwrite
mc ls --recursive vektor/fs01-archive | head
mc share download --expire 15m vektor/fs01-archive/test.tar.gz
```
Смотреть: `mc mirror` копирует только изменённое (дешёвый инкрементальный бэкап), `mc share download` печатает готовый presigned URL с `X-Amz-Expires=900`.

**8. Пользователи и политики (аналог IAM) в MinIO.**

```bash
mc admin user add vektor svc-backup 'Lab#2026-vektor'
mc admin policy attach vektor readwrite --user svc-backup     # в старых версиях: mc admin policy set [ПРОВЕРИТЬ]
mc admin user list vektor
```
Проверка обратного: пользователь с `readonly` при попытке `mc cp` получит `AccessDenied`. Это и есть least privilege в миниатюре.

**9. Метаданные изнутри ВМ** (только для облачной ВМ, на стенде не сработает):

```bash
curl -s -H "Metadata-Flavor: Google" http://169.254.169.254/computeMetadata/v1/instance/id
```
Так приложение узнаёт, в какой зоне и под каким ID оно живёт, без хардкода.

**10. Security group своими руками (аналог — nftables на GW01).**

```bash
sudo nft -a list ruleset | grep -i forward        # -a покажет handle
sudo nft add rule inet filter forward ip saddr 10.10.10.30 ip daddr 10.10.20.10 tcp dport 80 counter drop
curl -m 3 http://10.10.20.10/                     # из UBU01: таймаут
sudo nft delete rule inet filter forward handle <N>
```
Смотреть: счётчик `counter` — сработало ли правило вообще. В облаке ровно та же логика, только правила живут в API и применяются ко всем ВМ группы.

**11. Стоимость: считаем руками, до создания.**

```text
730 ч = средняя длительность месяца (365 × 24 / 12)

ВМ:    2 vCPU × 730 ч × <цена vCPU·час>
       4 ГБ   × 730 ч × <цена ГБ RAM·час>
Диск:  50 ГБ × <цена ГБ·мес>
IP:    1 × 730 ч × <цена публичного IP·час>
Egress:200 ГБ × <цена ГБ исходящего трафика>
S3:    500 ГБ × <цена ГБ·мес> + 100 000 запросов × <цена за 1000>
```
Цены подставляй из публичного калькулятора провайдера — я их специально не пишу, они меняются. `[ПРОВЕРИТЬ: включён ли НДС в цену на странице]`.

Подожди 90 секунд, повтори → `403` с XML, где `<Code>AccessDenied</Code>` и `<Message>Request has expired</Message>`.

**Диагностика по порядку:**
1. Открыть саму ссылку (не «попросить прислать скриншот», а взять URL) и прочитать XML-ответ: `AccessDenied` / `NoSuchKey` / `RequestTimeTooSkewed` — три разные причины. В нашем случае `Request has expired`.
2. Разобрать query-параметры: `X-Amz-Date` (когда подписано) и `X-Amz-Expires` (сколько живёт). Сложить — получить момент смерти ссылки.
3. Проверить время на UBU01 и на клиенте: `timedatectl`. Если часы разъехались больше чем на несколько минут, подпись «из будущего» и S3 ответит `RequestTimeTooSkewed`. Лечится `chrony`/`systemd-timesyncd`, а не пересозданием ключей.
4. Проверить, что объект на месте и не переехал: `mc ls --recursive vektor/fs01-archive | grep <имя>`.
5. Проверить, что ключ, которым подписывали, ещё жив: `mc admin user list vektor`. Если ключ перевыпустили вчера вечером — все старые ссылки мертвы, это не баг.
6. Убедиться, что бакет не пытались «сделать публичным» в обход: `mc anonymous get vektor/fs01-archive`.

**Решение.** Выпустить новую ссылку с разумным TTL: `mc share download --expire 24h vektor/fs01-archive/db-2026-01-01.tar.gz`. В нормальной среде TTL подбирается под задачу: 15 минут для «скачай сейчас», часы-сутки для передачи между людьми, но не «навсегда».

**Ответ пользователю:** «Мария, ссылка была разовой и действовала ограниченное время — это защита, чтобы её не мог открыть кто-то посторонний, если письмо перешлют. Выпустил новую, действует 24 часа: <ссылка>. Скачайте, пожалуйста, до завтрашнего утра, дальше снова обновимо. Ваш доступ к папке HR на FS01 не изменился».

**Закрытие заявки.** Категория «Object Storage / доступ», решение «истёк срок действия presigned URL», в комментарии — TTL и как проверить. Не делай бакет публичным «чтобы больше не повторялось».

## 6. Ошибки новичков и безопасность

1. **«Сделаю бакет публичным, чтобы не возиться со ссылками»** → через неделю в открытом доступе лежат сканы паспортов и договоры; утечка и уведомление регулятору. Правильно: приватный бакет + presigned URL с TTL + раздача через приложение.
2. **Статический ключ прямо в скрипте или в git** → ключ утекает вместе с репозиторием, и злоумышленник качает твои бэкапы или, хуже, удаляет их. Правильно: переменные окружения, секрет-хранилище, ключи с ограниченной ролью (урок 102).
3. **Один «главный» ключ на все задачи** → нет аудита «кто что сделал», при утечке отзывать нечего. Правильно: отдельный сервисный аккаунт на каждую систему, роль только на нужный бакет/каталог, ротация.
4. **Забыть удалить тестовую ВМ, диск и статический IP** → через месяц сюрприз в счёте. Правильно: сразу после эксперимента `stop` → проверка → `delete`, бюджетный алерт на 50% лимита, тег/лейбл на каждый ресурс с владельцем.
5. **Открыть SSH/RDP на `0.0.0.0/0`** → за сутки соберёшь тысячи попыток входа, а слабый пароль подоберут. Правильно: доступ только из офисной сети или через бастион/VPN, ключи вместо паролей, fail2ban.
6. **Думать, что «остановленная ВМ = бесплатно»** → диски, снапшоты и статические IP продолжают тарифицироваться `[ПРОВЕРИТЬ]`. Правильно: перед остановкой посмотреть, за что именно платишь.
7. **Считать только хранение и забыть исходящий трафик** → бэкап в облако дешёвый, а вот выгрузка 2 ТБ на восстановлении может стоить дороже месяца хранения. Правильно: считать egress заранее.
8. **Хранить единственную копию бэкапа в том же облаке и в том же регионе** → потеря доступа к аккаунту = потеря бэкапов. Правильно: правило 3-2-1, копия вне облака.

### Безопасность
Всё, что мы делали на стенде (единый пароль `Lab#2026-vektor`, MinIO с root-паролем в юните, правило `drop` на живом маршрутизаторе), в боевой среде недопустимо: root-креды хранятся в секрет-хранилище, у каждого сервиса свой аккаунт, изменения в сети идут через change-management (урок 93) с окном и откатом. Отдельно про РФ: персональные данные граждан по 152-ФЗ хранятся на территории РФ — выбирая провайдера, смотри, где физически лежат данные, и фиксируй это в документации. И никогда не выключай аудит действий в аккаунте: при разборе инцидента журнал — единственный источник правды.

## 7. Вопросы на собеседовании

**1. «Чем IaaS отличается от PaaS? Что выберете под 1С и почему?»**
IaaS — ты получаешь ВМ, сеть и диск и сам ставишь ОС, СУБД и обновления; PaaS — провайдер даёт готовый сервис (managed PostgreSQL, managed Kubernetes), ты отвечаешь только за конфигурацию и данные. Под 1С в реальности чаще берут IaaS: нужен контроль над версией платформы, лицензиями, файловым обменом и расположением данных, а также возможность перенести стенд обратно. PaaS хорош там, где нет требований к ОС.
*Что хочет услышать интервьюер:* разделение ответственности и что ты не тащишь managed-сервис туда, где он мешает.
*Красный флаг:* «PaaS всегда лучше, меньше работы» без разбора требований.

**2. «Как организуете сеть в облаке? Почему не всё в публичной подсети?»**
Отдельная VPC, минимум две подсети в разных зонах для отказоустойчивости: публичная — только для балансировщика и bastion, приватная — для приложений и БД. Security group по принципу default deny: 443 снаружи, 22 только с офисного диапазона или через bastion, между приложением и БД — конкретный порт и конкретный источник. NAT-шлюз для исходящего трафика из приватной подсети.
*Что хочет услышать:* сегментация, минимальные права в правилах, отказ от публичных IP у баз.
*Красный флаг:* «всё в одной подсети, всем открыл 22 и 3389 — так проще».

**3. «Что такое presigned URL и какие у него риски?»**
Это ссылка на объект в S3 с подписью и сроком жизни: кто угодно, у кого она есть, скачает объект без учётных данных. Риски: ссылка уходит в письмо/мессенджер и её пересылают дальше; слишком большой TTL; ссылка попадает в логи прокси или в историю браузера. Меры: короткий TTL, передача по защищённому каналу, при необходимости — одноразовые ссылки и аудит скачиваний.
*Что хочет услышать:* понимание, что ссылка = временный пропуск, и что TTL — параметр безопасности, а не формальность.
*Красный флаг:* «проще сделать бакет публичным».

**4. «Как контролировать и снижать стоимость облака?»**
Считать до создания: калькулятор + прикидка 730 часов. Дальше — теги/лейблы на ресурсы (владелец, проект, среда), разрезы в биллинге по ним, бюджетные алерты, регулярный ревью «неиспользуемое»: остановленные ВМ с дисками, старые снапшоты, забытые IP. Технические меры: автоскейлинг, расписание выключения dev-среды на ночь, холодное хранение для старых бэкапов, контроль egress, резервирование под стабильную нагрузку.
*Что хочет услышать:* «стоимость — это метрика, её видно в биллинге и её можно разрезать по владельцам».
*Красный флаг:* «облако дорогое, поэтому мы им не пользуемся» или «настроил алерт — и всё».

**5. «Как выдать приложению доступ к S3, не давая прав администратора?»**
Создать сервисный аккаунт, выдать роль только на конкретный бакет или каталог (чтение/запись объектов, без управления бакетами), выпустить статический ключ, положить его в секрет-хранилище или переменные окружения CI, а не в код. Настроить ротацию ключей, ограничить IP/сеть, включить логирование доступа к бакету. Проверить, что лишнее реально запрещено — попробовать удалить бакет этим ключом и получить отказ.
*Что хочет услышать:* least privilege + ротация + проверка отрицательного сценария.
*Красный флаг:* «дали роль editor на весь каталог, так быстрее».
