# Bash-скрипты для администратора: обработка логов, мониторинг, уведомления

Bash-скрипт — это «дежурный», который обходит стенд каждые пять минут, читает логи, считает проценты и, если что-то не так, стучится тебе в мессенджер. ## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Скрипт — обычный текстовый файл. Первая строка `#!/usr/bin/env bash` (shebang) говорит ядру, чем его исполнять. Дальше ядро запускает интерпретатор, тот читает файл построчно и выполняет команды. Bash работает на прикладном уровне (L7 модели OSI) — он ничего не знает про пакеты, он просто запускает другие программы и склеивает их потоки.

**Три потока у каждой команды:**
- `stdin` (fd 0) — откуда читаем;
- `stdout` (fd 1) — обычный вывод;
- `stderr` (fd 2) — ошибки.

Конвейер `|` соединяет stdout первой команды со stdin второй. `2>&1` — «ошибки туда же, куда обычный вывод». `>` перезаписывает файл, `>>` дописывает. Это важно: если ты в скрипте пишешь `command > /var/log/x.log`, то при каждом запуске лог затирается — частая причина «а почему в логе одна строка?».

**Код возврата (`exit code`).** После завершения любая команда отдаёт число 0–255: `0` — успех, не `0` — ошибка. Это единственный машинно-читаемый «пульс» скрипта. Именно по нему cron, Zabbix и systemd понимают, что произошло. Для проверок удобно соблюдать конвенцию мониторинга (Nagios-стиль):

```text
0 = OK  1 = WARNING  2 = CRITICAL  3 = UNKNOWN
```

Zabbix на MON01, если ты его потом подключишь, читает именно эти коды.

**Откуда брать логи.** В Ubuntu 24.04 Server работают два механизма разом:

```text
 приложение (sshd, nginx, cron)
        │  stdout/stderr
        ▼
   systemd ──► journald (бинарный журнал, /run/log/journal, ротация по размеру)
        │
        └──► rsyslog (текстовые файлы /var/log/*.log, ротация logrotate)
```

Схема: journald хранит всё, но в бинарном виде (`journalctl`), rsyslog дублирует в текстовые файлы (`/var/log/auth.log`, `/var/log/syslog`) — по ним и ходят `grep`/`awk`. Порты здесь прикладные: syslog по сети — UDP/514, SMTP для почтовых уведомлений — TCP/25 или 587, HTTPS для webhook (Telegram, Mattermost) — TCP/443. По умолчанию на UBU01 syslog-приём из сети выключен — и правильно.

**Три части любого «дежурного» скрипта:** сбор данных (команды), решение (сравнение с порогом), действие (лог + уведомление + код возврата).

## 3. Аналогия из жизни

Скрипт — это вахтёр на проходной завода. Ему выдали бумажку-инструкцию: «каждые пять минут обойди цеха, посмотри на манометры, если стрелка выше красной черты — звони начальнику цеха и запиши в журнал». Вахтёр не чинит станки, он не разбирается в давлении — он сравнивает с порогом и сообщает. Если инструкция написана криво («если стрелка выше — звони всем и всегда»), начальник перестаёт брать трубку через час — это и есть спам уведомлениями. Если в инструкции забыли пункт «записать в журнал», то утром никто не докажет, что обход был. А если вахтёру дали право самому останавливать станок, он однажды остановит завод — поэтому скрипт-проверка не должен ничего «лечить» без явного разрешения.

Аналогия ломается в одном: вахтёр — человек и сам поймёт, что ситуация изменилась, а скрипт без явно записанного состояния каждый раз видит мир заново и будет считать одно и то же нарушение новым.

## 4. Практика и команды

**1. Скелет скрипта и проверка синтаксиса.**

```bash
#!/usr/bin/env bash
set -euo pipefail
```

`set -e` — выйти при первой ошибке; `-u` — считать обращение к незаданной переменной ошибкой; `-o pipefail` — конвейер считается упавшим, если упала любая его часть (а не только последняя). Без `pipefail` конструкция `grep error /var/log/syslog | wc -l` вернёт 0 даже когда лога нет.

```bash
bash -n /opt/vektor/scripts/check-health.sh   # только проверка синтаксиса, без запуска
sudo apt install shellcheck -y
shellcheck /opt/vektor/scripts/check-health.sh
```

`shellcheck` — статический анализатор: ловит неэкранированные переменные, `for f in $(ls)` и прочие грабли до запуска в бою.

**2. Разбор текстового лога: кто ломился по SSH.**

```bash
sudo grep -E "Failed password" /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn | head -5
```

Вывод:

```text
     42 10.10.10.100
      3 10.10.10.101
```

`grep -E` — расширенные регулярки, `awk '{print $(NF-3)}'` берёт поле с конца (в строке `Failed password for invalid user admin from 10.10.10.100 port 4421 ssh2` IP стоит четвёртым с конца; в разных версиях sshd позиция гуляет — проверяй вывод глазами). `sort | uniq -c` считает повторы, второй `sort -rn` — по убыванию. Смотрим на топ: 42 попытки с одного адреса — это уже brute-force, тема урока 80.

**3. Арифметика по логам через awk (nginx).**

```bash
awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn
awk '$9 ~ /^5/ {c++} END {print c+0}' /var/log/nginx/access.log
awk '{s+=$10} END {printf "%.1f MB\n", s/1024/1024}' /var/log/nginx/access.log
```

`$9` в формате combined — код ответа, `$10` — размер ответа в байтах. Первая команда: сколько каких кодов. Вторая: число 5xx (ошибки сервера). Третья: суммарный трафик. `c+0` защищает от пустого вывода, когда совпадений нет.

**4. Выборка по времени и замена через sed.**

```bash
sudo sed -n '/10:0[0-9]:/p' /var/log/syslog | head -20
sed -i.bak 's/^THRESHOLD=.*/THRESHOLD=85/' /opt/vektor/scripts/check-health.sh
```

`sed -n '/regex/p'` — печатать только подходящие строки, `-i.bak` — правка «на месте» с сохранением копии. Всегда с `.bak`, иначе одна опечатка в регулярке — и конфиг испорчен.

**5. Журнал systemd.**

```bash
journalctl -u ssh --since "1 hour ago" -p err --no-pager
journalctl -u ssh --since today -o json | head -1
journalctl --disk-usage
```

`-u` — юнит, `--since` понимает `"1 hour ago"`, `today`, `"2026-02-01 10:00"`; `-p err` — приоритет error и выше; `--no-pager` — не открывать `less` (обязательно в скриптах). `-o json` — машиночитаемый вывод, его удобно отдавать в `jq`. `--disk-usage` — сколько журнал занимает; чистится `sudo journalctl --vacuum-size=200M` или `--vacuum-time=14d`.

**6. Проверка диска с порогом.**

```bash
df -P / | tail -1 | awk '{print $5}' | tr -dc '0-9'
du -xh --max-depth=1 /var | sort -rh | head -5
find /var/log -type f -size +100M -exec ls -lh {} \;
```

`df -P` — переносимый формат (одна строка на ФС, без переносов), `$5` — процент, `tr -dc '0-9'` убирает `%`. Пример вывода `du`: `2.1G /var/log`, `870M /var/lib` — сразу видно виновника. `-x` не переходит на другие ФС.

**7. Проверка сервиса и порта.**

```bash
systemctl is-active --quiet ssh; echo $?
ss -tulpn | grep ':22'
ss -tn state established '( sport = :22 )' | wc -l
```

`is-active --quiet` не печатает ничего и возвращает 0/не 0 — идеально для `if`. `ss -tulpn`: `t` TCP, `u` UDP, `l` слушающие, `p` процесс, `n` без DNS. Если `sshd` не слушает `:22` — SSH «не работает» независимо от firewall.

**8. Внешняя доступность.**

```bash
ping -c 3 -W 2 10.10.10.3 >/dev/null && echo "GW01 OK"
curl -s --fail --max-time 10 -o /dev/null -w '%{http_code} %{time_total}\n' http://10.10.20.10/
```

`-c` количество пакетов, `-W` таймаут ожидания в секундах. У `curl`: `--fail` — не считать успехом код 4xx/5xx, `--max-time` — жёсткий таймаут (иначе скрипт зависнет навсегда), `-w` — шаблон вывода, `-o /dev/null` — тело не нужно.

**9. Замок от параллельного запуска и уборка.**

```bash
exec 9>/run/lock/vektor-health.lock
flock -n 9 || { echo "already running"; exit 0; }
tmp=$(mktemp); trap 'rm -f "$tmp"' EXIT
```

`flock -n` — неблокирующий захват: если предыдущий запуск ещё идёт (например, `du` по огромному каталогу), второй экземпляр просто выйдет. `trap ... EXIT` гарантирует удаление временного файла даже при падении.

**10. Уведомление: журнал, syslog, почта, webhook.**

```bash
logger -t vektor-health "DISK / 91% (CRITICAL)"
printf '%s %s\n' "$(date '+%F %T')" "DISK / 91%" >> /var/log/vektor/health.log
curl -s --fail --max-time 10 -X POST "$HOOK_URL" \
  --data-urlencode "text=[UBU01] DISK / 91% CRITICAL"
```

`logger` кладёт строку в журнал с меткой — потом ищется через `journalctl -t vektor-health`. `curl -X POST --data-urlencode` отправляет уведомление в webhook (Mattermost/Telegram-бот); токен — **из файла**, не в теле скрипта (урок 76):

```bash
HOOK_URL=$(< /etc/vektor/hook.url)   # файл chmod 600, владелец root
```

Про почту: `mail -s "Тема" adm.student@corp.vektor.lab` работает только если на UBU01 настроен MTA (postfix/msmtp). В учебном стенде проще webhook — на нём и остановимся. Telegram-бот и Python-обёртки — урок 84, здесь только базовый `curl`.

1. `df -h /` — где закончилось место, насколько. Видим `/ 91%`.
2. `sudo du -xh --max-depth=2 /var | sort -rh | head -20` — копаем вглубь. Видим `/var/log/vektor` — 4+ ГБ.
3. `sudo find /var/log -type f -size +100M -exec ls -lh {} \;` — конкретные файлы-виновники.
4. `journalctl --disk-usage` — не журнал ли съел (у нас нет, но проверять надо всегда).
5. `sudo cat /var/log/vektor/health.log | tail -30` — почему писем 40, а не одно: смотрим, менялось ли состояние (`state`-файл либо отсутствует, либо пишется до отправки, а не после).
6. `sudo ls -la /run/vektor-health.state` — есть ли файл состояния и тот ли владелец (если скрипт запускается от root, а state создан пользователем — `set -u`/`read` упадёт, и код каждый раз «новый»).

**Решение:**

```bash
# 1. Освобождаем место: сначала самый крупный мусор
sudo rm -f /var/log/vektor/big-old.log /var/tmp/fill.bin
sudo journalctl --vacuum-time=14d
df -h /
# 2. Проверяем, что SSH снова пускает
ss -tulpn | grep ':22'; systemctl is-active ssh
# 3. Правим скрипт: состояние пишем ПОСЛЕ успешной отправки, добавляем flock и ротацию
sudo tee /etc/logrotate.d/vektor-health >/dev/null <<'EOF'
/var/log/vektor/health.log {
    weekly
    rotate 8
    compress
    missingok
    notifempty
}
EOF
sudo logrotate -d /etc/logrotate.d/vektor-health   # -d = проверка без изменений
```

Дополнительно в скрипте: сравнивать текущее состояние с предыдущим и слать уведомление только при переходе `OK→CRITICAL` или `CRITICAL→OK`, повтор напоминания — не чаще раза в час (`REMIND_AFTER=3600`), и обязательно передавать в сообщение конкретику (`DISK / 91% (/var/log/vektor 4.2G)`), чтобы получатель сразу знал, куда смотреть.

**Что ответить пользователю:**

Место освободил, SSH работает, уведомления перенастроил: теперь пишет один раз при смене состояния и с указанием, что именно занимает диск. Отчёт по складу перезапущу вручную сейчас, к 13:00 будет у тебя на почте. Проверь, пожалуйста, и напиши, если не пришёл.»

## 6. Ошибки новичков и безопасность

1. **`rm -rf $DIR/` с пустой переменной → сносит `/`.** К чему приводит: сервер в брак. Правильно: `set -u`, `${DIR:?DIR is empty}` и всегда кавычки `"$DIR"`.
2. **Без кавычек вокруг переменных** (`if [ $STATUS = OK ]`) → при пустом значении скрипт падает с `unary operator expected`, а в путях с пробелами — работает не с тем файлом. Правильно: `[[ "$STATUS" == "OK" ]]`.
3. **`for f in $(ls /var/log)`** и разбор вывода `ls` → ломается на пробелах и спецсимволах. Правильно: `for f in /var/log/*.log; do [ -e "$f" ] || continue; ...`.
4. **Нет `set -euo pipefail`** → скрипт «успешно» заканчивается с кодом 0, хотя внутри всё упало. Именно так отчёт Сидорова и не сформировался.
5. **Проверка без гистерезиса** → уведомление на каждом запуске, адресат добавляет тебя в спам, алерты перестают читать. Правильно: состояние в файле + напоминание раз в N минут + разные пороги на вход и выход (85% и 80%).
6. **Правка через `sed -i` без бэкапа** → одна кривая регулярка, и скрипт не запускается. Правильно: `sed -i.bak`, git (урок 85), тест на копии.
7. **Скрипт без `flock`** → два экземпляра одновременно дублируют уведомления и нагружают диск (`du` в двух копиях).
8. **Свой лог без ротации** → скрипт мониторинга сам становится причиной «кончилось место». Это самая частая ирония в этой теме.

### Безопасность

- **Токены и webhook-URL — не в скрипте и не в git.** Файл `chmod 600`, владелец root; в боевой среде — Vault или аналог (урок 76).
- **Не запускай мониторинг от root «на всякий случай».** Дай `sudoers` право только на конкретные команды (`systemctl is-active`, `df`) или на конкретный путь скрипта — не `NOPASSWD: ALL`.
- **Не суй в уведомления персональные данные.** ФИО сотрудников, логины, содержимое писем в открытом канале — это разговор с 152-ФЗ (урок 78). Формат «сервис + метрика + значение» безопаснее.
- **`curl` к webhook — только по HTTPS.** HTTP-канал = токен в открытом виде в трафике.
- **Отключение файрвола ради теста.** Соблазн большой, когда проверка «не проходит». Правильно: `sudo ufw status`, добавить правило под конкретный адрес и порт и вернуть состояние как было.
- **Скрипт, который сам «лечит»** (удаляет логи, рестартует сервисы), — только после снапшота и с записью действия в лог. В боевой среде такое сначала проходит code review.

## 7. Вопросы на собеседовании

**1. Как заставить bash-скрипт остановиться при ошибке, в том числе внутри пайпа?**

Ответ: `set -euo pipefail` в начале, shebang `#!/usr/bin/env bash`. `-e` — выход при ненулевом коде команды, `-u` — ошибка на незаданной переменной, `-o pipefail` — код пайпа равен коду первой упавшей команды. Важно знать исключения: `-e` не срабатывает внутри условий (`if cmd; then`) и после `&&`/`||` — это не бага, а задумка. Плюс `trap 'cleanup' EXIT` для уборки.

*Что хочет услышать интервьюер:* понимание `pipefail` (главная деталь) и того, что `set -e` не панацея.

*Красный флаг:* «просто пишу `set -e`» без `pipefail`; уверенность, что `set -e` ловит всё.

**2. Как не дать двум копиям скрипта работать одновременно?**

Ответ: `flock`. Классика — `exec 9>/run/lock/task.lock; flock -n 9 || exit 0`, или одной строкой `flock -n /run/lock/task.lock /path/script.sh`. `-n` — неблокирующий: если замок занят, сразу выходим. `-w 30` — подождать до 30 секунд. Замок держится, пока открыт файловый дескриптор, поэтому нельзя закрывать fd раньше времени.

*Что хочет услышать интервьюер:* `flock` и понимание, что это нужно для тяжёлых проверок и для уведомлений.

*Красный флаг:* «проверю `ps aux | grep script`» — гонка процессов, ненадёжно.

**3. Где смотреть логи в системе с systemd и чем это отличается от `/var/log`?**

Ответ: `journalctl` читает бинарный журнал journald: `-u unit`, `--since`, `-p err`, `-o json`, `-f` (аналог `tail -f`), `--vacuum-size` для чистки. Текстовые файлы в `/var/log` пишет rsyslog (`auth.log`, `syslog`) и сами приложения (`/var/log/nginx/`), их ротирует logrotate. Журнал и файлы не одно и то же: journald видит stdout сервисов и метаданные, rsyslog — только то, что ему передали. В контейнерах и минимальных образах текстовых логов может не быть вообще.

*Что хочет услышать интервьюер:* различает journald, rsyslog и логи приложения; знает `--vacuum` и `logrotate`.

*Красный флаг:* «всё в `/var/log/syslog`, journalctl не пользуюсь».

**4. Как сделать уведомления, которые не превращаются в спам?**

Ответ: хранить предыдущее состояние (файл в `/run` или `/var/lib`), отправлять только при переходе между состояниями; ввести гистерезис (алерт при 85%, отбой при 80%); ограничить напоминания (`не чаще раза в час`); группировать (`одно сообщение со списком проблем`); в тексте давать конкретику, а не «что-то не так»; разделять каналы по критичности (CRITICAL — звонок/чат, WARNING — почта).

*Что хочет услышать интервьюер:* дедупликация и приоритизация — то, из-за чего алерты реально перестают читать.

*Красный флаг:* «шлю всегда, пусть смотрят» или «настрою, чтобы писалось только в лог» (то есть никто не узнает).

**5. Как ты проверяешь скрипт перед запуском на боевом сервере?**

Ответ: `bash -n` (синтаксис), `shellcheck` (типовые ошибки), запуск с `bash -x` или `set -x` на тестовом стенде, «сухой прогон» с переменной `DRY_RUN=1`, когда вместо изменений печатается план; проверка кодов возврата (`echo $?`) на искусственно сломанном состоянии; версионирование в git и ревью (урок 85); на проде — сначала запуск вручную, потом в планировщик.

*Что хочет услышать интервьюер:* системность и наличие тестового стенда — у нас это и есть UBU01.

*Красный флаг:* «сразу запускаю на проде, там видно будет».
