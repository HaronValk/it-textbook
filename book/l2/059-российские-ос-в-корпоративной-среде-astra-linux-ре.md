## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Главное, что надо понять сразу: почти все «российские ОС» — это сборки на чужом шасси.** Astra Linux Common Edition — на базе Debian (пакеты `.deb`, менеджер APT). РЕД ОС — RHEL-совместимая (пакеты `.rpm`, DNF/YUM). АЛЬТ — собственный пакетный стек с APT-RPM и репозиторием Sisyphus. Национальность здесь определяется не ядром, а: локализацией и документацией на русском, набором отечественного ПО (КриптоПро, ГОСТ-TLS, 1С), интеграцией с отечественными СЗИ и, главное, **сертификатами ФСТЭК/Минобороны** и вхождением в реестр отечественного ПО.

**Что такое «уровни защищённости».** Это не характеристика «крутости» ОС, а язык требований регулятора. Заказчик смотрит: если это ИСПДн — ему нужен уровень защищённости по приказу ФСТЭК №21 (УЗ-1…УЗ-4); если ГИС — класс защищённости по приказу ФСТЭК №17 (1А…3Б). Дальше он смотрит в сертификат: каким требованиям соответствует конкретная сборка ОС и какие меры она реализует — идентификация и аутентификация, дискреционное управление доступом, **мандатное управление доступом**, контроль целостности, регистрация событий безопасности (аудит), очистка остаточной информации, замкнутая программная среда (ЗПС — запрет запускать что-либо вне разрешённого списка). Точные формулировки сертификатов и перечень версий — только с сайта вендора `[ПРОВЕРИТЬ]`.

Ключевое практическое следствие: **Common Edition и Special Edition — это разные продукты**. В Astra Linux CE (свободная, без сертификации для высоких классов) нет полноценной подсистемы мандатного доступа; «ПАРСЕК» — это как раз набор средств защиты в Special Edition `[ПРОВЕРИТЬ]`. Поэтому вопрос «а почему у нас не работает мандатная метка?» почти всегда имеет ответ «потому что это CE».

```text
        ASTRA01 10.10.10.31            UBU01 10.10.10.30            (в перспективе)
        ┌───────────────────┐          ┌───────────────────┐      ┌──────────────────┐
        │ Fly (GUI) / SSH   │          │ GNOME / SSH       │      │ Cockpit :9090    │ РЕД ОС
        │ systemd → ядро    │          │ systemd → ядро    │      │ alterator :8080  │ АЛЬТ
        │ APT + .deb        │          │ APT + .deb        │      │ DNF + .rpm       │
        │ sources.list      │          │ sources.list      │      │ /etc/yum.repos.d │
        │ СЗИ ПАРСЕК (SE)   │          │ AppArmor          │      │ firewalld, auditd│
        └─────────┬─────────┘          └─────────┬─────────┘      └────────┬─────────┘
                  │ HTTPS 443 / HTTP 80 (репозиторий), SSH 22, NTP 123, LDAP 389/636
                  ▼                              ▼
          repo вендора (Astra)           archive.ubuntu.com
```

Слои, которые нас касаются: ядро (патчи безопасности вендора) → systemd (юниты и таймеры, урок 54) → PAM (аутентификация, урок 51) → пакетный менеджер и репозитории → прикладной слой (СЗИ, браузер с ГОСТ, 1С). Аудит (`auditd`) стоит отдельным «регистратором»: он пишет в `/var/log/audit/audit.log`, а в сертифицированных сборках ещё и дополняется модулем самой ОС.

**Репозитории — самое частое место аварии.** Правила: (1) на сертифицированной машине разрешены только репозитории вендора — любой сторонний пакет ломает сертификацию и снимает поддержку; (2) все репозитории должны быть подписаны GPG-ключом вендора; (3) в закрытом контуре (без интернета) делается локальное зеркало или обновление с ISO-образа, а не «отключим проверку подписи». Команды и пути различаются: Astra и АЛЬТ — `/etc/apt/sources.list` и `/etc/apt/sources.list.d/`; РЕД ОС — `/etc/yum.repos.d/*.repo`.

## 3. Аналогия из жизни

Представь пассажирский автобус. Шасси, двигатель и коробка передач куплены у известного мирового производителя (Debian или RHEL). Дальше — своё: кузов, сиденья, поручни, документация на русском, ремни безопасности по ГОСТу и техосмотр по более строгим правилам, чем у обычного городского автобуса. «Уровень защищённости» — это категория техосмотра: кому-то достаточно городского, а кому-то нужен допуск на режимный объект, и тогда инспектор проверяет не только ремни, но и то, что водитель не может самовольно отключить ограничитель скорости (мандатное управление доступом и ЗПС). Аналогия перестаёт работать в одном месте: ремни в автобусе можно физически заменить на другие, а вот средства защиты в сертифицированной ОС встроены в ядро и проверены испытаниями — «наклеить сертификат» сбоку нельзя.

## 4. Практика и команды

**1. Определить, что за ОС и какая версия (работает везде).**
```bash
cat /etc/os-release
hostnamectl
uname -r
```
`/etc/os-release` — стандартный файл спецификации `os-release`: `NAME`, `VERSION_ID`, `PRETTY_NAME`. Смотрим на `PRETTY_NAME` и `VERSION_ID`. На Astra дополнительно:
```bash
cat /etc/astra_version    # [ПРОВЕРИТЬ] файл есть в Astra Linux, содержит номер сборки
```
Типичный вывод:
```text
PRETTY_NAME="Astra Linux (Common Edition)"
NAME="Astra Linux"
VERSION_ID="2.12"          # [ПРОВЕРИТЬ] актуальную версию сверяйте с сайтом вендора
```
Смотреть надо: CE или SE перед вами — от этого зависит всё остальное.

**2. Узнать пакетную базу и количество пакетов.**
```bash
dpkg --print-architecture          # amd64 / arm64 / elbrus / e2k [ПРОВЕРИТЬ для отечественных платформ]
dpkg -l | wc -l                    # Debian-семейство: Astra, АЛЬТ
rpm -qa | wc -l                    # RPM-семейство: РЕД ОС
apt --version ; dnf --version      # что вообще установлено
```

**3. Посмотреть репозитории (Astra / АЛЬТ).**
```bash
grep -rhv '^#' /etc/apt/sources.list /etc/apt/sources.list.d/ | grep -v '^$'
```
`-r` рекурсивно, `-h` без имён файлов, `-v` инвертирует (выкидываем комментарии). Вывод:
```text
deb https://download.astralinux.ru/astra/stable/.../repository-debian/ stable main contrib non-free   # [ПРОВЕРИТЬ URL]
```
Смотреть: домен вендора в каждой строке, дистрибутив (`stable`), отсутствие «левых» зеркал.

**4. Посмотреть репозитории (РЕД ОС).**
```bash
ls /etc/yum.repos.d/
cat /etc/yum.repos.d/redos.repo     # [ПРОВЕРИТЬ имя файла]
dnf repolist --all
```
```text
repo id        repo name          status
redos-base     RED OS base        enabled
redos-updates  RED OS updates     enabled
```
Смотреть: `enabled/disabled`, `baseurl` указывает на вендора, `gpgcheck=1`. Ключи — в `/etc/pki/rpm-gpg/`.

**5. Обновить индексы пакетов.**
```bash
sudo apt-get update        # Astra, АЛЬТ
sudo dnf makecache         # РЕД ОС (аналог)
```
Смотреть: строки `Hit`/`Get` без `Err`/`404`. Любой `Err` — это либо сеть/DNS, либо битая строка в sources. На боевом сервере `update` безопасен (только индексы), в отличие от `upgrade`.

**6. Найти и поставить пакет.**
```bash
apt-cache policy htop          # есть ли кандидат и из какого репозитория
apt-cache search '^htop$'
sudo apt-get install -y htop tree
dnf info htop ; sudo dnf install -y htop    # РЕД ОС
```
`apt-cache policy` — главный инструмент диагностики «пакет не находится»:
```text
htop:
  Installed: (none)
  Candidate: 3.x.x-x
  Version table:
     3.x.x-x 500
        500 https://download.astralinux.ru/... stable/main amd64 Packages
```
Если `Candidate: (none)` — репозитория нет в индексе, дело не в пакете.

**7. Посмотреть историю установок (кто что сделал до тебя).**
```bash
grep ' install ' /var/log/dpkg.log | tail -n 10
tail -n 20 /var/log/apt/history.log
sudo dnf history | head -n 15 ; sudo dnf history info <ID>    # РЕД ОС
```
Это первое, что смотрят при разборе «после чего сломалось».

**8. Проверить подписи репозиториев.**
```bash
ls -la /etc/apt/trusted.gpg.d/
apt-key list 2>/dev/null | head -n 20    # устаревшая команда, но ещё встречается
rpm -qa 'gpg-pubkey*'                    # РЕД ОС/АЛЬТ: список импортированных ключей
```
Правильно — ключ вендора лежит отдельным файлом в `trusted.gpg.d` или в `signed-by=` строки `deb`. Неправильно — глобально отключённая проверка подписи.

**9. АЛЬТ-специфика: apt-repo и etcnet.**
```bash
apt-repo list                 # активные репозитории
apt-repo add <репозиторий>    # добавить
apt-repo rm  <репозиторий>
cat /etc/net/ifaces/*/options # настройки интерфейсов в etcnet
systemctl restart network     # применение сетевых настроек [ПРОВЕРИТЬ имя юнита в вашей версии]
```
В АЛЬТ сеть настраивается не через netplan, а через свой фреймворк etcnet — это важно помнить при переносе привычек с Ubuntu (урок 53).

**10. Проверить, включены ли средства защиты и аудит.**
```bash
systemctl status auditd --no-pager
sudo auditctl -l                      # список правил аудита (пусто = правил нет)
sudo ausearch -ts today | head -n 20
getenforce ; sestatus                 # только там, где есть SELinux (РЕД ОС) [ПРОВЕРИТЬ]
ls /etc/parsec 2>&1                   # Astra SE: конфигурация подсистемы защиты [ПРОВЕРИТЬ]
```
Если `auditd` не запущен на сертифицированной машине — это уже инцидент: события безопасности не пишутся.

**11. Проверить firewall.**
```bash
sudo firewall-cmd --state ; sudo firewall-cmd --get-active-zones   # firewalld (РЕД ОС)
sudo nft list ruleset | head -n 30                                 # nftables
sudo ufw status verbose                                            # если ufw
```
GUI (где есть): Astra — Fly, «Центр управления политикой безопасности» `fly-admin-smc` `[ПРОВЕРИТЬ]`; АЛЬТ — веб-конфигуратор alterator `http://<host>:8080` `[ПРОВЕРИТЬ]`; РЕД ОС — Cockpit на `https://<host>:9090` `[ПРОВЕРИТЬ]`.

**Как воспроизвести поломку (на ASTRA01, под sudo):**
```bash
sudo cp /etc/apt/sources.list /root/sources.list.bak-059
sudo sed -i 's/^deb /#deb /' /etc/apt/sources.list      # «оптимизатор» закомментировал репозиторий
```

**Диагностика по шагам (именно в этом порядке, от дешёвого к дорогому):**
1. Воспроизвести: `sudo apt-get install htop` → `has no installation candidate`. Симптом подтверждён.
2. `apt-cache policy htop` → `Candidate: (none)`. Значит, проблема на уровне индексов, а не пакета.
3. `grep -rhv '^#' /etc/apt/sources.list /etc/apt/sources.list.d/ | grep -v '^$'` → пусто. **Вот он, корень.**
4. `sudo apt-get update` → `E: The list of sources could not be read` или обновление «ничего не делает». Подтверждает: репозиториев нет.

## 6. Ошибки новичков и безопасность

1. **Путать Common Edition и Special Edition.** → Ставишь задачи по мандатному доступу и ЗПС на CE, где их нет; в отчёте заказчику — неверные выводы. → Правильно: первым делом смотреть `/etc/os-release`, `/etc/astra_version` и читать, какая сборка сертифицирована под какие требования.
2. **Подключать сторонние репозитории «как на Ubuntu».** → На сертифицированной машине это ломает сертификацию и снимает поддержку вендора, а иногда и загрузку. → Правильно: только репозитории вендора; сторонний софт — отдельным согласованным контуром.
3. **Отключать проверку подписи пакетов (`gpgcheck=0`, `[trusted=yes]`), чтобы «просто поставилось».** → Любой подменённый пакет ставится молча. → Правильно: импортировать ключ вендора, а при `NO_PUBKEY` разбираться с ключом, а не с проверкой.
4. **Гнать `apt-get upgrade` / `dnf upgrade` на боевом сервере днём без окна и бэкапа.** → Обновление ядра или СЗИ, незапланированный ребут, недоступный сервис. → Правильно: снапшот/бэкап, окно, `-s` (симуляция) сначала, откат продуман заранее.
5. **Копировать URL репозитория из интернета под другую версию ОС.** → 404 на `update`, битые зависимости, «пакет есть, но не ставится». → Правильно: URL только из документации вендора под конкретную версию.
6. **Смешивать пакетные базы (ставить `.rpm` на Debian-подобную через alien).** → Мусор в системе, конфликты, неработающие обновления. → Правильно: искать пакет в родном формате или собирать из исходников в отдельном префиксе.
7. **Игнорировать аудит и время.** → `auditd` выключен (нет доказательной базы по инциденту), время уехало (падает Kerberos, ломаются логи и подписи). → Правильно: `auditd` включён, `chrony`/`systemd-timesyncd` смотрят на DC01.
8. **Считать, что «Linux есть Linux».** → На АЛЬТ сеть в etcnet, на РЕД ОС firewalld и DNF, на Astra свой центр политики — привычные ubuntu-рецепты не работают. → Правильно: перед изменением смотреть, какие службы и файлы реально есть на этой машине.

**Безопасность.** В боевой среде сертифицированная ОС — часть **аттестованного объекта**: самовольное отключение аудита, средств защиты, firewall или установка непроверенного ПО — это не «админское решение», а нарушение требований безопасности, за которое отвечает организация. Изменения делаются по заявке/регламенту, с записью в журнале, а пароли стенда вида `Lab#2026-vektor` в реальной работе недопустимы: там нужны индивидуальные учётки, сложные пароли и запрет общего sudo-пароля.

## 7. Вопросы на собеседовании

**1. Чем Astra Linux Special Edition отличается от Common Edition и когда какую применяют?**
Ответ: CE — свободно распространяемая сборка на базе Debian, без сертификации под высокие требования, для обычных задач и пилотов. SE — сертифицированная сборка со средствами защиты (мандатное управление доступом, ЗПС, контроль целостности, расширенный аудит), её ставят там, где требования regulator'а обязывают: ИСПДн, ГИС, объекты с повышенными требованиями. Выбор идёт от требований: класс защищённости по приказу №17 / уровень защищённости по приказу №21 → смотрим сертификат конкретной версии → только потом ставим.
*Что хочет услышать интервьюер:* что ты выбираешь ОС от требований и сертификата, а не от «что удобнее».
*Красный флаг:* «SE — это просто платная версия, разницы нет» или «сертификат можно получить на любую сборку».

**2. Что такое уровень защищённости и как он связан с ОС?**
Ответ: это категория требований регулятора к системе (УЗ-1…УЗ-4 для ИСПДн по приказу ФСТЭК №21; классы 1А…3Б для ГИС по приказу №17). ОС — одно из средств, которыми эти требования закрываются: в сертификате перечислено, какие меры реализованы (идентификация/аутентификация, дискреционный и мандатный доступ, контроль целостности, регистрация событий, очистка остаточной информации). Задача админа — не «повысить уровень», а настроить и не отключать то, что уже заложено.
*Что хочет услышать:* понимание, что сертификация — про набор мер, а не про «наклейку».
*Красный флаг:* путаница «уровень защищённости = версия ОС» без ссылки на требования.

**3. Как добавить репозиторий и обновить систему в Astra / РЕД ОС / АЛЬТ?**
Ответ: Astra и АЛЬТ — APT: строка `deb` в `/etc/apt/sources.list` или `sources.list.d`, ключ вендора в `trusted.gpg.d` или `signed-by=`, затем `apt-get update` и `apt-get install`. В АЛЬТ ещё `apt-repo add`. РЕД ОС — DNF: файл в `/etc/yum.repos.d/` c `baseurl` и `gpgcheck=1`, ключ в `/etc/pki/rpm-gpg/`, затем `dnf makecache`. В закрытом контуре — локальное зеркало или обновление с ISO, но не отключение проверки подписи.
*Что хочет услышать:* что ты знаешь различия и не отключаешь подписи.
*Красный флаг:* «ставлю `gpgcheck=0`, иначе не работает».

**4. Как убедиться, что обновление прошло корректно, и что делать, если после него сервис не поднялся?**
Ответ: до — снапшот/бэкап и симуляция (`apt-get -s full-upgrade`, `dnf --assumeno upgrade`); после — `dpkg --audit`, `dnf history`, `systemctl --failed`, `journalctl -u <сервис> -b`, проверка версии ядра и перезагрузки. Если сервис не поднялся: смотрим журнал юнита, конфиг, зависимости, при необходимости откатываем пакет (`dnf history undo`, установка предыдущей версии из кэша) или всю ВМ из снапшота.
*Что хочет услышать:* порядок «бэкап → симуляция → обновление → проверка → откат».
*Красный флаг:* «обновил и пошёл дальше, проверю, если пользователи пожалуются».

**5. В закрытом контуре нет доступа к репозиториям вендора. Как обновлять?**
Ответ: поднять внутреннее зеркало (или периодически приносить ISO-образ обновлений), подключить его как локальный репозиторий (`file://` / внутренний HTTP), сохранив подписи вендора и GPG-ключи; обновления проводить по регламенту с окном и бэкапом. Промежуточный вариант для одной машины — монтирование ISO и временный локальный source, но это фиксируется в журнале и убирается после.
*Что хочет услышать:* что ты не ломаешь подписи и умеешь жить без интернета.
*Красный флаг:* «скачаю пакеты с левого FTP и поставлю с `--allow-unauthenticated`».
