## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**KVM (Kernel-based Virtual Machine)** — модуль ядра (`kvm_intel` или `kvm_amd`), который использует аппаратные расширения VT-x (Intel) или AMD-V. Модуль даёт устройство `/dev/kvm` — через него программа получает «право» запускать код гостя прямо на процессоре в непривилегированном режиме. Сам по себе KVM ничего не умеет, кроме исполнения CPU-кода.

**QEMU** — пользовательская программа, которая изображает «железо»: чипсет, диск, сетевую карту, BIOS/OVMF. Вместе QEMU+KVM дают быструю виртуалку. Всё, что медленное и эмулированное (например, `e1000`), — это QEMU; всё, что через `virtio` (virtio-net, virtio-scsi, balloon), — полувиртуализация, гость знает, что он гость, и работает почти на скорости железа.

**LXC** — не виртуализация, а контейнеризация: одно ядро, изоляция через namespaces и cgroups. Контейнер стартует за секунду и ест мало RAM, но не может иметь своё ядро и другой дистрибутив ядра.

**Proxmox VE** — это набор служб поверх Debian:

```text
┌────────── VMware Workstation на ПК админа (гипервизор 2 типа) ─────────┐
│  ВМ PVE01 10.10.10.70 (VMnet8, NAT)                                     │
│  ┌──────────────────── Proxmox VE (Debian) ──────────────────────────┐  │
│  │ pveproxy(8006)  pvedaemon  pvestatd  pve-cluster  pve-firewall    │  │
│  │ /etc/pve — единая конфигурация узла (FUSE + SQLite, pmxcfs)       │  │
│  │   ├── qemu-server/100.conf   ← ВМ (KVM)                           │  │
│  │   ├── lxc/200.conf           ← контейнер (LXC)                    │  │
│  │   └── storage.cfg, user.cfg, firewall/, nodes/                    │  │
│  │ storage: local (dir) / local-lvm (LVM-thin) / NFS / Ceph          │  │
│  ├───────────────────────────────────────────────────────────────────┤  │
│  │ QEMU (userspace): чипсет, диски, virtio, BIOS/OVMF                │  │
│  │ KVM (ядро: kvm_intel/kvm_amd) → /dev/kvm → VT-x/AMD-V             │  │
│  └───────────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────────┘
```

Ключевая идея: **вся конфигурация лежит в `/etc/pve`** — это виртуальная ФС (pmxcfs), которая хранит файлы в SQLite и реплицирует их между узлами кластера. Поэтому конфиг ВМ — обычный текстовый файл, но редактировать его руками почти никогда не нужно: есть `qm` и `pct`.

| Порт | Что это |
|------|---------|
| 8006/tcp | веб-интерфейс и REST API (`pveproxy`) |
| 22/tcp | SSH, консоль, туннель миграции |
| 3128/tcp | SPICE-прокси |
| 5405–5412/udp | corosync, обмен кластера `[ПРОВЕРИТЬ]` |
| 60000–60050/tcp | миграция ВМ без шифрования `[ПРОВЕРИТЬ]` |

Хранилища (`storage`) — отдельный слой: `dir` (папка с qcow2/ISO/бэкапами), `lvmthin` (блочные тонкие тома — быстрые, поддерживают снапшоты), `zfspool`, NFS/CIFS, Ceph. Тип хранилища определяет, будут ли работать снапшоты.

## 3. Аналогия из жизни

Proxmox — это **управляющая компания в доме**. KVM — несущие стены и фундамент: без них ничего не построить, но жить в стенах нельзя. QEMU — планировка квартиры: сколько комнат, где розетки, какая входная дверь (это эмуляция железа). `/etc/pve` — журнал управляющей компании: в нём записано, кто в какой квартире живёт, какие у него ключи и где парковка. `storage` — сами парковки и кладовки: они бывают разные, и не на каждой можно поставить машину на домкрат (снапшот). Контейнер LXC — комната в коммуналке: быстро, дешево, но общие стены и общий фундамент с соседями.

Аналогия перестаёт работать в одном месте: квартиру нельзя «откатить» на 20 минут назад, а виртуалку — можно снапшотом.

## 4. Практика и команды

Все команды — на PVE01, от `root` (в учебном стенде; в бою — через sudo/роли).

**1. Версия и состав пакетов**
```bash
pveversion -v
```
`-v` — подробно, по компонентам. В выводе смотри `proxmox-ve`, `pve-kernel-*`, `qemu-server`, `pve-manager`: по этим строкам сверяют версию при обращении в поддержку и при проверке CVE.

**2. Проверка аппаратной виртуализации**
```bash
lsmod | grep kvm
grep -c -E 'vmx|svm' /proc/cpuinfo
```
Первая команда должна показать `kvm_intel`/`kvm_amd` и `kvm`. Вторая — число vCPU с флагом VT-x/AMD-V. Если `0` — вложенная виртуализация не проброшена, ВМ внутри PVE01 не запустятся.

**3. Хранилища**
```bash
pvesm status
pvesm list local-lvm
```
Типичный вывод:
```text
Name             Type     Status     Total     Used   Available   %
local             dir     active   30700000  2500000    26000000  8.14
local-lvm     lvmthin     active   40000000        0    40000000  0.00
```
`Status: active` — хранилище подключено; `Total/Available` — свободное место. Если `inactive` — смотри `journalctl -u pvestatd`.

**4. Список ВМ**
```bash
qm list
```
```text
 VMID NAME      STATUS    MEM(MB) BOOTDISK(GB) PID
  100 tst-vm    running      1024         8.00 12345
```
Смотри `STATUS` (`running`/`stopped`) и `PID` — если PID есть, а статус странный, процесс QEMU жив, но завис.

**5. Конфиг ВМ**
```bash
qm config 100
```
```text
boot: order=scsi0;ide2
cores: 1
cpu: host
memory: 1024
name: tst-vm
net0: virtio=BC:24:11:AA:BB:CC,bridge=vmbr0
scsi0: local-lvm:vm-100-disk-0,size=8G
```
Здесь главное — `cpu: host` (проброс реальных флагов CPU, нужен для вложенной виртуализации), `net0` (мост) и привязка дисков к хранилищу.

**6. Создание ВМ из CLI**
```bash
qm create 100 --name tst-vm --memory 1024 --cores 1 \
  --net0 virtio,bridge=vmbr0 --scsi0 local-lvm:8 \
  --ide2 local:iso/ubuntu-24.04.2-live-server-amd64.iso,media=cdrom \
  --boot order=scsi0\;ide2 --cpu host --agent enabled=1
```
`--scsi0 local-lvm:8` — диск 8 ГБ на thin-хранилище. `--agent enabled=1` — ждём в госте `qemu-guest-agent` (корректное выключение и IP гостя в UI).

**7. Управление питанием**
```bash
qm start 100
qm status 100
qm shutdown 100 --timeout 60
qm stop 100
```
`shutdown` — вежливо, через ACPI/агента; `stop` — как выдернуть питание. Всегда сначала `shutdown`.

**8. Консоль QEMU-монитора**
```bash
qm monitor 100
```
Внутри: `info status`, `info cpus`, `info block`. Выход — `quit`. Это «взгляд изнутри» на ВМ, когда гостевой ОС уже не доверяем.

**9. Снапшоты ВМ**
```bash
qm snapshot 100 before-test --description "перед обновлением"
qm listsnapshot 100
qm rollback 100 before-test
qm delsnapshot 100 before-test
```
Работают, только если диски лежат на snapshot-совместимом хранилище (`lvmthin`, `zfspool`, `qcow2`). На «толстом» LVM команда вернёт ошибку.

**10. Клон и шаблон**
```bash
qm clone 100 101 --name tst-vm-copy --full 1
qm template 100
```
`--full 1` — полная копия дисков. Linked clone (общая база, экономия места) возможен только от шаблона.

**11. Бэкап и восстановление**
```bash
vzdump 100 --storage local --mode snapshot --compress zstd
ls -lt /var/lib/vz/dump/
qmrestore /var/lib/vz/dump/vzdump-qemu-100-2026_xx_xx-xx_xx_xx.vma.zst 102
```
Режимы: `stop` (ВМ гасится), `suspend` (пауза), `snapshot` (без простоя). Файл бэкапа — `vma.zst`.

**12. Контейнеры LXC**
```bash
pveam update
pveam available --section system | grep ubuntu-24.04
pct list
pct enter 200
```
`pveam` — менеджер шаблонов контейнеров. Точное имя файла шаблона зависит от версии `[ПРОВЕРИТЬ]`. `pct enter` — вход в контейнер без SSH.

**13. Кластер и HA**
```bash
pvecm status
ha-manager status
```
На одиночном узле `pvecm` честно скажет, что узел не в кластере. `ha-manager` на одиночном узле бесполезен — HA требует минимум два узла и кворум.

**14. Логи задач и служб**
```bash
ls -lt /var/log/pve/tasks/ | head
journalctl -u pveproxy -n 20 --no-pager
pvesh get /cluster/resources --output-format yaml
```
Каждая операция в UI — задача с ID вида `UPID:pve01:...`. Полный текст — в `/var/log/pve/tasks/`. `pvesh` дергает тот же API, что и веб-интерфейс, — удобно для скриптов.

**15. Производительность диска**
```bash
pveperf
```
Показывает `FSYNCS/SECOND`, `AVERAGE SEEK TIME`, скорость чтения. Низкие `FSYNCS/SECOND` (<200) — диск хоста слабый, ВМ будут «тормозить» на записи.

**Через GUI:** Datacenter → Summary (общая картина), узел pve01 → Shell / System → Syslog, ВМ → Summary / Snapshots / Hardware.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия
Стенд L2 готов: DC01 (10.10.10.10, AD/DNS/DHCP), FS01, WIN11-CL01, WIN10-CL02, UBU01, ASTRA01, домен `corp.vektor.lab`. Нужен свободный PVE01 — 10.10.10.70.

**Важно:** в таблице стенда PVE01 помечен треком «сисадмин», но тема урока — Proxmox, поэтому разворачиваем его **сейчас**, на том же адресе 10.10.10.70. Других машин не добавляем. ISO Proxmox VE качаем с официального `proxmox.com` — он бесплатный (подписка нужна только на репозиторий enterprise и поддержку); из РФ скачивание обычно работает, оплата подписки может быть затруднена — тогда живём на бесплатном репозитории `pve-no-subscription`.

### Снапшот
В VMware Workstation создаём ВМ PVE01 (пустой диск) и **сразу** делаем снапшот: правый клик по ВМ → Snapshot → Take Snapshot, имя `before-l2-045`. Это точка отката до установки. Внутренние снапшоты Proxmox (`qm snapshot`) — отдельная сущность, их делаем по ходу шагов.

### Шаги

1. **VMware Workstation → New Virtual Machine.** Гость Linux, 4 vCPU, 8 ГБ RAM, диск 64 ГБ (один), сеть — VMnet8 (NAT). В настройках ВМ → Processors включить галочку **«Virtualize Intel VT-x/EPT or AMD-V/RVI»**. Если галочки нет или она серая — на хосте выключи «Изоляцию ядра» Windows (Core Isolation) и перезагрузись. Ожидаемо: ВМ создана, снапшот `before-l2-045` снят.
2. **Смонтировать ISO Proxmox VE, включить ВМ.** В графическом установщике: `Install Proxmox VE` → принять лицензию → диск `ext4` → Location `Europe/Moscow` → пароль root `Lab#2026-vektor`, e-mail любой → **Management Network**: hostname `pve01.corp.vektor.lab`, IP `10.10.10.70/24`, gateway `10.10.10.2`, DNS `10.10.10.10`. Ожидаемо: установка ~10 минут, затем консоль с адресом `https://10.10.10.70:8006`.
3. **Первый вход по консоли.** `pveversion -v`, `ip -br a`, `ping -c2 10.10.10.10`. Ожидаемо: версия ядра PVE, адрес 10.10.10.70 на `vmbr0`, DC01 пингуется.
4. **Репозитории.** В `/etc/apt/sources.list.d/` отключить `pve-enterprise` (комментарий или переименовать файл), добавить `pve-no-subscription` в `/etc/apt/sources.list` (строка вида `deb http://download.proxmox.com/debian/pve bookworm pve-no-subscription` — сверь актуальную для твоей версии `[ПРОВЕРИТЬ]`). Затем `apt update && apt full-upgrade -y`. Ожидаемо: `apt update` проходит без 401.
5. **Веб-интерфейс.** Открыть `https://10.10.10.70:8006`, логин `root`, realm `PAM`, пароль стенда. Ожидаемо: слева узел pve01, предупреждение про отсутствие подписки — это норма.
6. **Проверка на вложенность.** `lsmod | grep kvm` и `grep -c vmx /proc/cpuinfo`. Ожидаемо: модули загружены, счётчик больше 0.
7. **Создать ВМ 100 `tst-vm`** (команда из п.4.6, ISO — любой Ubuntu Server 24.04, который ты уже качал для UBU01). `qm start 100`, открыть Console. Ожидаемо: видно меню установщика Ubuntu — значит KVM с вложенностью работает. Установку до конца делать не обязательно, достаточно дойти до меню.
8. **Снапшот и клон.** `qm snapshot 100 before-test`, `qm listsnapshot 100`, затем `qm clone 100 101 --name tst-vm-copy --full 1`. Ожидаемо: снапшот в списке, в `qm list` две ВМ.
9. **Контейнер.** `pveam update`, `pveam available --section system | grep ubuntu-24.04`, затем `pveam download local <имя_файла>`. Создать: `pct create 200 local:vztmpl/<имя_файла> --hostname tst-ct --cores 1 --memory 512 --rootfs local-lvm:4 --net0 name=eth0,bridge=vmbr0,ip=dhcp --unprivileged 1 --features nesting=1`. `pct start 200`, `pct enter 200`, внутри `ip a`. Ожидаемо: контейнер получил адрес от DC01 из пула 10.10.10.100–150.
10. **Проверка с клиента.** На WIN11-CL01: `ping <адрес tst-ct>`. Ожидаемо: пинг идёт, контейнер виден в офисной сети через мост `vmbr0`.
11. **Бэкап.** `vzdump 100 --storage local --mode snapshot --compress zstd`, затем `ls -lt /var/lib/vz/dump/`. Ожидаемо: файл `.vma.zst` и запись задачи в `/var/log/pve/tasks/`.
12. **Записать в `stand-log.md`** изменения: PVE01, адрес, версия, хранилища, объекты 100/101/200.

### Сломай и почини

**Пользователь:** `ivanov` (бухгалтерия, WIN11-CL01)
**ВМ:** PVE01, контейнер `tst-ct` (VMID 200)
**Что написал:** «Тестовый стенд не открывается, пингую — тишина. Нам на нём базу проверять, а мы застряли. Срочность: высокая»
**Срочность:** высокая

**Как воспроизвести:** в веб-интерфейсе PVE01 → `tst-ct` → Network → изменить `net0`, поставить bridge `vmbr1` (такого моста нет) → перезапустить контейнер. Или из CLI: `pct set 200 --net0 name=eth0,bridge=vmbr1,ip=dhcp`, затем `pct stop 200`.

**Диагностика по порядку:**
1. `pct list` — статус `stopped` (или контейнер «запущен», но без сети).
2. `pct start 200` — читаем ошибку. Ожидаемо: `bridge 'vmbr1' does not exist`.
3. `pct config 200 | grep net0` — видим `bridge=vmbr1`.
4. `cat /etc/network/interfaces` — в списке только `vmbr0`; моста `vmbr1` в конфигурации узла нет.
5. Сверяем с `stand-log.md`: раньше был `vmbr0`. Вывод — кто-то правил сеть контейнера.

**Решение:**
```bash
pct set 200 --net0 name=eth0,bridge=vmbr0,ip=dhcp
pct start 200
pct enter 200   # внутри: ip a
```
С клиента: `ping <адрес tst-ct>`.

**Ответ пользователю:** «Иван, тестовый стенд снова доступен, проверил пинг с вашей машины — отвечает. Причина: в сетевом профиле тестовой машины был указан несуществующий сегмент сети, после исправления всё поднялось. Извините за простой».

**Закрытие заявки:** категория «Виртуализация → Сеть ВМ», решение — правка `net0`, корневая причина «изменение сетевого профиля без проверки бриджа». Профилактика: в чек-лист правок PVE добавить пункт «после смены бриджа — `pct start` и пинг с клиентской ВМ». Время простоя фиксируем в заявке.

Частичный откат: внутри Proxmox `qm rollback 100 before-test`, удаление объектов `qm destroy 101`, `pct destroy 200`. После отката — обнови `stand-log.md`, чтобы журнал не врал.

## 6. Ошибки новичков и безопасность

1. **Оставили репозиторий `pve-enterprise` без подписки** → `apt update` падает с 401, человек думает, что «сломал систему» → отключить enterprise и подключить `pve-no-subscription` (в бою — купить подписку, она же даёт стабильные апдейты).
2. **Не проверили вложенную виртуализацию** → ВМ внутри PVE01 не стартуют с ошибкой про KVM/VT-x → проверять `vmx`/`svm` и галочку в VMware **до** установки.
3. **Снапшот вместо бэкапа** → снапшот лежит на том же хранилище; умер диск — умерли и ВМ, и снапшоты → снапшоты для быстрых откатов, `vzdump`/PBS для реального восстановления (тема урока 49).
4. **Клонирование работающей ВМ без остановки** → гость не консистентен, клон «странно себя ведёт» → останавливать или использовать снапшот-режим и `qemu-guest-agent` с fsfreeze.
5. **`qm stop` вместо `qm shutdown`** → обрыв питания, повреждение ФС гостя → ACPI/агент в первую очередь.
6. **Игнорирование `/var/log/pve/tasks/`** → гадание по всплывающему окну вместо точной причины → каждая задача имеет полный лог.
7. **Overcommit «на глаз»** → RAM хоста ушла в swap, все ВМ тормозят → следить за `pvestatd`, ballooning и KSM (урок 47).
8. **Всем выдали `root@pam`** → нет аудита, один человек ломает всё → отдельные пользователи в realm `PVE`, роли и API-токены.

### Безопасность
Веб-интерфейс 8006 наружу не публикуют: это полный контроль над гипервизором. В бою — отдельный management-VLAN, VPN, firewall (`pve-firewall`), 2FA, вход по SSH-ключам с запретом пароля root (`PermitRootLogin prohibit-password`), отдельные сервисные учётки. На стенде пароль `Lab#2026-vektor` — учебный; в реальной среде `root` с общим паролем недопустим. Также помни: при удалении ВМ командой `qm destroy` диск стирается сразу, без корзины.

## 7. Вопросы на собеседовании

**Вопрос 1. «Чем KVM отличается от QEMU и зачем нужны оба?»**
Ответ: KVM — модуль ядра, использующий VT-x/AMD-V, он исполняет код гостя на процессоре и даёт `/dev/kvm`. Сам по себе он не умеет ничего, кроме CPU и памяти. QEMU — userspace-эмулятор железа: чипсет, диски, сеть, BIOS. Вместе — быстрая ВМ: критичное на CPU идёт через KVM, устройства — через QEMU, а полувиртуализация через virtio снимает большую часть накладных расходов.
*Интервьюер хочет услышать:* разделение «ядро/пользовательское пространство» и понимание virtio.
*Красный флаг:* «KVM — это программа, которую запускают».

**Вопрос 2. «Что такое `/etc/pve` в Proxmox и почему туда не стоит писать руками?»**
Ответ: это ФС pmxcfs (FUSE + SQLite) с конфигурацией узла/кластера, которая реплицируется между узлами. Файлы ВМ — `/etc/pve/qemu-server/<vmid>.conf`, контейнеров — `lxc/`. Руками не пишут, потому что есть API и `qm`/`pct`, которые валидируют конфиг и не ломают синхронизацию; кроме того, прямые правки могут не подхватиться без перезапуска задач.
*Что хочет услышать:* что это кластерная шина конфигурации, а не обычная папка.
*Красный флаг:* «это просто папка, правлю vi».

**Вопрос 3. «Когда вы выберете LXC, а когда полноценную ВМ?»**
Ответ: LXC — когда нужен лёгкий сервис на том же ядре: прокси, тестовый веб, утилита. Плюс — секунды на старт, минимум RAM, десятки контейнеров на хосте. KVM — когда нужно своё ядро, другой гипервизор внутри, Windows, нестандартные модули, изоляция сильнее. Для Windows и 1С — только KVM.
*Что хочет услышать:* понимание компромисса «плотность против изоляции».
*Красный флаг:* «LXC — это то же самое, что KVM, только быстрее».

**Вопрос 4. «Чем снапшот Proxmox отличается от бэкапа и что будет при отказе диска?»**
Ответ: снапшот — состояние дисков на момент времени, хранится на том же хранилище и не защищает от отказа оборудования; он для быстрого отката перед обновлением. Бэкап (`vzdump`, Proxmox Backup Server) — независимая копия, которую можно восстановить на другом узле; отказ диска снапшот переживёт только если хранилище реплицировано/внешнее.
*Что хочет услышать:* «снапшот ≠ бэкап».
*Красный флаг:* «снапшот и бэкап — одно и то же».

**Вопрос 5. «ВМ не стартует. Ваши действия?»**
Ответ: смотрю текст задачи в `/var/log/pve/tasks/` или `journalctl -u pvedaemon/qemu-server`; проверяю `qm config <vmid>` (CPU тип, бридж, хранилище), `pvesm status` (активно ли хранилище, есть ли место), `lsmod | grep kvm` и флаги CPU, свободную RAM хоста. Типовые причины: бридж `vmbr1` отсутствует, thin-pool переполнен, `cpu: kvm64` без вложенности, ISO/диск удалён.
*Что хочет услышать:* порядок «лог → конфиг → ресурсы», а не «перезагружу хост».
*Красный флаг:* «сразу переустановлю Proxmox».
