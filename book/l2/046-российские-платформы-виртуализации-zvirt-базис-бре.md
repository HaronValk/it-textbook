## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

### Фундамент: KVM + QEMU + libvirt

**KVM** (Kernel-based Virtual Machine) — модуль в ядре Linux, который превращает ядро в гипервизор **первого типа**: он работает прямо на железе, без промежуточной ОС (в отличие от VMware Workstation в твоём стенде — это тип 2). **QEMU** — процесс, который эмулирует «железо» для виртуальной машины (чипсет, диски, сетевые карты). **libvirt** — слой управления, единый API и набор утилит (`virsh`), через который менеджер общается с QEMU. Ты уже трогал всё это в главах 41 и 45.

Ключевой вывод: zVirt, Базис, Брест и «Горизонт-ВС» — **не новые гипервизоры**. Это надстройки (management-слой) над KVM: веб-интерфейс, база данных, права, API, шаблоны, живая миграция, HA, журналы. Отличаются они диспетчерской, а не двигателем.

### Что ломается при переезде с VMware

Механика ВМ у VMware и KVM разная в трёх местах, и именно там живут все аварии:

1. **Контроллер диска.** У VMware — LSI Logic SAS / PVSCSI, у KVM — virtio-scsi или virtio-blk. Windows без драйвера virtio-scsi даёт `STOP 0x0000007B INACCESSIBLE_BOOT_DEVICE`.
2. **Сетевая карта.** VMXNET3 / E1000 → virtio-net. Нет драйвера — нет сети (а в Windows ещё и «неизвестное устройство»).
3. **Прошивка.** BIOS → SeaBIOS, UEFI → OVMF. Гость, поставленный в UEFI, не загрузится в BIOS-режиме.

Плюс административные мелочи: VMware Tools заменяется на **qemu-guest-agent**, снапшоты VMware не переносятся вообще, а лицензирование Windows при смене «железа» — вопрос к юристам `[ПРОВЕРИТЬ с вендором и лицензионным отделом]`.

## 3. Аналогия из жизни

Ты живёшь в доме, где сменилась управляющая компания. Стены, проводка, стояки — те же, их никто не перестраивал (это KVM в ядре Linux). Поменялась диспетчерская: новые квитанции, новый личный кабинет, новый слесарь, новые правила «кто за что отвечает» (это Manager, API, права, шаблоны). Плита у тебя осталась своя, но розетки в новой диспетчерской считают по-другому, и переходник (virtio-драйвер) надо купить заранее, иначе чайник не включится — ровно как BSOD 0x7B на ВМ.

Аналогия перестаёт работать в одном месте: у управляющей компании нельзя выкинуть фундамент и залить свой, а в виртуализации движок можно заменить целиком — часть вендоров пишет собственный менеджмент или даже уходит с oVirt-кода на что-то своё, и тогда «переходник» придётся искать заново.

## 4. Практика и команды

Все команды — на стенде «Вектор», на PVE01 (10.10.10.70) и UBU01 (10.10.10.30). Логика одна: платформы на KVM, значит инструменты KVM применимы к любой из них.

**1. Инвентаризация ВМ на гипервизоре (PVE01)**
```bash
qm list
qm config 100
```
`qm list` — таблица ВМ: VMID, имя, статус, память, загрузочный диск. `qm config <VMID>` — полный конфиг: `scsi0`, `virtio0`, `net0`, `bios`. Вывод:
```text
      VMID NAME         STATUS     MEM(MB)    BOOTDISK(GB) PID
       100 TST-L2       stopped    2048              20.00 0
scsi0: local-lvm:vm-100-disk-0,size=20G
net0: virtio=BC:24:11:AA:BB:CC,bridge=vmbr0
```
Смотреть: тип шины диска (`scsi0` c virtio-scsi vs `sata0`) и модель сетевой (`virtio` vs `e1000`). Это ровно те два поля, которые определят судьбу ВМ на новой платформе.

**2. Проверка API менеджера через curl**
```bash
curl -k -H "Authorization: PVEAPIToken=root@pam!lab=<UUID>" \
  https://10.10.10.70:8006/api2/json/nodes
```
`-k` — не проверять самоподписанный сертификат (на стенде нормально, в бою — нет). Ответ — JSON. Смысл упражнения: у zVirt API oVirt-совместимый, путь вида `/ovirt-engine/api/vms` `[ПРОВЕРИТЬ]`, и работать с ним учат так же — HTTP + токен/сессия.

**3. Информация о диске**
```bash
qemu-img info /root/tst-l2.qcow2
```
Показывает формат (`qcow2`/`raw`), виртуальный и фактический размер, backing file. Виртуальный размер больше фактического — норма для qcow2 (thin provisioning).

**4. Проверка целостности образа**
```bash
qemu-img check /root/tst-l2.qcow2
```
Ищи строку `No errors were found on the image.` Если есть `leaks` или `corruptions` — образ битый, переносить нельзя.

**5. Конвертация диска в формат, понятный KVM-платформам**
```bash
qemu-img convert -p -f raw -O qcow2 /dev/pve/vm-100-disk-0 /root/tst-l2.qcow2
```
`-p` — прогресс, `-f raw` — исходный формат (LVM-том «сырой»), `-O qcow2` — целевой. Это ядро любой миграции VMware→KVM: сначала vmdk→qcow2/raw (в VMware — `vmkfstools`, в Workstation просто копируешь `.vmdk` и конвертируешь), потом импорт в платформу.

**6. Сверка «до/после»**
```bash
qemu-img compare -f raw -F qcow2 /dev/pve/vm-100-disk-0 /root/tst-l2.qcow2
```
`-f`/`-F` — форматы первого и второго файла. Ожидаемо: `Images are identical.` Команда долгая, но это единственный честный способ убедиться, что конвертация не побила данные `[ПРОВЕРИТЬ поддержку ключей в вашей версии qemu-img]`.

**7. Конвертация «чужой» ВМ в KVM (virt-v2v)**
```bash
sudo apt install -y virt-v2v
virt-v2v -i vmx /path/win10-cl02.vmx -o local -os /var/lib/libvirt/images
```
`virt-v2v` — официальная утилита проекта libguestfs: читает VMware/Hyper-V ВМ, подкладывает virtio-драйверы в гость и создаёт KVM-ВМ. `-i vmx` — входной формат, `-o local` — выход в локальный libvirt `[ПРОВЕРИТЬ доступность пакета в Ubuntu 24.04 и полный набор ключей]`. Это то, что вендоры заворачивают в свой «мастер миграции».

**8. Проверка драйверов virtio внутри Windows-гостя**
```powershell
pnputil /enum-drivers | Select-String -Pattern "virtio","Red Hat"
Get-PnpDevice -Class SCSIAdapter | Format-Table FriendlyName,Status
```
Первая команда ищет в хранилище драйверов пакеты virtio. Вторая показывает контроллеры. Если контроллер — `Red Hat VirtIO SCSI controller` со статусом OK, ВМ переживёт переезд. Драйверы берутся с официального образа **virtio-win** (свободно распространяемый проект) `[ПРОВЕРИТЬ актуальный источник загрузки]`.

**9. Время и синхронизация**
```bash
timedatectl
chronyc tracking
```
```powershell
w32tm /query /status
```
Менеджер платформы, хосты и гости должны жить в одной секунде: иначе «прыгают» сертификаты, Kerberos в домене `corp.vektor.lab` и журналы. Смотри `System clock synchronized: yes` и `Leap status : Normal`.

**10. Сеть гипервизора**
```bash
ip -br a
bridge link
bridge vlan show
```
Показывает мосты и влан-теги. Перед миграцией фиксируешь: какие VLAN нужны ВМ, где trunk, какой MTU. В веб-интерфейсе любой платформы это те же «виртуальные сети/дата-центры».

**11. Готово ли железо к KVM**
```bash
egrep -c '(vmx|svm)' /proc/cpuinfo
lsmod | grep kvm
sudo apt install -y cpu-checker && kvm-ok
```
`kvm-ok` должен сказать `KVM acceleration can be used`. Если нет — в VMware Workstation в настройках ВМ UBU01 включи «Virtualize Intel VT-x/EPT or AMD-V/RVI» (вложенная виртуализация).

**12. Проверка продукта в Реестре российского ПО**
```text
Сайт: reestr.digital.gov.ru → поиск по названию продукта
```
Смотришь: запись есть, правообладатель — российское юрлицо, класс ПО «Средства виртуализации». Именно эту строчку просят в обосновании закупки.

**GUI-пути:** Proxmox — `https://10.10.10.70:8006`, раздел Datacenter → Node → VM. zVirt — веб-портал администратора (Administration Portal) `[ПРОВЕРИТЬ название]`. Базис и «Горизонт-ВС» — веб-интерфейсы управления `[ПРОВЕРИТЬ]`. Логика меню у всех одинаковая: Виртуальные машины / Хосты / Хранилища / Сети / Шаблоны / Задачи.

2. **UBU01, поддержка виртуализации.** `egrep -c '(vmx|svm)' /proc/cpuinfo` → число > 0; `lsmod | grep kvm` → `kvm_intel`/`kvm_amd`. Ожидаемо: KVM-модуль загружен.
3. **PVE01, инвентаризация.** `qm list` и `qm config 100`. Ожидаемо: ВМ в списке, в конфиге видно `scsi0` и `net0: virtio`.

Важно: сам WIN10-CL02 в этой лабе не переносим — он нужен целым для следующих глав. Воспроизводим **ту же механику** на тестовой TST-L2 (Linux), а для Windows-кейса проходим логику по шагам.

**Как воспроизвести поломку (PVE01):**
```bash
qm stop 100
qm set 100 --delete scsi0
qm set 100 --sata0 local-lvm:vm-100-disk-0,size=20G
qm start 100
qm terminal 100
```
Диск подключён другим контроллером — гость не находит корень и падает в initramfs / kernel panic. В Windows-кейсе это выглядит как `INACCESSIBLE_BOOT_DEVICE`.

**Диагностика по шагам (порядок важен):**
1. Смотрим консоль: `qm terminal 100` (выход `Ctrl+O`) или noVNC в веб-интерфейсе. Ищем `Unable to find root device` / `Kernel panic` — это сразу указывает на контроллер/шину, а не на данные.
2. Сверяем конфиг с эталоном: `qm config 100` — видим `sata0` вместо `scsi0`. Здесь 90% случаев закрываются.
3. Проверяем сам диск: `qemu-img check /root/tst-l2.qcow2` — цел ли образ (не повредила ли конвертация).
4. Проверяем, есть ли модуль в initramfs: монтируем диск (`qm set 100 --scsi0 ...` обратно, но не стартуем; либо подключаем live-ISO) и внутри chroot `lsinitramfs /boot/initrd.img-* | grep virtio`.
5. Только если данные целы — правим загрузку: возвращаем `scsi0` (virtio-scsi), при необходимости пересобираем initramfs `update-initramfs -u -k all` внутри chroot.
6. Для Windows порядок другой и делается **до** переноса: загрузить ВМ в VMware, `pnputil /add-driver <virtio-win>\viostor\w10\amd64\*.inf /install /subdirs`, затем конвертировать. Аварийный вариант — загрузиться в WinRE и подгрузить драйвер вручную.

**Решение:** вернуть `scsi0` с virtio-scsi, запустить, убедиться что гость поднялся и сеть есть (`ip -br a` внутри).
```bash
qm stop 100
qm set 100 --delete sata0
qm set 100 --scsi0 local-lvm:vm-100-disk-0,size=20G
qm start 100
```
**Ответ пользователю:** «Мария, добрый день. Проблема на стороне нового сервера — при переносе неправильно подключили диск, данные не пострадали. Исправил, включайте машину. Проверьте, пожалуйста, что открываются документы и 1С; если что-то ещё не так — напишите, я рядом. Приношу извинения за задержку.»

**Закрытие заявки:** категория «Виртуализация / миграция ВМ», решение — «несовпадение типа контроллера диска при импорте, исправлено переключением на virtio-scsi», в описании — команды и время восстановления. Отдельным пунктом — в план миграции: «все Windows-ВМ проходят предварительную установку virtio-драйверов, миграция без этого запрещена».

## 6. Ошибки новичков и безопасность

1. **«Выбрали zVirt, потому что он похож на VMware»** → к платформе прилагается другой набор ограничений по гостям, СХД и API, и выясняется это на этапе переноса 1С → правильно: сначала матрица требований (гостевые ОС, СХД, VDI, API, поддержка), потом продукт.
2. **Считать, что миграция = «скопировать диск»** → BSOD 0x7B, «пропавшая» сеть, нерабочий домен → правильно: до переноса — virtio-драйверы в гость, после — проверка `pnputil`, `Get-PnpDevice`, сети и времени.
3. **Верить обещаниям «поддерживает всё»** → на инвентаризации вылезает АРМ на Windows 7 или самописная программа под старой ОС → правильно: собрать список всех гостевых ОС до закупки, письменно получить от вендора подтверждение по каждой.
4. **Migrate без инвентаризации ресурсов** → «мы перенесли 30 ВМ, и всё упало в своп» → правильно: считать vCPU/RAM/IOPS до, а не после; помнить про overcommit из урока 41.
5. **Игнорировать СХД** → HA и живая миграция не работают, потому что диски лежат на локальных LUN → правильно: для HA нужен общий ресурс (NFS/iSCSI/FC) — см. урок 48.
6. **Один менеджер без резервирования** → падение Manager = нет управления платформой (ВМ при этом живы) → правильно: отказоустойчивый Manager или документированная процедура восстановления, и она должна быть протестирована.
7. **Не зафиксировать лицензии и поддержку** → через год выясняется, что обновления без продлённой поддержки недоступны → правильно: в план закупки сразу заложить поддержку и обучение.
8. **Проверять реестр ПО «на глаз»** → в обосновании закупки указан продукт без записи в реестре → правильно: скриншот записи из `reestr.digital.gov.ru` в пакет документов.

**Безопасность.** Нельзя: давать менеджеру платформы учётку `root`/`admin` с общим паролем (как учебный `Lab#2026-vektor` — только для стенда); открывать веб-интерфейс управления в офисную сеть без разграничения — он идёт по 443 и при этом управляет всем; отключать проверку сертификатов (`-k` в curl) в боевой среде; запускать миграцию через непроверенные сторонние скрипты в обход штатного мастера. В нормальной среде: отдельные учётки по ролям через LDAP/AD, MFA на портале админа, отдельный management-VLAN, журналирование всех действий с ВМ, регулярные обновления хостов.

## 7. Вопросы на собеседовании

**1. Чем российские платформы виртуализации отличаются от VMware на уровне архитектуры?**
Ответ: гипервизор — KVM в ядре Linux (тип 1, как ESXi), а не собственная микроядровая ОС VMware. Сверху — management-слой: веб-интерфейс, БД, API, шаблоны, HA. Отличие в зрелости экосистемы: у VMware 20 лет инструментов (vMotion, DRS, Veeam, тонны драйверов), у российских решений — набор функций уже близкий, но интеграций и обкатанных сценариев меньше. Формат диска — qcow2/raw вместо vmdk, драйверы — virtio вместо VMXNET3/PVSCSI.
*Что хочет услышать:* что ты понимаешь: это не «новый гипервизор», а надстройка над KVM, и поэтому навыки KVM переносимы. *Красный флаг:* «это те же VMware, только русские» или «там всё другое, я не разбирался».

**2. Как бы вы переносили Windows-ВМ с VMware на zVirt или Базис?**
Ответ: инвентаризация (ОС, контроллер, прошивка UEFI/BIOS, сеть, зависимости); до миграции — установка virtio-драйверов в гость (`pnputil /add-driver`), иначе BSOD 0x7B; конвертация диска (`qemu-img convert` / `vmkfstools` + `virt-v2v` / мастер миграции вендора); импорт, замена VMware Tools на qemu-guest-agent; проверка сети, времени, домена; тест на клоне, только потом боевая ВМ. Отдельно — окно обслуживания и точка возврата.
*Что хочет услышать:* порядок «сначала драйверы, потом конвертация», тест на клоне, наличие плана отката. *Красный флаг:* «просто скопирую диск и запущу».

**3. Что такое Реестр российского ПО и зачем он вам?**
Ответ: официальный перечень (`reestr.digital.gov.ru`), подтверждающий, что ПО создано российским правообладателем; используется для обоснования закупок и выполнения требований импортозамещения, особенно в госсекторе и КИИ. Проверяю перед закупкой: наличие записи, класс «средства виртуализации», правообладателя. Отдельно уточняю сертификаты ФСТЭК, если есть требования по безопасности.
*Что хочет услышать:* что ты знаешь, где проверить, и не путаешь реестр с «российским происхождением кода». *Красный флаг:* «реестр — это формальность, никто не проверяет».

**4. Как выбрать платформу для компании на 50 человек с 1С и КриптоПро?**
Ответ: сначала требования — гостевые ОС и их версии, наличие сертифицированных сборок КриптоПро под конкретную ОС, требования 1С к производительности и лицензированию, необходимость VDI, объём данных и СХД, требования по безопасности. Затем — реестр ПО, наличие поддержки в РФ, референсы, стоимость владения, наличие мастеров миграции и API для автоматизации. И обязательный этап — пилот на 3–5 ВМ, включая 1С и КриптоПро.
*Что хочет услышать:* «сначала требования и пилот, потом выбор», упоминание 1С и КриптоПро как реальных ограничений. *Красный флаг:* «возьмём самый дешёвый/самый известный, разберёмся по ходу».

**5. ВМ после миграции не загружается. Ваши действия?**
Ответ: смотрю консоль (не только статус в интерфейсе) — характер ошибки; проверяю конфиг ВМ: контроллер диска, прошивка, порядок загрузки; проверяю сам образ (`qemu-img check`); смотрю в госте наличие модулей в initramfs (Linux) / драйверов virtio (Windows); правлю контроллер или доставляю драйверы; фиксирую причину и добавляю её в чек-лист миграции, чтобы не повторилось.
*Что хочет услышать:* системный порядок действий от консоли к конфигу и образу, и что причина уходит в чек-лист. *Красный флаг:* «переустановлю ВМ» или «перезагружу менеджер».
