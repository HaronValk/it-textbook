# Администрирование Linux: пользователи, группы, права, sudo, PAM

## 1. Введение (зачем это нужно в реальной работе)

Тикет #4821. Пользователь: Иван Иванов (`ivanov`), ВМ WIN11-CL01. Что написал: «Здравствуйте! Вы мне давали доступ к папке на UBU01, я туда клал файлы выгрузки для склада. Сегодня WinSCP пишет „Permission denied“. И ещё: коллеги говорят, что мои файлы в общей папке они не видят. Срочно, отчёт в конце дня».

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Кто есть кто.** В Linux пользователь — это просто число: UID. Имя — удобная надпись. На Ubuntu UID 0 — root, 1–999 — системные учётки (демоны), с 1000 — обычные люди. GID — то же самое для групп. Права проверяются ядром по числам, а не по именам: имя `ivanov` ищется через NSS (в простом случае — файл `/etc/passwd`, позже — через SSSD и AD, см. урок 58).

**Четыре файла-справочника:**

```text
/etc/passwd   ivanov:x:1001:1001:Иван Иванов:/home/ivanov:/bin/bash
              имя : пароль(x=смотри в shadow) : UID : GID основной группы : GECOS(комментарий) : домашний каталог : оболочка

/etc/shadow   ivanov:$y$j9T$....:19700:0:99999:7:::
              имя : хеш пароля : дата последней смены (в днях от 1970) : мин.срок : макс.срок : предупреждение : ...

/etc/group    GG-Buh:x:1002:ivanov,petrova
              имя : пароль : GID : список ДОПОЛНИТЕЛЬНЫХ участников

/etc/gshadow  пароли групп и администраторы групп
```

**Основная и дополнительные группы.** У пользователя один primary GID (он идёт в новые файлы по умолчанию) и список supplementary-групп. Именно из-за этого списка и возникает классическая проблема: `usermod -aG` меняет файлы, но **уже открытая сессия SSH права не подхватывает** — перелогиньтесь.

**Права: 9 бит и три спецбита.** `rwx` для владельца, группы, остальных. Плюс:

```text
SUID  (4xxx) — программа запускается с UID владельца файла (пример: /usr/bin/passwd)
SGID  (2xxx) — на файле: запуск с GID владельца; на КАТАЛОГЕ: новые файлы получают группу каталога, а не группу создателя
Sticky(1xxx) — в каталоге удалять файл может только его владелец (пример: /tmp, режим 1777)
```

SGID на каталоге — главный приём для файловых шар: `/srv/Buh` с `2770` и группой `GG-Buh` даёт то, что все файлы внутри принадлежат группе `GG-Buh`, кто бы их ни создал.

Если битов не хватает (нужен доступ одному человеку вне группы) — **ACL**: `setfacl -m u:petrova:rx /srv/Buh`. В `ls -l` такой каталог помечается плюсом.

**PAM (Pluggable Authentication Modules)** — слой между программой и способом проверки личности. Программа (sshd, login, su, sudo, passwd) не знает, откуда берётся пароль; она вызывает библиотеку PAM, а та читает свой конфиг из `/etc/pam.d/<сервис>`.

```text
 ssh ivanov@10.10.10.30
         │
         ▼
   sshd  ──pam_start("sshd")──►  /etc/pam.d/sshd
         │                        │
         │                        ├── include  /etc/pam.d/common-auth   ← AUTH: проверить пароль
         │                        │       ├─ pam_faillock  (счётчик неудач)
         │                        │       ├─ pam_unix      (сверяет с /etc/shadow)
         │                        │       └─ pam_env, pam_limits
         │                        ├── include  /etc/pam.d/common-account  ← ACCOUNT: не истёк ли пароль, не заблокирован ли
         │                        ├── include  /etc/pam.d/common-session  ← SESSION: лимиты, монтирование /home, umask, SELinux/AppArmor
         │                        └── include  /etc/pam.d/common-password ← PASSWORD: смена пароля, проверка сложности
         ▼
   оболочка /bin/bash с UID, GID и списком групп
```

У каждого модуля в строке есть **тип** (`auth`, `account`, `session`, `password`) и **флаг управления**: `required` (обязательно пройти, ошибка запоминается), `requisite` (провал = немедленный отказ), `sufficient` (успех = хватит, дальше не идти), `optional`, `[success=N default=ignore]` — переходы по числу шагов.

**sudo** — отдельная история: это не «стать root», а «выполнить конкретную команду от имени конкретного пользователя, если это разрешено в `/etc/sudoers`». Формат правила:

```text
Кто      Где      =(От кого)  Что можно
ivanov   ALL      =(root)     /usr/bin/systemctl status ssh
```

Бонус: sudo **логирует каждую команду** в `/var/log/auth.log` — это ваша доказательная база при разборе инцидентов.

## 3. Аналогия из жизни

Представьте проходную завода. `/etc/passwd` — это список сотрудников на вахте: фамилия, номер пропуска (UID), отдел (GID). `/etc/shadow` — сейф с образцами подписей, вахтёру сам список не показывают. Группы — это профсоюзные списки: человек может состоять в нескольких, и в бухгалтерию его пустят по членству в «бухгалтерской» секции, даже если он вообще из склада. Права на файл — это табличка на двери: «директору — можно всё, бухгалтерии — читать, остальным — нельзя».

PAM — это не вахтёр, а **цепочка постов охраны внутри здания**: на первом проверяют, не в чёрном ли вы списке (faillock), на втором сверяют подпись (pam_unix), на третьем смотрят, не истёк ли пропуск (account), на четвёртом выдают ключи от кабинета (session). Можно поменять инструкцию любому посту, не перестраивая здание.

sudo — это начальник цеха, который не выдаёт вам мастер-ключ от всего завода, а подписывает разовое разрешение «зайти в этот шкаф и только в этот», причём каждый раз заново и под запись в журнале.

Аналогия ломается на ACL: это как если бы на двери висела не табличка «отдел», а именной список конкретных людей, который не отменяет общий, а дополняет его.

## 4. Практика и команды

Все примеры — на UBU01 (Ubuntu Server 24.04, `10.10.10.30`). `sudo` — вы под `adm.student`.

**1. Кто я и кто он: `id`, `whoami`, `groups`**

```bash
id
id ivanov
groups petrova
```

```text
uid=1000(adm.student) gid=1000(adm.student) groups=1000(adm.student),27(sudo),1003(GG-IT)
uid=1001(ivanov) gid=1001(ivanov) groups=1001(ivanov),1002(GG-Buh)
```

Смотрим: UID (0 = root, ≥1000 = человек), основной GID и полный список групп. Первое, что вы делаете в любой заявке «нет доступа» — `id <пользователь>`.

**2. `getent` вместо `cat /etc/passwd`**

```bash
getent passwd ivanov
getent group GG-Buh
getent group | grep -i buh
```

`getent` спрашивает через NSS — то есть покажет и локальных, и (после урока 58) доменных пользователей из AD. `cat /etc/passwd` покажет только локальных. Привыкайте к `getent`.

**3. Создание группы и пользователя**

```bash
sudo groupadd GG-Buh
sudo useradd -m -U -s /bin/bash -G GG-Buh -c "Иван Иванов, бухгалтерия" ivanov
sudo passwd ivanov            # задаём Lab#2026-vektor
sudo chage -d 0 ivanov        # заставить сменить пароль при первом входе
```

`-m` — создать `/home/ivanov` из `/etc/skel` (без него дом. каталога не будет, и половина программ будет падать со странными ошибками); `-U` — создать одноимённую основную группу; `-s` — оболочка; `-G` — дополнительные группы; `-c` — комментарий (GECOS). Пароль задаём отдельно — `useradd` его не спрашивает.

**4. Изменение пользователя: главная ловушка**

```bash
sudo usermod -aG GG-HR petrova     # ПРАВИЛЬНО: добавить в доп. группу
sudo usermod -G GG-HR petrova      # ЛОВУШКА: заменить ВЕСЬ список доп. групп
sudo usermod -g GG-HR petrova      # сменить ОСНОВНУЮ группу
sudo usermod -L ivanov             # заблокировать (в shadow появится !)
sudo usermod -U ivanov             # разблокировать
sudo usermod -s /usr/sbin/nologin sidorov   # запретить интерактивный вход
```

`-a` = append. Без него вы молча выкидываете человека из всех групп, где он был.

**5. Удаление**

```bash
sudo userdel -r sidorov     # -r: снять домашний каталог и почтовый ящик
sudo groupdel GG-Sklad
```

Перед удалением проверьте, нет ли живых процессов: `ps -u sidorov`. И помните: файлы, созданные им вне домашки, останутся с его UID — после удаления в `ls -l` вместо имени будет просто число.

**6. Права на каталог: `chmod`, `chown`, `stat`**

```bash
sudo chown root:GG-Buh /srv/Buh
sudo chmod 2770 /srv/Buh
ls -ld /srv/Buh
stat /srv/Buh
```

```text
drwxrws--- 2 root GG-Buh 4096 ... /srv/Buh
```

`rws` в позиции группы владельца — это SGID. Восьмерично: 2 (SGID) + 7 (rwx владельцу) + 7 (rwx группе) + 0 (остальным). `chmod g+s` — то же самое буквами, `chmod g-s` — снять.

**7. `umask` — права по умолчанию**

```bash
umask            # типично 0022
umask 002        # файлы 664, каталоги 775 — то, что нужно файловому серверу
echo 'umask 002' | sudo tee /etc/profile.d/umask-vektor.sh
```

`umask` — не права, а маска вычитания из 666 (файлы) и 777 (каталоги). При 0022 файл получается 644: коллеги из группы читать смогут, писать — нет. Отсюда и жалоба «мои файлы никто не видит» при 0077.

**8. ACL — точечный доступ вне группы**

```bash
sudo apt install acl
sudo setfacl -m u:petrova:rx /srv/Buh
sudo setfacl -R -m u:petrova:rX /srv/Buh    # -R рекурсивно, X = x только на каталоги
getfacl /srv/Buh
ls -ld /srv/Buh     # в выводе появится '+' после прав
sudo setfacl -x u:petrova /srv/Buh          # убрать
```

`-m` — изменить, `-x` — удалить запись. ACL живёт поверх обычных прав и не отменяет их.

**9. Найти «опасные» файлы**

```bash
sudo find / -xdev -perm -4000 -type f 2>/dev/null
```

```text
/usr/bin/passwd
/usr/bin/sudo
/usr/bin/su
/usr/bin/mount
/usr/lib/openssh/ssh-keysign
```

SUID/SGID-бинарники — потенциальный путь повышения привилегий. Список должен быть коротким и объяснимым; новый незнакомый файл — повод для разбора.

**10. Ограниченный sudo через drop-in файл**

```bash
sudo visudo -f /etc/sudoers.d/10-vektor
```

```text
%GG-IT  ALL=(ALL:ALL) ALL
ivanov  ALL=(root) /usr/bin/systemctl status ssh, /usr/bin/journalctl -u ssh
Defaults:ivanov !requiretty
```

Проверка синтаксиса и результата:

```bash
sudo visudo -c                      # /etc/sudoers.d/10-vektor: parsed OK
sudo -l -U ivanov                   # что именно разрешено пользователю
```

Важно: команда в sudoers матчится **вместе с аргументами**. `sudo journalctl -u ssh` разрешено, а `sudo journalctl -u ssh -n 100` — уже нет. Файлы в `sudoers.d` не должны содержать точку или `~` в имени, иначе sudo их игнорирует.

**11. Работа с sudo и сброс «доверия»**

```bash
sudo -l             # что могу я
sudo -k             # забыть пароль sudo сейчас
sudo -i             # root-shell (если разрешено)
sudo -u postgres psql   # выполнить от имени другого пользователя
```

По умолчанию sudo помнит пароль 15 минут (`timestamp_timeout`). `sudo -k` полезен, когда передаёте ноутбук/сессию коллеге.

**12. Сроки жизни паролей**

```bash
sudo chage -l ivanov
sudo passwd -S ivanov
```

```text
Last password change                                    : Jan 12, 2026
Password expires                                        : Apr 12, 2026
Minimum number of days between password change          : 0
Maximum number of days between password change          : 90
```

`passwd -S` даёт кратко: `P` (задан), `L` (заблокирован), `NP` (пустой). Глобальные значения по умолчанию — в `/etc/login.defs`.

**13. PAM: смотрим и настраиваем блокировку**

```bash
ls /etc/pam.d/ | head -30
grep -v '^#' /etc/pam.d/common-auth
sudo cp /etc/pam.d/common-auth /root/common-auth.bak
```

Типовая стопка Ubuntu с включённым faillock выглядит примерно так (точный порядок строк стоит сверить с вашим релизом — `[ПРОВЕРИТЬ]` для 24.04):

```text
auth    required                        pam_faillock.so preauth
auth    [success=1 default=ignore]      pam_unix.so nullok
auth    [default=die]                   pam_faillock.so authfail
auth    sufficient                      pam_faillock.so authsucc
```

Параметры блокировки в современных версиях принято задавать в `/etc/security/faillock.conf`:

```text
deny = 3
unlock_time = 300
```

Управление счётчиком:

```bash
sudo faillock --user ivanov
sudo faillock --user ivanov --reset
```

**14. GUI-вариант (если очень надо мышкой)**

На Ubuntu Server «из коробки» GUI для пользователей нет. Есть веб-консоль Cockpit: `sudo apt install cockpit`, затем `https://10.10.10.30:9090` — раздел Accounts. Для настольных редакций — `gnome-system-tools`/`users-admin` `[ПРОВЕРИТЬ актуальность]`. В любом случае на сервере Linux админ работает через `useradd`/`usermod`, а не через меню.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

- Стенд L1 собран: DC01, FS01, WIN11-CL01, WIN10-CL02, **UBU01** (`10.10.10.30`), ASTRA01.
- На UBU01 есть локальная учётка `adm.student` с sudo, открыт SSH (проверяется командой `ssh adm.student@10.10.10.30`).
- Если sudo у `adm.student` нет — сначала пройдите тему L1 «Linux: установка и базовая настройка сервисов» или загрузитесь в recovery mode через GRUB и добавьте себя в группу `sudo`: `usermod -aG sudo adm.student`.
- Сетевые папки FS01 трогать не будем: Samba и интеграция с AD — урок 58. Здесь делаем локальный аналог на UBU01 в `/srv`, чтобы отработать права и ACL.

### Снапшот

В VMware Workstation на ВМ **UBU01**: меню `VM → Snapshot → Take Snapshot…`, имя `before-l2-051`, описание «до лабораторной 51 — пользователи, группы, права, sudo, PAM». Кнопка «Take Snapshot». (Если делаете из CLI хоста с установленным `vmrun` — `vmrun snapshot "<путь к UBU01.vmx>" before-l2-051`.)

### Шаги

1. **Вход и фиксация состояния.** На хосте: `ssh adm.student@10.10.10.30`. Затем `hostnamectl`, `id`, `cat /etc/os-release | head -3`. Ожидаемо: `Ubuntu 24.04.x LTS`, ваш UID 1000 и наличие `sudo` в списке групп.
2. **Инвентаризация.** `getent passwd | awk -F: '$3>=1000'` и `getent group | awk -F: '$3>=1000'`, `ls -l /home`. Ожидаемо: только `adm.student` (и, возможно, служебные учётки). Запомните занятые UID/GID.
3. **Создаём группы.** По одной: `sudo groupadd GG-Buh`, `GG-HR`, `GG-Sklad`, `GG-IT`. Проверка: `getent group GG-Buh` → `GG-Buh:x:1002:`. Ожидаемо: четыре новые группы.
4. **Создаём пользователей UBU01 (локальные «двойники» доменных).**
```bash
sudo useradd -m -U -s /bin/bash -G GG-Buh   -c "Иван Иванов, бухгалтерия" ivanov
sudo useradd -m -U -s /bin/bash -G GG-HR    -c "Мария Петрова, HR"        petrova
sudo useradd -m -U -s /bin/bash -G GG-Sklad -c "Алексей Сидоров, склад"   sidorov
sudo usermod -aG GG-IT adm.student
for u in ivanov petrova sidorov; do echo "$u:Lab#2026-vektor" | sudo chpasswd; done
sudo chage -d 0 ivanov
```
Ожидаемо: три домашних каталога в `/home`, у `ivanov` при первом входе запросят смену пароля. Пароль `Lab#2026-vektor` — учебный, только для стенда.
5. **Готовим каталоги.** 
```bash
sudo mkdir -p /srv/Obshchee /srv/Buh /srv/HR
sudo chown root:GG-Buh   /srv/Buh  && sudo chmod 2770 /srv/Buh
sudo chown root:GG-HR    /srv/HR   && sudo chmod 2770 /srv/HR
sudo chown root:GG-IT    /srv/Obshchee && sudo chmod 1777 /srv/Obshchee
ls -ld /srv/*
```
Ожидаемо: у `/srv/Buh` и `/srv/HR` — `drwxrws---` (SGID), у `/srv/Obshchee` — `drwxrwxrwt` (sticky).
6. **Проверяем доступ руками.** `su - ivanov` (пароль, затем смена), дальше:
```bash
touch /srv/Buh/otchet-ivanov.txt && ls -l /srv/Buh/otchet-ivanov.txt
ls /srv/HR
```
Ожидаемо: файл создан и его группа — `GG-Buh` (работает SGID), а в `/srv/HR` — `Permission denied`. Выход: `exit`.
7. **Проверяем sticky.** `su - petrova`, `touch /srv/Obshchee/otchet-ivanov.txt` — создаём файл с чужим именем. Затем `su - ivanov` и `rm /srv/Obshchee/otchet-ivanov.txt` → `Operation not permitted`. Ожидаемо: удалить чужой файл в обменнике нельзя. Свой — можно.
8. **Правим umask.** Создайте `/etc/profile.d/umask-vektor.sh` со строкой `umask 002` (`echo 'umask 002' | sudo tee /etc/profile.d/umask-vektor.sh`). Перелогиньтесь под `ivanov`, `umask` → `0002`, `touch /srv/Buh/new.txt && ls -l` → `-rw-rw-r--`. Ожидаемо: новые файлы пишутся группой.
9. **ACL для petrova.** `sudo setfacl -m u:petrova:rx /srv/Buh`, `getfacl /srv/Buh`, `ls -ld /srv/Buh` (появился `+`). Под `petrova`: `ls /srv/Buh` работает, `touch /srv/Buh/x.txt` → `Permission denied`. Ожидаемо: чтение есть, записи нет.
10. **Ограниченный sudo.** `sudo visudo -f /etc/sudoers.d/10-vektor`, содержимое:
```text
%GG-IT  ALL=(ALL:ALL) ALL
ivanov  ALL=(root) /usr/bin/systemctl status ssh, /usr/bin/journalctl -u ssh
Defaults:ivanov !requiretty
```

1. `id ivanov` — убеждаемся, что `GG-Buh` на месте. Если группы нет → `usermod`, но это не наш случай.

3. `namei -l /srv/Buh/otchet.md` — проверяем права на каждом уровне пути (`/`, `/srv`, `/srv/Buh`, файл). Классика: доступ закрыт не на последнем звене, а на родительском каталоге.

6. `sudo ls -l /srv/Buh` — смотрим, какие файлы унаследовали неверную группу.

sudo chown -R root:GG-Buh /srv/Buh

Проверяем под `ivanov`: `touch /srv/Buh/otchet.md` — работает, группа у файла `GG-Buh`.

## 6. Ошибки новичков и безопасность

1. **`chmod -R 777` «чтобы точно заработало»** → любой пользователь читает, пишет и удаляет чужие файлы, а на сервере с веб-приложением это прямой путь к компрометации. Правильно: группы + `2770`, ACL для исключений.
2. **`usermod -G` без `-a`** → человек молча выпадает из всех прежних групп, ломается доступ к почте, базе, шарам. Правильно: всегда `-aG`.
3. **`chown -R` не глядя, с корня** → сломанные SUID-бинарники и неработающий вход в систему (`/usr/bin/sudo` с неверным владельцем). Правильно: сначала `ls -ld`, потом команда только на конкретный каталог.
4. **Правка `/etc/sudoers` обычным `nano`** → одна опечатка, и sudo не работает ни у кого, включая вас. Правильно: только `visudo` (он проверяет синтаксис при сохранении) и `visudo -f` для drop-in файлов.
5. **`NOPASSWD: ALL` всей группе** → любой сотрудник ИТ-отдела фактически root без пароля. Правильно: поимённое перечисление команд под конкретными учётками.
6. **Забыть `-m` в `useradd`** → пользователь без `/home`, программы падают с невнятными ошибками. Правильно: `useradd -m -U -s /bin/bash`.
7. **Тестировать блокировку PAM на своей учётке** → `faillock` запирает `adm.student`, sudo недоступен, лечится только консолью VMware. Правильно: тестировать на отдельном пользователе и держать открытой вторую сессию с root.
8. **Пароли в открытом виде** — `echo 'ivanov:Pass123' >> script.sh` или `passwd` в истории bash. Правильно: `chpasswd` из защищённого файла, `HISTCONTROL=ignorespace` для команд с секретами, для сервисов — ключи SSH, а не пароли.

### Безопасность

В боевой среде: не выдавайте пользователям полный sudo «на время» — это не откатывается в головах; не редактируйте `common-auth` без резервной копии и без второй открытой root-сессии (это единственный способ не потерять доступ); не отключайте `faillock` ради удобства тестов; не логиньтесь под root напрямую по SSH — только свой пользователь + sudo, потому что sudo пишет, кто и что запускал, а root-сессия — нет. Учебный пароль `Lab#2026-vektor` — исключительно для стенда: в реальной работе такие пароли запрещены политикой и проверяются аудитом.

## 7. Вопросы на собеседовании

**1. Что происходит от ввода пароля до появления шелла при `ssh ivanov@host`?**

Ответ: sshd аутентифицирует по ключу или паролю; для пароля он вызывает PAM через `/etc/pam.d/sshd`, который подключает `common-auth` (в нём `pam_faillock` для счётчика неудач и `pam_unix`, сверяющий хеш с `/etc/shadow`). Дальше идут `account` (не истёк ли пароль, не заблокирован ли), `session` (`pam_limits`, `pam_systemd`, создание домашнего каталога при необходимости) и `password` — но последний только при смене пароля. После успеха sshd выставляет UID/GID и список групп пользователя и запускает его оболочку из `/etc/passwd`.

*Что хочет услышать интервьюер:* что вы понимаете PAM как цепочку из четырёх типов модулей, а не «sshd сам проверяет пароль».
*Красный флаг:* «sshd читает /etc/passwd напрямую» или путаница между `/etc/passwd` и `/etc/shadow`.

**2. Чем отличаются режимы 755, 2775 и 1777?**

Ответ: 755 — владелец rwx, группа и остальные r-x, обычный каталог. 2775 — то же плюс SGID: новые файлы и подкаталоги наследуют группу каталога, а не группу создателя; стандарт для общих папок отделов. 1777 — sticky bit: писать могут все, но удалять/переименовывать файл — только его владелец, владелец каталога или root; так устроен `/tmp` и обменники.

*Что хочет услышать интервьюер:* что вы знаете прикладной смысл SGID на каталоге (наследование группы), а не только цифры.
*Красный флаг:* «2775 — это когда у файла две группы» или незнание, что SGID на каталоге и на файле ведёт себя по-разному.

**3. Как дать пользователю ровно одну команду от root и не дать больше?**

Ответ: через drop-in файл `/etc/sudoers.d/` (создаётся `visudo -f`), правило вида `ivanov ALL=(root) /usr/bin/systemctl status ssh`, без `NOPASSWD`. Помнить, что команда матчится вместе с аргументами: `sudo systemctl status ssh` разрешено, `sudo systemctl stop ssh` — нет. Проверять `sudo -l -U ivanov` и `visudo -c`. Каждое выполнение попадёт в `/var/log/auth.log`. Если нужна одна операция, а не команда — лучше сделать скрипт-обёртку с фиксированной логикой и разрешить только его.

*Что хочет услышать интервьюер:* дисциплина минимальных привилегий и знание, что sudo логируется.
*Красный флаг:* «добавлю в группу sudo, потом уберу» или `NOPASSWD: ALL`.

**4. Пользователь говорит «я в группе, но доступа нет». Ваши действия?**

Ответ: `id пользователя` — реально ли группа в списке; напомнить про перелогин, если группу добавили в текущей сессии. Затем `namei -l` по полному пути — проверить права на каждом уровне (часто закрыт родительский каталог, а не конечный). Затем `getfacl` — нет ли мешающей ACL-записи, `ls -ld` — правильная ли группа-владелец и цел ли SGID. И только потом смотреть логи (`/var/log/auth.log`), не связано ли это с PAM или sudo.

*Что хочет услышать интервьюер:* системный порядок проверки и знание про `namei`/ACL, а не «сразу chmod 777».
*Красный флаг:* «сделаю 777 и закрою заявку» — так вы создаёте инцидент информационной безопасности.

**5. Что такое PAM и зачем нужен `common-auth`?**

Ответ: PAM — подключаемый слой аутентификации: приложение вызывает библиотеку, а она читает `/etc/pam.d/<сервис>` и выполняет модули. `common-auth` — общий файл, который большинство сервисов подключают через `include`, поэтому изменение в нём действует сразу на весь вход в систему (SSH, su, login, sudo). Плюс: единая политика. Минус: ошибка в этом файле блокирует вход всем, поэтому нужны бэкап и вторая открытая сессия. На Ubuntu файлами `common-*` управляет `pam-auth-update` по профилям из `/usr/share/pam-configs`.

*Что хочет услышать интервьюер:* понимание риска «одна ошибка — и сервер недоступен» и аккуратность администрирования.
*Красный флаг:* «PAM — это файрвол» или «не трогаю PAM, там страшно» без понимания сути.
