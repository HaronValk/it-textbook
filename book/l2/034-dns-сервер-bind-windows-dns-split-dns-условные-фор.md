## 2. Теория «под капотом»

**Две роли DNS-сервера.** *Авторитативный* — тот, у которого есть сама зона (файл с записями): он отвечает «это мои данные». *Рекурсивный (кэширующий/форвардер)* — тот, который сам данных не имеет, но бегает за них спрашивать и складывает ответ в кэш. DC01 в нашем стенде — и то и другое: он авторитативен для `corp.vektor.lab` и рекурсивен для всего остального.

**Резолюция по шагам.** Клиент шлёт запрос своему DNS-серверу (рекурсивный запрос, флаг RD=1). Если сервер не авторитативен и в кэше пусто — он идёт по цепочке от корневых серверов к TLD и к авторитативному серверу зоны (итеративные запросы, RD=0), получает ответ, кэширует его на время TTL и возвращает клиенту.

**Порты и протоколы.** Классика — `53/udp` (быстрые короткие запросы) и `53/tcp` (крупные ответы, зонные трансферы AXFR/IXFR, работа при обрезанном UDP). EDNS0 расширяет размер UDP-пакета. DNS over TLS — `853/tcp`, DNS over HTTPS — `443/tcp`. В AD DNS критичны SRV-записи (`_ldap._tcp.dc._msdcs...`) — без них домен «не находится», хотя пинг по IP работает.

**Форвардер vs условный форвардер.** Обычный форвардер — «всё, что не моё, отправляй вот сюда» (например, на DNS провайдера). Условный (conditional forwarder) — «имена зоны X отправляй на конкретный сервер Y». Второй нужен для партнёрских доменов, отдельных сегментов и split-DNS.

**Split-DNS (views).** Один и тот же домен отдаёт разные ответы в зависимости от того, кто спросил. Внутри — приватные адреса, снаружи — публичные. В BIND это делается директивами `view` + `match-clients`, в Windows — зонными областями (zone scopes) и DNS-политиками, появившимися в Windows Server 2016.

**Кэширование.** Каждый ответ живёт TTL секунд. Отрицательный ответ (NXDOMAIN/NODATA) тоже кэшируется — на время из поля SOA Minimum. Поэтому «поменял A-запись, а у пользователей старый IP» — это не баг, это TTL.

```text
WIN11-CL01 (DHCP, DNS = 10.10.10.10)
   │ 1) A? www.vektor.lab   UDP/53, RD=1
   ▼
DC01 10.10.10.10 — рекурсивный + авторитативный для corp.vektor.lab
   │ 2) в зоне corp.vektor.lab совпадений нет
   │ 3) условный форвардер зоны vektor.lab → 10.10.10.30
   ▼
UBU01 10.10.10.30 — BIND 9, авторитативный для vektor.lab
   ├── view "internal" (match-clients 10.10.10.0/24, 127.0.0.1)
   │      www.vektor.lab    A 10.10.20.10
   │      intranet.vektor.lab A 10.10.10.20
   └── view "external" (match-clients any)
          www.vektor.lab    A 203.0.113.10   (документационный диапазон RFC 5737)
```

## 3. Аналогия из жизни

Представьте справочную в большом бизнес-центре. На стойке сидит администратор (рекурсивный DNS): он сам не знает, где находится фирма «Ромашка», но у него есть телефонный справочник города (корневые серверы), справочник района (TLD) и телефон самой фирмы (авторитативный сервер). Он звонит по цепочке, узнаёт номер и **записывает его на стикер с датой** — стикер живёт, пока не истечёт срок (TTL). Если фирма переехала, а стикер ещё не истёк — администратор уверенно отправляет вас по старому адресу.

Условный форвардер — это отдельная записка «по всем вопросам про фирму „Вектор“ звонить не в справочник, а сразу на её ресепшн». А split-DNS — два разных справочника на одном стойке: для сотрудников бизнес-центра (внутренний) и для внешних посетителей (внешний), причём в внешнем нет половины внутренних телефонов.

Аналогия перестаёт работать в одном месте: администратор на стойке не «стареет» и не забывает стикеры сам — кэш надо чистить руками, и именно этим вы будете заниматься половину лабораторной.

## 4. Практика и команды

### Windows DNS (DC01)

**1. Посмотреть зоны и их тип.**
```powershell
Get-DnsServerZone | Select-Object ZoneName, ZoneType, IsDsIntegrated, ReplicationScope
```
`ZoneType`: `Primary` / `Secondary` / `Stub` / `Forwarder`. `IsDsIntegrated = True` — зона хранится в AD и реплицируется на DC02 автоматически, отдельного «переноса файла» не нужно. `Forwarder` в этом списке — это и есть условные форвардеры.

**2. Разобрать содержимое зоны.**
```powershell
Get-DnsServerResourceRecord -ZoneName corp.vektor.lab -Name "@" -RRType SOA
Get-DnsServerResourceRecord -ZoneName corp.vektor.lab | Where-Object { $_.RecordType -eq 'A' } | Select-Object HostName, RecordType, @{n='IP';e={$_.RecordData.IPv4Address}}
```
Смотрите на SOA: `SerialNumber` (растёт при каждом изменении), `PrimaryServer`, и особенно `Minimum` — это TTL отрицательного кэширования.

**3. Завести условный форвардер.**
```powershell
Add-DnsServerConditionalForwarderZone -Name "vektor.lab" -MasterServers 10.10.10.30
Get-DnsServerZone | Where-Object ZoneType -eq 'Forwarder' | Select-Object ZoneName, MasterServers
```
Обратите внимание: `vektor.lab` — родительская зона для `corp.vektor.lab`, но это не конфликт: DNS всегда выбирает **самое длинное совпадение суффикса**, поэтому `ivanov.corp.vektor.lab` уйдёт в AD-зону, а `www.vektor.lab` — на BIND. [ПРОВЕРИТЬ: поведение оснастки при создании форвардера для родительской зоны в вашей сборке Windows Server]

**4. Кэш сервера: посмотреть и сбросить.**
```powershell
Get-DnsServerCache | Select-Object -First 20
Clear-DnsServerCache -Force
```
`Get-DnsServerCache` показывает, что сервер уже знает и сколько секунд это ещё проживёт. `Clear-DnsServerCache -Force` — без запроса подтверждения. Эквивалент через утилиту: `dnscmd /clearcache`.

**5. Точечный запрос к конкретному серверу.**
```powershell
Resolve-DnsName www.vektor.lab -Server 10.10.10.30 -Type A -DnsOnly
Resolve-DnsName www.vektor.lab -Server 10.10.10.10 -Type A -DnsOnly
```
`-Server` — спросить именно этот сервер, минуя настройки клиента. `-DnsOnly` — только DNS, без NetBIOS-фолбэков, чтобы результат был честным. Если прямой запрос к UBU01 и запрос через DC01 дают **разные** адреса — проблема в форвардере или кэше DC01, а не в BIND.

**6. Кэш клиента.**
```cmd
ipconfig /displaydns
ipconfig /flushdns
```
В выводе `/displaydns` смотрите `Record Name`, `Record Type`, `Time To Live` — TTL уменьшается с каждой секундой и по нулю запись исчезает. Этим же лечится 90% «а у меня старый адрес».

**7. Проверка здоровья DNS домена.**
```cmd
dcdiag /test:dns /v
```
Прогоняет набор подтестов (регистрация записей, разрешение внешних имён, форвардеры, делегирование) и печатает отчёт по каждому DC. Красный `FAIL` в разделе `DNS Tests` — почти всегда причина «домен не находится».

**8. Статистика сервера.**
```powershell
Get-DnsServerStatistics -ComputerName DC01 | Format-List
```
Счётчики запросов, ответов, попаданий в кэш, отказов. Смотрите соотношение «recursive queries» и «cache hits»: много рекурсии при малом кэше — признак того, что TTL занижен или форвардер медленный. Точные имена свойств зависят от версии [ПРОВЕРИТЬ].

**9. Полный дамп зоны (для диффа и бэкапа).**
```cmd
dnscmd /zoneprint corp.vektor.lab
```
Печатает зону в текстовом виде — удобно сохранить в файл и сравнить «до/после».

GUI: `dnsmgmt.msc` → Forward Lookup Zones → правый клик по серверу → Properties → Forwarders; для условного — правый клик на `Conditional Forwarders`.

### BIND на UBU01

**10. Проверка конфигурации до рестарта.**
```bash
sudo named-checkconf -z
sudo named-checkzone vektor.lab /etc/bind/zones/db.vektor.lab.internal
```
`-z` дополнительно пытается загрузить все зоны — ловит ошибки и в `named.conf`, и в файлах зон. `named-checkzone` проверяет синтаксис конкретного файла и соответствие SOA/NS правилам.

**11. Управление сервисом через rndc.**
```bash
sudo rndc status
sudo rndc reload
sudo rndc querylog on
sudo rndc dumpdb -cache
sudo rndc reload vektor.lab
```
`rndc` — канал управления BIND. `reload` перечитывает конфиг без обрыва соединений (в отличие от `systemctl restart`). `querylog on` включает запись запросов в лог (по умолчанию syslog → `journalctl -u named -f`). `dumpdb -cache` выгружает кэш в `/var/cache/bind/named_dump.db` — по нему видно, что сервер реально закэшировал и с каким TTL.

**12. Запросы через dig.**
```bash
dig @10.10.10.30 www.vektor.lab A +short
dig @10.10.10.30 www.vektor.lab +noall +answer
dig @10.10.10.30 www.vektor.lab +norecurse
dig -x 10.10.20.10
```
`@сервер` — к кому шлём. `+short` — только значение. `+noall +answer` — только блок ответа (видно TTL в первом столбце). `+norecurse` — запретить рекурсию: сразу видно, авторитативен ли сервер для этого имени.

**13. Проверка views с нужного адреса источника.**
```bash
dig -b 10.10.20.1 @10.10.10.30 www.vektor.lab +short
dig @10.10.10.30 CH TXT version.bind
```
`-b` подставляет исходный адрес — единственный способ на одном и том же хосте проверить разные view. Вторая команда показывает версию BIND: на боевом сервере её прячут (`version "not disclosed";`), чтобы не облегчать подбор эксплойта.

**14. Перехват трафика на порту 53.**
```bash
sudo tcpdump -ni any port 53 -c 20
```
Показывает, кто и куда реально шлёт запросы. Если клиент вообще не обращается к DC01 — проблема на клиенте (опция DHCP, файрвол), а не в DNS.

Если GW01 нет — он нужен только для проверки внешнего view; тогда проверяйте внешний view через `dig -b 10.10.10.30` (источник будет 10.10.10.30 — тоже попадёт под `any`).

### Снапшот
В VMware Workstation для каждой затрагиваемой ВМ: правый клик на ВМ → Snapshot → Take Snapshot, имя `before-l2-034`. ВМ: **DC01, DC02, UBU01, WIN11-CL01, GW01**.

### Шаги

1. **UBU01.** Ставим BIND и утилиты: `sudo apt update && sudo apt install -y bind9 bind9-utils bind9-dnsutils`. Проверяем: `named -v`. Ожидаемо — строка версии BIND 9.x.
2. **UBU01.** Создаём каталог зон и первую зону:
   ```bash
   sudo mkdir -p /etc/bind/zones
   sudo nano /etc/bind/zones/db.vektor.lab.internal
   ```
   ```text
   $TTL 300
   $ORIGIN vektor.lab.
   @       IN SOA ns1.vektor.lab. admin.vektor.lab. (
                   2026023401 ; serial
                   3600       ; refresh
                   900        ; retry
                   604800     ; expire
                   300 )      ; negative TTL
           IN NS  ns1.vektor.lab.
   ns1     IN A   10.10.10.30
   www     IN A   10.10.20.10
   intranet IN A  10.10.10.20
   ```
3. **UBU01.** Копируем во второй файл и меняем данные под внешний view: `www IN A 203.0.113.10`, `ns1 IN A 203.0.113.53`, строку `intranet` **удаляем**. Serial оставляем тот же.
4. **UBU01.** Правим `/etc/bind/named.conf`: сверху оставляем `include "/etc/bind/named.conf.options";`, а `named.conf.local` и `named.conf.default-zones` **комментируем** — при использовании views все зоны обязаны лежать внутри view. Добавляем:
   ```text
   acl "internal-net" { 127.0.0.1; 10.10.10.0/24; };

   view "internal" {
       match-clients { internal-net; };
       recursion yes;
       allow-query { any; };
       allow-transfer { none; };
       include "/etc/bind/named.conf.default-zones";
       zone "vektor.lab" { type master; file "/etc/bind/zones/db.vektor.lab.internal"; };
   };

   view "external" {
       match-clients { any; };
       recursion no;
       allow-query { any; };
       allow-transfer { none; };
       include "/etc/bind/named.conf.default-zones";
       zone "vektor.lab" { type master; file "/etc/bind/zones/db.vektor.lab.external"; };
   };
   ```
   `view "external"` обязан идти **последним**: views проверяются сверху вниз, срабатывает первое совпадение `match-clients`.
5. **UBU01.** `sudo named-checkconf -z` — ожидаемо тишина (ошибок нет). Затем `sudo named-checkzone vektor.lab /etc/bind/zones/db.vektor.lab.internal` — ожидаемо `zone vektor.lab/IN: loaded serial 2026023401`.
6. **UBU01.** `sudo systemctl restart named && sudo systemctl enable named`. Проверяем, что слушает: `ss -lunp | grep :53` — должен быть `named` на 10.10.10.30:53. Если порт занят systemd-resolved — отключаем stub-листенер [ПРОВЕРИТЬ конфигурацию в вашей сборке].
7. **UBU01.** Локальная проверка: `dig @127.0.0.1 www.vektor.lab +short` → `10.10.20.10`. `dig @127.0.0.1 intranet.vektor.lab +short` → `10.10.10.20`.
8. **GW01.** Проверяем внешний view: `dig -b 10.10.20.1 @10.10.10.30 www.vektor.lab +short` → `203.0.113.10`, а `dig -b 10.10.20.1 @10.10.10.30 intranet.vektor.lab` → пусто/NXDOMAIN. Split-DNS работает.
9. **DC01.** Создаём условный форвардер: `Add-DnsServerConditionalForwarderZone -Name "vektor.lab" -MasterServers 10.10.10.30`. Проверяем `Get-DnsServerZone | Where-Object ZoneType -eq 'Forwarder'`.
10. **DC01.** `Resolve-DnsName www.vektor.lab -Server 10.10.10.10 -Type A -DnsOnly` → `10.10.20.10`. Теперь DC01 знает про зону `vektor.lab`.
11. **WIN11-CL01.** `ipconfig /flushdns`, затем `nslookup www.vektor.lab` → `10.10.20.10`. Запомните TTL.
12. **WIN11-CL01.** `ipconfig /displaydns | findstr /i vektor` — видим запись и уменьшающийся `Time To Live`. Через 5 минут повторите — TTL обнулился, запись ушла.
13. **Кэш на BIND.** На UBU01: `sudo rndc dumpdb -cache`, затем `sudo grep -i vektor /var/cache/bind/named_dump.db`. Увидите закэшированные записи с остатком TTL.
14. **DC02.** Проверяем репликацию условного форвардера: `Get-DnsServerZone -ComputerName DC02 | Where-Object ZoneType -eq 'Forwarder'`. Запись должна быть видна — значит, она легла в AD-раздел.
15. **stand-log.md.** Записываем изменения (см. ниже).

### Сломай и почини

> **Пользователь:** ivanov (Иван Иванов, бухгалтерия)
> **ВМ:** WIN11-CL01
> **Что написал:** «Внутренний портал `www.vektor.lab` не открывается — браузер висит и выдаёт ошибку. Интернет работает. У Петровой то же самое.»
> **Срочность:** высокая

**Как воспроизвести.** На UBU01 поменяйте views местами: блок `view "external"` перенесите **выше** `view "internal"`. `sudo named-checkconf -z && sudo rndc reload`. Теперь первым совпадением для любого клиента становится внешний view.

**Диагностика по шагам.**
1. На WIN11-CL01: `ipconfig /flushdns`, затем `nslookup www.vektor.lab`. Ответ `203.0.113.10` — адрес из документационного диапазона, заведомо недостижимый. Значит, имя резолвится, но неправильно → проблема не на клиенте.
2. `dig @10.10.10.10 www.vektor.lab +short` — тот же `203.0.113.10`. DC01 отдаёт то же, что и клиент, значит DC01 не виноват: он всего лишь форвардит.
3. `dig @10.10.10.30 www.vektor.lab +short` с UBU01 — снова `203.0.113.10`. Источник проблемы локализован: BIND.
4. `dig -b 10.10.10.30 @10.10.10.30 www.vektor.lab +short` — тоже внешний ответ. Внутренний источник получает внешние данные → сломано сопоставление views.
5. `sudo named-checkconf -z` — синтаксис в порядке (это важно: checkconf такое не ловит). Смотрим сам файл: `sudo grep -n 'view' /etc/bind/named.conf` — видим, что `external` идёт первым.
6. Проверяем, что дело не в кэше: `sudo rndc flush` и повторный `dig` — ответ тот же. Кэш не при чём.

**Решение.** Вернуть `view "internal"` наверх, `view "external"` — вниз (с `match-clients { any; }` он обязан быть последним). `sudo named-checkconf -z && sudo rndc reload`. Проверить с двух адресов: внутренний → `10.10.20.10`, внешний → `203.0.113.10`. На DC01 и на клиенте сбросить кэш: `Clear-DnsServerCache -Force`, `ipconfig /flushdns`.

## 6. Ошибки новичков и безопасность

1. **Указать на DC внешний DNS (8.8.8.8) в качестве основного** → AD ломается: SRV-записи не находятся, вход в домен виснет на «Применение параметров». Правильно: DC смотрит только на себя (127.0.0.1 или свой IP), внешний мир — через форвардеры.
2. **Путать форвардер и условный форвардер** → весь трафик уходит не туда, внутренние имена перестают резолвиться. Правильно: условный — только для конкретной зоны, обычный — для «всего остального».
3. **Ставить `view "external"` с `match-clients { any; }` выше внутреннего** → внутренние клиенты получают внешние адреса. Правильно: `any` — всегда последним.
4. **Забыть увеличить serial в SOA** → вторичные серверы и кэши не узнают об изменениях. Правильно: serial += 1 при каждом изменении, затем `rndc reload`.
5. **Открытый рекурсивный резолвер** (`recursion yes` + `allow-query { any; }` наружу) → сервер становится участником DNS-amplification атак. Правильно: `allow-recursion` только для внутренних подсетей, `allow-transfer { none; }`.
6. **Менять A-запись и ждать мгновенного эффекта** → у всех старый адрес в кэше до истечения TTL. Правильно: заранее снизить TTL за сутки до изменения, потом вернуть.
7. **Не настроить очистку (scavenging) в Windows DNS** → зона зарастает устаревшими записями от старых DHCP-адресов, появляются «фантомные» имена. Правильно: включить aging/scavenging с интервалами, превышающими TTL DHCP-аренды.
8. **Проверять DNS только через `nslookup` на клиенте** → видите кэш клиента и не видите, что происходит на сервере. Правильно: `Resolve-DnsName -Server` по цепочке, от клиента к источнику.

### Безопасность
В боевой среде нельзя: держать рекурсию открытой в интернет; разрешать зонные трансферы всем (`allow-transfer`); светить версию BIND (`version.bind`); логировать полные запросы без ротации и без учёта персональных данных (по DNS-запросам видно, какие сайты посещает сотрудник); использовать публичные резолверы для внутренних имён. В нашей лабе мы намеренно используем простой учебный пароль и не настраиваем DNSSEC — в реальности для домена с AD как минимум включают DNSSEC для внешних зон и DoT/DoH для клиентов, уходящих наружу. Отдельно по РФ: часть зарубежных DoH-резолверов может быть недоступна или ограничена, доверенный резолвер обычно даёт провайдер или корпоративный сервер [ПРОВЕРИТЬ актуальный статус].

## 7. Вопросы на собеседовании

**1. Чем форвардер отличается от условного форвардера и когда вы выберете второй?**
Ответ: обычный форвардер — адрес, куда уходит всё, что сервер не может разрешить сам; условный — привязка конкретной зоны к конкретным серверам. Второй выбирают, когда есть партнёрский/дочерний домен, отдельный сегмент (DMZ) или split-DNS, и когда нельзя пускать эти запросы в общий интернет. Плюс условный форвардер экономит время: не надо строить цепочку от корня.
*Что хочет услышать:* понимание, что DNS выбирает самое длинное совпадение суффикса, и что условный форвардер можно хранить в AD.
*Красный флаг:* «это одно и то же, просто в разных меню».

**2. Что такое split-DNS и как его сделать в BIND и в Windows DNS?**
Ответ: один домен отдаёт разные ответы в зависимости от источника запроса. В BIND — `view` с `match-clients`, порядок views критичен, все зоны должны быть внутри view. В Windows Server 2016+ — зонные области (zone scopes) и DNS-политики; альтернатива — отдельная внутренняя зона `corp.example.lab` и внешняя `example.lab`. Зачем: не публиковать внутренние адреса наружу и не гонять внутренних пользователей через внешний IP (hairpin NAT).
*Что хочет услышать:* что views проверяются по порядку и «any» идёт последним.
*Красный флаг:* «делается через файл hosts».

**3. Пользователь говорит, что сайт не открывается. Как за 5 минут понять, DNS это или нет?**
Ответ: `ping`/`Test-NetConnection` по IP — если по IP работает, а по имени нет, это DNS. Дальше `ipconfig /displaydns` (кэш клиента), `nslookup имя` (какой сервер ответил), `Resolve-DnsName -Server <dc>` (проверка сервера), `dig @<source-server>` (проверка зоны), `tcpdump port 53` (дошёл ли запрос вообще). Смотрим, где ответ расходится с ожидаемым.
*Что хочет услышать:* движение по цепочке клиент → сервер → зона → источник, а не «перезагрузил и заработало».
*Красный флаг:* сразу `ipconfig /flushdns` без диагностики.

**4. Поменяли IP сервера, а часть пользователей ходит на старый. Почему и что делать?**
Ответ: старый адрес лежит в кэше — на клиенте, на DC01, на форвардерах — и живёт до истечения TTL. Плюс отрицательный кэш по SOA Minimum. Решение: заранее снизить TTL, после изменения сбросить кэши (`Clear-DnsServerCache -Force`, `ipconfig /flushdns`, `rndc flush`), проверить `dig +noall +answer` — TTL должен тикать. `nslookup` при этом кэш не сбрасывает.
*Что хочет услышать:* понимание TTL и того, что кэшей несколько.
*Красный флаг:* «DNS сам обновится, подождите».

**5. Как защитить DNS-сервер в корпоративной сети?**
Ответ: ограничить рекурсию (`allow-recursion`, `allow-query` только для своих), запретить зонные трансферы (`allow-transfer { none; }`), скрыть версию, включить DNSSEC для внешних зон, использовать DoT/DoH для трафика наружу, логировать запросы с ротацией и контролем доступа, мониторить аномалии (всплеск запросов = amplification/tunneling), для Windows — ограничить динамические обновления режимом «только защищённые».
*Что хочет услышать:* «открытая рекурсия — это DDoS-усилитель».
*Красный флаг:* «поставить файрвол и всё».
