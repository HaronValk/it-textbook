## 2. Теория «под капотом»

### Лес, дерево, домен

**Лес (forest)** — верхний уровень: набор доменов с общей схемой и общим глобальным каталогом. Лес — это **граница безопасности** в AD. Официальная позиция Microsoft: домен **не** является границей безопасности (администратор домена может при желании добраться до других доменов леса), лес — является.

**Домен** — контейнер административной автономии: своя база пользователей, своя политика паролей, свои контроллеры. Домен — это в первую очередь **граница репликации и групповой политики**.

**Дерево** — домены с общим пространством имён (`corp.vektor.lab` → `moscow.corp.vektor.lab`). **Доверие (trust)** — связь между доменами, по которой один домен доверяет аутентификацию другому.

У нас в стенде один лес = один домен: `corp.vektor.lab`, NetBIOS `VEKTOR`.

### Разделы каталога (naming contexts / partitions)

База AD — это не одна таблица. Это несколько разделов, каждый реплицируется по своим правилам:

| Раздел | Что внутри | Область репликации |
|---|---|---|
| Domain (`DC=corp,DC=vektor,DC=lab`) | пользователи, группы, OU, компьютеры | все DC этого домена |
| Configuration (`CN=Configuration,DC=corp,...`) | сайты, site links, службы, настройки репликации | все DC **леса** |
| Schema (`CN=Schema,...`) | определения классов и атрибутов | все DC **леса** |
| DomainDNSZones / ForestDNSZones | зоны DNS, интегрированные в AD | по уровню зоны |
| Application partitions | данные отдельных приложений | по списку реплик |

### Сайты и подсети

**Сайт (site)** — это физическая топология: совокупность хорошо связанных подсетей (обычно один офис или ЦОД). **Подсеть** — объект `10.10.10.0/24`, привязанный к сайту. Клиент при старте определяет свой IP, находит свою подсеть в AD, узнаёт свой сайт и просит DNS «дай мне DC из моего сайта».

Сайты нужны, чтобы: (1) клиент шёл к ближайшему DC; (2) репликация между площадками была сжатой и по расписанию, а не «на каждое изменение».

- Внутри сайта: репликация почти мгновенная (change notification, интервал порядка секунд), трафик не сжимается.
- Между сайтами: по расписанию из **site link**, по умолчанию раз в 180 минут, трафик сжимается, используется один сервер-мост (**bridgehead**), которого выбирает ISTG (Inter-Site Topology Generator).

Топологию внутри сайта строит **KCC** (Knowledge Consistency Checker) — служба, которая сама рисует «кольцо» партнёров репликации, чтобы изменений было не больше 3–4 прыжков.

### Как распространяются изменения

Репликация AD — **мультимастер**: писать может любой DC. Механика:

1. Каждый DC ведёт счётчик **USN** (Update Sequence Number) — «номер версии» каждого объекта в его базе.
2. Партнёр говорит: «дай мне всё, что у тебя новее USN 12345» (**high-watermark**).
3. Дополнительно передаётся **up-to-dateness vector** — какие USN других DC уже видел источник, чтобы не гонять одно и то же по кругу.
4. Конфликт (двое правили один атрибут) решается по: версии атрибута → времени изменения → GUID источника. Побеждает не «кто позже нажал», а кто по этим правилам выше.
5. Удаление — «надгробная плита» (**tombstone**), живёт `tombstoneLifetime`, по умолчанию 180 дней. Дольше — DC считается «залежавшимся» и требует принудительной репликации или восстановления. (Подробно — в уроке 26 про AD Recycle Bin и восстановление.)

### FSMO-роли

Пять операций нельзя делать мультимастерно — их закрепляют за одним DC. Это **FSMO** (Flexible Single Master Operations):

| Роль | Область | За что отвечает | Если недоступна |
|---|---|---|---|
| Schema Master | лес | изменения схемы | нельзя расширить схему (например, при установке Exchange/1С-интеграций) |
| Domain Naming Master | лес | добавление/удаление доменов и разделов | нельзя создать/удалить домен |
| PDC Emulator | домен | приоритет смены паролей, блокировки аккаунтов, источник времени домена | «старый пароль ещё работает», рассинхрон времени → Kerberos |
| RID Master | домен | выдаёт DC пулы RID (блоками по 500) | кончается пул → нельзя создать объекты |
| Infrastructure Master | домен | обновление ссылок на объекты других доменов | «фантомные» несуществующие ссылки в мультидоменном лесу |

Важно: **Infrastructure Master не нужен**, если все DC в домене — глобальные каталоги, и при включённом AD Recycle Bin. В однодоменном лесу это почти всегда так.

Перенос и захват ролей — урок 27.

### Глобальный каталог (GC)

**Глобальный каталог** — это DC, который, помимо своей полной доменной базы, хранит **частичный набор атрибутов** (partial attribute set) всех остальных доменов леса. Это «телефонная книга» леса: быстро найти объект в любом домене и узнать его членство в универсальных группах.

Зачем нужен в одно-доменном лесу: (1) вход в систему — DC проверяет универсальные группы; (2) поиск по всему лесу в Outlook/ADUC; (3) разгрузка запросов. Слушает **порты 3268 (LDAP) и 3269 (LDAPS)** в дополнение к 389/636.

Схема стенда:

```text
ЛЕС corp.vektor.lab  (граница безопасности)
│
├── Домен corp.vektor.lab  (граница репликации и GPO)
│   ├── раздел Domain:   OU Company/Бухгалтерия, HR, Склад, IT
│   ├── DC01  10.10.10.10  ← все 5 FSMO + GC + DNS + DHCP
│   └── DC02  10.10.10.11  ← появится в уроке 17
│
├── раздел Configuration (сайты, site links) — реплицируется на ВСЕ DC леса
├── раздел Schema — реплицируется на ВСЕ DC леса
│
└── САЙТ Default-First-Site-Name
      └── подсеть 10.10.10.0/24  →  клиенты WIN11-CL01, WIN10-CL02, UBU01
      └── site link DEFAULTIPSITELINK (интервал 180 мин, сжатие)

Порты DC: 53 DNS | 88 Kerberos | 123 NTP | 135 RPC | 389 LDAP | 445 SMB
           464 kpasswd | 636 LDAPS | 3268 GC | 3269 GC/SSL | 49152+ динамический RPC
```

### Уровни функционирования

**DFL/FFL** (domain/forest functional level) — режим совместимости, который включает те или иные возможности. На стенде (Windows Server 2022) выставляется Windows Server 2016 — это максимальный уровень и для более новых версий `[ПРОВЕРИТЬ для Windows Server 2025]`. Повышение — урок 27.

## 3. Аналогия из жизни

Представь крупную городскую библиотеку с филиалами.

**Лес** — вся библиотечная система города: единые правила каталогизации (схема), единый сводный каталог (глобальный каталог). **Домен** — отдельный филиал со своим фондом и своим заведующим; филиалы договариваются обслуживать читателей друг друга (**доверие**). **Сайт** — здание филиала: читателю из этого района логично идти в ближайшее здание, а не через весь город. **Site link** — расписание курьерской машины между зданиями: возит пачками, по графику, а внутри здания книгу просто передают из рук в руки за минуту. **KCC** — завхоз, который составляет маршруты курьеров так, чтобы книга не объехала весь город. **FSMO-роли** — пять главных должностей, которые нельзя раздвоить: главный каталогизатор (Schema Master), директор по открытию новых филиалов (Domain Naming Master), кассир, через которого проводят все изменения читательских билетов (PDC Emulator), кладовщик, выдающий бланки с номерами (RID Master), и сверщик межфилиальных заявок (Infrastructure Master). **Глобальный каталог** — сводный каталог, где по каждому филиалу есть краткая карточка: книги ищутся по всему городу быстро, но полного текста в карточке нет.

Аналогия перестаёт работать там, где речь о конфликтах: в библиотеке два завхоза просто поругаются, а в AD конфликт разрешается строго автоматически — по версии атрибута, времени и GUID.

## 4. Практика и команды

Все команды PowerShell — на DC01, из-под `VEKTOR\adm.student`. Нужен модуль **ActiveDirectory** (ставится с RSAT, у нас уже есть с урока 8). Запускай PowerShell от администратора и не забудь `Import-Module ActiveDirectory`, если модуль не подхватился.

**1. Инвентаризация леса и домена**

```powershell
Get-ADForest | Format-List Name,ForestMode,RootDomain,Domains,GlobalCatalogs,Sites,SchemaMaster,DomainNamingMaster
Get-ADDomain | Format-List DNSRoot,NetBIOSName,DomainMode,PDCEmulator,RIDMaster,InfrastructureMaster,DistinguishedName
```

`Get-ADForest` отдаёт параметры всего леса, `Get-ADDomain` — текущего домена. Смотри `ForestMode`/`DomainMode` (у нас `Windows2016Forest` и `Windows2016Domain`) и список `GlobalCatalogs`.

**2. Все пять FSMO одной командой (классика, работает и в CMD)**

```cmd
netdom query fsmo
```

```text
Schema master               DC01.corp.vektor.lab
Domain naming master        DC01.corp.vektor.lab
PDC                         DC01.corp.vektor.lab
RID pool manager            DC01.corp.vektor.lab
Infrastructure master       DC01.corp.vektor.lab
The command completed successfully.
```

На собеседовании это спрашивают чаще, чем что угодно другое из AD. Запомни порядок вывода.

**3. Инвентарь контроллеров и кто из них GC**

```powershell
Get-ADDomainController -Filter * |
  Select-Object Name,Site,IPv4Address,IsGlobalCatalog,OperationMasterRoles,Enabled |
  Format-Table -AutoSize
```

Колонка `IsGlobalCatalog` — то, что нужно в 90% заявок «не пускает в домен». `OperationMasterRoles` покажет, какие FSMO на каком DC.

**4. Корень каталога: какие разделы вообще есть**

```powershell
Get-ADRootDSE | Format-List namingContexts,defaultNamingContext,schemaNamingContext,configurationNamingContext,isGlobalCatalogReady
```

`namingContexts` — список разделов на этом DC. `isGlobalCatalogReady: True` — DC реально отдаёт GC-запросы (не то же самое, что галочка в свойствах: галочка может быть, а готовность ещё не наступила после перезапуска).

**5. Сайты, подсети, site links**

```powershell
Get-ADReplicationSite -Filter *
Get-ADReplicationSubnet -Filter *
Get-ADReplicationSiteLink -Filter * | Select-Object Name,Cost,ReplicationFrequencyInMinutes,SitesIncluded
```

На свежем стенде: один сайт `Default-First-Site-Name`, подсетей **ноль** (это нормально, пока никто не создал — и это одна из причин «клиент ходит не туда» в будущем), один линк `DEFAULTIPSITELINK` с частотой 180 минут.

**6. Состояние репликации: с кем и как**

```cmd
repadmin /showrepl
repadmin /replsummary
```

```text
DC01\CORP
DSA Options: IS_GC
Site Options: (none)
DSA object GUID: 8f4c...-...
DSA invocationID: 2b71...-...
```

При одном DC входящих партнёров не будет — это **не поломка**. Запомни формат: в уроке 17 здесь появятся строки `Source: CORP\DC02` с `Last success` и `Number of failures`. `IS_GC` в `DSA Options` — признак глобального каталога.

**7. Быстрый смоук-тест домена**

```cmd
dcdiag /test:advertising /test:netlogons /v
```

`Advertising` проверяет, что DC объявил себя в DNS как DC/GC/Kerberos; `NetLogons` — что он обслуживает вход. Экономь время: гонять полный `dcdiag /v` в проде посреди дня не стоит, это нагрузка и шум.

**8. Как клиент находит DC и GC**

```cmd
nltest /dsgetdc:corp.vektor.lab /gc /force
```

```text
           DC: \\DC01
      Address: \\10.10.10.10
     Dom Name: corp.vektor.lab
 Dc Site Name: Default-First-Site-Name
Our Site Name: Default-First-Site-Name
        Flags: GC DS LDAP KDC TIMESERV WRITABLE DNS_DC DNS_DOMAIN DNS_FOREST
The command completed successfully.
```

С `Flags: GC` — DC годится как глобальный каталог. Если GC в лесу нет, команда вернёт ошибку `1355 ERROR_NO_SUCH_DOMAIN`. Это и есть проверка «а GC вообще жив?».

**9. Порты: слушает ли DC то, что должен**

```powershell
Test-NetConnection -ComputerName DC01 -Port 3268
Get-NetTCPConnection -LocalPort 3268,389,88,53 -State Listen | Select-Object LocalAddress,LocalPort,OwningProcess
```

Первый — с клиента (WIN11-CL01). Второй — на DC01. `3268` не в LISTEN → GC-запросы не работают, даже если вход в систему ещё проходит.

**10. Проверка GC с Linux (UBU01)**

```bash
sudo apt install -y ldap-utils
ldapsearch -x -H ldap://10.10.10.10:3268 -b "" -s base "(objectClass=*)" namingContexts isGlobalCatalogReady
```

```text
dn:
namingContexts: DC=corp,DC=vektor,DC=lab
namingContexts: CN=Configuration,DC=corp,DC=vektor,DC=lab
namingContexts: CN=Schema,CN=Configuration,DC=corp,DC=vektor,DC=lab
namingContexts: DC=DomainDnsZones,DC=corp,DC=vektor,DC=lab
namingContexts: DC=ForestDnsZones,DC=corp,DC=vektor,DC=lab
isGlobalCatalogReady: TRUE
```

Удобно, когда DC «на слуху», а Windows-оснасток под рукой нет. `-s base` = читаем только корень (rootDSE), без выгрузки базы.

**11. Время: без него не работает Kerberos**

```powershell
w32tm /query /status
w32tm /query /source
```

`Source: Local CMOS Clock` на DC — нормально для изолированного стенда. `Source: DC01.corp.vektor.lab` на клиенте — тоже. А вот расхождение часов больше 5 минут ломает аутентификацию («часы на клиенте и сервере расходятся» — самая недооценённая причина «неверного пароля»). В домене источник времени — PDC Emulator.

**12. Глубина: срок жизни tombstone и уровень леса**

```powershell
$cfg = "CN=Directory Service,CN=Windows NT,CN=Services," + (Get-ADRootDSE).configurationNamingContext
Get-ADObject $cfg -Properties tombstoneLifetime | Select-Object tombstoneLifetime
Get-ADObject (Get-ADRootDSE).defaultNamingContext -Properties msDS-Behavior-Version | Select-Object msDS-Behavior-Version
```

`tombstoneLifetime` может быть не задан — тогда действует 180 дней по умолчанию. `msDS-Behavior-Version` = 7 означает Windows Server 2016 `[ПРОВЕРИТЬ соответствие чисел и версий]`.

GUI-пути, которые надо знать наизусть: `dsa.msc` → правый клик по домену → **Operations Masters** (RID/PDC/Infrastructure); `domain.msc` → правый клик → **Operations Master** (Domain Naming); оснастка Schema — `regsvr32 schmmgmt.dll`, затем `mmc` → Add/Remove Snap-in → **Active Directory Schema** → правый клик → **Operations Master** (Schema Master).

## 6. Ошибки новичков и безопасность

1. **«Раз в лесу один домен, значит иерархия не нужна»** → не создают сайты и подсети, клиенты из филиала ходят через WAN к чужому DC, вход медленный → создавай сайт и подсеть на каждую площадку, даже маленькую.
2. **Путают домен и лес** → обещают «изоляцию» между доменами, которой нет → помни: граница безопасности — лес, домен — граница репликации и политик.
3. **Держат все FSMO на одном DC и не проверяют это** → падение сервера останавливает смену паролей и создание объектов → знай, где роли (`netdom query fsmo`), и планируй их размещение; на стенде все на DC01 — это осознанное упрощение.
4. **Снимают Global Catalog «для оптимизации»** → ломается вход и поиск по лесу → GC снимают только когда в лесу есть другой GC и понятно, кто обслуживает сайт.
5. **Читают `repadmin /showrepl` как «ошибка: партнёров нет»** → ложная тревога и лишние перезагрузки → при одном DC пустой список партнёров — норма; смотри `DSA Options` и наличие строк `error`.
6. **Проверяют репликацию только глазами в AD Sites and Services** → не видят реальных задержек и ошибок → используй `repadmin /replsummary` и `dcdiag`, они дают цифры.
7. **Игнорируют время** → «неверный пароль» и отказ Kerberos при расхождении часов больше 5 минут → проверяй `w32tm /query /source` до того, как сбрасывать пароли.
8. **Меняют архитектуру днём, без окна** → снятие GC/остановка NTDS в рабочие часы валит всех → любые изменения разделов, ролей и GC — в согласованное окно, со снапшотом/бэкапом.

### Безопасность

- На стенде пароль `Lab#2026-vektor` одинаковый везде — в реальной среде так нельзя: компрометация одного хоста = компрометация домена.
- Не давай `adm.student` (Domain Admin) повседневную работу: вход с DA на клиентскую ВМ — классический путь для кражи хешей и тикетов (тема урока 25).
- Лес — граница безопасности: администратор леса может всё. Если бизнесу нужна настоящая изоляция — это отдельный лес, а не «отдельный OU с ограничениями».
- `nltest`, `ldapsearch` и `repadmin` — легальные инструменты диагностики, но анонимный LDAP-запрос (`-x` без bind) в боевой среде должен быть запрещён политикой: он отдаёт структуру каталога без пароля.
- Evaluation-лицензии Windows Server — 180 дней, для стенда нормально; продлевать «активаторами» нельзя, легально — переустановка Evaluation или учебная подписка (Azure for Students / Visual Studio Subscriptions).

## 7. Вопросы на собеседовании

**Вопрос 1. Какие FSMO-роли вы знаете, какие из них лесные, а какие доменные? Что будет, если упадёт сервер с ролью RID Master?**

**Ответ.** Пять ролей. Лесные: Schema Master (изменения схемы) и Domain Naming Master (добавление/удаление доменов и разделов). Доменные: PDC Emulator (приоритет смены паролей, блокировки, источник времени домена), RID Master (выдаёт DC пулы RID блоками по 500), Infrastructure Master (обновление ссылок на объекты других доменов). Если недоступен RID Master, домен продолжает жить: у каждого DC есть запасной пул, обычно 500 RID, — их хватает на создание новых объектов. Проблема наступит, когда пул исчерпан: создание пользователей, групп, компьютеров начнёт падать с ошибкой. Тогда либо поднимают RID Master, либо (если он потерян навсегда) захватывают роль через `ntdsutil`, а после — перезапускают NTDS на DC, у которых кончился пул. Проверка — `netdom query fsmo`.

**Что хочет услышать интервьюер:** чёткое деление «2 лесные + 3 доменные», понимание, что падение FSMO — не мгновенная смерть, а отложенная деградация, и знание команды проверки.

**Красный флаг:** «FSMO — это пять контроллеров» или «если упал RID Master, домен сразу ложится».

**Вопрос 2. Почему Microsoft говорит, что домен — не граница безопасности, а лес — граница? Что из этого следует на практике?**

**Ответ.** Администратор домена (Domain Admin) в много-доменном лесу технически может повысить права до администратора леса: через изменения в Configuration/Schema, через группу Enterprise Admins при определённых условиях, через владение объектами. Поэтому «изолировать подразделение отдельным доменом» — не решение задачи изоляции: сетевые и сервисные связи леса всё равно дают путь наверх. Настоящая изоляция — отдельный лес с отдельными доверенностями (или без них). Практический вывод: домены создают ради разных политик паролей (хотя с FGPP это уже не аргумент — урок 23), делегирования администрирования и раздельной репликации, а не ради безопасности. Для реальной сегрегации — отдельный лес, ESAE/Red Forest-подход или хотя бы модель тиринга.

**Что хочет услышать интервьюер:** понимание официальной позиции Microsoft и того, что «отдельный домен ≠ безопасно».

**Красный флаг:** «Домен — это безопасный периметр, мы так и изолируем филиалы».

**Вопрос 3. Как работает репликация между контроллерами домена? Что такое USN и как разрешается конфликт изменений?**

**Ответ.** Репликация мультимастерная, по разделам: доменный раздел реплицируется на все DC домена, Configuration и Schema — на все DC леса. Каждый DC ведёт USN — счётчик, который увеличивается на каждое изменение в его базе. Партнёр запрашивает «всё, что новее моего high-watermark», плюс передаёт up-to-dateness vector, чтобы не гонять изменения по кругу. Топологию внутри сайта строит KCC (кольцо, не больше 3–4 прыжков), между сайтами — ISTG выбирает bridgehead, репликация по расписанию site link, сжатая, по умолчанию раз в 180 минут; внутри сайта — почти сразу, без сжатия. Конфликт (один атрибут поправлен на двух DC) решается по version атрибута, затем по timestamp, затем по GUID источника. Удаление — tombstone, живёт 180 дней по умолчанию. Диагностика — `repadmin /showrepl`, `repadmin /replsummary`, `dcdiag`.

**Что хочет услышать интервьюер:** USN, high-watermark, KCC/ISTG, разделение intra/inter-site и порядок разрешения конфликтов. Упоминание `repadmin` — обязательно.

**Красный флаг:** «Репликация идёт по FTP/по расписанию раз в час везде» или «конфликты решает админ вручную».

**Вопрос 4. Зачем нужен глобальный каталог и что произойдёт, если в лесу не останется ни одного GC?**

**Ответ.** GC хранит полную копию своего домена и частичный набор атрибутов всех остальных доменов леса, слушает порты 3268/3269, используется для поиска по лесу и для проверки членства в универсальных группах при входе. Если GC нет: в много-доменном лесу вход в систему ломается (если не включено кэширование универсальных групп), поиск по лесу не работает, часть приложений (адресные книги, каталоги) отказывает. Диагностика: `Get-ADDomainController -Filter * | select IsGlobalCatalog`, `Get-ADRootDSE | select isGlobalCatalogReady`, `nltest /dsgetdc:<домен> /gc`, проверка порта 3268. Быстрое решение — включить GC на другом DC (галочка в NTDS Settings), подождать готовности, проверить порт и вход пользователя. Нюанс: `isGlobalCatalogReady` может быть `False` сразу после запуска — это нормальное состояние догоняющей репликации, а не поломка.

**Что хочет услышать интервьюер:** порт 3268, частичный набор атрибутов, связь с универсальными группами и конкретный порядок проверки/лечения.

**Красный флаг:** «GC — это просто ещё один DC, разницы нет» или «GC нужен только для Exchange».

**Вопрос 5. Чем сайт AD отличается от подсети и как клиент выбирает контроллер домена?**

**Ответ.** Подсеть — объект `10.10.10.0/24`, привязанный к сайту; сайт — совокупность таких подсетей, то есть физическая/сетевая топология. При входе клиент определяет свой IP, находит подсеть в AD, узнаёт свой сайт и через DNS (SRV-записи) просит DC; предпочтение отдаётся DC из своего сайта, при отсутствии — из ближайшего по стоимости site link. Проверить, что выбрал клиент, можно `nltest /dsgetdc:<домен> /force` — там видны `Dc Site Name` и `Our Site Name`; если они разные, значит либо у клиента нет подсети в AD, либо DC своего сайта недоступен. Отсутствие подсетей в AD (как на нашем стенде) — частая причина «почему мой компьютер цепляется к DC из другого города».

**Что хочет услышать интервьюер:** понимание «подсеть → сайт → SRV → выбор DC», знание `nltest /dsgetdc` и того, что сайт влияет и на репликацию, и на выбор DC.

**Красный флаг:** «Сайт — это OU для компьютеров» (грубое смешение логической и физической структуры).
