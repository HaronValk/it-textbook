## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Цифры, которые ты видишь в PerfMon, не «считываются с датчиков на железе». Их считает само ядро Windows и отдаёт через провайдеры счётчиков.

Схема цепочки:

```text
 [процесс]   [служба]   [драйвер]        [ядро Windows]
     \           |          |        планировщик (CPU),
      \          |          |        диспетчер памяти (RAM),
       \         |          |        диспетчер ввода-вывода (I/O),
        \        |          |        кэш-менеджер (файловый кэш)
         \       |          |              |
          v      v          v              v
     провайдеры счётчиков: HKEY_PERFORMANCE_DATA + провайдеры V2
                          |
        +-----------------+------------------+
        |                 |                  |
    Performance        Resource          Get-Counter,
    Monitor (GUI +     Monitor (GUI,     typeperf, logman
    Data Collector     живой срез)       (скрипты, расписания)
    Sets)                  |                  |
        +-----------------+------------------+
                          |
             .blg / .csv / .xml  (журналы) + живой анализ
                          |
        вывод: где узкое место — CPU / RAM / диск / сеть
```

Ключевые моменты, без которых ты будешь врать сам себе:

- **Счётчики бывают мгновенные и вычисляемые.** `\Memory\Available MBytes` — мгновенное значение. `\Processor(_Total)\% Processor Time`, `\LogicalDisk(_Total)\Disk Bytes/sec` — это **скорость**, её нельзя получить из одного замера: нужно два и разница между ними. Поэтому первый семпл после старта сбора почти всегда 0 — это нормально, а не поломка.
- **Интервал замера — часть методики.** Для быстрых процессов 1–2 секунды, для длинного мониторинга сервера — 15–60 секунд (иначе журнал распухнет).
- **Кэш-менеджер забирает свободную RAM под файловый кэш.** Поэтому на нормальном файловом сервере `Available MBytes` маленький — это хорошо, а не «нехватка памяти». Реальная нехватка видна по `Pages/sec` и жёстким страничным ошибкам.
- **Узкое место определяется триадой: загрузка + очередь + задержка.** Загрузка 60% без очереди — не проблема. Загрузка 95% с растущей очередью и задержкой диска 40 мс — проблема, даже если «в среднем за сутки 12%».
- **Локализация.** На русской версии Windows имена счётчиков локализованы (`\Процессор(_Total)\% загруженности процессора`), и скрипт с английскими именами там упадёт. Для переносимых скриптов используй CIM-классы `Win32_PerfFormattedData_*` — имена классов и свойств всегда английские.

Справочник по счётчикам, минимум для работы:

| Ресурс | Счётчик | Тревожно | Что значит |
|---|---|---|---|
| CPU | `\Processor(_Total)\% Processor Time` | устойчиво > 80–85% | суммарная загрузка ядер |
| CPU | `\System\Processor Queue Length` | > 2 на ядро | потоки ждут процессор → реальная нехватка CPU |
| CPU | `\Processor(_Total)\% Privileged Time` | > 30% | время в ядре: драйверы, антивирус, I/O |
| RAM | `\Memory\Available MBytes` | < 100–200 МБ при большой нагрузке | сколько отдать новым процессам |
| RAM | `\Memory\Pages/sec` | устойчиво > 20–25 | жёсткие страничные ошибки, чтение с диска |
| RAM | `\Memory\% Committed Bytes In Use` | > 85–90% | сколько выделенной памяти от лимита |
| Диск | `\LogicalDisk(_Total)\Avg. Disk sec/Read` / `Write` | > 0,025 с (25 мс) | задержка ввода-вывода — главный показатель |
| Диск | `\LogicalDisk(_Total)\Current Disk Queue Length` | > 2 на шпиндель/устройство | сколько запросов стоит в очереди |
| Диск | `\LogicalDisk(_Total)\% Disk Time` | > 80% | загрузка, но может показывать > 100% при очереди |
| Сеть | `\Network Interface(*)\Bytes Total/sec` | близко к скорости линка | фактический трафик |
| Сеть | `\Network Interface(*)\Output Queue Length` | > 2 | пакеты ждут отправки |
| Сеть | `\TCPv4\Segments Retransmitted/sec` | заметно > 0 | потери/дуплекс/проблемы линка |

Ориентиры по задержке диска (общепринятая практика, для HDD и SSD различаются): до 10 мс — отлично, 10–25 мс — терпимо, 25–50 мс — плохо, > 50 мс — пользователи уже чувствуют «зависания» [ПРОВЕРИТЬ под свою СХД].

## 3. Аналогия из жизни

Представь кухню ресторана. **CPU** — это повара: если все заняты, новые заказы ложатся в очередь на выдаче (Processor Queue Length). **RAM** — рабочий стол повара: пока на нём помещаются продукты, повар работает быстро; как только стол забит, он бегает в холодильник (страничный файл) — это и есть `Pages/sec`. **Диск** — кладовая с одной дверью: даже если повара свободны, все блюда упираются в очередь у двери, и важна не «занятость двери», а сколько времени повар стоит и ждёт (задержка I/O). **Сеть** — официанты: их может быть много, но если коридор узкий, тарелки остывают по дороге (retransmit).

Аналогия ломается в одном месте: в Windows часть «продуктов» вообще не ходит в кладовую — их отдаёт файловый кэш из памяти, поэтому диск может быть свободен, а приложение всё равно «тормозит».

## 4. Практика и команды

**1. Запуск инструментов.** `Win+R` → `perfmon` (Performance Monitor) или `resmon` (Resource Monitor). `perfmon /res` открывает PerfMon сразу в режиме Resource Monitor. Путь через GUI: Server Manager → Tools → Performance Monitor / Resource Monitor.

**2. Отчёт «здоровье системы» одной командой.**
```cmd
perfmon /report
```
Собирает данные 60 секунд и открывает отчёт в оснастке (Reports → System → System Diagnostics). Ключи: `/report` — сбор и отчёт, `/res` — Resource View. Смотри разделы «Диагностические результаты», «Предупреждения», «Память», «Диск». Хорошо для быстрого скрининга, плохо для поиска периодической проблемы.

**3. Живой сбор в PowerShell.**
```powershell
Get-Counter -Counter '\Processor(_Total)\% Processor Time','\Memory\Available MBytes','\LogicalDisk(_Total)\Avg. Disk sec/Write' -SampleInterval 2 -MaxSamples 5
```
`-SampleInterval` — секунды между замерами, `-MaxSamples` — сколько снять. Вывод: объекты с `CounterSamples.CookedValue`. Быстрый способ получить среднее и максимум:
```powershell
$s = Get-Counter '\LogicalDisk(_Total)\Avg. Disk sec/Write' -SampleInterval 1 -MaxSamples 30
$s.CounterSamples.CookedValue | Measure-Object -Average -Maximum
```
Ключ `-ComputerName FS01` — сбор с другого сервера (нужны права администратора или членство в группе Performance Log Users).

**4. Список доступных счётчиков.**
```powershell
(Get-Counter -ListSet 'LogicalDisk').Paths | Select-Object -First 10
```
`-ListSet *` — все наборы. На русской ОС имена будут русскими — это нормально.

**5. Быстрый срез через CMD.**
```cmd
typeperf "\Processor(_Total)\% Processor Time" -si 1 -sc 10
typeperf -qx | findstr /i disk
```
`-si` — интервал, `-sc` — количество семплов, `-qx` — список всех счётчиков. Удобно, когда PowerShell на сервере недоступен по политике.

**6. Создание постоянного сборщика (Data Collector Set) из командной строки.**
```cmd
mkdir C:\PerfLogs\Baseline
logman create counter DCS-Baseline-FS01 -c "\Processor(_Total)\% Processor Time" "\System\Processor Queue Length" "\Memory\Available MBytes" "\Memory\Pages/sec" "\LogicalDisk(_Total)\Avg. Disk sec/Read" "\LogicalDisk(_Total)\Avg. Disk sec/Write" "\LogicalDisk(_Total)\Current Disk Queue Length" "\Network Interface(*)\Bytes Total/sec" -si 15 -f bincirc -max 256 -o C:\PerfLogs\Baseline\fs01-baseline.blg
logman start DCS-Baseline-FS01
logman query DCS-Baseline-FS01
logman stop DCS-Baseline-FS01
```
`-c` — счётчики, `-si` — интервал, `-f bincirc` — бинарный файл с перезаписью по кругу, `-max 256` — лимит в МБ (защита от распухания), `-o` — путь к журналу. Выполнять из консоли с правами администратора. Через GUI то же самое: Data Collector Sets → User Defined → правый клик → New → Data Collector Set.

**7. Пересчёт журнала в CSV и обратно в PowerShell.**
```cmd
relog C:\PerfLogs\Baseline\fs01-baseline.blg -f csv -o C:\PerfLogs\Baseline\fs01-baseline.csv
```
```powershell
$c = Import-Counter C:\PerfLogs\Baseline\fs01-baseline.blg
($c.CounterSamples | Where-Object Path -like '*avg. disk sec/write*' | Measure-Object CookedValue -Average -Maximum)
```
`relog` умеет резать по времени (`-b`/`-e`) и прореживать (`-cf`). `Import-Counter` читает `.blg` напрямую, `Export-Counter` — пишет.

**8. Resource Monitor — кто именно грузит диск.**
```text
resmon → вкладка «Диск»: столбцы процесса, файла, Read/Write B/sec и Response Time
resmon → вкладка «Память»: «Жесткие ошибки/с» по процессам
resmon → вкладка «Сеть»: процессы, TCP-подключения, потери пакетов
resmon → вкладка «ЦП»: «Связанные дескрипторы» и «Связанные модули» — видно, какая DLL/драйвер крутит CPU
```
Это единственный штатный инструмент, который сразу показывает **файл**, а не только процесс.

**9. Кто ест CPU и память.**
```powershell
Get-Process | Sort-Object CPU -Descending | Select-Object -First 10 Name, Id, CPU, WS
Get-Counter '\Process(*)\IO Data Bytes/sec' | ForEach-Object { $_.CounterSamples } | Sort-Object CookedValue -Descending | Select-Object -First 10 Path, CookedValue
```
`CPU` — суммарное процессорное время в секундах с момента старта процесса, `WS` — рабочий набор (память в байтах).

**10. Память и диск через CIM (работает на любой локали и в старых PowerShell).**
```powershell
Get-CimInstance Win32_PerfFormattedData_PerfOS_Memory | Select-Object AvailableMBytes, PagesPerSec, PercentCommittedBytesInUse
Get-CimInstance Win32_PerfFormattedData_PerfDisk_LogicalDisk | Select-Object Name, AvgDisksecPerRead, AvgDisksecPerWrite, CurrentDiskQueueLength
Get-CimInstance Win32_PerfFormattedData_PerfOS_System | Select-Object ProcessorQueueLength
```
Отличный способ писать переносимые скрипты: имена свойств не зависят от языка ОС.

**11. Сеть.**
```powershell
Get-NetAdapterStatistics
Get-NetTCPConnection -State Established | Group-Object OwningProcess | Sort-Object Count -Descending | Select-Object -First 5
Get-Counter '\TCPv4\Segments Retransmitted/sec' -SampleInterval 1 -MaxSamples 10
```

**12. Sysinternals — когда встроенных мало.**
```text
Process Explorer — CPU/Private Bytes/I-O в колонках, дерево процессов, свойства → Performance
Process Monitor — кто и к какому файлу/ключу реестра обращается
RAMMap — Active / Standby / Modified: понять, куда ушла память
```
Скачивать только с официального сайта Microsoft (learn.microsoft.com/sysinternals).

3. Цифры: `Get-Counter '\LogicalDisk(_Total)\Current Disk Queue Length','\LogicalDisk(_Total)\Avg. Disk sec/Write','\Processor(_Total)\% Processor Time' -SampleInterval 2 -MaxSamples 5`. Очередь выше 2 и задержка выше 25 мс — подтверждение.
4. Виновник: `Get-Counter '\Process(*)\IO Data Bytes/sec'` и в Resource Monitor — конкретные файлы. В нашем случае это `System`/`svchost` и путь `\\FS01\Obshchee\dump`.
5. События: Event Viewer → Windows Logs → System, фильтр по источнику `disk` (коды 7, 11, 51, 153 — классика проблем ввода-вывода, набор зависит от драйвера) и `storahci`. Здесь их быть не должно — это важно: отсутствие ошибок диска подтверждает, что железо живо, а виновата нагрузка.
6. Плановые задания: `Get-ScheduledTask | Where-Object State -eq 'Running'`, проверь бэкап, антивирусное сканирование, теневые копии (`vssadmin list shadowstorage`). В реальности причина часто именно здесь, а не в «плохом сервере».
7. Решение: остановить копирование (`Stop-Process` по найденному PID или Ctrl+C в сессии на `WIN11-CL01`), убедиться, что очередь и задержка вернулись к базовой линии. В боевой среде дальше — перенос окна бэкапа/сканирования, ограничение полосы, `SMB bandwidth limits` или QoS.
8. Ответ пользователю: коротко, по делу, без обвинений.

**Что написать пользователю:**
> Иван, добрый день. Причину нашёл: на файловом сервере шла массовая операция копирования в `\\FS01\Obshchee` (служебная папка), она заняла диски и канал, из-за этого открытие `Buh` висело. Операцию остановил, сейчас проверил: папка открывается за 1–2 секунды, очередь к диску в норме. Проверьте, пожалуйста, сохранение Excel — если файл открывался «только для чтения», закройте его и откройте заново. Если снова повторится — сразу звоните, посмотрю в моменте.

**Закрытие заявки:** категория «Производительность → файловый сервер», решение «высокая дисковая нагрузка от служебного копирования, процесс остановлен», привяжи путь к журналам `C:\PerfLogs\Baseline\fs01-load.blg`, отметь «требуется профилактика: согласовать окно копирования вне рабочих часов».

### Что изменилось на стенде

- `FS01`: создана папка `C:\PerfLogs\Baseline`, в ней журналы `fs01-baseline.blg`, `fs01-load.blg`, `fs01-load.csv`.
- `FS01`: созданы Data Collector Sets `DCS-Baseline-FS01` (через `logman`) и `DCS-Manual-FS01` (через GUI).
- `WIN11-CL01`: отчёт `perfmon /report` (если сохранил) и папка `\\FS01\Obshchee\dump` с мусором от нагрузочного копирования — удали её после лабораторной.
- Запись в базе знаний: runbook «Снятие базовой линии и разбор узкого места на FS01».
- В `stand-log.md` зафиксированы эталонные значения: CPU, `Available MBytes`, задержка диска в покое и под нагрузкой.

### Откат

Если что-то пошло не так (журналы заняли весь диск, `FS01` не отвечает, набор счётчиков не удаляется): VMware Workstation → **VM → Snapshot → Snapshot Manager**, выбери `before-l2-009` и нажми **Go To / Revert**. Откатывать нужно все три ВМ, чтобы состояние было согласованным. Перед откатом скопируй нужные журналы на хост через общую папку VMware — после отката они исчезнут. Если откат не нужен, просто удали сборщик: `logman delete DCS-Baseline-FS01` (или правый клик → Delete в PerfMon).

## 6. Ошибки новичков и безопасность

1. **Замер без базовой линии.** «CPU 70% — это много?» Без эталона ответить нельзя: для одного сервера 70% — норма, для другого — авария. → Сначала снимай baseline в спокойное время, потом сравнивай. → Правильно: baseline на каждом сервере при вводе в эксплуатацию, обновлять после крупных изменений.
2. **Смотреть только диспетчер задач и только CPU.** Диспетчер показывает мгновенный срез и не показывает очереди и задержки. → Пропускаешь диск и память, лечишь не ту болезнь. → Правильно: PerfMon/`Get-Counter` с интервалом и журналом.
3. **Верить одному семплу.** «`% Processor Time` = 0, значит сервер свободен» (а это был первый семпл вычисляемого счётчика). → Ложный вывод. → Правильно: минимум 5–10 семплов, смотри среднее и максимум.
4. **Путать `LogicalDisk` и `PhysicalDisk`.** На RAID/Storage Spaces один физический диск — много логических томов, и наоборот. → Неверная оценка очереди. → Правильно: задержку смотри по логическим томам, насыщение железа — по физическим.
5. **Паниковать от «% Disk Time > 100%».** Счётчик может показывать больше 100% при очереди — это не баг. → Лишняя эскалация. → Правильно: ориентируйся на `Avg. Disk sec/*` и `Current Disk Queue Length`.
6. **Считать низкий `Available MBytes` нехваткой памяти.** Кэш-менеджер специально занимает свободную RAM. → Закупаешь память, которая не нужна. → Правильно: смотри `Pages/sec` и жёсткие страничные ошибки.
7. **Забыть остановить сборщик.** `DCS` без `-max` и ротации за сутки съедает диск на сервере. → Новый инцидент, сделанный своими руками. → Правильно: всегда `-max` и `-f bincirc`, проверка `logman query`.
8. **Мерить в окно бэкапа/антивирусного сканирования** и делать вывод «сервер плохой». → Неверный вывод, зря потраченное время. → Правильно: сверяй время жалобы с расписанием заданий.

**Безопасность.** Не отключай антивирус и не «оптимизируй» сервер сторонними утилитами с торрентов ради красивых цифр — это классический способ привезти в компанию майнер или шифровальщик. Не запускай PerfMon и скрипты под доменной учёткой администратора — для сбора достаточно локального администратора или группы **Performance Log Users**. Журналы `.blg` содержат имена серверов, процессов, путей и учёток — это внутренняя информация, не выкладывай их в публичные чаты и на форумы; при передаче вендору — обезличивай. И не делай кадровых выводов по данным мониторинга активности пользователей: в боевой среде такие данные собираются только по регламенту и с уведомлением сотрудников.

## 7. Вопросы на собеседовании

**Вопрос 1. «Пользователи жалуются, что файловый сервер тормозит. С чего начнёте?»**
Ответ: сначала уточню у заявителей время, характер операций и массовость — один пользователь или все. Параллельно проверю доступность и SMB (445 порт, `Get-SmbSession`), затем сниму живые счётчики: CPU, `Available MBytes`, `Avg. Disk sec/Read/Write`, `Current Disk Queue Length`, сеть. Дальше найду процесс и файл через Resource Monitor, сверю с расписанием бэкапов и антивируса, посмотрю System log на ошибки диска. Сравню с базовой линией и только потом сделаю вывод.
*Что хочет услышать интервьюер:* структурный подход, а не «перезагружу сервер».
*Красный флаг:* сразу предлагает «добавить RAM» или «перезагрузить» без единого замера.

**Вопрос 2. «Как понять, что узкое место — диск, а не процессор?»**
Ответ: по трём признакам. CPU низкий (`% Processor Time` и `Processor Queue Length` в норме), но задержка диска высокая (`Avg. Disk sec/*` > 25 мс), очередь к диску растёт (`Current Disk Queue Length` > 2), а время в привилегированном режиме (`% Privileged Time`) повышено, потому что потоки висят в ожидании I/O. Дополнительно Resource Monitor покажет конкретный процесс и файл с большим Response Time.
*Что хочет услышать интервьюер:* понимание связки «загрузка + очередь + задержка» и что задержка важнее процента загрузки.
*Красный флаг:* «если диск 100% в диспетчере задач — значит диск».

**Вопрос 3. «Какие счётчики памяти смотрите и что считаете тревожным?»**
Ответ: `Available MBytes`, `Pages/sec`, `% Committed Bytes In Use`, `Paging File(_Total)\% Usage`. Тревожно: устойчивый `Pages/sec` выше 20–25, `% Committed Bytes In Use` выше 85–90%, `Available MBytes` в сотнях килобайт при активной работе. Низкий `Available MBytes` сам по себе не проблема — свободную память занимает файловый кэш.
*Что хочет услышать интервьюер:* что кандидат не путает кэш и реальную нехватку памяти.
*Красный флаг:* «смотрю только «Память» в диспетчере задач».

**Вопрос 4. «Что такое базовая линия и зачем она нужна?»**
Ответ: это набор эталонных значений счётчиков, снятый на здоровом сервере в типичное рабочее время. Без неё цифры ничего не говорят: 60% CPU для одного сервера норма, для другого — деградация. Базовая линия обновляется после изменений (новая роль, миграция, обновление), хранится в базе знаний вместе с описанием конфигурации и используется при разборе инцидентов и при планировании мощностей.
*Что хочет услышать интервьюер:* инженерную зрелость, понимание, что производительность — относительная величина.
*Красный флаг:* «базовая линия — это когда всё нормально, я такое не снимаю».

**Вопрос 5. «Проблема плавающая: раз в день на 5 минут. Как поймать?»**
Ответ: поставить постоянный сбор Data Collector Set с интервалом 15–30 секунд, с ротацией (`bincirc` + лимит размера), запускать по расписанию или круглосуточно. Дополнительно — сбор на стороне клиента и на сервере, чтобы коррелировать. Когда пользователь сообщает о проблеме, фиксирую время и вырезаю окно из журнала (`relog -b/-e`). Если 5 минут мало для счётчиков, включаю трассировку WPR/WPA на время инцидента [ПРОВЕРИТЬ наличие wpr на своей версии Server].
*Что хочет услышать интервьюер:* умение организовать длительное наблюдение и работать с временными окнами.
*Красный флаг:* «приду и посмотрю в моменте» — плавающую проблему так не поймать.
