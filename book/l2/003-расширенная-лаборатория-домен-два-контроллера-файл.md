# Расширенная лаборатория: домен, два контроллера, файловый сервер, Linux-сервера, сегментированная сеть на VMware

## 1. Введение (зачем это нужно в реальной работе)

Заявка `INC-L2-003`. Пользователь: ivanov (WIN11-CL01). Что написал: «После обеда перестал открываться сайт `http://10.10.20.10` — таймаут. И на `\\FS01\Obshchee` стал заходить через раз. Раньше всё работало». Срочность: средняя.

На первый взгляд — «сайт не работает». Но чтобы эту заявку реально закрыть, нужно: знать, что сайт живёт в отдельном сегменте за маршрутизатором; уметь пинговать и трассировать через этот маршрутизатор; понимать, что «через раз заходит на шару» может быть связано с тем, что клиент аутентифицируется то на DC01, то на DC02, и один из них отдаёт старые данные. Одним словом, нужен стенд, на котором эти сущности существуют одновременно и взаимодействуют.

На уровне L1 у вас был «плоский» стенд: один контроллер, файловый сервер, пара клиентов и Linux-машина для практики. Этого хватает, чтобы сдать базовые заявки. Но L2 начинается там, где проблема не в одной машине, а в связке: домен + репликация + маршрутизация + сервисы на разных ОС.

В этой главе вы достроите стенд «Вектора» до состояния, в котором можно репетировать боевые сценарии: второй контроллер домена DC02, сегмент DMZ на отдельной виртуальной сети VMnet10 с веб-сервером WEB01, маршрутизатор GW01 на Debian, сервер мониторинга MON01. Все последующие главы L2 будут опираться именно на эту топологию — больше машины вводить почти не придётся, вы будете их настраивать и ломать.

Что вы должны уметь после главы: добавить контроллер домена в существующий домен и проверить репликацию; развести сети в VMware и сделать маршрутизацию между ними; поднять Linux-роутер с nftables и IP-форвардингом; проверить доступность сервиса по цепочке «клиент → шлюз → сервер»; и главное — не сломать стенд насовсем.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Виртуальные сети VMware Workstation.** Для каждой сети VMware создаёт в ОС хоста виртуальный коммутатор (виртуальный сетевой адаптер). У вас уже есть VMnet8 — тип **NAT**: виртуальные машины получают адреса в 10.10.10.0/24 от DC01, а сам VMware отдаёт им «интернет» через свой NAT-механизм с адресом шлюза 10.10.10.2. Второй тип, который нам нужен, — **Host-only**: сеть существует только между виртуальными машинами и хостом, наружу не выходит. Это идеальный кандидат для DMZ: даже случайно опубликовать сервис из неё в физическую сеть нельзя.

Ключевая идея сегментации: DMZ (`de-militarized zone`, демилитаризованная зона) — это сеть, где живут сервисы, доступные «снаружи». Если такой сервис взломают, атакующий окажется в изолированном сегменте, а не в офисной сети рядом с файловым сервером и контроллерами домена.

**Как соединяются сегменты.** Машина с двумя сетевыми картами, подключёнными к разным сетям, и включённой пересылкой IP-пакетов становится маршрутизатором. Пакет от клиента в офисе приходит на один интерфейс, ядро смотрит таблицу маршрутизации, понимает, что сеть назначения 10.10.20.0/24 доступна через второй интерфейс, и отдаёт пакет туда. Это уровень L3 модели OSI. Фильтрация — nftables в Debian — решает, *можно ли* этот пакет передать дальше.

```text
                       ХОСТ (VMware Workstation)
 ┌──────────────────────────────────────────────────────────────────┐
 │  VMnet8 (NAT) 10.10.10.0/24, шлюз в интернет 10.10.10.2          │
 │                                                                  │
 │  DC01 .10    DC02 .11    FS01 .20    SRV1C01 .25                 │
 │  UBU01 .30   ASTRA01 .31 MON01 .40                               │
 │  WIN11-CL01 (DHCP)      WIN10-CL02 (DHCP)                        │
 │                          │                                       │
 │                          │ ens33 10.10.10.3                      │
 │                     ┌────┴─────┐                                 │
 │                     │   GW01   │ маршрутизатор, nftables         │
 │                     └────┬─────┘                                 │
 │                          │ ens37 10.10.20.1                      │
 │  VMnet10 (Host-only) 10.10.20.0/24                               │
 │                    WEB01 .10  (nginx)                            │
 └──────────────────────────────────────────────────────────────────┘
   Логически: [ОФИС] --- GW01 --- [DMZ]   (в бою между ними ещё фаервол)
```

**Домен с двумя контроллерами.** Все контроллеры домена AD DS равноправны по данным (multi-master), но не по ролям: есть пять FSMO-ролей (Schema Master, Domain Naming Master, PDC Emulator, RID Master, Infrastructure Master), и они в один момент времени принадлежат одному DC. Изменение (новый пароль, новая группа) записывается на том DC, куда пришёл клиент, помечается номером USN и реплицируется на партнёров. Внутри сайта по умолчанию репликация идёт примерно каждые 15 секунд, между сайтами — реже. Топологию репликации строит служба KCC. Папка SYSVOL (там лежат GPO-скрипты) синхронизируется отдельным механизмом — DFS Replication.

Практический вывод: после того как в домене два DC, любая заявка «у меня не тот пароль / не вижу группу / не применяется политика» может означать не «сломался DC01», а «сломалось то, что между DC01 и DC02».

**Порты, без которых домен не живёт:** DNS 53 (UDP/TCP), Kerberos 88 (UDP/TCP), LDAP 389 (TCP/UDP), LDAPS 636, Global Catalog 3268/3269, SMB 445, RPC endpoint mapper 135 и динамический диапазон RPC 49152–65535, NTP 123 (время критично для Kerberos — расхождение больше 5 минут ломает аутентификацию). Для нашего веб-сервиса — 80/443, для Linux-серверов — SSH 22.

## 3. Аналогия из жизни

Представьте офис компании. Есть рабочая зона с бухгалтерией, складом и HR — это VMnet8. Есть приёмная с отдельным входом с улицы, где сидят курьеры и посетители и куда сотрудникам ходить не обязательно — это DMZ, VMnet10. Между ними стоит вахтёр GW01: у него две двери, и он по инструкции решает, кого куда пустить. Два контроллера домена — это два нотариуса с одинаковыми книгами учёта: запись, сделанная у одного, должна через пару секунд появиться у второго, иначе клиент, которого отправили к другому нотариусу, увидит устаревшую страницу. Файловый сервер — архив за стеклянной дверью, ключи от которой выдаёт нотариус.

Аналогия перестаёт работать в одном месте: вахтёр пропускает конкретного человека, а маршрутизатор оперирует отдельными пакетами одного и того же соединения, и ему приходится помнить состояние (conntrack), иначе ответные пакеты он не узнает.

## 4. Практика и команды

**1. Список контроллеров домена и владельцев FSMO**

```powershell
Get-ADDomainController -Filter * | Format-Table Name, IPv4Address, IsGlobalCatalog, OperationMasterRoles
netdom query fsmo
```
`-Filter *` — «все объекты», без него командлет требует конкретное имя. Смотрим: два DC в списке, у одного в `OperationMasterRoles` перечислены роли — это значит, что FSMO остались на DC01, и это нормально.

**2. Диагностика DC «в одну строку»**

```cmd
dcdiag /q
dcdiag /test:dns /v
```
`/q` — quiet, печатает только ошибки (пусто = хорошо). `/test:dns /v` — подробный тест DNS-части, а именно на ней ломается 90% репликации. В выводе ищите строки FAIL и предупреждения про SRV-записи `_ldap._tcp.dc._msdcs.corp.vektor.lab`.

**3. Состояние репликации**

```cmd
repadmin /replsummary
repadmin /showrepl
```
`/replsummary` — сводка: наибольший «лаг» и число ошибок по каждому партнёру. `/showrepl` — по каждому партнёру даты последней успешной репликации. Смотрим, что входящие (INBOUND) связи с обоих DC имеют статус `successful`.

**4. Добавление второго контроллера (PowerShell, на DC02 после смены имени и IP)**

```powershell
Install-WindowsFeature AD-Domain-Services -IncludeManagementTools
$cred = Get-Credential VEKTOR\adm.student
Install-ADDSDomainController -DomainName corp.vektor.lab -InstallDns -Credential $cred -SiteName "Default-First-Site-Name"
```
`-Credential` обязателен: учётка должна быть в Domain Admins/Enterprise Admins. `-InstallDns` ставит DNS-сервер на DC02. Команда запросит пароль DSRM (режим восстановления служб каталогов) — сохраните его в своей записке по стенду. После завершения — автоматическая перезагрузка.

**5. Проверка файлового сервера (на FS01)**

```powershell
Get-SmbShare | Format-Table Name, Path
Get-SmbShareAccess -Name Buh
Get-SmbSession | Format-Table ClientComputerName, ClientUserName, NumOpens
```
Первая — какие шары опубликованы. Вторая — кто имеет доступ к `Buh` (должна быть группа `GG-Buh`, а не отдельные пользователи). Третья — кто прямо сейчас держит файлы открытыми; при жалобе «файл занят» смотрим `Get-SmbOpenFile`.

**6. Проверка доступности порта с Windows**

```powershell
Test-NetConnection 10.10.20.10 -Port 80
Resolve-DnsName fs01.corp.vektor.lab
```
`-Port` переключает проверку с ICMP-пинга на TCP-коннект — это правильный способ проверять сервис (ICMP часто заблокирован, а сервис жив). `TcpTestSucceeded : True` — сервис отвечает.

**7. Маршрут до DMZ на Windows**

```cmd
route -p add 10.10.20.0 mask 255.255.255.0 10.10.10.3
route print -4
tracert 10.10.20.10
```
`-p` делает маршрут постоянным (без него исчезнет после перезагрузки). `tracert` должен показать два хопа: 10.10.10.3 (GW01) и 10.10.20.10 (WEB01). Один хоп с финальным адресом — значит, маршрут есть, а форвардинг нет.

**8. Linux: адреса, маршруты, сокеты**

```bash
ip -br a
ip r
ss -tulnp
```
`ip -br a` — компактный список интерфейсов и адресов (на GW01 должно быть два: ens33 10.10.10.3 и ens37 10.10.20.1). `ip r` — таблица маршрутизации, ищем `default via 10.10.10.2`. `ss -tulnp` — какие порты слушаются: на WEB01 должен быть `:80`.

**9. Проверка и применение правил nftables**

```bash
sudo nft -c -f /etc/nftables.conf
sudo nft list ruleset
sudo systemctl restart nftables
```
`-c` — check: только проверить синтаксис файла, ничего не применяя. Это спасает от «применил правило — потерял SSH». `list ruleset` — что реально загружено в ядро (может отличаться от файла, если забыли рестарт).

**10. Форвардинг и «кто съел пакет»**

```bash
sysctl net.ipv4.ip_forward
sudo tcpdump -ni ens37 port 80
sudo tcpdump -ni any host 10.10.20.10
```
`ip_forward = 0` — пакеты приходят на GW01 и умирают там, это самая частая причина «через шлюз ничего не работает». `tcpdump` показывает, долетает ли трафик до интерфейса: если на ens37 пусто, проблема на стороне клиента/маршрута; если пакеты есть, а ответа нет — проблема на WEB01.

**11. Проверка веб-сервиса из Linux**

```bash
curl -I http://10.10.20.10
curl -v http://10.10.20.10
```
`-I` — только заголовки, ждём `HTTP/1.1 200 OK`. `-v` — подробно, видно, на каком этапе затык (DNS, TCP-коннект, TLS).

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

Стенд L1 полностью готов: DC01 (10.10.10.10, AD DS + DNS + DHCP), FS01 (10.10.10.20, шары `Obshchee`, `Buh`, `HR`), WIN11-CL01 и WIN10-CL02 в домене, UBU01 (10.10.10.30) и ASTRA01 (10.10.10.31) на связи. Лежат ISO: Windows Server 2022 Evaluation, Debian 12 (netinst), Ubuntu Server 24.04 LTS. Есть не менее 16 ГБ RAM и ~150 ГБ свободного диска на хосте (DC02 — 4 ГБ, GW01 — 1 ГБ, WEB01 — 2 ГБ, MON01 — 2 ГБ).

Если чего-то из L1 нет — вернитесь к модулю L1 и не начинайте эту главу, стенд должен быть целым.

### Снапшот

В VMware Workstation на **каждой** из ВМ: `VM → Snapshot → Take Snapshot`, имя `before-l2-003`. На DC01 и FS01 снимайте при выключенной или хотя бы «спокойной» ВМ (подробнее про подводные камни отката DC — в разделе 6).

### Шаги

1. **Проверяем исходное состояние.** На DC01: `dcdiag /q` (пусто), `Get-SmbShare` на FS01, `ip -br a` на UBU01. На WIN11-CL01: `ipconfig /all` — адрес из пула 10.10.10.100–150, DNS 10.10.10.10. Ожидаемо: всё зелёное, стенд L1 здоров.

2. **Создаём сеть VMnet10.** На хосте: меню `Edit → Virtual Network Editor → Change Settings` (нужны права администратора) → `Add Network` → выбрать `VMnet10` → тип **Host-only** → подсеть `10.10.20.0`, маска `255.255.255.0` → снять галку `Use local DHCP service` → адрес хостового адаптера VMnet10 поменять с `10.10.20.1` на **`10.10.20.254`** → Apply. Ожидаемо: сеть появилась, DHCP выключен, `.1` свободен для GW01. *Почему 254: по умолчанию VMware забирает `.1` под адаптер хоста, а нам нужен этот адрес для GW01.*

3. **Создаём DC02.** Новая ВМ: Windows Server 2022 Evaluation, 2 vCPU, 4 ГБ RAM, 60 ГБ диск, сеть — только VMnet8. Установка «Server Core» или «Desktop Experience» — на ваш вкус. Внутри: `Rename-Computer -NewName DC02 -Restart`, затем статический адрес:

```powershell
New-NetIPAddress -InterfaceAlias "Ethernet0" -IPAddress 10.10.10.11 -PrefixLength 24 -DefaultGateway 10.10.10.2
Set-DnsClientServerAddress -InterfaceAlias "Ethernet0" -ServerAddresses 10.10.10.10
```
Имя интерфейса проверьте `Get-NetAdapter`. Ожидаемо: `ping corp.vektor.lab` и `nltest /dsgetdc:corp.vektor.lab` отвечают от DC01.

4. **Вводим DC02 в домен как контроллер.** Сначала `Add-Computer -DomainName corp.vektor.lab -Credential VEKTOR\adm.student -Restart`, после перезагрузки — команда из раздела 4, п.4. Ожидаемо: длинная установка, перезагрузка, вход под `VEKTOR\adm.student`.

5. **Проверяем репликацию.** На DC02: `Get-ADDomainController -Filter *` (два DC), `dcdiag /q` (пусто), `repadmin /replsummary` (0 ошибок). Затем меняем что-нибудь на DC01 (`New-ADUser test.repl -Enabled $false`) и на DC02 проверяем `Get-ADUser test.repl` — пользователь должен появиться в течение ~15–60 секунд. Удалите тестового пользователя.

6. **Создаём GW01.** Новая ВМ Debian 12 netinst, 1 vCPU, 1 ГБ RAM, 20 ГБ. Два сетевых адаптера: первый — `Custom: VMnet8`, второй — `Custom: VMnet10`. При установке — без графики, SSH-сервер да. Настраиваем `/etc/network/interfaces`:

```text
auto lo
iface lo inet loopback

auto ens33
iface ens33 inet static
    address 10.10.10.3/24
    gateway 10.10.10.2

auto ens37
iface ens37 inet static
    address 10.10.20.1/24
```
Имена интерфейсов сверьте по `ip -br a` до правки. DNS пропишите в `/etc/resolv.conf` (`nameserver 10.10.10.10`) или поставьте пакет `resolvconf`, если хотите директиву `dns-nameservers`. После `systemctl restart networking` — `ping 10.10.10.10` проходит.

7. **Включаем маршрутизацию и nftables на GW01.**

```bash
sudo tee /etc/sysctl.d/99-router.conf <<'EOF'
net.ipv4.ip_forward=1
EOF
sudo sysctl --system
sudo apt install -y nftables
sudo tee /etc/nftables.conf <<'EOF'
#!/usr/sbin/nft -f
flush ruleset

table inet filter {
  chain forward {
    type filter hook forward priority filter; policy drop;
    ct state established,related accept
    iifname "ens33" oifname "ens37" accept
    iifname "ens37" oifname "ens33" accept
  }
}

table ip nat {
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept
    ip saddr 10.10.20.0/24 oifname "ens33" masquerade
  }
}
EOF
sudo nft -c -f /etc/nftables.conf && sudo systemctl enable --now nftables
sudo systemctl restart nftables
```
Ожидаемо: `sysctl net.ipv4.ip_forward` → `= 1`, `sudo nft list ruleset` показывает оба правила. **Правило безопасности:** вторая строка forward-цепочки (`ens37 → ens33`) в лабе разрешает из DMZ в офис всё подряд. В боевой среде так нельзя — открывайте только конкретные пары «адрес:порт».

8. **Создаём WEB01.** Ubuntu Server 24.04, 2 ГБ RAM, 20 ГБ, один адаптер — `Custom: VMnet10`. Правим `/etc/netplan/50-cloud-init.yaml` (точное имя — `ls /etc/netplan`):

```yaml
network:
  version: 2
  ethernets:
    ens33:
      dhcp4: false
      addresses: [10.10.20.10/24]
      routes:
        - to: default
          via: 10.10.20.1
      nameservers:
        addresses: [10.10.10.10]
```
`sudo netplan apply`, затем `sudo apt update && sudo apt install -y nginx`. Ожидаемо: `curl -I http://localhost` на WEB01 отдаёт `200 OK`, `curl -I http://10.10.10.10` (проверка выхода через GW01 в офис) тоже работает.

9. **Проверяем путь из офиса в DMZ.** На DC01:

```cmd
route -p add 10.10.20.0 mask 255.255.255.0 10.10.10.3
tracert 10.10.20.10
curl.exe -I http://10.10.20.10
```
Ожидаемо: два хопа, `HTTP/1.1 200 OK`. На WIN11-CL01 добавьте такой же маршрут без `-p` — и убедитесь, что без маршрута страница не открывается (это и есть доказательство, что сеть сегментирована). В нормальной среде этот маршрут не прописывают руками на каждой машине, а раздают через DHCP опцию 121 (Classless Static Routes) на DC01.

10. **Создаём MON01.** Ubuntu Server 24.04, 2 ГБ RAM, 20 ГБ, адаптер VMnet8, адрес 10.10.10.40/24, шлюз 10.10.10.2, DNS 10.10.10.10 (через netplan, как в шаге 8). Сам Zabbix поставим в главе про мониторинг — сейчас достаточно, что машина в сети, доступна по SSH и видит `10.10.10.10`.

11. **Записываем результат в `stand-log.md`.** Дата, номер урока, что добавлено (см. следующий подраздел), какие адреса заняты.

### Проверка

- [ ] В Virtual Network Editor есть VMnet10 типа Host-only, DHCP выключен, подсеть 10.10.20.0/24, адаптер хоста — 10.10.20.254.
- [ ] `Get-ADDomainController -Filter *` на DC02 возвращает DC01 и DC02.
- [ ] `dcdiag /q` на обоих DC не выводит ошибок; `repadmin /replsummary` — 0 ошибок.
- [ ] Новый объект, созданный на DC01, виден на DC02 в течение минуты.
- [ ] `sysctl net.ipv4.ip_forward` на GW01 = 1; `nft list ruleset` содержит правила forward и masquerade.
- [ ] С DC01 `tracert 10.10.20.10` даёт хоп 10.10.10.3 и финиш 10.10.20.10; `curl.exe -I http://10.10.20.10` → 200.

### Сломай и почини

**Пользователь:** ivanov / ВМ WIN11-CL01 / **Что написал:** «Сайт `http://10.10.20.10` не открывается — Connection timed out. Утром работал, потом я перезагружал компьютер. Коллега с соседнего места говорит, что у него тоже». **Срочность:** средняя.

**Как воспроизвести поломку.** На GW01 выполните `sudo sysctl -w net.ipv4.ip_forward=0` (это меняет значение только до перезагрузки — то есть имитирует «правило не сохранилось»). Затем на WIN11-CL01 повторите попытку открыть страницу.

**Диагностика по порядку (снизу вверх по стеку):**

1. На WIN11-CL01: `route print -4` — есть ли маршрут 10.10.20.0 → 10.10.10.3. Если нет (перезагрузка убила непостоянный маршрут), сначала добавить: `route add 10.10.20.0 mask 255.255.255.0 10.10.10.3`.
2. `ping 10.10.10.3` — GW01 доступен. `ping 10.10.20.10` с клиента — не отвечает. Значит, проблема не в клиенте.
3. На GW01: `ping 10.10.20.10` — с самого шлюза отвечает. Значит, WEB01 жив, проблема в передаче пакетов между интерфейсами.
4. `sysctl net.ipv4.ip_forward` — видим `= 0`. Причина найдена.
5. Для верности: `sudo tcpdump -ni ens33 host 10.10.20.10` при попытке клиента — пакеты приходят; `sudo tcpdump -ni ens37 host 10.10.20.10` — тишина. Подтверждает: ядро не пересылает.
6. Проверяем, что настройка действительно не персистентна: `ls /etc/sysctl.d/` — файла `99-router.conf` нет.

**Решение.** `sudo sysctl -w net.ipv4.ip_forward=1`, затем создать `/etc/sysctl.d/99-router.conf` с `net.ipv4.ip_forward=1` и выполнить `sudo sysctl --system`, чтобы переживало перезагрузку. Проверить `sudo nft list ruleset` (правила на месте) и `curl -I http://10.10.20.10` с DC01.

**Ответ пользователю:** «Добрый день! Причина найдена: на маршрутизаторе между офисной сетью и сегментом с сайтом отключилась пересылка трафика. Включили и закрепили настройку, чтобы не повторилось после перезагрузки. Сейчас `http://10.10.20.10` открывается — проверьте, пожалуйста, и напишите, если что-то ещё не так. **Закрытие заявки:** категория «Сеть / маршрутизация», корневая причина «несохранённая настройка `ip_forward`», решение описано, действие-предотвращение — «проверить на GW01, что все sysctl-настройки лежат в `/etc/sysctl.d/` и попадают в бэкап конфигурации». ## 6. Ошибки новичков и безопасность

1. **Забыли выключить DHCP VMware на VMnet10** → в сегменте DMZ два источника адресов, WEB01 получает «не тот» адрес и шлюз, диагностика превращается в угадайку. → Всегда проверяйте в Virtual Network Editor галку `Use local DHCP service`.
2. **Оставили хостовый адаптер VMnet10 на 10.10.20.1** → конфликт адресов с GW01, часть трафика уходит в никуда. → Отдайте хосту `.254`.
3. **Клонировали DC01 и назвали клон DC02** → дубликаты идентификаторов, «USN rollback», репликация разваливается необратимо. → Второй DC только чистой установкой и штатным промоушеном.
4. **Прописали DC02 в DNS самого себя единственным адресом** → он перестаёт видеть зону, которую обслуживает DC01, репликация DNS ломается. → Первичный DNS у дополнительного DC — адрес другого DC, вторичный — свой собственный.
5. **Не сохранили `ip_forward` в sysctl** → до перезагрузки всё работает, после — «сайт не открывается». Ровно наша поломка из лабораторной. → Все sysctl-настройки только через файлы в `/etc/sysctl.d/`.
6. **Правило nftables применили «в лоб» по SSH** → одним правилом отрезали себе доступ, дальше только через консоль VMware. → Всегда `nft -c -f` перед применением и `systemctl restart nftables` вместо ручного набора.
7. **Не обратили внимание на время** → Kerberos не пускает пользователей, если часы расходятся больше чем на 5 минут. На стенде время ВМ должно совпадать с хостом. → Проверяйте `w32tm /query /status` на Windows и `timedatectl` на Linux.
8. **Забыли про срок Evaluation** → Windows Server Evaluation живёт 180 дней, потом начинает отключаться. → Запишите дату установки в `stand-log.md`.

**Безопасность.** В лабораторной мы осознанно разрешили трафик из DMZ в офисный сегмент целиком — на стенде это удобно, в боевой среде так делать нельзя: DMZ существует именно для того, чтобы скомпрометированный веб-сервер не дотянулся до контроллера домена. Там правило формулируется наоборот: по умолчанию запрещено, разрешены только конкретные направления (например, WEB01 → DC01:53 для DNS и WEB01 → сервер обновлений). Отдельно: не храните пароль DSRM от DC02 и пароль `adm.student` в открытом виде в заметках на рабочем столе — на стенде это учебные данные, а привычка останется. И не отключайте брандмауэр Windows «чтобы проверить» — вместо этого проверяйте порт `Test-NetConnection -Port`, это быстрее и ничего не ломает.

## 7. Вопросы на собеседовании

**1. Зачем в домене второй контроллер и что изменится, если один упадёт?**

Ответ: отказоустойчивость аутентификации и DNS. Пока живы хотя бы два DC, клиенты продолжают логиниться, Kerberos и LDAP работают, зона DNS обслуживается. При падении одного DC его FSMO-роли нужно перенести (или они освободятся при восстановлении), но домен не «встанет». Плюс второй DC — это распределение нагрузки на аутентификацию и точка для сайтов/площадок. Важный нюанс: DHCP обычно живёт на одном сервере, и его отказ — отдельная проблема; для этого делают split-scope или DHCP failover.

*Что хочет услышать интервьюер:* что вы понимаете разницу между «данные реплицируются на всех» и «роли FSMO принадлежат одному»; что DNS — критичная часть домена, а не отдельная тема.

*Красный флаг:* «второй контроллер нужен для скорости» без единого слова про FSMO, DNS и репликацию.

**2. Как вы убедитесь, что репликация между контроллерами в порядке?**

Ответ: `repadmin /replsummary` — нет ошибок и лаг в пределах нормы; `repadmin /showrepl` — все входящие партнёры успешны; `dcdiag /q` и `dcdiag /test:dns` — чисто; проверка практикой — создал объект на одном DC, увидел на другом. Дополнительно смотрю журнал Directory Service на предмет событий 1311/1863 (проблемы репликации) и состояние DFSR для SYSVOL.

*Что хочет услышать интервьюер:* конкретные команды и понимание, что DNS — самая частая причина поломки репликации.

*Красный флаг:* «просто подожду, оно само синхронизируется».

**3. Что такое DMZ и почему туда ставят веб-сервер, а не в офисную сеть?**

Ответ: DMZ — сегмент между внешним миром и внутренней сетью, куда выносят сервисы, доступные извне. Если такой сервис взломают, атакующий получает доступ только к изолированному сегменту, а трафик в офисную сеть контролируется правилами фаервола. Плюс это позволяет независимо управлять политиками: во внутренней сети разрешено почти всё внутри, в DMZ — минимум. В идеале доступ из DMZ в офис идёт только по конкретным адресам и портам.

*Что хочет услышать интервьюер:* принцип наименьших привилегий на уровне сети и понимание, что DMZ — это про ограничение ущерба, а не про «удобно разместить сайт».

*Красный флаг:* «DMZ — это просто отдельная подсеть».

**4. С рабочего места не открывается сайт в другом сегменте. Как будете искать причину?**

Ответ: по слоям, снизу вверх. Сначала маршрут до сети назначения (`route print`, `tracert`) — есть ли он и через какой шлюз. Потом доступность шлюза (`ping`) и самого сервера с шлюза (`ping` уже с GW01) — это делит проблему на «до шлюза» и «после шлюза». Затем на шлюзе: форвардинг (`sysctl net.ipv4.ip_forward`), правила фильтрации (`nft list ruleset`), и `tcpdump` на обоих интерфейсах, чтобы увидеть, долетает ли трафик и приходит ли ответ. Потом сам сервис на целевой машине (`ss -tulnp`, `curl` локально), и в конце — DNS, если обращались по имени. На каждом шаге фиксирую результат, чтобы не ходить по кругу.

*Что хочет услышать интервьюер:* системный порядок действий, а не «попробую перезагрузить»; владение tcpdump/tracert.

*Красный флаг:* сразу лезть на сервер с сайтом, пропустив проверку маршрута и шлюза.

**5. Чем Host-only отличается от NAT в VMware и что выбрать для DMZ?**

Ответ: NAT даёт виртуальным машинам выход наружу через механизм VMware и обычно свой DHCP-пул; машины видят хост и внешний мир, но снаружи к ним напрямую не подключиться без проброса портов. Host-only создаёт сеть только между ВМ и хостом — внешнего выхода нет вообще, и это дополнительный барьер. Для DMZ правильнее Host-only: даже при ошибке в конфигурации сервис не окажется доступен из физической сети. Интернет внутри DMZ, если нужен, даём осознанно через роутер GW01 с NAT, а не через VMware.

*Что хочет услышать интервьюер:* понимание разницы типов виртуальных сетей и того, что изоляция — это свойство архитектуры, а не настройка приложения.

*Красный флаг:* «разницы нет, главное чтобы пинговалось».
