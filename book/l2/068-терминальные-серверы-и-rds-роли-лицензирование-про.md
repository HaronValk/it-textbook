Терминальный сервер — это машина, на которой сотрудники работают «внутри сервера»: их рабочий стол, 1С, Excel и браузер крутятся на одном мощном железе, а на клиенте идёт только картинка. ## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Терминальный доступ в Windows — это служба **Remote Desktop Services (RDS)**. Клиент подключается по протоколу **RDP** (Remote Desktop Protocol), по умолчанию **TCP 3389** (плюс UDP 3389 для транспорта, если включён UDP-режим). Внутри RDP трафик шифруется TLS, а аутентификация пользователя по умолчанию идёт через **NLA** (Network Level Authentication, CredSSP) — то есть логин проверяется до создания сеанса.

Ключевое отличие RDS от обычного «удалённого рабочего стола» Windows 10/11: серверный RDS умеет держать **много одновременных сеансов** и публиковать не весь рабочий стол, а отдельные приложения (**RemoteApp**). Именно так в РФ массово публикуют 1С: на терминале стоит тонкий клиент, пользователь видит только окно 1С (см. уроки 66–67 про сервер 1С).

Роли RDS:

| Роль | Что делает |
|------|-----------|
| **RD Session Host (RDSH)** | собственно сервер, где живут сеансы и приложения |
| **RD Connection Broker** | «диспетчер»: распределяет пользователей по хостам, помнит, кто где сидит, даёт коллекции |
| **RD Web Access** | веб-портал с ярлыками RemoteApp |
| **RD Gateway** | публикация RDP наружу через HTTPS 443, без открытия 3389 в интернет |
| **RD Licensing** | выдаёт RDS-лицензии (CAL) сеансам |
| **RD Virtualization Host** | хост для VDI на Hyper-V (это уже урок 69) |

Схема учебного стенда:

```text
   WIN11-CL01 (10.10.10.x, DHCP)
   клиент mstsc / xfreerdp
            │
            │ RDP: TCP 3389, TLS + NLA
            ▼
   ┌──────────────────────────────────────────────┐
   │ FS01 (10.10.10.20) — RDS-хост                │
   │  ├─ RD Session Host  → сеансы ivanov/petrova │
   │  ├─ RD Connection Broker → коллекция         │
   │  ├─ RD Licensing     → grace 120 дней        │
   │  └─ FSLogix Agent    → профиль = VHDX        │
   └───────────────┬──────────────────────────────┘
                   │ SMB 445
                   ▼
        \\FS01\Profiles\ivanov\Profile-ivanov.vhdx
   DC01 (10.10.10.10) — DNS, DHCP, AD, GPO (loopback)
```

**Лицензирование.** RDS-сеанс требует **RDS CAL** — клиентской лицензии. Два режима: **Per Device** (лицензия привязана к устройству, подходит для смен и общих компьютеров) и **Per User** (привязана к человеку, подходит, когда у сотрудника несколько устройств). Режим задаётся групповой политикой, а не «сам по себе». Свежеустановленный сервер живёт в **льготном периоде 120 дней** (grace period), потом сеансы блокируются. Именно это чаще всего и ломает работу бухгалтерии.

**Профили.** По умолчанию у пользователя **локальный профиль на каждом RDSH** — при нескольких хостах или переустановке сервера настройки теряются. Историческая эволюция: перемещаемые профили (roaming) → обязательные (mandatory) → перенаправление папок → **FSLogix**. FSLogix хранит профиль в **VHDX-контейнере на SMB-шаре** и подключает его к сеансу при входе: пользователь получает свои настройки на любом хосте, а файл профиля не «размазан» тысячей мелких файлов по сети. Есть Profile Container (весь профиль), Office Container (только Office-кэш) и App Masking (подмена приложений).

## 3. Аналогия из жизни

Представь коворкинг. Ты приходишь со своим ноутбуком (тонкий клиент), но работаешь за столом в общем зале (RDSH): монитор, chair, программы — всё хозяйское. На входе стоит турникет с **абонементом** (RDS CAL): без действующего абонемента охрана тебя не пустит, а если ты взял абонемент «на себя» (Per User) — проходишь с любого устройства, если «на конкретный стол» (Per Device) — только за свой стол. В раздевалке тебе выдают **шкафчик с личными вещами** (профиль): в старом варианте шкафчик прибит к конкретному залу, и в другой зал ты приходишь голым; FSLogix — это шкафчик на колёсах, который приезжает к тому столу, где ты сел. А «сломалось» — это когда шкафчик уже кто-то занял и второй ключ не выдаётся: ты стоишь в дверях, а внутри твои настройки.

Аналогия перестаёт работать в одном: в коворкинге ты можешь уйти в соседнее здание, а в RDS всё хозяйство (сеансы, лицензии, шары профилей) — это один и тот же сервер, и если он упал, работать негде вообще.

## 4. Практика и команды

**1. Список сеансов: `qwinsta` (= `query session`)**

```cmd
qwinsta /server:FS01
```

Вывод (сокращённо):

```text
 SESSIONNAME       USERNAME                 ID  STATE   TYPE        DEVICE
 services                                    0  Disc
 console                                     1  Conn
 rdp-tcp#7         ivanov                    3  Active
 rdp-tcp#8         petrova                   4  Disc
```

Смотрим: `STATE` — `Active` (работает), `Disc` (отключён, но висит и держит память и лицензию), `Listen` (слушатель). Отключённые сеансы — главный источник «терминал тормозит».

**2. Кто именно сидит: `quser`**

```cmd
quser /server:FS01
```

Колонки: USERNAME, SESSIONNAME, ID, STATE, IDLE TIME, LOGON TIME. `IDLE TIME` больше нескольких часов + `Disc` = кандидат на принудительный логаут.

**3. Принудительное завершение сеанса**

```cmd
logoff 4 /server:FS01
```

`logoff <ID>` завершает сеанс по-человечески (приложения получают сигнал). Есть более грубый `rwinsta <ID> /server:FS01` — он просто сбрасывает сеанс, несохранённые данные теряются. В бою сначала звонят пользователю, потом `logoff`, и только в крайнем случае `rwinsta`.

**4. Забрать «залипший» сеанс себе: `tscon`**

```cmd
tscon 3 /dest:console
```

`tscon <ID> /dest:console` пересаживает существующий сеанс на консоль сервера. Классика: пользователь ушёл домой, сеанс остался, а VHDX профиля заблокирован — администратор переносит сеанс на консоль, делает `logoff` и освобождает контейнер.

**5. Подключение и теневое управление**

```cmd
mstsc /v:10.10.10.20 /admin
mstsc /shadow:3 /v:10.10.10.20 /control
```

`/admin` — вход в консольный сеанс для администрирования (не занимает лицензию). `/shadow:<ID> ... /control` — «подглядеть» в сеанс пользователя и при необходимости управлять его мышью: незаменимо, когда надо показать, где кнопка. Требует прав и включённой политики [ПРОВЕРИТЬ имя политики «Remote control» в разделе RDS].

**6. Доступность порта с клиента**

```powershell
Test-NetConnection -ComputerName 10.10.10.20 -Port 3389
```

Смотрим `TcpTestSucceeded : True`. С UBU01 то же самое:

```bash
ss -tn state established '( dport = :3389 or sport = :3389 )'
xfreerdp /v:10.10.10.20 /u:ivanov /d:VEKTOR /f +clipboard
```

Пакет в Ubuntu 24.04 называется `freerdp2-x11` или `freerdp3-x11` [ПРОВЕРИТЬ актуальное имя], бинарник — `xfreerdp`/`xfreerdp3`.

**7. Состояние RDS через PowerShell (на брокере)**

```powershell
Import-Module RemoteDesktopServices
Get-RdsSession -ConnectionBroker "fs01.corp.vektor.lab" -CollectionName "Vektor-Desktop"
Get-RdsUserSession -ConnectionBroker "fs01.corp.vektor.lab" -CollectionName "Vektor-Desktop"
```

Вывод (сокращённо): CollectionName, UserName, SessionId, State, HostServer. Удобно для скриптов и для отчёта «сколько народу реально работает».

**8. Журналы событий — главный инструмент**

```powershell
Get-WinEvent -LogName 'Microsoft-Windows-TerminalServices-LocalSessionManager/Operational' -MaxEvents 30 |
  Select-Object TimeCreated, Id, Message
Get-WinEvent -LogName 'Microsoft-Windows-TerminalServices-RemoteConnectionManager/Operational' -MaxEvents 30
```

`LocalSessionManager` показывает входы/выходы/отключения (ID 21 — вход, 23 — отключение, 24 — отключён, 25 — переподключение). `RemoteConnectionManager` — прослушиватели и попытки подключения. Ошибки лицензирования лежат в журнале `Microsoft-Windows-TerminalServices-Licensing` [ПРОВЕРИТЬ точное имя журнала в вашей сборке].

**9. Проверка настроек лицензирования**

```powershell
Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Services\TermService\Parameters' |
  Select-Object LicenseServers, SpecifiedLicenseServers
Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Terminal Server\RCM\GracePeriod' -ErrorAction SilentlyContinue
gpresult /h C:\Temp\rds-gp.html
```

`SpecifiedLicenseServers` — куда сервер ходит за лицензиями; пусто = ищем автоматически. Наличие ключа `GracePeriod` = льготный период ещё идёт. В GUI: **Server Manager → Tools → Remote Desktop Services → RD Licensing Diagnoser** — она прямо пишет «лицензий нет / режим не задан».

**10. Проверка профилей FSLogix**

```powershell
Get-ItemProperty 'HKLM:\SOFTWARE\FSLogix\Profiles'
Get-ChildItem '\\FS01\Profiles' | Select-Object Name, LastWriteTime
Get-SmbOpenFile | Where-Object Path -like '*Profiles*'
Get-Content 'C:\ProgramData\FSLogix\Logs\*' -Tail 40
```

Ключевые значения реестра: `Enabled=1`, `VHDLocations=\\FS01\Profiles`, `VolumeType=VHDX`, `SizeInMBs`, `DeleteOnCleanup`, `LoggingEnabled`. `Get-SmbOpenFile` покажет, кто именно держит VHDX.

**11. Счётчики производительности сеансов**

```powershell
Get-Counter '\Terminal Services Session(*)\Active Sessions', '\Terminal Services Session(*)\Inactive Sessions'
```

Активные/неактивные сеансы + объём RAM на сеанс — так ты докажешь, что «тормозит» не сеть, а переполненная память от брошенных сеансов.

**12. Проверка самого протокола**

```powershell
Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Terminal Server' |
  Select-Object fDenyTSConnections, fSingleSessionPerUser
```

`fDenyTSConnections=1` — RDP выключен полностью (классика после «оптимизаторов»). `fSingleSessionPerUser=1` — вторым сеансом тот же пользователь не зайдёт.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Шаги

1. **FS01.** Ставим роли:


Ожидаемо: `Success: True`, после перезагрузки в Server Manager появится раздел **Remote Desktop Services**.

2. **FS01.** Создаём развёртывание и коллекцию:

6. **FS01.** Готовим шару под профили:

7. **FS01.** Ставим FSLogix Agent (с сайта Microsoft, дистрибутив бесплатный для Windows Enterprise/RDS [ПРОВЕРИТЬ актуальные условия лицензии]) и настраиваем:

8. **WIN11-CL01.** Заходим под `VEKTOR\ivanov` и подключаемся:

Ожидаемо: открывается рабочий стол FS01, «Не удалось войти» не появляется.

11. **FS01.** Диагностика «здоровья»:

### Сломай и почини

**Пользователь:** petrova (Мария Петрова, HR)
**ВМ:** WIN10-CL02
**Что написал:** «Здравствуйте! Не могу зайти на терминал: пишет "Не удалось войти в систему" и почти сразу закрывается. Утром всё работало, ivanov заходит нормально. Мне до обеда нужно отправить отчёт».
**Срочность:** Средняя.

**Воспроизведение поломки.** На FS01 от `adm.student` «занимаем» контейнер профиля так, будто он остался от аварийно завершённого сеанса:

```powershell
Mount-DiskImage -ImagePath '\\FS01\Profiles\petrova\Profile-petrova.vhdx'
Get-SmbOpenFile | Where-Object Path -like '*petrova*'
```

Теперь файл заблокирован, и FSLogix не сможет его смонтировать при входе.

**Диагностика по шагам:**

1. Смотрим журнал входов: `Get-WinEvent -LogName 'Microsoft-Windows-TerminalServices-LocalSessionManager/Operational' -MaxEvents 20` — видим событие входа petrova и сразу следом отключение (сеанс создался, но профиль не поднялся).
2. Смотрим логи FSLogix: `Get-Content 'C:\ProgramData\FSLogix\Logs\*' -Tail 50` — там будет сообщение о том, что контейнер уже используется / не удалось подключить VHDX.
3. Проверяем, кто держит файл: `Get-SmbOpenFile | Where-Object Path -like '*petrova*'` — видим открытый хэндл на `Profile-petrova.vhdx`.
4. Проверяем, нет ли «фантомного» сеанса: `qwinsta` — если у petrova висит `Disc`, снимаем `logoff <ID>`.
5. Проверяем права на шару и свободное место: `Get-SmbShareAccess -Name Profiles`, `Get-PSDrive C`. Мало места — тоже классика («профиль не помещается»).

**Решение.** Закрыть хэндл и размонтировать образ:

```powershell
Dismount-DiskImage -ImagePath '\\FS01\Profiles\petrova\Profile-petrova.vhdx'
Get-SmbOpenFile | Where-Object Path -like '*petrova*' | Close-SmbOpenFile -Force
```

## 6. Ошибки новичков и безопасность

1. **Ставить RDSH на контроллер домена.** → Хаос в правах, конфликт ролей, домен становится заложником терминала. → RDSH — отдельный сервер, в бою ещё и не один.
2. **Не задать режим лицензирования.** → Через 120 дней все сеансы падают с ошибкой «нет доступных лицензий», обычно в самый неподходящий момент. → Режим и сервер лицензий задаются GPO сразу после установки.
3. **Путать Per User и Per Device.** → Купили не те CAL: либо переплатили, либо не хватает лицензий на смену. → Per Device — для общих рабочих мест и смен, Per User — когда у человека несколько устройств.
4. **Хранить профили на том же сервере, что и RDSH, или на дешёвом NAS.** → Блокировки VHDX, дикие задержки входа. → Отдельная SMB-шара на нормальном хранилище, FSLogix не любит медленный диск.
5. **Пытаться «продлить» grace period правкой реестра.** → Нарушение лицензионного соглашения и внезапная блокировка после обновления. → Покупать CAL или переходить на легальную альтернативу.
6. **Брошенные отключённые сеансы.** → Память и лицензии съедены, «терминал тормозит». → Политики таймаутов сеансов + регулярный `qwinsta`.
7. **Игнорировать loopback processing.** → Пользовательские GPO не применяются на терминале, «у всех всё по-разному». → Включать loopback в GPO для OU серверов.
8. **Антивирус сканирует VHDX-контейнеры.** → Файл заблокирован, вход невозможен. → Исключения на каталог профилей.

**Безопасность.** Никогда не публикуй RDP (3389) напрямую в интернет — это самый сканируемый порт в мире; для удалённого доступа нужен RD Gateway (443 + TLS) или VPN (урок 71). Обязательны NLA и TLS, ограничение круга лиц, кто может входить на терминал (группа в AD, а не «Domain Users»), и учёт того, что на терминале в одном процессе могут оказаться данные разных людей — если FSLogix настроен неправильно, пользователь увидит чужой профиль. На стенде мы работаем в льготном периоде и с учебным паролем `Lab#2026-vektor` — в бою так нельзя.

## 7. Вопросы на собеседовании

**Вопрос 1. Из каких ролей состоит RDS и что делает каждая?**
Ответ: Session Host — держит сеансы и приложения; Connection Broker — распределяет пользователей по хостам и хранит коллекции; Web Access — веб-портал с RemoteApp; Gateway — публикует RDP через HTTPS без открытия 3389; Licensing — выдаёт RDS CAL. Плюс RD Virtualization Host для VDI на Hyper-V.
*Что хочет услышать интервьюер:* что ты не путаешь RDSH с брокером и понимаешь, зачем нужен шлюз.
*Красный флаг:* «RDS — это просто включить удалённый рабочий стол в свойствах системы».

**Вопрос 2. Чем Per User отличается от Per Device и что будет, если не настроить лицензирование?**
Ответ: Per User — CAL закрепляется за учёткой, человек может заходить с любого устройства; Per Device — за конкретным компьютером, удобно для смен. Без настроенного режима и сервера лицензий сервер работает 120 дней в льготном периоде, затем сеансы блокируются с ошибкой о недоступных лицензиях.
*Что хочет услышать интервьюер:* знание grace period и того, что режим задаётся GPO.
*Красный флаг:* «можно продлить льготный период через реестр» — это прямое нарушение лицензии.

**Вопрос 3. Почему FSLogix предпочтительнее перемещаемых профилей?**
Ответ: профиль лежит в одном VHDX-контейнере на SMB-шаре, а не в тысячах мелких файлов — вход быстрее, сеть не задыхается, конфликтов блокировок меньше; контейнер подключается на любом хосте коллекции, поддерживается Office Container и App Masking, есть понятные логи. Плюс FSLogix разруливает ситуацию «несколько хостов — один пользователь».
*Что хочет услышать интервьюер:* понимание, что FSLogix — про производительность входа и предсказуемость, а не «просто модно».
*Красный флаг:* «FSLogix — это антивирус для терминалов» или полное незнание темы профилей.

**Вопрос 4. Пользователь не может войти на терминал. Твои действия?**
Ответ: уточняю текст ошибки и когда началось; проверяю `qwinsta`/`quser` на хосте (нет ли зависшего сеанса); смотрю журналы LocalSessionManager и Licensing; проверяю, не кончились ли лицензии и не истёк ли grace; проверяю шару профилей — хэндлы через `Get-SmbOpenFile` и логи FSLogix; проверяю права и свободное место; проверяю доступность 3389 и GPO. Дальше — точечное исправление: `logoff`, размонтировать контейнер, пересоздать профиль с бэкапом.
*Что хочет услышать интервьюер:* чёткий порядок «от простого к сложному» и работа с логами, а не «перезагружу сервер».
*Красный флаг:* «сразу перезагружаю RDSH» — на сервере в этот момент работают двадцать человек.

**Вопрос 5. Что такое loopback processing и зачем он на терминальном сервере?**
Ответ: режим обработки групповых политик, при котором к пользователю, вошедшему на компьютер, применяются пользовательские политики, привязанные к OU этого компьютера. На RDS это нужно, чтобы на терминале действовали свои настройки пользователей (таймауты сеансов, перенаправление папок, ограничения), а не политики их обычных рабочих станций. Режимы Merge и Replace.
*Что хочет услышать интервьюер:* понимание порядка применения GPO и разницы Merge/Replace.
*Красный флаг:* «loopback — это когда политика применяется дважды».
