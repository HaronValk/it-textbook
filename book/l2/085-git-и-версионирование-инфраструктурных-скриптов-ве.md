# Git и версионирование инфраструктурных скриптов: ветки, pull request, code review

## 1. Введение (зачем это нужно в реальной работе)

**Заявка в поддержку.**

> **Пользователь:** Петрова Мария, HR
> **ВМ:** WIN10-CL02
> **Что написала:** «Открываю `\\FS01\HR` — «Отказано в доступе». Вчера всё работало, я ничего не трогала. У меня сегодня собеседования, нужны документы.»
> **Срочность:** высокая

Ты идёшь на FS01, смотришь права на папку — группы `GG-HR` в списке доступа нет. Кто её убрал? Когда? Пять минут назад всё было нормально. Ты начинаешь вспоминать: вчера кто-то «поправил» скрипт, который раскладывает права на шары. Скрипт лежит прямо на сервере, называется `Set-FolderAcl.ps1`, рядом валяется копия `Set-FolderAcl_old.ps1` и файл `Set-FolderAcl_НОВЫЙ(2).ps1`. Какая из них рабочая — непонятно. Правки вносились прямо на FS01, блокнотом, в 19:40, и что именно там поменяли — никто не знает.

Знакомая картина? Именно так выглядит администрирование без версионирования. **Git** — это система контроля версий (VCS, Version Control System). Она хранит всю историю изменений файлов, позволяет вернуться к любой версии, показывает, кто и когда изменил конкретную строку, и даёт безопасный способ вносить правки вдвоём, не затирая работу друг друга.

После этой главы ты будешь уметь: создать репозиторий для своих скриптов и положить его на сервер стенда, работать с ветками, выкатывать изменения через отдельную ветку и **pull request** (PR, запрос на слияние), проводить **code review** (разбор чужого кода перед слиянием), откатывать сломанный коммит одной командой и отвечать на вопрос «кто это сделал» за две минуты вместо двух часов.

Для L2 это не «модно, потому что DevOps», а конкретная экономия нервов: у поддержки скапливаются десятки скриптов (массовое создание учёток, чистка логов, отчёты), и все они рано или поздно ломаются. Git превращает «кто-то что-то поменял» в «вот коммит, вот автор, вот дифф, откатываем».

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Git — распределённая система. Это значит, что у каждого участника есть **полная копия истории** в скрытой папке `.git`. Нет «главного сервера, где живёт правда»: сервер (bare-репозиторий) — просто точка обмена.

Три состояния файла в рабочей копии:

```text
 Рабочая копия          Индекс (staging)        Локальный репозиторий      Удалённый репозиторий
 (что на диске)         (.git/index)            (.git/objects)             (bare, на UBU01)

   правишь     --git add-->  подготовил  --git commit-->  зафиксировал  --git push-->  отправил
       ^                          |                            |                             |
       |                          |                            +---- git fetch/pull <-------+
       +------ git checkout/restore ----+                    (получить чужое)
```

**Объекты.** Git хранит не «разницу между версиями», а снимки: **blob** (содержимое файла), **tree** (структура папок), **commit** (снимок дерева + автор + дата + ссылка на родительский коммит). Коммиты образуют граф (DAG). Из-за этого откат — это просто переезд указателя.

**Ссылки.** Ветка (`main`, `feature/acl-fix`) — это файл, в котором лежит SHA-1/SHA-256 коммита. «Создать ветку» = записать один хеш. `HEAD` — указатель на текущую ветку.

**Ветки и слияние.**

```text
      A---B---C  main
           \
            D---E  feature/acl-fix        <- git merge feature/acl-fix из main

   fast-forward: если main не двигался, указатель просто переезжает на E
   merge commit: если main двигался (появился C), создаётся коммит M с двумя родителями

      A---B---C-------M  main
           \         /
            D-------E    feature/acl-fix
```

**Rebase** — альтернатива merge: коммиты D и E «переписываются» поверх C. История линейная и красивая, но хеши меняются — на общей ветке rebase делать нельзя.

**Pull request (PR) / Merge request (MR).** Ветку пушат на сервер, в веб-интерфейсе (Gitea, GitLab, GitFlic) открывают PR: «вот мои изменения, посмотрите». Ревьюер читает дифф построчно, оставляет комментарии, просит правки, апрувит. Только после апрува нажимается Merge. На сервере включают **protected branch** — правило «в `main` напрямую пушить нельзя».

**Транспорт и порты.** SSH — 22/tcp, HTTPS — 443/tcp, старый `git://` — 9418/tcp (не использовать: без аутентификации и шифрования). Git работает на прикладном уровне, модель OSI тут нужна только чтобы помнить: если `git clone` висит — сначала проверяй `ssh -T user@host` и firewall.

**Где это в общей картине.** Репозиторий со скриптами — «единственный источник правды» для инфраструктурного кода. Дальше из него растёт CI (урок 87): пуш → линтер → запуск → деплой. На стенде L2 форжа ещё нет (GIT01 появится только на DevOps-треке), поэтому сервер Git поднимаем на UBU01.

## 3. Аналогия из жизни

Представь конструкторское бюро. Есть основной альбом чертежей (`main`) — по нему на заводе делают детали. Инженер не рисует прямо в альбоме: он берёт **кальку** (создаёт ветку), переносит на неё нужный лист, правит. Потом приносит кальку главному конструктору: «смотри, вот тут я поменял допуск» — это **pull request**. Главный конструктор смотрит, говорит «тут ошибка, перечерти» (**code review**, запрос правок). Инженер перечерчивает, получает подпись «в производство» (**approve**), и лист вшивают в основной альбом (**merge**). А ещё в бюро есть архив: любой лист можно достать в редакции десятилетней давности и посмотреть, чья подпись стоит в углу (**git blame**).

Где аналогия ломается: Git сливает изменения **построчно**, а не «листами целиком», поэтому двое могут править один и тот же файл в разных местах — и конфликта не будет. А ещё кальку нельзя «перебазировать» на новую версию альбома с сохранением подписи, а `git rebase` — можно (и подпись при этом, то есть хеш коммита, изменится).

## 4. Практика и команды

Ниже — минимум, который нужен каждый день. Windows-команды выполняются в PowerShell на WIN11-CL01, Linux — в SSH-сессии на UBU01.

**Установка и проверка**

```powershell
winget install --id Git.Git -e
git --version
```

```bash
sudo apt update && sudo apt install -y git
git --version
```

`winget` — штатный менеджер пакетов Windows. Если `winget` недоступен, легальный установщик Git for Windows берётся с git-scm.com (`[ПРОВЕРИТЬ]` актуальную версию и доступность зеркала из РФ; в бою часто используют пакет из внутреннего репозитория компании).

**1. Идентичность и настройки**

```bash
git config --global user.name "Ivan Ivanov (adm.student)"
git config --global user.email "adm.student@corp.vektor.lab"
git config --global init.defaultBranch main
git config --global --list --show-origin
```

`--global` пишет в `~/.gitconfig` (на Windows — `C:\Users\<user>\.gitconfig`). `--show-origin` показывает, из какого файла взято значение — незаменимо, когда «настройка есть, а не работает». Имя и почта попадают в каждый коммит, поэтому «Administrator <Administrator@PC>` — плохая подпись, по ней потом не найдёшь автора.

**2. Создать серверный (bare) репозиторий и клонировать**

```bash
# на UBU01
sudo mkdir -p /srv/git && sudo chown adm.student:adm.student /srv/git
git init --bare --initial-branch=main /srv/git/infra-scripts.git
ls /srv/git/infra-scripts.git
```

```text
HEAD  config  description  hooks  info  objects  refs
```

Bare-репозиторий — «голая» копия без рабочих файлов, только `.git`-содержимое: она и есть сервер. `--initial-branch=main` задаёт имя главной ветки (git ≥ 2.28). Дальше с клиента:

```powershell
git clone adm.student@10.10.10.30:/srv/git/infra-scripts.git C:\Git\infra-scripts
```

Первый коннект спросит про fingerprint хоста — отвечаешь `yes`. Аутентификация — по SSH-паролю (наш учебный `Lab#2026-vektor`); в бою — ключи, а пароль на Git-сервере отключён.

**3. `git status` — где я**

```bash
git status -sb
```

```text
## main...origin/main
 M powershell/Set-FolderAcl.ps1
?? bash/log-scan.sh
```

`## main...origin/main` — ветка и её удалённый аналог. `M` — файл изменён и не в индексе, `??` — Git его вообще не отслеживает. Проверяй `status` перед каждым `commit`: половина «магических» проблем — это забытый `git add`.

**4. `git add` — положить в индекс**

```bash
git add powershell/Set-FolderAcl.ps1
git add -p bash/log-scan.sh      # по кускам, с вопросом y/n на каждый
git add .                        # всё из текущей папки
```

`-p` (patch) — самый полезный режим: Git показывает по одному фрагменту и спрашивает `Stage this hunk [y,n,q,a,d,s,?]`. Позволяет не тащить в коммит случайную отладку.

**5. `git commit` и `--amend`**

```bash
git commit -m "acl: вернуть GG-HR права Modify на \\FS01\HR"
git commit --amend --no-edit      # дописать забытый файл в последний коммит
```

`--amend` переписывает **последний** коммит. Правило: amend допустим только до `push`. После пуша в общую ветку — только новый коммит или `revert`.

**6. `git log` и `git show` — история**

```bash
git log --oneline --graph --all --decorate -15
```

```text
* 9f1c2ab (HEAD -> main, tag: v1.0, origin/main) acl: вернуть GG-HR
* 3b7e001 Merge branch 'feature/acl-cleanup'
|\
| * 5d2a118 acl: переименовать группу
|/
* 1a0f4c3 init: скрипты из уроков 82-84
```

`--graph` рисует ветвление, `--all` — все ветки, `--decorate` — метки и `origin`. `git show 5d2a118` покажет сам дифф коммита. Это первое, что открываешь, когда «сломалось после вчерашнего».

**7. `git diff` — что именно изменилось**

```bash
git diff                            # рабочая копия vs индекс
git diff --staged                   # индекс vs последний коммит
git diff main...origin/feature/acl-fix   # вся ветка против main (то, что увидит ревьюер в PR)
git diff --name-only --diff-filter=U     # файлы с неразрешённым конфликтом
```

Три точки `...` — сравнение от точки ветвления, то есть только то, что принесла ветка. Именно это показывает веб-интерфейс PR.

**8. Ветки**

```bash
git switch -c feature/acl-fix
git branch -vv
git switch main
git branch -d feature/acl-fix          # удалить локально (только если слита)
git push origin --delete feature/acl-fix  # удалить на сервере
```

`switch -c` = создать ветку + переключиться. Смотри `-vv`: он показывает, за каким коммитом и каким remote следит каждая ветка.

**9. Remote, fetch, pull, push**

```bash
git remote -v
git fetch --prune
git pull --ff-only
git push -u origin feature/acl-fix
```

```text
origin  adm.student@10.10.10.30:/srv/git/infra-scripts.git (fetch)
origin  adm.student@10.10.10.30:/srv/git/infra-scripts.git (push)
```

`fetch` забирает изменения, не трогая твои файлы; `pull` = `fetch` + `merge` (или rebase). `--ff-only` запрещает pull, если он потребует merge-коммита: так ты заметишь, что ветка разошлась, и не создашь «случайный» merge. `--prune` чистит локальные ссылки на удалённые ветки, которых уже нет. `-u` один раз связывает локальную ветку с удалённой.

**10. `git merge` и разрешение конфликта**

```bash
git switch main
git merge --no-ff feature/acl-fix
```

```text
Auto-merging powershell/Set-FolderAcl.ps1
CONFLICT (content): Merge conflict in powershell/Set-FolderAcl.ps1
Automatic merge failed; fix conflicts and then commit the result.
```

Конфликт — это не ошибка, а «Git не угадал». В файле появляются маркеры:

```powershell
<<<<<<< HEAD
$Group = 'GG-HR'
=======
$Group = 'GG-HR-Users'
>>>>>>> feature/acl-fix
```

Правишь вручную (оставляешь нужное, маркеры удаляешь), затем `git add <файл>` и `git commit` (сообщение Git подставит сам). Отменить всё: `git merge --abort`.

**11. `revert` против `reset`**

```bash
git revert --no-edit 5d2a118
git reset --soft HEAD~1     # снять последний коммит, оставив изменения в индексе
git reset --hard HEAD~1     # ВНИМАНИЕ: уничтожает изменения в рабочей копии
```

`revert` создаёт **новый** коммит, отменяющий старый — безопасно для уже опубликованной истории. `reset` переписывает историю — только локально, до пуша. `--hard` теряет незакоммиченную работу безвозвратно.

**12. `git stash` — «отложить в сторону»**

```bash
git stash push -m "отладка acl"
git stash list
git stash pop
```

```text
stash@{0}: On main: отладка acl
```

Классика: правил скрипт, прилетела срочная заявка, нужно переключиться на другую ветку с чистыми руками. `pop` возвращает и удаляет из стека, `apply` — возвращает и оставляет.

**13. Кто это сделал: `blame`, `log -S`, `bisect`**

```bash
git blame -L 1,30 powershell/Set-FolderAcl.ps1
git log -S "GG-HR-Users" --oneline     # в каком коммите появилась/исчезла строка
git bisect start
git bisect bad
git bisect good 1a0f4c3
git bisect reset
```

`blame` показывает для каждой строки коммит и автора. `git log -S` (pickaxe) ищет коммиты, где менялось **число вхождений** строки — это быстрее, чем читать диффы. `bisect` — бинарный поиск «между хорошим и плохим коммитом»: помечаешь коммиты `good`/`bad`, Git переключает рабочую копию, ты тестируешь; на 100 коммитах — 7 проверок вместо 100.

**14. Теги — метки релизов**

```bash
git tag -a v1.0 -m "первая версия набора скриптов"
git push origin v1.0
```

Аннотированный тег хранит автора, дату и сообщение. Так фиксируют «эту версию скриптов проверяли и применяли на FS01 10.03».

**GUI.** На Windows удобно смотреть диффы в VS Code (`Ctrl+Shift+G` — панель Source Control, кликом по файлу открывается построчный diff) или в веб-интерфейсе Gitea/GitLab. Командную строку это не отменяет: GUI показывает то же самое, но хуже объясняет, что происходит.

## 6. Ошибки новичков и безопасность

1. **Секреты в репозитории.** Пароль от сервисной учётки, токен Telegram-бота или ключ API, вписанные в скрипт, остаются в истории Git **навсегда** — даже если следующим коммитом удалить строку, она видна в `git log -p`. *Как правильно:* параметры и секреты — в переменные окружения, в файл вне репозитория, в хранилище секретов; `.gitignore` для `*.env`, `secrets/`, `*.pfx`. Если секрет уже уехал — не «удалять файл», а **менять пароль/токен** и только потом чистить историю.

2. **`git push --force` в общую ветку.** Перезаписывает историю на сервере: чужие коммиты, которые ты не видел, исчезают. *Как правильно:* `--force-with-lease` (сработает только если никто ничего не пушил после тебя), а лучше — вообще не force'ить `main`.

3. **Правки «по-быстрому» прямо на сервере.** Поправил скрипт на FS01 блокнотом — и репозиторий больше не описывает реальность. Через месяц никто не знает, какая версия «настоящая». *Как правильно:* правка только через репозиторий → ветка → review → выкатка. Файлы на сервере — результат работы скрипта, а не место для редактирования.

4. **Коммит «всё сразу».** Один коммит на 800 строк, где одновременно переименование, рефакторинг и багфикс. Ревьюер такое не читает, а если и читает — не находит ошибку. *Как правильно:* атомарные коммиты, одна логическая правка = один коммит, сообщение в императиве: «acl: вернуть GG-HR».

5. **`git reset --hard` на рабочей копии с несохранёнными изменениями.** Молча стирает всё, что не закоммичено. Восстановления нет. *Как правильно:* сначала `git stash push -m "..."`, и только потом эксперименты; `reset --hard` — осознанно и с проверенным `git status`.

6. **Коммиты от имени `Administrator`.** Атрибуции нет, `git blame` показывает безликого «Administrator@WIN-XXXX». *Как правильно:* у каждого инженера свой `user.name`/`user.email`, у сервисных аккаунтов — отдельные имена вида `svc-automation`.

7. **CRLF против LF.** Скрипт `.sh`, сохранённый в Windows, падает на Ubuntu с `/bin/bash^M: bad interpreter`. *Как правильно:* `.gitattributes` с `* text=auto`, `*.sh text eol=lf`, `*.ps1 text eol=crlf`.

8. **Нет защиты `main`.** Любой, у кого есть доступ, пушит напрямую, review существует только на словах. *Как правильно:* protected branch + обязательный апрув, у сервисных аккаунтов — минимальные права.

### Безопасность

- **Репозиторий — не место для персональных данных.** Скрипты экспорта из AD (урок 82) генерируют файлы с ФИО, должностями, логинами сотрудников — это **персональные данные** (152-ФЗ). ## 7. Вопросы на собеседовании

**1. Чем `merge` отличается от `rebase` и когда что использовать?**

При `merge` история сохраняется как есть и создаётся merge-коммит с двумя родителями. При `rebase` коммиты ветки «переписываются» поверх целевой ветки: история становится линейной, но **хеши меняются**. Merge безопасен для общей ветки, rebase — только для своей локальной, до пуша. Типовая практика: `feature/*` перед PR делают `git rebase main`, чтобы ревьюер видел чистую историю; в `main` — merge через PR.
*Что хочет услышать интервьюер:* что кандидат понимает необратимость rebase и не советует «ребейзить общий main».
*Красный флаг:* «rebase всегда лучше, merge — для нубов» или «разницы нет».

**2. Что такое pull request и зачем code review в репозитории инфраструктурных скриптов?**

PR — это предложение влить ветку в основную, оформленное на сервере: дифф, обсуждение, апрув, merge. В инфраструктуре review критичен, потому что скрипт выполняется с высокими правами на множестве машин, и ошибка стоит дорого (пример: опечатка в имени группы → у HR пропал доступ к папке). Review ловит опечатки, хардкод путей и паролей, опасные конструкции (`rm -rf`, `Remove-Item -Recurse` без проверки пути) и распространяет знание о скрипте на команду.
*Что хочет услышать интервьюер:* понимание, что review — про снижение риска и передачу знаний, а не про бюрократию.
*Красный флаг:* «у нас один админ, review не нужен».

**3. Как откатить сломанный коммит, который уже уехал в общий `main`?**

`git revert <sha>` — создаёт новый коммит с обратными изменениями, история сохраняется, безопасно для всех, у кого уже есть эта ветка. `git reset --hard` в этом случае нельзя: он переписывает историю, и у коллег останутся «фантомные» коммиты; после force-push они получат конфликты и потеряют работу. Порядок: revert → ветка → PR → review → merge → выкатка на серверы.
*Что хочет услышать интервьюер:* чёткое «revert для опубликованного, reset для локального».
*Красный флаг:* «сделаю reset --hard и force push, так же быстрее».

**4. Скрипт сломался, но непонятно, в каком коммите. Как найти?**

Три инструмента: `git log --oneline -- <файл>` — когда файл менялся, с сообщениями; `git blame -L <диапазон> <файл>` — кто и каким коммитом добавил конкретную строку; `git log -S "<строка>"` — в каких коммитах строка появлялась/исчезала. Если непонятно даже, какой коммит плохой, а их много — `git bisect`: помечаешь заведомо хороший и заведомо плохой коммит, Git делит диапазон пополам, ты проверяешь каждый шаг и за ~log2(N) шагов находишь виновника.
*Что хочет услышать интервьюер:* что кандидат ищет причину инструментами, а не «спрашивает в чате, кто трогал».
*Красный флаг:* «посмотрю дату изменения файла через ls».

**5. Что делать, если в репозиторий случайно закоммитили пароль?**

Считать пароль скомпрометированным и **немедленно сменить** — это первое и главное. Потом убрать его из кода (переменные окружения, хранилище секретов), добавить файл в `.gitignore` и, если репозиторий публичный или доступ широкий, вычистить историю (`git filter-repo` [ПРОВЕРИТЬ актуальность инструмента] или BFG) с последующим force-push и оповещением всех, у кого есть клоны. Удаление файла новым коммитом историю не чистит.
*Что хочет услышать интервьюер:* «сначала ротация пароля, потом чистка истории» — именно в таком порядке.
*Красный флаг:* «просто удалю файл следующим коммитом и всё».

## 8. Источники (официальная документация)

- **git-scm.com** — официальный сайт Git. Книга «Pro Git» (бесплатная, на русском тоже есть): главы 2 «Git Basics» и 3 «Git Branching». Встроенная справка: `git help <команда>`. Поиск: `pro git branching merging rebase`.
- **git-scm.com/docs** — справочник по командам (`git-merge`, `git-revert`, `git-bisect`, `gitattributes`). Поиск: `gitattributes text eol`.
- **docs.gitea.com** — документация Gitea: разделы «Installation with binary», «Configuration Cheat Sheet», «Protected branches». Поиск: `gitea installation binary systemd`. `[ПРОВЕРИТЬ]` актуальную версию и точные флаги `gitea admin user create`.
- **docs.gitlab.com** — раздел «Merge requests» и «Protected branches» (пригодится на DevOps-треке с GIT01). Поиск: `gitlab protected branches merge request approvals`.
- **learn.microsoft.com** — материалы по работе с Git в Visual Studio / Azure DevOps. Поиск: `git in visual studio microsoft learn`. `[ПРОВЕРИТЬ]` точное название раздела.
- **ubuntu.com / help.ubuntu.com** — установка пакетов, `apt`, управление службами systemd. Поиск: `ubuntu server install git apt`.
- Российские площадки для размещения кода (импортозамещение): GitFlic, GitVerse — `[ПРОВЕРИТЬ]` актуальные условия бесплатных тарифов и наличие в реестре российского ПО.
