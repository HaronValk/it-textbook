# Прокси и фильтрация трафика: Squid, веб-фильтры, анализ логов, SSL-инспекция

## 1. Введение (зачем это нужно в реальной работе)

**Тикет #4127.** Пользователь: Петрова (WIN10-CL02, HR). Текст: «Открываю любой сайт — браузер требует логин и пароль, ввожу доменный пароль — пишет 407 Proxy Authentication Required. Утром всё работало». Срочность: высокая, HR не может зайти на портал кадрового учёта.

Дальше вы выясняете: ночью коллега «оптимизировал» права на файл с паролями прокси, и Squid перестал его читать. Внешне это выглядит как «интернет сломался у одного человека», а на деле — сломанный сервис на шлюзе.

Прокси в корпоративной сети — это не «одна программа для экономии трафика», а точка контроля: кто ходил, куда, когда, сколько скачал, почему получил отказ. Такие заявки приходят в поддержку L2 постоянно: «сайт не открывается», «просит пароль», «слишком медленно», «а почему у соседа открывается, а у меня нет». После этой главы вы будете уметь: поднять Squid на шлюзе, закрыть доступ по доменам, IP и группам, читать `access.log` и `cache.log` и отвечать на вопрос «что именно произошло с этим пользователем в 14:37». Плюс поймёте, что такое SSL-инспекция, зачем она нужна, почему ломает приложения и почему её нельзя включать «на всякий случай».

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Прокси-сервер** — посредник прикладного уровня (L7): клиент открывает TCP-соединение не к сайту, а к прокси, и просит его сходить на сайт вместо себя. Есть три режима, которые надо различать:

- **Прямой (forward) прокси явный** — клиент знает адрес прокси (настройка в браузере / GPO / PAC-файл). HTTP-запрос идёт в виде `GET http://example.com/ HTTP/1.1` прямо прокси. Порт по умолчанию у Squid — **3128**.
- **Прозрачный прокси (transparent/intercept)** — клиент ничего не настраивает, трафик на 80/443 молча перенаправляется на прокси правилом nftables/iptables на шлюзе. На стенде это возможно только если клиент ходит в интернет через GW01 (то есть его default gateway — 10.10.10.3). По умолчанию на стенде шлюз — 10.10.10.2 (NAT VMware), поэтому прозрачный режим — отдельное упражнение, а не база.
- **Обратный (reverse) прокси** — стоит перед своими веб-серверами, публикует их наружу (типичный сценарий для WEB01 в DMZ).

Плюс отдельный зверь — **DNS-фильтрация**: подменяем ответ DNS, чтобы домен не резолвился. Она видит только имя домена, не видит ни URL, ни содержимое, и обходится сменой DNS или IP. Прокси видит полный URL по HTTP, поэтому «фильтр на прокси» гибче, но дороже по ресурсам.

**Как Squid устроен.** Один процесс `squid`, событийная модель, никакой многопоточности «на запрос». Рядом — helper-процессы: авторизация (`basic_ncsa_auth`, `squid_ldap_auth`, Kerberos), переписывание URL, генератор сертификатов для SSL-bump. Логика доступа — это ACL (списки контроля доступа) + правила `http_access`. **Правила проверяются сверху вниз, срабатывает первое совпадение**, поэтому порядок строк — это и есть политика. В конце обязателен `http_access deny all`.

Типовая цепочка HTTP-запроса через прокси:

```text
[WIN11-CL01 10.10.10.xxx]                      [GW01 10.10.10.3]                  [сайт]
        |                                              |                              |
        |-- TCP 3128 -->  GET http://site/ HTTP/1.1 ->|                              |
        |                                              |-- ACL: src? user? domain?    |
        |                                              |   deny -> 403 + access.log   |
        |                                              |   allow -> соединение на 80 --|-->|
        |<-- 200 OK + Via: 1.1 gw01 (squid/5.x) -------|<-- ответ --------------------|<--|
        |                                              | access.log: TCP_MISS/200 ... |
```

**HTTPS и CONNECT.** По HTTPS прокси не может «прочитать запрос» — браузер просит туннель: метод `CONNECT example.com:443`, прокси открывает TCP до сайта и дальше просто перекладывает байты. В логе вы видите **домен и объём**, но не URL и не содержимое. Это `TCP_TUNNEL/200`.

**SSL-инспекция (SSL bump, MITM).** Если нужно видеть содержимое HTTPS, прокси встаёт в середину: подменяет сертификат сайта своим, подписанным **своим внутренним CA**, который предварительно установлен в доверенные на клиентах. Режимы Squid `ssl_bump`: `peek` (посмотреть SNI и отпустить), `stare`, `splice` (не расшифровывать), `bump` (расшифровать и перевыпустить сертификат), `terminate`.

```text
Без инспекции:   Клиент <== TLS(сайт) ==> Squid(тупо туннель) <== TLS ==> Сайт
С bump:          Клиент <== TLS(CA Вектора!) ==> Squid(расшифровал) <== TLS ==> Сайт
                                              |
                                     видит URL, заголовки, файлы
```

Ломается это на **certificate pinning** (приложение жёстко ждёт конкретный сертификат), на клиентах без установленного CA и на сайтах, которые сами не разрешают MITM. Отсюда практика: `ssl_bump splice` для банков/госуслуг/медицины и `bump` только для нужных категорий. И юридическая часть: скрытый перехват переписки сотрудников — это не «настройка сети», это вопросы трудового договора, локальных актов и 152-ФЗ; в нормальной компании о фильтрации и инспекции сотрудников уведомляют.

## 3. Аналогия из жизни

Прокси — это вахтёр на проходной бизнес-центра. Вы не идёте в чужой офис напрямую: вы говорите вахтёру «мне в 305-й», он смотрит список (ACL), уточняет, кто вы (аутентификация), и либо провожает, либо разворачивает. В журнале на стойке (это `access.log`) остаётся запись: кто, когда, куда, на сколько минут, пустили или нет.

Прозрачный прокси — тот же вахтёр, но двери устроены так, что мимо него пройти физически нельзя, и спрашивать адрес не нужно.

SSL-инспекция — вахтёр, которому разрешили вскрывать каждую посылку, читать содержимое и запечатывать обратно **своей** пломбой. Получатель посылку принимает, только если ему заранее сказали, что пломба Вектора — законная (сертификат CA в доверенных). Если у получателя в инструкции написано «пломба должна быть именно от отправителя, номер сверяю» — он вскрытую посылку отвергнет (certificate pinning), и вы получите заявку «сайт не открывается, ошибка сертификата».

Аналогия перестаёт работать в одном месте: вахтёр видит лицо и пропуск, а прокси часто не знает человека вообще — только IP-адрес, который на DHCP-стенде сегодня принадлежит одному сотруднику, а завтра другому.

## 4. Практика и команды

**1. Установка и проверка сервиса на GW01 (Debian 12).**

```bash
sudo apt update && sudo apt install -y squid apache2-utils
systemctl status squid --no-pager
ss -tlnp | grep 3128
```

`apache2-utils` нужен ради утилиты `htpasswd` (файл логинов/паролей). Ожидаемый вывод: `Active: active (running)`, и строка `LISTEN 0 4096 *:3128 *:* users:(("squid",pid=812,fd=12))`. Если порта нет — смотрите `journalctl -u squid -n 50`.

**2. Проверка и перечитывание конфигурации.**

```bash
sudo squid -k parse          # только проверка синтаксиса, ничего не перезапускает
sudo squid -k reconfigure    # применить конфиг без разрыва соединений
sudo squid -k rotate         # прокрутить логи
```

`parse` — первое, что делают после правки `squid.conf`. Если в конце нет строк с `FATAL`, конфиг синтаксически валиден (предупреждения `WARNING` — не смертельно). `reconfigure` быстрее и мягче, чем `systemctl restart`.

**3. Тест с Linux-клиента (UBU01).**

```bash
curl -x http://10.10.10.3:3128 -I http://example.com
curl -x http://10.10.10.3:3128 -U 'ivanov:Lab#2026-vektor' -I http://example.com
curl -x http://10.10.10.3:3128 -o /dev/null -s -w '%{http_code}\n' http://example.com
```

`-x` — адрес прокси, `-U` (большая) — логин/пароль **прокси** (маленькая `-u` — для самого сайта), `-I` — только заголовки, `-w '%{http_code}'` — печатать только код ответа. Пароль в кавычках обязателен: `#` в bash начинает комментарий. В ответе ищите `Via: 1.1 gw01.vektor.lab (squid/5.x)` — значит, трафик реально прошёл через прокси.

**4. Настройка клиента Windows (GUI).**

`Пуск → Параметры → Сеть и Интернет → Прокси → Настройка прокси вручную → Изменить`: адрес `10.10.10.3`, порт `3128`, в исключениях `*.vektor.lab;10.10.10.*`. Это настройка WinINET — её используют Edge, Chrome, IE. Firefox по умолчанию живёт своей жизнью: `Settings → Network Settings → Manual proxy configuration`.

**5. Проверка прокси в Windows через PowerShell и netsh.**

```powershell
Get-ItemProperty 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings' |
    Select-Object ProxyEnable, ProxyServer, ProxyOverride
netsh winhttp show proxy
curl.exe -x http://10.10.10.3:3128 -I http://example.com
```

`ProxyEnable=1` и `ProxyServer="10.10.10.3:3128"` — системный прокси включён. `netsh winhttp` показывает **другой** прокси — WinHTTP, его используют службы (обновления, часть фонового ПО), а не браузеры; путать эти два уровня — классическая ошибка. И в PowerShell пишите именно `curl.exe`, иначе вы вызовете алиас `Invoke-WebRequest`.

**6. Анатомия `access.log`.**

```bash
sudo tail -f /var/log/squid/access.log
# 1774000123.456  187 10.10.10.100 TCP_MISS/200 4821 GET http://example.com/ ivanov HIER_DIRECT/93.184.216.34 text/html
```

Поля: время (epoch) · длительность, мс · IP клиента · результат/код · байт · метод · URL · пользователь · иерархия/куда ходили · тип контента. Что смотреть: `TCP_HIT` (из кэша), `TCP_MISS` (пошли на сайт), `TCP_TUNNEL/200` (HTTPS-туннель), `TCP_DENIED/403` (запретили по ACL), `TCP_DENIED/407` (не прошла аутентификация).

**7. Топ доменов за сегодня.**

```bash
sudo awk '{print $7}' /var/log/squid/access.log \
  | sed -E 's#^[a-z]+://##; s#/.*##; s#:[0-9]+$##' \
  | sort | uniq -c | sort -rn | head -10
```

`sed` снимает схему (`http://`), путь и порт, оставляя чистое имя домена. По выводу сразу видно «дыру» в политике: если в топе облачное хранилище на 40 ГБ — пора либо разрешать осознанно, либо блокировать.

**8. Кто и что получил отказ.**

```bash
sudo awk '$4 ~ /^TCP_DENIED/ {print $3, $7}' /var/log/squid/access.log \
  | sort | uniq -c | sort -rn | head -20
sudo awk '{print $8}' /var/log/squid/access.log | sort | uniq -c | sort -rn | head
```

Первая команда — отказы в разрезе IP + URL, вторая — активность по пользователям (поле 8). Именно так отвечают на вопрос «а меня почему не пускает».

**9. Медленные запросы и объём трафика по клиентам.**

```bash
sudo awk '$2 > 2000 {printf "%6d ms  %-15s %s\n", $2, $3, $7}' /var/log/squid/access.log | sort -rn | head
sudo awk '{s[$3]+=$5} END {for (i in s) printf "%.1f MB  %s\n", s[i]/1048576, i}' /var/log/squid/access.log | sort -rn | head
```

Отбираем запросы дольше 2 секунд (`$2`) и суммируем байты (`$5`) по IP. Это первый шаг, когда жалуются «интернет тормозит»: разница между «медленно у всех» и «медленно у одного, потому что он качает 40 ГБ».

**10. HTTPS: что видно без расшифровки.**

```bash
sudo grep CONNECT /var/log/squid/access.log | tail -5
openssl s_client -proxy 10.10.10.3:3128 -connect example.com:443 -servername example.com </dev/null
```

`CONNECT example.com:443` в логе даёт домен и объём — этого достаточно для 95% разборов. `openssl s_client -proxy` проверяет, что туннель устанавливается и сертификат сайта отдаётся нормально (без подмены). Если нужен «живой» перехват пакетов — `sudo tcpdump -i any -n port 3128` на GW01.

**11. Проверка блокировки по имени домена (формулировка ACL).**

```bash
curl -x http://10.10.10.3:3128 -U 'ivanov:Lab#2026-vektor' \
     -o /dev/null -s -w '%{http_code}\n' https://www.tiktok.com
```

`403` — ACL отработал, `200` — домен в обход политики. `dstdomain .tiktok.com` закрывает и сам домен, и поддомены; `dstdomain tiktok.com` — только точное имя.

### Шаги

1. **GW01.** `sudo apt update && sudo apt install -y squid apache2-utils`. Ожидаемо: пакет установлен, `systemctl status squid` → `active (running)`, `ss -tlnp | grep 3128` показывает LISTEN.

3. **GW01.** Приведите рабочую часть конфига к виду:

```text
visible_hostname gw01.vektor.lab
dns_nameservers 10.10.10.10

http_port 3128

acl localhost src 127.0.0.1/32 ::1
acl localnet src 10.10.10.0/24
acl SSL_ports port 443
acl Safe_ports port 80
acl Safe_ports port 443
acl Safe_ports port 8080
acl CONNECT method CONNECT

auth_param basic program /usr/lib/squid/basic_ncsa_auth /etc/squid/passwd
auth_param basic realm Vektor proxy
auth_param basic credentialsttl 8 hours
acl authenticated proxy_auth REQUIRED

acl blocked_sites dstdomain "/etc/squid/blocked.txt"
acl hr_user proxy_auth -i petrova
acl hr_extra dstdomain .youtube.com

http_access allow localhost manager
http_access deny manager
http_access deny !Safe_ports
http_access deny CONNECT !SSL_ports
http_access deny blocked_sites
http_access deny hr_extra hr_user
http_access allow authenticated
http_access deny all

access_log daemon:/var/log/squid/access.log squid
cache deny all
coredump_dir /var/spool/squid
```

`cache deny all` отключает кэширование — для лабы так проще, всё видно в логах. В реальной работе кэш включают через `cache_mem` и `cache_dir`.
4. **GW01.** Создайте список блокировок и пароли:

```bash
sudo tee /etc/squid/blocked.txt >/dev/null <<'EOF'
.tiktok.com
.twitch.tv
EOF
sudo htpasswd -c /etc/squid/passwd ivanov      # пароль Lab#2026-vektor
sudo htpasswd    /etc/squid/passwd petrova     # тот же пароль
sudo chown proxy:proxy /etc/squid/passwd
sudo chmod 640 /etc/squid/passwd
```

`-c` создаёт файл (только первый раз!), без `-c` — добавляет пользователя. Права `proxy:proxy 640` обязательны: Squid работает под пользователем `proxy`. **Не используйте `htpasswd -B`** (bcrypt) — `basic_ncsa_auth` его не понимает.
5. **GW01.** `sudo squid -k parse` (в конце нет `FATAL`), затем `sudo squid -k reconfigure`. Ожидаемо: `ss -tlnp | grep 3128` по-прежнему слушает, в `/var/log/squid/cache.log` нет ошибок чтения `passwd`.
6. **UBU01.** Проверьте отказ и успех:

```bash

# ожидаемо: 407 Proxy Authentication Required

# ожидаемо: 403

curl -x http://10.10.10.3:3128 -U 'ivanov:Lab#2026-vektor' -o /dev/null -s -w '%{http_code}\n' https://www.youtube.com

Ожидаемо: страница открылась, браузер один раз спросил логин/пароль (учётка `ivanov` — это **учётка прокси**, а не доменная). Проверьте `Get-ItemProperty 'HKCU:\...\Internet Settings' | Select ProxyEnable, ProxyServer`.
9. **GW01.** Разберите логи: `sudo tail -20 /var/log/squid/access.log`. Найдите строки с `10.10.10.100` (WIN11-CL01), `TCP_DENIED/407` (первый запрос без пароля) и `TCP_TUNNEL/200 CONNECT` (HTTPS). Выполните команды из пунктов 7–9 раздела 4, сохраните вывод в `stand-log.md`.

11. **DC01 (по желанию).** Раздайте настройку через GPO: `Group Policy Management` → создайте GPO `GPO-Proxy`, привяжите к OU `Компьютеры`, в `User Configuration → Preferences → Windows Settings → Registry` создайте элементы в `HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings`: `ProxyEnable` (REG_DWORD = 1), `ProxyServer` (REG_SZ = `10.10.10.3:3128`), `ProxyOverride` (REG_SZ = `*.vektor.lab;10.10.10.*`). Это позволяет рубить HTTPS по имени из TLS-handshake, не вскрывая шифр. Синтаксис `ssl::server_name` и порядок `ssl_bump`-строк `[ПРОВЕРИТЬ]` по документации Squid для вашей версии; если Squid не стартует — верните конфиг из бэкапа и сделайте `reconfigure`.

### Сломай и почини

**Пользователь:** petrova / WIN10-CL02.
**Что написал:** «Не открывается ни один сайт. Браузер просит логин и пароль, ввожу свой доменный — не пускает, потом пишет 407 Proxy Authentication Required. Утром работало».
**Срочность:** высокая (HR, портал кадрового учёта).

**Как воспроизвести поломку (на GW01, от имени root):**

```bash
sudo chown root:root /etc/squid/passwd
sudo chmod 600 /etc/squid/passwd
sudo squid -k reconfigure
```

Теперь файл паролей не читается пользователем `proxy`, хелпер аутентификации не может никого проверить, и **все** получают 407 — что и делает заявку реалистичной.

**Диагностика по шагам (строго в этом порядке):**

1. **Границы проблемы:** `curl -x http://10.10.10.3:3128 -I http://example.com` с UBU01. Если 407 у всех — проблема на сервисе, а не у Петровой.
2. **Жив ли сервис:** `systemctl status squid`, `ss -tlnp | grep 3128`. Слушает — значит, сеть и порт в порядке, копаем в аутентификацию.
3. **Что говорит лог клиента:** `sudo grep 'TCP_DENIED/407' /var/log/squid/access.log | tail -5`. Видим IP WIN10-CL02 и время — совпадает с обращением.
4. **Главный лог причин:** `sudo tail -50 /var/log/squid/cache.log`. Ищем строки про `basic_ncsa_auth` / `passwd`: типично `Permission denied` или `helper exited`.
5. **Проверка гипотезы:** `ls -l /etc/squid/passwd` → `-rw------- 1 root root`. Вот и корень: Squid работает под `proxy`.
6. **Проверка, что дело не в пароле:** `sudo htpasswd -vb /etc/squid/passwd petrova 'Lab#2026-vektor'` → `Password for user petrova correct.` Значит, содержимое файла цело и дело не в пароле.

**Решение:**

```bash
sudo chown proxy:proxy /etc/squid/passwd
sudo chmod 640 /etc/squid/passwd
sudo squid -k reconfigure
curl -x http://10.10.10.3:3128 -U 'petrova:Lab#2026-vektor' -I http://example.com   # 200 OK
```

**Ответ пользователю:** «Мария, добрый день. Проблема была на стороне прокси-сервера: после ночных работ у файла с учётными записями прокси сбились права доступа, и сервис не мог никого авторизовать. Права восстановили, доступ проверен — сайты и портал кадрового учёта открываются. Пожалуйста, закройте и откройте браузер (или Ctrl+F5), чтобы он не держал старую сессию. Если снова попросит пароль — напишите, разберёмся отдельно».

**Закрытие заявки:** в комментарии — «root cause: неверные права на /etc/squid/passwd после изменения владельца; fix: chown proxy:proxy, chmod 640, reconfigure; проверено curl с UBU01 и на рабочем месте пользователя». Категория — «Инфраструктура / прокси», привязка к проблемному изменению.

## 6. Ошибки новичков и безопасность

1. **Правило `http_access allow` поставлено выше `deny`** → запрет никогда не срабатывает, потому что срабатывает первое совпадение. Правильно: сначала `deny`-исключения для конкретных групп, потом общий `allow`, в конце `deny all`. После каждой правки — `squid -k parse`.
2. **Нет `http_access deny all` в конце** → открытый прокси. Через сутки его найдут сканеры, и ваш шлюз станет участником рассылки спама. Это авария масштаба компании.
3. **`acl localnet src` не соответствует реальной подсети** (например, оставили дефолтный RFC1918 целиком, включая 10.10.20.0/24 DMZ) → доступ получают те, кому не положено. Правильно: перечислить только 10.10.10.0/24.
4. **Права на `/etc/squid/passwd`** `root:root 600` → 407 у всех (наш кейс). Правильно: `proxy:proxy`, `640`, и не забыть проверить после любого «улучшения» прав.
5. **`htpasswd -B` (bcrypt)** → `basic_ncsa_auth` не понимает хэш, аутентификация всегда падает. Правильно: обычный `htpasswd` (crypt/MD5 APR1) или переход на LDAP/Kerberos-аутентификацию.
6. **Путаница WinHTTP и WinINET** → «я прописал прокси через netsh, а браузер всё равно напрямую». Правильно: `netsh winhttp` — для служб, GUI-настройка/реестр — для браузеров, Firefox — вообще отдельно.
7. **Прокси-аутентификация как доменная** → пользователь вводит пароль AD и получает 407. NCSA-файл — отдельная база логинов; для настоящего SSO нужен Kerberos/LDAP-хелпер (`squid_kerb_auth`, `squid_ldap_auth`).
8. **Включили `ssl_bump` на всё** без установки CA на клиентов → вал заявок «ошибка сертификата» в браузерах и мобильных приложениях, сломанные банк-клиенты и 1С-обмены. Правильно: `splice` для чувствительных категорий, `bump` — точечно, CA — через GPO.

**Безопасность.** Прокси с логированием — это сбор данных о поведении сотрудников: URL, время, объёмы. В боевой среде такие логи хранят ограниченно, доступ к ним — только у ответственных, а сотрудников уведомляют о фильтрации локальным актом (152-ФЗ, трудовое законодательство). SSL-инспекция — это полноценный MITM: перехват содержимого, включая пароли к внешним сервисам, если они не защищены дополнительно. Никогда не включайте `bump` «на весь интернет» без письменного решения и без исключений для банков, госуслуг и медицины. И никогда не делайте прокси «для удобства» открытым (`http_access allow all` + порт наружу) — это самая быстрая дорога к инциденту.

## 7. Вопросы на собеседовании

**1. Чем прозрачный прокси отличается от явного и какие у каждого минусы?**
Явный: клиент сам настроен на прокси, знает про него, поддерживает аутентификацию, легко логируется по пользователю, но требует конфигурации на всех устройствах (GPO/PAC) и ломается на устройствах без настроек. Прозрачный: клиент ничего не настраивает, трафик подхватывается на шлюзе правилом nftables/iptables, но аутентификация по логину фактически невозможна (нет обмена 407 в явном виде — точнее, он не будет обработан клиентом), ломается часть не-HTTP протоколов, и всё зависит от того, что клиент действительно ходит через шлюз. **Интервьюер хочет услышать:** понимание, что разница — в способе доставки трафика на прокси и в цене аутентификации. **Красный флаг:** «прозрачный — это когда без пароля, а явный — с паролем».

**2. Пользователь говорит «сайт не открывается». Ваши действия?**
Сначала уточнить: один сайт или все, один пользователь или все, что именно видит (код, текст ошибки, скриншот). Дальше: 1) смотреть `access.log` по IP/логину пользователя в нужное время — есть ли вообще его запросы; 2) если есть `TCP_DENIED/403` — вопрос политики ACL, смотреть какое правило сработало; 3) если `TCP_DENIED/407` — аутентификация, `cache.log`, права на `passwd`; 4) если записей нет — клиент не ходит через прокси (проверить настройки, WinHTTP vs WinINET, Firefox); 5) если `TCP_TUNNEL/200`, а у пользователя ошибка — проблема на стороне сайта/сертификата, проверять `openssl s_client -proxy`; 6) проверить воспроизводимость с другого клиента. **Хочет услышать:** дисциплину «сначала локализовать, потом гипотезы, лог — источник истины». **Красный флаг:** «перезапущу Squid, вдруг поможет».

**3. Что такое SSL-инспекция, зачем она и почему иногда ломает всё?**
Прокси в режиме bump расшифровывает TLS: клиенту отдаёт сертификат, подписанный внутренним CA, сам устанавливает отдельное TLS-соединение с сайтом. Нужна, чтобы видеть URL/содержимое HTTPS и фильтровать по категориям, а не только по домену. Ломается на certificate pinning (мобильные приложения, банки, некоторые обновляторы), на клиентах без CA в доверенных, на двусторонней аутентификации и на нестандартных протоколах поверх TLS. Лечится исключениями через `ssl_bump splice` и установкой CA через GPO. **Хочет услышать:** понимание MITM-природы, требований к CA на клиентах и практики исключений. **Красный флаг:** «SSL-инспекция — это просто галочка в Squid».

**4. Как вы посмотрите, кто съедает канал, по логам прокси?**
`awk` по `access.log`: сумма байт (поле 5) по IP клиента или по пользователю (поле 8), плюс топ доменов и топ медленных запросов (поле 2 — время в мс). Дальше — сопоставить IP с DHCP-арендой на DC01 или с логином из поля 8. Отдельно проверить, нет ли большого объёма через `TCP_TUNNEL` (HTTPS) — там URL не видно, только домен и байты. **Хочет услышать:** конкретные команды и понимание, что IP без привязки к DHCP-аренде ничего не значит. **Красный флаг:** «посмотрю в Zabbix» без понимания, что метрики интерфейса не показывают, кто именно качает.

**5. Прокси vs DNS-фильтрация vs NGFW — что выберете для 50 человек?**
DNS-фильтрация — дешево, ничего не настраивать на клиентах, но видит только домен, не видит URL и легко обходится сменой DNS (лечится блокировкой 53 наружу на шлюзе). Прокси — полный URL по HTTP, учёт по пользователю, гибкие ACL, отчёты, но требует настройки клиентов и не видит содержимое HTTPS без bump. NGFW — всё сразу и с категориями, но дорого и требует экспертизы. Для 50 человек с AD и одним шлюзом разумный минимум — Squid с ACL по группам плюс DNS-фильтр как страховка. **Хочет услышать:** сравнение по цене, трудозатратам и видимости, а не «берём самое дорогое». **Красный флаг:** «прокси устарел, всё решает только NGFW».
