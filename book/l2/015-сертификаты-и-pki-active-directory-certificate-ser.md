# Сертификаты и PKI: Active Directory Certificate Services, шаблоны, выдача, отзыв, автоподписка

## 1. Введение (зачем это нужно в реальной работе)

Тикет №4821. **Пользователь:** ivanov (бухгалтерия, WIN11-CL01). **Что написал:** «Здравствуйте! С утра не могу отправить отчёт: программа подписи пишет "Сертификат не найден или срок его действия истёк". Вчера всё работало, я ничего не трогал. Завтра сдавать, очень срочно». **Срочность:** высокая.

Пока ты работал на L1, сертификаты для тебя были «где-то в браузере». На L2 ты обнаружишь, что они висят на половине сервисов компании: HTTPS для внутреннего портала, 802.1X для Wi-Fi, VPN, RDP с TLS, подпись документов и отчётов в 1С, шифрование папок (EFS) и дисков (BitLocker), авторизация устройств в NAC. И почти все они живут в одной системе — PKI (Public Key Infrastructure, инфраструктура открытых ключей), которую в Windows-мире строят на роли **AD CS (Active Directory Certificate Services)**.

Типичные заявки L2 звучат так: «не выдался сертификат», «сертификат отозван, а приложение его пускает», «срок действия истёк», «после переустановки Windows пропала подпись», «браузер не доверяет внутреннему сайту». Чтобы их закрывать, надо понимать цепочку доверия, уметь ставить и обслуживать УЦ, управлять шаблонами, выдавать и отзывать сертификаты и настраивать автоподписку через GPO.

После этой главы ты будешь уметь: развернуть Enterprise Root CA на member-сервере, создать и опубликовать шаблон, настроить автоподписку на OU, вручную выпустить сертификат через `certreq`, отозвать его и опубликовать CRL, проверить цепочку и найти причину, почему автоподписка не сработала.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Основа — асимметричная криптография.** У каждого участника пара ключей: закрытый (private, никогда не покидает владельца) и открытый (public, его все видят). Что подписано закрытым — проверяется открытым.

**Сертификат X.509 v3** — это подписанный удостоверяющим центром «паспорт», который связывает открытый ключ с личностью. Ключевые поля:

| Поле | Что означает |
|------|--------------|
| Subject | Чей это сертификат (`CN=WIN11-CL01` или `CN=Иванов Иван`) |
| Issuer | Кто подписал (наш УЦ) |
| Serial Number | Уникальный номер — по нему отзывают |
| Validity | NotBefore / NotAfter |
| Public Key | Сам открытый ключ |
| Extensions | EKU (для чего годится), SAN (имена сайтов), Key Usage |
| Signature | Подпись издателя |

**Цепочка доверия.** Клиент доверяет не сертификату сотрудника, а корневому сертификату УЦ, который лежит в хранилище **Trusted Root Certification Authorities**. Дальше цепочка: корень → издающий УЦ → конечный сертификат. Если хоть одно звено не сходится — браузер орёт `NET::ERR_CERT_AUTHORITY_INVALID`.

**Как выглядит инфраструктура в корпоративной сети «Вектор»:**

```text
        AD (DC01)                         FS01
 ┌───────────────────────┐        ┌───────────────────────────┐
 │ Configuration NC:     │        │  Роль AD CS               │
 │  CN=Certificate       │◄──────►│  VEKTOR-Root-CA           │
 │     Templates         │  LDAP  │  закрытый ключ УЦ         │
 │  CN=Certification     │        │  база запросов/выданных   │
 │     Authorities       │        │  шаблоны (published)      │
 │  CN=CDP (CRL)         │        │  CRL                      │
 └───────────┬───────────┘        └────────────┬──────────────┘
             │ GPO: Auto-Enrollment            │ RPC/DCOM (135 + dynamic)
             ▼                                 ▼
      WIN11-CL01 / WIN10-CL02  ── запрос сертификата ──►  выдача
      Cert:\LocalMachine\My
```

**Что происходит при автоподписке (autoenrollment), по шагам:**

```text
Клиент                    DC01 (AD/GPO)                  FS01 (CA)
  |                            |                             |
  |-- gpupdate --------------->|                             |
  |<-- GPO: Auto-Enrollment ---|                             |
  |                            |                             |
  |-- LDAP: список опубликованных шаблонов с Autoenroll ---> |
  |-- проверка прав на шаблоне (Read / Enroll / Autoenroll)  |
  |                            |                             |
  |-- RPC/DCOM запрос (TCP 135 + динамический порт) -------> |
  |<-- подписанный сертификат ------------------------------ |
  |  кладётся в Cert:\LocalMachine\My  | база CA: Request ID |
```

**Порты и протоколы, которые надо помнить:**

- **LDAP 389 / LDAPS 636** — чтение шаблонов, точек публикации CRL, корневых сертификатов из AD.
- **RPC: 135 (endpoint mapper) + динамический диапазон 49152–65535** — общение клиента и консоли с CA по DCOM. Именно поэтому «CA за файрволом» часто ломается.
- **HTTP 80** — если развёрнут IIS с Web Enrollment, оттуда забираются CRL и AIA (`http://FS01/CertEnroll/...`).
- **HTTPS 443** — NDES/SCEP (для сетевого оборудования) и CEP/CES.

**Шаблоны (certificate templates).** Шаблон — это «бланк»: какие EKU, срок жизни, кто имеет право запрашивать (ACL), требуется ли подтверждение оператора, куда берётся Subject (из AD или вводится вручную). Шаблоны хранятся в AD как объекты `pKICertificateTemplate`. Шаблон можно создать, но пока он не **опубликован на CA**, клиенты его не увидят — это самая частая причина «автоподписка не работает».

**Отзыв.** Если ноутбук украли или ключ утёк, сертификат нужно отозвать. Список отозванных сертификатов — **CRL (Certificate Revocation List)**; он имеет срок жизни (по умолчанию у Enterprise CA — 1 неделя `[ПРОВЕРИТЬ]`) и его надо периодически перепубликовывать. Клиент узнаёт, откуда брать CRL, из расширения **CDP (CRL Distribution Point)**, а где взять сертификат издателя — из **AIA (Authority Information Access)**. Есть и онлайн-проверка **OCSP** (роль Online Responder) — быстрее, чем качать CRL.

**Где это в РФ 2026:** AD CS отлично закрывает RSA-сценарии (TLS, 802.1X, RDP, EFS/BitLocker). Для **квалифицированной ЭП по ГОСТ** нужен отдельный УЦ на средствах КриптоПро (например, «КриптоПро УЦ») `[ПРОВЕРИТЬ актуальные редакции]` — AD CS ГОСТ-сертификаты не выпускает. Импортозамещённые аналоги УЦ тоже существуют, но на стенде мы работаем с бесплатным AD CS из состава Windows Server Evaluation.

## 3. Аналогия из жизни

PKI — это паспортная система. **Корневой УЦ** — МВД: его печать знают все, и его бланки никто не подделывает. **Издающий УЦ** — паспортный стол района: он сам имеет доверенность от МВД и выдаёт паспорта людям. **Шаблон** — это тип бланка: «паспорт гражданина», «загранпаспорт», «служебное удостоверение» — на каждом свои степени защиты и свой срок действия. **CSR (запрос на сертификат)** — заявление, которое ты подаёшь, чтобы тебе выдали паспорт. **CRL** — список украденных и аннулированных паспортов, который регулярно рассылают на погранпереходы: паспорт физически на руках, но по списку он уже недействителен. **Автоподписка** — это когда HR при приёме сотрудника сам отправляет заявку, и к вечеру у человека уже лежит удостоверение в кармане, без похода в окошко.

Аналогия перестаёт работать в одном месте: паспорт нельзя перевыпустить без человека, а сертификат компьютер запрашивает себе сам, автоматически и сколько угодно раз.

## 4. Практика и команды

Все команды выполняются на стенде «Вектор». CA у нас — `FS01`, имя УЦ `VEKTOR-Root-CA`, строка конфигурации `FS01\VEKTOR-Root-CA`.

**1. Установка роли AD CS (FS01, PowerShell от adm.student).**

```powershell
Install-WindowsFeature ADCS-Cert-Authority -IncludeManagementTools
```
`-IncludeManagementTools` тянет консоль `certsrv.msc` и модуль `ADCSDeployment`. GUI-путь: *Server Manager → Add Roles and Features → Active Directory Certificate Services*. Перезагрузка после установки роли не требуется.

**2. Настройка УЦ (пост-инсталляционный мастер или PowerShell).**

```powershell
Install-AdcsCertificationAuthority -CAType EnterpriseRootCA `
  -CACommonName "VEKTOR-Root-CA" `
  -KeyLength 4096 -HashAlgorithmName SHA256 `
  -ValidityPeriod Years -ValidityPeriodUnits 10 `
  -CryptoProviderName "RSA#Microsoft Software Key Storage Provider" -Force
```
`-CAType EnterpriseRootCA` — УЦ, интегрированный с AD (умеет шаблоны и автоподписку). `-KeyLength`/`-HashAlgorithmName` — 4096 бит и SHA-256. `-ValidityPeriod` — срок жизни самого корневого сертификата. `[ПРОВЕРИТЬ]` точное имя параметра хранилища ключей и допустимость `-CryptoProviderName` с KSP в вашей сборке — в мастере GUI это пункт «Cryptographic provider». По умолчанию корневой Enterprise CA создаётся на 5 лет, мы ставим 10 осознанно.

**3. Проверка живости службы.**

```cmd
certutil -ping -config "FS01\VEKTOR-Root-CA"
certutil -cainfo -config "FS01\VEKTOR-Root-CA"
```
Вывод `-ping`:
```text
Connecting to FS01\VEKTOR-Root-CA ...
Server "VEKTOR-Root-CA" ICertRequest2 interface is alive (0ms)
```
`-cainfo` показывает имя, срок действия сертификата УЦ, хранилище ключа и точки публикации. Смотрим: `NotAfter` корня в будущем, `Key Container` на месте.

**4. Список опубликованных шаблонов.**

```cmd
certutil -catemplates -config "FS01\VEKTOR-Root-CA"
```
```text
Vektor-Workstation: Vektor-Workstation -- Auto-Enroll
Computer: Computer -- Auto-Enroll
User: User -- Auto-Enroll
```
Если твоего шаблона в списке нет — он не опубликован, и клиент его не увидит, сколько бы прав ни было в ACL.

**5. Что лежит в хранилище клиента (PowerShell).**

```powershell
Get-ChildItem Cert:\LocalMachine\My | Format-List Subject,Issuer,NotAfter,Thumbprint
Get-ChildItem Cert:\LocalMachine\Root | Where-Object Subject -like "*VEKTOR*"
```
`Cert:\` — провайдер PowerShell поверх хранилищ Windows. `My` — личные сертификаты машины, `Root` — доверенные корни. Смотрим: Subject = имя компьютера, Issuer = `CN=VEKTOR-Root-CA`, NotAfter в будущем.

**6. То же через certutil.**

```cmd
certutil -store My
certutil -store Root VEKTOR-Root-CA
```
`-store <имя> [<фильтр>]` выводит сертификаты хранилища с серийником, хешем и провайдером ключа. Серийник отсюда понадобится для отзыва.

**7. Запуск автоподписки вручную.**

```cmd
gpupdate /force
gpresult /r
certutil -pulse
```
`gpupdate /force` — переприменить политики. `gpresult /r` — покажет, какие GPO применились к компьютеру и пользователю (ищем `PKI-Autoenrollment` в разделе Computer Settings). `certutil -pulse` — принудительно прогнать цикл автоподписки прямо сейчас, не дожидаясь расписания.

**8. Ручной запрос через certreq (когда автоподписки нет).**

```cmd
certreq -new request.inf request.req
certreq -submit -config "FS01\VEKTOR-Root-CA" request.req cert.cer
certreq -retrieve -config "FS01\VEKTOR-Root-CA" <RequestID> cert.cer
certreq -accept cert.cer
```
`-new` формирует CSR по INF-файлу, `-submit` отправляет на CA, `-retrieve` забирает по номеру запроса (нужен, если запрос ушёл в состояние Pending), `-accept` связывает сертификат с закрытым ключом в хранилище.

**9. Отзыв и перепубликация CRL.**

```cmd
certutil -view -config "FS01\VEKTOR-Root-CA" -restrict "Disposition=20" -out "RequestID,RequesterName,SerialNumber,NotAfter"
certutil -revoke -config "FS01\VEKTOR-Root-CA" <SerialNumber> 1
certutil -CRL -config "FS01\VEKTOR-Root-CA"
```
`-restrict "Disposition=20"` — только выданные (21 — отозванные, 30 — отклонённые) `[ПРОВЕРИТЬ коды в своей версии]`. В `-revoke` второй аргумент — причина: `0` unspecified, `1` keyCompromise, `2` cACompromise, `3` affiliationChanged, `4` superseded, `5` cessationOfOperation, `6` certificateHold `[ПРОВЕРИТЬ нумерацию]`. `-CRL` публикует новый список отзыва — **без этого шага отзыв не виден клиентам**.

**10. Проверка цепочки и доступности CRL/AIA.**

```cmd
certutil -verify -urlfetch -config "FS01\VEKTOR-Root-CA" win11.cer
```
`-urlfetch` заставляет утилиту реально скачать CRL и AIA по указанным в сертификате адресам. В выводе ищем `Revocation Status: ok` или `Revoked`. Если видим `Unable to retrieve` — сломаны точки публикации, и это отдельная заявка.

**11. Разбор сертификата на Linux (UBU01).**

```bash
openssl x509 -inform DER -in win11.cer -text -noout
openssl x509 -inform DER -in win11.cer -noout -subject -issuer -dates -serial
openssl verify -CAfile vektor-root.pem win11.pem
```
Сертификат Windows отдаёт в DER, поэтому `-inform DER`. `-text` печатает все расширения: EKU, SAN, CDP, AIA. `openssl verify` проверяет цепочку против указанного корня — удобно, когда надо доказать, что проблема не в клиенте, а в самом сертификате.

**12. Резервная копия УЦ (делается сразу после установки).**

```cmd
certutil -backup -p "<пароль_бэкапа>" C:\CA-Backup
```
Сохраняет закрытый ключ CA, сертификат, базу и реестровые настройки. Потеря этого бэкапа = потеря УЦ и перевыпуск **всех** сертификатов компании.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

- **DC01** (10.10.10.10) — AD DS, DNS, DHCP, домен `corp.vektor.lab` работает, есть OU `Компьютеры` с учётками WIN11-CL01 и WIN10-CL02.
- **FS01** (10.10.10.20) — Windows Server 2022, введён в домен, роль файлового сервера (из урока 13). Отдельного сервера под PKI на стенде L2 нет, поэтому CA ставим на member-сервер FS01. **В продакшене так не делают:** под УЦ выделяют отдельную ВМ, а корневой УЦ вообще держат выключенным (offline root) или строят двухуровневую иерархию. Совмещать CA с контроллером домена — хуже, чем с файловым сервером: компрометация DC означает компрометацию ключа УЦ.
- **WIN11-CL01**, **WIN10-CL02** — в домене, получают адреса по DHCP.
- Время на всех ВМ синхронизировано с DC01 (`w32tm /query /source` → `DC01.corp.vektor.lab`). Проверка срока действия сертификата без синхронного времени бессмысленна.
- Права: `adm.student` — администратор домена и локальный админ на FS01.

### Снапшот

В VMware Workstation на каждой затрагиваемой ВМ: *VM → Snapshot → Take Snapshot*, имя — `before-l2-015`.

ВМ: **DC01**, **FS01**, **WIN11-CL01**, **WIN10-CL02**. В описании снапшота напиши «до установки AD CS».

### Шаги

1. **FS01.** Проверить время и домен:
   ```cmd
   w32tm /query /source
   whoami /fqdn
   ```
   Ожидаемо: источник времени `DC01.corp.vektor.lab` (или PDC), пользователь `adm.student@corp.vektor.lab`.

2. **FS01.** Установить роль AD CS:
   ```powershell
   Install-WindowsFeature ADCS-Cert-Authority -IncludeManagementTools
   ```
   Ожидаемо: `Success: True`, `Restart Needed: No`.

3. **FS01.** Запустить пост-инсталляционную настройку: *Server Manager → жёлтый флаг → Configure Active Directory Certificate Services* → роль **Certification Authority** → **Enterprise** → **Root CA** → **Create a new private key** → провайдер `RSA#Microsoft Software Key Storage Provider`, 4096, SHA-256 → CN `VEKTOR-Root-CA`, срок 10 лет → **Configure**.
   Ожидаемо: «Configuration succeeds», служба `CertSvc` в состоянии Running.

4. **FS01.** Проверить УЦ:
   ```cmd
   certutil -ping -config "FS01\VEKTOR-Root-CA"
   certutil -cainfo -config "FS01\VEKTOR-Root-CA"
   ```
   Ожидаемо: `interface is alive`, в `-cainfo` — имя УЦ и срок действия.

5. **FS01.** Сделать шаблон: `certsrv.msc` → правый клик по **Certificate Templates** → **Manage** → найти `Computer` → правый клик → **Duplicate Template** → вкладка **General**: имя `Vektor-Workstation`, срок действия 1 год, «Publish certificate in Active Directory» снять → **Security**: у `Domain Computers` должны быть `Read`, `Enroll`, `Autoenroll` → **OK**.
   Ожидаемо: шаблон появился в списке `Certificate Templates`.

6. **FS01.** Опубликовать шаблон на УЦ: `certsrv.msc` → **Certificate Templates** → правый клик → **New → Certificate Template to Issue** → `Vektor-Workstation`. Проверить:
   ```cmd
   certutil -catemplates -config "FS01\VEKTOR-Root-CA"
   ```
   Ожидаемо: строка `Vektor-Workstation ... Auto-Enroll` в списке.

7. **DC01.** Создать GPO автоподписки: `gpmc.msc` → домен `corp.vektor.lab` → OU `Компьютеры` → **Create a GPO in this domain, and Link it here** → имя `PKI-Autoenrollment` → **Edit** → *Computer Configuration → Policies → Windows Settings → Security Settings → Public Key Policies → Certificate Services Client - Auto-Enrollment* → **Enabled**, галочки «Renew expired certificates…» и «Update certificates that use certificate templates».
   Ожидаемо: GPO связана с OU `Компьютеры`.

8. **WIN11-CL01.** Применить политику и прогнать автоподписку:
   ```cmd
   gpupdate /force
   gpresult /r
   certutil -pulse
   ```
   Ожидаемо: в `gpresult /r` в Computer Settings присутствует `PKI-Autoenrollment`; `certutil -pulse` завершается без ошибок.

9. **WIN11-CL01.** Проверить сертификат:
   ```powershell
   Get-ChildItem Cert:\LocalMachine\My | Format-List Subject,Issuer,NotAfter,Thumbprint
   Get-ChildItem Cert:\LocalMachine\Root | Where-Object Subject -like "*VEKTOR*"
   ```
   Ожидаемо: сертификат `CN=WIN11-CL01`, Issuer `CN=VEKTOR-Root-CA`, срок ~1 год; корневой сертификат присутствует в `Root`.

10. **WIN10-CL02.** Повторить шаги 8–9. Ожидаемо: сертификат `CN=WIN10-CL02`. Убедиться, что на FS01 в `certsrv.msc → Issued Certificates` появились две новые записи.

11. **WIN10-CL02 + FS01.** Имитировать компрометацию: взять SerialNumber сертификата WIN10-CL02 (`certutil -store My`), затем на FS01:
    ```cmd
    certutil -revoke -config "FS01\VEKTOR-Root-CA" <SerialNumber> 1
    certutil -CRL -config "FS01\VEKTOR-Root-CA"
    certutil -view -config "FS01\VEKTOR-Root-CA" -restrict "Disposition=21" -out "RequestID,RequesterName,SerialNumber"
    ```
    Ожидаемо: запись в списке отозванных; в `certsrv.msc → Revoked Certificates` — сертификат с причиной `Key compromise`.

12. **WIN10-CL02.** Запустить `certutil -pulse`. Ожидаемо: машина получает **новый** сертификат (старый удалится, если в GPO включена опция «Remove revoked certificates»). Проверить `Get-ChildItem Cert:\LocalMachine\My`. Записать всё в `stand-log.md`.

### Сломай и почини

**Пользователь / ВМ:** petrova / WIN10-CL02
**Что написал:** «Здравствуйте! Программа для подписи документов пишет «сертификат не найден». Вчера подписывала — всё было хорошо. Отчётность стоит, но не горит.»
**Срочность:** средняя.

**Как воспроизвести поломку:** на FS01 в `certsrv.msc → Certificate Templates → Manage → Vektor-Workstation → Security` поставить группе `Domain Computers` галочку **Deny** напротив `Enroll`. На WIN10-CL02 удалить сертификат из `Cert:\LocalMachine\My` и выполнить `certutil -pulse`. Сертификат не появится.

**Диагностика по шагам:**

1. WIN10-CL02: `gpresult /r` — политика `PKI-Autoenrollment` применена? Если нет — проблема в GPO или в том, что ВМ не в OU `Компьютеры`.
2. WIN10-CL02: `certutil -pulse` — читаем вывод. Сообщение вида «no certificate templates could be found» — шаблон не опубликован или не подходит; «access denied» — ACL.
3. WIN10-CL02: журнал *Event Viewer → Applications and Services Logs → Microsoft → Windows → CertificateServicesClient-Lifecycle-System* — смотрим последние события с источником `CertificateServicesClient`. Текст сообщения важнее номера события: конкретные ID отличаются по версиям `[ПРОВЕРИТЬ]`.
4. FS01: `certutil -ping` — УЦ жив? Если нет, всё остальное бессмысленно.
5. FS01: `certutil -catemplates` — шаблон опубликован? Если нет — `New → Certificate Template to Issue`.
6. FS01: `certsrv.msc → Certificate Templates → Manage → Vektor-Workstation → Security` — проверяем ACL. **Вот и причина:** `Deny` для `Domain Computers` бьёт сильнее любого `Allow`.
7. Убираем `Deny`, возвращаем `Read + Enroll + Autoenroll`.
8. WIN10-CL02: `gpupdate /force`, `certutil -pulse`, `Get-ChildItem Cert:\LocalMachine\My` — сертификат появился.

**Ответ пользователю:** «Мария, добрый день. Причина была в правах на шаблоне сертификата на сервере PKI — после правки настроек ваш компьютер получил сертификат автоматически. Проверьте, пожалуйста, подписание документов; если программа всё ещё ругается — перезапустите её. Заявку закрываю, при повторении — сразу пишите.»

**Закрытие заявки:** категория «PKI / сертификаты», решение — «Откорректирован ACL шаблона `Vektor-Workstation` (снят Deny с Domain Computers), сертификат перевыпущен через автоподписку». Добавить в базу знаний короткую заметку: «Проверка автоподписки: gpresult → certutil -pulse → ACL шаблона → публикация шаблона».

## 6. Ошибки новичков и безопасность

1. **Ставить CA на контроллер домена «чтобы проще».** → Компрометация DC = компрометация закрытого ключа УЦ, и наоборот; плюс проблемы при повышении/понижении DC. → Правильно: отдельный member-сервер (в идеале — offline root + отдельный issuing CA).
2. **Не сделать бэкап ключа CA.** → Умер диск FS01 — придётся перевыпускать сертификаты на 50 машин, VPN, сайты. → Правильно: `certutil -backup` сразу после установки, с паролем, копия вне сервера, доступ у двух человек.
3. **Отозвать сертификат и не перепубликовать CRL.** → Отзыв не виден клиентам, «украденный» сертификат продолжает работать. → Правильно: `certutil -CRL` сразу после `-revoke` и проверка срока действия CRL в мониторинге.
4. **Опубликовать шаблон и забыть про ACL.** → Либо никто не может запросить (как в лабораторной), либо запросить может кто угодно, включая сертификат с произвольным Subject. → Правильно: минимальные права, `Enroll` только нужным группам, отдельно проверять опцию «Supply in the request».
5. **Раздавать права `Issue and Manage Certificates` / `Manage CA` всему IT-отделу.** → Кто угодно может выпустить себе сертификат от чужого имени или изменить политику. → Правильно: роли CA — только PKI-администратору, аудит доступа к CA.
6. **Забыть про точки публикации CDP/AIA.** → После установки только роли CA без IIS адрес `http://FS01/CertEnroll/...` может быть недоступен, и внешние (не доменные) устройства не смогут проверить CRL. → Правильно: проверить `certutil -verify -urlfetch`, при необходимости развернуть Web Enrollment или настроить другой HTTP-хост для CRL.
7. **Ломать автоподписку «на глазок».** → Правки в шаблоне без понимания, что автоподписка требует одновременно: GPO + опубликованный шаблон + ACL + доступность CA по RPC. → Правильно: проверять по цепочке, а не менять всё сразу.
8. **Считать, что AD CS закроет ГОСТ-ЭП.** → AD CS выдаёт RSA-сертификаты; для квалифицированной подписи по ГОСТ 2012 нужен УЦ на КриптоПро. → Правильно: разделять задачи TLS/802.1X (AD CS) и юридически значимой ЭП (аккредитованный УЦ).

**Безопасность.** Закрытый ключ УЦ — самый ценный актив в компании: с ним можно выпустить сертификат на любой домен и любого пользователя. В боевой среде корневой УЦ держат выключенным (offline, на отдельной машине без сети), ключ — на HSM или хотя бы на защищённом носителе; издающий УЦ — на выделенном сервере с ограниченным сетевым доступом. Никогда не отключай проверку отзыва «чтобы работало» и не добавляй корень «в доверенные» на всех машинах через GPO без понимания последствий. На стенде пароль `Lab#2026-vektor` и пароль бэкапа — учебные; в реальной работе так нельзя.

## 7. Вопросы на собеседовании

**Вопрос 1. Что такое PKI и зачем компании свой УЦ, если можно поставить самоподписанный сертификат на сервер?**
**Ответ:** PKI — это инфраструктура управления ключами и сертификатами: УЦ, шаблоны, выдача, отзыв, публикация CRL. Самоподписанный сертификат никому не доказывает личность сервера — браузер покажет ошибку доверия, и администратору придётся вручную добавлять исключения на каждой машине. Свой УЦ даёт единую точку доверия: корень один раз попадает в доверенные (через AD/GPO), а дальше любой внутренний сервис получает сертификат автоматически, и его можно отозвать централизованно.
**Что хочет услышать интервьюер:** понимание цепочки доверия, централизации и отзыва, а не только «чтобы не было ошибки в браузере».
**Красный флаг:** «самоподписанный ничем не хуже, главное галочку в браузере нажать».

**Вопрос 2. Как работает автоподписка сертификатов в AD и что нужно, чтобы она заработала?**
**Ответ:** Нужны четыре условия. Первое — GPO `Certificate Services Client - Auto-Enrollment`, привязанная к OU с компьютерами/пользователями. Второе — шаблон, **опубликованный** на CA. Третье — права на шаблоне: `Read`, `Enroll`, `Autoenroll` у соответствующей группы (`Domain Computers` или группы пользователей). Четвёртое — доступность CA по RPC (135 + динамический диапазон) и корректное время на клиенте. Клиент читает опубликованные шаблоны из AD по LDAP, проверяет ACL, отправляет запрос на CA и кладёт сертификат в `Cert:\LocalMachine\My` или `Cert:\CurrentUser\My`.
**Что хочет услышать интервьюер:** что ты знаешь все четыре условия и умеешь диагностировать по шагам, а не «перезагрузите компьютер».
**Красный флаг:** «достаточно включить GPO, дальше само».

**Вопрос 3. Чем отзыв сертификата отличается от его удаления с компьютера? Что такое CRL и OCSP?**
**Ответ:** Удаление с компьютера убирает локальную копию, но сертификат остаётся действительным — если у кого-то есть копия (или украден закрытый ключ), он продолжит работать. Отзыв — это запись в базе CA: серийный номер попадает в CRL, и все клиенты, проверяющие отзыв, перестают доверять этому сертификату. CRL — подписанный список отозванных сертификатов с ограниченным сроком действия, его публикуют заново по расписанию и вручную (`certutil -CRL`). OCSP — онлайн-проверка статуса конкретного сертификата, быстрее и свежее, реализуется ролью Online Responder. Важно помнить про кеш: клиент может держать старую CRL.
**Что хочет услышать интервьюер:** разницу между локальным состоянием и состоянием в PKI, а также что отзыв без публикации CRL не работает.
**Красный флаг:** «удалю сертификат с компьютера — и всё, он недействителен».

**Вопрос 4. Чем Enterprise CA отличается от Standalone CA и когда что выбирать?**
**Ответ:** Enterprise CA интегрирован с AD: использует шаблоны, автоматически публикует сертификат УЦ и CRL в AD, умеет автоподписку, а аутентификация запросов идёт по учётной записи домена. Standalone CA не зависит от AD: запросы обрабатываются вручную или через веб-интерфейс, шаблонов в привычном виде нет, автоподписки нет. Enterprise выбирают внутри домена для сотрудников и компьютеров; Standalone — когда домена нет, нужен offline root или жёсткий ручной контроль выдачи (например, для инфраструктурных сертификатов).
**Что хочет услышать интервьюер:** понимание, что разница практическая (шаблоны, автоподписка, AD-публикация), а не «одна платная, другая бесплатная».
**Красный флаг:** «это одно и то же, просто ставится по-разному».

**Вопрос 5. Сгорел сервер с УЦ. Твои действия?**
**Ответ:** Сначала уточняю, есть ли бэкап CA (`certutil -backup`: ключ, сертификат, база, реестр). Если есть — разворачиваю сервер с тем же именем, восстанавливаю CA из бэкапа (`certutil -restore`), проверяю, что корневой сертификат тот же (иначе все клиенты перестанут доверять), публикую CRL. Если бэкапа нет — придётся строить новый УЦ, распространять новый корень через GPO и перевыпускать все сертификаты; это авария на дни. Поэтому бэкап CA и мониторинг срока действия CRL и корневого сертификата — обязательные процедуры.
**Что хочет услышать интервьюер:** что бэкап ключа CA — базовая гигиена, и что ты понимаешь последствия смены корня.
**Красный флаг:** «просто поставлю новый УЦ, делов-то».
