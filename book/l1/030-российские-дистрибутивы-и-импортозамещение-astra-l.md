## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Все три системы — это Linux. Одно ядро Linux, один `systemd`, один Bash, одни и те же `journalctl`, `top`, `ssh`. Различия лежат **выше ядра** — в том, из чего собран дистрибутив: база пакетов, формат пакетов, менеджер пакетов, набор служебных утилит и надстроек безопасности.

```text
                    ┌─────────────────────────────┐
                    │   Ядро Linux (одинаковое)   │
                    │   systemd, Bash, OpenSSH    │
                    └─────────────────────────────┘
                                  ▲
        ┌─────────────────────────┼─────────────────────────┐
        │                         │                         │
   ┌─────────┐              ┌──────────┐              ┌──────────┐
   │  Astra  │              │  РЕД ОС  │              │   ALT    │
   │ Linux   │              │          │              │  Linux   │
   ├─────────┤              ├──────────┤              ├──────────┤
   │ .deb    │              │ .rpm     │              │ .rpm     │
   │ apt+dpkg│              │ dnf+rpm  │              │ apt+rpm  │
   │ Debian  │              │ RPM-мир  │              │ Sisyphus │
   │ + СЗИ   │              │ + свой   │              │ + alter- │
   │ (SE)    │              │ рабочий  │              │   ator   │
   │         │              │ стол     │              │          │
   └─────────┘              └──────────┘              └──────────┘
     Debian-семейство         RPM-семейство           своя база,
                                                      формат .rpm
```

Ключевое различие для L1 — **формат пакета**:

- **`.deb`** — формат Debian-семейства. Debian → Ubuntu → **Astra Linux**. Менеджеры: низкоуровневый `dpkg`, поверх него `apt`.
- **`.rpm`** — формат RPM-семейства (Red Hat, CentOS, Fedora). Сюда относятся **РЕД ОС** (менеджер `dnf`) и **ALT Linux** (у ALT свой путь: формат `.rpm`, но менеджер пакетов — `apt` с RPM-бэкендом, база пакетов называется Sisyphus).

Пакет — это архив с файлами программы плюс метаданные: имя, версия, зависимости, скрипты установки. Поставить `.deb` на систему с `dnf` «в один клик» нельзя: другая база зависимостей, другие пути, другие версии библиотек. Технически существуют конвертеры (`alien`) и обёртки вроде `epm` в ALT, но в боевой среде так почти никогда не делают — это ломает целостность пакетной базы.

Второй важный слой — **репозитории**. Пакет ставится не «из файла», а из репозитория вендора: подписанного хранилища пакетов, к которому система ходит по HTTP/HTTPS (порт 80/443). Если адрес репозитория указан неверно или указывает на другой релиз — обновления и установка ломаются. Конфиги:

| Параметр | Astra Linux | РЕД ОС | ALT Linux |
|---|---|---|---|
| Формат пакетов | `.deb` | `.rpm` | `.rpm` |
| Менеджер | `apt` / `dpkg` | `dnf` / `rpm` | `apt` (apt-rpm) / `rpm` |
| Файлы репозиториев | `/etc/apt/sources.list`, `/etc/apt/sources.list.d/` | `/etc/yum.repos.d/*.repo` | `/etc/apt/sources.list`, `apt-repo` |
| Обновление индексов | `apt update` | `dnf makecache` | `apt-get update` |
| Рабочий стол | Fly (собственная среда) | GNOME с доработками `[ПРОВЕРИТЬ]` | на выбор (Xfce, MATE, KDE) `[ПРОВЕРИТЬ]` |
| База | Debian `[ПРОВЕРИТЬ версию]` | независимая RPM-сборка | собственная, Sisyphus |
| Бесплатная версия | Common Edition | свободно доступная сборка `[ПРОВЕРИТЬ]` | Simply Linux / ALT Education |

Третий слой — **безопасность и сертификация**. ФСТЭК России сертифицирует конкретные версии ОС на соответствие требованиям к средствам вычислительной техники (уровни доверия, профили защиты). Наличие сертификата означает, что проверен конкретный набор функций защиты: мандатное управление доступом (MAC — доступ решается не только «кто ты», но и «какой у тебя уровень допуска» и «какая метка у файла»), контроль целостности, замкнутая программная среда (ЗПС — разрешено запускать только подписанное/разрешённое ПО), очистка памяти. В Astra Linux эти механизмы собраны в подсистему «Пароль» и присутствуют в **Special Edition** (исполнения «Орёл», «Смоленск» и др. `[ПРОВЕРИТЬ]`); в бесплатной Common Edition их, как правило, нет `[ПРОВЕРИТЬ]`. У ALT сертифицированная линейка — «ALT 8 СП»; у РЕД ОС тоже есть сертифицированные сборки `[ПРОВЕРИТЬ]`.

Отсюда практический вывод для L1: **одна и та же ОС в двух исполнениях ведёт себя по-разному**. Если в заявке написано «Astra», надо уточнить, какое исполнение — CE или SE, потому что от этого зависят и права пользователя, и то, почему у него «не открывается файл с флешки» (ЗПС).

## 3. Аналогия из жизни

Представьте, что компании «Вектор» сверху спустили разнарядку: служебный автопарк переводим на отечественные марки. Первая — предприятие, которое по лицензии собирает иностранную платформу, но ставит на неё свой кузов и свою сигнализацию: под капотом всё знакомо, но снаружи и в электрике — свои детали (**Astra Linux** = Debian + надстройка безопасности). Вторая — молодая марка на распространённой иностранной платформе со своим салоном и своим набором опций (**РЕД ОС** = RPM-база + свой рабочий стол). Третья — завод с собственной конструкторской школой с 1990-х и собственной логикой, местами непохожей на остальных (**ALT Linux** = своя база Sisyphus). Запчасти между марками в основном не взаимозаменяемы — как `.deb` не подходит к `dnf`.

Аналогия перестаёт работать в одном: у автомобиля сертификат соответствия выдаётся на модель в целом, а у ОС сертификат ФСТЭК привязан к конкретной версии и конкретной конфигурации защитных механизмов — стоит администратору «на минутку» отключить мандатный контроль, и сертифицированная конфигурация перестала быть сертифицированной, хотя система работает.

## 4. Практика и команды

**4.1. Универсальная идентификация ОС**

```bash
cat /etc/os-release
```

```text
PRETTY_NAME="Astra Linux (Common Edition) 2.12"
NAME="Astra Linux (Common Edition)"
ID=astra
VERSION_ID="2.12"
```

Смотрим `PRETTY_NAME` (человеческое имя), `ID` (`astra` / `redos` / `altlinux` / `ubuntu` `[ПРОВЕРИТЬ значения]`), `VERSION_ID`. Это первая команда при любой заявке «у меня Linux» — работает на всех дистрибутивах и не требует прав root.

**4.2. Идентификация через systemd**

```bash
hostnamectl
```

```text
 Static hostname: ASTRA01
Operating System: Astra Linux (Common Edition) 2.12
          Kernel: Linux 5.15.0-... [ПРОВЕРИТЬ]
    Architecture: x86-64
```

Одна команда даёт имя машины, ОС, версию ядра и архитектуру. Удобно, когда надо продиктовать данные в заявку или сравнить две машины стенда.

**4.3. Файлы версии конкретного вендора**

```bash
cat /etc/astra_version      # Astra [ПРОВЕРИТЬ имя файла]
cat /etc/redos-release      # РЕД ОС [ПРОВЕРИТЬ]
cat /etc/altlinux-release   # ALT Linux
```

Вендоры дублируют версию в свои файлы. Если `os-release` отсутствует или урезан (бывает в контейнерах и на старых сборках), эти файлы спасают. Быстрый поиск:

```bash
ls /etc/*release* /etc/*version* 2>/dev/null
```

**4.4. Ядро и архитектура**

```bash
uname -r && uname -m
```

```text
5.15.0-...
x86_64
```

Пригодится, когда программа требует «не ниже ядра X» — типичный вопрос от 1С и КриптоПро.

**4.5. Пакетный менеджер: что реально стоит**

```bash
dpkg -l | wc -l          # Astra, Ubuntu (deb)
rpm -qa | wc -l          # РЕД ОС, ALT (rpm)
dnf list installed       # РЕД ОС
```

Считаем количество пакетов и проверяем конкретный:

```bash
dpkg -s htop | grep -E 'Status|Version'   # Astra
rpm -qi htop                              # РЕД ОС / ALT
```

Смотрим `Status: install ok installed` или блок `Name/Version/Vendor`. По полю `Vendor` в RPM видно, вендорский это пакет или собранный сторонней сборкой — важный признак для аттестованной среды.

**4.6. Где лежат репозитории**

```bash
cat /etc/apt/sources.list ; ls /etc/apt/sources.list.d/     # Astra
ls /etc/yum.repos.d/ ; cat /etc/yum.repos.d/*.repo          # РЕД ОС
apt-repo list                                               # ALT
```

Внутри — строки вида `deb https://.../repository-main/ 1.7_x86-64 main` `[ПРОВЕРИТЬ пример URL и имя ветки]`. Ключевые поля: адрес, **suite/ветка** (у Astra это кодовое имя вроде `1.7_x86-64`, `[ПРОВЕРИТЬ]`) и компоненты (`main`, `contrib`). 90% поломок обновления — ошибка именно здесь.

**4.7. Обновление индексов и системы**

```bash
sudo apt update && sudo apt upgrade -y                 # Astra
sudo dnf makecache && sudo dnf upgrade -y              # РЕД ОС
sudo apt-get update && sudo apt-get dist-upgrade -y    # ALT
```

`update`/`makecache` скачивает список пакетов, само обновление — вторая команда. `upgrade` обновляет в рамках текущего релиза, `dist-upgrade` в ALT может потянуть смену релиза — на боевой машине это делают только по согласованию.

**4.8. Поиск и установка программы**

```bash
apt search htop ; sudo apt install -y htop          # Astra
dnf search htop ; sudo dnf install -y htop          # РЕД ОС
apt-cache search htop ; sudo apt-get install -y htop # ALT
```

Перед установкой полезно посмотреть, откуда пакет приедет и какая версия:

```bash
apt-cache policy htop     # Astra / ALT: показывает репозиторий-источник
dnf info htop             # РЕД ОС: репозиторий, размер, лицензия
```

**4.9. Что за защитный механизм включён (Astra)**

```bash
astra-safepolicy                    # текущий режим защищённости [ПРОВЕРИТЬ]
pdp-id                              # текущий уровень пользователя [ПРОВЕРИТЬ]
pdpl-user -i 3 student              # выдать уровень, пример синтаксиса [ПРОВЕРИТЬ]
```

Это инструменты подсистемы мандатного доступа. На Common Edition их может не быть вовсе — тогда вывод команды `command not found` сам по себе является ответом «здесь SE-механизмов нет».

**4.10. Службы и логи — одинаково везде**

```bash
systemctl status sshd
journalctl -u sshd -n 30 --no-pager
```

Приятная новость: после уроков 26–29 всё это работает на Astra, РЕД ОС и ALT без изменений. Если служба не поднимается — смотрим `systemctl status`, потом `journalctl`, как на Ubuntu.

**GUI-пути для L1** (когда проще кликнуть, чем печатать): в Astra обновления — «Меню → Настройки → Менеджер обновлений» `[ПРОВЕРИТЬ]`, администрирование — «Центр управления Fly» `[ПРОВЕРИТЬ]`; в ALT — «Центр управления системой» (`acc`) `[ПРОВЕРИТЬ]`; в РЕД ОС — «Центр управления» `[ПРОВЕРИТЬ]`.


Ожидаемо: `apt update` выдаёт ошибку по этому адресу — `404 Not Found` либо «Release file ... does not have a Release file» `[ПРОВЕРИТЬ формулировку]`.

**Диагностика по шагам (строго в этом порядке):**

1. Прочитать ошибку целиком. `sudo apt update` — найти в выводе строку `Err:`/`E:` и выписать URL и «ветку» (второе поле после адреса).
2. Посмотреть, какие файлы репозиториев вообще есть и что менялось последним:
   ```bash
   ls -la /etc/apt/sources.list.d/
   ```
   Свежая дата у `broken.list` — почти приговор.
3. Сравнить содержимое с эталоном вендора:
   ```bash
   cat /etc/apt/sources.list.d/broken.list
   ```
   Ветка `99_no_such_release` не существует — вот причина.
4. Исключить проблему с часами (даёт другую ошибку, «is not valid yet»):
   ```bash
   timedatectl
   ```
   Дата и время должны быть актуальными.
5. Исключить сеть и DNS: `ping -c 3 dl.astralinux.ru` и `getent hosts dl.astralinux.ru`. Если не резолвится — проблема не в репозитории.
6. Исправить: удалить битый файл (или заменить ветку на верную).
   ```bash
   sudo rm /etc/apt/sources.list.d/broken.list
   sudo apt update
   ```
7. Убедиться, что установка снова работает: `sudo apt install -y tree` (или любой неустановленный мелкий пакет).

## 6. Ошибки новичков и безопасность

1. **Совать `.rpm` в Astra или `.deb` в РЕД ОС** → ошибка «не удалось прочитать пакет», потерянное время и нервы пользователя. → Сначала `cat /etc/os-release`, потом выбирайте нужный пакет.
2. **Подключать репозиторий Ubuntu к Astra** (или наоборот) → конфликт зависимостей, «сломалась» система, восстановление только переустановкой. → Только репозитории вендора и только для своей ветки.
3. **Считать, что «Linux — он и есть Linux»** → на вопрос «какая у вас ОС» отвечают «линукс», и вся заявка идёт по ложному следу. → `os-release` и `hostnamectl` — первые две команды.
4. **Ставить программу из скачанного файла вместо репозитория** → программа не обновляется, дыры в безопасности живут годами. → Сначала поиск в репозитории, файл — только если пакета нет и это согласовано.
5. **Путать исполнения Astra (CE и SE)** → «у пользователя не открывается документ с флешки», а причина — замкнутая программная среда, а не «глючный файл». → Уточнять исполнение в самом начале.
6. **`dist-upgrade` на боевой машине «чтобы обновилось посвежее»** → смена релиза, несовместимость с 1С и КриптоПро. → Обновления только в рамках релиза и по регламенту.
7. **Не дочитывать вывод `apt`/`dnf`** → «поставилось», а на деле половина пакетов осталась не настроена. → Читаем последние 10 строк и проверяем установку отдельной командой.

### Безопасность

- **Не отключать защитные механизмы.** Понижение режима защищённости в Astra (`astra-safepolicy`), вывод из ЗПС, изменение мандатных меток — это не «настройка», а изменение аттестованной конфигурации. В боевой среде такие действия согласуются с отделом ИБ и оформляются документом.
- **Не добавлять сторонние репозитории и не ставить ПО не из реестра** на машинах, где этого требует заказчик или регулятор. Формально «работает», юридически — нарушение требований.
- **Не использовать `root` для повседневной работы** и не хранить пароли в открытом виде в скриптах — на стенде это прощается, в бою это инцидент.
- **Помните про учебный пароль** `Lab#2026-vektor`: он одинаковый на всех машинах стенда и допустим только в лаборатории.

## 7. Вопросы на собеседовании

**Вопрос 1. Чем `.deb` отличается от `.rpm` и какие российские ОС на какой базе построены?**

Ответ: это два разных формата пакетов с разными метаданными и разными базами зависимостей. `.deb` — Debian-семейство, менеджеры `dpkg`/`apt`; на этой базе стоит Astra Linux. `.rpm` — RPM-семейство, менеджер `dnf` (`rpm` как низкий уровень); на этой базе РЕД ОС. ALT Linux — отдельный случай: формат `.rpm`, но менеджер пакетов `apt` с RPM-бэкендом и собственной базой Sisyphus. Взаимозаменять пакеты нельзя.

*Что хочет услышать интервьюер:* что вы знаете три конкретные ОС и не путаете пакетные менеджеры.
*Красный флаг:* «Linux один, разницы нет» или «на Astra ставится rpm через alien, это норма».

**Вопрос 2. Как за 10 секунд определить, что за система перед вами, и где смотреть версию?**

Ответ: `cat /etc/os-release` — покажет `ID` и `PRETTY_NAME`; `hostnamectl` — ОС, ядро, архитектуру одной командой. Дополнительно вендорские файлы: `/etc/astra_version`, `/etc/redos-release`, `/etc/altlinux-release`. Дальше по `ID` сразу понятно, какой пакетный менеджер использовать.

*Что хочет услышать интервьюер:* автоматизм — «сначала идентифицирую, потом действую».
*Красный флаг:* «посмотрю в свойствах системы мышкой» без единой команды.

**Вопрос 3. Зачем нужна сертификация ФСТЭК и почему Astra Linux Special Edition отличается от Common Edition?**

Ответ: сертификация подтверждает, что конкретная версия ОС реализует заданный набор функций защиты — мандатное управление доступом, контроль целостности, замкнутую программную среду, очистку памяти — и соответствует требованиям к уровню доверия. Это нужно для государственных информационных систем и объектов, где есть регулятор. Special Edition содержит эти механизмы, Common Edition — бесплатная сборка без них. Практическое следствие для поддержки: на SE пользователь может «не открыть» файл из-за ЗПС или меток доступа, и это не поломка, а работа защиты.

*Что хочет услышать интервьюер:* понимание, что сертификат — про функции защиты, а не «значок качества», и что CE ≠ SE.
*Красный флаг:* «сертификация — это формальность, всё равно всё отключаем».

**Вопрос 4. Как обновить систему на Astra, РЕД ОС и ALT?**

Ответ: Astra — `sudo apt update && sudo apt upgrade`; РЕД ОС — `sudo dnf makecache && sudo dnf upgrade`; ALT — `sudo apt-get update && sudo apt-get dist-upgrade` (осторожно, `dist-upgrade` может потянуть смену релиза). Перед обновлением на боевой машине — снапшот или бэкап, обновление по регламенту, после — проверка ключевого ПО (1С, КриптоПро).

*Что хочет услышать интервьюер:* знание трёх команд и привычка думать про бэкап и совместимость.
*Красный флаг:* «накачу `dist-upgrade` на проде, посмотрим, что будет».

**Вопрос 5. Пользователь просит поставить программу, которой нет в репозитории. Ваши действия?**

Ответ: уточняю, что за задача и есть ли эта программа в реестре российского ПО; ищу аналог в репозитории вендора; если аналога нет — оформляю согласование с ИБ/руководителем, ставлю из проверенного источника, документирую установку. На аттестованной машине установка ПО не из реестра и не из репозитория — отдельное согласование, а не самодеятельность.

*Что хочет услышать интервьюер:* что вы не «просто ставите», а работаете по процессу.
*Красный флаг:* «скачаю с первого сайта и поставлю, потом разберёмся».
