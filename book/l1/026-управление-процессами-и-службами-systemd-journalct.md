## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

### Что такое процесс

**Процесс** — это запущенная программа. У каждого процесса есть:
- **PID** (Process ID) — уникальный номер, например `1234`;
- **PPID** (Parent PID) — PID родителя, который его запустил;
- владелец (root или `adm.student`);
- состояние: `R` (running), `S` (sleeping), `Z` (zombie), `D` (uninterruptible sleep);
- потребление CPU и памяти.

Процессы образуют дерево: `systemd` (PID 1) — корень, от него рождаются все остальные.

### Что такое служба (демон)

**Демон** (daemon) — процесс, работающий в фоне без терминала. **Служба** (service) — это демон, которым управляет система. В Ubuntu 24.04 службами управляет **systemd** — система инициализации и менеджер служб. Она стартует первой (PID 1) и поднимает всё остальное.

Служба описывается **юнитом** (unit) — файлом с расширением `.service`. Лежат они в `/lib/systemd/system/` (пакетные) и `/etc/systemd/system/` (твои). Пример имени: `ssh.service`, `cron.service`, `systemd-journald.service`.

### Что такое journalctl

**journald** — служба, которая собирает логи всех служб и ядра в бинарный журнал. **journalctl** — утилита для чтения этого журнала. Аналог «Просмотра событий» в Windows. Логи хранятся в `/var/log/journal/` (если включён persistent-режим) или в `/run/log/journal/` (только в памяти, теряются при перезагрузке).

### Схема

```text
┌─────────────────────────────────────────────────────────────┐
│  systemd (PID 1)                                            │
│  ├── ssh.service        ← служба SSH (порт 22)              │
│  ├── cron.service       ← планировщик задач                 │
│  ├── systemd-journald   ← сборщик логов                     │
│  └── ...                                                    │
│                                                             │
│  Управление:  systemctl start|stop|restart|status <unit>    │
│  Логи:        journalctl -u <unit>                          │
│  Процессы:    ps, top, htop, kill                           │
└─────────────────────────────────────────────────────────────┘
```

### Ключевые понятия systemctl

- **enable** — включить автозапуск при загрузке (создаёт симлинк в `/etc/systemd/system/multi-user.target.wants/`);
- **start** — запустить сейчас (но не при загрузке);
- **disable** — выключить автозапуск;
- **stop** — остановить сейчас;
- **restart** — stop + start;
- **status** — состояние + последние строки лога;
- **daemon-reload** — перечитать файлы юнитов после правки.

Важно: `start` и `enable` — **разные вещи**. Служба может быть запущена, но не включена в автозапуск — после перезагрузки она не поднимется. Это классическая причина «вчера работало, сегодня нет».

### Сигналы

`kill` посылает процессу **сигнал**:
- `SIGTERM` (15) — «завершись корректно», процесс может сохранить данные и выйти;
- `SIGKILL` (9) — «умри немедленно», процесс не может его перехватить, данные могут потеряться;
- `SIGHUP` (1) — «перечитай конфиг» (не все демоны это умеют).

Правило: сначала `SIGTERM`, если не помогло — `SIGKILL`.

## 3. Аналогия из жизни

Представь большой офисный центр. **systemd** — это вахтёр на входе с журналом: он знает всех арендаторов (службы), открывает им двери утром (start), закрывает вечером (stop), ведёт список тех, кто должен приходить каждый день (enable). **journalctl** — это камера наблюдения и книга происшествий: кто во сколько пришёл, кто ругался, кто упал на входе. **top/htop** — это обход здания с планшетом: сколько народу в каждом кабинете, кто шумит (жрёт CPU), кто занял всю переговорку (память). **kill** — это охрана, которая выводит нарушителя: сначала вежливо просит (SIGTERM), потом выносит (SIGKILL).

Аналогия ломается в одном: в офисе вахтёр один, а в Linux службы могут зависеть друг от друга (юниты с `After=`/`Requires=`), и systemd сам решает порядок запуска — как если бы вахтёр знал, что уборщица не может войти раньше, чем электрик включит свет.

## 4. Практика и команды

Все команды — на **UBU01** под `adm.student`. Часть требует `sudo`.

### 1. `top` — живой обзор процессов

```bash
top
```

Вывод (примерный):

```text
top - 14:22:01 up  2:15,  1 user,  load average: 0.00, 0.01, 0.05
Tasks: 118 total,   1 running, 117 sleeping,   0 stopped,   0 zombie
%Cpu(s):  0.3 us,  0.2 sy,  0.0 ni, 99.5 id
MiB Mem :   1966.0 total,   1203.4 free,    312.1 used,    450.5 buff/cache
    PID USER      PR  NI    VIRT    RES  %CPU  %MEM     TIME+ COMMAND
      1 root      20   0  168000  12000   0.0   0.6   0:03.12 systemd
    812 root      20   0   15000   8000   0.0   0.4   0:00.05 sshd
```

Что смотреть: `load average` (три числа — за 1, 5, 15 минут; если больше числа ядер — перегрузка), `%Cpu(s) id` (idle — простой; если близко к 0, CPU занят), `MiB Mem` (used/free), колонка `%CPU` и `%MEM` у процессов.

Клавиши в `top`: `q` — выход, `M` — сортировка по памяти, `P` — по CPU, `k` — kill по PID.

### 2. `htop` — то же, но удобнее

```bash
sudo apt install htop
htop
```

`htop` в Ubuntu Server 24.04 по умолчанию не установлен — ставится через `apt`. В `htop` есть цветные полоски CPU/RAM, дерево процессов (`F5`), поиск (`F3`), kill (`F9`). Если `apt` не работает из-за сети — это отдельная тема (урок 35).

### 3. `ps aux` — снимок процессов

```bash
ps aux
ps aux | grep sshd
```

`a` — все пользователи, `u` — формат с пользователем, `x` — включая процессы без терминала. Вторая команда — фильтр по имени. Пример вывода:

```text
root         812  0.0  0.4  15000  8000 ?        Ss   12:05   0:00 sshd: /usr/sbin/sshd -D [listener] 0 of 10-100 startups
```

`Ss` — sleeping, лидер сессии. Если процесса нет — служба не запущена.

### 4. `systemctl status` — состояние службы

```bash
systemctl status ssh
```

Пример вывода:

```text
● ssh.service - OpenBSD Secure Shell server
     Loaded: loaded (/lib/systemd/system/ssh.service; enabled; preset: enabled)
     Active: active (running) since Mon 2026-01-12 12:05:01 MSK; 2h 17min ago
   Main PID: 812 (sshd)
     Status: "Server listening on 0.0.0.0 port 22."
```

Смотреть: `Loaded` (enabled/disabled — автозапуск), `Active` (active/inactive/failed), `Main PID`. Если `failed` — ниже будут строки лога с причиной.

### 5. `systemctl start/stop/restart/enable/disable`

```bash
sudo systemctl stop ssh
sudo systemctl start ssh
sudo systemctl restart ssh
sudo systemctl enable ssh
sudo systemctl disable ssh
```

Каждая команда — отдельное действие. `restart` = stop + start. `enable`/`disable` меняют только автозапуск, не текущее состояние.

### 6. `journalctl -u` — логи службы

```bash
sudo journalctl -u ssh --no-pager -n 50
sudo journalctl -u ssh -f
```

`-u ssh` — только по юниту `ssh`, `-n 50` — последние 50 строк, `--no-pager` — без интерактивного просмотрщика (удобно для копирования), `-f` — «следить» в реальном времени (как `tail -f`). Без `-u` — весь журнал. `-b` — только с текущей загрузки. `--since "10 min ago"` — за последние 10 минут.

### 7. `kill` и `killall` — завершение процессов

```bash
kill 1234
kill -9 1234
killall -TERM sshd
```

`kill <PID>` посылает SIGTERM. `kill -9 <PID>` — SIGKILL (жёстко). `killall <имя>` — по имени процесса. PID берётся из `ps`/`top`/`htop`.

### 8. `systemctl list-units` и `list-unit-files`

```bash
systemctl list-units --type=service --state=running
systemctl list-unit-files --type=service | grep enabled
```

Первая — какие службы **сейчас работают**. Вторая — какие **включены в автозапуск**. Разница между этими двумя списками — источник 80% проблем «после перезагрузки не работает».

### 9. `systemctl daemon-reload` — после правки юнита

```bash
sudo systemctl daemon-reload
sudo systemctl restart <unit>
```

Если ты изменил файл `.service` в `/etc/systemd/system/`, systemd не увидит изменений, пока не сделаешь `daemon-reload`. Правка юнитов — тема L2, но знать про `daemon-reload` нужно уже сейчас.

### 10. `uptime` и `free -h` — быстрая сводка

```bash
uptime
free -h
```

`uptime` — сколько работает система и `load average`. `free -h` — память в человекочитаемом виде (`-h` = human). Смотреть на `available`, а не на `free` — Linux кэширует диски в память, это нормально.

## 6. Ошибки новичков и безопасность

1. **`kill -9` сразу, без SIGTERM.** → Процесс убивается без сохранения данных, могут остаться битые файлы, блокировки, «зомби». → Сначала `kill <PID>` (SIGTERM), подожди 5–10 секунд, только потом `-9`.

2. **`systemctl start` без `enable`.** → Служба работает сейчас, но после перезагрузки не поднимется. Классика «вчера работало, сегодня нет». → Если служба должна работать постоянно — `enable` обязателен.

3. **`systemctl restart` вместо `reload`.** → Перезапуск рвёт активные соединения (например, у SSH-сессий или у базы). → Если служба поддерживает `reload` (перечитать конфиг без остановки) — используй его. Проверить: `systemctl reload <unit>`; если не поддерживает — вернёт ошибку.

4. **Правка юнита без `daemon-reload`.** → Изменения не применяются, ты думаешь, что «не работает», а systemd просто не перечитал файл. → После правки `.service` — `sudo systemctl daemon-reload`, потом `restart`.

5. **`ps aux | grep` без учёта самого `grep`.** → В выводе всегда есть строка с `grep` — новичок думает, что процесс есть. → Смотри на строки без `grep` или используй `pgrep <имя>`.

6. **`top` без понимания `load average`.** → Видишь «5.0» и паникуешь, а у тебя 8 ядер — это норма. → Сравнивай `load average` с числом ядер (`nproc`).

7. **`journalctl` без `sudo`.** → Не видишь логи системных служб (только свои). → Для системных юнитов — `sudo journalctl -u <unit>`.

8. **Остановка службы «на всякий случай».** → На боевом сервере остановка `ssh` = потеря доступа; остановка `cron` = не выполняются задачи; остановка `systemd-journald` = теряются логи. → Останавливай только то, что понимаешь, и только по заявке.

### Безопасность

- **Не отключай SSH на удалённом сервере без запасного доступа** (консоль, IPMI, второй SSH-порт). На стенде у тебя есть консоль VMware — на боевом сервере в дата-центре её может не быть.
- **Не давай `adm.student` полный sudo без пароля** «чтобы удобнее». На стенде это допустимо, в бою — грубое нарушение.
- **Не запускай `kill -9 1`** (PID 1 — systemd). На стенде это просто перезагрузка, в бою — паника и простой.
- **Логи могут содержать чувствительные данные** (IP, имена пользователей, иногда токены). Не выкладывай `journalctl` целиком в публичные чаты — вырезай лишнее.
- **Пароль стенда `Lab#2026-vektor` — только для стенда.** В реальной работе такой пароль — нарушение парольной политики.

## 7. Вопросы на собеседовании

**Вопрос 1. «Чем отличается `systemctl start` от `systemctl enable`?»**

Ответ: `start` запускает службу прямо сейчас, но не влияет на автозапуск. `enable` включает автозапуск при загрузке, но не запускает службу сейчас. Обычно нужно и то, и другое: `systemctl enable --now <unit>` делает оба действия одной командой.

*Что хочет услышать интервьюер:* что ты понимаешь разницу между «сейчас» и «при загрузке» и знаешь про `--now`.

*Красный флаг:* «Это одно и то же» или путаница в терминах.

**Вопрос 2. «Служба не стартует. Как будешь диагностировать?»**

Ответ: Сначала `systemctl status <unit>` — смотрю `Active` и `Loaded`. Если `failed` — читаю строки лога под статусом. Дальше `sudo journalctl -u <unit> -n 50 --no-pager` — ищу причину: нет файла, неверный конфиг, занят порт, нет прав. Проверяю `systemctl list-units --failed` — нет ли других упавших юнитов. Если конфиг правил я — `daemon-reload` и `restart`.

*Что хочет услышать интервьюер:* последовательность «статус → логи → причина → фикс», а не «перезагружу сервер».

*Красный флаг:* «Перезагружу и посмотрю» как первый шаг.

**Вопрос 3. «Сервер тормозит. Что смотришь в первую очередь?»**

Ответ: `uptime` — `load average` и сравниваю с числом ядер (`nproc`). `top` или `htop` — кто ест CPU и память. `free -h` — не кончилась ли память (смотрю `available`, не `free`). Если вижу процесс-пожиратель — `ps aux | grep <имя>`, смотрю владельца и что это вообще. Дальше решаю: это штатная нагрузка или аномалия.

*Что хочет услышать интервьюер:* что ты знаешь про `load average` и `available`, и не путаешь `free` с `available`.

*Красный флаг:* «Открою диспетчер задач» (на Linux его нет) или «перезагружу».

**Вопрос 4. «Как корректно завершить процесс?»**

Ответ: Сначала `kill <PID>` — это SIGTERM, процесс может сохранить данные и выйти. Жду несколько секунд, проверяю `ps`. Если не завершился — `kill -9 <PID>` (SIGKILL), но это крайняя мера: данные могут потеряться. PID беру из `ps`/`top`/`htop` или `pgrep`.

*Что хочет услышать интервьюер:* что ты знаешь про SIGTERM vs SIGKILL и не начинаешь с `-9`.

*Красный флаг:* «Сразу `kill -9`, чтобы наверняка».

**Вопрос 5. «Где смотреть логи службы в Ubuntu?»**

Ответ: `journalctl -u <unit>` — логи конкретной службы. `-n 50` — последние 50 строк, `-f` — следить в реальном времени, `--since "10 min ago"` — за период, `-b` — с текущей загрузки. Для системных юнитов нужен `sudo`. Если журнал не persistent — после перезагрузки старые логи теряются.

*Что хочет услышать интервьюер:* что ты знаешь `journalctl` и его ключи, и понимаешь про `sudo` и persistent-режим.

*Красный флаг:* «Смотрю `/var/log/syslog`» без упоминания `journalctl` (в современных Ubuntu основной журнал — journald).
