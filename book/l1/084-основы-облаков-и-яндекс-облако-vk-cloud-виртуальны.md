# Основы облаков и Яндекс Облако / VK Cloud: виртуальные машины, сети, диски

## 1. Введение (зачем это нужно в реальной работе)

Заявка в учебной системе «Вектора»:

В Москве это уже норма: стартапы живут в Yandex Cloud и VK Cloud, крупные компании держат гибрид — часть в своём ЦОД, часть в облаке. Даже L1-специалисту приходится: создать ВМ по инструкции, проверить, что она пингуется, открыть порт в облачной сети, посмотреть, почему «не подключается по SSH», и не забыть удалить ресурсы, чтобы не пришёл счёт на 30 тысяч рублей.

После этой главы ты будешь понимать, из чего состоит облако (виртуальная машина, сеть, диск, образ, группа безопасности), уметь создать ВМ в Yandex Cloud и VK Cloud через веб-консоль, подключиться к ней по SSH, разобраться с типовыми проблемами «не пингуется / не пускает / не видно диска» и аккуратно всё удалить. Плюс поймёшь, чем облако отличается от твоей VMware Workstation на домашнем ПК — и почему в работе это разные инструменты для разных задач.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Облако** — это чужие серверы в дата-центре, которые ты арендуешь по кусочкам через веб-панель или API. Провайдер сам следит за железом, электричеством, охлаждением и сетью. Ты получаешь виртуальную машину (ВМ), виртуальную сеть, виртуальные диски и платишь за то, что реально используешь: часы работы ВМ, гигабайты диска, гигабайты трафика наружу.

Ключевые понятия, одинаковые у всех провайдеров (Yandex Cloud, VK Cloud, Selectel, Cloud.ru, AWS, Azure — названия разные, суть одна):

- **Виртуальная машина (instance / ВМ)** — то же, что у тебя в VMware, только на железе провайдера. Имеет CPU, RAM, диски, сетевые интерфейсы.
- **Образ (image)** — шаблон, из которого создаётся ВМ: Ubuntu 24.04, Windows Server 2022, Astra Linux и т.д. Аналог ISO + уже установленная ОС.
- **Диск (disk / volume)** — блочное хранилище. Бывает **загрузочный** (с ОС) и **дополнительный** (данные). Диски в облаке — сетевые, их можно отключать от одной ВМ и подключать к другой.
- **Сеть (VPC, virtual private cloud)** — твоя изолированная сеть в облаке. Внутри — **подсеть** с диапазоном адресов, как у тебя 10.10.10.0/24 в VMnet8.
- **Группа безопасности (security group)** — облачный файрвол. По умолчанию входящий трафик закрыт, надо явно разрешить порт (22 для SSH, 3389 для RDP, 80/443 для веба).
- **Публичный IP** — адрес, по которому ВМ видна из интернета. Без него до ВМ не достучаться снаружи.
- **Внутренний IP** — адрес внутри твоей облачной сети, по нему ВМ общаются друг с другом.

Схема типичной облачной установки:

```text
   Интернет
      │
      │  (публичный IP, например 158.160.x.x)
      ▼
 ┌────────────────────────────────────────────┐
 │  Облачная сеть (VPC) 10.128.0.0/16         │
 │                                            │
 │   ┌──────────────┐    ┌──────────────┐     │
 │   │ ВМ web-01    │    │ ВМ db-01     │     │
 │   │ 10.128.0.5   │───▶│ 10.128.0.6   │     │
 │   │ публичный IP │    │ только внутр.│     │
 │   └──────────────┘    └──────────────┘     │
 │        │                    │              │
 │   Группа безопасности:      │              │
 │   разрешено 22, 80, 443     │              │
 └────────────────────────────────────────────┘
```

Чем облако отличается от твоей VMware Workstation:

| | VMware Workstation (дома) | Облако |
|---|---|---|
| Где железо | твой ПК | ЦОД провайдера |
| Кто отвечает за железо | ты | провайдер |
| Платишь | за электричество и ПК | за часы ВМ, диск, трафик |
| Сеть | VMnet8, VMnet10 | VPC, подсети, группы безопасности |
| Создание ВМ | 30–60 минут (установка ОС) | 1–3 минуты (из образа) |
| Удаление | удалил папку | удалил ВМ, диск, IP — иначе счёт |

Важно: **облако — это не «VMware, но в интернете»**. В облаке ты не настраиваешь BIOS, не ставишь ОС с ISO (хотя можно), не лезешь в гипервизор. Ты работаешь с абстракциями: «дай мне ВМ 2 vCPU / 4 ГБ RAM / 30 ГБ диск с Ubuntu 24.04 в подсети X с публичным IP». Всё остальное — забота провайдера.

**Yandex Cloud** и **VK Cloud** — два крупнейших российских публичных облака. Оба дают бесплатный пробный период (обычно грант на несколько тысяч рублей на 1–2 месяца) [ПРОВЕРИТЬ актуальные условия на 2026 год]. Оба принимают карты «Мир», оба имеют ЦОД в РФ (это важно для 152-ФЗ — персональные данные россиян должны храниться в России, ты это проходил в уроке 67).

## 3. Аналогия из жизни

Представь, что тебе нужна мастерская на неделю, чтобы покрасить шкаф. Дома красить нельзя — жена выгонит. Ты едешь в **коворкинг для мастеров**: там есть помещение (ВМ), верстак (диск), розетки и свет (сеть), и охрана на входе, которая пускает только по пропуску (группа безопасности). Ты платишь за каждый час аренды и за каждый киловатт. Когда шкаф покрашен — убираешь за собой, сдаёшь ключ, иначе продолжат списывать деньги. Если забыл выключить свет — счёт придёт больше, чем ты планировал.

Аналогия перестаёт работать в одном месте: в коворкинге ты физически видишь, что происходит, а в облаке ВМ может «не пинговаться» из-за группы безопасности, о которой ты забыл, — и это невидимо, пока не откроешь панель.

## 4. Практика и команды

Облачные провайдеры управляются двумя способами: **веб-консоль** (клики) и **CLI** (команды). L1 обычно работает через консоль, но знать CLI полезно — на нём построены скрипты и IaC (инфраструктура как код, урок 85).

### 4.1. Веб-консоль Yandex Cloud — создание ВМ

Путь по меню: **console.yandex.cloud → каталог (folder) → Compute Cloud → Виртуальные машины → Создать ВМ**. Заполняешь: имя, зона доступности (`ru-central1-a`), образ (Ubuntu 24.04), размер (2 vCPU, 2 ГБ RAM), диск (20 ГБ SSD), подсеть, публичный IP, SSH-ключ. Через 1–2 минуты ВМ в статусе `RUNNING`.

### 4.2. Веб-консоль VK Cloud — создание ВМ

Путь: **cloud.vk.com → Проект → Облачные вычисления → Виртуальные машины → Создать**. Аналогично: имя, образ, тип ВМ, диск, сеть, ключ SSH. VK Cloud часто предлагает готовые пресеты («Ubuntu 24.04 + Docker» и т.п.).

### 4.3. Yandex Cloud CLI — установка и настройка

```bash
curl -sSL https://storage.yandexcloud.net/yandexcloud-yc/install.sh | bash
exec -l $SHELL
yc init
```

`yc init` спросит OAuth-токен (получаешь в браузере), каталог по умолчанию, зону. После этого все команды `yc` работают от твоего аккаунта. [ПРОВЕРИТЬ актуальный URL установщика на 2026 год — провайдеры иногда меняют пути.]

### 4.4. Создать ВМ через `yc`

```bash
yc compute instance create \
  --name test-vm-01 \
  --zone ru-central1-a \
  --network-interface subnet-name=default-ru-central1-a,nat-ip-version=ipv4 \
  --create-boot-disk image-folder-id=standard-images,image-family=ubuntu-2404-lts \
  --ssh-key ~/.ssh/id_ed25519.pub
```

Ключи: `--name` — имя ВМ, `--zone` — зона доступности, `--network-interface` — подсеть и публичный IP (`nat-ip-version=ipv4`), `--create-boot-disk` — загрузочный диск из семейства образов Ubuntu 24.04, `--ssh-key` — публичный ключ, который попадёт в `~/.ssh/authorized_keys` пользователя по умолчанию (обычно `ubuntu` или `yc-user`). Вывод примерный:

```text
done (12s)
id: fhm1a2b3c4d5e6f7g8h9
folder_id: b1g...
created_at: "2026-01-15T10:23:45Z"
name: test-vm-01
status: RUNNING
network_interfaces:
  - ip_address: 10.128.0.15
    nat_ip_address: 158.160.12.34
```

Смотри `status: RUNNING` и `nat_ip_address` — это твой публичный IP.

### 4.5. Список ВМ и получение IP

```bash
yc compute instance list
yc compute instance get test-vm-01
```

Первая команда — таблица всех ВМ (имя, зона, статус, внутренний IP). Вторая — подробности одной ВМ, включая публичный IP. Если `nat_ip_address` пустой — публичного IP нет, снаружи не подключишься.

### 4.6. Подключение по SSH

```bash
ssh -i ~/.ssh/id_ed25519 ubuntu@158.160.12.34
```

`-i` — приватный ключ. Пользователь `ubuntu` — стандартный для образов Ubuntu в Yandex Cloud [ПРОВЕРИТЬ для конкретного образа]. Если «Permission denied (publickey)» — либо ключ не тот, либо в ВМ не попал публичный ключ, либо группа безопасности не пускает 22 порт.

### 4.7. VK Cloud CLI (openstack)

VK Cloud построен на OpenStack, CLI называется `openstackclient`. Установка:

```bash
pip install python-openstackclient
```

Дальше скачиваешь в панели VK Cloud файл `openrc.sh` (в разделе «Проект → API-ключи» или «Доступ к API») и подгружаешь его:

```bash
source openrc.sh
openstack server list
openstack server show test-vm-01
```

`openstack server list` — таблица ВМ (ID, имя, статус, сети). `openstack server show` — подробности. [ПРОВЕРИТЬ точные названия пунктов меню VK Cloud на 2026 год — интерфейс меняется.]

### 4.8. Проверка доступности ВМ снаружи

```bash
ping 158.160.12.34
nc -zv 158.160.12.34 22
```

`ping` проверяет ICMP — но в облаках ICMP часто **закрыт по умолчанию** группой безопасности, поэтому «не пингуется» ≠ «ВМ не работает». `nc -zv` (netcat) проверяет TCP-порт 22: если «succeeded» — SSH открыт, если «Connection refused» или таймаут — порт закрыт или служба не слушает. На Windows аналог: `Test-NetConnection 158.160.12.34 -Port 22` в PowerShell.

### 4.9. Группы безопасности — открыть порт

В Yandex Cloud через CLI:

```bash
yc vpc security-group update-rules <sg-id> --add-rule "direction=ingress,port=22,protocol=tcp,v4-cidrs=[0.0.0.0/0]"
```

`direction=ingress` — входящий, `port=22` — SSH, `protocol=tcp`, `v4-cidrs=[0.0.0.0/0]` — откуда (все адреса; в проде так нельзя, только свой офисный IP). Через консоль: **VPC → Группы безопасности → нужная группа → Редактировать → Добавить правило**.

### 4.10. Диски — список и подключение

```bash
yc compute disk list
yc compute disk attach --instance-name test-vm-01 --disk-name data-disk-01
```

`disk list` — все диски (имя, размер, статус, к какой ВМ привязан). `disk attach` подключает дополнительный диск к работающей ВМ. Внутри Linux он появится как `/dev/vdb` (или `/dev/sdb`), его надо разметить (`fdisk`), отформатировать (`mkfs.ext4`) и смонтировать (`mount`). Это ты уже умеешь из уроков 24–25.

### 4.11. Удаление ресурсов (важнее, чем создание!)

```bash
yc compute instance delete test-vm-01
yc compute disk delete data-disk-01
```

Удалять надо **всё**: ВМ, диски (они не удаляются вместе с ВМ автоматически, если создавались отдельно), статические публичные IP (они платные, если не привязаны). В VK Cloud: `openstack server delete test-vm-01`, потом через панель удалить диск и IP.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

Тема облачная, поэтому лабораторная идёт **на твоём домашнем ПК** (Windows-хост) с доступом в интернет и браузером. ВМ стенда «Вектор» не меняются — облако живёт отдельно. Но снапшот всё равно делаем: если что-то пойдёт не так с сетью хоста или ты случайно тронешь WIN11-CL01, откатишься.

### Предусловия

- Стенд «Вектор» в состоянии после урока 83: DC01 с доменом `corp.vektor.lab`, WIN11-CL01 и WIN10-CL02 в домене, FS01, UBU01, ASTRA01 — все работают. Ничего из этого мы не трогаем.
- На хосте есть браузер, доступ в интернет.
- Зарегистрирован аккаунт в Yandex Cloud (или VK Cloud) с активированным пробным периодом. Если пробный период недоступен из твоей ситуации — можно ограничиться веб-консолью без создания ВМ, но лучше создать и сразу удалить, чтобы увидеть полный цикл.
- На хосте есть SSH-клиент (в Windows 10/11 он встроен: `ssh` в PowerShell).
- Ключ SSH на хосте: если нет — сгенерируй `ssh-keygen -t ed25519` в PowerShell.

### Снапшот

В VMware Workstation на хосте: снапшот `before-l1-084` на **WIN11-CL01** (единственная ВМ, которую теоретически можно задеть, если будешь проверять связность из неё). Остальные ВМ не трогаем, но для порядка можно снять снапшот и с WIN10-CL02. Команда через `vmrun`:

```powershell
vmrun -T ws -vp "Lab#2026-vektor" snapshot "C:\Lab\vektor\VMs\WIN11-CL01\WIN11-CL01.vmx" before-l1-084
```

[ПРОВЕРИТЬ синтаксис `vmrun snapshot` в твоей версии VMware Workstation — в некоторых версиях требуется `-vp` только для зашифрованных ВМ, а WIN11-CL01 у нас зашифрована из-за vTPM.]

### Шаги

1. **Регистрация в Yandex Cloud.** Открой `console.yandex.cloud`, войди через Яндекс ID. Создай платёжный аккаунт (привяжи карту «Мир» — без неё пробный период не активируется). Создай каталог (folder) с именем `vektor-lab`. Ожидаемо: видишь консоль с пустым каталогом.

2. **Создай SSH-ключ на хосте** (если ещё нет). В PowerShell:
    ```powershell
    ssh-keygen -t ed25519 -f $env:USERPROFILE\.ssh\id_ed25519
    ```
    Ожидаемо: два файла — `id_ed25519` (приватный) и `id_ed25519.pub` (публичный). Публичный открой в блокноте — он понадобится.

3. **Создай ВМ через веб-консоль.** Compute Cloud → Виртуальные машины → Создать ВМ. Имя `test-vm-01`, зона `ru-central1-a`, образ Ubuntu 24.04 LTS, 2 vCPU / 2 ГБ RAM, диск 20 ГБ SSD, публичный IP — «Автоматически», SSH-ключ — вставь содержимое `id_ed25519.pub`. Создай. Ожидаемо: через 1–2 минуты ВМ в статусе `RUNNING`, есть внутренний и публичный IP.

4. **Проверь ВМ через CLI.** Установи `yc` (п. 4.3), выполни `yc init`, потом:
    ```bash
    yc compute instance list
    ```
    Ожидаемо: таблица с одной строкой `test-vm-01`, статус `RUNNING`, IP-адреса. Сверь публичный IP с тем, что в консоли.

5. **Подключись по SSH.**
    ```bash
    ssh -i $env:USERPROFILE\.ssh\id_ed25519 ubuntu@<публичный-IP>
    ```
    Ожидаемо: приглашение `ubuntu@test-vm-01:~$`. Если «Permission denied» — вернись к п. 3 и проверь, что ключ вставлен целиком (одна строка, начинается с `ssh-ed25519`).

6. **Проверь сеть изнутри ВМ.**
    ```bash
    ip a
    ip r
    ping -c 3 8.8.8.8
    ```
    Ожидаемо: интерфейс `eth0` с внутренним IP `10.128.0.x`, маршрут по умолчанию через шлюз подсети, пинг до 8.8.8.8 идёт (исходящий трафик в облаке обычно открыт). Если пинга нет — проверь, что у ВМ есть публичный IP.

7. **Проверь доступность порта с хоста.**
    ```powershell
    Test-NetConnection <публичный-IP> -Port 22
    ```
    Ожидаемо: `TcpTestSucceeded : True`. Если `False` — группа безопасности закрывает 22 порт (в Yandex Cloud по умолчанию группа `default-sg` обычно разрешает 22, но проверь).

8. **Создай дополнительный диск и подключи.**
    ```bash
    yc compute disk create --name data-disk-01 --size 10GB --zone ru-central1-a
    yc compute disk attach --instance-name test-vm-01 --disk-name data-disk-01
    ```
    Ожидаемо: диск создан, привязан. Внутри ВМ `lsblk` покажет новый диск `/dev/vdb` (10G, без файловой системы).

9. **Разметь и смонтируй диск** (внутри ВМ):
    ```bash
    sudo mkfs.ext4 /dev/vdb
    sudo mkdir /mnt/data
    sudo mount /dev/vdb /mnt/data
    df -h /mnt/data
    ```
    Ожидаемо: `df` показывает 10G, смонтированные в `/mnt/data`. Запиши туда файл `echo hello > /mnt/data/test.txt` и проверь `cat`.

10. **Проверь группу безопасности — закрой и открой порт.** В консоли: VPC → Группы безопасности → группа ВМ → удали правило для 22. С хоста снова `Test-NetConnection <IP> -Port 22` — ожидаемо `False` (SSH не подключается). Верни правило — снова `True`. Это упражнение на понимание, что «не пускает» чаще всего = группа безопасности.

11. **Удали всё.** Сначала отмонтируй диск внутри ВМ (`sudo umount /mnt/data`), выйди из SSH (`exit`). Потом:
    ```bash
    yc compute instance delete test-vm-01
    yc compute disk delete data-disk-01
    ```
    Ожидаемо: `yc compute instance list` пуст, `yc compute disk list` пуст. В консоли проверь, что нет «висящих» публичных IP (они платные).

12. **Запиши в журнал.** В `C:\Lab\vektor\stand-log.md` добавь строку: «Урок 84: облако — создана и удалена ВМ test-vm-01 в Yandex Cloud, стенд „Вектор“ не менялся».

### Проверка

- [ ] ВМ `test-vm-01` создана в Yandex Cloud, статус `RUNNING`, есть публичный IP.
- [ ] SSH-подключение к ВМ работает под пользователем `ubuntu`.
- [ ] Изнутри ВМ виден внутренний IP `10.128.0.x` и работает исходящий пинг.
- [ ] `Test-NetConnection` с хоста показывает `True` для порта 22 при открытой группе безопасности и `False` — при закрытой.

### Сломай и почини

**Заявка:**

> **Пользователь:** Иван Иванов (бухгалтерия), ВМ WIN11-CL01
> **Что написал:** «Мне для теста 1С дали облачную машину `test-vm-01` с адресом 158.160.12.34. Говорят, SSH-ключ мой. Но `ssh ubuntu@158.160.12.34` пишет `Connection timed out`. Пинг тоже не идёт. Что делать?»
> **Срочность:** высокая, тест 1С завтра.

**Как воспроизвести поломку** (на стенде, в облаке):

1. Создай ВМ `test-vm-01` как в лабораторной (шаги 1–3).
2. В группе безопасности **удали правило для порта 22** (или не создавай его — в некоторых конфигурациях группа по умолчанию не содержит SSH).
3. С хоста проверь: `Test-NetConnection 158.160.12.34 -Port 22` → `False`. `ping 158.160.12.34` → таймаут (ICMP тоже закрыт).

**Диагностика по шагам:**

1. **Проверь, что ВМ вообще работает.** В консоли Yandex Cloud: Compute Cloud → Виртуальные машины → `test-vm-01` → статус. Если `RUNNING` — ВМ жива, проблема в сети. Если `STOPPED` — включи.
2. **Проверь публичный IP.** В карточке ВМ есть `nat_ip_address`. Если пусто — публичного IP нет, снаружи не подключиться. Привяжи публичный IP (в консоли: «Сетевой интерфейс → Публичный IP → Добавить»).
3. **Проверь группу безопасности.** VPC → Группы безопасности → группа, привязанная к ВМ. Есть ли правило `ingress tcp 22`? Если нет — добавь.
4. **Проверь, что служба SSH слушает.** Если есть доступ через серийную консоль (в Yandex Cloud: «Подключиться → Серийная консоль») — зайди и выполни `sudo ss -tlnp | grep :22`. Должно быть `LISTEN 0 128 0.0.0.0:22`. Если пусто — `sudo systemctl status ssh` и `sudo systemctl start ssh`.
5. **Проверь ключ.** Если порт открыт, но «Permission denied» — значит, публичный ключ не попал в `~/.ssh/authorized_keys` пользователя `ubuntu`. Через серийную консоль проверь `cat ~/.ssh/authorized_keys` — там должен быть твой `ssh-ed25519 ...`.

**Решение:** добавить правило `ingress tcp 22` в группу безопасности (и, если нужно, `ingress icmp` для пинга). После этого `Test-NetConnection` → `True`, SSH работает.

## 6. Ошибки новичков и безопасность

1. **Забыл удалить ВМ после теста.** К чему приводит: счёт за месяц на несколько тысяч рублей, а на пробном периоде — блокировка аккаунта. Как правильно: после каждого эксперимента — чек-лист «ВМ, диск, публичный IP, снапшот» и удаление всего.

2. **Открыл порт 22 (или 3389) для всего интернета `0.0.0.0/0`.** К чему приводит: боты за пару часов подберут пароль (если он есть) или начнут брутфорсить SSH. Как правильно: в группе безопасности указывать конкретный IP офиса/дома, а не весь интернет. Для SSH — только ключи, без пароля.

3. **Путает «не пингуется» и «не работает».** К чему приводит: час диагностики, хотя ВМ жива, просто ICMP закрыт. Как правильно: проверять TCP-порт (`Test-NetConnection -Port 22`), а не только `ping`.

4. **Создал ВМ без публичного IP и удивляется, что не подключается.** К чему приводит: потеря времени. Как правильно: при создании ВМ явно включать публичный IP, если нужен доступ снаружи; для внутренних ВМ — не включать (безопаснее и дешевле).

5. **Забыл, что диск не удаляется вместе с ВМ.** К чему приводит: платишь за диск, который ни к чему не привязан. Как правильно: удалять диски отдельно, проверять `yc compute disk list`.

6. **Использует пароль root вместо SSH-ключа.** К чему приводит: брутфорс, компрометация. Как правильно: только ключи, пароль root отключён в облачных образах по умолчанию.

7. **Создаёт ВМ в зоне, где нет нужного образа или квоты.** К чему приводит: ошибка создания, потеря времени. Как правильно: смотреть список доступных образов и квот в консоли перед созданием.

8. **Хранит секреты (пароли, ключи) в открытом виде в репозитории.** К чему приводит: утечка, компрометация аккаунта. Как правильно: ключи — только локально, в репозиторий — `.gitignore`; для CI/CD — секреты в переменных окружения (урок 83).

### Безопасность

В боевой среде **нельзя**:

- Открывать порты `0.0.0.0/0` без крайней необходимости (и тогда — только с MFA и мониторингом).
- Оставлять ВМ с публичным IP без обновлений и файрвола.
- Хранить ключи и пароли в открытом виде в коде, в Git, в заметках.
- Создавать ресурсы без тегов/меток — потом не найдёшь, кто и зачем.
- Игнорировать биллинг — облако списывает деньги за всё, что работает.

В учебной лаборатории мы делаем упрощения (открываем 22 для всех, используем тестовые ключи) — в реальной работе так нельзя.

## 7. Вопросы на собеседовании

**Вопрос 1. Чем облако отличается от виртуализации на своём сервере?**

Как задают: «Вот у нас VMware в ЦОД, зачем нам облако?»

Ответ: «В облаке провайдер отвечает за железо, сеть, электричество, охлаждение — я получаю ВМ, сеть и диск через панель или API за минуты. В своей виртуализации я сам админю гипервизор, железо, обновления. Облако удобно для быстрых экспериментов, пиков нагрузки, гибридных сценариев; своя виртуализация — для предсказуемой нагрузки и данных, которые нельзя выносить. На стенде я работал и с VMware Workstation, и с Yandex Cloud — разница именно в том, кто отвечает за нижний слой».

Что хочет услышать интервьюер: понимание модели ответственности (IaaS/PaaS), а не заученные названия.

Красный флаг: «облако — это просто чужие серверы» без понимания, что за это платят и что за железо отвечает провайдер.

**Вопрос 2. Пользователь говорит: „ВМ в облаке не пингуется“. Твои действия?**

Как задают: «Вот заявка, что делаешь?»

Ответ: «Сначала проверяю в консоли статус ВМ — `RUNNING` или `STOPPED`. Потом публичный IP — есть ли он. Потом группу безопасности — открыт ли ICMP и нужный TCP-порт. Потом проверяю TCP-порт через `Test-NetConnection -Port 22` — потому что ICMP в облаках часто закрыт по умолчанию, и „не пингуется“ ≠ „не работает“. Если порт открыт, но SSH не пускает — смотрю ключ и службу ssh внутри ВМ через серийную консоль».

Что хочет услышать: системную диагностику по слоям (ВМ → IP → группа безопасности → служба), а не «перезагрузите».

Красный флаг: сразу лезет в ВМ, не проверив группу безопасности.

**Вопрос 3. Что такое группа безопасности и чем она отличается от файрвола внутри ОС?**

Как задают: «Зачем в облаке ещё один файрвол?»

Ответ: «Группа безопасности — это облачный файрвол на уровне сети, он фильтрует трафик до того, как он попадёт в ВМ. Файрвол внутри ОС (iptables, Windows Firewall) — второй слой, уже внутри ВМ. Обычно работают оба: группа безопасности закрывает лишнее снаружи, файрвол ОС — детализирует правила. Если порт закрыт в группе — до файрвола ОС трафик не дойдёт».

Что хочет услышать: понимание двух слоёв защиты.

Красный флаг: «достаточно одного файрвола».

**Вопрос 4. Как не забыть удалить ресурсы и не получить счёт?**

Как задают: «Как контролируешь расходы в облаке?»

Ответ: «После каждого эксперимента — чек-лист: ВМ, диски, публичные IP, снапшоты, балансировщики. Проверяю `yc compute instance list` и `yc compute disk list` — пусто ли. Смотрю раздел биллинга. В проде — теги/метки на ресурсах, чтобы понимать, чьи они, и алерты на аномальный расход. На стенде я это отрабатывал: создал ВМ, удалил, проверил, что списки пусты».

Что хочет услышать: дисциплину и понимание, что облако — это деньги.

Красный флаг: «удаляю ВМ, а диск пусть висит».

**Вопрос 5. Что такое VPC и зачем подсеть?**

Как задают: «Объясни, как устроена сеть в облаке».

Ответ: «VPC — виртуальная частная сеть, моя изолированная сеть в облаке. Внутри неё — подсети с диапазонами адресов, как в обычной сети. ВМ в одной подсети видят друг друга напрямую, между подсетями — маршрутизация. Публичный IP даёт доступ снаружи, внутренний — только внутри VPC. Группы безопасности фильтруют трафик. Это похоже на мою домашнюю VMnet8, только управляется через панель».

Что хочет услышать: понимание, что облачная сеть — это те же IP-подсети и маршрутизация, просто управляемые иначе.

Красный флаг: «VPC — это что-то магическое».
