# Установка и обновление ПО: apt, dpkg, репозитории

## 1. Введение (зачем это нужно в реальной работе)

```
Заявка #L1-0271
Пользователь: Сидоров (склад)
ВМ: UBU01 (10.10.10.30)
Что написал: «Здравствуйте! По инструкции подрядчика должен посмотреть
архив с накладными на сервере UBU01 в файловом менеджере mc.
Ввожу sudo apt install mc — ответ:
"E: Unable to locate package mc". Отгрузка до 18:00, помогите!»
Срочность: средняя
```

В Windows вы ставите программу мышкой, а обновления приходят сами через Windows Update. В Linux почти всё то же самое, но руками и командами: пакеты, зависимости, репозитории. На L1 это одна из самых частых Linux-заявок: «не ставится программа», «нет такой команды», «apt ругается», «после обновления всё сломалось».

После этой главы вы должны уметь: объяснить разницу между `apt` и `dpkg`; обновить список пакетов и поставить/удалить программу; посмотреть, что за пакет установлен и какие файлы он принёс; понять по выводу apt, чего ему не хватает (сеть, DNS, репозиторий, зависимость); починить сломанное состояние пакетной базы; и не навредить серверу командой, которую нашли в интернете.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Пакет** — это архив с программой плюс метаданные: имя, версия, архитектура, список файлов и список зависимостей. В семействе Debian (Ubuntu, Astra Linux, РЕД ОС, ALT — у каждого свои детали, см. урок 30) формат пакета — `.deb`.

**Зависимость** — пакет, без которого этот работать не будет. Например, `htop` требует библиотеки `libncursesw6`, `libtinfo6`. Менеджер пакетов ставит их автоматически — это его главная ценность.

Два уровня инструментов:

- **`dpkg`** — низкоуровневый. Умеет «распаковать вот этот файл .deb и разложить файлы по каталогам». Про зависимости он знает, но скачать их не может: показывает ошибку и оставляет пакет в недонастроенном состоянии.
- **`apt`** — высокоуровневый. Ходит в **репозитории** (склады пакетов по HTTP/HTTPS), скачивает индексы, сам разруливает зависимости, вызывает `dpkg` для реальной установки.

**Репозиторий** — сервер с деревом пакетов и подписанными индексами. apt скачивает индекс (`Packages`), где перечислено всё, что есть на складе, и уже по нему понимает, что можно поставить. Индексы и пакеты подписаны GPG-ключом: apt проверяет подпись, поэтому подменённый пакет с левого зеркала не встанет.

Схема:

```text
        ВЫ                 UBU01                        ИНТЕРНЕТ
  +-----------+     +------------------+          +----------------------+
  | sudo apt  | --> | apt (high-level) | --HTTP--> | archive.ubuntu.com   |
  | install   |     |  /etc/apt/       |   :80/443 |  dists/noble/main/   |
  |  htop     |     |  sources.list.d/ | <--GPG--- |   binary-amd64/      |
  +-----------+     |      |           |           |   Packages.gz        |
                    |      v           |           |  pool/main/h/htop/   |
                    | dpkg (low-level) |           +----------------------+
                    |      |           |
                    |      v           |
                    | файлы в /usr,    |
                    | /etc, /var       |
                    +------------------+
```

Где что лежит на диске:

| Путь | Что это |
|------|---------|
| `/etc/apt/sources.list.d/ubuntu.sources` | список репозиториев (в Ubuntu 24.04 — новый формат deb822, файл `.sources`) |
| `/etc/apt/sources.list` | старый формат, по одной строке на репозиторий; в 24.04 пустой/закомментирован |
| `/var/lib/apt/lists/` | скачанные индексы (то, что обновляет `apt update`) |
| `/var/cache/apt/archives/` | скачанные `.deb` |
| `/var/lib/dpkg/status` | база: что установлено и в каком состоянии |
| `/var/log/apt/history.log`, `/var/log/dpkg.log` | журналы: кто, что и когда поставил |

По модели OSI это всё прикладной уровень (HTTP/HTTPS) плюс DNS (порт 53), чтобы имя зеркала превратилось в IP. Поэтому «apt не работает» в половине случаев — это не apt, а сеть или DNS.

## 3. Аналогия из жизни

Представьте стройку. `dpkg` — это кладовщик: ему принесли коробку с деталью, он её аккуратно поставил на полку и записал в журнал. Но искать деталь по поставщикам, выяснять, что к шкафу нужны ещё петли и шурупы, и заказывать всё вместе — не его работа. Этим занимается `apt` — снабженец: у него есть каталог поставщика (репозиторий), он сверяет, чего на складе не хватает, заказывает комплект целиком и только потом зовёт кладовщика всё разложить.

Аналогия перестаёт работать в одном месте: снабженец в жизни не проверяет цифровую печать на каждой коробке, а apt проверяет GPG-подпись индексов и пакетов всегда — иначе любой мог бы подсунуть «лекарство» вместо программы.

## 4. Практика и команды

Все команды — на UBU01 под своим пользователем с `sudo`.

**1. Посмотреть, какие репозитории подключены**

```bash
cat /etc/apt/sources.list.d/ubuntu.sources
ls -l /etc/apt/sources.list /etc/apt/sources.list.d/
```

Типичный (сокращённый) вывод:

```text
Types: deb
URIs: http://archive.ubuntu.com/ubuntu/
Suites: noble noble-updates noble-backports
Components: main restricted universe multiverse
Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg
```

Смотрим: правильный ли URI, есть ли компонент `universe` (там живёт половина «народных» программ — `htop`, `mc`, `tree`), указан ли ключ подписи.

**2. Обновить индексы пакетов — `apt update`**

```bash
sudo apt update
```

```text
Hit:1 http://archive.ubuntu.com/ubuntu noble InRelease
Get:2 http://archive.ubuntu.com/ubuntu noble-updates InRelease [126 kB]
Reading package lists... Done
Building dependency tree... Done
5 packages can be upgraded. Run 'apt list --upgradable' to see them.
```

`update` ничего не устанавливает — только обновляет каталог. Если здесь `Temporary failure resolving` — проблема в DNS, `Could not connect` — в сети/шлюзе.

**3. Найти и изучить пакет**

```bash
apt search htop
apt show htop
apt policy htop
```

`apt policy` — самая полезная для диагностики: показывает установленную версию, кандидата на установку и из какого репозитория он берётся. Если «Candidate: (none)» — пакета нет в индексах.

**4. Установить пакет**

```bash
sudo apt install htop
sudo apt install -y --no-install-recommends tree
```

`-y` — не спрашивать подтверждение; `--no-install-recommends` — не тянуть «рекомендованные» пакеты (меньше мусора на сервере). В выводе читаем строку `The following NEW packages will be installed:` и итоговое `Setting up htop (...)`.

**5. Что установлено и что можно обновить**

```bash
apt list --installed | wc -l
apt list --upgradable
```

**6. Обновить систему**

```bash
sudo apt upgrade
sudo apt full-upgrade   # если требуется умение удалять/добавлять пакеты ради обновления
```

`upgrade` не удаляет пакеты; `full-upgrade` может — на боевом сервере это осознанное решение, а не «на всякий случай». После обновления ядра нужна перезагрузка.

**7. Список пакетов через dpkg**

```bash
dpkg -l | grep ^ii | wc -l
dpkg -l htop
dpkg -l | grep -v ^ii     # всё, что НЕ в нормальном состоянии
```

```text
Desired=Unknown/Install/Remove/Purge/Hold
| Status=Not/Inst/Conf-files/Unpacked/halF-conf/Half-inst/trig-aWait/Trig-pend
ii  htop   3.3.0-4build1   amd64   interactive processes viewer
```

`ii` = «хочу установить» + «установлен и настроен». Лютая для L1 комбинация — `iU`/`iF`: распакован, но не настроен (сломанные зависимости).

**8. Какие файлы принёс пакет и кто владеет файлом**

```bash
dpkg -L tree | head -n 15
dpkg -S $(which htop)
```

`-L` — list files, `-S` — search (поиск пакета-владельца). Ответ вида `htop: /usr/bin/htop`.

**9. Удаление**

```bash
sudo apt remove htop       # убрать программу, конфиги останутся
sudo apt purge htop        # убрать вместе с конфигами
sudo apt autoremove        # убрать зависимости, которые больше никому не нужны
```

**10. Ручная установка .deb и починка**

```bash
sudo dpkg -i /tmp/nmap_*.deb          # низкий уровень: зависимости не подтянет
sudo apt --fix-broken install         # доустановить недостающее
sudo dpkg --configure -a              # доделать прерванную настройку
```

Правильный способ поставить локальный файл — `sudo apt install ./nmap_*.deb` (обязательно `./`): apt сам разберётся с зависимостями.

**11. Заморозить версию и почистить кэш**

```bash
sudo apt-mark hold <пакет>     # не обновлять
sudo apt-mark unhold <пакет>
sudo apt clean                 # вычистить /var/cache/apt/archives
```

**12. Журналы**

```bash
tail -n 30 /var/log/apt/history.log
tail -n 20 /var/log/dpkg.log
```

Здесь видно, что и когда ставили — это ваш главный источник при разборе «а что вчера делали на сервере?».

**GUI.** На UBU01 графики нет. На десктопных Ubuntu есть «Программы и обновления» (`software-properties-gtk`) [ПРОВЕРИТЬ название в вашей версии], в Astra Linux — графический менеджер пакетов на базе Synaptic [ПРОВЕРИТЬ]. Но на серверах L1 работает только командами.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

- UBU01 (Ubuntu Server 24.04 LTS, 10.10.10.30) установлен в уроке 24, вы умеете входить в консоль VMware и работать в bash (уроки 25–26).
- У вас есть sudo. Дальше в командах я пишу `student` — подставляйте своё имя пользователя с UBU01 (если назвали его `adm.student`, как доменную учётку, команды совпадут один в один).
- На UBU01 настроен шлюз 10.10.10.2 (NAT-устройство VMware, интернет через хост). Если в `/etc/resolv.conf` прописан только 10.10.10.10, а роль DNS на DC01 ещё не настроена (она появится в сетевом модуле позже), временно добавьте внешний резолвер — в лабораторной это разрешено, в боевой среде так не делают без согласования:

```bash
sudo resolvectl status | head
# временно:
echo "nameserver 1.1.1.1" | sudo tee /etc/resolv.conf    # [ПРОВЕРИТЬ доступность в вашей сети]
```

- Проверка сети до начала: `ping -c 2 10.10.10.2` и `getent hosts archive.ubuntu.com`.
- Если доступа к archive.ubuntu.com из РФ нет/он нестабилен — легальная альтернатива: зеркало университета/провайдера [ПРОВЕРИТЬ актуальный список], прописанное в `ubuntu.sources` вместо archive.ubuntu.com.

### Снапшот

В VMware Workstation при **выключенной** UBU01: правой кнопкой по ВМ → **Snapshot → Take Snapshot** (или иконка фотоаппарата), имя — `before-l1-027`. Снимок на включённой ВМ тоже возможен, но тогда в него попадает и состояние диска «на середине записи» — для учебных целей лучше выключить.

### Шаги

1. **UBU01, консоль.** Проверить, кто вы и где: `hostname; whoami; cat /etc/os-release | head -n 3`. Ожидаемо: `UBU01`, ваше имя, `Ubuntu 24.04.x LTS`.
2. **Сеть и DNS.** `ip -br a` (адрес 10.10.10.30/24), `ip route` (default via 10.10.10.2), `getent hosts archive.ubuntu.com`. Ожидаемо: адрес сервера в ответе `getent`.
3. **Репозитории.** `cat /etc/apt/sources.list.d/ubuntu.sources`, `ls /etc/apt/sources.list.d/`. Ожидаемо: блок с `URIs: http://archive.ubuntu.com/ubuntu/` и компонентом `universe`.
4. **Индексы.** `sudo apt update`. Ожидаемо: строки `Hit:`/`Get:` и `Reading package lists... Done` без ошибок.
5. **Изучить пакет.** `apt policy mc`, затем `apt show mc | head -n 15`. Ожидаемо: `Candidate:` не `(none)`, в описании — Midnight Commander.
6. **Установить.** `sudo apt install -y mc`. Ожидаемо: apt сам перечислит зависимости, скачает и закончит `Setting up mc`.
7. **Проверить результат.** `dpkg -l mc` (статус `ii`), `which mc`, `dpkg -S $(which mc)`, `dpkg -L mc | head`. Ожидаемо: файл `/usr/bin/mc` принадлежит пакету `mc`.
8. **Поставить ещё один пакет и посмотреть зависимости.** `sudo apt install -y htop`, затем `apt show htop | grep -i depends`. Ожидаемо: список библиотек, которые apt подтянул сам.
9. **Обновления.** `apt list --upgradable`, затем `sudo apt upgrade -y`. Ожидаемо: список обновляемых пакетов и финальное `Setting up ...`. Если обновилось ядро (`linux-image-*`) — `sudo reboot` и после входа `uname -r`.
10. **Журналы.** `tail -n 20 /var/log/apt/history.log`. Ожидаемо: записи о ваших `install` и `upgrade` с датой и командой.
11. **Журнал стенда.** Открыть `stand-log.md` и записать, что изменилось (см. раздел «Что изменилось на стенде»).

### Проверка

- [ ] `sudo apt update` завершается без `Err:` и `W:`
- [ ] `apt policy mc` показывает кандидата и источник `noble/universe`
- [ ] `dpkg -l mc` и `dpkg -l htop` — статус `ii`
- [ ] `dpkg -S $(which mc)` возвращает `mc: /usr/bin/mc`
- [ ] `apt list --upgradable` не показывает ошибок
- [ ] в `/var/log/apt/history.log` есть записи ваших команд
- [ ] снапшот `before-l1-027` существует и виден в Snapshot Manager

### Сломай и почини

```
Пользователь: Сидоров (склад)
ВМ: UBU01 (10.10.10.30)
Что написал: «Скачал по инструкции файл nmap и поставил через
"sudo dpkg -i nmap_7...deb". Оно поставилось, но с ошибкой
"dependency problems prevent configuration". Теперь любая установка
падает: "E: Unmet dependencies. Try 'apt --fix-broken install'".
Отгрузка стоит.»
Срочность: высокая, до 18:00
```

**Воспроизводим поломку (на UBU01):**

```bash
cd /tmp
sudo apt download nmap         # скачивает только .deb, без зависимостей
sudo dpkg -i /tmp/nmap_*.deb   # ожидаемо: ошибки про неустановленные зависимости
sudo apt install -y tree       # ожидаемо: apt падает с E: Unmet dependencies
```

**Диагностика по шагам (именно в этом порядке):**

1. `sudo apt update` — если падает с `Unmet dependencies`, значит apt в принципе не может строить дерево. Это не сеть, идём дальше.
2. `dpkg -l nmap` — смотрим статус. Ожидаемо `iU` (распакован, не настроен) вместо `ii`. Вывод: пакет «полуустановлен».
3. `dpkg -l | grep -v ^ii` — ищем все пакеты не в норме, чтобы не чинить вслепую.
4. `apt show nmap | grep -i depends` (или `apt-cache depends nmap`) — понимаем, каких библиотек не хватает и есть ли они в репозитории.
5. Причина ясна: `dpkg -i` не умеет тянуть зависимости. Лечим высокоуровневым инструментом: `sudo apt --fix-broken install`.
6. Если apt сообщает `dpkg was interrupted` — `sudo dpkg --configure -a`, затем повторить п. 5.
7. Проверка: `dpkg -l nmap` → `ii`, `nmap --version` работает, `sudo apt install -y tree` проходит без ошибок.
8. Профилактика на будущее: локальный `.deb` ставить через `sudo apt install ./файл.deb`.

**Ответ пользователю:**

> Алексей, добрый день! Проблема была в способе установки: `dpkg -i` ставит файл, но не подтягивает зависимости, поэтому пакет остался в недонастроенном состоянии и заблокировал apt. Я доустановил недостающие библиотеки, `nmap` работает. Проверил установку других пакетов — проходит штатно. На будущее: файлы `.deb` ставим командой `sudo apt install ./имя.deb`. Заявку закрываю, если что — пишите.

**Закрытие заявки:** категория «Установка ПО / Linux-сервер», решение — «восстановлено состояние пакетной базы (`apt --fix-broken install`), пакет настроен», приложить вывод `dpkg -l nmap`.

### Что изменилось на стенде

- UBU01: установлены пакеты `mc`, `htop` (и `nmap` — если оставляете после починки); при необходимости `tree`.
- UBU01: обновлены индексы apt и пакеты в рамках `apt upgrade`; возможно новое ядро → потребовалась перезагрузка.
- UBU01: в `/etc/resolv.conf` временно может быть внешний DNS — зафиксируйте в журнале, что это временно, и верните 10.10.10.10, когда на DC01 появится DNS.
- Журналы `/var/log/apt/history.log` и `/var/log/dpkg.log` содержат записи лабораторной.
- Снапшот `before-l1-027` существует.

### Откат

VMware Workstation → правой кнопкой по UBU01 → **Snapshot → Snapshot Manager** → выбрать `before-l1-027` → **Restore**. ВМ вернётся ровно к состоянию до лабораторной: установленные пакеты, обновления и правки `/etc/apt/*` исчезнут. Если ВМ включена, VMware предложит сделать дополнительный снимок текущего состояния — для учёбы это нормально, но диск «на ходу» лучше не откатывать, выключите ВМ.

## 6. Ошибки новичков и безопасность

1. **`apt upgrade` без `apt update`** → apt видит старый каталог: обновления не приходят, новые пакеты «не находятся». Правильно: сначала `update`, потом `install/upgrade`.
2. **Подключение сторонних репозиториев и PPA «по первой ссылке из интернета»** → конфликт версий, «dependency hell», система может перестать обновляться. Правильно: только официальные репозитории дистрибутива; добавление стороннего — осознанное решение с проверкой источника.
3. **`dpkg -i` вместо `apt install ./file.deb`** → недонастроенные пакеты, блокировка apt. Мы это только что разбирали.
4. **Не читать подтверждение перед `Y/n`** → apt пишет `The following packages will be REMOVED:`, а новичок жмёт Enter и теряет половину системы. Всегда читайте блок «будут УДАЛЕНЫ».
5. **`rm /var/lib/dpkg/lock*` при «Could not get lock»** → снятие блокировки под работающим процессом рвёт пакетную базу. Правильно: понять, кто держит (`ps aux | grep -i apt`, `sudo fuser -v /var/lib/dpkg/lock-frontend`, `systemctl status unattended-upgrades`), дождаться или остановить службу.
6. **Не перезагружаться после обновления ядра/библиотек** → странные ошибки у сервисов, «обновил, а не работает». Правильно: понять по выводу apt, требуется ли перезагрузка или перезапуск служб (в Ubuntu 24.04 об этом может спрашивать утилита `needrestart` [ПРОВЕРИТЬ поведение в вашей сборке]).
7. **`apt full-upgrade` на боевом сервере без окна обслуживания** → неожиданное удаление пакетов и простой. Правильно: снапшот/бэкап, окно, предварительный прогон на тесте.
8. **Установка «левых» `.deb` и `curl ... | bash`** → выполнение чужого кода от root. Правильно: официальный репозиторий, проверка подписи, чтение скрипта перед запуском.

**Безопасность.** Никогда не отключайте проверку GPG-подписи (`[trusted=yes]`, `--allow-unauthenticated`) «чтобы поставилось» — так на сервер попадает непроверенный код. Держите включёнными обновления безопасности (`unattended-upgrades`, настройки в `/etc/apt/apt.conf.d/20auto-upgrades` и `50unattended-upgrades`). На стенде у нас учебный пароль и временный внешний DNS — в реальной компании так нельзя: DNS и репозитории согласуются с ИБ, а изменения фиксируются в заявке.

## 7. Вопросы на собеседовании (3–5 вопросов с ответами)

**1. Чем `apt` отличается от `dpkg`?**
Ответ: `dpkg` — низкий уровень, работает с одним локальным `.deb`: распаковывает и регистрирует пакет, но зависимости не скачивает. `apt` — надстройка: ходит в репозитории, скачивает индексы, разрешает зависимости и вызывает `dpkg` для установки. `dpkg -i` на пакете с зависимостями оставит систему в состоянии `Unmet dependencies`, а `apt install ./file.deb` поставит всё нужное.
Что хочет услышать: понимание «слоёв» и того, что apt — про зависимости и репозитории.
Красный флаг: «это одно и то же, просто apt короче».

**2. Что делает `apt update` и чем отличается от `apt upgrade`?**
Ответ: `update` обновляет только локальный каталог доступных пакетов из репозиториев, ничего не устанавливая. `upgrade` устанавливает новые версии уже установленных пакетов. Порядок всегда: `update` → `upgrade`. Есть ещё `full-upgrade`, который может удалять пакеты, если иначе обновление не сходится.
Что хочет услышать: чёткое «каталог vs установка».
Красный флаг: «update обновляет систему».

**3. Пользователь пишет: `E: Could not get lock /var/lib/dpkg/lock-frontend`. Что делаете?**
Ответ: это значит, что с пакетной базой уже работает другой процесс — чаще всего `unattended-upgrades`, `apt-daily` или чужой `apt` в другой сессии. Смотрю `ps aux | grep -i apt`, `sudo fuser -v /var/lib/dpkg/lock-frontend`, `systemctl status unattended-upgrades`. Если это автообновление — жду завершения или останавливаю службу и повторяю команду. Удалять lock-файлы руками нельзя — можно разрушить базу.
Что хочет услышать: «нашёл процесс, а не удалил файл».
Красный флаг: «сразу `rm -rf /var/lib/dpkg/lock*`».

**4. Как узнать, какой пакет поставил файл, и какие файлы поставил пакет?**
Ответ: `dpkg -S /usr/bin/htop` — пакет-владелец файла; `dpkg -L htop` — список файлов пакета. Если `dpkg -S` говорит «no path found», значит файл создан вручную или другим способом.
Что хочет услышать: знание обеих команд и их направления.
Красный флаг: «через `find / -name`», без упоминания dpkg.

**5. Зачем нужны репозитории и как система понимает, что пакет не подменён?**
Ответ: репозиторий — централизованный склад пакетов и индексов; он описан в `/etc/apt/sources.list.d/*.sources`. Индексы и пакеты подписаны GPG: apt проверяет подпись ключом из `Signed-By`/`/etc/apt/trusted.gpg.d`. Если подпись не сходится — установка блокируется. Поэтому нельзя «просто отключить проверку», это дыра в безопасности.
Что хочет услышать: GPG-подпись и понимание, что отключение проверки недопустимо.
Красный флаг: «подписи не важны, главное чтобы встало».
