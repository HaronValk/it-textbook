## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

В Windows ты привык скачивать `.exe` с сайта и запускать установщик. В Linux другой подход: программы распространяются в виде **пакетов** — архивов с файлами и метаданными (имя, версия, зависимости, контрольные суммы). Пакеты лежат в **репозиториях** — серверах, откуда их можно скачать по сети. Пакетный менеджер сам скачивает, проверяет подписи, распаковывает и настраивает.

Два уровня:

- **`dpkg`** — низкоуровневый инструмент. Работает с одним `.deb`-файлом: распаковать, зарегистрировать в базе, удалить. Про зависимости ничего не знает.
- **`apt`** — надстройка над `dpkg`. Умеет ходить в репозитории, разрешать зависимости (если пакету нужна библиотека — apt её тоже поставит), обновлять всё разом.

Схема:

```text
   [ apt ]  ← ты пишешь: apt install nginx
      │
      ├── читает /etc/apt/sources.list и /etc/apt/sources.list.d/*.list
      │      (адреса репозиториев)
      │
      ├── apt update → скачивает индексы (Packages.gz) из репозиториев
      │      и кладёт в /var/lib/apt/lists/
      │
      ├── apt install → находит пакет в индексе, скачивает .deb
      │      в /var/cache/apt/archives/, проверяет GPG-подпись
      │
      └── вызывает dpkg -i для каждого .deb по очереди
             │
             └── dpkg распаковывает файлы в /, регистрирует в
                    /var/lib/dpkg/status, запускает postinst-скрипты
```

Ключевые пути, которые надо знать:

| Путь | Что там |
|------|---------|
| `/etc/apt/sources.list` | основной список репозиториев |
| `/etc/apt/sources.list.d/` | дополнительные списки (по файлу на репозиторий) |
| `/var/lib/apt/lists/` | скачанные индексы пакетов (кэш метаданных) |
| `/var/cache/apt/archives/` | скачанные `.deb`-файлы |
| `/var/lib/dpkg/status` | база установленных пакетов |
| `/var/log/apt/history.log` | история установок и удалений |
| `/var/log/apt/term.log` | полный вывод apt (что реально происходило) |
| `/var/log/dpkg.log` | что делал dpkg с каждым пакетом |

**Репозитории** — это HTTP/HTTPS-серверы (реже FTP). Каждый репозиторий подписан GPG-ключом; apt проверяет подпись, чтобы никто не подсунул тебе левый пакет. Если ключ просрочен или отсутствует — apt откажется работать с репозиторием. Это не баг, это защита.

**Зависимости.** Пакет `nginx` требует библиотеки `libpcre3`, `zlib1g` и т.д. apt строит граф зависимостей и ставит всё нужное. Если два пакета требуют разных версий одной библиотеки — конфликт, apt откажется. Это нормальная ситуация, и её надо уметь читать.

**Версии Ubuntu.** В `/etc/os-release` у UBU01 будет `VERSION_CODENAME=noble` (Ubuntu 24.04). В `sources.list` репозитории указываются с этим кодовым именем: `noble`, `noble-updates`, `noble-security`. Если перепутать — apt будет искать пакеты не там.

## 3. Аналогия из жизни

Представь склад стройматериалов. `dpkg` — это грузчик: даёшь ему коробку с кирпичами — он её разгружает и ставит на полку. Что внутри коробки и нужны ли ещё гвозди для этих кирпичей — его не волнует. `apt` — это прораб: у него есть каталог поставщиков (репозитории), он знает, что для фундамента нужны и кирпичи, и цемент, и арматура, и заказывает всё сразу. `apt update` — это когда прораб обзванивает поставщиков и обновляет прайс-листы (индексы). `apt upgrade` — когда он сверяет, что у тебя на складе, с новыми прайсами и заказывает замены.

Аналогия ломается на подписях: в реальном складе ты доверяешь поставщику по договору, а apt проверяет криптографическую подпись каждого пакета — если ключ не совпал, пакет не примут, даже если поставщик «свой».

## 4. Практика и команды

Все команды — на UBU01 под `adm.student` с `sudo`. Пароль стенда: `Lab#2026-vektor`.

### 4.1. Обновить индексы пакетов

```bash
sudo apt update
```

`update` (не `upgrade`!) — скачивает свежие списки пакетов из репозиториев. Ничего не устанавливает. Пример вывода (примерно):

```text
Hit:1 http://archive.ubuntu.com/ubuntu noble InRelease
Get:2 http://archive.ubuntu.com/ubuntu noble-updates InRelease [126 kB]
Get:3 http://security.ubuntu.com/ubuntu noble-security InRelease [126 kB]
Fetched 252 kB in 2s (126 kB/s)
Reading package lists... Done
Building dependency tree... Done
Reading state information... Done
15 packages can be upgraded. Run 'apt list --upgradable' to see them.
```

Смотреть: сколько пакетов можно обновить, нет ли ошибок `W: GPG error` или `E: Failed to fetch`.

### 4.2. Обновить установленные пакеты

```bash
sudo apt upgrade
```

Ставит новые версии уже установленных пакетов. Спросит подтверждение (`Y/n`). Не удаляет пакеты и не ставит новые — только обновляет существующие. Если нужно и то и другое (например, ядро требует новых зависимостей) — `sudo apt full-upgrade`.

### 4.3. Установить пакет

```bash
sudo apt install htop
```

`htop` — интерактивный монитор процессов, полезен в поддержке. apt сам подтянет зависимости. Пример вывода (примерно):

```text
The following NEW packages will be installed:
  htop
0 upgraded, 1 newly installed, 0 to remove and 15 not upgraded.
Need to get 165 kB of archives.
After this operation, 452 kB of additional disk space will be used.
Do you want to continue? [Y/n]
```

Смотреть: `Need to get` (сколько качать), `After this operation` (сколько займёт на диске), список `NEW packages` (что именно поставится).

### 4.4. Удалить пакет

```bash
sudo apt remove htop
sudo apt purge htop
```

`remove` удаляет программу, но оставляет конфиги в `/etc`. `purge` удаляет и конфиги. В поддержке чаще `purge`, если ставишь заново «с чистого листа».

### 4.5. Найти пакет

```bash
apt search nginx
apt show nginx
```

`search` ищет по имени и описанию. `show` показывает подробности: версию, размер, зависимости, описание. Пример `apt show` (примерно):

```text
Package: nginx
Version: 1.24.0-2ubuntu7
Priority: optional
Section: web
Depends: nginx-core | nginx-full | ...
Description: small, powerful, scalable web/proxy server
```

Смотреть: `Version`, `Depends` (что потянет за собой), `Section` (категория).

### 4.6. Что установлено

```bash
dpkg -l | grep htop
apt list --installed | grep htop
```

`dpkg -l` — список всех пакетов из базы. Первые две буквы в начале строки — статус: `ii` = установлен и настроен, `rc` = удалён, но конфиги остались, `iU` = распакован, но не настроен (сломанное состояние). Пример:

```text
ii  htop  3.3.0-4build1  amd64  interactive processes viewer
```

### 4.7. Какой пакет владеет файлом

```bash
dpkg -S /usr/bin/htop
```

Показывает, из какого пакета файл. Полезно, когда надо понять, «откуда эта программа взялась».

### 4.8. Установить локальный .deb-файл

```bash
sudo dpkg -i /tmp/somepackage.deb
sudo apt install -f
```

`dpkg -i` ставит `.deb` напрямую, но не тянет зависимости. Если после него apt ругается на «unmet dependencies» — `apt install -f` (fix-broken) доставит недостающее. Это классический сценарий: скачал `.deb` с сайта вендора, поставил через `dpkg`, а он просит библиотеку.

### 4.9. Очистить кэш

```bash
sudo apt clean
sudo apt autoremove
```

`clean` удаляет скачанные `.deb` из `/var/cache/apt/archives/` (освобождает место). `autoremove` удаляет пакеты, которые были поставлены как зависимости, но больше никому не нужны. На сервере с малым диском — обязательная гигиена.

### 4.10. История установок

```bash
less /var/log/apt/history.log
```

Показывает, что и когда ставилось/удалялось. В поддержке — первое, что смотришь, когда «вчера работало, сегодня нет».

### 4.11. Где репозитории

```bash
cat /etc/apt/sources.list
ls /etc/apt/sources.list.d/
```

На Ubuntu 24.04 основной файл может быть почти пустым, а реальные репозитории — в `/etc/apt/sources.list.d/ubuntu.sources` (новый формат deb822) [ПРОВЕРИТЬ формат в твоей установке]. Смотри оба места.

## 6. Ошибки новичков и безопасность

1. **Путать `apt update` и `apt upgrade`.** `update` только обновляет индексы, `upgrade` ставит новые версии. Новичок пишет `apt upgrade` без `update` — apt работает по старым индексам и не видит свежих пакетов. Правильно: сначала `update`, потом `upgrade`.

2. **`apt upgrade` на боевом сервере без окна обслуживания.** Обновление ядра или `openssh-server` может потребовать перезагрузки или временно уронить службу. В бою — только в согласованное окно, с бэкапом и снапшотом. На стенде — можно, но привычку вырабатывай сразу.

3. **`dpkg -i` без `apt install -f`.** Поставил `.deb` с сайта вендора, получил «unmet dependencies», бросил. Пакет в состоянии `iU` (распакован, не настроен), система «наполовину сломана». Правильно: после `dpkg -i` всегда `apt install -f`.

4. **`apt remove` вместо `apt purge`.** Удалил программу, конфиги остались в `/etc`, при переустановке — старые настройки. Если хочешь «с чистого листа» — `purge`.

5. **`apt autoremove` без просмотра списка.** Иногда `autoremove` хочет удалить пакет, который ты ставил вручную, но apt считает его «зависимостью». Всегда смотри список перед `Y`.

6. **Игнорировать `W: GPG error`.** apt предупреждает, что подпись репозитория не проверена. Это значит, что пакеты могут быть подменены. Правильно: разобраться с ключом (`apt-key` устарел, в 24.04 ключи кладут в `/etc/apt/keyrings/` [ПРОВЕРИТЬ]), а не отключать проверку.

7. **Добавлять левые репозитории «потому что там свежее».** PPA и сторонние репозитории — источник нестабильности и риска. В бою — только проверенные источники, лучше — внутреннее зеркало.

8. **Забывать про место на диске.** `apt upgrade` на заполненном диске встаёт на середине, половина пакетов обновлена. Перед крупным обновлением — `df -h`, при необходимости `apt clean`.

### Безопасность

- **Не отключай проверку GPG-подписей** (`[trusted=yes]` в sources.list) — это открывает дорогу подмене пакетов. В бою так делать нельзя.
- **Не добавляй репозитории с непроверенных сайтов.** В 2026 году в РФ участились атаки через подменённые зеркала. Используй официальные зеркала Ubuntu или внутреннее зеркало компании.
- **Не запускай `apt` от root без `sudo`** — привыкай к `sudo`, это логируется.
- **Пароль стенда `Lab#2026-vektor` — только для стенда.** В бою — уникальные пароли, лучше — ключи SSH (тема урока 29).
- **`apt upgrade` на сервере с 1С или КриптоПро** может сломать зависимости. В бою такие серверы обновляют отдельно, с тестированием.

## 7. Вопросы на собеседовании

**Вопрос 1. Чем отличается `apt` от `dpkg`?**

Как реально спросят: «Вот у тебя Ubuntu, надо поставить пакет. Что используешь — apt или dpkg? В чём разница?»

Ответ: `dpkg` — низкоуровневый инструмент, работает с одним `.deb`-файлом, не разрешает зависимости. `apt` — надстройка над `dpkg`, ходит в репозитории, сам скачивает пакеты, проверяет подписи и разрешает зависимости. В работе почти всегда `apt`; `dpkg` — когда надо поставить локальный `.deb` или посмотреть, из какого пакета файл (`dpkg -S`).

Что хочет услышать интервьюер: что ты понимаешь два уровня и не будешь ставить `.deb` через `dpkg -i` и бросать систему в состоянии «unmet dependencies».

Красный флаг: «apt и dpkg — одно и то же, просто разные команды».

**Вопрос 2. Что делает `apt update` и чем отличается от `apt upgrade`?**

Ответ: `apt update` скачивает свежие индексы пакетов из репозиториев в `/var/lib/apt/lists/`, ничего не устанавливает. `apt upgrade` ставит новые версии уже установленных пакетов, используя эти индексы. Порядок: сначала `update`, потом `upgrade`. Если сделать `upgrade` без `update` — apt работает по старым индексам и не видит свежих версий.

Что хочет услышать: что ты не путаешь эти команды и понимаешь, что `update` — это про метаданные, а `upgrade` — про сами пакеты.

Красный флаг: «`apt update` обновляет систему».

**Вопрос 3. Как узнать, из какого пакета файл, и что установлено на сервере?**

Ответ: `dpkg -S /путь/к/файлу` — покажет пакет-владелец. `dpkg -l` — список всех пакетов из базы, первые две буквы — статус (`ii` — установлен и настроен, `rc` — удалён, конфиги остались). `apt list --installed` — то же через apt, удобнее фильтровать. Для истории установок — `/var/log/apt/history.log`.

Что хочет услышать: что ты умеешь разбираться, «откуда эта программа», и знаешь, где смотреть историю.

Красный флаг: «Не знаю, я всегда смотрю в `ls /usr/bin`».

**Вопрос 4. Что делать, если после `dpkg -i` apt ругается на unmet dependencies?**

Ответ: запустить `sudo apt install -f` (fix-broken) — apt доставит недостающие зависимости. Если не помогло — посмотреть `apt show <пакет>` и `Depends:`, разобраться, чего не хватает. Если пакет из стороннего репозитория — проверить, что репозиторий подключён и ключ валиден. В крайнем случае — `sudo dpkg --remove <пакет>` и поставить заново через `apt`.

Что хочет услышать: что ты знаешь `apt install -f` и не бросаешь систему в полусобранном состоянии.

Красный флаг: «Переустановлю Ubuntu».

**Вопрос 5. Где apt хранит репозитории и как добавить новый?**

Ответ: основной список — `/etc/apt/sources.list`, дополнительные — `/etc/apt/sources.list.d/*.list` (или `.sources` в новом формате deb822 на 24.04 [ПРОВЕРИТЬ]). Добавить репозиторий — дописать строку `deb http://адрес/ubuntu noble main` в файл в `sources.list.d/`, положить GPG-ключ в `/etc/apt/keyrings/` (в 24.04 `apt-key` устарел [ПРОВЕРИТЬ]), затем `apt update`. В бою — только проверенные источники, лучше — внутреннее зеркало.

Что хочет услышать: что ты знаешь структуру и не будешь добавлять левые PPA на прод.

Красный флаг: «Просто добавляю `[trusted=yes]`, чтобы не мучиться с ключами».
