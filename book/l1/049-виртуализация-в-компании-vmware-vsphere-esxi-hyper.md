## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Гипервизор** — это слой ПО, который делит физический сервер (или ваш ПК) на несколько изолированных «компьютеров» — виртуальных машин (ВМ, VM). Каждая ВМ думает, что у неё своё железо: процессор, память, диск, сетевая карта. На самом деле всё это — файлы и процессы на хосте.

**Два типа гипервизоров:**

- **Тип 1 (bare-metal)** — ставится прямо на железо, без обычной ОС. Примеры: VMware ESXi, Microsoft Hyper-V (роль в Windows Server), Proxmox VE (KVM). Так работает продакшн в компании.
- **Тип 2 (hosted)** — программа внутри обычной ОС. Пример: **VMware Workstation** — ровно то, что стоит у вас на ПК. Так работает учебный стенд и рабочие места разработчиков.

```text
        ПРОДАКШН (тип 1)                     ВАШ СТЕНД (тип 2)
 ┌──────────────────────────────┐     ┌──────────────────────────────┐
 │  vCenter / Proxmox UI / WAC  │     │  Windows 11 на вашем ПК      │
 │            ▲                 │     │            ▲                 │
 │  ┌─────────┴──────────────┐  │     │  VMware Workstation (GUI)    │
 │  │ Гипервизор ESXi /      │  │     │            ▲                 │
 │  │ Hyper-V / KVM          │  │     │  ┌─────────┴──────────────┐  │
 │  ├────────┬───────┬───────┤  │     │  │ VMware Workstation     │  │
 │  │ VM:DC01│VM:FS01│VM:1C │  │     │  ├────────┬───────┬───────┤  │
 │  └────────┴───────┴───────┘  │     │  │WIN11-  │ DC01  │ UBU01 │  │
 │  vSwitch ── физический NIC   │     │  │CL01    │       │       │  │
 └──────────────┬───────────────┘     └──┴────────┴───────┴───────┘  │
                │                                  │                 │
        коммутатор, сеть 10.10.10.0/24      VMnet8 (NAT) 10.10.10.0/24│
```

**Три платформы, которые надо знать в лицо:**

| Критерий | VMware vSphere / ESXi | Microsoft Hyper-V | Proxmox VE |
|---|---|---|---|
| Тип | 1 (bare-metal) | 1 (роль Windows Server) | 1 (Debian + KVM/LXC) |
| Управление | vCenter (веб, 443) + ESXi Host Client | Hyper-V Manager, Windows Admin Center, PowerShell | собственный веб-интерфейс, порт **8006** |
| Формат диска ВМ | VMDK | VHDX / VHD | qcow2, LVM-thin, ZFS |
| Снапшоты | да, цепочка diff-файлов | да, checkpoint (standard/production) | да, у KVM и у LXC |
| Кластер / HA / живая миграция | vMotion, HA, DRS | Failover Cluster, Live Migration | corosync-кластер, миграция ВМ |
| Контейнеры | нет (отдельный продукт) | нет (есть WSL/контейнеры в Windows) | **да, LXC** «из коробки**»** |
| Лицензия для учёбы | Workstation Pro — бесплатно для личного использования `[ПРОВЕРИТЬ актуальные условия Broadcom]` | Windows Server Evaluation (180 дней), Hyper-V бесплатен как роль | свободная (GPL/AGPL), подписка только на репозиторий |
| Где встречается в РФ в 2026 | ещё много в промышленной эксплуатации, но официальные поставки прекращены | средний и малый бизнес, часто «в комплекте» с Windows Server | растёт как замена VMware; плюс отечественные zVirt, РЕД Виртуализация, «Брест», ROSA Virtualization `[ПРОВЕРИТЬ состав реестра]` |

**Ключевые понятия, без которых вы не поймёте ни одну заявку:**

- **vCPU** — виртуальное ядро, которое гипервизор выдаёт по расписанию из физических ядер. 4 vCPU на ВМ при 4 физических ядрах хоста — это уже уплотнение (overcommit), и все ВМ начинают «ждать» процессор.
- **Datastore / хранилище** — место, где лежат файлы ВМ. Закончилось место → ВМ не стартует, снапшот не создаётся.
- **Виртуальный коммутатор** (vSwitch, Virtual Network Editor в Workstation) — «патч-панель» внутри гипервизора. Он соединяет виртуальный адаптер ВМ с физической сетью. Именно здесь ваши ВМ попадают в VMnet8 (10.10.10.0/24) и получают адрес от DHCP на DC01.
- **VMware Tools / Integration Services / open-vm-tools** — агент внутри гостя. Даёт драйверы (нормальное видео, vmxnet3), корректное время, «мягкое» выключение и «тихие» снапшоты (quiescing).
- **Снапшот (snapshot / checkpoint)** — снимок состояния ВМ в моменте. Это **не бэкап**: он лежит на том же хранилище, зависит от родительского диска и деградирует производительность.

**Порты для кругозора:** vCenter/ESXi — 443, SSH на ESXi — 22, Proxmox UI — 8006, SSH — 22, Hyper-V Live Migration — TCP 6600, WinRM для управления Hyper-V — 5985/5986, RDP в гостя — 3389.

## 3. Аналогия из жизни

Гипервизор — это **гостиница**. Здание одно (физический сервер), но в нём много номеров (виртуальных машин). Каждый гость в своём номере уверен, что живёт отдельно: у него своя кровать, свой санузел, свой счётчик. Администратор на ресепшене (vCenter, Proxmox UI, Hyper-V Manager) знает про всех: кому какой номер, кто шумит, кому не хватило полотенец. Горничная, которая может перенести гостя в другой номер, пока он спит, — это vMotion / Live Migration. А если администратор продал больше номеров, чем есть кроватей, — это overcommit: пока все на экскурсии, всё хорошо, но вечером, когда все вернулись, кто-то будет спать на полу.

Аналогия перестаёт работать в одном месте: в реальной гостинице нельзя «продать» одному гостю сразу четверть кровати на 10 миллисекунд, а потом отдать её другому — а гипервизор именно так и делит процессорное время между vCPU.

## 4. Практика и команды

### 4.1. Посмотреть настройки ВМ глазами гипервизора (GUI, хост)

VMware Workstation: выделите ВМ → **VM → Settings** (или кнопка с гаечным ключом). Вкладки **Hardware** (CPU, Memory, Hard Disk, Network Adapter, CD/DVD) и **Options**. Смотреть нужно: сколько vCPU и RAM выдано, на каком VMnet висит адаптер, включена ли галочка **Connect at power on**.

### 4.2. `systeminfo` — кто я на самом деле

```cmd
systeminfo | findstr /C:"System Model" /C:"System Manufacturer" /C:"Hyper-V"
```

`findstr` фильтрует вывод по строкам. Типичный результат в гостя на VMware:

```text
System Manufacturer:       VMware, Inc.
System Model:              VMware Virtual Platform
Hyper-V Requirements:      VM Monitor Mode Extensions: Yes
                           Virtualization Enabled In Firmware: Yes
                           Second Level Address Translation: Yes
                           Data Execution Prevention Available: Yes
```

Смотрим: **System Model = VMware Virtual Platform** — это ВМ, а не физический ПК. Если вместо этого вы видите `A hypervisor has been detected...` — внутри гостя уже работает гипервизор (Hyper-V, WSL2, Device Guard). Это отдельная ветка диагностики: такие ВМ часто не могут сами запускать вложенную виртуализацию.

### 4.3. `Get-ComputerInfo` — то же самое в PowerShell, но удобнее грепать

```powershell
Get-ComputerInfo | Select-Object CsName, CsManufacturer, CsModel, HyperVisorPresent
```

Свойства `Cs*` — «Computer System», `HyperVisorPresent` = `True`, если внутри гостя крутится свой гипервизор. Удобно тем, что вывод — объект, и его можно сравнивать по всем ВМ скриптом.

### 4.4. `Get-CimInstance Win32_DiskDrive` — виртуальный диск

```powershell
Get-CimInstance Win32_DiskDrive | Select-Object Model, InterfaceType, Size
```

```text
Model                                InterfaceType        Size
-----                                -------------        ----
VMware Virtual disk SCSI Disk Device SCSI          64424509440
```

`Size` — в байтах (64 424 509 440 ≈ 60 ГБ). Это размер виртуального диска, а не файла на хосте: файл VMDK может быть меньше (thin provisioning) или, наоборот, раздуться из-за снапшотов.

### 4.5. `Get-Disk` и `Get-Partition` — что видит гость

```powershell
Get-Disk | Format-Table Number, FriendlyName, TotalSize, PartitionStyle
```

Смотрим таблицу разделов и размер. Если `TotalSize` меньше, чем вы задавали в настройках ВМ, — либо диск не расширили в гипервизоре, либо расширили, но не расширили раздел внутри Windows (`Resize-Partition`).

### 4.6. `Get-NetAdapter` — виртуальная сетевая карта

```powershell
Get-NetAdapter | Format-Table Name, InterfaceDescription, Status, LinkSpeed
```

```text
Name        InterfaceDescription            Status   LinkSpeed
----        --------------------            ------   ---------
Ethernet0   vmxnet3 Ethernet Adapter        Up       10 Gbps
```

`vmxnet3` — «родной» паравиртуальный адаптер VMware (быстрый). `Intel(R) 82574L Gigabit Network Connection` (e1000e) — эмуляция реальной карты, медленнее, но совместимее. Для L1 важно: **если адаптер в настройках ВМ переключили на другой VMnet, здесь всё останется «Up», но адрес будет 169.254.x.x**.

### 4.7. Проверка VMware Tools

```powershell
Get-Service | Where-Object DisplayName -like '*VMware*' | Select-Object Name, DisplayName, Status
```

Служба **VMware Tools** должна быть `Running`. Если её нет — в госте не работают нормальное разрешение экрана, обмен файлами с хостом, «мягкое» выключение и корректные снапшоты. На Linux аналог — `open-vm-tools`.

### 4.8. Есть ли на сервере роль Hyper-V (только проверка, не установка!)

```powershell
# На Windows Server (DC01), PowerShell от администратора
Get-WindowsFeature -Name Hyper-V | Select-Object Name, InstallState
```

```text
Name      InstallState
----      ------------
Hyper-V   Available
```

`Available` = роль есть в системе, но не установлена. На клиентской Windows 11 аналог: `Get-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V-All`. **Устанавливать Hyper-V на DC01 мы не будем** — см. раздел 6.

### 4.9. Linux-гость: определяем гипервизор

```bash
systemd-detect-virt                 # vmware
sudo dmidecode -s system-product-name   # VMware Virtual Platform
lscpu | grep -i hypervisor          # Hypervisor vendor: VMware
lsblk -o NAME,SIZE,TYPE             # sda 60G disk
```

`systemd-detect-virt` возвращает `none` на физическом железе и имя гипервизора (`vmware`, `kvm`, `microsoft`) в ВМ. Удобно, когда непонятно, «почему на сервере странные часы/диски».

### 4.10. Команды старших треков (для кругозора, на L1 их не запускаем)

```bash
# ESXi (по SSH, если включено)
esxcli storage filesystem list
vim-cmd vmsvc/getallvms

# Proxmox VE (машина PVE01, трек «сисадмин»)
qm list
pct list
pvesh get /nodes
```

`qm` — управление KVM-ВМ, `pct` — LXC-контейнерами. Держите в голове: когда появится PVE01, вы будете делать то же самое, что сейчас в VMware Workstation, только через веб-интерфейс на 8006.

### 4.11. Где лежат файлы ВМ (GUI)

Workstation: правый клик по ВМ → **Open VM Directory** (или **Settings → Options → Working directory**). В папке вы увидите:

- `.vmx` — текстовый конфиг ВМ (блокнотом читается!);
- `.vmdk` — виртуальные диски (их может быть несколько: `-000001.vmdk` — дельта снапшота);
- `.vmsd` / `.vmsn` — метаданные и состояние снапшотов;
- `.nvram` — «BIOS» ВМ;
- `.lck` — папки-блокировки, пока ВМ запущена.

1. **В госте WIN11-CL01:** `ipconfig /all`. Смотрим: адрес вида `169.254.x.x` = DHCP-сервер недоступен, адрес не получен. `10.10.10.x` — сеть в порядке, проблема выше.
2. **В госте:** `Get-NetAdapter` — адаптер `Up` или `Disconnected`? Если `Disconnected`, проблема в «железе» ВМ, а не в Windows.
3. **В госте:** `Test-NetConnection 10.10.10.10 -Port 67` (DHCP) и `Test-NetConnection 10.10.10.20 -Port 445` (SMB на FS01). Оба падают — сеть ВМ не работает вообще.
4. **На хосте:** **VM → Settings → Network Adapter** для WIN11-CL01. Ожидаемо по документации стенда: **Custom: VMnet8**. Если стоит Bridged — причина найдена.
5. **На хосте:** галочка **Connected** и **Connect at power on** — стоят? Если снята, ВМ «отключена от сети» на уровне гипервизора.
6. **Исключаем серверную часть:** на DC01 `Get-DhcpServerv4Scope` (или оснастка DHCP → область 10.10.10.0) — область активна, адреса из пула 10.10.10.100–150 есть; `Get-Service DHCPServer` — Running.
7. **Исключаем VMnet8:** **Virtual Network Editor** — подсеть та же, NAT-шлюз 10.10.10.2, локальный DHCP по-прежнему выключен.

**Решение:** вернуть адаптер в **Custom: VMnet8**, поставить галочки **Connected** и **Connect at power on**, ОК. В госте: `ipconfig /renew` → должен получить адрес из 10.10.10.100–150 с шлюзом 10.10.10.2 и DNS 10.10.10.10. Проверка: `nltest /sc_verify:corp.vektor.lab` (должно быть `NERR_Success`), `Test-Path \\FS01\Obshchee`.

**Что написать пользователю:**
> Иван, добрый день. Причина найдена: у вашей рабочей станции в настройках виртуальной машины был переключён сетевой адаптер (вместо офисной сети VMnet8 стоял режим «Bridged»), поэтому она не получала адрес от сервера и не видела ни 1С, ни сетевую папку. Вернул настройку на место, доступ восстановлен — проверьте, пожалуйста, 1С и `\\FS01\Obshchee`. Если повторится, напишите — посмотрим, что переключает адаптер.

**Закрытие заявки:** категория «Виртуальная инфраструктура → сеть ВМ», решение «возврат сетевого адаптера ВМ на VMnet8», время — 15 мин.

### Что изменилось на стенде

- Созданы снапшоты `before-l1-049` на WIN11-CL01, DC01, UBU01 (состояние «после урока 48»).
- Тестовый снапшот `test-l1-049` на WIN11-CL01 создан и **удалён** — итоговое состояние не изменилось.
- На UBU01 при необходимости установлен пакет `open-vm-tools` (постоянное изменение).
- Сетевой адаптер WIN11-CL01 возвращён на `Custom: VMnet8` — состояние соответствует описанию стенда.
- Новых машин нет. **PVE01 не создавался.**
- Обновлён `stand-log.md`: версия VMware Workstation, параметры VMnet8, набор файлов ВМ.

### Откат

1. Выключить ВМ гостевой командой (Shutdown).
2. **VM → Snapshot → Snapshot Manager** → выбрать `before-l1-049` → **Revert** (или **Go To**).
3. Если создавались лишние снапшоты — удалите их **до** отката, иначе получите длинную цепочку и лишний расход места.
4. Проверить, что ВМ стартует, входит в домен и видит сеть. Если DC01 откатили — подождите 2–3 минуты, пока поднимутся AD DS, DNS и DHCP, прежде чем включать клиента.

## 6. Ошибки новичков и безопасность

1. **«Дам ВМ побольше vCPU, чтобы быстрее работала».** → 8 vCPU на ВМ при 4 физических ядрах: гипервизор заставляет все ядра ждать, тормозит вся инфраструктура. → Правильно: сначала смотрим загрузку хоста и «CPU Ready» (в vSphere) / общий CPU хоста в Workstation, а не крутим ползунки.
2. **Копирование папки ВМ в проводнике вместо Clone/Export.** → Две ВМ с одинаковыми UUID и MAC-адресами, конфликт в сети, битые снапшоты. → Правильно: **VM → Manage → Clone** или **File → Export to OVF**.
3. **Снапшоты «на всякий случай» пачками.** → Цепочка дельт растёт, datastore заполняется, ВМ замедляется, откат идёт минутами, потом «No space left on device». → Правильно: снапшот — на время работ, максимум на сутки, с последующим **Delete**; бэкап — отдельно (урок 48).
4. **Считать снапшот бэкапом.** → Хранилище умерло — умерли и ВМ, и все её снапшоты. → Правильно: снапшот ≠ резервная копия.
5. **Откат боевой ВМ без предупреждения пользователя.** → «Пропали» файлы за два дня, письма, документы; у доменной ВМ — потенциальный разрыв доверия к домену. → Правильно: предупредить, согласовать окно, после отката проверить `nltest /sc_verify`.
6. **Переключение адаптера на Bridged «чтобы был интернет».** → ВМ вылетает из 10.10.10.0/24, DHCP от DC01 её не видит, домен и сетевые папки недоступны. → Правильно: на стенде всегда `Custom: VMnet8`.
7. **Установка Hyper-V «потестить» на DC01 или на рабочей ВМ.** → На DC — категорически нельзя (это роль гипервизора на контроллере домена, лишняя поверхность атаки и риск для AD); внутри VMware-гостя — конфликт с VMware Tools и сильное падение производительности. → Правильно: Hyper-V только на выделенном сервере и только через Evaluation-редакцию.
8. **Хранение VMDK на сетевой папке, в OneDrive/облаке или под активным антивирусом.** → Файлы блокируются и повреждаются, ВМ «умирает». → Правильно: локальный SSD, папка в исключениях антивируса.

### Безопасность

- Доступ к консоли гипервизора (vCenter, Proxmox root, Hyper-V) = доступ ко **всем** ВМ и их дискам, включая базы 1С и файлы бухгалтерии. Не давайте этот доступ «посмотреть» и не сохраняйте пароль root в браузере на общем ПК.
- Снапшот с памятью содержит в дампе пароли и ключи в открытом виде. Такой файл — такой же секрет, как и сама ВМ.
- Экспорт ВМ в OVF и вынос файла за пределы компании = вынос персональных данных. В боевой среде — только по заявке и с согласованием.
- Управляющую сеть гипервизора (management) держат в отдельном VLAN, не в общей офисной сети, и доступ к ней — только с админских рабочих мест.
- Учебный пароль `Lab#2026-vektor` и «снапшот всего» — только для стенда. В продакшне: уникальные пароли, MFA на vCenter/Proxmox, журналирование действий администраторов.

## 7. Вопросы на собеседовании (3–5 вопросов с ответами)

**1. Чем гипервизор первого типа отличается от второго? Что стоит у нас на стенде?**
Ответ: тип 1 ставится прямо на железо (ESXi, Hyper-V, Proxmox VE на KVM) — так работает продакшн; тип 2 — приложение внутри обычной ОС (VMware Workstation, VirtualBox) — так работает учебный стенд и рабочие места разработчиков. У нас на хосте Windows 11 + VMware Workstation, то есть тип 2; внутри ВМ мы эмулируем продакшн-серверы.
*Что хочет услышать интервьюер:* понимание разницы и того, что тип 2 непригоден для продакшна (зависимость от хостовой ОС, накладные расходы).
*Красный флаг:* «это одно и то же, разницы нет» или путаница Hyper-V и VirtualBox.

**2. Что такое снапшот ВМ и почему это не резервная копия?**
Ответ: снапшот фиксирует состояние ВМ в моменте, дальше запись идёт в дельта-файл, который зависит от родительского диска и лежит на том же хранилище. Растёт цепочка — падает производительность, при потере хранилища теряются и ВМ, и снапшоты. Бэкап — это независимая копия по стратегии 3-2-1, которую можно восстановить на другом оборудовании. Снапшот нужен на время работ: сделал — поработал — удалил.
*Что хочет услышать интервьюер:* что кандидат не будет держать 20 снапшотов месяцами и понимает риск.
*Красный флаг:* «снапшот и есть бэкап»; «снапшоты можно хранить годами».

**3. Пользователь говорит, что его ВМ не видит контроллер домена. Ваши действия?**
Ответ: иду снизу вверх. В госте — `ipconfig /all`: если 169.254.x.x, значит DHCP не отвечает. Дальше `Get-NetAdapter` — адаптер подключён? Потом на хосте смотрю настройки ВМ: какой VMnet, стоит ли «Connected». Затем исключаю серверную часть: служба DHCP и область на DC01, пинг до 10.10.10.10, `nltest /sc_verify`. Часто причина — переключённый на Bridged адаптер или отключённая галочка «Connect at power on».
*Что хочет услышать интервьюер:* методичный порядок диагностики и понимание, что ВМ-сеть — это настройка гипервизора, а не только Windows.
*Красный флаг:* сразу «переустановлю драйвер/перезагружу контроллер домена» или «наверное, вирус».

**4. Зачем нужны VMware Tools / Integration Services?**
Ответ: это агент внутри гостя: драйверы (видео, сетевой vmxnet3, ballooning), корректное время, «мягкое» завершение работы из консоли, «тихие» снапшоты через VSS и обмен файлами с хостом. Без них ВМ работает, но медленно и с артефактами; снимки могут быть неконсистентными. На Linux — `open-vm-tools`.
*Что хочет услышать интервьюер:* что кандидат знает про quiescing и что Tools — обязательный чек-лист после развёртывания ВМ.
*Красный флаг:* «это просто чтобы мышка работала».

**5. Компания выбирает платформу виртуализации. Какие критерии вы назовёте?**
Ответ: список ВМ и нагрузки, требования к HA и живой миграции, поддерживаемое хранилище (FC/iSCSI/NFS/локальное), совместимость гостевых ОС (включая Astra Linux и РЕД ОС), наличие поддержки вендора и доступность в РФ (лицензии, реестр отечественного ПО), наличие компетенций у команды и наличие системы бэкапа (Veeam и аналоги), итоговая стоимость владения. Для малого бизнеса часто Hyper-V «в комплекте» или бесплатный Proxmox; для крупного — корпоративные платформы или отечественные решения вроде zVirt, РЕД Виртуализация `[ПРОВЕРИТЬ актуальный состав реестра]`.
*Что хочет услышать интервьюер:* что кандидат думает не «что мне нравится», а «что подходит и легально доступно».
*Красный флаг:* «VMware лучший, остальное не рассматриваем» — без учёта доступности и поддержки.
