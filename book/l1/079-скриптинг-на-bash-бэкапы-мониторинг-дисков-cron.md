После этой главы ты сможешь написать скрипт бэкапа с проверкой ошибок, скрипт мониторинга дисков с порогом и поставить оба в cron так, чтобы они реально работали, а не «вроде запускались».

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Bash — это командная оболочка (shell) и одновременно язык программирования. Когда ты пишешь `./backup.sh`, происходит вот что:

```text
ты в терминале
   │
   ▼
bash читает файл backup.sh построчно
   │
   ├─► запускает внешние команды (tar, df, cp) как дочерние процессы
   ├─► вычисляет переменные, условия if, циклы for
   └─► возвращает код выхода (exit code): 0 = успех, не 0 = ошибка
   │
   ▼
cron (демон crond) по расписанию запускает тот же bash с тем же файлом
   │
   ▼
результат пишется в лог-файл или в почту (если настроена)
```

Ключевые понятия, без которых скрипт не работает:

- **Shebang** — первая строка `#!/bin/bash`. Говорит ядру, каким интерпретатором запускать файл.
- **Права на выполнение** — `chmod +x script.sh`. Без этого `./script.sh` даст «Permission denied».
- **Переменные** — `NAME=value` (без пробелов вокруг `=`), использование `$NAME` или `${NAME}`.
- **Код выхода** — `$?` хранит код последней команды. `0` — успех, всё остальное — ошибка. На этом строится вся надёжность скриптов.
- **`set -euo pipefail`** — «строгий режим»: скрипт падает при первой ошибке, при обращении к необъявленной переменной и при ошибке в любой части конвейера. Ставь в начало каждого серьёзного скрипта.
- **cron** — демон, который читает crontab (таблицу расписаний) и запускает команды по времени. Формат строки: `минута час день_месяца месяц день_недели команда`. Пять звёздочек `* * * * *` — каждую минуту.
- **Окружение cron** — важнейшая ловушка. У cron минимальный `PATH` (обычно `/usr/bin:/bin`), нет твоего `.bashrc`, нет переменных из интерактивной сессии. Поэтому в скрипте для cron всегда указывай полные пути к командам или явно задавай `PATH`.

Порты и протоколы тут почти не участвуют — это локальная автоматизация. Единственное сетевое — если скрипт копирует файлы по SSH/SCP на другую машину (порт 22) или отправляет уведомление по SMTP (порт 25/587). На нашем стенде почтового сервера нет, поэтому уведомления будут писаться в лог-файл.

## 3. Аналогия из жизни

Представь вахтёра в офисе. У него есть список поручений на каждый день: «в 23:00 обойди этажи и проверь, закрыты ли окна», «каждое утро посмотри, не переполнен ли мусорный бак, и если да — позвони». Вахтёр не думает, он выполняет чёткие инструкции из блокнота. Bash-скрипт — это такой блокнот с инструкциями, а cron — будильник, который поднимает вахтёра в нужное время. Если в блокноте написано «позвонить по номеру 555», а вахтёр не знает, где телефон, — он ничего не сделает и промолчит. Так и cron: если в скрипте не указан полный путь к команде, скрипт «промолчит» с ошибкой, которую ты не увидишь, пока не заглянешь в лог. Аналогия перестаёт работать в одном: вахтёр хотя бы заметит, что не смог позвонить, а cron по умолчанию просто тихо проглотит ошибку.

## 4. Практика и команды

Все команды — на UBU01 (Ubuntu Server 24.04, пользователь `adm.student`, sudo). Часть команд работает и на других Linux-машинах стенда (ASTRA01), но лабораторная — на UBU01.

**1. Создать и запустить первый скрипт**

```bash
mkdir -p ~/scripts
cat > ~/scripts/hello.sh <<'EOF'
#!/bin/bash
echo "Привет, $(whoami), сейчас $(date '+%Y-%m-%d %H:%M:%S')"
EOF
chmod +x ~/scripts/hello.sh
~/scripts/hello.sh
```

`<<'EOF'` — heredoc, способ записать многострочный текст в файл. Кавычки вокруг `EOF` важны: без них bash подставит переменные ещё при записи файла. `chmod +x` даёт право на выполнение. Ожидаемый вывод примерно: `Привет, adm.student, сейчас 2026-01-15 14:32:07`.

**2. Проверить код выхода**

```bash
ls /nonexistent; echo "exit=$?"
ls /home; echo "exit=$?"
```

Первый `ls` вернёт ошибку и код `2`, второй — код `0`. Это основа любой проверки «сработало или нет».

**3. Строгий режим и проверка аргументов**

```bash
cat > ~/scripts/args.sh <<'EOF'
#!/bin/bash
set -euo pipefail
if [ $# -lt 1 ]; then
    echo "Использование: $0 <имя>" >&2
    exit 1
fi
echo "Аргумент: $1"
EOF
chmod +x ~/scripts/args.sh
~/scripts/args.sh
~/scripts/args.sh vektor
```

`$#` — число аргументов, `$1` — первый аргумент, `$0` — имя скрипта. `>&2` отправляет сообщение в stderr (поток ошибок), а не в stdout. Без аргумента скрипт напечатает подсказку и выйдет с кодом 1.

**4. Проверить свободное место на диске**

```bash
df -h /
df -h --output=pcent / | tail -1 | tr -dc '0-9'
```

`df -h` показывает занятость в человекочитаемом виде. Второй вариант вытаскивает только число процентов — именно так скрипт сравнивает с порогом. Вывод примерно: `23` (если корень занят на 23%).

**5. Сделать архив с датой в имени**

```bash
tar -czf /tmp/test-$(date +%F).tar.gz -C /etc hostname hosts
ls -lh /tmp/test-*.tar.gz
```

`tar -czf` — создать (`c`) gzip-архив (`z`) в файл (`f`). `-C /etc` — перейти в каталог перед упаковкой, чтобы в архиве были относительные пути. `$(date +%F)` даёт `2026-01-15`. Вывод `ls` покажет размер архива.

**6. Найти старые файлы и удалить**

```bash
find /tmp -maxdepth 1 -name 'test-*.tar.gz' -mtime +7 -print
find /tmp -maxdepth 1 -name 'test-*.tar.gz' -mtime +7 -delete
```

`-mtime +7` — старше 7 дней. Сначала всегда запускай с `-print` и смотри, что удалится, потом меняй на `-delete`. Это правило номер один при работе с `find -delete`.

**7. Посмотреть текущий crontab и отредактировать**

```bash
crontab -l
crontab -e
```

`crontab -l` — показать свои задачи (у нового пользователя может быть пусто или «no crontab for adm.student»). `crontab -e` — открыть редактор (по умолчанию nano или vi). Строка вида `0 2 * * * /home/adm.student/scripts/backup.sh` означает «каждый день в 02:00».

**8. Проверить, что cron работает и логирует**

```bash
systemctl status cron
sudo journalctl -u cron --since "1 hour ago" | tail -20
```

`systemctl status cron` покажет, активен ли демон. `journalctl -u cron` — его журнал. Если задачи не запускаются, смотри сюда в первую очередь.

**9. Проверить синтаксис скрипта без запуска**

```bash
bash -n ~/scripts/backup.sh
```

`-n` — только разбор синтаксиса, без выполнения. Ловит опечатки вроде незакрытого `if` до того, как скрипт уйдёт в cron.

**10. Запустить скрипт «как cron» — с чистым окружением**

```bash
env -i /bin/bash --noprofile --norc -c '/home/adm.student/scripts/backup.sh'
```

Это имитация окружения cron. Если скрипт работает в интерактивной сессии, но падает здесь — почти наверняка проблема в `PATH` или относительных путях.

    THRESHOLD=80
    LOG="/home/adm.student/logs/disk.log"

## 6. Ошибки новичков и безопасность

1. **Ошибка:** забыть `chmod +x` и запускать `./script.sh`. **К чему приводит:** «Permission denied», скрипт не работает. **Как правильно:** `chmod +x` после создания, или запускать через `bash script.sh` (тогда право на выполнение не нужно, но и shebang игнорируется).
2. **Ошибка:** не ставить `set -euo pipefail`. **К чему приводит:** скрипт продолжает работу после ошибки, делает бэкап «пустого» каталога, затирает хороший архив плохим. **Как правильно:** строгий режим в начале каждого серьёзного скрипта.
3. **Ошибка:** относительные пути в скрипте для cron (`tar -czf backup.tar.gz data`). **К чему приводит:** в интерактивной сессии работает, из cron — «No such file or directory», потому что cron запускается из домашнего каталога, а не оттуда, где ты был. **Как правильно:** только абсолютные пути (`/home/adm.student/data`).
4. **Ошибка:** `find ... -delete` без предварительного `-print`. **К чему приводит:** удаление не того, что хотел, включая свежие файлы. **Как правильно:** сначала `-print`, глазами проверить список, потом `-delete`.
5. **Ошибка:** `rm -rf $DIR/` без проверки, что `$DIR` не пустая. **К чему приводит:** если переменная не задана, команда превращается в `rm -rf /` — катастрофа. **Как правильно:** `set -u` (падает на необъявленной переменной) и проверка `[ -n "$DIR" ]` перед удалением.
6. **Ошибка:** не логировать работу cron-задач. **К чему приводит:** задача «молча» не работает месяцами, узнаёшь об этом от пользователя. **Как правильно:** каждая cron-задача пишет в лог-файл с датой и результатом.
7. **Ошибка:** хранить пароли и ключи прямо в скрипте. **К чему приводит:** утечка при любом `cat` или попадании в Git. **Как правильно:** переменные окружения, файлы с правами `600`, или менеджер секретов (в боевой среде).

**Безопасность.** В боевой среде нельзя: запускать `crontab -r` без резервной копии (удалит все задачи пользователя); давать скриптам `sudo` без необходимости; писать в `/tmp` предсказуемые имена файлов (символьные атаки); делать бэкапы в тот же каталог, что и оригинал (при потере диска теряется всё). На стенде мы делаем бэкап в `~/backups` рядом с `~/data` — это учебное упрощение; в реальной работе бэкап уходит на другой диск или сервер. Пароль `Lab#2026-vektor` — только для стенда, в скриптах его быть не должно.

## 7. Вопросы на собеседовании

**Вопрос 1. «Как вы поставите скрипт на ежедневный запуск в Linux?»**

Ответ: «Через cron. Открываю `crontab -e` под нужным пользователем и добавляю строку вида `0 2 * * * /home/user/scripts/backup.sh`. Пять полей — минута, час, день месяца, месяц, день недели. Важно: cron запускает скрипт с минимальным окружением, поэтому в скрипте должны быть абсолютные пути и явный `PATH`, а результат должен писаться в лог-файл, иначе ошибку не увидишь. Проверяю через `journalctl -u cron` и по логу самого скрипта.»

*Что хочет услышать интервьюер:* что ты знаешь про окружение cron и про логирование, а не только про синтаксис строки.
*Красный флаг:* «просто добавляю в crontab и всё работает» — без упоминания логов и путей.

**Вопрос 2. «Что делает `set -euo pipefail` и зачем это в скрипте?»**

Ответ: «`-e` — скрипт завершается при первой команде с ненулевым кодом выхода. `-u` — ошибка при обращении к необъявленной переменной. `-o pipefail` — конвейер возвращает ошибку, если упала любая его часть, а не только последняя. Вместе это «строгий режим»: скрипт падает громко и сразу, а не делает вид, что всё хорошо. Без него бэкап может «успешно» создать пустой архив, если исходный каталог не смонтирован.»

*Что хочет услышать интервьюер:* понимание, что надёжность скрипта — это про обработку ошибок, а не про красоту кода.
*Красный флаг:* путаница в том, что делает каждый флаг.

**Вопрос 3. «Скрипт работает в терминале, но не работает из cron. Что проверять?»**

Ответ: «Первое — окружение: у cron другой `PATH`, нет `.bashrc`. Второе — рабочий каталог: cron запускает из домашнего, относительные пути ломаются. Третье — права: cron работает от имени пользователя, у которого может не быть доступа к файлам. Четвёртое — логи: смотрю `journalctl -u cron` и лог самого скрипта. Пятое — имитирую окружение через `env -i /bin/bash --noprofile --norc -c '...'` и воспроизвожу.»

*Что хочет услышать интервьюер:* системный подход к диагностике, а не «перезапустил — заработало».
*Красный флаг:* «наверное, cron сломался».

**Вопрос 4. «Как сделать бэкап каталога с ротацией, чтобы старые архивы удалялись?»**

Ответ: «`tar -czf archive-$(date +%F).tar.gz -C /path/to dir` — создаёт архив с датой в имени. Ротация — через `find /backup -name 'archive-*.tar.gz' -mtime +7 -delete`. Сначала запускаю с `-print`, проверяю список, потом меняю на `-delete`. Всё это в скрипт, скрипт в cron, результат в лог.»

*Что хочет услышать интервьюер:* что ты знаешь про `find -mtime` и про безопасную проверку перед удалением.
*Красный флаг:* удаление через `rm -rf` по маске без проверки.

**Вопрос 5. «Чем `df` отличается от `du` и что вы будете использовать в скрипте мониторинга диска?»**

Ответ: «`df` показывает занятость файловых систем (сколько всего и сколько свободно на разделе), `du` — сколько занимает конкретный каталог или файл. Для мониторинга «не кончается ли место на разделе» — `df`, потому что он смотрит на файловую систему целиком. В скрипте беру `df -h --output=pcent /`, вытаскиваю число и сравниваю с порогом, при превышении пишу ALERT в лог и возвращаю код 1.»

*Что хочет услышать интервьюер:* понимание разницы и умение вытащить число из вывода для сравнения.
*Красный флаг:* «`du` показывает свободное место» — путаница.
