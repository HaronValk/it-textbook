# DNS: иерархия, записи, кэш, диагностика через nslookup и dig

## 1. Введение (зачем это нужно в реальной работе)

Понедельник, 9:20. В тикете новое сообщение:

> **Пользователь:** Иван Иванов (бухгалтерия, WIN11-CL01)
> **Что написал:** «Не могу зайти на сервер: набираю `UBU01.corp.vektor.lab` — браузер/проводник пишет, что не удаётся найти узел. Но `ping 10.10.10.30` проходит нормально!»
> **Срочность:** средняя, но бухгалтерия стоит.

Это классика. Сеть работает, адрес есть, а имя не превращается в адрес. Значит, проблема почти наверняка в DNS — и разбираться нужно быстро и по шагам, а не «перезагрузите компьютер».

DNS (Domain Name System, система доменных имён) — это то, что превращает понятное человеку имя в понятный машине IP-адрес. В работе L1 ты будешь сталкиваться с DNS каждый день: «не открывается сайт», «не подключается папка по имени», «не могу войти в домен», «после переезда сервера половина людей видит старый адрес», «не печатает принтер по имени». Больше половины заявок «не работает интернет» на поверку оказываются DNS-заявками.

После этой главы ты должен уметь: объяснить, что происходит при запросе имени; понимать, из чего состоит DNS-ответ; знать основные типы записей и зачем каждая нужна; проверять имя через `nslookup`, `Resolve-DnsName` и `dig`; читать кэш и сбрасывать его; и главное — по симптомам отличать «сломан DNS» от «сломано что-то другое».

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

DNS — прикладной протокол, работает поверх UDP-порта 53. Если ответ не влезает в UDP-пакет или это передача зоны, используется TCP/53. Есть ещё шифрованные варианты: DoT (DNS over TLS, порт 853) и DoH (DNS over HTTPS, порт 443) — в корпоративной среде их обычно прикрывают, чтобы не обходить внутреннюю фильтрацию.

**Иерархия.** DNS — распределённая база, устроенная как дерево. Сверху корень «`.`», ниже домены первого уровня (`ru`, `com`, `lab`), ниже — твои домены (`corp.vektor.lab`), внутри них — отдельные записи. За каждую зону отвечает свой авторитативный (authoritative) сервер: именно он хранит «настоящие» записи зоны и отвечает по ним.

```text
                       . (корневые серверы)
                       |
        +--------------+--------------+
        |              |              |
       ru             com            lab  <- TLD (домены верхнего уровня)
                                     |
                            corp.vektor.lab   <- авторитативная зона
                                     |            (наш DC01)
        +--------+--------+----------+---------+
        |        |        |          |         |
    DC01(A)  UBU01(A)  ASTRA01(A)  ubu(CNAME)  PTR
```

**Полный цикл запроса.** Клиент (резолвер Windows) спрашивает у своего DNS-сервера — на стенде это DC01 (10.10.10.10). Если у DC01 ответа нет, он идёт спрашивать дальше: к корневым серверам, затем к серверу зоны `.lab`, затем к авторитативному серверу `corp.vektor.lab`. Клиенту DC01 отвечает **рекурсивно** («я всё сделаю сам, вот тебе готовый ответ»), а к вышестоящим серверам обращается **итеративно** («мне нужен `.lab` — иди спроси у него»). Разницу между рекурсией и итерацией любят спрашивать на собеседованиях.

**Кэш.** Каждый ответ приходит с параметром TTL (Time To Live, время жизни) в секундах: сколько его можно держать в кэше, не переспрашивая. Кэшей в цепочке несколько: кэш твоего резолвера на DC01, кэш клиента Windows (служба «DNS Client», она же Dnscache), на Linux — systemd-resolved. TTL — это причина, почему «я поправил запись, а пользователь видит старый адрес».

**Отрицательный кэш.** Кэшируется и ответ «такого имени нет» (NXDOMAIN) — по значению из SOA-записи зоны. Поэтому после создания новой записи иногда приходится ждать или сбрасывать кэш.

**Основные типы записей** (это то, что ты будешь создавать и читать руками):

| Тип | Что делает | Пример |
|-----|-----------|--------|
| A | имя → IPv4-адрес | `UBU01.corp.vektor.lab → 10.10.10.30` |
| AAAA | имя → IPv6-адрес | `UBU01 → fd00::30` |
| CNAME | псевдоним → другое имя | `ubu → UBU01.corp.vektor.lab` |
| PTR | обратная запись, адрес → имя | `30.10.10.10.in-addr.arpa → UBU01...` |
| MX | почтовый сервер домена | `corp.vektor.lab → mail...` |
| TXT | произвольный текст (SPF, проверки) | `v=spf1 ...` |
| NS | какие серверы обслуживают зону | `corp.vektor.lab → dc01...` |
| SOA | «паспорт» зоны: кто главный, default TTL | `corp.vektor.lab → dc01...` |
| SRV | сервис + порт + хост | `_ldap._tcp.corp.vektor.lab`, `_kerberos._tcp...` |

Записи SRV — кровь домена Active Directory: клиент по ним ищет контроллер домена. Если SRV сломаны, «не могу войти в домен» будет даже при работающем пинге.

**Где лежит в ОС.** Linux читает `/etc/resolv.conf` (на Ubuntu 24.04 это ссылка и там обычно `nameserver 127.0.0.53` — заглушка systemd-resolved), локальные переопределения — в `/etc/hosts`. Windows берёт адреса DNS-серверов из настроек адаптера (или из DHCP), переопределения — в `C:\Windows\System32\drivers\etc\hosts`. Порядок обычно такой: hosts → кэш → DNS-сервер.

## 3. Аналогия из жизни

Представь огромную справочную службу города, где нет единой базы, а есть иерархия: на верхнем уровне — «Главная справочная страны», у неё есть номера «справочных по районам», у тех — «справочные по улицам», а уж они знают конкретные квартиры.

Ты звонишь в свою районную справочную (свой DNS-сервер) и спрашиваешь: «дай телефон Сидорова на Складской, 5». Если её уже спрашивали сегодня, она отвечает мгновенно по записке из ящика (кэш), причём записка действительна ограниченное время (TTL) — потом её выбрасывают. Если не спрашивали, она сама обзванивает вышестоящие справочные (итеративные запросы), получает ответ, диктует тебе и заодно кладёт себе записку.

Ты же, повесив трубку, тоже записал номер на стикер и приклеил на монитор — это кэш клиента. И если человека перевели в другой офис, ты будешь звонить по стикеру, пока его не снять.

Аналогия перестаёт работать в одном месте: у телефонного номера нет срока годности, а у DNS-записи есть TTL — и именно из-за него «всё поправили, а у меня не работает».

## 4. Практика и команды

**1. `nslookup` без аргументов — какой сервер используется.**

```cmd
C:\>nslookup
Default Server:  UnKnown
Address:  10.10.10.10
```

`UnKnown` — это не ошибка: `nslookup` при старте делает обратный запрос к своему DNS-серверу, чтобы показать его имя, и не находит PTR-запись для 10.10.10.10. Как только добавим PTR для DC01 — увидим нормальное имя. Смотреть здесь нужно строку `Address` — тот сервер, который реально будет опрашиваться.

**2. Прямой запрос имени и полного имени (FQDN).**

```cmd
C:\>nslookup UBU01.corp.vektor.lab
Server:  UnKnown
Address:  10.10.10.10

Non-authoritative answer:
Name:    UBU01.corp.vektor.lab
Address:  10.10.10.30
```

FQDN (Fully Qualified Domain Name, полное доменное имя) — имя с зоной. `Non-authoritative answer` означает «ответ взят из кэша, а не с авторитативного сервера» — это норма, а не ошибка (частая паника новичков).

**3. Короткое имя — проверка суффиксов.**

```cmd
C:\>nslookup UBU01
Server:  UnKnown
Address:  10.10.10.10

Name:    UBU01.corp.vektor.lab
Address:  10.10.10.30
```

Сработало, потому что клиент подставил суффикс из списка поиска. Посмотреть список суффиксов: `ipconfig /all` → строки `Primary DNS Suffix` и `DNS Suffix Search List`. Если короткое имя не находится, а FQDN — да, проблема в суффиксе (на стенде он приходит из DHCP, option 015), а не в DNS-сервере.

**4. Запрос конкретного типа записи.**

```cmd
C:\>nslookup -type=SOA corp.vektor.lab
C:\>nslookup -type=NS corp.vektor.lab
C:\>nslookup -type=SRV _ldap._tcp.corp.vektor.lab
```

Ключ `-type=` (в интерактивном режиме — `set type=`) задаёт тип записи. SRV смотри на будущее: когда поднимем AD, эти записи должны быть на месте, иначе клиенты не найдут контроллер домена.

**5. Обратный запрос по IP (PTR).**

```cmd
C:\>nslookup 10.10.10.30
Server:  UnKnown
Address:  10.10.10.10

Name:    UBU01.corp.vektor.lab
Address:  10.10.10.30
```

Обратный запрос работает только если есть зона обратного просмотра `10.10.10.in-addr.arpa` с PTR-записью. Нет зоны — будет `can't find 30.10.10.10.in-addr.arpa: Non-existent domain`. Для диагностики это важно: многие программы (логи, мониторинг, некоторые проверки прав) любят обратный резолв.

**6. Опрос другого DNS-сервера — сравнение ответов.**

```cmd
C:\>nslookup UBU01.corp.vektor.lab 8.8.8.8
```

Второй аргумент — адрес сервера. Приём №1 в диагностике: спросить внутреннее имя у внутреннего сервера (10.10.10.10) и у внешнего. Если внутренний отвечает, а внешний — нет, «поломки DNS» нет вообще, так и должно быть: внешние резолверы про `corp.vektor.lab` не знают. Отдельно: доступность публичных резолверов из РФ в 2026 может отличаться — в бою используй те, что выданы провайдером/компанией, а не «8.8.8.8 по привычке».

**7. `ipconfig` — настройки и кэш клиента.**

```cmd
C:\>ipconfig /all
C:\>ipconfig /displaydns
C:\>ipconfig /flushdns
C:\>ipconfig /registerdns
```

`/all` — смотреть блок адаптера: `DNS Servers`, `DNS Suffix Search List`, кто выдал адрес (DHCP-сервер). `/displaydns` — содержимое кэша: `Record Name`, `Record Type`, `Time To Live` (сколько секунд осталось), `A (Host) Record`. `/flushdns` — очистить кэш (первое, что делаем после правки записи). `/registerdns` — попросить клиента перерегистрировать своё имя в DNS.

**8. PowerShell: современная замена nslookup.**

```powershell
PS> Resolve-DnsName UBU01.corp.vektor.lab -Server 10.10.10.10
PS> Resolve-DnsName corp.vektor.lab -Type SOA
PS> Get-DnsClientCache | Where-Object Entry -like "*vektor*"
PS> Clear-DnsClientCache
```

`-Server` — кого спрашиваем, `-Type` — тип записи, `-CacheOnly` — посмотреть только кэш, `-DnsOnly` — не лезть в hosts и прочие источники. Вывод объектовый: с колонками `Name`, `Type`, `TTL`, `IPAddress` — читать удобнее, чем текст `nslookup`.

**9. На DNS-сервере (DC01): что реально лежит в зоне.**

```powershell
PS> Get-DnsServerZone
PS> Get-DnsServerResourceRecord -ZoneName corp.vektor.lab
PS> Get-DnsServerResourceRecord -ZoneName corp.vektor.lab -Name UBU01
PS> Clear-DnsServerCache
```

Команды модуля `DnsServer` (стоят на DC01 вместе с ролью). Это взгляд «изнутри»: не что ответил сервер, а что у него записано. `Clear-DnsServerCache` — сброс кэша самого сервера (нужно, если DC01 закэшировал чужой/неверный ответ).

**10. Linux: `dig`, базовый вывод.**

```bash
$ sudo apt install -y bind9-dnsutils    # если dig ещё не установлен
$ dig @10.10.10.10 UBU01.corp.vektor.lab A

; <<>> DiG 9.18.x <<>> @10.10.10.10 UBU01.corp.vektor.lab A
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 41235
;; flags: qr aa rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 1, ADDITIONAL: 1

;; QUESTION SECTION:
;UBU01.corp.vektor.lab.        IN    A

;; ANSWER SECTION:
UBU01.corp.vektor.lab.    3600    IN    A    10.10.10.30

;; Query time: 1 msec
;; SERVER: 10.10.10.10#53(10.10.10.10) (UDP)
```

`@сервер` — кого спрашиваем (без него dig пойдёт в systemd-resolved на 127.0.0.53). Что смотреть: `status:` (`NOERROR` — ок, `NXDOMAIN` — имени нет, `SERVFAIL` — сервер не смог, `REFUSED` — не пустили), флаг `aa` (ответ авторитативный, из самой зоны), `ANSWER SECTION` с TTL, и строку `SERVER` — точно ли тот сервер ответил.

**11. Linux: короткие формы и обратный запрос.**

```bash
$ dig +short UBU01.corp.vektor.lab
10.10.10.30

$ dig -x 10.10.10.30 +short
UBU01.corp.vektor.lab.

$ dig @10.10.10.10 corp.vektor.lab SOA +noall +answer
$ dig @10.10.10.10 UBU01.corp.vektor.lab +norecurse
```

`+short` — только ответ (удобно в скриптах), `-x` — обратный запрос, `+noall +answer` — только секция ответа, `+norecurse` — «не рекурсируй» (показывает, есть ли ответ именно у этого сервера).

**12. Linux: показать иерархию вживую и проверить, куда смотрит система.**

```bash
$ dig +trace corp.vektor.lab
$ resolvectl status
$ resolvectl query UBU01.corp.vektor.lab
$ getent hosts UBU01.corp.vektor.lab
```

`+trace` проходит от корневых серверов вниз — наглядная демонстрация иерархии (нужен доступ в интернет; если в лаборатории его нет — команда просто не отработает, это нормально). `resolvectl status` показывает, какие DNS-серверы у каждого интерфейса. `getent hosts` идёт через NSS, то есть **учитывает `/etc/hosts`** — в отличие от `dig` и `nslookup`, которые всегда спрашивают DNS напрямую. Это ключевое различие для диагностики.

**GUI на стенде.** DNS-оснастка на DC01: `Win+R` → `dnsmgmt.msc` → дерево «Зоны прямого просмотра» / «Зоны обратного просмотра». На клиенте кэш смотреть нечем — только `ipconfig /displaydns` или `Get-DnsClientCache`.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

- **DC01** (10.10.10.10, статический IP) — роль DNS установлена, настроена в уроке 33 вместе с DHCP (DHCP отдаёт клиентам option 006 = 10.10.10.10). AD DS ещё не установлен — зону делаем обычную, с хранением в файле; в модуле Active Directory она станет интегрированной в AD.
- **WIN11-CL01** — получает адрес по DHCP, DNS-сервер = 10.10.10.10.
- **UBU01** (10.10.10.30, статический IP) — для проверок по SSH, `dig` установлен (`bind9-dnsutils`).
- **ASTRA01** (10.10.10.31) — если создана в уроке 30, добавим и её; если нет, шаг пропускаем.
- FS01 в этот момент ещё не существует — она появится в темах про файлы и печать. Ничего страшного, проверять будем на UBU01.

### Снапшот

В VMware Workstation на **DC01**, **WIN11-CL01** и **UBU01**: правой кнопкой по вкладке ВМ → **Snapshot → Take Snapshot**, имя `before-l1-034`. (Можно и через меню **VM → Snapshot → Take Snapshot**.) Снапшот делать при выключенной или хотя бы «уснувшей» ВМ — так надёжнее.

### Шаги

1. **DC01.** Проверяем, что DNS-служба жива: `Get-Service DNS`. Ожидаемо: `Status = Running`. Если роли нет — `Install-WindowsFeature DNS -IncludeManagementTools`, перезапуск не требуется.
2. **DC01.** Смотрим зоны: `Get-DnsServerZone`. Ожидаемо: в списке есть `corp.vektor.lab` (тип `Primary`, `IsDsIntegrated = False`) либо её нет. Если нет — создаём:
   ```powershell
   Add-DnsServerPrimaryZone -Name corp.vektor.lab -ZoneFile corp.vektor.lab.dns
   ```
   Ожидаемо: зона появилась, в ней автоматически есть записи `SOA` и `NS`.
3. **DC01.** Создаём A-записи для серверов:
   ```powershell
   Add-DnsServerResourceRecordA -Name UBU01 -ZoneName corp.vektor.lab -IPv4Address 10.10.10.30 -CreatePtr
   Add-DnsServerResourceRecordA -Name ASTRA01 -ZoneName corp.vektor.lab -IPv4Address 10.10.10.31 -CreatePtr
   ```
   Ключ `-CreatePtr` заодно создаёт PTR (если зоны обратного просмотра ещё нет, команда её создаст — если не создала, делаем шаг 4). Ожидаемо: записи появились. Если `ASTRA01` нет — пропускаем вторую строку.
4. **DC01.** Если зоны обратного просмотра нет — создаём вручную:
   ```powershell
   Add-DnsServerPrimaryZone -NetworkId 10.10.10.0/24 -ReplicationScope None
   ```
   Ожидаемо: появилась зона `10.10.10.in-addr.arpa`. **`[ПРОВЕРИТЬ]`** точный синтаксис `-NetworkId` в твоей версии; альтернатива — GUI: `dnsmgmt.msc` → «Зоны обратного просмотра» → «Создать зону» → «Основная зона» → «IPv4, обратная зона» → `10.10.10`.
5. **DC01.** Добавляем PTR для самого контроллера домена и CNAME-псевдоним:
   ```powershell
   Add-DnsServerResourceRecordPtr -Name 10 -ZoneName 10.10.10.in-addr.arpa -PtrTarget DC01.corp.vektor.lab
   Add-DnsServerResourceRecordCName -Name ubu -HostNameAlias UBU01.corp.vektor.lab -ZoneName corp.vektor.lab
   ```
   Ожидаемо: `nslookup 10.10.10.10` отвечает `DC01.corp.vektor.lab`, `nslookup ubu` — `10.10.10.30`.
6. **WIN11-CL01.** Проверяем настройки и резолв:
   ```cmd
   ipconfig /all
   nslookup UBU01.corp.vektor.lab
   nslookup ubu.corp.vektor.lab
   ```
   Ожидаемо: `DNS Servers . . . : 10.10.10.10`, оба запроса отдают `10.10.10.30`. Строка `Default Server` теперь показывает `DC01.corp.vektor.lab`, а не `UnKnown` — потому что появился PTR.
7. **WIN11-CL01.** Смотрим кэш и его TTL:
   ```cmd
   ipconfig /displaydns
   ```
   Ожидаемо: в выдаче есть `ubu.corp.vektor.lab` и `UBU01.corp.vektor.lab` с `Time To Live`, уменьшающимся при повторном запуске.
8. **WIN11-CL01.** Демонстрация обратного резолва:
   ```cmd
   nslookup 10.10.10.30
   nslookup 10.10.10.55
   ```
   Ожидаемо: первая команда вернёт имя, вторая — `Non-existent domain` (машины нет). Так выглядит «нет PTR».
9. **UBU01.** Смотрим, куда смотрит Linux, и спрашиваем DC01 напрямую:
   ```bash
   cat /etc/resolv.conf
   resolvectl status | head -20
   dig @10.10.10.10 UBU01.corp.vektor.lab A
   dig @10.10.10.10 ubu.corp.vektor.lab A +short
   ```
   Ожидаемо: в `/etc/resolv.conf` — `nameserver 127.0.0.53` (это systemd-resolved, норма для Ubuntu 24.04), в `resolvectl status` DNS-сервер `10.10.10.10`, оба `dig` возвращают `10.10.10.30`, флаг `aa` присутствует.
10. **UBU01.** Обратный запрос и проверка отсутствующего имени:
    ```bash
    dig -x 10.10.10.30 +short
    dig @10.10.10.10 server99.corp.vektor.lab
    ```
    Ожидаемо: первая — `UBU01.corp.vektor.lab.`, вторая — `status: NXDOMAIN`. Запомни этот ответ: именно так в диагностике выглядит «имени не существует».
11. **DC01 (необязательно, но показательно).** Проверяем динамическую регистрацию: `dnsmgmt.msc` → свойства зоны `corp.vektor.lab` → `Dynamic Updates` → временно `Nonsecure and secure`; на WIN11-CL01 — `ipconfig /registerdns`; на DC01 — `Get-DnsServerResourceRecord -ZoneName corp.vektor.lab -Name WIN11-CL01`. Ожидаемо: появилась A-запись клиента.
    **Безопасность:** режим `Nonsecure and secure` разрешает *любому* хосту в сети перезаписать любую запись — на стенде это допустимо на 5 минут, в боевой среде так делать нельзя. Сразу верни `Secure only`; при не-AD-зоне безопасная динамика не работает, поэтому для клиентов вне домена записи обычно создают вручную или через DHCP.
12. **Все машины.** Возвращаем зону в безопасный режим (`Secure only`), проверяем `stand-log.md` и записываем изменения.

1. Воспроизводим симптом: `ping UBU01.corp.vektor.lab`. Ожидаемо: пинг идёт на `10.10.10.99` и не отвечает — **при этом адрес в выводе уже подозрительный**, не тот, что мы ожидаем.

## 6. Ошибки новичков и безопасность

1. **«Пропишем 8.8.8.8, чтобы точно работало».** → Внутренние имена (`corp.vektor.lab`, `FS01`) перестают резолвиться: внешний сервер про них не знает. → Правильно: DNS-серверы для рабочих станций выдаёт DHCP (внутренний 10.10.10.10), а внешние запросы DC01 пересылает через forwarders.
2. **Верить `ping` и не проверять `nslookup`.** → Лечишь «сеть», когда виноват hosts-файл или кэш. → Правильно: всегда сверять, что говорит DNS (`nslookup`/`dig`) и что говорит система (`ping`, `getent hosts`). Расхождение — почти всегда локальный источник имён.
3. **Править запись и не сбрасывать кэш.** → «Я же исправил, почему у пользователя старый адрес?» → Правильно: помнить про TTL на трёх уровнях (клиент → сервер → вышестоящий) и после правки делать `ipconfig /flushdns` на клиенте, при необходимости `Clear-DnsServerCache` на DC01.
4. **Создавать CNAME на контроллер домена или на имя, где нужны MX/NS.** → Ломается регистрация SRV, почта, вход в домен. → Правильно: для серверов — A-записи; CNAME только для псевдонимов сервисов (веб, печать), и никогда в вершине зоны рядом с MX/NS.
5. **Считать «Non-authoritative answer» ошибкой.** → Тратишь время на исправление того, что работает. → Правильно: это просто ответ из кэша; смотри на `status`/`ANSWER`.
6. **Путать «имени нет» и «сервер не отвечает».** → `NXDOMAIN` — записи не существует; `SERVFAIL`/`REFUSED`/таймаут — проблема с сервером или сетью. → Правильно: сначала читать `status`, потом делать вывод.
7. **Ставить «nonsecure» динамические обновления «чтобы заработало».** → Любой хост в сети может перезаписать любую запись и увести трафик на себя. → Правильно: AD-интегрированная зона + `Secure only`; записи статичных серверов создавать вручную.
8. **Не проверять обратный резолв.** → Часть приложений и мониторинга тихо страдает, а заявки «иногда не пускает» копятся. → Правильно: держать в порядке зоны обратного просмотра для всех внутренних подсетей.

**Безопасность.** DNS — лакомая цель: подмена ответа уводит пользователя на чужой сервер с тем же интерфейсом (DNS spoofing), а неверная запись может отправить почту или трафик наружу. В боевой среде нельзя: разрешать небезопасные динамические обновления; отдавать передачу зоны (`dig AXFR`) всем желающим — только своим DNS-серверам; держать внутреннюю зону на публичном резолвере; менять записи без записи в тикете (все изменения DNS должны быть задокументированы — иначе через месяц никто не поймёт, откуда взялся адрес). На стенде учебный пароль `Lab#2026-vektor` — только для стенда: в реальной работе такие пароли недопустимы.

## 7. Вопросы на собеседовании

**1. Пользователь говорит: «Сайт по имени не открывается, а по IP открывается». С чего начнёте?**

Ответ: это сужает круг до преобразования имени. Порядок: (1) с машины пользователя `nslookup <имя>` — есть ли ответ и тот ли адрес; (2) `ipconfig /all` — какие DNS-серверы и суффиксы выданы, не «8.8.8.8» ли там; (3) сверить с `ping <имя>` — если расходятся, проверять `C:\Windows\System32\drivers\etc\hosts`; (4) посмотреть кэш `ipconfig /displaydns`, при необходимости `ipconfig /flushdns`; (5) проверить запись на самом DNS-сервере (`Get-DnsServerResourceRecord`, `dnsmgmt.msc`); (6) убедиться, что сервис на целевом хосте вообще слушает нужный порт, а не только пингуется. Дальше — эскалация на L2, если запись на сервере верная, а резолв не идёт.

*Что хочет услышать интервьюер:* структурный порядок «клиент → кэш → сервер → сервис» и понимание, что DNS и доступность сервиса — разные вещи.
*Красный флаг:* «перезагрузите компьютер», «пропишите 8.8.8.8», «переустановите Windows» без единой проверки.

**2. Чем рекурсивный запрос отличается от итеративного и кто такие авторитативные серверы?**

Ответ: рекурсивный — «сделай всё сам и верни готовый ответ»: клиент так спрашивает свой резолвер, и тот обязан найти ответ или вернуть ошибку. Итеративный — «ответь, что знаешь, или подскажи, к кому идти»: резолвер так обходит корневые серверы, серверы зон `.lab` и `corp.vektor.lab`. Авторитативный сервер — тот, у которого хранится сама зона; он отвечает с флагом `aa` и считается источником истины, остальные ответы — кэш.

*Что хочет услышать интервьюер:* понимание, что резолвер — это «прослойка с кэшем», а не «главный сервер интернета».
*Красный флаг:* путаница «авторитативный = главный в мире» или уверение, что клиент сам обходит корневые серверы.

**3. Какие типы DNS-записей знаете и зачем они нужны?**

Ответ: A — имя в IPv4; AAAA — в IPv6; CNAME — псевдоним на другое имя; PTR — обратная запись, адрес в имя (зоны `in-addr.arpa`); MX — почтовые серверы домена с приоритетами; TXT — текст (SPF/DKIM, подтверждения владения доменом); NS — какие серверы обслуживают зону; SOA — параметры зоны, включая TTL для отрицательного кэша; SRV — сервис + порт + хост, критично для Active Directory (`_ldap._tcp`, `_kerberos._tcp`).

*Что хочет услышать интервьюер:* что помнишь не только A, и что знаешь про SRV и PTR.
*Красный флаг:* «есть A и ещё какие-то».

**4. Что такое TTL и почему после изменения записи пользователи видят старый адрес?**

Ответ: TTL — время жизни ответа в кэше в секундах. Ответ кэшируется на клиенте, на внутреннем резолвере и, возможно, выше. Пока TTL не истёк, все получают старое значение. Практика: заранее снизить TTL до правки (например, до 300), подождать истечения старого TTL, внести изменение, а на клиентах сделать `ipconfig /flushdns` (`Clear-DnsClientCache`); на Linux — `resolvectl flush-caches`; на DNS-сервере — `Clear-DnsServerCache`. Кэшируется и отрицательный ответ (NXDOMAIN) — по SOA.

*Что хочет услышать интервьюер:* понимание многоуровневости кэша и того, что сброс кэша — часть процедуры изменения, а не «костыль».
*Красный флаг:* «TTL — это время работы сервера» или «кэш только на клиенте».

**5. Чем `nslookup` отличается от `dig` и почему `nslookup` «врёт»?**

Ответ: обе утилиты опрашивают DNS-сервер напрямую и **не читают** `/etc/hosts` и hosts-файл Windows — поэтому они показывают «истину DNS», а не то, что реально использует система. Различия: `nslookup` есть в Windows из коробки, работает в интерактивном режиме, вывод текстовый и менее удобный; `dig` (Linux, пакет `bind9-dnsutils`) даёт структурированный ответ с секциями QUESTION/ANSWER/AUTHORITY, флагами (`aa`, `rd`, `ra`), статусом (`NOERROR`, `NXDOMAIN`, `SERVFAIL`), умеет `+short`, `+trace`, `-x`, `@server`. Чтобы увидеть, что реально получит приложение с учётом hosts, на Linux используют `getent hosts`, на Windows — `ping` по имени или `Resolve-DnsName` без `-DnsOnly` (учитывает локальные источники).

*Что хочет услышать интервьюер:* что ты понимаешь разницу между «что в DNS» и «что получит программа».
*Красный флаг:* «dig и nslookup — одно и то же, просто для разных ОС» без понимания источников имён.
