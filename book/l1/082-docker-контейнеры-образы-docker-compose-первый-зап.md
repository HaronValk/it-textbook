## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Контейнер** — это изолированный процесс (или группа процессов) на хосте, которому ОС подсовывает иллюзию отдельной машины: своё дерево файлов, свои сетевые интерфейсы, свой список процессов, свои лимиты на CPU и память.

Изоляцию дают две механизмы ядра Linux:

- **namespaces** — «шторки», через которые процесс не видит чужих процессов (pid), своей сетью (net), своей точкой монтирования (mnt), своим именем хоста (uts), своими пользователями (user).
- **cgroups** (control groups) — «счётчики и лимиты»: сколько процессу можно CPU, памяти, дискового I/O.

Ключевое: **контейнер не содержит своей ОС**. Он использует ядро хоста. Поэтому контейнер весит мегабайты, стартует за секунды и на одной ВМ их помещаются десятки. Виртуальная машина (как твои DC01 и FS01) — это полноценная ОС со своим ядром, отсюда гигабайты и минуты на загрузку.

**Образ (image)** — это упакованная файловая система плюс метаданные (какая команда запускается, какие порты открыты, какие переменные окружения). Образ собирается **слоями**: каждый шаг сборки — новый read-only слой поверх предыдущих. Слои переиспользуются между образами, поэтому `nginx` и `nginx:alpine` могут делить половину слоёв. Сверху контейнер получает тонкий **записываемый слой** (обычно драйвер `overlay2`), и всё, что процесс пишет внутрь контейнера, живёт только пока живёт контейнер. Удалил контейнер — данные внутри исчезли. Именно поэтому в реальной работе базы и файлы выносят в **volumes** (тома).

**Реестр (registry)** — склад образов. Публичный — Docker Hub (`hub.docker.com`), обращения идут на `registry-1.docker.io` и `auth.docker.io` по HTTPS (443). Скачивание образа = `docker pull`, отправка своего = `docker push`.

Схема того, что происходит на UBU01:

```text
   ТЫ                    UBU01 (10.10.10.30, Ubuntu 24.04)
    │                          │
    │ docker run -d -p 8080:80 │
    ├─────────────────────────►│  docker (CLI)  ──HTTP──► /var/run/docker.sock
    │                          │        │
    │                          │        ▼
    │                          │   dockerd (демон, root)
    │                          │        │ создаёт контейнер
    │                          │        ▼
    │                          │   containerd ──► runc ──► процесс nginx
    │                          │                            │
    │                          │   namespaces (изоляция)    │
    │                          │   cgroups   (лимиты)       │
    │                          │   overlay2  (слои образа + RW-слой)
    │                          │
    │ ◄── TCP 8080 ────────────┤  проброс порта хоста в контейнер
   браузер на WIN11-CL01
```

**docker-compose (сегодня — команда `docker compose`)** — это декларативный способ описать несколько контейнеров в одном YAML-файле: какие образы, какие порты, какие тома, какой порядок запуска. Compose сам создаёт общую сеть, в которой контейнеры видят друг друга **по имени сервиса как по DNS-имени**. Это твой первый шаг к «инфраструктура как код»: файл лежит в Git (урок 77), и по нему стенд воспроизводится один в один.

Важно про уровни: L1 не собирает образы и не пишет Dockerfile — L1 **эксплуатирует** уже готовое и диагностирует. Но понимать слои и порты обязан, иначе диагностика превращается в гадание.

## 3. Аналогия из жизни

Представь многоэтажный дом. **Ядро Linux** — это фундамент и общие трубы дома: водопровод, электричество, канализация. **Контейнер** — съёмная квартира в этом доме: у неё свои стены (namespaces), свой счётчик воды и электричества (cgroups), свой номер (IP), и соседи не видят, что у тебя происходит за стеной. **Образ** — типовой проект квартиры: планировка, мебель, обои. Из одного проекта можно собрать хоть двадцать одинаковых квартир, и все они будут выглядеть идентично. **Реестр** — склад типовых проектов, откуда ты берёшь нужный. **Compose** — договор аренды сразу на несколько квартир: «веб-сервер в 12-й, а whoami в 13-й, и пусть они ходят друг к другу в гости по именам».

Ломается аналогия на одном: если квартира затапливает, страдает весь дом, потому что фундамент и трубы общие — как и контейнер, который «съел» всю память хоста, роняет соседей, ведь ядро у них одно.

## 4. Практика и команды

Все команды — на **UBU01** (Ubuntu Server 24.04, 10.10.10.30), под своим пользователем через `sudo`, либо под пользователем из группы `docker`.

### 4.1. Установка Docker Engine

Официальный путь (репозиторий Docker):

```bash
sudo apt update
sudo apt install -y ca-certificates curl gnupg
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

Разбор: `docker-ce` — сам движок, `docker-ce-cli` — клиент, `containerd.io` — низкоуровневый runtime, `docker-buildx-plugin` — расширенная сборка, `docker-compose-plugin` — тот самый `docker compose` (обрати внимание: с пробелом, не через дефис; старый `docker-compose` v1 устарел).

**Реалии РФ 2026:** `download.docker.com` из России может быть недоступен или нестабилен `[ПРОВЕРИТЬ]`. Легальная альтернатива — пакет из репозитория самой Ubuntu:

```bash
sudo apt update
sudo apt install -y docker.io docker-compose-v2
```

Пакеты старее официальных, но рабочие и без внешних репозиториев `[ПРОВЕРИТЬ: наличие docker-compose-v2 в noble]`. Ещё одна легальная альтернатива — **Podman** (совместимый CLI, умеет rootless). Никаких «крякнутых Docker Desktop» — это не вариант ни по лицензии, ни по безопасности.

### 4.2. Проверка версии

```bash
docker --version
docker version
```

Ожидаемо: `Docker version 27.x.x, build ...` `[ПРОВЕРИТЬ актуальную мажорную версию на 2026]`. `docker version` покажет две части — Client и Server. Если Server пустой и ошибка «Cannot connect to the Docker daemon» — демон не запущен: `sudo systemctl status docker`.

### 4.3. Информация о движке

```bash
docker info
```

Сокращённый вывод:

```text
Server Version: 27.x
Storage Driver: overlay2
Cgroup Driver: systemd
Containers: 3
 Running: 1
Images: 5
Server: Docker Engine - Community
```

Что смотреть: `Storage Driver` (должен быть `overlay2`), `Running` (сколько контейнеров живо), `Images` (сколько образов на диске). Если тут `Containers: 87` и диск забит — пора чистить.

### 4.4. Скачать образ и посмотреть список

```bash
docker pull nginx:stable-alpine
docker images
```

```text
REPOSITORY   TAG             IMAGE ID       CREATED        SIZE
nginx        stable-alpine   a1b2c3d4e5f6   2 weeks ago    48MB
hello-world  latest          d1e2f3a4b5c6   3 months ago   13.3kB
```

Ключи: `pull <образ>:<тег>` — тег это версия; **никогда не используй `latest` в работе**, он «переезжает» и однажды ломает сервис. Смотри на `SIZE`: `alpine`-варианты в разы меньше.

### 4.5. Запустить контейнер

```bash
docker run -d --name web-test -p 8080:80 nginx:stable-alpine
```

Разбор по частям:
- `run` — создать контейнер из образа и запустить;
- `-d` (detach) — в фоне, вернуть управление;
- `--name web-test` — человекочитаемое имя (иначе Docker выдаст случайное вроде `focused_turing`);
- `-p 8080:80` — **хост-порт:порт-в-контейнере**. Именно здесь новички путают порядок;
- образ в конце.

Ожидаемый вывод — длинный ID контейнера.

### 4.6. Список контейнеров

```bash
docker ps
docker ps -a
```

```text
CONTAINER ID   IMAGE                 STATUS         PORTS                  NAMES
9f8e7d6c5b4a   nginx:stable-alpine   Up 2 minutes   0.0.0.0:8080->80/tcp   web-test
```

`docker ps` — только живые, `docker ps -a` — все, включая `Exited (1)`. **Всегда начинай диагностику с `-a`**, иначе упавший контейнер просто не увидишь.

### 4.7. Логи

```bash
docker logs web-test
docker logs -f --tail 50 web-test
```

`-f` — следить в реальном времени (выход по Ctrl+C), `--tail 50` — последние 50 строк. Логи — первое, что читают, когда контейнер упал. Если контейнер выходит сразу, здесь будет причина: `nginx: [emerg] ...`, `permission denied`, `port already in use`.

### 4.8. Зайти внутрь

```bash
docker exec -it web-test sh
ls /usr/share/nginx/html
cat /etc/nginx/conf.d/default.conf
exit
```

`exec` — выполнить команду в работающем контейнере, `-i` — интерактивно, `-t` — псевдотерминал. В alpine-образах нет bash, только `sh`. Внутри ты видишь только файлы контейнера — это его собственная файловая система.

### 4.9. Подробности о контейнере

```bash
docker inspect web-test --format '{{.State.Status}} {{.NetworkSettings.IPAddress}}'
docker inspect web-test --format '{{json .Config.Env}}'
```

`--format` — Go-шаблоны, удобно вытащить одно поле. Смотреть `State.Status`, `State.ExitCode`, `HostConfig.RestartPolicy`.

### 4.10. Кто занял порт (Linux)

```bash
sudo ss -tlnp | grep 8080
```

`-t` TCP, `-l` слушающие, `-n` номера вместо имён, `-p` процесс. На Windows-хосте аналог — `netstat -ano | findstr :8080` в `cmd` и потом `tasklist /FI "PID eq <pid>"`.

### 4.11. Остановить и удалить

```bash
docker stop web-test
docker rm web-test
docker rmi nginx:stable-alpine
```

`stop` — мягкая остановка (SIGTERM, потом SIGKILL), `rm` — удалить контейнер, `rmi` — удалить образ (нельзя, пока от него есть контейнеры). Быстро: `docker rm -f web-test`.

### 4.12. Compose

```bash
docker compose up -d
docker compose ps
docker compose logs -f
docker compose down
```

`up -d` — создать и запустить всё из файла в фоне, `ps` — статус сервисов, `down` — остановить и удалить контейнеры и сеть (данные в томах остаются; `down -v` удаляет и тома — осторожно).

### 4.13. Сколько места занял Docker

```bash
docker system df
```

```text
TYPE            TOTAL     ACTIVE    SIZE
Images          5         1         1.2GB
Containers      3         1         12MB
Local Volumes   2         1         45MB
```

Если «Images 40GB» — это нормальная причина «на сервере кончилось место», и это уже L1-задача.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

- **UBU01** (10.10.10.30, Ubuntu Server 24.04 LTS) — установлен, доступен по SSH, есть sudo. Пользователь — тот, которого ты создавал при установке Ubuntu (дальше в примерах логин `student`; если у тебя другой — подставляй свой).
- **WIN11-CL01** — рабочая станция ivanov, в домене, нужна только для проверки из браузера.
- **DC01** — без изменений, но проверь, что с WIN11-CL01 пингуется 10.10.10.30 (DNS и сеть у нас уже отработаны в предыдущих модулях).
- **FS01** — не участвует.

Важно: Docker на **Windows** (Docker Desktop) для этой лабы не нужен и не рекомендуется — из-за лицензии (платная подписка для компаний крупнее порога, бесплатна для личного использования и малого бизнеса `[ПРОВЕРИТЬ актуальные условия]`) и из-за того, что в реальных компаниях РФ контейнеры крутятся на Linux. Если очень надо посмотреть GUI — Docker Desktop → вкладка Containers, путь по меню: `Docker Desktop → Containers`.

### Снапшот

В VMware Workstation на **UBU01**: правый клик по ВМ → `Snapshot` → `Take Snapshot...` → имя `before-l1-082`. (Меню: `VM → Snapshot → Take Snapshot`.)

WIN11-CL01 не меняем — снапшот ей не нужен, но если хочешь строгого порядка, сделай и ей `before-l1-082`.

### Шаги

1. **Подключись к UBU01 по SSH** с WIN11-CL01 или с хоста:
   ```bash
   ssh student@10.10.10.30
   ```
   Ожидаемо: приглашение `student@UBU01:~$`. Проверь, что ты именно там: `hostname -I` → `10.10.10.30`.

2. **Поставь Docker** по варианту 4.1 (официальный репозиторий, а если сеть не пускает — пакет `docker.io` из Ubuntu).
   Ожидаемо: `sudo systemctl status docker` → `active (running)`.

3. **Добавь себя в группу docker и перелогинься:**
   ```bash
   sudo usermod -aG docker student
   exit
   ssh student@10.10.10.30
   docker ps
   ```
   Ожидаемо: `CONTAINER ID  IMAGE ...` без ошибки прав. Без перелогина группа не подхватится — это классическая «почему permission denied на /var/run/docker.sock».
   *Безопасность: группа `docker` = фактически root на машине. В боевой среде её дают очень ограниченному кругу.*

4. **Проверь движок тестовым контейнером:**
   ```bash
   docker run --rm hello-world
   ```
   Ожидаемо: текст `Hello from Docker!` и `This message shows that your installation appears to be working correctly.`

5. **Скачай nginx и посмотри слои:**
   ```bash
   docker pull nginx:stable-alpine
   docker images
   docker history nginx:stable-alpine | head -n 10
   ```
   Ожидаемо: в `docker history` несколько строк — это и есть слои образа.

6. **Запусти первый контейнер:**
   ```bash
   docker run -d --name web-test -p 8080:80 nginx:stable-alpine
   docker ps
   curl -I http://localhost:8080
   ```
   Ожидаемо: `HTTP/1.1 200 OK` и заголовок `Server: nginx/...`.

7. **Проверь с рабочей станции.** На WIN11-CL01 открой браузер → `http://10.10.10.30:8080`.
   Ожидаемо: страница `Welcome to nginx!`. Если не открывается — на UBU01 проверь `sudo ufw status`; если файрвол включён, `sudo ufw allow 8080/tcp`. (На учебном стенде ufw обычно неактивен.)

8. **Зайди внутрь и посмотри логи:**
   ```bash
   docker exec -it web-test sh
   ls /usr/share/nginx/html
   exit
   docker logs web-test
   ```
   Ожидаемо: `index.html  50x.html` и в логах строка вида `GET / HTTP/1.1" 200`.

9. **Останови и удали ручной контейнер** — дальше всё через Compose:
   ```bash
   docker stop web-test && docker rm web-test
   ```

10. **Создай каталог проекта и свою страницу:**
    ```bash
    mkdir -p ~/vektor-site/site
    cat > ~/vektor-site/site/index.html <<'EOF'
    <!doctype html>
    <html lang="ru"><head><meta charset="utf-8"><title>Вектор</title></head>
    <body><h1>Внутренний портал отдела</h1><p>Стенд «Вектор», сервис запущен в Docker.</p></body></html>
    EOF
    ```
    Ожидаемо: файл ~200 байт, `cat ~/vektor-site/site/index.html` показывает текст.

11. **Напиши `compose.yaml`:**
    ```yaml
    services:
      web:
        image: nginx:stable-alpine
        ports:
          - "8080:80"
        volumes:
          - ./site:/usr/share/nginx/html:ro
        restart: unless-stopped
      whoami:
        image: traefik/whoami:latest
        ports:
          - "8081:80"
        restart: unless-stopped
    ```
    Пояснения: `volumes` монтирует локальную папку `./site` внутрь контейнера, `:ro` — только чтение (контейнер не испортит файлы); `restart: unless-stopped` — политика перезапуска, контейнер поднимется после ребута хоста. Ключ `version:` в Compose v2 больше не нужен — он устарел.

12. **Подними и проверь:**
    ```bash
    cd ~/vektor-site
    docker compose up -d
    docker compose ps
    curl -s http://localhost:8080 | head -n 3
    curl -s http://localhost:8081 | head -n 5
    ```
    Ожидаемо: два контейнера в статусе `running`/`Up`, первая команда вернёт твой HTML, вторая — текст вида `Hostname: <id>` и `IP: 172.x.x.x`. Имена контейнеров будут `vektor-site-web-1` и `vektor-site-whoami-1` (проект = имя каталога).

13. **Проверь внутренний DNS между сервисами:**
    ```bash
    docker compose exec web sh -c "wget -qO- http://whoami"
    ```
    Ожидаемо: тот же текст whoami. Это значит, что контейнеры нашли друг друга **по имени сервиса** в общей сети проекта, без всяких IP.

14. **Проверь с WIN11-CL01:** `http://10.10.10.30:8080` — твоя страница «Внутренний портал отдела», `http://10.10.10.30:8081` — текст whoami. Запиши в `stand-log.md`, что появилось на стенде.

## 6. Ошибки новичков и безопасность

1. **Ошибка:** работать с Docker только через `sudo`, потому что лень настроить группу.
   **К чему приводит:** все файлы в примонтированных папках создаются от root, потом обычный пользователь их не может прочитать; кроме того, `sudo docker` — это фактически `sudo` без пароля для любого скрипта.
   **Как правильно:** добавить себя в группу `docker` (`usermod -aG docker`) и перелогиниться. В боевой среде — rootless-режим или Podman.

2. **Ошибка:** `docker run -p 8080:80` и `-p 80:8080` воспринимать как одно и то же.
   **К чему приводит:** сервис «не открывается», хотя контейнер жив; полчаса диагностики впустую.
   **Как правильно:** запомнить намертво: **слева хост, справа контейнер**. Проверка — `docker ps`, колонка `PORTS`: `0.0.0.0:8080->80/tcp`.

3. **Ошибка:** использовать тег `latest`.
   **К чему приводит:** сегодня сервис работает, завтра после `docker compose pull` — падает, потому что образ обновился до несовместимой версии. Воспроизвести «как было» невозможно.
   **Как правильно:** фиксировать версию: `nginx:stable-alpine`, `postgres:16-alpine`.

4. **Ошибка:** хранить данные внутри контейнера (файлы, базу).
   **К чему приводит:** `docker compose down` или пересоздание контейнера — данные исчезли навсегда.
   **Как правильно:** volumes или bind-mount (`./site:/usr/share/nginx/html:ro`). Данные живут вне контейнера, контейнер — расходник.

5. **Ошибка:** смотреть только `docker ps`.
   **К чему приводит:** «контейнеров нет» → вывод «Docker не работает», хотя контейнер есть, просто упал.
   **Как правильно:** сначала `docker ps -a`, потом `docker logs`.

6. **Ошибка:** публиковать порты на `0.0.0.0`, когда сервис нужен только локально.
   **К чему приводит:** админка без пароля или база данных торчат в офисную сеть; это уже инцидент ИБ.
   **Как правильно:** `-p 127.0.0.1:8080:80` — слушать только localhost, наружу отдавать через обратный прокси.

7. **Ошибка:** складывать пароли и токены прямо в `compose.yaml`, а файл коммитить в Git (урок 77).
   **К чему приводит:** секреты навсегда остаются в истории репозитория, даже если потом удалить строку.
   **Как правильно:** `.env`-файл вне Git, `env_file`, секреты Docker / vault; в `stand-log.md` пароли не писать.

8. **Ошибка:** «почистить место» командой `docker system prune -a --volumes` без раздумий.
   **К чему приводит:** удаляются все неиспользуемые образы **и тома с данными** — вместе с базой.
   **Как правильно:** сначала `docker system df` и `docker ps -a`, потом точечно `docker rmi`/`docker rm`; `prune` — осознанно и с бэкапом.

**Безопасность.** На учебном стенде мы открыли 8080 и 8081 на всю сеть 10.10.10.0/24 и добавили пользователя в группу `docker` — это допустимо только потому, что стенд изолирован в VMware. В боевой среде: (1) порт Docker-демона 2375 открывать нельзя **никогда** — это неаутентифицированный root на хосте, для удалённого управления только 2376 с TLS-сертификатами; (2) группа `docker` приравнивается к root — выдаётся по заявке и по принципу минимальных привилегий; (3) контейнеры запускаются от непривилегированного пользователя с `--read-only` там, где возможно; (4) у сервиса, доступного в сети, должен быть владелец, регламент обновлений и мониторинг (урок 86); (5) скачивать образы только из доверенных реестров и по фиксированным тегам — непроверенный образ может содержать чужой код. И да: `docker` не отменяет бэкапы. Никогда.

## 7. Вопросы на собеседовании

**Вопрос 1. Чем контейнер отличается от виртуальной машины?**

**Ответ.** ВМ запускает полноценную гостевую ОС со своим ядром через гипервизор — это гигабайты и десятки секунд загрузки. Контейнер — это изолированный процесс на хосте, который использует **ядро хоста**, а изоляцию получает через namespaces (свои процессы, сеть, файловая система) и cgroups (лимиты CPU и памяти). Отсюда: мегабайты, запуск за секунды, десятки контейнеров на одной ВМ. Обратная сторона — слабее изоляция: пробил ядро — пробил всех.

**Что хочет услышать интервьюер:** что ты понимаешь «контейнер — это не маленькая ВМ», знаешь слова namespaces/cgroups и знаешь обратную сторону медали.
**Красный флаг:** «Контейнер — это лёгкая виртуалка»; не знать, что ядро общее; рассказывать про Docker как про систему виртуализации.

**Вопрос 2. Что такое образ Docker и почему образы так быстро скачиваются?**

**Ответ.** Образ — это набор read-only слоёв файловой системы плюс метаданные (точка входа, порты, переменные окружения). Каждый слой — результат шага сборки, и слои переиспользуются: если `ubuntu:24.04` уже лежит локально, другой образ на его основе докачает только свои верхние слои. Сверху при запуске контейнер получает тонкий записываемый слой (overlay2). Поэтому `pull` часто занимает секунды, а контейнер из того же образа стартует мгновенно.

**Что хочет услышать интервьюер:** понимание слоёв, кэша и того, что записываемый слой принадлежит конкретному контейнеру.
**Красный флаг:** «Образ — это контейнер, который ещё не запустили», без понимания слоёв; уверенность, что внутри образа есть своя ОС целиком.

**Вопрос 3. Что делает команда `docker run -d --name web -p 8080:80 nginx:stable-alpine`?**

**Ответ.** Скачивает образ `nginx` с тегом `stable-alpine`, если его нет локально; создаёт контейнер с именем `web`; запускает его в фоне (`-d`) и пробрасывает TCP-порт 8080 хоста на порт 80 внутри контейнера. Слева всегда хост, справа контейнер. Проверить, что получилось: `docker ps`, колонка PORTS покажет `0.0.0.0:8080->80/tcp`; `curl -I http://localhost:8080` вернёт `200 OK`.

**Что хочет услышать интервьюер:** чёткое понимание порядка портов, `-d`, тега и того, как проверить результат.
**Красный флаг:** путать `-p` и `-P`, не знать порядок «хост:контейнер», не уметь назвать способ проверки.

**Вопрос 4. Пользователь пишет «сервис не открывается». Твои действия?**

**Ответ.** Сначала локализую: клиент или сервер. С рабочей станции — `ping` до сервера, потом `curl`/браузер на нужный порт. Если сеть жива, иду на сервер: `sudo ss -tlnp | grep <порт>` — слушается ли порт вообще. Дальше `docker ps -a` — есть ли контейнер и в каком он статусе. Если `Exited` — `docker logs --tail 100 <имя>` и смотрю код выхода: 137 — убит по памяти (OOM), 1 — ошибка приложения, «port is already allocated» — конфликт портов. Дальше `docker inspect` (переменные, политика рестарта) и `docker compose config` за опечатками в конфиге. Поднимаю: `docker compose up -d`. Проверяю `200 OK` и отписываю пользователю с просьбой подтвердить. В тикет — причину и действие, не «перезапустил, стало работать».

**Что хочет услышать интервьюер:** последовательность «сеть → порт → контейнер → логи → конфиг», а не «сразу перезапустил».
**Красный флаг:** «Перезапущу контейнер и посмотрю»; не заглядывать в логи; не проверять результат у пользователя.

**Вопрос 5. Зачем нужен docker-compose, если есть `docker run`?**

**Ответ.** `docker run` — императивно: одну команду на один контейнер. Как только сервисов два-три (веб + база + кэш), руками нужно помнить порты, тома, порядок запуска и общую сеть. Compose описывает всё в одном `compose.yaml`: сервисы, порты, тома, переменные, зависимости, — и поднимает одной командой `docker compose up -d`. Файл лежит в Git, значит конфигурация версионируется и воспроизводится на любом стенде. Compose сам создаёт сеть, где сервисы обращаются друг к другу по именам — `http://whoami` вместо IP. Плюс `docker compose ps/logs/down` дают единый интерфейс управления всей группой.

**Что хочет услышать интервьюер:** декларативность, воспроизводимость, версионирование в Git, DNS по именам сервисов.
**Красный флаг:** «Compose — это для разработки, в проде не нужен» (Compose спокойно живёт на небольших серверах); не знать, что `version:` в современном Compose устарел.
