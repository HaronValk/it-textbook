## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Контейнер** — это изолированный процесс на хосте, которому ядро Linux через механизмы namespaces (изоляция: PID, сеть, файловая система, пользователи) и cgroups (ограничение CPU/памяти) даёт иллюзию отдельной маленькой системы. В отличие от виртуалки, у контейнера нет своего ядра — он использует ядро хоста. Поэтому контейнеры Linux запускаются только на Linux-хосте (на Windows — через WSL2 или Hyper-V-изоляцию, но это отдельная история).

**Образ (image)** — это «слепок» файловой системы и метаданных (какие команды запускать, какие порты открывать), собранный слоями. Образы хранятся в **реестре** (registry): Docker Hub, Harbor, GitLab Container Registry. Контейнер — это запущенный экземпляр образа; из одного образа можно запустить много контейнеров.

**Docker Engine** — демон `dockerd`, который слушает локальный сокет `/var/run/docker.sock` и управляет контейнерами. Клиент `docker` отправляет ему команды. На UBU01 демон работает как systemd-служба `docker`.

**Сеть контейнера.** По умолчанию Docker создаёт bridge-сеть `docker0` (обычно 172.17.0.0/16). Контейнер получает внутренний IP, а наружу выходит через NAT. Чтобы к сервису в контейнере можно было обратиться снаружи, используется **проброс порта** `-p host_port:container_port`. Снаружи виден только проброшенный порт; внутренний IP контейнера снаружи недоступен.

**Тома (volumes).** Данные внутри контейнера живут, пока жив контейнер. Чтобы данные сохранялись или чтобы отдать контейнеру файлы с хоста, используют тома (`-v`) — либо именованные (`myvol:/data`), либо bind-mount (`/opt/site:/usr/share/nginx/html`).

**docker-compose** — утилита, которая читает YAML-файл с описанием нескольких сервисов и запускает их одной командой. В современных версиях это плагин `docker compose` (через пробел), старая утилита `docker-compose` (через дефис) ещё встречается. На стенде ставим плагин.

Схема:

```text
   Хост UBU01 (10.10.10.30, ядро Linux)
   ┌──────────────────────────────────────────────┐
   │  dockerd (служба docker)                     │
   │   ├── bridge docker0  172.17.0.1/16          │
   │   │                                          │
   │   │   ┌── контейнер web (nginx) ──┐          │
   │   │   │  IP 172.17.0.2:80        │          │
   │   │   └──────────┬───────────────┘          │
   │   │              │ проброс -p 8080:80        │
   │   │   ┌── контейнер app ──────────┐          │
   │   │   │  IP 172.17.0.3:5000       │          │
   │   │   └───────────────────────────┘          │
   │   └──────────────────────────────────────────│
   │   порт 8080 на 10.10.10.30 слушает dockerd   │
   └──────────────────────────────────────────────┘
              ▲
              │ HTTP 10.10.10.30:8080
              │
   WIN10-CL02 (10.10.10.52) — браузер Петровой
```

Порты, которые встретятся: 80 (HTTP внутри контейнера), 8080 (наружу на хосте), 5000 (внутренний порт второго сервиса), 2375/2376 (API Docker — на стенде не открываем).

## 3. Аналогия из жизни

Образ — это как коробка с готовым конструктором LEGO по инструкции: внутри детали и схема сборки. Контейнер — это собранная из этой коробки модель, стоящая на столе. Из одной коробки можно собрать несколько одинаковых моделей (несколько контейнеров из одного образа). Если модель сломали — её выбрасывают и собирают заново из той же коробки: образ не портится. `docker-compose` — это лист, на котором написано: «собери три модели, поставь их рядом и соедини деталью», чтобы не собирать каждую вручную. Аналогия перестаёт работать в одном месте: у LEGO-модели нет своего «ядра», а у контейнера его тоже нет — он делит ядро с хостом, и это важно для безопасности.

## 4. Практика и команды

Все команды — на UBU01 под `adm.student`, где нужно — через `sudo`. Перед установкой Docker проверьте, что вы на UBU01:

```bash
hostname
ip -br a
```

Ожидаемо: `ubu01` и адрес `10.10.10.30/24` на интерфейсе `ens33` (имя интерфейса может отличаться, `[ПРОВЕРИТЬ]` в вашей ВМ).

**1. Установка Docker Engine из официального репозитория.** В РФ зеркала Docker Hub и `download.docker.com` могут быть недоступны или нестабильны `[ПРОВЕРИТЬ]`. Официальная инструкция — на docs.docker.com; если репозиторий не открывается, легальная альтернатива — пакет `docker.io` из репозитория Ubuntu (`sudo apt install docker.io docker-compose-v2`), он старее, но рабочий.

```bash
sudo apt update
sudo apt install -y ca-certificates curl gnupg
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

Что смотреть: последняя команда должна завершиться без ошибок, пакеты `docker-ce` и `docker-compose-plugin` установлены.

**2. Проверка, что демон работает.**

```bash
sudo systemctl status docker --no-pager
sudo docker version
```

Ожидаемо: `active (running)`, в выводе `docker version` есть блоки `Client` и `Server`. Если `Server` не отвечает — демон не запущен.

**3. Добавить `adm.student` в группу `docker` (чтобы не писать `sudo` каждый раз).**

```bash
sudo usermod -aG docker adm.student
newgrp docker
docker run --rm hello-world
```

`--rm` — удалить контейнер после выхода. Ожидаемо: сообщение «Hello from Docker!». **Безопасность:** членство в группе `docker` фактически равно root на хосте (можно смонтировать `/` внутрь контейнера). В боевой среде так дают только доверенным администраторам.

**4. Список образов и контейнеров.**

```bash
docker images
docker ps
docker ps -a
```

`docker images` — локальные образы. `docker ps` — только запущенные контейнеры. `docker ps -a` — все, включая остановленные. Смотреть колонки `IMAGE`, `STATUS`, `PORTS`.

**5. Запуск nginx с пробросом порта и bind-mount.**

```bash
mkdir -p /opt/vektor-web
echo "<h1>Vektor test page</h1>" | sudo tee /opt/vektor-web/index.html
docker run -d --name vektor-web -p 8080:80 -v /opt/vektor-web:/usr/share/nginx/html:ro nginx:stable
```

Ключи: `-d` — в фоне, `--name` — имя контейнера, `-p 8080:80` — порт хоста 8080 → порт контейнера 80, `-v host:container:ro` — папка хоста только для чтения. Ожидаемо: длинный ID контейнера. Проверка с UBU01: `curl http://127.0.0.1:8080` вернёт HTML с «Vektor test page».

**6. Логи и выполнение команды внутри контейнера.**

```bash
docker logs vektor-web
docker exec -it vektor-web sh -c 'ls /usr/share/nginx/html'
```

`docker logs` — stdout/stderr контейнера (у nginx — access/error log). `docker exec -it` — запустить команду внутри работающего контейнера в интерактивном режиме. Ожидаемо: в логах строки о старте nginx, во второй команде — `index.html`.

**7. Остановка, запуск, удаление.**

```bash
docker stop vektor-web
docker start vektor-web
docker rm -f vektor-web
```

`stop` — корректно гасит процесс, `start` — снова поднимает, `rm -f` — удаляет (с `-f` даже если работает). Образ `nginx:stable` при этом остаётся в `docker images`.

**8. `docker-compose` — два сервиса одной командой.** Создаём папку и файл:

```bash
mkdir -p /opt/vektor-compose && cd /opt/vektor-compose
cat > compose.yaml <<'EOF'
services:
  web:
    image: nginx:stable
    ports:
      - "8081:80"
    volumes:
      - ./site:/usr/share/nginx/html:ro
  app:
    image: alpine:3.20
    command: sh -c "while true; do echo app alive; sleep 30; done"
EOF
mkdir -p site
echo "<h1>Vektor compose page</h1>" > site/index.html
docker compose up -d
docker compose ps
docker compose logs --tail=20
```

`up -d` — поднять всё в фоне, `ps` — статус сервисов, `logs` — логи всех сервисов. Ожидаемо: два сервиса `running`, порт 8081 проброшен. Остановить и убрать: `docker compose down`.

**9. Проверка с клиента.** С WIN10-CL02 (или WIN11-CL01) в браузере открыть `http://10.10.10.30:8080` (или `:8081` для compose-варианта). Ожидаемо: страница «Vektor test page» / «Vektor compose page». Если не открывается — смотреть `docker ps` (порт проброшен?), `sudo ss -tlnp | grep 8080` на UBU01, и правило брандмауэра (на Ubuntu по умолчанию ufw выключен, но `[ПРОВЕРИТЬ]`).

## 6. Ошибки новичков и безопасность

1. **Путать образ и контейнер.** Ошибка: `docker rm nginx:stable` — не удалит образ, выдаст ошибку. Правильно: `docker rmi nginx:stable` для образа, `docker rm <имя>` для контейнера.
2. **Забыть `-d`.** Без `-d` контейнер займёт терминал, и вы решите, что «зависло». Правильно: `docker run -d ...` или `Ctrl+C` и перезапуск с `-d`.
3. **Проброс порта в обратном порядке.** `-p 80:8080` вместо `-p 8080:80` — сервис не откроется. Формат всегда `хост:контейнер`.
4. **Монтировать `/` или `/etc` в контейнер.** Ошибка: `-v /:/host` — контейнер получает доступ ко всей системе. Правильно: монтировать только нужную папку, по возможности `:ro`.
5. **Давать всем группу `docker`.** Членство в `docker` = root. В боевой среде — только администраторам, лучше через отдельный хост или rootless-режим `[ПРОВЕРИТЬ]`.
6. **Открывать Docker API наружу.** Порт 2375 без TLS — это удалённое управление хостом без пароля. Никогда не открывать в сеть.
7. **Хранить данные только в контейнере.** После `docker rm` данные исчезнут. Правильно: тома или bind-mount на хосте.
8. **Ставить образы «с интернета» без проверки.** Официальные образы (`nginx`, `alpine`) — с Docker Hub; сторонние могут содержать вредоносный код. В компании — только из доверенного реестра (Harbor, внутренний registry).

**Безопасность.** На стенде мы разрешаем `adm.student` работать без `sudo` через группу `docker` — это удобно, но в боевой среде так нельзя без согласования. Пароли и токены реестров не храните в `compose.yaml` в открытом виде — используйте переменные окружения или секреты. Не публикуйте порты наружу без необходимости: каждый открытый порт — потенциальная точка входа.

## 7. Вопросы на собеседовании (3–5 вопросов с ответами)

**Вопрос 1. Чем контейнер отличается от виртуальной машины?**
Как спросят: «Объясните разницу между Docker-контейнером и ВМ».
Ответ: «ВМ запускает полноценную гостевую ОС со своим ядром через гипервизор, поэтому стартует минуты и занимает гигабайты. Контейнер — это изолированный процесс на хосте, использующий ядро хоста через namespaces и cgroups; стартует секунды и занимает мегабайты. На стенде я поднимал nginx в контейнере на UBU01 за пару секунд, а виртуалка с той же ролью заняла бы больше ресурсов».
Что хочет услышать: понимание, что контейнер — не «маленькая ВМ», а процесс с изоляцией.
Красный флаг: «контейнер — это лёгкая виртуалка» без упоминания общего ядра.

**Вопрос 2. Что такое образ и реестр?**
Как спросят: «Откуда Docker берёт образы?»
Ответ: «Образ — это слоистый слепок файловой системы и метаданных. Хранится в реестре: Docker Hub, Harbor, GitLab Registry. При `docker run` демон сначала ищет образ локально, если нет — тянет из реестра. На стенде я скачивал `nginx:stable` с Docker Hub; в компании обычно используют внутренний реестр».
Что хочет услышать: понимание цепочки registry → local image → container.
Красный флаг: путаница «образ = контейнер».

**Вопрос 3. Как пробросить порт и почему сервис не открывается снаружи?**
Как спросят: «Контейнер работает, а с другого компьютера сайт не открывается — что проверить?»
Ответ: «Проверить `docker ps` — есть ли проброс `-p host:container`. Проверить `ss -tlnp` на хосте — слушается ли порт. Проверить брандмауэр хоста. Проверить, что сервис внутри контейнера слушает на `0.0.0.0`, а не только на `127.0.0.1`. На стенде я ловил именно остановленный контейнер — `docker ps -a` показал `Exited`».
Что хочет услышать: системную диагностику, а не «перезапустить Docker».
Красный флаг: сразу `systemctl restart docker` без диагностики.

**Вопрос 4. Зачем нужен docker-compose?**
Как спросят: «Когда использовать compose, а когда — просто `docker run`?»
Ответ: «Compose удобен, когда сервисов несколько и они связаны: сеть, зависимости, общие тома. Описание в YAML — это фактически документация стенда. Для одного контейнера хватит `docker run`. На стенде я поднимал nginx и alpine одной командой `docker compose up -d`».
Что хочет услышать: понимание декларативного подхода и повторяемости.
Красный флаг: «compose нужен всегда» или «compose — это Kubernetes».

**Вопрос 5. Почему членство в группе `docker` опасно?**
Как спросят: «Можно ли дать пользователю права на Docker?»
Ответ: «Член группы `docker` может смонтировать `/` хоста в контейнер и получить root. Поэтому в боевой среде — только администраторам, лучше rootless или отдельный хост. На стенде я добавил `adm.student` в группу для удобства, но это учебное упрощение».
Что хочет услышать: понимание модели угроз.
Красный флаг: «да, любому пользователю, это же удобно».
