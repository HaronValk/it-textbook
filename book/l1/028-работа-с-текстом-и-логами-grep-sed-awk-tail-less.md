## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Всё есть текст.** Linux-утилиты работают с потоком байт: файл — последовательность строк, разделённых символом перевода строки `\n` (код 10). Никакой «структуры лога» для ОС не существует: для неё это просто текст. Поэтому `grep` находит ошибки и в логе nginx, и в `/etc/passwd`, и в выводе другой команды.

**Три потока и конвейер.** У каждой программы есть стандартный ввод (stdin, fd 0), стандартный вывод (stdout, fd 1) и вывод ошибок (stderr, fd 2). Символ `|` соединяет stdout одной команды со stdin следующей. Отсюда главная идея: `grep`, `sed`, `awk`, `sort`, `uniq`, `wc` — это **фильтры**, которые можно собирать в цепочки.

**Как лог появляется на диске.** Современный Ubuntu Server пишет логи в journald (тема 26), а файлы в `/var/log/` появляются, если работает rsyslog. Схема:

```text
 приложение (vektor-sync)
        │ пишет в stdout/stderr
        ▼
 systemd-journald ──► /run/log/journal (RAM, теряется при перезагрузке)
        │             └► /var/log/journal (диск, если включено постоянное хранение)
        │ (если установлен rsyslog — читает журнал и раскладывает по файлам)
        ▼
 /var/log/syslog      — общесистемные сообщения
 /var/log/auth.log    — входы, sudo, sshd
 /var/log/apt/        — история установок и обновлений (см. урок 27)
        │
        ▼
 logrotate (обычно раз в сутки через systemd-таймер):
   app.log → app.log.1 → app.log.2.gz → ... → удаление по сроку
        │
        ▼
 ты: less / tail -f / grep / awk → вывод → цитата в тикет
```

**Порты и сеть.** Локальные логи портов не используют — journald общается через unix-сокет `/run/systemd/journal/socket`. Порты появляются, когда логи шлют по сети: классический syslog — **UDP 514** (RFC 3164), современный syslog — **514/tcp**, сборщики вроде Loki/ELK — свои порты. На L1 достаточно знать: «логи на другом сервере» = syslog по 514 или агент.

**Модель OSI** здесь ни при чём: это прикладной уровень и работа с файлами. Зато важны **слои ОС**: ядро (`dmesg`) → systemd/journald → приложение (свой файл в `/var/log/` или `/opt/...`).

**Регулярные выражения.** `grep` по умолчанию использует BRE (базовые регулярные выражения POSIX): `.` — любой символ, `*` — ноль и более предыдущего, `^` — начало строки, `$` — конец, `[...]` — набор, `\` — экранирование. С ключом `-E` включается ERE, где работают `+`, `?`, `|`, `()` без экранирования. Это минимум, который нужен на L1; глубже — на треке L2.

## 3. Аналогия из жизни

Представь склад с журналом приёмки: одна длинная амбарная книга, куда кладовщик построчно пишет дату, время, тип записи и что произошло.

- `less` — это сесть с книгой за стол и листать: можно открыть на любой странице, найти слово поиском, вернуться назад. Книга при этом не «переписывается».
- `tail` — подойти к книге и посмотреть последние записи: что происходило только что. С `-f` ты стоишь рядом с кладовщиком и читаешь через плечо по мере того, как он пишет.
- `grep` — попросить помощника: «покажи только строки, где написано „брак“». Помощник читает всю книгу и выписывает подходящие строки на отдельный листок.
- `awk` — попросить того же помощника: «выпиши не всю строку, а только дату и название товара» — он понимает, что строка состоит из полей, разделённых пробелами.
- `sed` — корректор с ручкой: «в этой строке замени „Иванов“ на „Петров“». С `-i` он правит саму книгу, и без бэкапа ты уже не узнаешь, что там было.

Аналогия перестаёт работать в одном месте: корректор из `sed` — это потоковый редактор, он обрабатывает книгу слева направо и не «понимает» смысла строк, поэтому может случайно заменить слово не там, где ты хотел.

## 4. Практика и команды

Ниже — минимальный рабочий набор. Примеры даны на файле `~/lab28/app.log` (создадим его в лабораторной); формат строки: `дата время УРОВЕНЬ сервис сообщение`.

### 4.1. `less` — смотреть большой файл

```bash
less /var/log/syslog
less -N -S app.log
```

`-N` — номера строк, `-S` — не переносить длинные строки (удобно для логов). Внутри: `Space` — страница вперёд, `b` — назад, `/ERROR` — поиск вперёд, `n` — следующее совпадение, `G` — в конец, `g` — в начало, `F` — режим «следить за файлом» (как `tail -f`), выход из слежения — `Ctrl+C`, выход из `less` — `q`. Файл целиком в память не читается, поэтому даже гигабайтный лог открывается моментально.

### 4.2. `tail` — последние строки и «прямой эфир»

```bash
tail -n 50 app.log
tail -f /var/log/auth.log
tail -F /var/log/vektor/app.log
```

`-n 50` — последние 50 строк (по умолчанию 10), `-n +100` — начиная со 100-й строки до конца, `-c 200` — последние 200 байт. `-f` — «follow»: держит файл открытым и печатает новые строки. `-F` = `--follow=name --retry` — то же, но по имени файла: переживает ротацию (файл переименовали — `-F` откроет новый). В работе для логов почти всегда нужен `-F`.

Вывод: строки лога, последняя внизу. Смотреть: время последней записи (сервис вообще жив?), уровень (ERROR/WARN), текст.

### 4.3. `head` и `wc` — быстрый осмотр

```bash
head -n 20 app.log
wc -l app.log
```

`head` — первые строки (обычно заголовок и первые события). `wc -l` — число строк; полезно, чтобы понять масштаб: 200 строк читаем глазами, 2 млн — только фильтрами.

### 4.4. `grep` — поиск по строкам

```bash
grep -in "error" app.log
grep -c "ERROR" app.log
grep -v "INFO" app.log
grep -rn "10.10.10.20" /etc/ssh/
```

Ключи: `-i` — игнорировать регистр, `-n` — показывать номер строки, `-c` — только количество совпавших строк, `-v` — инвертировать (показать всё, кроме), `-r` — рекурсивно по каталогу, `-w` — только целое слово, `-l` — только имена файлов, `-o` — печатать только совпавшую часть, `-F` — искать как обычную строку без регулярки (быстрее и безопаснее для IP и путей с точками).

Коды возврата: `0` — совпадения есть, `1` — нет, `2` — ошибка. Из-за этого проверки в скриптах пишут как `if grep -q "ERROR" app.log; then ...`.

### 4.5. `grep -E` — несколько шаблонов и контекст

```bash
grep -E "ERROR|CRITICAL" app.log
grep -n -A 3 -B 1 "ERROR" app.log
```

`-A 3` — три строки после совпадения, `-B 1` — одна до, `-C 2` — по две с каждой стороны. Контекст критичен: в строке ошибки часто только «failed to read», а причина — в предыдущей строке.

### 4.6. `sed` — замена и выбор строк

```bash
sed -n '5,10p' app.log
sed 's/10\.10\.10\.20/FS01/g' app.log
sed -i.bak 's/WARN /WARNING /g' app.log
```

`-n` отключает автопечать, `p` печатает указанный диапазон. `s/что/на что/` — замена первого вхождения в строке, `g` — всех. `-i.bak` — правка «на месте» с сохранением копии `app.log.bak` (правило: `sed -i` без бэкапа на боевом конфиге — только с согласованием и бэкапом). Точки в IP экранируют `\.`, иначе `.` = «любой символ».

### 4.7. `awk` — работа с полями

```bash
awk '{print $3}' app.log
awk '$3 == "ERROR" {print $1, $2, $5}' app.log
awk -F: '$3 >= 1000 && $3 < 65534 {print $1, $3}' /etc/passwd
```

`$1`, `$2` — поля строки, `$0` — вся строка, `$NF` — последнее поле, `NF` — число полей, `NR` — номер строки. По умолчанию разделитель — любые пробелы/табы (подряд идущие считаются одним), `-F:` задаёт другой разделитель. В фигурных скобках — действие, перед ними — условие. `awk` умеет считать:

```bash
awk '$3 == "ERROR" {c++} END {print "ошибок:", c+0}' app.log
```

### 4.8. Конвейер: top ошибок

```bash
awk '{print $3}' app.log | sort | uniq -c | sort -nr | head
```

`sort` сортирует, `uniq -c` считает **соседние** одинаковые строки (поэтому `uniq` без `sort` почти всегда бесполезен), `sort -nr` — по числу, по убыванию. Типичный вывод: `17 ERROR`, `4 WARN`, `112 INFO`.

### 4.9. Реальные логи и ротация

```bash
ls -lh /var/log/
zgrep -i "fail" /var/log/auth.log.2.gz
du -sh /var/log/* | sort -hr | head
```

Сжатые архивные логи (`*.gz`) читают через `zgrep` и `zcat | grep`, смотрят — через `zless`. `du -sh` показывает размер каталогов (быстрый ответ на «куда ушло место»). Настройки ротации: `/etc/logrotate.conf` и `/etc/logrotate.d/*`; проверка конфига без изменений — `logrotate -d /etc/logrotate.conf` (dry run, только показывает, что сделал бы).

### 4.10. Журнал systemd (повторение урока 26)

```bash
journalctl -p err -b | tail -20
journalctl -u ssh --since today | grep -i "fail"
```

`-p err` — важность «error и выше», `-b` — с момента загрузки, `--since today` — с начала суток. Смысл тот же: сначала сузить, потом искать.

### 4.11. Эквиваленты в Windows (пригодится на WIN11-CL01)

| Linux | PowerShell |
|-------|-----------|
| `tail -n 50 app.log` | `Get-Content .\app.log -Tail 50` |
| `tail -f app.log` | `Get-Content .\app.log -Wait` |
| `grep -i error app.log` | `Select-String -Path .\app.log -Pattern 'error'` |
| `grep -c` | `(Select-String -Path .\app.log -Pattern 'ERROR').Count` |
| `sed 's/a/b/g'` | `(Get-Content .\app.log) -replace 'a','b'` |
| `wc -l` | `(Get-Content .\app.log).Count` |

### 4.12. Полезный минимум рядом

```bash
grep -a "ERROR" app.log      # файл «бинарный» — искать как по тексту
grep -I -l "vektor" /etc/*.conf   # только текстовые файлы, только имена
cut -d' ' -f1 app.log | sort -u
```

`-a` — обходить проверку на бинарность (частая ситуация, когда в лог попал нулевой байт и `grep` пишет «Binary file matches»). `cut -d' '` не «схлопывает» повторные пробелы — в отличие от `awk`, поэтому для колонок с выравниванием пробелами лучше `awk`.

## 6. Ошибки новичков и безопасность

1. **`cat` гигабайтного лога в терминал** → вал текста, зависший терминал, иногда отвалившийся SSH-сеанс. Правильно: `less` (читает постранично) или `tail`/`grep`.
2. **`grep` без якоря и без `-F` по IP или пути** → точка в шаблоне означает «любой символ», находятся ложные совпадения. Правильно: `grep -F "10.10.10.20"` или экранировать `10\.10\.10\.20`.
3. **`sed -i` без бэкапа на конфиге** → опечатка в шаблоне портит `/etc/ssh/sshd_config` или `/etc/fstab`, сервис не стартует. Правильно: `sed -i.bak`, а лучше сначала `sed 's/.../.../' файл | diff - файл` и посмотреть, что изменится.
4. **`uniq -c` без `sort`** → считает только подряд идущие одинаковые строки, результат случайный. Правильно: всегда `sort | uniq -c` (или `sort | uniq -c | sort -nr`).
5. **`tail -f` вместо `-F`** → после ротации логи смотрятся в «мёртвый» переименованный файл, новых записей нет, и кажется, что сервис молчит. Правильно: `tail -F`.
6. **`grep -r` по `/`** → минуты нагрузки на диск и горы нерелевантного вывода. Правильно: сузить путь (`/etc`, `/var/log`), добавить `--include="*.conf"`.
7. **Считать, что «лог пустой = ничего не было»** → файл ротирован или приложение пишет в journald, а не в `/var/log`. Правильно: `ls -l` рядом (есть ли `.1`, `.gz`), `zgrep`, `journalctl -u <сервис>`.
8. **Чистить логи `rm` вместо `truncate`** → приложение продолжает писать в удалённый файл, место не освобождается. Правильно: `: > файл` или `truncate -s 0 файл` (после согласования), плюс настройка logrotate.

### Безопасность

- **Логи содержат персональные данные и секреты.** В `auth.log` — имена пользователей и IP; в логах приложений встречаются токены и пути к документам. Не вставляй лог целиком в общий чат или тикет: цитируй только нужные строки, маскируй логины и адреса.
- **Права на логи.** `/var/log/auth.log` читается только root — и это правильно. `sudo chmod 666 /var/log/*` «чтобы удобнее было» открывает атакующему возможность подделать журнал.
- **`sed -i` на боевом сервере** — это изменение конфигурации. В нормальной среде: бэкап, изменение через систему управления конфигурациями, окно работ, запись в заявке.
- **Учебные вольности.** На стенде мы свободно правим файлы в `~/lab28` и заводим правило logrotate. В боевой среде правило ротации для чужого сервиса согласуется с владельцем: неверный `copytruncate`/`compress` может «съесть» часть логов, которая нужна разбору инцидента.

## 7. Вопросы на собеседовании (3–5 вопросов с ответами)

**1. «Как посмотреть лог в реальном времени и в чём разница между `tail -f` и `tail -F`?»**
`tail -f файл` держит открытым файловый дескриптор и печатает всё, что дописывается. `-F` (`--follow=name --retry`) следит за **именем**: если файл переименовали при ротации, команда дождётся появления нового файла с тем же именем и переключится на него. Для боевых логов, которые ротируются, нужен `-F`.
*Что хочет услышать интервьюер:* что ты знаешь про ротацию и не будешь час смотреть в «мёртвый» файл.
*Красный флаг:* «разницы нет».

**2. «В логе 2 ГБ, нужно найти все ошибки за вчера. Что сделаешь?»**
Не открывать целиком: `grep -n "2026-02-10.*ERROR" app.log` по нужной дате, при необходимости контекст `-A 3 -B 1`, результат в `less` или `tail`. Если файлов несколько — `grep -rn --include="*.log"`. Если уже ротирован и сжат — `zgrep`. Дополнительно проверю `journalctl --since yesterday -p err`. И заведу задачу на ротацию/сжатие, чтобы 2 ГБ не появлялись снова.
*Что хочет услышать интервьюер:* фильтрация вместо перебора, знание `zgrep` и journald.
*Красный флаг:* «открою в блокноте и поищу».

**3. «Как посчитать, сколько раз встречается каждая ошибка в логе?»**
Вытащить поле с текстом ошибки через `awk`, нормализовать и посчитать: `awk '$3=="ERROR" {print $5}' app.log | sort | uniq -c | sort -nr`. Важно: `uniq` работает только по соседним строкам, поэтому `sort` перед ним обязателен.
*Что хочет услышать интервьюер:* понимание конвейера и подводного камня с `uniq`.
*Красный флаг:* `uniq -c` без `sort` и непонимание, почему цифры неверные.

**4. «Чем `grep` отличается от `sed` и `awk` — что когда брать?»**
`grep` только **ищет и показывает** строки по шаблону. `sed` — потоковый редактор: умеет заменять, удалять, печатать диапазоны, в том числе править файл на месте (`-i.bak`). `awk` — язык обработки полей: выбор по номеру поля, условия, подсчёты, вывод только нужных колонок. Практика: поиск — `grep`, точечная правка конфига — `sed`, разбор колонок и арифметика — `awk`.
*Что хочет услышать интервьюер:* что ты выбираешь инструмент по задаче, а не «чем привык».
*Красный флаг:* «это всё одно и то же».

**5. «Файл лога пустой, а пользователь говорит, что ошибки были. Куда смотреть?»**
Проверить каталог: рядом могут быть `app.log.1`, `app.log.2.gz` — файл ротирован. Смотреть `ls -l` с датами, читать архивы через `zless`/`zgrep`/`zcat | tail`. Если файла нет вообще — проверить journald (`journalctl -u <сервис>`, `journalctl --since`) и настройки rsyslog/ротации. Отдельно убедиться, что приложение вообще пишет в этот файл (путь в его конфиге).
*Что хочет услышать интервьюер:* что ты не веришь «файл пустой» на слово и знаешь про ротацию и journald.
*Красный флаг:* «значит, ошибок не было».
