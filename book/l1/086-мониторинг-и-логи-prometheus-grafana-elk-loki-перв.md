# Мониторинг и логи: Prometheus + Grafana, ELK/Loki — первое знакомство

## 1. Введение (зачем это нужно в реальной работе)

```
Заявка #4128
Пользователь: Петрова Мария (HR), ВМ WIN10-CL02
Текст: «После обеда компьютер жутко тормозит, браузер еле открывает отчёт.
        Утром всё было нормально. Помогите, пожалуйста.»
Срочность: Средняя
```

Дальше начинается то, чем L1 занимается каждый день. Ты подходишь к её машине в 15:40, машина работает нормально. Открываешь диспетчер задач — процессор 5%. Пользователь говорит «ну вот, при вас всегда работает». Ты закрываешь заявку «проблема не воспроизвелась», через день она возвращается, а через неделю выясняется, что на FS01 в это время шёл бэкап и упирался в диск. Никто этого не видел, потому что никто не смотрел.

Мониторинг — это привычка не спорить с пользователем, а смотреть цифры. Метрики отвечают на вопрос «насколько плохо и когда», логи — «что именно произошло». Это две разные половины одной задачи, и на L1 ты будешь пользоваться обеими: в реальной работе ты чаще всего открываешь готовый дашборд в Zabbix или Grafana и читаешь журнал Windows.

После этой главы ты сможешь: поднять Prometheus, экспортёр и Grafana в Docker на UBU01, написать пять базовых запросов PromQL, отличать метрики от логов, объяснить на собеседовании архитектуру ELK и Loki и, главное, превращать «тормозит» в измеримый факт.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Все четыре слова из названия — это HTTP-сервисы (прикладной уровень, L7 модели OSI), которые общаются JSON'ом поверх TCP. Никакой магии.

**Метрики.** Число + момент времени + набор меток. Вот так выглядит одна временная серия (time series) в Prometheus:

```text
node_cpu_seconds_total{cpu="0", job="ubu01", mode="idle"} 123456.78
```

`node_cpu_seconds_total` — имя метрики, `{...}` — метки (labels), `123456.78` — значение, а время Prometheus хранит рядом. Каждые 15 секунд он добавляет новую точку. 15 дней таких точек — это и есть его база (TSDB). По умолчанию retention ровно 15 дней, меняется флагом `--storage.tsdb.retention.time`.

**Prometheus работает по pull-модели.** Он сам, по расписанию, идёт на `http://цель:9100/metrics` и забирает текст. Цель, которая умеет отдавать такой текст, называется **экспортёр** (exporter) — это маленький сервис-переводчик: он читает `/proc`, счётчики ОС или WMI и публикует их в формате Prometheus. Для Linux это `node_exporter` (порт 9100), для Windows — `windows_exporter` (порт 9182).

**Grafana — это только экран.** Она ничего не хранит и ничего не опрашивает по расписанию: ты открываешь дашборд, она идёт в Prometheus через HTTP API и рисует то, что он вернул. Поэтому «в Grafana пропали данные» почти всегда значит «сломался Prometheus или экспортёр», а не «сломалась Grafana».

**Логи.** Тут модель другая: приложение пишет строки, их кто-то собирает и складывает в хранилище с поиском.

```text
                UBU01 (10.10.10.30), docker compose
   ┌────────────────────────────────────────────────────────────┐
   │                                                            │
   │  [node_exporter :9100]  ◄── GET /metrics ──┐               │
   │                                            │               │
   │  [prometheus :9090] ── TSDB (15 дней) ─────┘               │
   │        │                                                   │
   │        │ HTTP /api/v1/query                                │
   │        ▼                                                   │
   │  [grafana :3000]  ──────► браузер на хосте (10.10.10.x)    │
   │        ▲                                                   │
   │        │ HTTP /loki/api/v1/query_range                     │
   │  [loki :3100] ◄── push логов ── [promtail] ◄── /var/log/*  │
   └────────────────────────────────────────────────────────────┘

   Windows (WIN11-CL01): Event Viewer / Get-WinEvent — руками,
   windows_exporter появится позже, на L2 (MON01).
```

**ELK** — это Elasticsearch (хранилище и поиск, порт 9200), Logstash (тяжёлый конвейер обработки, порт 5044 для Beats) и Kibana (веб-интерфейс, порт 5601). Плюс лёгкие агенты Beats/Filebeat, которые ставятся на машины и отправляют логи. ELK индексирует **каждое слово** в каждой строке: поиск по содержимому мощный, но Elasticsearch — это JVM, и на стенде ему нужно несколько гигабайт памяти.

**Loki** — «Elasticsearch для бедных» от той же Grafana Labs. Он индексирует только метки (job, host, container), а сам текст лога просто сжимает и хранит чанками. Ищет медленнее и без сложных запросов, зато ест в разы меньше. Язык запросов — LogQL: `{job="varlogs"} |= "error"`. Именно Loki мы и поднимем на стенде, потому что 4–8 ГБ на UBU01 хватит, а на ELK — нет. Про Promtail сразу оговорка: Grafana продвигает ему на замену Grafana Alloy, статус поддержки Promtail стоит уточнить в документации `[ПРОВЕРИТЬ]`.

Порты, которые надо помнить: 9090 Prometheus, 9100 node_exporter, 9182 windows_exporter, 3000 Grafana, 3100 Loki, 9080 Promtail, 9200 Elasticsearch, 5601 Kibana.

## 3. Аналогия из жизни

Представь автомобиль. На приборной панели — стрелки: скорость, температура, топливо. Это **метрики**: быстро, компактно, видно общую картину, но по стрелке «температура в норме» нельзя узнать, почему вчера был перегрев.

В бардачке лежит путевой журнал, куда записано каждое событие: «14:32, выехал из Москвы», «16:05, заехал на заправку», «18:11, загорелся чек». Это **логи**: много текста, зато видно причины и подробности.

Prometheus — это самописец, который каждые 15 секунд сам обходит все датчики и записывает их показания в толстую тетрадь (на 15 дней). Grafana — это панель приборов, на которую ты можешь вывести любые стрелки из этой тетради. Loki — тот самый путевой журнал, только с оглавлением по номеру машины и дате, а не по каждой букве.

Аналогия перестаёт работать в одном месте: в машине датчики сами «кричат» на панель (push), а Prometheus наоборот — сам приходит и опрашивает каждого (pull). И ещё: журнал и стрелки не заменяют друг друга — они отвечают на разные вопросы.

## 4. Практика и команды

**1. Проверить, что экспортёр вообще отдаёт метрики.** Первое действие при «на графиках пусто».

```bash
curl -s http://10.10.10.30:9100/metrics | head -n 20
```

`-s` — тихий режим, без прогресс-бара. Смотрим, что вернулся текст с комментариями `# HELP` / `# TYPE` и строками вида `node_cpu_seconds_total{...}`. Если в ответ пусто или `connection refused` — проблема на стороне экспортёра, а не Prometheus.

**2. Проверить живость самого Prometheus.**

```bash
curl -s http://10.10.10.30:9090/-/healthy
curl -s http://10.10.10.30:9090/-/ready
```

Ожидаемый ответ: `Prometheus Server is Healthy.` и `Prometheus Server is Ready.` `healthy` — процесс жив, `ready` — готов отвечать (догрузил WAL после рестарта). Второй полезнее: контейнер может быть `Up`, но не `ready`.

**3. Посмотреть, кого Prometheus опрашивает и с каким результатом.**

```bash
curl -s http://10.10.10.30:9090/api/v1/targets | python3 -m json.tool | head -n 40
```

В JSON ищи поля `health` (`up` / `down`), `lastError` и `lastScrape`. Это ровно то же, что показывает веб-интерфейс: **Status → Targets**. Если `lastError` = `context deadline exceeded` — цель не отвечает по сети или висит; `connection refused` — сервис не слушает порт.

**4. Базовый запрос доступности.**

```text
up
```

Пишется в веб-интерфейсе Prometheus на вкладке **Graph**, в поле Expression. `up` — синтетическая метрика: 1, если последний скрейп удался, 0 если нет. Запрос `up == 0` сразу отфильтрует только упавшие цели. Это первое, что смотрит любой дежурный.

**5. Загрузка процессора в процентах.**

```text
100 - (avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
```

`node_cpu_seconds_total` — счётчик (counter), он только растёт. `rate(...[5m])` превращает его в «сколько прибавлялось за секунду» на окне 5 минут. `mode="idle"` — доля простоя от 0 до 1. `avg` усредняет по всем ядрам, `* 100` — в проценты, `100 -` — потому что нам нужна загрузка, а не простой.

**6. Свободное место на корне.**

```text
node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"} * 100
```

Даёт процент свободного места. На L1 это самая частая причина «всё сломалось»: `df -h` руками ты тоже обязан уметь, но график показывает, **когда** место начало кончаться.

**7. Смотреть логи контейнеров, когда сервис не поднялся.**

```bash
docker compose ps
docker compose logs --tail=50 prometheus
docker compose logs -f node-exporter
```

`ps` покажет статус (`Up`, `Exited (1)`, `Restarting`). `logs --tail=50` — последние 50 строк, `-f` — режим «хвоста» в реальном времени. В 90% случаев причина старта в логах написана прямым текстом: `permission denied`, `yaml: line 7: did not find expected key`.

**8. Проверить Loki и поискать в логах.**

```bash
curl -s http://10.10.10.30:3100/ready
```

Ответ `ready` — Loki готов. Запрос в Grafana → Explore → источник Loki:

```text
{job="varlogs"} |= "error"
```

`{job="varlogs"}` — выбор потока по метке (без метки Loki ничего не найдёт, это его главное отличие от ELK), `|=` — «содержит подстроку». Дальше можно `count_over_time({job="varlogs"} |= "error" [5m])` — сколько ошибок за 5 минут.

**9. Читать журнал Windows на WIN11-CL01.** Открыть: `Win+R` → `eventvwr.msc` → **Windows Logs → System**.

```powershell
Get-WinEvent -LogName System -MaxEvents 20
Get-WinEvent -FilterHashtable @{LogName='System'; Level=2; StartTime=(Get-Date).AddHours(-24)}
```

Первая команда — 20 последних событий. Вторая — только ошибки (`Level=2`; `1` — Critical, `2` — Error, `3` — Warning) за сутки. Это ручной мониторинг: пока на машине нет экспортёра, другого способа узнать, что там происходило, нет.

**10. Классика Linux, которая всегда под рукой.**

```bash
df -h
free -m
journalctl -p err -n 20 --no-pager
```

`df -h` — диски в человекочитаемом виде, `free -m` — память в мегабайтах, `journalctl -p err` — только ошибки из системного журнала. Это тот минимум, который ты выполняешь на сервере, если мониторинга под рукой нет.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

- UBU01 (10.10.10.30, Ubuntu Server 24.04 LTS) включён, доступен по SSH с хоста, установлены Docker и плагин `docker compose` (урок 82). Проверка: `docker version` и `docker compose version` отвечают без ошибок.
- WIN11-CL01 включён и в домене (для шага с журналом Windows).
- **MON01 мы не создаём.** Эта ВМ появляется только на треке L2, отдельного сервера мониторинга на L1 в стенде нет. Поэтому всё поднимаем контейнерами на UBU01 — это нормальная практика и для реальных небольших контор.

### Снапшот

В VMware Workstation: выделить UBU01 → **VM → Snapshot → Take Snapshot** → имя `before-l1-086`. На WIN11-CL01 изменения не вносятся (только чтение журнала), но если хочешь зафиксировать состояние — сделай такой же снапшот и там.

### Шаги

1. **UBU01, по SSH.** Создать каталог и зайти в него:
   ```bash
   mkdir -p ~/monitoring && cd ~/monitoring && pwd
   ```
   Ожидаемо: `/home/<твой_пользователь>/monitoring`.

2. **Создать конфиг Prometheus** `nano prometheus.yml`:
   ```yaml
   global:
     scrape_interval: 15s
     evaluation_interval: 15s

   scrape_configs:
     - job_name: prometheus
       static_configs:
         - targets: ["localhost:9090"]
     - job_name: ubu01
       static_configs:
         - targets: ["node-exporter:9100"]
   ```
   `scrape_interval` — как часто опрашивать цели. Обрати внимание: адрес цели — имя контейнера, а не IP, потому что внутри compose-сети работает встроенный DNS.

3. **Создать `docker-compose.yml`** с тремя сервисами (prometheus, node-exporter, grafana), томами `prom_data` и `grafana_data`. Ключевые моменты: `./prometheus.yml:/etc/prometheus/prometheus.yml:ro`, для node-exporter — `pid: host`, `command: ["--path.rootfs=/host"]` и монтирование `/:/host:ro,rslave` (иначе контейнер покажет файловую систему самого контейнера, а не хоста). Полный файл — в справке по compose из урока 82; теги образов `prom/prometheus`, `prom/node-exporter`, `grafana/grafana` возьми актуальные на hub.docker.com (для стенда допустимо `latest`, для работы — только фиксированная версия `[ПРОВЕРИТЬ актуальные теги]`).

4. **Поднять и проверить:**
   ```bash
   docker compose up -d
   docker compose ps
   ```
   Ожидаемо: три контейнера в состоянии `Up`, у prometheus и grafana — `(healthy)` при наличии healthcheck.

5. **Проверить экспортёр и Prometheus** командами 1 и 2 из раздела 4. Ожидаемо: текст метрик и `Prometheus Server is Ready.`

6. **Открыть в браузере на хосте** `http://10.10.10.30:9090` → **Status → Targets**. Ожидаемо: две цели (`prometheus`, `ubu01`) в состоянии **UP**, `Last Scrape` — секунды назад. Если `ubu01` в DOWN — смотреть `lastError` (команда 3).

7. **Выполнить PromQL** на вкладке **Graph**: `up`, затем запрос CPU из раздела 4. Ожидаемо: таблица со значением `1` для обеих целей и число загрузки CPU в процентах (на простаивающей ВМ — единицы).

8. **Настроить Grafana:** `http://10.10.10.30:3000`, вход `admin` / `admin`, мастер попросит сменить пароль — поставь учебный `Lab#2026-vektor` (на стенде он один на всё, в реальной работе так нельзя). Далее **Connections → Data sources → Add data source → Prometheus**, URL `http://prometheus:9090` (имя контейнера!), **Save & test**. Ожидаемо: зелёное сообщение об успешном подключении.

9. **Построить панель:** **Explore** → источник Prometheus → запрос `up` → **Run query** → **Add to dashboard**. Ожидаемо: график с двумя линиями на значении 1. При желании импортируй готовый дашборд: **Dashboards → New → Import**, ID `1860` (Node Exporter Full) `[ПРОВЕРИТЬ актуальность ID]`, источник — свой Prometheus.

10. **Проверить журнал Windows (WIN11-CL01):** выполнить `Get-WinEvent -FilterHashtable @{LogName='System'; Level=2; StartTime=(Get-Date).AddHours(-24)}`. Ожидаемо: список ошибок за сутки или пусто — это и есть «сырые» логи, которые Prometheus не видит.

11. **Часть Б (по желанию, если на UBU01 ≥ 4 ГБ RAM): Loki + Promtail.** Создать `promtail.yml` (клиент `http://loki:3100/loki/api/v1/push`, `__path__: /var/log/*log`, метка `job: varlogs`) и файл `docker-compose.loki.yml` с сервисами `loki` (порт 3100, `command: -config.file=/etc/loki/local-config.yaml`) и `promtail`. Поднять поверх основного проекта:
    ```bash
    docker compose -f docker-compose.yml -f docker-compose.loki.yml up -d
    ```
    Ожидаемо: контейнеры `loki` и `promtail` в статусе `Up`, `curl -s http://10.10.10.30:3100/ready` отвечает `ready`. В Grafana добавить источник Loki с URL `http://loki:3100` и в Explore выполнить `{job="varlogs"}`. Если Loki не стартует с дефолтным конфигом — взять актуальный пример конфигурации из документации Grafana `[ПРОВЕРИТЬ]`.

### Проверка

- [ ] `docker compose ps` на UBU01: prometheus, node-exporter, grafana — `Up`.
- [ ] `curl http://10.10.10.30:9100/metrics` отдаёт текст метрик.
- [ ] `/-/healthy` и `/-/ready` отвечают положительно.
- [ ] В Prometheus **Status → Targets** обе цели UP.
- [ ] Запрос `up` возвращает `1`, запрос `100 - (...)` — число от 0 до 100.
- [ ] Grafana: источник Prometheus подключён, тест зелёный.
- [ ] В дашборде виден хотя бы один график.
- [ ] (Часть Б) `{job="varlogs"}` в Grafana возвращает строки лога.
- [ ] Запись в `stand-log.md` добавлена.

### Сломай и почини

```
Пользователь / ВМ: Петрова Мария (HR) / WIN10-CL02
Что написал: «После обеда компьютер жутко тормозит, браузер еле открывает
             отчёт. Вы же говорили, что теперь всё мониторите — посмотрите,
             может, сервер упал?»
Срочность: Средняя
```

**Как воспроизвести поломку.** На UBU01 останови экспортёр — это имитирует «мониторинг ослеп», самая частая авария в практике дежурного:

```bash
docker compose stop node-exporter
```

**Диагностика по шагам.**

1. Открыть Prometheus → **Status → Targets**. Видим: цель `ubu01` — **DOWN**, `lastError` вроде `connection refused`, `Last Scrape` — «5 minutes ago». Значит, метрик по серверу нет, и утверждать «сервер в норме» мы не имеем права.
2. Проверить порт руками: `curl -s http://10.10.10.30:9100/metrics`. Пусто/отказ — подтверждает, что дело не в Prometheus.
3. На UBU01: `docker compose ps` — `node-exporter` в статусе `Exited (0)`.
4. `docker compose logs --tail=30 node-exporter` — ошибок нет, значит контейнер просто остановили (или упал хост). Проверить `uptime` и `free -m` самого UBU01: не было ли перезагрузки/нехватки памяти.
5. Поднять обратно: `docker compose start node-exporter`, через 15–30 секунд снова открыть Targets — цель UP, графики пошли.

**Решение.** Вернуть экспортёр в работу, убедиться, что цель UP и данные пишутся. Дополнительно: по графику UBU01 проверить, что сам сервер не перегружен (CPU, память, место). Важно: **по WIN10-CL02 метрик нет вообще** — на нём нет экспортёра, поэтому «сервер упал» мы подтвердить или опровергнуть не можем. Заодно снять факты с машины пользователя: диспетчер задач, `Get-WinEvent` по System/Application за сутки, `Get-CimInstance Win32_LogicalDisk` на свободное место.

**Ответ пользователю:** «Мария, добрый день. Проверил серверную часть — по нашим данным сервер в норме, загрузка низкая. Уточните, пожалуйста: тормозит только отчёт или весь браузер? В какое время началось? Подойду к вам после 16:00 и посмотрю журнал на вашем компьютере, он пока не подключён к мониторингу, поэтому точных данных по нему у меня нет».

**Закрытие заявки.** Статус «Решено» только после того, как причина найдена и подтверждена, иначе — «Ожидает ответа пользователя» или перевод на другую линию с описанием того, что уже проверено (это экономит время коллегам).

### Что изменилось на стенде

## 6. Ошибки новичков и безопасность

**1. Думать, что Prometheus «увидит» Windows сам.** → Ставишь Prometheus, добавляешь WIN11-CL01 в targets и получаешь вечный DOWN, потому что на Windows нет ничего, что отдаёт `/metrics`. → Сначала ставится `windows_exporter` (порт 9182), в targets указывается `IP:9182`, и только потом всё остальное.

**2. Путать метрики и логи.** → Ищешь в Grafana текст ошибки приложения и не находишь, делаешь вывод «мониторинг не работает». → Grafana с источником Prometheus отвечает на вопрос «насколько плохо», текст ошибки — только в Loki/ELK или в журнале ОС.

**3. Считать `up == 1` доказательством, что сервис работает.** → `up` означает лишь «скрейп прошёл», а приложение при этом может отдавать пользователю 500-е. → Для доступности приложения нужны его собственные метрики (или хотя бы проверка HTTP-кода через blackbox_exporter `[ПРОВЕРИТЬ]`), а не только `up`.

**4. Ставить тег `latest` и обновляться «когда захочется».** → Однажды `docker compose pull` приносит новую мажорную версию, конфиг не подходит, мониторинг лежит в самый неподходящий момент. → В работе — фиксированные версии, обновление по плану, со снапшотом и чтением changelog.

**5. Забыть про `pid: host` и `--path.rootfs` у node-exporter.** → Контейнер показывает метрики самого контейнера: 0% CPU, 2 ГБ диска. → Проверять, что в targets видно реальный хост, а графики похожи на правду.

**6. Тянуть ELK на слабую ВМ «чтобы по-настоящему».** → Elasticsearch съедает память, всё уходит в swap, стенд встаёт колом, и ты чинишь не мониторинг, а последствия. → На L1 для логов — Loki; ELK — когда есть отдельный сервер с RAM.

**7. Игнорировать время и часовой пояс.** → На графике «проблема была в 03:00», а на самом деле в 06:00 по Москве, потому что контейнеры живут в UTC. → Проверять таймзону контейнеров и настройку Grafana, для России обычно `Europe/Moscow`.

### Безопасность

- **Grafana/прометеевский стек — это внутренний инструмент, а не сайт.** В лаборатории мы открываем порт 3000 на всю сеть VMnet8, и это допустимо только потому, что сеть изолирована на твоём ПК. В боевой среде такие порты закрывают файрволом, доступ дают через VPN или SSH-туннель, а публикация `0.0.0.0:3000` в интернет — это утечка данных о всей инфраструктуре и почти гарантированный взлом.
- **Пароль `admin/admin` меняется сразу.** На стенте мы поставили единый учебный пароль — и это явное упрощение: в реальности он был бы уникальным и хранился бы в менеджере паролей.
- **Метрики и логи содержат чувствительное.** Имена пользователей, IP, пути, иногда куски SQL и токены в строках логов. Не выкладывай скриншоты дашбордов в публичные чаты и не коммить реальные конфиги в открытые репозитории.
- **Не отключай файрвол «чтобы порты открылись».** Правильно — добавить разрешающее правило для конкретной подсети, а не гасить ufw целиком.

## 7. Вопросы на собеседовании

**Вопрос 1. Чем метрики отличаются от логов и когда вы используете что?**

Ответ: метрика — это число с метками и временной точкой, дешёвая по объёму, хорошо агрегируется, отвечает на вопрос «насколько плохо и когда». Лог — текстовая запись о конкретном событии, дорогая по объёму, отвечает на вопрос «что именно произошло и почему». Практика: сначала смотрим метрики (быстрый обзор, алерты, «когда началось»), затем идём в логи за причиной в этом узком интервале времени. Хороший пример: график CPU показал скачок в 14:00 — открываем логи приложения за 13:55–14:05 и ищем ошибку.

*Что хочет услышать интервьюер:* что кандидат не считает это взаимоисключающим и понимает порядок действий «метрики → логи».
*Красный флаг:* «логи важнее, метрики не нужны» или путаница в терминах.

**Вопрос 2. Почему Prometheus сам опрашивает цели, а не ждёт, что они пришлют данные? В чём плюс и минус такого решения?**

Ответ: pull-модель. Плюсы: Prometheus сам знает список целей и видит факт неудачного опроса как метрику `up` (то есть падение цели автоматически становится событием), проще отладка — можно руками сходить `curl` на `/metrics`, проще контроль нагрузки. Минусы: цель должна быть доступна по сети в момент опроса (плохо для машин за NAT), неудобно для короткоживущих задач вроде CronJob — их прикрывают pushgateway `[ПРОВЕРИТЬ]`.

*Что хочет услышать интервьюер:* понимание, что `up` — это следствие модели, а не «магия».
*Красный флаг:* «push лучше, потому что так быстрее» без объяснений.

**Вопрос 3. ELK или Loki — что выберете и почему?**

Ответ: зависит от задачи и ресурсов. ELK индексирует полный текст: мощный поиск, сложные запросы, готовые пайплайны Logstash, но ресурсоёмко (JVM, память, диски) и сложнее в сопровождении. Loki индексирует только метки, текст хранит сжатыми чанками: дёшево, быстро разворачивается, родная интеграция с Grafana, но искать можно только по меткам + фильтру подстроки, без полнотекстового индекса. Для небольшой компании и типового «найти ошибку в логах контейнера за последний час» — Loki. Для полноценного аудита и разбора с юридическими требованиями по хранению и поиску — ELK.

*Что хочет услышать интервьюер:* что выбор обоснован требованиями, а не модой.
*Красный флаг:* «Loki лучше, потому что бесплатный» — обе бесплатны, вопрос в другом.

**Вопрос 4. Пользователь пишет «всё тормозит». Ваши первые действия?**

Ответ: сначала уточняю, что именно тормозит: одна программа или всё, одна операция или постоянно, с какого времени, воспроизводится ли сейчас. Затем смотрю объективные данные: дашборд мониторинга по серверу за этот период (CPU, память, диск, `up`), журнал событий Windows на машине пользователя (`Get-WinEvent` по System и Application с фильтром по уровню Error/Warning), свободное место на диске. Если мониторинга по этой машине нет — честно фиксирую это как пробел и собираю факты руками. Результат — не «перезагрузите», а конкретная причина или её отсутствие с описанием, что проверено.

*Что хочет услышать интервьюер:* структуру вместо случайных кликов и готовность признать «данных нет».
*Красный флаг:* «перезагружу компьютер и посмотрю» как единственный план.
