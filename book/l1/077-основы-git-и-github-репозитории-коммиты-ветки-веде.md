## 1. Введение (зачем это нужно в реальной работе)

Заявка в учебной системе «Вектора»:

> **Пользователь:** Мария Петрова (HR), ВМ WIN10-CL02
> **Что написала:** «Иван из бухгалтерии прислал мне по почте инструкцию по 1С, а в ней половина шагов не совпадает с тем, что у меня на экране. И ещё он говорит, что у него версия новее. Как понять, какая инструкция правильная и кто что менял?»
> **Срочность:** средняя

Знакомая ситуация: документ ходит по почте в трёх копиях, у каждого своя «финальная-финальная-2.docx», и никто не помнит, чья версия актуальна. В нормальной ИТ-команде такие документы (инструкции для пользователей, схемы сети, чек-листы, runbook'и для дежурного) хранят в системе контроля версий — чаще всего в Git, а общий доступ и обсуждение организуют через GitHub или его аналоги.

Git — это распределённая система контроля версий (DVCS, distributed version control system). Проще: программа, которая запоминает каждое изменение файлов, кто и когда его сделал и зачем, и позволяет откатиться, сравнить, объединить правки разных людей. GitHub — облачный хостинг для Git-репозиториев (есть и российские аналоги: GitFlic, GitVerse — упомянем в теории).

Для L1 это нужно в трёх местах. Первое — документация: база знаний, инструкции, шаблоны заявок. Второе — передача смены и эскалация: тимлид хочет видеть, что именно ты поменял в инструкции, а не «вроде поправил». Третье — это мост к DevOps: в DevOps-треке вся инфраструктура (Ansible-плейбуки, Dockerfile, манифесты Kubernetes) живёт в Git, и без базового понимания коммитов и веток туда не пройти. После этой главы ты сможешь: создать репозиторий, сделать осмысленные коммиты, работать с ветками, отправить репозиторий на GitHub и вести документацию так, чтобы её можно было читать и проверять.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Git хранит не «версии файлов», а **снимки состояния** всего проекта. Каждый коммит — это указатель на дерево файлов плюс метаданные (автор, дата, сообщение) плюс ссылка на родительский коммит. Отсюда цепочка истории.

Три «этажа» Git:

```text
Рабочая папка (working tree)   — файлы, которые ты редактируешь
        │  git add
        ▼
Индекс (staging area)          — что попадёт в следующий коммит
        │  git commit
        ▼
Локальный репозиторий (.git)   — история коммитов на твоём ПК
        │  git push / git pull
        ▼
Удалённый репозиторий (remote) — GitHub, GitFlic, GitVerse, GitLab
```

Ключевые понятия:

- **Репозиторий (repo)** — папка проекта вместе со скрытой подпапкой `.git`, где лежит вся история.
- **Коммит (commit)** — зафиксированный снимок с сообщением. У каждого свой хеш (SHA-1, 40 hex-символов; в новых версиях Git возможен SHA-256 `[ПРОВЕРИТЬ]`).
- **Ветка (branch)** — подвижный указатель на коммит. `main` (или `master` в старых репозиториях) — основная.
- **Удалённый репозиторий (remote)** — обычно называется `origin`.
- **Клонирование (clone)** — скопировать удалённый репозиторий целиком с историей.
- **Pull request (PR)** — запрос на слияние твоей ветки в основную; на GitHub это ещё и площадка для ревью.

Протоколы доступа к удалённому репозиторию:

| Способ | Порт | Когда используется |
|--------|------|--------------------|
| HTTPS | 443 | проще всего, работает через прокси и NAT |
| SSH | 22 | удобно для автоматизации, ключи вместо пароля |
| git:// | 9418 | устаревший, анонимный, в корпоративной среде не используется |

На домашнем стенде «Вектора» ты будешь работать через HTTPS: у хоста есть интернет через NAT-устройство VMware (VMnet8, шлюз 10.10.10.2), а SSH-ключи к GitHub — это уже тема DevOps-трека. Git на Windows ставится как обычная программа (Git for Windows, включает Git Bash и `git.exe` для PowerShell/CMD).

Где Git живёт в общей картине: это инструмент «ниже» систем заявок и «выше» файловой системы. Он не заменяет GLPI (систему заявок) и не заменяет файловый сервер FS01 — он фиксирует **изменения** документов и кода. В DevOps-треке Git станет источником истины: из репозитория CI/CD будет забирать код и разворачивать его.

## 3. Аналогия из жизни

Представь бумажный журнал сдачи смены в диспетчерской. Каждая запись — дата, кто дежурил, что произошло, подпись. Страницы пронумерованы, старые не вырывают, а новую запись делают ниже. Если кто-то хочет проверить, что было в ночь с пятницы на субботу, он листает журнал и находит запись. Если нужно вести параллельно две линии (например, «инструкция для бухгалтерии» и «инструкция для склада»), заводят два журнала — это ветки. Когда обе линии готовы, их можно свести в один сводный журнал — это слияние (merge).

Git — тот же журнал, только электронный, с автоматической нумерацией страниц (хеши), возможностью откатиться на любую страницу и вести параллельные журналы без путаницы. Аналогия перестаёт работать в одном месте: в бумажном журнале нельзя «отменить» уже сделанную запись, а в Git можно — и это нормальная практика, а не подлог.

## 4. Практика и команды

Все команды ниже выполняются на хосте (Windows) в PowerShell или Git Bash. Git for Windows ставит и то, и другое. Скачать легально: git-scm.com (бесплатно, open source). Если сайт недоступен из РФ — есть зеркала и пакетные менеджеры (winget, chocolatey) `[ПРОВЕРИТЬ актуальность зеркал]`.

### 1. Проверить, что Git установлен и настроить себя

```powershell
git --version
git config --global user.name "Ivan Ivanov"
git config --global user.email "ivanov@corp.vektor.lab"
git config --global init.defaultBranch main
```

`--global` — настройки для всех репозиториев пользователя Windows. Имя и почта попадут в каждый коммит. `init.defaultBranch main` — чтобы новые репозитории сразу создавались с веткой `main`, а не `master` (в старых версиях Git по умолчанию был `master`).

Пример вывода `git --version`:

```text
git version 2.45.1.windows.1
```

Версия у тебя может быть другой — это нормально.

### 2. Создать репозиторий в существующей папке

```powershell
cd C:\Lab\vektor
git init
git status
```

`git init` создаёт скрытую папку `.git` в текущей директории. `git status` показывает, что в рабочей папке, что в индексе, на какой ты ветке.

Пример вывода `git status` (примерно):

```text
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        docs/
        stand-log.md

nothing added to commit but untracked files present (use "git add" to track)
```

Смотреть: на какой ветке, какие файлы untracked (не отслеживаются), какие staged (готовы к коммиту).

### 3. Добавить файлы в индекс и сделать первый коммит

```powershell
git add stand-log.md
git add docs
git commit -m "Первый коммит: журнал стенда и папка docs"
```

`git add <файл>` — положить в индекс. `git add <папка>` — добавить всё содержимое рекурсивно. `git commit -m "..."` — зафиксировать. Сообщение должно отвечать на вопрос «что и зачем», а не «изменения».

Пример вывода `git commit`:

```text
[main (root-commit) 3f2a1b9] Первый коммит: журнал стенда и папка docs
 2 files changed, 15 insertions(+)
 create mode 100644 stand-log.md
 create mode 100644 docs/README.md
```

### 4. Посмотреть историю

```powershell
git log --oneline
git log --oneline --graph --all
```

`--oneline` — по одной строке на коммит (хеш + сообщение). `--graph --all` — ASCII-граф веток, полезно, когда веток больше одной.

Пример:

```text
3f2a1b9 (HEAD -> main) Первый коммит: журнал стенда и папка docs
```

### 5. Создать ветку и переключиться

```powershell
git switch -c docs/instrukciya-1c
```

`-c` — создать и сразу переключиться. Старый эквивалент: `git checkout -b docs/instrukciya-1c`. Имя ветки `docs/instrukciya-1c` — с префиксом `docs/`, чтобы было видно, что это документация. В DevOps-треке ты увидишь префиксы `feature/`, `fix/`, `hotfix/` — та же идея.

### 6. Сравнить изменения до коммита

```powershell
git diff
git diff --staged
```

`git diff` — разница между рабочей папкой и индексом (что ещё не добавлено). `git diff --staged` — между индексом и последним коммитом (что попадёт в следующий коммит). Вывод в формате unified diff: строки с `-` удалены, с `+` добавлены.

### 7. Привязать удалённый репозиторий и отправить

```powershell
git remote add origin https://github.com/<твой-логин>/vektor-docs.git
git branch -M main
git push -u origin main
```

`git remote add origin <url>` — задать адрес удалённого репозитория под именем `origin`. `git branch -M main` — переименовать текущую ветку в `main` (если была `master`). `git push -u origin main` — отправить ветку `main` на `origin` и запомнить связь (`-u` = upstream), чтобы дальше хватало `git push`.

Пример вывода (примерно):

```text
Enumerating objects: 5, done.
Writing objects: 100% (5/5), 1.2 KiB | 1.2 MiB/s, done.
To https://github.com/<твой-логин>/vektor-docs.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

При первом `push` GitHub попросит логин и **personal access token** (PAT) вместо пароля — обычный пароль для Git-операций GitHub не принимает с 2021 года. Токен создаётся в Settings → Developer settings → Personal access tokens.

### 8. Забрать изменения с удалённого

```powershell
git pull
```

`git pull` = `git fetch` + `git merge` (или `rebase`, если настроено). Забирает новые коммиты с `origin` и сливает в текущую ветку. Если ты единственный автор — обычно проходит без конфликтов.

### 9. Слить ветку в main (локально)

```powershell
git switch main
git merge docs/instrukciya-1c
git push
```

`git merge <ветка>` — влить изменения из указанной ветки в текущую. Если в обеих ветках менялись одни и те же строки — будет конфликт, Git попросит разрешить вручную (в файле появятся маркеры `<<<<<<<`, `=======`, `>>>>>>>`).

### 10. Посмотреть, что реально изменилось в файле

```powershell
git show HEAD
git show HEAD~1:stand-log.md
```

`git show HEAD` — последний коммит целиком (метаданные + diff). `git show HEAD~1:stand-log.md` — содержимое файла `stand-log.md` в предыдущем коммите (`HEAD~1` = «на один коммит назад»). Удобно, когда нужно понять, что было в инструкции до правки.

### 11. Отменить изменения в рабочей папке (осторожно)

```powershell
git restore stand-log.md
```

`git restore <файл>` — вернуть файл к состоянию из индекса (или из последнего коммита, если в индексе ничего нет). **Все несохранённые правки в этом файле пропадут.** В рабочей среде это спасает, когда случайно сломал документ; но если ты не коммитил — потеряешь работу.

### 12. Файл `.gitignore`

```text
# .gitignore
*.tmp
*.bak
~$*
Thumbs.db
```

`.gitignore` — список шаблонов, которые Git не отслеживает. `~$*` — временные файлы Word/Excel (начинаются с `~$`). `*.bak` — резервные копии. Это защита от случайного коммита мусора.

2. Создай ветку `docs/fix-1c` и в ней поменяй первую строку `docs/instrukciya-1c.md` (например, «Инструкция по 1С (версия 2)»). Закоммить.
3. Переключись на `main` и в том же файле поменяй ту же первую строку по-другому («Инструкция по 1С (версия 3)»). Закоммить.
4. Слей: `git merge docs/fix-1c`. Git выдаст конфликт.

Ожидаемый вывод (примерно):

```text
Auto-merging docs/instrukciya-1c.md
CONFLICT (content): Merge conflict in docs/instrukciya-1c.md
Automatic merge failed; fix conflicts and then commit the result.
```

В файле появятся маркеры:

```text
<<<<<<< HEAD
Инструкция по 1С (версия 3)
=======
Инструкция по 1С (версия 2)
>>>>>>> docs/fix-1c
```

**Диагностика по шагам:**

1. `git status` — покажет `both modified: docs/instrukciya-1c.md`. Это значит: конфликт в одном файле.
2. Открой файл, найди маркеры `<<<<<<<`, `=======`, `>>>>>>>`. Верхняя часть (до `=======`) — из текущей ветки (`HEAD`, то есть `main`), нижняя — из вливаемой (`docs/fix-1c`).
3. Реши, какой текст оставить (или объедини оба варианта в один осмысленный). Удали все три маркера.
4. `git add docs/instrukciya-1c.md` — отметить конфликт разрешённым.
5. `git commit` (без `-m` Git откроет редактор с заготовкой «Merge branch…»; можно `git commit -m "merge: разрешён конфликт в инструкции по 1С"`).
6. `git push`.

**Ответ пользователю:**

> Иван, это конфликт слияния — Git не смог автоматически решить, какая версия строки правильная, и показал обе. Я вручную выбрал актуальную версию, закоммитил и запушил. Обнови страницу репозитория — инструкция снова читается нормально. Впредь, если правишь инструкцию, делай это в отдельной ветке и присылай pull request — тогда конфликтов будет меньше.

**Закрытие заявки:** категория «Документация / база знаний», решение — «разрешён merge-конфликт в docs/instrukciya-1c.md, ветка docs/fix-1c слита в main, изменения запушены». Ссылка на коммит — в комментарии к заявке.

## 6. Ошибки новичков и безопасность

1. **Коммит «на всё» с сообщением «fix» или «update».** → Через месяц никто не поймёт, что менялось. → Пиши сообщение по схеме «что и зачем»: `docs: добавил шаг про резервное копирование в инструкцию по 1С`.
2. **`git add .` в папке с секретами.** → В репозиторий уедут пароли, токены, ключи. → Всегда проверяй `git status` перед коммитом; секреты — в `.gitignore`; если уже закоммитил — считай пароль скомпрометированным и меняй.
3. **`git push --force` в общую ветку.** → Перезапишет чужие коммиты, коллеги потеряют работу. → `--force` только в свою личную ветку и только осознанно; в `main` — никогда.
4. **Работа прямо в `main` без ветки.** → Любая ошибка сразу в основной ветке. → Заводи ветку под каждую задачу (`docs/...`, `fix/...`), сливай через PR.
5. **`git restore` без коммита.** → Несохранённые правки пропадут безвозвратно. → Сначала `git add` + `git commit`, потом экспериментируй.
6. **Клонирование репозитория в папку с другим проектом.** → Смешаются два проекта, `.git` перезапишется. → `git clone` всегда в пустую папку.
7. **Хранение PAT в открытом виде в скрипте.** → Утечка токена = доступ ко всем твоим репозиториям. → Используй Git Credential Manager (идёт с Git for Windows) или переменные окружения; токен — с минимальными правами и сроком жизни.
8. **Игнорирование `git pull` перед работой.** → Конфликты и потеря времени. → Начинай день с `git pull`.

### Безопасность

- **Никогда не коммить в публичный репозиторий** внутренние адреса, имена серверов, схемы сети, учётки, пароли, конфиги с секретами. На стенде «Вектора» это учебные данные, но привычка должна быть: в рабочей среде утечка схемы сети — инцидент ИБ.
- **Приватный репозиторий ≠ безопасный.** Доступ к нему есть у всех, кому ты дал права; проверяй список коллабораторов.
- **Пароли на стенде только учебные** (`Lab#2026-vektor`). В реальной работе пароль в Git-конфиге или в скрипте — грубое нарушение.
- **Проверяй, куда пушишь.** Опечатка в URL remote может отправить код в чужой репозиторий. `git remote -v` перед первым push.

## 7. Вопросы на собеседовании (3–5 вопросов с ответами)

**Вопрос 1. Чем Git отличается от GitHub?**

Как задают: «Git и GitHub — это одно и то же?»

Ответ: Git — это программа контроля версий, работает локально, хранит историю в папке `.git`. GitHub — облачный хостинг Git-репозиториев с дополнительными функциями: pull request, issues, CI/CD. Можно пользоваться Git без GitHub (локально или с другим хостингом — GitLab, GitFlic, GitVerse). GitHub без Git не бывает.

Что хочет услышать интервьюер: что ты понимаешь разницу между инструментом и сервисом.

Красный флаг: «GitHub — это и есть Git» или «Git — это облако».

**Вопрос 2. Что такое коммит и что в него попадает?**

Как задают: «Опиши жизненный цикл изменения файла в Git».

Ответ: Изменение файла в рабочей папке → `git add` кладёт его в индекс (staging area) → `git commit` фиксирует снимок индекса в локальном репозитории с метаданными (автор, дата, сообщение, хеш, ссылка на родителя). В коммит попадает только то, что в индексе, а не всё, что изменено в рабочей папке. Дальше `git push` отправляет коммиты на удалённый репозиторий.

Что хочет услышать интервьюер: понимание трёх этажей (working tree → index → repo) и что `add` и `commit` — разные шаги.

Красный флаг: «Коммит — это сохранение файла» (это `Ctrl+S`, а не коммит).

**Вопрос 3. Зачем нужны ветки и что такое merge-конфликт?**

Как задают: «Как вы работаете с ветками и что делаете при конфликте?»

Ответ: Ветка — подвижный указатель на коммит, позволяет вести параллельные линии работы (например, `docs/instrukciya-1c` и `main`) не мешая друг другу. Слияние — `git merge <ветка>`. Конфликт возникает, когда в обеих ветках менялись одни и те же строки одного файла; Git не может выбрать автоматически и оставляет маркеры `<<<<<<<`, `=======`, `>>>>>>>`. Разрешение: открыть файл, выбрать/объединить нужный текст, удалить маркеры, `git add`, `git commit`. На стенде я это воспроизводил и разрешал вручную.

Что хочет услышать интервьюер: что ты не боишься конфликтов и умеешь их разрешать, а не «удаляю репозиторий и клонирую заново».

Красный флаг: «При конфликте всегда делаю `git push --force`».

**Вопрос 4. Что такое pull request и зачем он в документации?**

Как задают: «Как вы предлагаете изменения в общий документ?»

Ответ: Pull request (PR) — запрос на слияние твоей ветки в основную. На GitHub это ещё и площадка для ревью: коллега видит diff, комментирует, апрувит. В документации PR полезен так же, как в коде: тимлид видит, что именно ты поменял в инструкции, и может попросить правки до того, как изменение уйдёт в `main`. Это дисциплинирует и создаёт историю «кто и зачем менял».

Что хочет услышать интервьюер: что ты понимаешь ценность ревью и не пушишь сразу в `main`.

Красный флаг: «PR — это только для программистов».

**Вопрос 5. Что нельзя коммитить в Git и почему?**

Как задают: «Какие файлы вы добавляете в `.gitignore`?»

Ответ: Пароли, токены, ключи SSH, конфиги с секретами, временные файлы (`*.tmp`, `*.bak`, `~$*` от Word/Excel), большие бинарники (образы, бэкапы), локальные настройки IDE. Причина: репозиторий может быть публичным или доступным широкому кругу; история Git хранит всё навсегда, и «удалить потом» — значит переписать историю, что болезненно. Если секрет уже попал в коммит — считай его скомпрометированным и меняй.

Что хочет услышать интервьюер: базовую гигиену безопасности.

Красный флаг: «Коммичу всё, потом разберёмся».
