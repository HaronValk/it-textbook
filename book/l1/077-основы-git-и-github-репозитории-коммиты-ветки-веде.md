# Основы Git и GitHub: репозитории, коммиты, ветки, ведение документации

## 1. Введение (зачем это нужно в реальной работе)

Понедельник, 9:20. В систему заявок падает тикет:

> **Заявка #4821.** Пользователь: Сидоров (склад). Что написал: «Здравствуйте! Мне прислали три инструкции, как заходить на `\\FS01\Obshchee` — в письме от 12-го, в чате и на флешке. Везде разные шаги, по одной не пускает, по другой пускает, но папка `Buh` не видна. Какая правильная?»

Знакомо? В компании на 50 человек документация живёт в почте, в чатах, в папке «Инструкции_НОВЫЕ_финал(3).docx» на общем диске и в голове у одного человека, который как раз в отпуске. Заявка #4821 — это не проблема доступа, это проблема версий: никто не знает, какой документ актуальный.

Инструмент, который решает ровно эту проблему, — **Git**. Это **система контроля версий** (Version Control System, VCS): программа, которая хранит полную историю изменений файлов, помнит, кто и когда что поменял, и позволяет вернуть любую версию назад. **GitHub** — это сайт, где можно хранить копию такого репозитория в интернете, чтобы работать с нескольких машин и с коллегами.

Почему это в треке L1, а не «где-то в DevOps»:
- L1 пишет и поддерживает **базу знаний** — инструкции, чек-листы, шаблоны тикетов (урок 73). Git снимает боль «какая версия правильная».
- Git — это фундамент всего, что будет дальше: плейбуки Ansible (81), Dockerfile (82), CI/CD (83), Terraform (85) — всё лежит в Git. Без Git эти темы просто не откроются.
- На собеседовании на L1 вопрос «ты сталкивался с Git?» задают почти всегда, а на DevOps — это ежедневный инструмент.
- Git — это привычка «сначала зафиксируй, потом меняй», которая спасает от «я случайно удалил инструкцию и не помню, что там было».

После этой главы ты должен уметь: создать репозиторий, закоммитить файлы, откатить изменение, сделать ветку, слить её, запушить в GitHub и клонировать репозиторий на вторую машину.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Ключевая идея Git.** Большинство «версионных» инструментов хранят *разницу* между версиями файла. Git устроен иначе: он хранит **снимки состояния** (snapshots). Каждый раз, когда ты делаешь коммит, Git запоминает, как выглядели все отслеживаемые файлы на этот момент. Если файл не менялся — повторно он не копируется, Git переиспользует уже сохранённый объект, поэтому «полные снимки» не раздувают папку до небес.

**Четыре области — главная схема Git.** Пока ты её не запомнил, Git будет казаться магией.

```text
   РАБОЧАЯ КОПИЯ            ИНДЕКС (staging)          ЛОКАЛЬНЫЙ РЕПОЗИТОРИЙ
 C:\IT\vektor-it-docs  →   «что войдёт в     →   история коммитов в папке .git
 обычные файлы,            следующий коммит»      (лежит только на этой машине)
 которые ты правишь
        │   git add              │                       │
        └────────────────────────┴───────────────────────┼──→ git push  ──→ УДАЛЁННЫЙ РЕПО
                                                         │                  github.com/<вы>/vektor-it-docs
        ←────────────────────── git pull / git clone ───┘                  (HTTPS :443 / SSH :22)
```

1. **Рабочая копия (working tree)** — папка, где ты редактируешь файлы блокнотом или VS Code.
2. **Индекс (staging area)** — промежуточная зона: «вот эти изменения я хочу включить в следующий коммит». Именно она сбивает новичков.
3. **Локальный репозиторий** — папка `.git` внутри проекта. Вся история в ней, целиком, у тебя на диске. Поэтому Git называют **распределённой** VCS: ты можешь коммитить без интернета, хоть в самолёте.
4. **Удалённый репозиторий (remote)** — копия на сервере: GitHub, GitLab, Gitea. Обычно его называют `origin`.

**Коммит (commit)** — единица истории. Внутри: снимок файлов, автор, e-mail, дата, текст сообщения, ссылка на родительский коммит и **хеш** — уникальный идентификатор (по умолчанию SHA-1, выглядит как `a3f9c1d...`). Цепочка коммитов от родителя к родителю и есть история. Изменить прошлый коммит нельзя — можно только добавить новый, который отменяет старый.

**Ветка (branch)** — это просто **указатель на коммит**. Создать ветку — почти мгновенная операция, копирования файлов не происходит. Специальный указатель `HEAD` показывает, в какой ветке ты сейчас. Главная (основная) ветка в новых репозиториях — `main`.

```text
main              A --- B --- C -------------- F   (F — merge-коммит)
                              \              /
kb/fs01-access                 D --- E ------'
                   ↑ здесь ты правишь инструкцию, не ломая main
```

**Слияние (merge).** Когда ветка готова, её вливают в `main`. Если `main` с момента создания ветки не двигался — Git просто переставляет указатель вперёд: это **fast-forward**, самый простой случай. Если обе ветки двигались — делается **трёхстороннее слияние** (`three-way merge`): Git сравнивает два состояния и их общего предка и пытается склеить автоматически. Если оба меняли **одни и те же строки** — возникает **конфликт (merge conflict)**, и Git остановится, вставив в файл маркеры:

```text
<<<<<<< HEAD
Путь: \\FS01\HR
=======
Путь: \\FS01\HR (доступ через группу GG-HR)
>>>>>>> kb/fs01-access
```

Твоя задача — руками оставить правильный вариант, удалить маркеры, сохранить файл, добавить его в индекс и завершить коммит.

**Сеть и порты.** Git поверх HTTPS использует порт **443**, поверх SSH — **22**. В корпоративной сети они часто закрыты наружу — тогда пользуются внутренним GitLab/Gitea. Для GitHub с 2021 года пароль от аккаунта в `git push` не подходит: нужен **PAT** (personal access token) либо **SSH-ключ**. Именно поэтому при первом пуше Git for Windows открывает окно в браузере — это Git Credential Manager просит авторизоваться.

**Git ≠ GitHub.** Git — программа на твоём компьютере. GitHub — облачный хостинг репозиториев плюс обвязка: Pull Request (запрос на слияние с обсуждением), Issues (задачи), Actions (CI/CD, урок 83). Есть аналоги: GitLab, Gitea, Bitbucket, из российских — GitFlic, GitVerse `[ПРОВЕРИТЬ актуальный статус и тарифы]`. Доступ к GitHub из РФ в 2026 может быть нестабильным (замедление, ограничения) — легальная альтернатива: собственный GitLab CE на сервере GIT01 из DevOps-трека или локальный Gitea. Git при этом остаётся тем же самым.

## 3. Аналогия из жизни

Представь нотариальную контору. Ты приносишь туда документ — тебе выдают **заверенную копию** и делают запись в журнале: кто принёс, когда, что было на предыдущей странице. Дальше ты правишь документ дома, приносишь новую копию — появляется новая запись. Записи пронумерованы и связаны: невозможно вклеить запись «между» 5-й и 6-й, не порвав нумерацию. Любую старую копию можно достать из архива и посмотреть, что там было.

**Ветка** — это отдельный чистовик, который ты правишь у себя дома, пока основной документ в конторе не трогают. Когда работа готова — приносишь его и просишь сшить с основным. Если двое правили один и тот же абзац по-разному, нотариус не угадывает — он кладёт оба варианта перед тобой и говорит: «Решай сам».

Где аналогия ломается: нотариус хранит только бумажные копии, а Git дополнительно умеет сам **склеивать изменения в разных частях файла** без человека — если ты правил первый абзац, а коллега пятый, конфликта не будет вообще.

## 4. Практика и команды

### 4.1. Установка и проверка версии

```powershell
winget install --id Git.Git -e --source winget
git --version
```

```bash
sudo apt update && sudo apt install -y git
git --version
```

`winget` — штатный менеджер пакетов Windows. Ожидаемый вывод: `git version 2.4x.x.windows.1`. Если версия вывелась — установка прошла, Git for Windows заодно поставил **Git Bash** (эмуляцию bash на Windows — удобно, когда в мануале Linux-команды) и **Git Credential Manager**.

### 4.2. Базовая настройка (один раз на машину)

```bash
git config --global user.name "adm.student"
git config --global user.email "adm.student@corp.vektor.lab"
git config --global init.defaultBranch main
git config --global core.autocrlf true
git config --list --show-origin
```

- `--global` — «для моего пользователя Windows/Ubuntu», настройки пишутся в `C:\Users\adm.student\.gitconfig` или `~/.gitconfig`.
- `user.name` / `user.email` — подпись, которую Git ставит в каждый коммит. Не путай с логином на GitHub.
- `init.defaultBranch main` — чтобы новые репозитории создавались с веткой `main`, а не `master`.
- `core.autocrlf true` — на Windows: при коммите CRLF переводится в LF, при выгрузке обратно. Спасает от «весь файл помечен изменённым» на смешанных командах. На Linux оставлять по умолчанию.
- `--show-origin` — откуда прочитано значение: смотри, что настройка не пришла из чужого файла.

### 4.3. Инициализация и статус

```bash
cd C:\IT\vektor-it-docs
git init
git status
```

Вывод (`On branch main / No commits yet / Untracked files: README.md`) — Git видит файлы, но **не отслеживает** их. Что смотреть: `Untracked` — новые файлы, `Changes not staged for commit` — изменённые, `Changes to be committed` — уже в индексе. `git status` — самая часто используемая команда в Git; нажимай её перед каждым `add` и после каждого конфликта.

### 4.4. Добавление в индекс

```bash
git add README.md
git add kb/
git add .
git restore --staged README.md
```

`git add .` — добавить всё из текущей папки. `git restore --staged <файл>` — убрать файл из индекса (не удаляя содержимое). Что смотреть: после `git add` в `git status` файл перескочил в зелёную зону `Changes to be committed`.

### 4.5. Коммит

```bash
git commit -m "kb: добавлена инструкция по доступу к \\FS01\Obshchee"
git commit -am "kb: исправлен шаг 3"
```

`-m` — сообщение. `-a` — автоматически включить все изменённые **уже отслеживаемые** файлы (новые не захватит, их надо `add`). Вывод: `[main a3f9c1d] kb: ... 2 files changed, 47 insertions(+)` — ветка, короткий хеш, статистика. Хорошее сообщение — глагол + предмет: `kb: добавлен раздел про группы доступа`, а не `fix` и не `123`.

### 4.6. История и диффы

```bash
git log --oneline --graph --all
git log -p -1
git diff
git diff --staged
```

- `--oneline` — по строке на коммит, `--graph` — ASCII-схема веток и слияний, `--all` — все ветки.
- `-p -1` — показать **последний** коммит с полным диффом.
- `git diff` — чего ещё нет в индексе; `git diff --staged` — что попадёт в следующий коммит. Это две разные вещи, их часто путают.

Ожидаемый вывод: `a3f9c1d (HEAD -> main) kb: исправлен шаг 3`. Что смотреть: HEAD должен стоять на той ветке, где ты думаешь.

### 4.7. Ветки

```bash
git branch
git switch -c kb/fs01-access
git switch main
```

`git branch` — список веток, звёздочка у текущей. `switch -c` — создать и сразу переключиться (с Git 2.23; в старых мануалах `checkout -b` — эквивалент). Правило: любая правка документа — в отдельной ветке, `main` остаётся чистой.

### 4.8. Слияние и конфликт

```bash
git switch main
git merge kb/fs01-access
git status
```

При fast-forward вывод: `Fast-forward` и список изменённых файлов. При конфликте: `CONFLICT (content): Merge conflict in kb/fs01-access.md` и `Automatic merge failed`. Дальше: правишь файл руками, убираешь маркеры `<<<<<<<`, `=======`, `>>>>>>>`, затем `git add <файл>` и `git commit` (Git подставит готовое сообщение). `git merge --abort` — отменить слияние и вернуться как было.

### 4.9. Удалённый репозиторий и пуш

```bash
git remote add origin git@github.com:<твой-логин>/vektor-it-docs.git
git remote -v
git push -u origin main
```

`remote add` — привязать адрес под именем `origin` (имя любое, но `origin` — стандарт). `-u` — запомнить связь, дальше хватит `git push`. Вывод: `branch 'main' set up to track 'origin/main'`. Типичная ошибка при первом пуше: `remote: Support for password authentication was removed` — значит, нужен PAT или SSH-ключ, а не пароль.

### 4.10. Клонирование и получение изменений

```bash
git clone git@github.com:<твой-логин>/vektor-it-docs.git
cd vektor-it-docs
git pull
```

`clone` создаёт полную копию вместе с историей. `git pull` = `git fetch` (забрать) + `git merge` (влить в текущую ветку). Вывод `Already up to date.` — всё синхронно. Если после правок в другом месте будет `! [rejected] main -> main (fetch first)` — сначала делай `pull`, потом `push`.

### 4.11. Откат: restore, revert

```bash
git restore README.md
git revert a3f9c1d
git restore --source=HEAD~1 -- kb/fs01-access.md
```

- `restore <файл>` — выкинуть незакоммиченные правки (файл вернётся к последнему коммиту). Восстановлению не подлежит — сделай коммит, если не уверен.
- `revert <хеш>` — создать **новый** коммит, отменяющий изменения указанного. Безопасно для общей ветки: история не переписывается.
- `restore --source=HEAD~1 -- <файл>` — достать конкретный файл из предыдущего коммита (`HEAD~1` = «на один назад»).

### 4.12. Авторизация по SSH

```bash
ssh-keygen -t ed25519 -C "adm.student@corp.vektor.lab"
ssh -T git@github.com
```

`-t ed25519` — современный тип ключа, `-C` — комментарий-метка. Ключ ляжет в `~/.ssh/id_ed25519` и `id_ed25519.pub`; **публичную** часть (`.pub`) добавляешь в GitHub → Settings → SSH and GPG keys, приватную не отдаёшь никому. Проверка: `Hi <логин>! You've successfully authenticated...`

### 4.13. `.gitignore` и GUI

```text
# .gitignore
*.zip
*.log
~$*
Thumbs.db
secrets/
```

Файл в корне репозитория: перечисленное Git просто не замечает. Обязателен, если в папке есть бэкапы, офисные «хвосты» `~$документ.docx` и пароли.

**GUI-пути:** GitHub Desktop — File → Add local repository → Commit / Push. VS Code — панель Source Control (`Ctrl+Shift+G`): список изменённых файлов, поле сообщения, кнопка «Commit», затем «Sync Changes». В гибридном варианте удобно: правишь в VS Code, а сложные операции (конфликты, revert) делаешь в терминале.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

- **WIN11-CL01** — Windows 11, в домене `corp.vektor.lab`, заходишь под `adm.student` (входит в локальные администраторы), сеть DHCP от DC01.
- **UBU01** (10.10.10.30) — Ubuntu Server 24.04, доступ по SSH под твоим пользователем (создан при установке), интернет через NAT-шлюз 10.10.10.2.
- **FS01** (10.10.10.20) — файловый сервер, общая папка `\\FS01\Obshchee` доступна.
- Заведён учебный аккаунт на GitHub (личный, не корпоративный). Если доступ к github.com нестабилен — делай лабораторную с локальным репозиторием, а «удалённым» пусть выступит bare-репозиторий на UBU01: `git init --bare /srv/git/vektor-it-docs.git` и `git remote add origin ssh://<user>@10.10.10.30/srv/git/vektor-it-docs.git`. Логика команд та же.
- Из урока 73 у тебя есть черновик инструкции (например, «Как восстановить пароль в домене») — он и станет первым документом.

### Снапшот

В VMware Workstation: выделить ВМ → правый клик → **Snapshot → Take Snapshot**, имя `before-l1-077`. Сделать на **WIN11-CL01** и **UBU01** (это две затрагиваемые машины; FS01 меняется только папкой, но снапшот на нём тоже не помешает).

### Шаги

1. **WIN11-CL01.** Установить Git: `winget install --id Git.Git -e --source winget`. Открыть новое окно терминала. Ожидаемо: `git --version` печатает версию.
2. **WIN11-CL01.** Настроить `user.name`, `user.email`, `init.defaultBranch main`, `core.autocrlf true` (пункт 4.2). Ожидаемо: `git config --list` содержит все четыре значения.
3. **WIN11-CL01.** Создать папку `C:\IT\vektor-it-docs`, в ней `git init`. Создать `README.md` в две строки: «Документация IT компании Вектор» и «Ведёт: adm.student». Ожидаемо: `git status` показывает `Untracked files: README.md`.
4. **WIN11-CL01.** Скопировать в папку свою инструкцию как `kb/password-reset.md`, а также `stand-log.md`. Создать `.gitignore` из пункта 4.13. Ожидаемо: три файла в `Untracked`.
5. **WIN11-CL01.** `git add .` → `git status` → `git commit -m "kb: первичная документация стенда и инструкция по паролям"`. Ожидаемо: `1 file changed` (точнее — 3 файла) и `git log --oneline` показывает один коммит.
6. **WIN11-CL01.** Создать ветку `kb/fs01-access`, переключиться. Добавить файл `kb/fs01-access.md` с пошаговой инструкцией: открыть `\\FS01\Obshchee` (всем), `\\FS01\HR` (группа `GG-HR`), что делать при ошибке «Отказано в доступе». Закоммитить. Ожидаемо: `git log --oneline --graph --all` рисует две линии.
7. **WIN11-CL01.** `git switch main`, убедиться, что файла `kb/fs01-access.md` в папке **нет** (он живёт в ветке). Затем `git merge kb/fs01-access`. Ожидаемо: `Fast-forward`, файл появился.
8. **WIN11-CL01.** Смоделировать конфликт: в `main` в первой строке `kb/fs01-access.md` написать `Путь: \\FS01\HR`, закоммитить. Вернуться в `kb/fs01-access` (она теперь позади), там в той же строке написать `Путь: \\FS01\HR (через GG-HR)`, закоммитить, затем `git switch main` и `git merge kb/fs01-access`. Ожидаемо: `CONFLICT`. Открыть файл, оставить объединённый вариант, убрать маркеры, `git add`, `git commit`. Ожидаемо: `git status` чистый.

## 6. Ошибки новичков и безопасность

1. **Коммит паролей и ключей.** Ошибка: `git add .` в папке, где лежит `passwords.txt` или конфиг с токеном. К чему приводит: файл уходит в историю навсегда — его видят все, кому открыт доступ, а после публикации репозитория ещё и поисковые роботы. Правильно: `.gitignore` до первого `add`, репозиторий **private**, перед коммитом глазами посмотреть `git status`, а если секрет уже улетел — не «откатывать», а **менять сам пароль/токен**, потому что старый скомпрометирован.
2. **Работа прямо в `main`.** Ошибка: любая правка сразу в основной ветке. К чему приводит: сломанная инструкция публикуется, а «рабочая» версия перезаписана. Правильно: ветка на каждую правку, влитие в `main` — только когда документ проверен.
3. **Сообщения коммитов в стиле `fix`, `asd`, `update`.** К чему приводит: через месяц `git log` бесполезен, искать нужное изменение приходится перебором. Правильно: `kb: добавлен раздел про GG-HR`, `kb: исправлена опечатка в пути к FS01`.
4. **`git add .` без последующего `git status`.** К чему приводит: в репозиторий попадают `Thumbs.db`, `~$инструкция.docx`, `backup.zip` на 300 МБ. Правильно: `.gitignore` + привычка проверять `status` перед каждым коммитом.
5. **`git push --force` на общей ветке.** К чему приводит: твоя копия затирает коммиты коллег — их работа пропадает из общей ветки. Правильно: `--force` только в своей личной ветке и только осознанно; в общей — `git pull`, разбор, обычный `push`.
6. **Путать коммит и пуш.** Ошибка: «я же закоммитил, значит сохранилось везде». К чему приводит: документ есть только на одной машине, а коллега видит старую версию. Правильно: коммит — локально, `push` — на сервер, `pull` — забрать чужое.
7. **Два источника правды.** Ошибка: править инструкцию прямо в `\\FS01\Obshchee\IT` и «иногда» коммитить. К чему приводит: файл на шаре и файл в Git расходятся, и никто не знает, какой правильный — ровно заявка #4821. Правильно: Git — источник правды, на FS01 — копия, публикуемая после коммита.
8. **Хранить в Git большие бинарники и базы.** К чему приводит: репозиторий распухает, клонирование занимает минуты. Правильно: `[ПРОВЕРИТЬ]` Git LFS для больших файлов, а дампы БД и ISO — в отдельное хранилище, не в Git.

### Безопасность

- **В боевой среде нельзя** публиковать внутренние документы в публичный репозиторий: там адреса, схемы сети, имена серверов, иногда учётки. На стенде сеть `10.10.10.0/24` безобидна, в компании — это карта для атакующего. Корпоративная практика: внутренний GitLab/Gitea, репозиторий private, доступ по группам.
- **Нельзя** отключать 2FA на GitHub ради «чтобы проще пушить» и нельзя хранить приватный SSH-ключ в репозитории или в сетевой папке.
- **Нельзя** давать всем права на `main` напрямую: в нормальной среде правки идут через Pull Request с проверкой вторым человеком (аналог процедуры изменения из урока 69).
- На стенде ты работаешь под `adm.student` (администратор домена) на клиентской машине — это учебное упрощение. В реальной работе под доменным админом за рутинной машиной не сидят: для правок документации хватает обычной учётной записи, а админская — только через elevation.
- Ключи и PAT, которые ты выпустил на стенде, в конце обучения отзови: GitHub → Settings → Applications / SSH keys → Delete.

## 7. Вопросы на собеседовании

**Вопрос 1. Чем Git отличается от GitHub?**
Ответ: Git — распределённая система контроля версий, программа, которая ставится локально и хранит всю историю в папке `.git`; с ней можно работать без интернета. GitHub — это хостинг репозиториев и обвязка вокруг Git: веб-интерфейс, Pull Request, Issues, CI/CD. Git можно использовать без GitHub (локально, с GitLab, Gitea), а GitHub без Git — нет.
*Что хочет услышать интервьюер:* что кандидат понимает: коммиты делаются локально, а `push` — отдельное действие.
*Красный флаг:* «это одно и то же» или «Git — это облако, где хранятся файлы».

**Вопрос 2. Что такое ветка и зачем она нужна?**
Ответ: ветка — это подвижный указатель на коммит, а не копия папки, поэтому создаётся мгновенно. Нужна, чтобы делать изменения изолированно от основной ветки: правишь инструкцию или скрипт, не ломая `main`, затем вливаешь через `merge` (или Pull Request) после проверки. Указатель `HEAD` показывает текущую ветку.
*Что хочет услышать интервьюер:* понимание, что ветка — дешёвая сущность, и что работа идёт не в `main`.
*Красный флаг:* «ветка — это копия проекта на диске» или незнание, что такое `main`.

**Вопрос 3. Что такое merge conflict и как ты его решаешь?**
Ответ: конфликт возникает при слиянии, когда обе ветки меняли одни и те же строки одного файла — Git не может выбрать автоматически. Он останавливает merge и вставляет маркеры `<<<<<<<`, `=======`, `>>>>>>>`. Я смотрю `git status`, открываю файл, оставляю правильный вариант, удаляю маркеры, делаю `git add` и `git commit`. Если сомневаюсь — `git merge --abort` и разбираюсь заново. Изменения в разных частях файла Git склеивает сам, конфликта не будет.
*Что хочет услышать интервьюер:* что кандидат видел маркеры вживую и знает порядок «правим → add → commit».
*Красный флаг:* «удаляю файл и клонирую заново» или «делаю force push, чтобы прошло».

**Вопрос 4. Чем `git pull` отличается от `git fetch`? И как откатить неудачный коммит?**
Ответ: `fetch` только скачивает изменения с удалённого репозитория и обновляет `origin/main`, ничего не меняя в рабочей копии; `pull` = `fetch` + `merge` в текущую ветку. Откат: если коммит уже ушёл в общую ветку — `git revert <хеш>`, он создаёт новый коммит с обратными изменениями и не переписывает историю. `git reset --hard` переписывает историю и опасен в общей ветке. Незакоммиченные правки в файле откатываются `git restore <файл>`.
*Что хочет услышать интервьюер:* разница между «безопасным» revert и переписыванием истории, понимание, что в общей ветке историю не ломают.
*Красный флаг:* «делаю `reset --hard` и пушу с `-f`, всегда прокатывает».

**Вопрос 5. У тебя в репозитории оказался пароль. Что делаешь?**
Ответ: во-первых, считаю пароль скомпрометированным и меняю его — это главное, история Git уже разошлась по клонам. Во-вторых, убираю файл из отслеживания и добавляю в `.gitignore`, коммичу. В-третьих, если репозиторий публичный — делаю private, проверяю, не было ли форков/клонирования. При необходимости чищу историю (`git filter-repo` `[ПРОВЕРИТЬ актуальность инструмента]`), но только с согласованием, потому что это переписывание истории для всех.
*Что хочет услышать интервьюер:* приоритет «сменить секрет», а не «спрятать следы»; понимание, что Git не удаляет из истории просто так.
*Красный флаг:* «удалю файл и закоммичу — всё, пароля нет».
