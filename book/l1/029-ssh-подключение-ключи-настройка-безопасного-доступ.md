## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

SSH — это клиент-серверный протокол. На сервере работает демон `sshd` (SSH daemon), который слушает TCP-порт **22** (по умолчанию). Клиент (`ssh` в Linux, `ssh.exe` в Windows 10/11, PuTTY) открывает TCP-соединение на этот порт, стороны договариваются о шифровании, проверяют подлинность сервера (по его host key), затем аутентифицируют пользователя (пароль или ключ), и только после этого открывается сессия — псевдотерминал (PTY) или канал для команды/копирования файлов.

Схема одного подключения:

```text
   WIN11-CL01 (клиент)                        UBU01 (сервер)
   10.10.10.51                                10.10.10.30
   ┌──────────────┐                           ┌──────────────┐
   │ ssh.exe      │ ── TCP :22 ─────────────▶ │ sshd         │
   │ ~/.ssh/      │                           │ /etc/ssh/    │
   │  id_ed25519  │ ◀── host key сервера ──── │  ssh_host_*  │
   │  id_ed25519  │                           │              │
   │   .pub       │ ── аутентификация ──────▶ │ authorized_  │
   │ known_hosts  │    (пароль или ключ)      │  keys        │
   └──────────────┘                           └──────────────┘
```

Ключевые понятия:

- **Host key** — ключ самого сервера. При первом подключении клиент запоминает его в `~/.ssh/known_hosts`. Если потом ключ изменится (переустановили сервер, подменили), клиент заорёт `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!` — это защита от MITM (man-in-the-middle, «человек посередине»).
- **Пара ключей пользователя** — приватный (`id_ed25519`, никому не отдавать) и публичный (`id_ed25519.pub`, можно раздавать). Публичный кладётся на сервер в `~/.ssh/authorized_keys` пользователя, приватный остаётся у клиента. При входе сервер даёт задачку, которую можно решить только приватным ключом.
- **`sshd_config`** — конфиг сервера: на каком порту слушать, разрешать ли вход по паролю, под каким пользователем, какие алгоритмы.
- **`~/.ssh/config`** — конфиг клиента: алиасы хостов, какие ключи использовать, какие порты.

Порты и файлы, которые надо помнить на уровне L1:

| Что | Где | Зачем |
|-----|-----|-------|
| TCP 22 | сервер | порт `sshd` по умолчанию |
| `/etc/ssh/sshd_config` | сервер | конфиг демона |
| `/etc/ssh/ssh_host_*` | сервер | host keys |
| `~/.ssh/authorized_keys` | сервер, у пользователя | публичные ключи, которым можно входить |
| `~/.ssh/id_ed25519` и `.pub` | клиент | пара ключей пользователя |
| `~/.ssh/known_hosts` | клиент | запомненные host keys серверов |
| `~/.ssh/config` | клиент | алиасы и параметры подключений |

## 3. Аналогия из жизни

SSH — это как пропускная система в бизнес-центре. Сначала ты подходишь к двери (TCP-порт 22), охранник показывает тебе свой служебный жетон (host key), ты записываешь его номер в блокнот (`known_hosts`) — чтобы в следующий раз убедиться, что это тот же охранник, а не самозванец. Потом ты предъявляешь свой пропуск: либо называешь кодовое слово (пароль), либо прикладываешь брелок (ключ). Брелок удобнее: его нельзя подслушать, и он не «забывается». Список брелоков, которые пускают в здание, лежит у охраны (`authorized_keys`). Если ты потерял брелок — охрана тебя не пустит, пока не добавит новый. Аналогия ломается в одном месте: в реальном бизнес-центре охранник один и тот же, а в SSH host key — это математика, и «подделать жетон» практически невозможно, но и «перепутать охранника» тоже — клиент просто откажется входить.

## 4. Практика и команды

Все команды ниже — на стенде «Вектора». Клиент — WIN11-CL01 (Windows 11, встроенный OpenSSH-клиент), сервер — UBU01 (Ubuntu Server 24.04, `adm.student`).

**1. Проверить, что SSH-клиент есть на Windows.**

```powershell
Get-Command ssh
ssh -V
```

`Get-Command` показывает путь к `ssh.exe` (обычно `C:\Windows\System32\OpenSSH\ssh.exe`). `ssh -V` печатает версию, например `OpenSSH_for_Windows_8.6p1, LibreSSL 3.4.2` (точная версия зависит от сборки Windows). Если `ssh` не найден — включи компонент «Клиент OpenSSH» в «Параметры → Приложения → Дополнительные компоненты».

**2. Первое подключение по паролю.**

```powershell
ssh adm.student@10.10.10.30
```

`adm.student` — имя пользователя, `10.10.10.30` — адрес UBU01. При первом подключении увидишь примерно:

```text
The authenticity of host '10.10.10.30 (10.10.10.30)' can't be established.
ED25519 key fingerprint is SHA256:xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx.
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

Введи `yes` — ключ сервера запишется в `C:\Users\<твой_профиль>\.ssh\known_hosts`. Дальше спросит пароль `adm.student` — на стенде это `Lab#2026-vektor`. Пароль при вводе не отображается, это нормально.

**3. Выполнить одну команду без интерактивной сессии.**

```powershell
ssh adm.student@10.10.10.30 "hostname; uptime"
```

Всё, что в кавычках, выполнится на сервере, вывод вернётся, сессия закроется. Удобно для быстрых проверок и для скриптов.

**4. Сгенерировать пару ключей на клиенте.**

```powershell
ssh-keygen -t ed25519 -C "adm.student@WIN11-CL01"
```

- `-t ed25519` — тип ключа (современный, короче и быстрее RSA).
- `-C` — комментарий, чтобы потом понимать, чей это ключ.
- На вопрос «Enter file in which to save the key» жми Enter (сохранит в `C:\Users\<профиль>\.ssh\id_ed25519`).
- Passphrase можно оставить пустой на стенде; в реальной работе — обязательно задавать.

Получишь два файла: `id_ed25519` (приватный, никому) и `id_ed25519.pub` (публичный, его копируем на сервер).

**5. Скопировать публичный ключ на UBU01.**

На Windows нет `ssh-copy-id`, поэтому делаем вручную:

```powershell
$pub = Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub"
ssh adm.student@10.10.10.30 "mkdir -p ~/.ssh && chmod 700 ~/.ssh && echo '$pub' >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
```

Что делает: читает публичный ключ в переменную, заходит по паролю и добавляет строку в `~/.ssh/authorized_keys`, выставляя правильные права (`700` на каталог, `600` на файл). Если права будут шире — `sshd` откажется использовать файл.

**6. Проверить вход по ключу.**

```powershell
ssh -i "$env:USERPROFILE\.ssh\id_ed25519" adm.student@10.10.10.30
```

`-i` — путь к приватному ключу. Если всё сделано правильно, пароль не спросит. Если спросит — смотри `~/.ssh/authorized_keys` на сервере и права.

**7. Посмотреть конфиг `sshd` на сервере.**

```bash
sudo sshd -T | grep -Ei 'passwordauthentication|permitrootlogin|pubkeyauthentication|port'
```

`sshd -T` печатает действующий конфиг (после применения всех `Include` и дефолтов). `grep -Ei` фильтрует по ключевым параметрам. Примерный вывод:

```text
port 22
passwordauthentication yes
permitrootlogin prohibit-password
pubkeyauthentication yes
```

`permitrootlogin prohibit-password` — root может входить только по ключу, не по паролю. Это дефолт Ubuntu.

**8. Отредактировать `sshd_config` и перезапустить демон.**

```bash
sudo nano /etc/ssh/sshd_config
sudo sshd -t
sudo systemctl restart ssh
sudo systemctl status ssh --no-pager
```

- `sshd -t` — проверка синтаксиса конфига. **Всегда** делай её перед рестартом, иначе рискуешь оставить сервер без SSH.
- `systemctl restart ssh` — перезапуск. На Ubuntu служба называется `ssh`, не `sshd` (это частая путаница).
- `systemctl status ssh --no-pager` — проверка, что служба `active (running)`.

**9. Посмотреть логи SSH.**

```bash
sudo journalctl -u ssh -n 50 --no-pager
```

`-u ssh` — юнит, `-n 50` — последние 50 строк. Здесь видно все попытки входа: успешные (`Accepted publickey for adm.student`) и неудачные (`Failed password for ...`). Это первое, куда смотреть при «не пускает».

**10. Клиентский конфиг `~/.ssh/config` (на WIN11-CL01).**

```text
Host ubu01
    HostName 10.10.10.30
    User adm.student
    IdentityFile ~/.ssh/id_ed25519
```

Файл `C:\Users\<профиль>\.ssh\config`. После этого достаточно `ssh ubu01`. Удобно, когда серверов много.

**11. Копирование файлов через `scp`.**

```powershell
scp "$env:USERPROFILE\.ssh\id_ed25519.pub" adm.student@10.10.10.30:/tmp/
```

`scp` работает поверх SSH, использует те же ключи и `known_hosts`. Синтаксис: `scp источник пользователь@хост:назначение`.

**12. Удалить устаревший host key (если сервер переустановили).**

```powershell
ssh-keygen -R 10.10.10.30
```

`-R` удаляет запись из `known_hosts`. После этого при следующем подключении снова спросит `yes/no`. **Не** удаляй файл `known_hosts` целиком — потеряешь все запомненные серверы.

### Сломай и почини

**Заявка:**

> **Пользователь:** Иван Иванов (бухгалтерия)
> **ВМ:** WIN11-CL01
> **Что написал:** «Раньше заходил на UBU01 по SSH без пароля, а теперь пишет `Permission denied (publickey)`. Ключ я не трогал. Помогите, срочно, надо логи посмотреть.»
> **Срочность:** высокая

**Как воспроизвести поломку** (на UBU01, под `adm.student`):

```bash
chmod 644 ~/.ssh/authorized_keys
```

`sshd` по умолчанию требует, чтобы `authorized_keys` был не доступен на запись группе и остальным (`StrictModes yes`). С правами `644` файл игнорируется, и вход по ключу падает с `Permission denied (publickey)`.

**Диагностика по шагам:**

1. На WIN11-CL01 проверь, что ключ на месте и подключение вообще доходит до сервера:

    ```powershell
    ssh -vvv ubu01
    ```

    `-vvv` — максимальная отладочная информация. В выводе ищи строки `Offering public key: ...` и `Authentications that can continue: publickey`. Если ключ предлагается, но сервер его не принимает — проблема на стороне сервера.

2. На UBU01 (зайди по паролю, он ещё включён) посмотри логи:

    ```bash
    sudo journalctl -u ssh -n 30 --no-pager
    ```

    Ожидаемо: строки вида `Authentication refused: bad ownership or modes for file /home/adm.student/.ssh/authorized_keys`. Это прямой указатель на права.

3. Проверь права:

    ```bash
    ls -la ~/.ssh
    ```

    Ожидаемо: `-rw-r--r--` на `authorized_keys` — вот и причина.

**Решение:**

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
ls -la ~/.ssh
```

Ожидаемо: `drwx------` и `-rw-------`. После этого `ssh ubu01` с WIN11-CL01 снова пускает без пароля.

**Ответ пользователю:** «Иван, проблема была в правах на файл с вашим ключом на сервере — он стал доступен на запись другим пользователям, и SSH из соображений безопасности перестал его использовать. Права восстановлены, вход по ключу работает. Пожалуйста, не меняйте права на файлы в `~/.ssh` — если что-то нужно, пишите заявку.»

**Закрытие заявки:** категория «Доступ / SSH», решение «Восстановлены права 700/600 на `~/.ssh` и `authorized_keys` на UBU01», время — 10 минут.

## 6. Ошибки новичков и безопасность

1. **Ошибка:** копировать приватный ключ (`id_ed25519`) на сервер или в общий чат.
   **К чему приводит:** любой, кто получил файл, входит под тобой. Восстановление — смена ключа на всех серверах.
   **Как правильно:** на сервер идёт только `.pub`. Приватный ключ не покидает твою машину.

2. **Ошибка:** оставлять пустую passphrase на приватном ключе в рабочей среде.
   **К чему приводит:** украли ноутбук — украли доступ ко всем серверам.
   **Как правильно:** на стенде можно пустую, в работе — passphrase + `ssh-agent` для удобства.

3. **Ошибка:** `chmod 777 ~/.ssh` «чтобы точно работало».
   **К чему приводит:** `sshd` игнорирует ключи (`StrictModes`), плюс любой пользователь сервера может подменить `authorized_keys` и войти под тобой.
   **Как правильно:** `700` на каталог, `600` на файлы.

4. **Ошибка:** править `sshd_config` и сразу `restart`, без `sshd -t`.
   **К чему приводит:** синтаксическая ошибка — демон не стартует, ты теряешь SSH-доступ к серверу.
   **Как правильно:** `sudo sshd -t` перед каждым рестартом; держать открытой текущую сессию, пока не проверил вход из новой.

5. **Ошибка:** удалять `known_hosts` целиком при «host key verification failed».
   **К чему приводит:** теряешь защиту от MITM для всех серверов, к которым подключался.
   **Как правильно:** `ssh-keygen -R <хост>` — удаляет только нужную запись.

6. **Ошибка:** менять порт SSH «для безопасности» и забывать про firewall/документацию.
   **К чему приводит:** сервер «пропадает» для всех, кто не знает новый порт; в реальной работе — простой.
   **Как правильно:** менять порт только осознанно, с обновлением документации и правил firewall; на стенде до L1 №39 firewall не трогаем.

7. **Ошибка:** пускать root по паролю «потому что удобно».
   **К чему приводит:** брутфорс root — самая массовая атака на SSH в интернете.
   **Как правильно:** `PermitRootLogin prohibit-password` (дефолт Ubuntu) или `no`; вход под обычным пользователем + `sudo`.

8. **Ошибка:** считать, что «connection refused» и «permission denied» — одно и то же.
   **К чему приводит:** лечишь не то: правишь ключи, когда `sshd` вообще не слушает порт.
   **Как правильно:** `connection refused` — сеть/демон; `permission denied` — аутентификация; `host key verification failed` — сменился ключ сервера.

### Безопасность

- В боевой среде **нельзя** отключать `PasswordAuthentication`, не убедившись, что у всех нужных пользователей уже есть рабочие ключи, — иначе часть людей потеряет доступ.
- **Нельзя** хранить приватные ключи в репозиториях, тикетах, чатах, на общих дисках. В реальной работе для этого есть секрет-хранилища и политики.
- **Нельзя** отключать проверку host key (`StrictHostKeyChecking=no`) «чтобы не мешало» — это открывает дверь MITM-атакам.
- На стенде мы используем учебный пароль `Lab#2026-vektor` и пустую passphrase — это допустимо только в лаборатории. В рабочей среде так делать нельзя.

## 7. Вопросы на собеседовании

**Вопрос 1. «Пользователь говорит: `Permission denied (publickey)`. Что проверишь в первую очередь?»**

Ответ: «Сначала уточню, по ключу или по паролю он ходит и на какой сервер. Дальше по порядку: есть ли у него ключ в `~/.ssh/`, совпадает ли публичный ключ с тем, что в `~/.ssh/authorized_keys` на сервере, и какие права на `~/.ssh` и `authorized_keys` — должны быть `700` и `600`. Потом смотрю `journalctl -u ssh` на сервере: там будет либо `Authentication refused: bad ownership or modes`, либо `Failed publickey`. Если ключ на месте и права ок — проверяю `sshd_config`: не отключён ли `PubkeyAuthentication` и не сменился ли `AuthorizedKeysFile`.»

**Что хочет услышать интервьюер:** системный порядок проверки, а не «перезагрузите сервер».
**Красный флаг:** «Сразу переустановлю SSH» или «удалю `known_hosts`».

**Вопрос 2. «Чем отличается `connection refused` от `permission denied` при SSH?»**

Ответ: «`connection refused` — это уровень TCP: клиент достучался до IP, но на порту 22 никто не слушает. Причины: `sshd` не запущен, слушает другой порт, firewall режет. `permission denied` — TCP-соединение установилось, но аутентификация не прошла: неверный пароль, нет ключа, права на файлы. `host key verification failed` — третий случай: сервер ответил, но его host key не совпадает с запомненным в `known_hosts`.»

**Что хочет услышать интервьюер:** понимание, на каком уровне искать проблему.
**Красный флаг:** «Это одно и то же».

**Вопрос 3. «Как настроить вход по ключу с Windows на Linux-сервер?»**

Ответ: «На Windows генерирую пару `ssh-keygen -t ed25519`, приватный остаётся в `C:\Users\<профиль>\.ssh\`, публичный копирую на сервер в `~/.ssh/authorized_keys` пользователя, выставляю права `700` на каталог и `600` на файл. Проверяю `ssh -i путь_к_ключу user@host`. Если хочу совсем без пароля — добавляю алиас в `~/.ssh/config`. На Linux то же самое, только копировать удобнее через `ssh-copy-id`.»

**Что хочет услышать интервьюер:** что человек реально это делал, а не читал.
**Красный флаг:** «Скопирую приватный ключ на сервер».

**Вопрос 4. «Зачем нужен `known_hosts` и что делать, если host key изменился?»**

Ответ: «`known_hosts` защищает от MITM: клиент запоминает host key сервера при первом подключении и сверяет при следующих. Если ключ изменился — клиент отказывается входить. Это может быть либо переустановка сервера, либо подмена. Правильно: связаться с админом сервера, сверить fingerprint, и только потом `ssh-keygen -R <хост>` и подключиться заново. Удалять весь `known_hosts` нельзя.»

**Что хочет услышать интервьюер:** понимание, что это защита, а не «глюк».
**Красный флаг:** «Просто удалю `known_hosts` и зайду».

**Вопрос 5. «Какие базовые меры безопасности для SSH-сервера ты знаешь?»**

Ответ: «Вход root по паролю запрещён (`PermitRootLogin prohibit-password` или `no`), вход по паролю для пользователей по возможности отключён в пользу ключей (`PasswordAuthentication no`), у ключей и `authorized_keys` строгие права, `sshd_config` проверяется через `sshd -t` перед рестартом, логи смотрятся через `journalctl -u ssh`. Дополнительно — ограничение доступа по IP через firewall и, если нужно, смена порта, но это уже не «базовая» мера, а дополнительная.»

**Что хочет услышать интервьюер:** что человек знает дефолты Ubuntu и не сделает хуже.
**Красный флаг:** «Отключу пароли всем сразу» без проверки, что у людей есть ключи.
