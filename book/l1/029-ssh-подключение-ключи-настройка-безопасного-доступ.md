## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**SSH (Secure Shell)** — протокол прикладного уровня (7-й уровень OSI), работает поверх TCP, стандартный порт **22**. Реализация в подавляющем большинстве случаев — **OpenSSH** (есть и на Linux, и в Windows). Старая альтернатива, Telnet (порт 23), передаёт всё открытым текстом, включая пароль, поэтому в 2026 году в боевой среде её просто нет.

Как устроено соединение по шагам:

```text
WIN11-CL01 (клиент ssh)                        UBU01 (сервер sshd, 10.10.10.30)
┌───────────────────────┐                     ┌────────────────────────────────────┐
│ ssh (OpenSSH client)  │ ── TCP 22 ─────────►│ sshd (демон, слушает порт 22)      │
│ ~/.ssh/id_ed25519     │                     │ /etc/ssh/sshd_config               │
│ ~/.ssh/known_hosts    │ ◄── сессия, PTY ────│ ~/.ssh/authorized_keys             │
└───────────────────────┘                     └────────────────────────────────────┘
         │                                                  │
         │ 1. TCP-соединение, обмен версиями протокола       │ читает конфиг при старте
         │ 2. обмен ключами (KEX) → общий сессионный ключ    │ проверяет права на ~/.ssh
         │ 3. проверка host key сервера (known_hosts)        │ пишет события в journald
         │ 4. аутентификация: publickey / password           │
         │ 5. каналы: интерактивный shell, scp, sftp, туннели│
```

Три вещи, которые надо различать, иначе будет путаница:

1. **Ключ хоста (host key)** — ключ самого сервера. Клиент при первом подключении показывает отпечаток и спрашивает «доверяешь?». Отпечаток сохраняется в `known_hosts` клиента. Если сервер переустановили, отпечаток изменится — клиент заорёт `REMOTE HOST IDENTIFICATION HAS CHANGED` и правильно сделает: это базовая защита от подмены сервера (MITM).
2. **Ключ пользователя** — пара «приватный + публичный» (по умолчанию `id_ed25519` и `id_ed25519.pub`). Приватный **никогда** не покидает твою машину. Публичный — это не секрет, его копируют на сервер в файл `~/.ssh/authorized_keys`. При входе сервер даёт «задачу», клиент решает её приватным ключом — пароль по сети не передаётся вообще.
3. **Пароль** — тоже поддерживается (`PasswordAuthentication yes` по умолчанию), но это слабее: подбирается брутфорсом, утекает через пользователя, не даёт удобной автоматизации.

Файлы и их права — ключевая часть диагностики:

- `/etc/ssh/sshd_config` — конфиг сервера; в Ubuntu 22.04+ в начале файла есть `Include /etc/ssh/sshd_config.d/*.conf`, и срабатывает **первое** встреченное значение параметра.
- `/etc/ssh/ssh_config` и `~/.ssh/config` — конфиг клиента.
- `~/.ssh/` — права **700**, `authorized_keys` и приватный ключ — **600**. Если `sshd` увидит, что файлы доступны на запись группе или всем, он откажет в ключевом входе (`StrictModes yes`).

## 3. Аналогия из жизни

SSH-вход по ключу — это как проходная в бизнес-центре. У тебя есть **личный именной пропуск** (приватный ключ) в кармане, и есть **стойка охраны**, где записано, что такой-то пропуск действителен (это `authorized_keys` с публичной частью). Ты прикладываешь пропуск к турникету, охрана сверяет его со своей базой и открывает. Приватный пропуск ты никому не отдаёшь и на стойку не выкладываешь: на стойке только описание «пропуск № X действителен».

Пароль в этой аналогии — когда ты называешь охраннику кодовую фразу. Работает, но фразу можно подслушать и она у всех сотрудников часто одинаковая.

Аналогия ломается в одном месте: пропуск нельзя скопировать, а файл приватного ключа — можно, причём так, что владелец об этом не узнает. Поэтому ключи делают с парольной фразой (passphrase).

## 4. Практика и команды

Ниже — основной набор. **Важно:** в описании стенда локальные учётные записи Linux не зафиксированы. Мы используем ту, которую ты создал при установке Ubuntu; в примерах она названа `student`. Подставляй своё имя, если назвал иначе. Пароль стенда — `Lab#2026-vektor`.

### 4.1. Подключение

```bash
ssh student@10.10.10.30
```

`student` — логин на сервере (не Windows-логин!), `10.10.10.30` — UBU01. При первом подключении спросит про отпечаток:

```text
The authenticity of host '10.10.10.30' can't be established.
ED25519 key fingerprint is SHA256:9xQ...zK4.
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

Смотрим: тип ключа (ED25519 — хорошо), отпечаток, имя хоста. Пишем `yes` — отпечаток уйдёт в `~/.ssh/known_hosts`.

Полезные ключи: `-p 2222` — другой порт; `-i ~/.ssh/id_ed25519` — конкретный ключ; `-v` — отладочный вывод (на собеседовании спросят почти наверняка).

### 4.2. Проверка, что сервер вообще слушает

```bash
ss -tlnp | grep :22
```

```text
LISTEN 0 128 0.0.0.0:22 0.0.0.0:* users:(("sshd",pid=812,fd=3))
LISTEN 0 128    [::]:22    [::]:* users:(("sshd",pid=812,fd=4))
```

Смотрим: есть ли строка `LISTEN` на порту 22 и какой процесс (`sshd`). Пусто — сервер SSH не запущен или слушает другой порт.

### 4.3. Служба SSH

```bash
systemctl status ssh
sudo systemctl restart ssh
```

На Ubuntu демон называется **`ssh`** (не `sshd`, как в RHEL/Astra — там `sshd`, это классическая путаница). В Ubuntu 24.04 рядом может присутствовать `ssh.socket` — это socket-активация, тоже нормальный вариант `[ПРОВЕРИТЬ для твоей сборки]`. Смотрим `Active: active (running)`.

### 4.4. Генерация ключа (делается на клиенте)

**Windows (PowerShell на WIN11-CL01):**

```powershell
ssh-keygen -t ed25519 -C "ivanov@WIN11-CL01"
```

**Linux:**

```bash
ssh-keygen -t ed25519 -C "student@ubu01"
```

`-t ed25519` — тип ключа (короткий и современный; RSA 4096 тоже жив, но ed25519 предпочтительнее), `-C` — комментарий, по нему потом понятно, чей ключ. Спросит путь (`Enter` — по умолчанию `~/.ssh/id_ed25519` / `C:\Users\<ты>\.ssh\id_ed25519`) и passphrase — **ставь её**, даже на стенде это полезная привычка.

```text
Your identification has been saved in /home/student/.ssh/id_ed25519
Your public key has been saved in /home/student/.ssh/id_ed25519.pub
The key fingerprint is:
SHA256:5kL...Qm8 student@ubu01
```

### 4.5. Копирование публичного ключа на сервер

**Linux (есть готовая утилита):**

```bash
ssh-copy-id student@10.10.10.30
```

**Windows (утилиты нет, копируем вручную через PowerShell):**

```powershell
type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh student@10.10.10.30 "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
```

Что здесь происходит: читаем **публичный** файл, по SSH выполняем на сервере команду, которая создаёт каталог, ставит права и дописывает ключ в конец `authorized_keys`. Обрати внимание: `>>` (дописать), а не `>` (затереть) — иначе удалишь все остальные ключи.

### 4.6. Проверка прав на сервере

```bash
ls -ld ~ ~/.ssh && ls -l ~/.ssh/authorized_keys
```

```text
drwxr-x--- 5 student student 4096 Dec  1 10:05 /home/student
drwx------ 2 student student 4096 Dec  1 10:05 /home/student/.ssh
-rw------- 1 student student  102 Dec  1 10:05 /home/student/.ssh/authorized_keys
```

Смотрим: владелец — сам пользователь, `.ssh` = `drwx------` (700), `authorized_keys` = `-rw-------` (600), домашний каталог **не** доступен на запись группе/остальным. Любое отклонение — и ключевой вход молча не работает.

### 4.7. Отладочное подключение

```bash
ssh -v student@10.10.10.30
```

```text
debug1: Connecting to 10.10.10.30 [10.10.10.30] port 22.
debug1: Server host key: ssh-ed25519 SHA256:9xQ...zK4
debug1: Offering public key: /home/student/.ssh/id_ed25519 ED25519 SHA256:5kL...Qm8
debug1: Authentication succeeded (publickey).
```

Смотрим: дошло ли до `Offering public key`, был ли ключ **принят** (`Server accepts key`) и каким способом прошла аутентификация. Если видишь `Authentications that can continue: password` — сервер не принимает ключ, иди в логи сервера. `-vvv` даёт ещё больше деталей.

### 4.8. Логи SSH на сервере

```bash
sudo journalctl -u ssh -n 50 --no-pager
```

```text
Dec 01 10:12:31 UBU01 sshd[1234]: Accepted publickey for student from 10.10.10.101 port 51234 ssh2: ED25519 SHA256:5kL...Qm8
Dec 01 10:13:02 UBU01 sshd[1240]: Failed password for student from 10.10.10.101 port 51300 ssh2
Dec 01 10:13:40 UBU01 sshd[1241]: Authentication refused: bad ownership or modes for directory /home/student/.ssh
```

Смотрим: кто, откуда (IP), каким методом, успех или отказ. Третья строка — золотая: она прямо говорит про неправильные права. Дублируется в `/var/log/auth.log`, если в системе стоит rsyslog `[ПРОВЕРИТЬ на твоей ВМ]`.

### 4.9. Проверка конфига перед перезапуском

```bash
sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak-029
sudo nano /etc/ssh/sshd_config
sudo sshd -t
```

`sshd -t` — «протестировать конфиг и выйти». Молчание = синтаксис ок. Если есть ошибка — увидишь строку с файлом и номером. **Всегда** проверяй перед `restart`: сломанный конфиг = потеря удалённого доступа.

### 4.10. Управление known_hosts

```bash
ssh-keygen -F 10.10.10.30      # найти запись
ssh-keygen -R 10.10.10.30      # удалить запись (и создать .old)
```

`-F` — найти хост в `known_hosts`, `-R` — удалить. Второе нужно, когда сервер законно переустановили и отпечаток сменился. На Windows то же самое, путь `C:\Users\<ты>\.ssh\known_hosts`. **Не** удаляй запись, если не понимаешь, почему отпечаток изменился.

### 4.11. Копирование файлов (то, зачем пришёл ivanov)

```bash
scp -r ./vygruzka student@10.10.10.30:/home/student/
sftp student@10.10.10.30
```

`scp` работает поверх SSH и использует те же ключи. `sftp` — интерактивный режим (`put`, `get`, `ls`, `bye`). На Windows оба клиента есть вместе с OpenSSH.

## 6. Ошибки новичков и безопасность

1. **Включить `PermitRootLogin yes` и ходить под root.** → Подбор пароля root = полный контроль над сервером. → Правильно: `PermitRootLogin no`, работаем обычным пользователем через `sudo`.
2. **Права 777 «чтобы точно работало».** → `sshd` отказывает в ключевом входе (`StrictModes`), а заодно любой пользователь системы может подменить `authorized_keys` и войти под тобой. → 700 на `~/.ssh`, 600 на файлы.
3. **Скопировать приватный ключ на сервер «для удобства».** → Ключ перестаёт быть секретом, вход возможен с любой машины, где он лежит. → На сервер едет **только** `.pub`.
4. **Игнорировать предупреждение `REMOTE HOST IDENTIFICATION HAS CHANGED` и сразу делать `ssh-keygen -R`.** → Это может быть подмена сервера (MITM); ты сам отключаешь защиту. → Сначала выясни у админа/по консоли VMware, переустанавливали ли сервер, сверь отпечаток.
5. **Отключить `PasswordAuthentication` и перезапустить sshd, не проверив ключ.** → Если ключ не сработает, останется только консоль гипервизора. → Всегда держи открытую сессию + снапшот + `sshd -t` перед рестартом.
6. **Ключ без passphrase на ноутбуке.** → Украли ноутбук — получили доступ ко всем серверам, куда этот ключ положен. → Passphrase + ssh-agent.
7. **Открыть порт 22 в интернет «на минутку».** → Боты сканируют IPv4 круглосуточно; логи заполнятся `Failed password` за часы. → VPN, jump-host, смена порта — не защита, а косметика; при необходимости `fail2ban` и ограничение по IP.
8. **Путать `ssh` и `sshd` / `ssh` и `sshd` в systemd.** → На Ubuntu служба `ssh`, на RHEL/Astra — `sshd`; `systemctl restart sshd` на Ubuntu выдаст «Unit sshd.service not found», и новичок решает, что «SSH сломался». → Проверяй `systemctl list-units | grep -i ssh`.

**Безопасность.** Всё, что мы делали, — учебное. Пароль `Lab#2026-vektor` общий на весь стенд, так в реальной работе нельзя: пароли уникальные, хранятся в менеджере секретов. Отключение парольного входа на стенде — правильная практика, но в боевой среде её делают по регламенту, с предупреждением пользователей и с проверенным резервным доступом через консоль гипервизора или IPMI. Приватные ключи в боевой среде хранятся с passphrase и не пересылаются в мессенджерах.

## 7. Вопросы на собеседовании

**1. Как подключиться к серверу по SSH и что делать, если он отвечает `Permission denied (publickey)`?**

Ответ: `ssh user@host`, при необходимости `-p порт` и `-i путь_к_ключу`. При `Permission denied (publickey)` иду по цепочке: проверяю, тот ли логин; `ssh -v` — предлагается ли ключ и отклоняет ли его сервер; на сервере `journalctl -u ssh` — что именно пишет sshd; права на `~/.ssh` (700) и `authorized_keys` (600), владельца файлов, права на домашний каталог; наличие нужного ключа в `authorized_keys`; не перебивает ли настройки файл из `/etc/ssh/sshd_config.d/`.

*Что хочет услышать интервьюер:* что ты знаешь про логи и права, а не просто «переустановить SSH».
*Красный флаг:* «захожу под root и включаю пароли обратно» — без диагностики и без понимания рисков.

**2. Чем аутентификация по ключу лучше пароля?**

Ответ: по сети не передаётся секрет, который можно подобрать или подсмотреть; брутфорс паролей становится бессмысленным; ключ можно отозвать, удалив строку из `authorized_keys`, не меняя пароль пользователю; удобна автоматизация (скрипты, CI, `scp`). Минусы тоже есть: ключ — файл, его можно скопировать, поэтому нужна passphrase и контроль доступа к машине.

*Что хочет услышать интервьюер:* понимание, что ключ — тоже секрет, и он требует защиты.
*Красный флаг:* «ключи невозможно украсть».

**3. Что такое `known_hosts` и что делать при `REMOTE HOST IDENTIFICATION HAS CHANGED`?**

Ответ: файл на клиенте с отпечатками ключей хостов; защита от подмены сервера. При изменении отпечатка сначала выясняю причину: переустановка сервера, смена ключей, новый IP у того же хоста — или вмешательство. Сверяю отпечаток через доверенный канал (консоль гипервизора, админ сервера), и только потом `ssh-keygen -R host` и повторное подключение. Слепо удалять запись нельзя.

*Что хочет услышать интервьюер:* что ты понимаешь смысл предупреждения, а не воспринимаешь его как помеху.
*Красный флаг:* «просто удаляю `known_hosts` целиком».

**4. Как безопасно отключить вход по паролю?**

Ответ: сначала убедиться, что ключевой вход работает у всех, кому он нужен; сделать бэкап `sshd_config`; поставить `PasswordAuthentication no` и `PubkeyAuthentication yes`; проверить `sshd -t`; перезапустить службу, **держа открытой текущую сессию** и имея доступ к консоли гипервизора; проверить вход в новом окне; при проблеме вернуть бэкап. Дополнительно — проверить `sshd_config.d/` на переопределяющие файлы.

*Что хочет услышать интервьюер:* наличие плана отката и резервного доступа.
*Красный флаг:* «правлю конфиг прямо в единственной SSH-сессии и рестартую».

**5. На каком порту и протоколе работает SSH, где смотреть логи и как проверить, что сервис слушает?**

Ответ: TCP 22, прикладной уровень, OpenSSH. Слушает ли — `ss -tlnp | grep :22`. Состояние службы — `systemctl status ssh` (Ubuntu) или `sshd` (RHEL/Astra). Логи — `journalctl -u ssh`, дополнительно `/var/log/auth.log` при наличии rsyslog. Проверка конфига — `sudo sshd -t`.

*Что хочет услышать интервьюер:* уверенное владение парой команд диагностики без подглядывания.
*Красный флаг:* «SSH работает на 21 порту» или путаница SSH с FTP.
