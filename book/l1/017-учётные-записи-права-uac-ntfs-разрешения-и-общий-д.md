# Учётные записи, права, UAC, NTFS-разрешения и общий доступ к папкам

## 1. Введение (зачем это нужно в реальной работе)

**Заявка №1147**

> Пользователь: ivanov (Иван Иванов, бухгалтерия)
> ВМ: WIN11-CL01
> Что написал: «Добрый день! Не могу сохранить отчёт в \\FS01\Buh. Папка открывается, файлы вижу, но при сохранении — "Отказано в доступе". Закрываю месяц, очень срочно!»

Это самая частая заявка на L1 после «не печатает» и «забыл пароль». Пользователь видит файлы — значит, вход на сервер прошёл, значит, проблема не в сети и не в пароле, а в разрешениях. Найти, какого именно разрешения не хватает, — и есть работа.

Дальше будет ещё интереснее: половина таких заявок решается не на сервере, а на клиенте (сохранённые старые учётные данные), а половина — на сервере (человека забыли добавить в группу). Кроме того, в России 2026 года почти любая офисная сеть — это Active Directory, и учётки из домена `corp.vektor.lab` будут попадаться вам в каждой второй заявке. А ещё есть UAC — механизм, из-за которого «я же администратор, почему не даёт?».

После этой главы вы сможете: объяснить разницу между локальной и доменной учётной записью, посмотреть состав групп пользователя, прочитать ACL папки через `icacls`, настроить общий доступ и NTFS-разрешения, найти «эффективный доступ» и объяснить пользователю человеческим языком, почему ему что-то нельзя.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

### Учётная запись, SID и токен доступа

Учётная запись (account) — это запись в базе. Локальные учётки на рабочей станции или сервере лежат в файле `C:\Windows\System32\config\SAM`. Доменные — в базе Active Directory на контроллере домена. Пароль хранится не в открытом виде, а в виде хеша.

У каждой учётки есть **SID** — Security Identifier, уникальный номер вида `S-1-5-21-1111111111-2222222222-3333333333-1001`. Для Windows важно именно он: если удалить пользователя и создать заново с тем же именем, SID будет другой, и все разрешения «отвалятся». Есть встроенные SID, которые одинаковы везде: `S-1-5-11` — «Прошедшие проверку» (Authenticated Users, все, кто успешно вошёл), `S-1-1-0` — «Все» (Everyone, включая анонимов), `S-1-5-32-544` — локальные «Администраторы», `S-1-5-32-545` — «Пользователи».

Когда вы логинитесь, подсистема безопасности собирает **маркер доступа (access token)**: SID пользователя + SID всех его групп + список привилегий + уровень целостности. Дальше все проверки доступа идут по маркеру, а не по имени.

### Права и разрешения — это разные слова

- **Права (user rights)** — «что человеку можно делать в системе»: входить локально, менять системное время, выключать компьютер. Настраиваются в `secpol.msc` → Локальные политики → Назначение прав пользователя.
- **Разрешения (permissions)** — «что можно делать с конкретным объектом»: папкой, файлом, принтером. Лежат в ACL (Access Control List) объекта.

### UAC: два токена вместо одного

UAC (User Account Control, «Контроль учётных записей») — это не «отключение админа», а разделение прав. Если `adm.student` входит в группу «Администраторы», при входе Windows создаёт **два** токена: полный (High integrity) и урезанный (Medium integrity). Explorer и все программы по умолчанию запускаются с урезанным. Хотите полный — «Запуск от имени администратора» → появляется окно согласия UAC на защищённом рабочем столе → рождается процесс с полным токеном.

```text
Вход adm.student (член группы «Администраторы»)
        │
        ├─ обычный двойной клик  →  токен «Средний»  ≈ обычный пользователь
        │                            (не может писать в C:\Windows, Program Files)
        │
        └─ «Запуск от имени администратора»
                    │
              [окно UAC: Да / Нет]
                    │
                    └─►  токен «Высокий»  = полные права администратора
```

Настройки UAC: `secpol.msc` → Локальные политики → **Параметры безопасности** → строки «Контроль учётных записей: …» (их около десяти). В реестре — ветка `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System`, параметры `EnableLUA`, `ConsentPromptBehaviorAdmin`, `PromptOnSecureDesktop`.

### NTFS-разрешения

У папки/файла на томе NTFS есть ACL — список записей ACE (Access Control Entry). Каждая запись: «кому» + «что» + «разрешить/запретить» + «наследуется ли». Базовые уровни в GUI: «Полный доступ», «Изменение», «Чтение и выполнение», «Список содержимого папки», «Чтение», «Запись». В «Дополнительных» они разложены на 13 отдельных пунктов.

Ключевые правила:
1. Разрешения **складываются**: если пользователь в двух группах, берётся объединение.
2. **Явный «Запретить» побеждает всё.** Поэтому «Запретить» ставят, только когда очень надо, — почти всегда правильнее убрать «Разрешить».
3. **Наследование**: по умолчанию дочерние объекты наследуют ACL родителя. Сняли наследование — папка живёт со своим списком.
4. **Владелец** объекта всегда может изменить разрешения, даже если формально доступа нет.

### Общий доступ (share) и как считается итог

Общий доступ — это публикация папки в сеть по протоколу **SMB** (TCP-порт 445; устаревший NetBIOS — 139). У шары свой, отдельный и очень бедный ACL: всего три уровня — «Чтение», «Изменение», «Полный доступ».

```text
КЛИЕНТ WIN11-CL01                          ФАЙЛОВЫЙ СЕРВЕР FS01
┌────────────────────┐    SMB, TCP 445   ┌───────────────────────────────┐
│ Логон: FS01\ivanov │ ────────────────► │ 1) Аутентификация             │
│ Маркер:            │                   │    логин+пароль → SID+группы  │
│  SID пользователя  │                   │ 2) Проверка ШАРЫ              │
│  SID групп         │                   │    \\FS01\Buh → «Изменение»?  │
│  Уровень целост-ти │                   │ 3) Проверка NTFS              │
│  (Medium/High)     │                   │    C:\Shares\Buh → ACL        │
│                    │ ◄──────────────── │ 4) Итог = САМОЕ СТРОГОЕ      │
└────────────────────┘  доступ / отказ   │    из (2) и (3)               │
                                          └───────────────────────────────┘
```

**Итоговый доступ по сети = минимум из разрешений шары и разрешений NTFS.** Локально (сидя за самим сервером) шаровые разрешения не действуют вовсе — только NTFS.

Разрешения NTFS применяются **всегда**, и к локальному входу, и к сетевому.

## 3. Аналогия из жизни

Представьте завод с проходной и складами. Чтобы попасть на территорию, нужен пропуск на проходной — это **разрешения общего доступа**: они пускают на завод в целом и бывают трёх видов («только посмотреть», «заходить и брать», «полный доступ»). Но у каждого склада висит свой замок — это **разрешения NTFS**: он решает, что вы сделаете внутри конкретного помещения. Можно иметь пропуск «заходить и брать» и упереться в запертую дверь склада. И наоборот: дверь открыта, а пропуск «только посмотреть» — внутрь войдёте, но ничего не вынесете.

Отдельная история — **UAC**: это вахтёр, который знает, что вы заместитель директора, но всё равно звонит директору и спрашивает разрешения, прежде чем открыть оружейную комнату. Формально вы имеете право, но каждый раз нужно подтверждение.

Аналогия перестаёт работать на том, что охранник помнит один пропуск, а Windows при каждом открытии файла пересчитывает пересечение двух списков заново — и умеет автоматически копировать правила со склада на все полки внутри.

## 4. Практика и команды

### 4.1. Кто я и в каких я группах

```cmd
whoami /user
whoami /groups
whoami /priv
whoami /all
```

`/user` — SID текущего пользователя. `/groups` — все группы и **уровень целостности** в последней строке (`Средний обязательный уровень` / `Высокий обязательный уровень`). `/priv` — привилегии. `/all` — всё сразу.

```text
C:\> whoami /groups

Имя группы                          Тип            SID
=================================== ============== ================================
...
BUILTIN\Администраторы              Группа         S-1-5-32-544  Обязательный: ...
WIN11-CL01\GG-Buh                   Группа         S-1-5-21-...-1105
...
Обязательный уровень\Средний обязательный уровень  S-1-16-8192
```

Смотрим: есть ли нужная группа и какой уровень целостности. Если «Средний» — процесс не поднят, и многие действия провалятся.

### 4.2. Локальные учётки через net

```cmd
net user
net user ivanov
net user ivanov Lab#2026-vektor /add
net user ivanov /active:no
```

`net user` без аргументов — список локальных учёток. `net user ivanov` — карточка: когда входил, когда менял пароль, в каких группах. `/add` создаёт, `/active:no` блокирует. Работает только для локальных учёток; на контроллере домена — уже `net user ivanov /domain`.

### 4.3. Локальные группы через net

```cmd
net localgroup
net localgroup GG-Buh
net localgroup GG-Buh /add
net localgroup GG-Buh ivanov /add
net localgroup GG-Buh ivanov /delete
```

Список групп, состав группы, создание группы, добавление/удаление участника. На контроллере домена — `net group` вместо `net localgroup`.

### 4.4. То же в PowerShell

```powershell
Get-LocalUser
New-LocalUser -Name "ivanov" -Password (Read-Host -AsSecureString) -FullName "Иван Иванов" -PasswordNeverExpires
New-LocalGroup -Name "GG-Buh" -Description "Бухгалтерия"
Add-LocalGroupMember -Group "GG-Buh" -Member "ivanov"
Get-LocalGroupMember -Group "GG-Buh"
```

Читается лучше, чем `net`, и удобно в скриптах. Требует повышенных прав (запускать из консоли, открытой «от имени администратора»).

### 4.5. Смотрим NTFS-разрешения: icacls

```cmd
icacls C:\Shares\Buh
```

```text
C:\Shares\Buh NT AUTHORITY\СИСТЕМА:(OI)(CI)(F)
              BUILTIN\Администраторы:(OI)(CI)(F)
              FS01\adm.student:(OI)(CI)(F)
              GG-Buh:(OI)(CI)(M)
              BUILTIN\Пользователи:(OI)(CI)(RX)
```

Расшифровка: `(F)` полный, `(M)` изменение, `(RX)` чтение и выполнение, `(R)` чтение, `(W)` запись, `(D)` удаление. `(OI)` — наследуется объектами (файлами), `(CI)` — контейнерами (папками), `(I)` — унаследовано от родителя, `(IO)` — только наследование, `(NP)` — не распространяется вниз. На русской Windows встроенные группы печатаются по-русски.

### 4.6. Меняем NTFS: grant, remove, inheritance

```cmd
icacls C:\Shares\Buh /inheritance:r
icacls C:\Shares\Buh /grant "GG-Buh:(OI)(CI)(M)"
icacls C:\Shares\Buh /grant:r "GG-Buh:(OI)(CI)(M)"
icacls C:\Shares\Buh /remove "BUILTIN\Пользователи"
icacls C:\Shares\Buh /remove:d "GG-HR"
icacls C:\Shares\Buh /reset /T /C
```

`/inheritance:r` — отключить наследование и **удалить** унаследованные записи (`:d` — отключить, но скопировать их в явные). `/grant` — добавить, `/grant:r` — заменить существующую запись для этого аккаунта. `/remove` — убрать все записи аккаунта, `/remove:d` — только запрещающие. `/reset` — вернуть наследуемые по умолчанию, `/T` — рекурсивно по вложенным, `/C` — не останавливаться на ошибках, `/Q` — без вывода успехов.

### 4.7. Забрать владение

```cmd
takeown /f C:\Shares\Buh /r /d y
icacls C:\Shares\Buh /setowner "FS01\adm.student" /T /C
```

`takeown` делает вас владельцем (`/r` — рекурсивно, `/d y` — автоответ «да» на подтверждение для папок). `/setowner` у `icacls` меняет владельца точечно. В GUI: Свойства → Безопасность → Дополнительно → «Владелец: Изменить».

### 4.8. Общий доступ

```cmd
net share
net share Buh=C:\Shares\Buh /grant:"GG-Buh",CHANGE
net share Buh /delete
```

```powershell
New-SmbShare -Name "Buh" -Path "C:\Shares\Buh" -ChangeAccess "FS01\GG-Buh" -FullAccess "FS01\adm.student"
Get-SmbShare
Get-SmbShareAccess -Name "Buh"
```

`Get-SmbShareAccess` показывает ACL шары. Уровни: `Read`, `Change`, `Full`.

### 4.9. Меняем права на шаре

```powershell
Grant-SmbShareAccess  -Name "Buh" -AccountName "FS01\GG-Buh" -AccessRight Change -Force
Revoke-SmbShareAccess -Name "Buh" -AccountName "Все" -Force
Get-SmbSession
Close-SmbSession -ClientComputerName "10.10.10.x" -Force
```

`-Force` подавляет подтверждение. `Get-SmbSession` показывает, кто сейчас держит открытые сессии на сервере, — полезно, когда «изменения не применяются»: старые сессии живут до переподключения.

### 4.10. Клиентская сторона и «эффективный доступ»

```cmd
net use
net use B: \\FS01\Buh /user:FS01\ivanov Lab#2026-vektor /persistent:no
net use * /delete /y
cmdkey /list
```

`net use` показывает подключённые сетевые диски. `/user:FS01\ivanov` — явно указать, под кем подключаться (в рабочей группе это обязательно). `net use * /delete /y` разрывает всё — первое, что делают, когда «права дали, а не работает»: Windows могла закэшировать старую сессию.

```powershell
(Get-Acl C:\Shares\Buh).Access | Format-Table IdentityReference, FileSystemRights, AccessControlType, IsInherited
```

А нормальный человеческий способ проверить итог — GUI: **Свойства папки → Безопасность → Дополнительно → вкладка «Эффективный доступ» → «Выбор пользователя» → ivanov**. Windows сама посчитает, что человек реально сможет сделать.

### 4.11. UAC глазами администратора

```cmd
runas /user:FS01\ivanov cmd
```

Запуск процесса от другого пользователя (пароль спросит в консоли). Важно: `runas` **не повышает** права — он просто меняет пользователя.

GUI-пути: `secpol.msc` → Локальные политики → Параметры безопасности → «Контроль учётных записей: …»; `gpedit.msc` → Конфигурация компьютера → Конфигурация Windows → Параметры безопасности → Локальные политики → Параметры безопасности.

### 4.12. Со стороны Linux (стенд UBU01)

```bash
smbclient -L //10.10.10.20 -U 'FS01\ivanov'
smbclient //10.10.10.20/Buh -U 'FS01\ivanov'
```

Первый — список шар, второй — интерактивный доступ к папке. Обратите внимание: имя пользователя указывается с именем машины через обратный слэш — ровно та же логика, что в `net use`. `smbclient` может быть не установлен: `sudo apt install smbclient`. Аналог UAC в Linux — `sudo`: тоже повышение прав по запросу, но без отдельного урезанного токена.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

- **FS01** — Windows Server 2022 (Evaluation), статический адрес `10.10.10.20/24`, шлюз `10.10.10.2`, рабочая группа `WORKGROUP`. Локальный администратор — `adm.student`, пароль `Lab#2026-vektor`. Если FS01 у вас ещё нет — создайте ВМ по инструкции урока 14 (установка Windows Server Evaluation), при установке выберите «Рабочая группа». Отдельная роль «Файловый сервер» для простого общего доступа не нужна, шаринг работает из коробки.
- **WIN11-CL01** — Windows 11 Enterprise (Evaluation), локальный администратор `adm.student`, тот же пароль.
- **Домен `corp.vektor.lab` ещё не развёрнут** — он появится в модуле Active Directory. Поэтому сегодня всё делаем на **локальных** учётных записях, а имена людей и групп берём те же, что будут в домене: `ivanov`, `petrova`, `sidorov`, `GG-Buh`, `GG-HR`, `GG-Sklad`, `GG-IT`. После появления домена эти группы станут доменными, а локальные мы удалим — так вы своими руками увидите разницу.
- **WIN10-CL02** не обязательна. Если хотите проверить со второй машины — она должна быть в той же сети VMnet8.

> Если у машин ещё нет адресов от DC01 (DHCP появится в сетевом модуле), FS01 ставим статикой `10.10.10.20`, а на клиенте достаточно, чтобы обе ВМ были в VMnet8 и пинговались по имени. Разрешение имён в рабочей группе идёт широковещательно, по NetBIOS.

В VMware Workstation для **FS01** и **WIN11-CL01**:

Или из командной строки хоста (путь к `.vmx` подставьте свой):

```cmd
vmrun -T ws snapshot "C:\VMs\WIN11-CL01\WIN11-CL01.vmx" before-l1-017
```

2. **FS01, PowerShell от администратора.** Создаём структуру папок.

**Ожидаемо:** три папки в `C:\Shares`.

3. **FS01.** Создаём локальных пользователей.

**Ожидаемо:** `Get-LocalGroupMember -Group "GG-Buh"` показывает `FS01\ivanov`.

5. **FS01.** Публикуем папки в сеть с разными правами шары.

## 6. Ошибки новичков и безопасность

1. **Дать на шару «Все — Полный доступ» и успокоиться.**
   → К чему приводит: любой, кто попал в сеть и знает имя шары, читает и удаляет бухгалтерские файлы. Именно так и появляются истории про «шифровальщик зашифровал всё, что видел».
   → Как правильно: выдавать доступ **группе**, а не «Всем»; на шару — «Изменение», полный доступ оставить только администраторам.

2. **Путать шару и NTFS.**
   → К чему приводит: час поиска причины «нет доступа», хотя достаточно было посмотреть вторую вкладку.
   → Как правильно: всегда проверять обе — `Get-SmbShareAccess` и `icacls`, а затем «Эффективный доступ».

3. **Ставить «Запретить» вместо того, чтобы убрать «Разрешить».**
   → К чему приводит: запрет перебивает все разрешения из всех групп; пользователь не понимает, почему перестало работать то, что работало.
   → Как правильно: «Запретить» — только для действительно осознанных случаев. По умолчанию — убрать «Разрешить» у группы.

4. **Раздавать права конкретным людям, а не группам.**
   → К чему приводит: через полгода в ACL тридцать имён, половина — уволенные; при переводе сотрудника всё ломается.
   → Как правильно: одна группа = одна бизнес-роль (`GG-Buh`, `GG-HR`), людей двигаем внутри группы.

5. **Отключать UAC, потому что «мешает».**
   → К чему приводит: любая программа, запущенная пользователем, немедленно получает полные права администратора. Это первый шаг к шифровальщику.
   → Как правильно: UAC не отключать; если приложение требует прав — запускать его «от имени администратора» или настраивать через `secpol.msc` точечно.

6. **Работать всё время из-под администратора.**
   → К чему приводит: случайное удаление папки, заражение, следы в журналах «сделал админ», а не человек.
   → Как правильно: отдельная обычная учётка для почты и браузера, отдельная административная — только для админских задач (в домене это `adm.student`).

7. **Снимать наследование «на всякий случай».**
   → К чему приводит: у дочерних папок остаётся старая копия ACL, новые разрешения сверху перестают применяться — и никто не понимает, почему.
   → Как правильно: сначала понять, зачем снимаем. Использовать `/inheritance:d` (сохранить копию), а не `:r` вслепую.

8. **Не проверять, под кем пользователь реально сидит.**
   → К чему приводит: права дали, а «не работает» — потому что в диспетчере учётных данных висит старая учётка или диск подключён с чужого сеанса.
   → Как правильно: `whoami`, `net use`, `cmdkey /list` на клиенте до того, как лезть на сервер.

### Безопасность

- **Пароль `Lab#2026-vektor` — учебный.** В реальной среде такие пароли недопустимы: минимум 12–14 символов, разные для сервисов, хранение в менеджере паролей. Никогда не пересылайте пароли в чат тикета.
- **Не выдавайте права «навсегда, чтобы не бегать».** Права на файловые ресурсы пересматриваются при увольнении и переводе — иначе бывший сотрудник сохраняет доступ к бухгалтерии.
- **Не снимайте наследование и не меняйте ACL на боевом файловом сервере без бэкапа.** Сначала — экспорт текущего ACL: `icacls C:\Shares\Buh /save C:\acl_backup.txt /T`.
- **Не логиньтесь под доменным администратором на рабочей станции пользователя.** Это классический вектор кражи учётных данных (атаки типа pass-the-hash). Для задач L1 нужны делегированные права, а не «всё».
- **«Забрать владение» — это не «настройка», это аварийная мера.** В нормальной среде владелец папки — администратор или специальная сервисная учётка, а не первый, кому понадобилось.

## 7. Вопросы на собеседовании

### Вопрос 1. Чем отличаются разрешения общего доступа от NTFS-разрешений и как считается итоговый доступ?

**Ответ.** Разрешения общего доступа (share permissions) действуют только при подключении по сети через SMB и имеют всего три уровня: «Чтение», «Изменение», «Полный доступ». Разрешения NTFS действуют всегда — и по сети, и локально, — и бывают гораздо подробнее. Итоговый доступ по сети считается как **самое строгое** из двух: если шара даёт «Чтение», а NTFS «Изменение», пользователь получит «Чтение». Обычная практика: на шару выдавать «Изменение» группе, а тонкую настройку делать на NTFS.

**Что хочет услышать интервьюер:** что вы понимаете принцип «минимум из двух» и умеете проверять обе стороны, а не только одну вкладку.

**Красный флаг:** «Ну, они одинаковые» или «главное — NTFS, шару можно дать всем полный доступ».

### Вопрос 2. Что такое UAC и почему администратор всё равно получает запрос на повышение?

**Ответ.** UAC — механизм контроля учётных записей, который при входе администратора создаёт два маркера доступа: полный (High integrity) и урезанный (Medium integrity). Все программы по умолчанию запускаются с урезанным маркером, то есть фактически с правами обычного пользователя. Когда программа просит больше — появляется запрос на защищённом рабочем столе, и только после подтверждения создаётся процесс с полным маркером. Смысл в том, чтобы обычная работа (браузер, почта, Word) не шла с правами администратора: если пользователь запустит вредонос, тот тоже останется без прав. Плюс это защита от случайных разрушительных действий.

**Что хочет услышать интервьюер:** понимание, что UAC — это не «выключение админа», а разделение токенов; что защищённый рабочий стол защищает от подмены окна.

**Красный флаг:** «UAC — бесполезная фигня, я его всегда отключаю».

### Вопрос 3. Пользователь пишет «нет доступа к папке на файловом сервере». Ваши действия?

**Ответ.** Сначала уточняю формулировку ошибки — она делит проблему пополам. «Не удаётся получить доступ / неверный пароль» — это аутентификация: сеть, учётка, кэш учётных данных, блокировка. «Отказано в доступе» после ввода пароля — авторизация: права. Дальше проверяю по порядку: под кем реально вошёл пользователь (`whoami` на клиенте, `Get-SmbSession` на сервере), в каких он группах, что даёт шара (`Get-SmbShareAccess`), что даёт NTFS (`icacls`), и сверяю через «Эффективный доступ». Потом исправляю — обычно добавлением в группу или правкой ACL, — прошу переподключить диск (`net use * /delete /y`) и проверяю сам. В ответе пользователю объясняю причину без технического жаргона.

**Что хочет услышать интервьюер:** структурный подход, разделение «аутентификация vs авторизация», знание конкретных инструментов и проверку результата.

**Красный флаг:** «Сразу даю полный доступ — пусть работает» или «Переустанавливаю Windows».

### Вопрос 4. Чем локальная учётная запись отличается от доменной? Что такое SID?

**Ответ.** Локальная учётка существует только на одной машине, хранится в SAM, и её права действуют только там. Доменная учётка хранится в Active Directory на контроллере домена, аутентификация идёт по протоколу Kerberos, и одна и та же учётка работает на всех машинах домена, а права выдаются доменным группам. SID — уникальный идентификатор безопасности, по которому Windows опознаёт пользователя и группу; имя может измениться, SID — нет. Если удалить учётку и создать с тем же именем, SID будет другим, и все разрешения придётся выдавать заново.

**Что хочет услышать интервьюер:** что вы понимаете разницу домена и рабочей группы и почему «пересоздать пользователя» — не безобидная операция.

**Красный флаг:** «Доменная учётка — это та же локальная, просто в интернете» или незнание слова SID.

### Вопрос 5. Что такое наследование разрешений и что будет, если его отключить?

**Ответ.** Наследование — механизм, при котором дочерние папки и файлы автоматически получают ACL родителя. По умолчанию все разрешения вниз передаются, и правки на верхнем уровне применяются ко всему дереву. Если наследование отключить, у объекта остаётся свой собственный список, и изменения сверху на него больше не влияют. При отключении Windows предлагает скопировать унаследованные записи в явные (это безопаснее) или удалить их (папка останется вообще без доступа, кроме владельца). Поэтому перед отключением делают экспорт ACL через `icacls /save`, а отключают точечно, а не на весь диск.

**Что хочет услышать интервьюер:** что вы не отключите наследование «на всякий случай» и знаете про риск потерять доступ и про бэкап ACL.

**Красный флаг:** «Отключаю всегда, так проще» без понимания последствий.
