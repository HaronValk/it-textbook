## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Linux-сервер — это ядро + набор служб + файловая система. Для L1 важно понимать четыре вещи: как устроена файловая система, как машина получает адрес, как к ней подключаются удалённо и как выглядит загрузка.

**Файловая система Linux.** Всё — единое дерево от корня `/`. Ключевые каталоги: `/etc` — конфиги, `/var` — изменяемые данные (логи в `/var/log`), `/home` — домашние каталоги пользователей, `/root` — дом root, `/boot` — ядро и загрузчик, `/tmp` — временные файлы. Отдельные каталоги можно вынести на отдельные разделы — это и есть «разметка диска».

**Разметка.** На диске создаётся таблица разделов (GPT или MBR), внутри — разделы, на каждом — файловая система (ext4, xfs). Отдельно делают **swap** — раздел подкачки, куда ядро сбрасывает неиспользуемую память. Для сервера типичная схема: `/` (корень), swap, `/home` (данные пользователей отдельно от системы).

**Сеть.** Ubuntu Server 24.04 настраивает сеть через **netplan** — YAML-файлы в `/etc/netplan/`. Netplan — это «фасад» над systemd-networkd или NetworkManager. На сервере обычно systemd-networkd. Файл читается при загрузке и по команде `netplan apply`.

**SSH.** Secure Shell — протокол удалённого доступа по TCP-порту 22. Клиент подключается, сервер (`sshd`) аутентифицирует по паролю или по ключу и даёт shell. Для L1 SSH — основной инструмент работы с Linux-серверами.

**Загрузка.** UEFI/BIOS → загрузчик (GRUB) → ядро → systemd (PID 1) → службы. Если что-то не стартует — смотрим `systemctl status` и `journalctl`.

## 3. Аналогия из жизни

Установка Linux-сервера — как заселение в новую квартиру. Сначала ты решаешь планировку: где будет кухня, где спальня, где кладовка (это разметка диска). Потом завозишь мебель (установка пакетов). Потом оформляешь домофон и пропуска — кто и как может войти (это SSH и учётки). И только потом начинаешь жить: включаешь свет, проверяешь, что вода идёт (службы, сеть). Если планировку сделал криво — переделывать больно, поэтому на этапе разметки думают головой, а не «на автомате».

Аналогия ломается в одном: квартиру нельзя откатить к состоянию «до ремонта» одной кнопкой, а виртуалку — можно, снапшотом. Этим мы и пользуемся.

## 4. Практика и команды

Все команды — на UBU01 под `adm.student`, если не сказано иное. `sudo` нужен для действий от root.

**1. Проверить, что мы на месте и кто мы.**

```bash
whoami
hostnamectl
```

`whoami` — текущий пользователь. `hostnamectl` — имя машины, версия ОС, ядро. Ожидаемо: `adm.student`, `Ubuntu 24.04.x LTS`, ядро 6.8.x (примерно).

**2. Посмотреть диски и разделы.**

```bash
lsblk
df -h
```

`lsblk` — блочные устройства деревом. `df -h` — занятое место по файловым системам в человекочитаемом виде. Смотрим: есть ли `/`, swap, `/home`, сколько свободно.

**3. Посмотреть сеть.**

```bash
ip -br a
ip r
```

`ip -br a` — адреса коротко (интерфейс, состояние, адрес). `ip r` — таблица маршрутов, там ищем `default via 10.10.10.2`. Если default-маршрута нет — интернета и внешней сети не будет.

**4. Проверить netplan-конфиг.**

```bash
sudo cat /etc/netplan/50-cloud-init.yaml
sudo netplan try
```

`netplan try` применяет конфиг с таймаутом: если через 120 секунд не подтвердить Enter — откатится. Это защита от «настроил и потерял связь». `netplan apply` применяет без отката.

**5. Проверить SSH-службу.**

```bash
systemctl status ssh
sudo ss -tlnp | grep :22
```

`systemctl status ssh` — состояние службы (active/running). `ss -tlnp` — слушающие TCP-порты; `grep :22` оставляет только SSH. Ожидаемо: `LISTEN 0 ... 0.0.0.0:22` и `[::]:22`.

**6. Подключиться по SSH с WIN11-CL01.**

```powershell
ssh adm.student@10.10.10.30
```

Первый раз спросит про fingerprint — отвечаем `yes`. Дальше — пароль `Lab#2026-vektor`. Если подключились — видим приглашение `adm.student@UBU01:~$`.

**7. Посмотреть логи.**

```bash
journalctl -u ssh --no-pager | tail -n 20
```

`journalctl -u ssh` — журнал службы SSH. `--no-pager` — без постраничного просмотра. `tail -n 20` — последние 20 строк. Здесь видно попытки подключения и ошибки аутентификации.

**8. Обновить систему.**

```bash
sudo apt update
sudo apt upgrade -y
```

`apt update` — обновить список пакетов из репозиториев. `apt upgrade -y` — установить обновления без вопросов. На свежей системе это десятки пакетов.

**9. Установить полезное для диагностики.**

```bash
sudo apt install -y net-tools traceroute nmap
```

`net-tools` — старые `ifconfig`, `netstat` (пригодятся, потому что половина инструкций в интернете на них). `traceroute`, `nmap` — диагностика сети. По умолчанию в Ubuntu Server их нет.

**10. Перезагрузиться и проверить, что всё поднялось.**

```bash
sudo reboot
```

После перезагрузки снова зайти по SSH и проверить `ip -br a`, `systemctl status ssh`. Если что-то не поднялось — смотреть `journalctl -b` (журнал текущей загрузки).

**Заявка:**

> **Пользователь:** Иван Иванов (бухгалтерия)
> **ВМ:** WIN11-CL01
> **Что написал:** «Не могу зайти на сервер 10.10.10.30 по SSH. Пишет `Connection timed out`. Раньше работало, я ничего не трогал.»
> **Срочность:** высокая

**Как воспроизвести поломку.** На UBU01 под `adm.student` открыть netplan-конфиг и убрать маршрут по умолчанию (или поставить неверный шлюз, например `10.10.10.99`):

**Диагностика по шагам.**

1. С WIN11-CL01 проверить связность: `ping 10.10.10.30`. Если ping идёт, а SSH — нет, проблема в службе. Если ping не идёт — проблема в сети или в самой ВМ.
2. Если ping не идёт — зайти в консоль UBU01 через VMware (не по SSH, а прямо в окно ВМ). Проверить `ip -br a` — адрес на месте? Проверить `ip r` — есть ли default.
3. Если default нет — это и есть причина: без маршрута UBU01 не отвечает на запросы из подсети 10.10.10.0/24, если адрес клиента не в той же подсети (а он в той же, но маршрут всё равно нужен для корректной работы стека [ПРОВЕРИТЬ поведение в твоей версии]). В любом случае отсутствие default-маршрута — это поломка, которую надо устранить.
4. Если default есть, но SSH не отвечает — `systemctl status ssh`. Если `inactive` — `sudo systemctl start ssh` и `sudo systemctl enable ssh`.
5. Если служба активна, но подключения нет — `sudo ss -tlnp | grep :22`. Если порт не слушается — смотреть `journalctl -u ssh`.

**Решение.** Вернуть в netplan корректный маршрут:

```yaml

  - to: default
    via: 10.10.10.2
```

Применить `sudo netplan apply`, проверить `ip r`, `systemctl status ssh`, подключиться с WIN11-CL01.

**Ответ пользователю.** «Иван, проблема была на стороне сервера: слетел маршрут по умолчанию в сетевых настройках. Восстановил, SSH снова работает. Проверьте, пожалуйста, доступ — если что-то ещё не открывается, напишите.»

**Закрытие заявки.** Категория: «Сеть / Linux-сервер». Решение: «Восстановлен default-маршрут в netplan на UBU01». Время: 15 минут. Профилактика: после любых правок netplan — `netplan try`, а не `apply`, чтобы не потерять связь.

## 6. Ошибки новичков и безопасность

1. **Ошибка:** не поставить галочку «Install OpenSSH server» при установке. **К чему приводит:** после установки SSH нет, приходится ставить вручную (`sudo apt install openssh-server`) или переустанавливать. **Как правильно:** всегда ставить галочку на серверной ОС — это стандарт.

2. **Ошибка:** `netplan apply` вместо `netplan try` при правке сети по SSH. **К чему приводит:** потеря связи с сервером, лезть в консоль VMware. **Как правильно:** `netplan try` — он откатится сам, если не подтвердить.

3. **Ошибка:** разметка «всё в один раздел» на сервере. **К чему приводит:** при переполнении `/var/log` падает вся система, потому что `/` забит. **Как правильно:** отдельные разделы под `/`, `/home`, swap — как в лабораторной.

4. **Ошибка:** DHCP на сервере. **К чему приводит:** адрес «плавает», пользователи не могут подключиться, скрипты ломаются. **Как правильно:** серверы — статически. DHCP — только для клиентов (и то позже, в уроке 33).

5. **Ошибка:** работа под root «чтобы не писать sudo». **К чему приводит:** одна опечатка — и снесена система. **Как правильно:** обычный пользователь + sudo. Root — только когда реально нужно.

6. **Ошибка:** отключение файрвола «чтобы работало». **К чему приводит:** сервер открыт всему миру. **Как правильно:** открывать конкретный порт конкретному источнику. На стенде файрвол UBU01 по умолчанию не настроен (ufw не включён), но в боевой среде так нельзя.

7. **Ошибка:** хранение пароля в открытом виде в скриптах и заметках. **К чему приводит:** утечка. **Как правильно:** SSH-ключи (в уроке 29), менеджер паролей, никаких паролей в git.

8. **Ошибка:** игнорирование обновлений. **К чему приводит:** уязвимости. **Как правильно:** `apt update && apt upgrade` регулярно, в идеале — по расписанию.

### Безопасность

В боевой среде нельзя: держать SSH с входом по паролю root (`PermitRootLogin yes`), разрешать парольный вход без ограничений (лучше — только ключи), открывать SSH в интернет без fail2ban или аналога, ставить пароли вроде `12345`. На стенде пароль `Lab#2026-vektor` — учебный, в реальной работе так нельзя. Также нельзя «на время» отключать файрвол на сервере, который смотрит в интернет, — «на время» обычно растягивается на месяцы.

**Вопрос 1. «Чем Ubuntu Server отличается от Debian?»**

Ответ: «Debian — родитель Ubuntu. Ubuntu берёт пакетную базу Debian, но добавляет свой цикл релизов (LTS каждые 2 года, поддержка 5 лет), свои репозитории, инструменты вроде netplan и cloud-init, более свежие пакеты. Debian стабильнее и консервативнее, Ubuntu удобнее для быстрого старта и корпоративного использования. В России оба распространены, плюс есть отечественные сборки на их основе — Astra Linux, ALT.»

Что хочет услышать интервьюер: что ты понимаешь родство и различие, а не «это одно и то же».

Красный флаг: «Ubuntu — это отдельная ОС, никак не связана с Debian».

**Вопрос 2. «Как настроить статический IP на Ubuntu Server 24.04?»**

Ответ: «Через netplan. Файл в `/etc/netplan/`, обычно `50-cloud-init.yaml` или `01-netcfg.yaml`. Внутри YAML: `dhcp4: false`, `addresses: [10.10.10.30/24]`, `routes` с `to: default` и `via: <шлюз>`, `nameservers`. Применяю через `netplan try` — он откатится, если потеряю связь, потом подтверждаю Enter. Проверяю `ip -br a` и `ip r`.»

Что хочет услышать: знание netplan, а не `ifconfig`/`/etc/network/interfaces` (это устаревший способ).

Красный флаг: «правлю `/etc/network/interfaces`» — на 24.04 так уже не работает по умолчанию.

**Вопрос 3. «Пользователь не может подключиться по SSH. Что проверяешь?»**

Ответ: «Сначала ping — есть ли связность. Потом на сервере `systemctl status ssh` — запущена ли служба. Потом `ss -tlnp | grep :22` — слушается ли порт. Потом `journalctl -u ssh` — что в логах: отказ аутентификации, таймаут, ошибка ключа. Если ping не идёт — смотрю `ip a` и `ip r` на сервере, есть ли адрес и маршрут. Если ping идёт, а SSH нет — файрвол или служба.»

Что хочет услышать: системный подход «сеть → служба → порт → логи», а не «перезагрузи сервер».

Красный флаг: «сразу переустанавливаю SSH».

**Вопрос 4. «Зачем нужен swap и сколько его делать?»**

Ответ: «Swap — раздел или файл подкачки, куда ядро сбрасывает неиспользуемую память. Нужен, чтобы система не падала при нехватке RAM. На сервере обычно делают swap размером 1–2× RAM, но не больше 8–16 GB, если RAM много. На стенде я сделал 2 GB — этого достаточно для учебных задач.»

Что хочет услышать: понимание, что swap — не «костыль», а штатный механизм, и что размер зависит от нагрузки.

Красный флаг: «swap не нужен вообще» или «swap = 100 GB всегда».

**Вопрос 5. «Что такое sudo и зачем он нужен?»**

Ответ: «sudo — утилита, которая позволяет обычному пользователю выполнить команду от имени root (или другого пользователя) без входа под root. Права настраиваются в `/etc/sudoers` или через группу `sudo`. Это безопаснее, чем работать под root: меньше риск снести систему одной опечаткой, и все действия логируются.»

Что хочет услышать: понимание принципа наименьших привилегий.

Красный флаг: «sudo — это просто способ не писать пароль root».
