# Terraform/OpenTofu: описание инфраструктуры, state, модули, облачные провайдеры

## 1. Введение (зачем это нужно в реальной работе)

Тикет вhelpdesk «Вектора»:

> **Пользователь:** Петрова (HR) / **ВМ:** WIN10-CL02
> **Что написала:** «К понедельнику нужны три одинаковые ВМ для стажёров — как в прошлый раз, только с той же памятью и сетью, которые вы тогда настраивали. И, пожалуйста, ничего не забыть».
> **Срочность:** средняя, до понедельника.

В прошлый раз ты создавал такие ВМ руками в веб-интерфейсе Proxmox: три раза одни и те же клики, а потом полчаса выяснял, почему у второй ВМ сеть в другой VLAN и на 2 ГБ памяти меньше. Именно это решает Infrastructure as Code (IaC, «инфраструктура как код»): инфраструктура описывается текстовыми файлами, лежит в Git, ревьюится как код и создаётся одной командой — одинаково каждый раз.

Terraform (и его открытый форк OpenTofu) — самый распространённый инструмент такого описания: он умеет разговаривать с сотнями API — от Proxmox и VMware до Yandex Cloud, Selectel и VK Cloud. После этой главы ты будешь понимать, из чего состоит конфигурация, что такое state и почему его нельзя терять, как читать `plan`, как вынести повторяющееся в модуль и как подключить облачного провайдера. Это прямой шаг к DevOps-задачам и к вакансиям, где в требованиях стоит «Terraform — уверенно».

## 2. Теория «под капотом»

### Декларативный подход

Ты пишешь **что** должно быть, а не **как** это сделать. Terraform сам строит граф зависимостей, решает, в каком порядке создавать объекты (сеть → ВМ → диск), и что делать, если объект уже существует. Ansible из урока 75 — про **настройку** уже существующих машин (конфигурационный менеджмент), Terraform — про **создание и удаление** самих ресурсов (провижининг). Их нормально используют вместе: Terraform поднял ВМ, Ansible её настроил.

### Из чего состоит конфигурация

Файлы `*.tf` на языке HCL (HashiCorp Configuration Language):

| Блок | Смысл |
|------|-------|
| `terraform { required_providers {} }` | версия самого инструмента и версии провайдеров |
| `provider "proxmox" {}` | настройки подключения к API (endpoint, токен) |
| `resource "тип" "имя" {}` | объект, которым управляем; адрес = `тип.имя` |
| `data "тип" "имя" {}` | только чтение существующего объекта |
| `variable` / `locals` / `output` | входные параметры / вычисляемые значения / выходные данные |
| `module "имя" { source = ... }` | переиспользуемый набор ресурсов |

**Провайдер** — это плагин (отдельный бинарник), который умеет говорить с конкретным API. Ядро `tofu`/`terraform` не знает, что такое Proxmox: оно через gRPC (внутренний протокол вызова процедур) передаёт провайдеру «создай ресурс с такими атрибутами», а провайдер дёргает REST API по HTTPS и возвращает ID объекта. Провайдеры скачиваются в `.terraform/providers/`, а их версии и контрольные суммы фиксируются в `.terraform.lock.hcl`.

**Модуль** — каталог с `.tf`-файлами, который вызывается блоком `module`. Корневой модуль — тот, где ты запускаешь команды. Модули бывают локальные (`./modules/vm`) и из реестра (`registry.terraform.io`, `registry.opentofu.org`), с версией через `version = "~> 1.2"`.

### State — самое важное

State (состояние) — файл JSON (`terraform.tfstate`), где записано соответствие «адрес ресурса в конфиге → реальный объект в инфраструктуре + его атрибуты». Без state инструмент не знает, что уже создано, и либо попытается создать дубль, либо не поймёт, что удалять. Ключевые команды чтения: `tofu state list`, `tofu state show`. Рядом лежат `terraform.tfstate.backup` и, на время операции, `terraform.tfstate.lock.info` — файл блокировки.

Проблемы state: он **содержит секреты** в открытом виде (пароли, ключи), его нельзя хранить в Git, и с ним не могут одновременно работать двое. Поэтому в продакшене state кладут в **remote backend** — S3-совместимое хранилище (Yandex Object Storage, VK Object Storage, Selectel, MinIO) с блокировкой и версионированием.

### Цикл работы

```text
 .tf файлы (Git)
      │
      ├─ tofu init ──► скачать провайдеров + .terraform.lock.hcl
      │
      ├─ tofu plan ──► refresh (опросить реальные объекты)
      │                  │
      │                  ├─ граф зависимостей (DAG)
      │                  └─ дифф: state  ⟷  конфиг  ⟷  реальность
      │
      └─ tofu apply ──► API провайдера (HTTPS/JSON, L7 OSI)
                          │
                          ▼
                 [ Proxmox API :8006 | Cloud API :443 ]
                          │
                          ▼
                   новый state (backend: local / S3)
```

Расхождение «реальность ≠ state» называется **drift** (дрейф): кто-то поправил ВМ руками в веб-интерфейсе, а state об этом не знает. `plan` показывает дрейф как обычное изменение.

Порты: Proxmox VE API — HTTPS 8006; облачные API и реестры провайдеров — 443; бэкенд state — тоже 443. Всё это прикладной уровень, TLS поверх TCP.

### OpenTofu vs Terraform

В августе 2023 HashiCorp сменила лицензию Terraform с MPL на BUSL (начиная с версии 1.6) — использовать её в коммерческих продуктах-конкурентах нельзя. Сообщество сделало форк **OpenTofu** под лицензией MPL 2.0, теперь он живёт под эгидой Linux Foundation. Команды и синтаксис почти совпадают (`tofu` вместо `terraform`), большинство провайдеров работают с обоими. Отличия форка: шифрование state (появилось в OpenTofu 1.7) [ПРОВЕРИТЬ], свой реестр `registry.opentofu.org`, отсутствие части поздних фич Terraform. Для РФ-контекста это удобно: OpenTofu можно ставить и форкать без юридических вопросов, а в закрытых контурах — поднимать внутреннее зеркало провайдеров (`tofu providers mirror`, блок `provider_installation` в `.terraformrc`).

## 3. Аналогия из жизни

Представь, что ты заказываешь строительство дачного посёлка подрядчику. Ты отдаёшь **проект** — сколько домов, какой площади, где забор (это `.tf`-файлы). У подрядчика есть **акт приёмки** — список того, что уже реально построено и с какими номерами участков (это state). Приходит новая правка проекта — подрядчик сверяет её с актом: «этот дом уже стоит, менять не надо; этот надо перестроить; этот снести». Без акта бригадир построит второй дом поверх первого или снесёт чужой. Модуль — это типовой проект дома, который можно заказать пять раз с разными размерами.

Где аналогия ломается: в стройке перестройка — это месяцы и снос, а у нас `apply` может заменить сервер за две минуты, и главная боль не в скорости, а в том, что state может «отстать» от реальности, если кто-то строил мимо акта.

## 4. Практика и команды

Все примеры — для OpenTofu на **UBU01** (Linux). На Windows в PowerShell работает то же самое, только бинарник `tofu.exe`; ставится через `winget install OpenTofu.OpenTofu` или `choco install opentofu` [ПРОВЕРИТЬ имена пакетов]. GUI у Terraform нет — вся работа в терминале; веб-интерфейс есть только в платном Terraform Cloud, доступность которого из РФ ограничена — для нас это не вариант.

**1. Версия и проверка установки**

```bash
tofu version
# Terraform v1.8.1 / OpenTofu v1.8.x
# + provider registry.opentofu.org/bpg/proxmox v0.66.0
```

У `terraform version` вывод аналогичный. Смотри версию ядра и версии уже скачанных провайдеров.

**2. Инициализация**

```bash
tofu init
tofu init -upgrade            # пересчитать версии провайдеров под required_providers
tofu init -backend-config=backend.hcl   # параметры бэкенда отдельным файлом
```

Скачивает провайдеров, создаёт `.terraform/` и `.terraform.lock.hcl`. **Lock-файл коммитится в Git** — он гарантирует, что у всех одинаковая версия провайдера.

**3. Форматирование и валидация**

```bash
tofu fmt -recursive           # привести HCL к канону
tofu fmt -recursive -check    # только проверить, exit code 3 если не отформатировано
tofu validate                 # синтаксис и типы без обращения к API
```

`fmt` и `validate` — обязательные шаги в CI (урок 80).

**4. Планирование**

```bash
tofu plan -out=tfplan
tofu plan -var-file=prod.tfvars
tofu plan -target=module.vm          # точечно, только для отладки
tofu plan -refresh=false             # не опрашивать API (быстро, но без учёта дрейфа)
```

В выводе: `+` создать, `~` изменить на месте, `-/+` пересоздать (destroy+create), `-` удалить. Последняя строка: `Plan: 1 to add, 0 to change, 1 to destroy`.

**5. Применение**

```bash
tofu apply tfplan        # применить сохранённый план — правильный путь
tofu apply -auto-approve # без подтверждения, только в CI
```

Применение сохранённого файла гарантирует, что применят ровно то, что ты видел на экране.

**6. Работа со state**

```bash
tofu state list
# proxmox_virtual_environment_vm.test
tofu state show proxmox_virtual_environment_vm.test
# id = "pve01/9001", name = "tmp-tofu-01", memory[0].dedicated = 1024
tofu state pull > state-backup-$(date +%F).json
```

`state show` — единственный способ увидеть атрибуты, которых нет в конфиге, но которые вернул API.

**7. Переименование и удаление из state**

```bash
tofu state mv proxmox_virtual_environment_vm.test module.vm.proxmox_virtual_environment_vm.this
tofu state rm proxmox_virtual_environment_vm.test
```

`state mv` — когда переименовал ресурс или вынес в модуль, чтобы не пересоздавать объект. `state rm` — «забудь про объект», сам объект в инфраструктуре остаётся (dangerous, легко получить «сироту»).

**8. Импорт существующего объекта**

```bash
tofu import proxmox_virtual_environment_vm.test pve01/9001   # [ПРОВЕРИТЬ] формат ID у вашего провайдера
```

Подключает руками созданную ВМ к управлению. После импорта обязателен `tofu plan` — конфиг надо дописать под реальные атрибуты.

**9. Выходные данные**

```bash
tofu output
tofu output -json | jq -r '.vm_id.value'
```

Удобно для передачи ID в другие скрипты и в CI.

**10. Уничтожение**

```bash
tofu destroy
tofu destroy -target=module.vm
```

Удаляет всё, что в state. В продакшене — только через ревью и с бэкапами.

**11. Блокировка state**

```bash
tofu force-unlock 8f3a1c2e-...   # ID из текста ошибки
```

Только если точно уверен, что никто не выполняет apply прямо сейчас.

**12. Провайдеры и зеркало**

```bash
tofu providers                 # список провайдеров и версий
tofu providers lock -platform=linux_amd64 -platform=windows_amd64
tofu providers mirror /srv/tofu-mirror   # локальное зеркало для закрытого контура
```

**13. Граф зависимостей**

```bash
tofu graph | dot -Tsvg > graph.svg
```

Показывает, в каком порядке ресурсы будут создаваться. `dot` — из пакета `graphviz`.

В Proxmox созданные объекты проверяем в веб-интерфейсе `https://10.10.10.70:8006` или на PVE по SSH: `qm list`, `qm config 9001`.

## 5. Лабораторная работа

### Предусловия

- **PVE01** (`10.10.10.70`) — установленный Proxmox VE, доступ по SSH под `root`, веб-интерфейс на `:8006`. Если PVE01 ещё не поднят — вернись к главе, где он создавался: без цели Terraform бессмысленен.
- **UBU01** (`10.10.10.30`) — Ubuntu 24.04, SSH, git из урока 74, доступ в интернет для скачивания провайдера (или внутреннее зеркало).
- DC01, FS01, WIN11-CL01, WIN10-CL02, ASTRA01 не нужны.
- Учебный пароль стенда — `Lab#2026-vektor`, но для API-токена Proxmox мы используем отдельный секрет.

### Снапшот

В VMware Workstation: правый клик по ВМ → **Snapshot → Take Snapshot**, имя `before-sysadmin-076` — на **PVE01** и **UBU01**. Внутри PVE01 дополнительно ничего не создаём: тестовая ВМ одноразовая.

### Шаги

1. **UBU01.** Устанавливаем OpenTofu из официального apt-репозитория (команды из документации OpenTofu, скрипт установки может меняться — [ПРОВЕРИТЬ] актуальный вариант на `opentofu.org`):

   ```bash
   sudo apt-get update && sudo apt-get install -y apt-transport-https ca-certificates curl gnupg
   sudo install -m 0755 -d /etc/apt/keyrings
   # ключи и строка репозитория — по инструкции с opentofu.org
   sudo apt-get update && sudo apt-get install -y opentofu
   tofu version
   ```

   Ожидаемо: `OpenTofu v1.8.x` (или новее) [ПРОВЕРИТЬ версию]. Если репозиторий недоступен — скачать бинарник со страницы релизов на GitHub и распаковать в `/usr/local/bin`.

2. **PVE01.** Создаём отдельного пользователя и API-токен (не работаем под `root@pam`):

   ```bash
   pveum user add terraform@pve --comment "OpenTofu"
   pveum role add TerraformProv -privs "VM.Allocate VM.Audit VM.Config.CPU VM.Config.Memory VM.Config.Network VM.Config.Options VM.PowerMgmt Datastore.Audit Sys.Audit"
   pveum acl modify / --users terraform@pve --roles TerraformProv
   pveum user token add terraform@pve tofu --privsep 0
   ```

   Ожидаемо: вывод с `value=...` — **секрет токена показывается один раз**, сохраняем в менеджер паролей. `--privsep 0` даёт токену права пользователя — для лабы удобно, в бою лучше `privsep 1` и отдельные права. Список привилегий [ПРОВЕРИТЬ] под вашу версию PVE.

3. **UBU01.** Создаём рабочий каталог и файлы:

   ```bash
   mkdir -p ~/tofu/vektor/modules/vm && cd ~/tofu/vektor
   ```

   `versions.tf`:

   ```hcl
   terraform {
     required_version = ">= 1.8"
     required_providers {
       proxmox = {
         source  = "bpg/proxmox"
         version = "~> 0.66"   # [ПРОВЕРИТЬ] актуальную версию в реестре
       }
     }
   }
   ```

   `providers.tf` — токен берём из переменной окружения, в файл его не пишем:

   ```hcl
   provider "proxmox" {
     endpoint = "https://10.10.10.70:8006/"
     insecure = true   # только лаба: самоподписанный сертификат PVE
   }
   ```

   `variables.tf`:

   ```hcl
   variable "pve_node" {
     type    = string
     default = "pve01"   # [ПРОВЕРИТЬ] имя узла: hostname на PVE01
   }
   ```

   `main.tf` — ВМ без диска (полноценные образы будут в уроке 77):

   ```hcl
   resource "proxmox_virtual_environment_vm" "test" {
     name      = "tmp-tofu-01"
     node_name = var.pve_node
     vm_id     = 9001

     cpu    { cores = 1 }
     memory { dedicated = 1024 }

     started = false
   }
   ```

   `outputs.tf`:

   ```hcl
   output "vm_id" { value = proxmox_virtual_environment_vm.test.vm_id }
   ```

   Имена аргументов у провайдера `bpg/proxmox` меняются между версиями — сверяйтесь с документацией провайдера в реестре [ПРОВЕРИТЬ].

4. **UBU01.** Экспортируем токен и делаем init:

   ```bash
   export PROXMOX_VE_API_TOKEN='terraform@pve!tofu=<секрет>'
   export PROXMOX_VE_INSECURE=true      # [ПРОВЕРИТЬ] имя переменной у провайдера
   tofu init
   ```

   Ожидаемо: `OpenTofu has been successfully initialized!` и появившийся `.terraform.lock.hcl`.

5. **UBU01.** `tofu fmt -recursive && tofu validate` → ожидаемо `Success! The configuration is valid.`

6. **UBU01.** `tofu plan -out=tfplan` → ожидаемо `Plan: 1 to add, 0 to change, 0 to destroy.` Читаем план глазами: имя, `vm_id`, память.

7. **UBU01.** `tofu apply tfplan` → ожидаемо `Apply complete! Resources: 1 added.` и вывод `vm_id = 9001`.

8. **PVE01.** Проверяем: `qm list | grep 9001` и `qm config 9001` → ВМ есть, память 1024. В веб-интерфейсе — та же картина.

9. **UBU01.** `tofu state list`, `tofu state show proxmox_virtual_environment_vm.test`, `tofu state pull | jq '.serial, .lineage'` → видим адрес ресурса, атрибуты и служебные поля state.

10. **UBU01.** Меняем в `main.tf` память на `2048`, снова `tofu plan` → `~ memory... 1024 -> 2048` и `Plan: 0 to add, 1 to change`. `tofu apply` → изменение на месте, без пересоздания.

11. **Дрейф.** На PVE01 вручную: `qm set 9001 --memory 4096`. На UBU01 `tofu plan` → план вернёт 2048. Это и есть drift: state и конфиг говорят одно, реальность — другое.

12. **Модуль.** Переносим ресурс в `modules/vm/` (`main.tf` с `variable "name"`, `variable "vm_id"`, `variable "memory_mb"`, ресурс с `var.*`), а в корне:

    ```hcl
    module "vm" {
      source    = "./modules/vm"
      name      = "tmp-tofu-01"
      vm_id     = 9001
      memory_mb = 2048
    }

    moved {
      from = proxmox_virtual_environment_vm.test
      to   = module.vm.proxmox_virtual_environment_vm.this
    }
    ```

    `tofu plan` → ожидаемо `No changes.` Без блока `moved` инструмент решил бы, что старую ВМ надо удалить, а новую создать.

13. **Уборка.** `tofu destroy` → `Destroy complete! Resources: 1 destroyed.` На PVE01 `qm list` больше не показывает 9001. Записываем результат в `stand-log.md`.

### Проверка

- [ ] `tofu version` показывает установленную версию OpenTofu.
- [ ] `.terraform.lock.hcl` существует и не содержит секретов.
- [ ] `tofu validate` проходит без ошибок.
- [ ] План до apply содержит `1 to add`, после apply — `No changes`.
- [ ] `tofu state list` показывает ровно один адрес ресурса.
- [ ] ВМ `tmp-tofu-01` (VMID 9001) видна и в `qm list`, и в веб-интерфейсе PVE.
- [ ] Ручное изменение памяти в PVE проявляется в `plan` как изменение.
- [ ] После выноса в модуль с блоком `moved` план пустой, ВМ не пересоздана.
- [ ] После `destroy` ВМ на PVE отсутствует, state пуст (`tofu state list` без вывода).

**Диагностика по порядку:**
1. `tofu state list` — пусто. Значит, инструмент не знает про объект, отсюда и попытка создать.
2. На PVE01: `qm list | grep 9001`, `qm config 9001` — что реально есть: память, ядра, имя.
3. Сверяем с `main.tf`: имя и VMID совпадают, память может отличаться (1024 против 2048).
4. Проверяем, нет ли lock: `ls -la .terraform.tfstate.lock.info` и нет ли текста `Error acquiring the state lock` в логе. Если lock остался от прерванного запуска — `tofu force-unlock <ID>` **только** убедившись, что никто не работает.
5. Решаем: объект нужен → импортируем; объект мусорный → удаляем.

**Решение (нужен):**

```bash
tofu import proxmox_virtual_environment_vm.test pve01/9001   # [ПРОВЕРИТЬ] формат ID
tofu plan     # покажет расхождения по памяти/ядрам
tofu apply    # приведёт ВМ к конфигу
```

**Решение (не нужен):** `qm destroy 9001` и обычный `tofu apply`.

**Ответ пользователю:** «ВМ с ID 9001 существовала вне управления, поэтому OpenTofu пытался создать её заново и получил конфликт. Мы подключили её к state командой `import` и привели память к описанной в конфиге. Впредь создавайте ВМ только через код: ручные изменения в веб-интерфейсе не попадают в state и всплывают при следующем `plan`».

**Закрытие заявки:** фиксируем в тикете команду импорта и её вывод, добавляем в `stand-log.md` строку «VMID 9001 добавлен в state через import, память приведена к 2048».

## 6. Ошибки новичков и безопасность

1. **State в Git.** → В репозитории оказываются пароли и ключи из атрибутов, а история Git их хранит вечно. → State только в remote backend с ограниченным доступом, в `.gitignore` — `*.tfstate*`, `.terraform/`.
2. **Ручные правки инфраструктуры при живом Terraform.** → Дрейф, потерянные изменения, «почему у меня всё откатилось». → Меняем только код; срочно — потом всё равно в код и `apply`.
3. **`apply` без чтения плана или с `-auto-approve` руками.** → Случайное `-/+` (пересоздание) на боевом сервере. → Всегда `plan -out` + чтение глазами, `-auto-approve` только в CI.
4. **`-target` как основной способ работы.** → State и конфиг расходятся, потом большой `apply` делает неожиданное. → `-target` только для аварийного ремонта.
5. **Один огромный state на всю компанию.** → Любая ошибка бьёт по всему, `plan` идёт минутами, блокировка мешает всем. → Делим по смыслу: сеть / серверы / облако, отдельный state на среду.
6. **Не зафиксированы версии провайдеров.** → У коллеги скачалась другая версия, план «поехал», аргументы переименовались. → `required_providers` с `~>` и коммит `.terraform.lock.hcl`.
7. **`tofu state rm` вместо `state mv`.** → Объект остался жить, но вне управления: «сирота», которая ест ресурсы и деньги. → Сначала `state mv`, `rm` — осознанно и с записью в журнал.
8. **Работа под `root@pam` с паролем в `provider`.** → Утечка полного доступа к гипервизору. → Отдельный пользователь + API-токен из переменной окружения или Vault (урок 75).

### Безопасность

В лабе мы поставили `insecure = true` (отключена проверка TLS-сертификата) и `--privsep 0` (токен с полными правами пользователя). В боевой среде так нельзя: `insecure` означает, что любой MITM подменит API гипервизора, а «широкий» токен превращает утечку одного файла в компрометацию всего кластера. Правильно: внутренний CA или нормальный сертификат на PVE, `privsep 1` и минимальный набор привилегий, ротация токенов, state в хранилище с шифрованием и версионированием, отдельные «читающие» креды для `plan` в CI. Помни: state — это тоже секрет, к нему относятся как к паролю.

## 7. Вопросы на собеседовании

**1. Что такое state и почему его нельзя хранить в Git?**

Ответ: state — JSON-файл, который связывает адреса ресурсов в конфигурации с реальными объектами и их атрибутами; без него инструмент не знает, что уже создано, и не может корректно посчитать дифф или удалить ресурс. В state попадают значения атрибутов, включая чувствительные (пароли, ключи, токены), поэтому в Git его класть нельзя — утечка через историю. В продакшене — remote backend (S3-совместимое хранилище, Terraform Cloud и т.п.) с блокировкой, версионированием и ограничением доступа; в OpenTofu дополнительно доступно шифрование state.

*Что хочет услышать интервьюер:* понимание, что state — не «кеш», а источник истины, и что в нём секреты. *Красный флаг:* «state можно просто хранить в репозитории, так удобнее» или «state не нужен, Terraform всё видит по API».

**2. Чем `plan` отличается от `apply` и что такое drift?**

Ответ: `plan` только читает (refresh) реальные объекты, строит граф и показывает дифф между конфигом, state и реальностью; ничего не меняет. `apply` исполняет план через API провайдера и обновляет state. Сохранить план (`-out`) и применить именно его — способ гарантировать, что применят ровно проверенное. Drift — расхождение реальности и state из-за ручных изменений или внешних факторов; он виден в `plan` как обычное изменение и «затирается» при `apply`.

*Что хочет услышать интервьюер:* что `plan` — это ревю-артефакт, и что дрейф лечится не «руками обратно», а приведением к коду. *Красный флаг:* «plan — это просто предпросмотр, можно пропускать».

**3. Как несколько инженеров работают с одним state?**

Ответ: через remote backend с блокировкой — пока один выполняет операцию, второй получает ошибку `Error acquiring the state lock`; снимать блокировку `force-unlock` можно только убедившись, что операция мертва. Дальше — дисциплина: короткие ветки, PR с выводом `plan`, применение из CI, разделение state по средам и доменам, чтобы люди не блокировали друг друга. В S3-бэкенде блокировка исторически делалась через отдельный сервис (DynamoDB в AWS); в свежих версиях есть `use_lockfile`, но поддержку нужно проверять под своё хранилище [ПРОВЕРИТЬ].

*Что хочет услышать интервьюер:* «блокировка + разделение state + применение из CI». *Красный флаг:* «у нас у каждого свой локальный state, потом мержим» — так не работает.

**4. Зачем модули и как их версионировать?**

Ответ: модуль — переиспользуемый набор ресурсов с параметрами; он убирает копипасту (три одинаковые ВМ для стажёров), задаёт стандарт (теги, размер диска, сеть) и упрощает ревью. Локальные модули живут в репозитории, внешние — в реестре; версия фиксируется `version = "~> 1.2"` и поднимается осознанно. Версионирование — по semver и Git-тегам, для локальных модулей работает тот же git-flow из урока 74. Важно: переименование адреса ресурса при выносе в модуль делается блоком `moved`, иначе ресурс пересоздастся.

*Что хочет услышать интервьюер:* модуль как контракт + фиксация версий + `moved`/`state mv` при рефакторинге. *Красный флаг:* «модули — это просто папки, версии не нужны».

**5. Terraform или Ansible — что выбрать? И почему OpenTofu?**

Ответ: разные задачи. Terraform/OpenTofu — провижининг: создать/изменить/удалить ВМ, сеть, балансировщик, DNS, бакет; он декларативен и хранит state. Ansible — конфигурация уже существующих машин: пакеты, файлы, сервисы, пользователи; state не хранит, работает по факту. Нормальная связка: Terraform поднял инфраструктуру → Ansible её настроил → CI проверяет оба. OpenTofu — форк Terraform под MPL 2.0 после перехода Terraform на BUSL с версии 1.6; команды и синтаксис практически совпадают, есть свой реестр провайдеров и шифрование state. Выбор зависит от лицензионных ограничений и требований к вендорной независимости — в РФ это частый аргумент в пользу OpenTofu.

*Что хочет услышать интервьюер:* чёткое разделение ответственности инструментов и знание лицензионного контекста. *Красный флаг:* «это одно и то же» или «Ansible тоже умеет state».
