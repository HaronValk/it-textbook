## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Пакетный менеджер — это две вещи: **база установленных пакетов** (локально, `/var/lib/dpkg/status` в Debian-семействе, RPM-база `/var/lib/rpm` в Red Hat-семействе) и **репозиторий** — HTTP/FTP/локальный каталог с пакетами и метаданными.

Метаданные — самое важное. Клиент не «ищет пакеты», он скачивает индекс и работает по нему:

```text
dists/noble/
  InRelease              <- Release + GPG-подпись в одном файле
  Release                <- хэши SHA256 всех файлов ниже
  main/binary-amd64/
     Packages            <- список пакетов: имя, версия, зависимости, SHA256
     Packages.gz
pool/main/n/nginx/nginx_1.24.0-2ubuntu7_amd64.deb
```

Цепочка доверия: GPG-ключ в `trusted.gpg.d`/`signed-by` → проверка `InRelease` → из него берутся хэши `Packages` → из `Packages` берутся хэши самих `.deb`. Если ключа нет — apt откажется работать, и это правильно. В RPM-мире аналог: `repodata/repomd.xml` + `repomd.xml.asc`, параметры `gpgcheck=1` и `repo_gpgcheck=1` в `.repo`-файле.

Схема стенда после этой главы:

```text
                    интернет
                       |
   upstream: archive.ubuntu.com, dl.astralinux.ru, ... (HTTPS 443)
                       |
                       v
        +---------------------------------+
        | MIRR01  10.10.10.35             |
        |  nginx :80   -> /srv/repo/public|  <- статический срез (aptly publish)
        |  apt-cacher-ng :3142            |  <- pull-through кэш "по требованию"
        |  GPG-ключ VEKTOR-REPO           |
        +---------------------------------+
             ^                    ^
             | HTTP               | HTTP
   +---------+--------+   +-------+----------+
   | UBU01            |   | ASTRA01          |
   | 10.10.10.30      |   | 10.10.10.31      |
   +------------------+   +------------------+
```

Два принципиально разных подхода, которые постоянно путают:

- **Pull-through cache** (apt-cacher-ng, Squid, Nexus, Artifactory, Pulp с remote): машина первый раз качает пакет из интернета и кладёт в кэш; второй раз отдаёт из кэша. Экономит канал, ничего не гарантирует по составу версий — что вендор выложил, то и будет.
- **Полное/фильтрованное зеркало** (aptly, debmirror, apt-mirror, `reposync`): вы сами решаете, какие дистрибутивы, компоненты и версии лежат локально, и когда вы их обновляете. Это уже контроль: обновление попадает к сотрудникам тогда, когда вы синхронизировали зеркало, а не когда проснулся вендор.

Протоколы и порты: HTTP 80, HTTPS 443, FTP 21, rsync 873 (используется для репликации зеркал), локально `file://`. Отдельного «порта APT» не существует — это обычный веб. Для RPM-инфраструктуры Katello добавляет свои порты (443, 80, 8140, 23443 у Candlepin) `[ПРОВЕРИТЬ в документации вашей версии]`.

Где что лежит в корпоративной архитектуре:

| Слой | Инструмент | Задача |
|---|---|---|
| Клиент | apt / dnf / apt-rpm (ALT) | обновить индекс, поставить пакет |
| Кэш | apt-cacher-ng, Squid, Nexus | сэкономить канал |
| Локальное зеркало | aptly, debmirror, apt-mirror, `reposync` + `createrepo_c` | фиксированный набор версий + подпись |
| Платформа управления контентом | Pulp 3 | REST API, версионирование, публикация, плагины `pulp_deb` / `pulp_rpm` |
| Управление жизненным циклом + хосты | Foreman + Katello | Content Views, окружения Library → Dev → Prod, эрраты, привязка хостов |

**Pulp 3** — это «движок контента» с REST API. Ты создаёшь *remote* (откуда тянуть), *repository* (версионируемое хранилище), *publication* и *distribution* (что и по какому URL отдать). Pulp не управляет хостами и не знает про окна обслуживания — только контент. Ставится через `pulp_installer` (Ansible), требует PostgreSQL и Redis, API по умолчанию на 24817, content app на 24816 `[ПРОВЕРИТЬ]`.

**Foreman** — управление жизненным циклом серверов (Puppet/Ansible, provisoning, отчёты). **Katello** — плагин к Foreman, который добавляет управление контентом и подписками: под капотом у него как раз Pulp + Candlepin + Qpid. Ключевые понятия Katello: **Content View** (зафиксированный срез пакетов, «снимок репозитория»), **Lifecycle Environment** (Library → Dev → QA → Production), **эррата** (errata — бюллетени обновлений безопасности), **activation key** и `subscription-manager` на клиенте. Требования к ресурсам серьёзные: Katello официально просит порядка 20 ГБ RAM и 4+ vCPU `[ПРОВЕРИТЬ]`, поэтому на домашнем стенде мы её только разберём теоретически.

Windows-аналог того же самого — WSUS (или Microsoft Configuration Manager) на DC01: центральный сервер одобряет обновления, клиенты тянут с него. Принцип ровно тот же, что у Katello.

**Управление патчами (patch management)** — это не «поставить apt upgrade», это процесс:

1. Инвентаризация: что вообще есть и какие версии.
2. Классификация: security / bugfix / feature, критичность по CVSS, попадание в БДУ ФСТЭК.
3. Тест: пилотная группа (2–3 ВМ), проверка приложения (для «Вектора» — 1С и печать).
4. Окно обслуживания и раскатка волнами.
5. Откат: снапшот, `apt install pkg=версия`, `dnf history undo`, etckeeper для конфигов.
6. Отчётность: сколько хостов, что установлено, что просрочено. Для ГИС это ещё и требование приказа ФСТЭК России № 17 о своевременной установке обновлений безопасности.

## 3. Аналогия из жизни

Представь сеть продуктовых магазинов. Каждый магазин может сам ездить на оптовый рынок за городом (каждая ВМ ходит в интернет) — медленно, дорого, и ассортимент у всех разный.

**apt-cacher-ng** — это «дежурный курьер»: первый магазин заказал ящик молока, курьер привёз и запомнил; второй магазин просит тот же ящик — курьер отдаёт со склада, на рынок не едет. Ассортимент он не контролирует.

**Локальное зеркало (aptly)** — это распределительный центр: туда завозят товар по вашему списку, проверяют срок годности и наклеивают пломбу (GPG-подпись), и только оттуда развозят по магазинам. Ассортимент и дату поставки определяете вы.

**Pulp** — это тот же распредцентр, но с компьютерным учётом, API и возможностью держать несколько версий партии одновременно. **Foreman/Katello** — это уже менеджер всей сети: он решает, что в каком магазине продаётся (Content View), в каком регионе (Lifecycle Environment) и подписывает накладные на конкретные торговые точки (хосты).

Аналогия ломается в одном месте: молоко не проверяет пломбу само и не умеет откатываться на предыдущую партию, а `.deb` и `rpm` — умеют, и именно проверка подписи и есть главная причина, по которой вся эта инфраструктура существует.

## 4. Практика и команды

### 4.1. Откуда машина берёт пакеты

```bash
cat /etc/apt/sources.list
ls -l /etc/apt/sources.list.d/
```

В Ubuntu 24.04 (наша UBU01) классический `sources.list` пуст, всё лежит в `/etc/apt/sources.list.d/ubuntu.sources` в формате **deb822**. В Astra Linux Common Edition конфиг обычно в `/etc/apt/sources.list.d/astra.list` `[ПРОВЕРИТЬ в вашей версии]`.

```
# типичный вывод
-rw-r--r-- 1 root root 2.1K /etc/apt/sources.list.d/ubuntu.sources
```

Смотреть: какие URL, какие `Suites`/`Components`, нет ли дублей и «мусорных» репозиториев, добавленных по инструкции из интернета.

### 4.2. Обновление индекса и что означают ошибки

```bash
sudo apt-get update
```

Ключевые фразы в выводе: `Hit` — индекс не изменился, `Get` — скачан, `Ign` — проигнорирован (нет файла), `Err` — ошибка. `404 Not Found` на `InRelease` почти всегда означает неверный `Suites` (например, `jammy` вместо `noble`) или удалённый из зеркала релиз.

### 4.3. Политика версий и что вообще обновится

```bash
apt-cache policy nginx
apt list --upgradable
sudo apt-get -s dist-upgrade | head -40
```

```
nginx:
  Installed: 1.24.0-2ubuntu7
  Candidate: 1.24.0-2ubuntu7.1
  Version table:
     1.24.0-2ubuntu7.1 500
        500 http://10.10.10.35 noble/main amd64 Packages
 *** 1.24.0-2ubuntu7 100
        100 /var/lib/dpkg/status
```

`-s` (`--simulate`) — обязательная привычка: сначала посмотреть, что apt собирается сделать (особенно «Remove: ...»), и только потом запускать по-настоящему.

### 4.4. Точечное обновление и удержание версии

```bash
sudo apt-get install --only-upgrade openssh-server
sudo apt-mark hold nginx
apt-mark showhold
sudo apt-mark unhold nginx
```

`--only-upgrade` не поставит пакет, если его нет; `hold` запрещает менять версию. `hold` — это долг, который нужно записать в тикет и снять после проверки, иначе пакет не получит security-обновлений никогда.

### 4.5. Автоматические обновления безопасности

```bash
sudo dpkg-reconfigure --priority=low unattended-upgrades
sudo unattended-upgrade --dry-run --debug
systemctl list-timers 'apt-daily*'
cat /var/log/unattended-upgrades/unattended-upgrades.log
```

Настройка — `/etc/apt/apt.conf.d/50unattended-upgrades` (какие origins разрешены, авторебут) и `/etc/apt/apt.conf.d/20auto-upgrades` (включено/выключено). На сервере с 1С авторебут включать нельзя — только `Unattended-Upgrade::Automatic-Reboot "false";` и ручное окно.

### 4.6. Кэш пакетов (pull-through)

На MIRR01:

```bash
sudo systemctl status apt-cacher-ng
sudo ss -lntp | grep 3142
tail -f /var/log/apt-cacher-ng/apt-cacher.log
```

На клиенте — файл `/etc/apt/apt.conf.d/01proxy`:

```text
Acquire::http::Proxy "http://10.10.10.35:3142";
Acquire::https::Proxy "DIRECT";
```

Смотреть в логе строки вида `|O|` (отдано из кэша) и `|H|` (скачано из интернета) — по соотношению видно, работает ли экономия `[ПРОВЕРИТЬ формат лога в вашей версии]`.

### 4.7. Своё подписанное зеркало через aptly

```bash
sudo aptly repo create -distribution=noble -component=main vektor-local
cd /tmp && apt-get download hello
sudo aptly repo add vektor-local /tmp/hello_*.deb
sudo aptly publish repo -batch -gpg-key=repo@corp.vektor.lab vektor-local
sudo aptly publish list
```

`repo create` задаёт `Distribution`/`Component` (это попадёт в путь `dists/noble/main`), `repo add` кладёт `.deb` в локальный репозиторий, `publish repo` генерирует метаданные и подписывает их GPG-ключом. Точный синтаксис `-gpg-key` и параметры фильтрации при `mirror create` проверяй в `aptly <команда> --help` `[ПРОВЕРИТЬ]`.

### 4.8. Подключение своего репозитория на клиенте (deb822)

```bash
curl -fsSL http://10.10.10.35/vektor-repo.asc \
  | sudo gpg --dearmor -o /usr/share/keyrings/vektor-repo.gpg

sudo tee /etc/apt/sources.list.d/vektor-local.sources >/dev/null <<'EOF'
Types: deb
URIs: http://10.10.10.35/
Suites: noble
Components: main
Signed-By: /usr/share/keyrings/vektor-repo.gpg
Enabled: yes
EOF
```

`Signed-By` — привязка ключа к конкретному репозиторию. Это правильнее, чем кидать ключ в общий `trusted.gpg.d`, где он начнёт доверять вообще любому источнику.

### 4.9. Приоритеты источников (pinning)

```text
# /etc/apt/preferences.d/vektor-local.pref
Package: *
Pin: origin 10.10.10.35
Pin-Priority: 1001
```

`1001` — «всегда предпочитать этот источник». Нужно, чтобы пакеты из внутреннего зеркала не перебивались версией из интернета.

### 4.10. RPM-сторона (для РЕД ОС / AlmaLinux / будущих проектов)

```bash
sudo dnf repolist -v
sudo dnf updateinfo list --security
sudo dnf upgrade --security
sudo dnf history
sudo dnf history undo 42
```

`updateinfo list --security` показывает только бюллетени безопасности; `history undo <id>` откатывает транзакцию целиком — этого в apt «из коробки» нет, там откат делается по пакетам.

### 4.11. Сборка локального RPM-репозитория

```bash
sudo dnf install -y dnf-plugins-core createrepo_c
sudo reposync --repo=baseos --download-path=/srv/repo
sudo createrepo_c /srv/repo/baseos
sudo gpg --detach-sign --armor /srv/repo/baseos/repodata/repomd.xml
```

`reposync` выкачивает пакеты, `createrepo_c` строит `repodata/`, отсоединённая подпись `repomd.xml.asc` закрывает проверку метаданных (`repo_gpgcheck=1`).

### 4.12. Что реально произошло на машине

```bash
tail -50 /var/log/apt/history.log
grep -E ' (install|upgrade) ' /var/log/dpkg.log | tail -20
sudo needrestart -r l
```

`history.log` — что и по чьей команде поставили; `dpkg.log` — пофайловая установка; `needrestart -r l` — список сервисов, которые работают на старых библиотеках после обновления. Классическая ошибка — обновить `libssl` и не перезапустить nginx.

### 4.13. GUI-путь (для L1-контекста)

Ubuntu Desktop: «Параметры» → «Ubuntu Software» → вкладка «Обновления». Astra Linux: «Центр управления» → «Обновление пакетов» `[ПРОВЕРИТЬ название пункта в вашей версии]`. В корпоративной среде графические обновлялки лучше отключать, чтобы не было двух конкурирующих механизмов.

### Шаги

1. **MIRR01.** Создать ВМ на PVE01: 2 vCPU, 4 ГБ RAM, 80 ГБ thin, один адаптер в bridge к VMnet8. Установить Ubuntu Server 24.04 LTS, пользователь `adm.student` `[ПРОВЕРИТЬ: логин на Linux-хостах стенда задай тот же, что в AD, для единообразия]`.
   *Ожидаемо:* система загрузилась, есть консоль.

2. **MIRR01.** Статическая сеть и имя:

```yaml

network:
  version: 2
  ethernets:
    ens18:
      addresses: [10.10.10.35/24]
      routes:
        - to: default
          via: 10.10.10.2
```

Имя интерфейса посмотреть `ip -br a` — может быть `ens18`, `ens33` или `enp0s3`. *Ожидаемо:* `ping 10.10.10.10` и `ping 8.8.8.8` проходят. Сделать снапшот `before-sysadmin-032`.

3. **MIRR01.** Установить сервисы:

```bash

sudo ss -lntp | grep -E ':(80|3142)\b'
```

*Ожидаемо:* слушают 80 (nginx) и 3142 (apt-cacher-ng).

4. **MIRR01.** Подготовить каталог и конфиг nginx:

```bash
sudo mkdir -p /srv/repo/public
sudo tee /etc/nginx/sites-available/repo >/dev/null <<'EOF'
server {
    listen 80 default_server;
    server_name mirr01.corp.vektor.lab 10.10.10.35;
    root /srv/repo/public;
    autoindex on;
    location / { try_files $uri $uri/ =404; }
    access_log /var/log/nginx/repo-access.log;
}
EOF
sudo rm -f /etc/nginx/sites-enabled/default
sudo ln -sf /etc/nginx/sites-available/repo /etc/nginx/sites-enabled/repo
sudo nginx -t && sudo systemctl reload nginx
```

*Ожидаемо:* `curl -I http://10.10.10.35/` отдаёт `200 OK`.

5. **MIRR01.** Настроить aptly (каталог публикации в `/srv/repo`):

```json
// /root/.aptly.conf

  "rootDir": "/srv/repo",
  "downloadConcurrency": 4,
  "architectures": ["amd64"]
}
```

```bash
sudo aptly repo create -distribution=noble -component=main vektor-local
sudo aptly repo list
```

*Ожидаемо:* репозиторий `vektor-local` в списке.

6. **MIRR01.** Сгенерировать ключ подписи и наполнить репозиторий:

```bash
sudo gpg --batch --passphrase '' --quick-generate-key \
  "VEKTOR Repo <repo@corp.vektor.lab>" rsa4096 sign 2y
cd /tmp && apt-get download hello
sudo aptly repo add vektor-local /tmp/hello_*.deb
sudo aptly publish repo -batch -gpg-key=repo@corp.vektor.lab vektor-local
sudo gpg --armor --export repo@corp.vektor.lab | sudo tee /srv/repo/public/vektor-repo.asc
```

*Ожидаемо:* в `/srv/repo/public/dists/noble/` появились `InRelease`, `Release`, `main/binary-amd64/Packages`.

### Сломай и почини

```text

```

Как воспроизвести: на MIRR01 остановить кэш — `sudo systemctl stop apt-cacher-ng`. Клиент при этом получает именно ошибку подключения к прокси, а не «нет пакетов» — это сбивает новичков.

Диагностика по порядку:

1. Клиент: `cat /etc/apt/apt.conf.d/01proxy` — куда вообще настроен прокси? Не сменился ли адрес после переезда ВМ.
2. Клиент: `curl -v http://10.10.10.35:3142/` — TLS не нужен, обычный HTTP. `Connection refused` → проблема на сервере, не на клиенте.
3. Клиент: `ping 10.10.10.35` и `nc -zv 10.10.10.35 3142` — сетевая доступность против доступности сервиса.
4. Сервер: `ssh adm.student@10.10.10.35 'systemctl status apt-cacher-ng --no-pager'` — упал/не запущен/в цикле рестартов.
5. Сервер: `journalctl -u apt-cacher-ng -n 50 --no-pager` — реальная причина (`No space left on device`, битый кэш, права на `/var/cache/apt-cacher-ng`).
6. Сервер: `df -h /var/cache/apt-cacher-ng` — типичная причина падения: кэш вырос и съел раздел.
7. Сервер: `sudo systemctl start apt-cacher-ng && sudo ss -lntp | grep 3142`.
8. Обходной путь на время: на клиенте закомментировать строку прокси, доказать, что обновления идут напрямую, и вернуть конфиг после починки (иначе машина останется в обход кэша навсегда).

Решение: освободить место (`sudo apt-cacher-ng` чистка кэша `sudo rm -rf /var/cache/apt-cacher-ng/*` при остановленном сервисе `[ПРОВЕРИТЬ: каталог кэша в вашей версии]`), либо расширить диск на PVE01, поднять сервис, проверить на клиенте `sudo apt-get update`.

Ответ пользователю: «Проблема была на стороне локального зеркала (переполнился кэш), сейчас исправлено. Обновления Astra снова доступны, повторите `sudo apt-get update && sudo apt-get upgrade`. Если увидите ошибку — пришлите полный текст вывода».

Закрытие заявки: указать корневую причину, действие, время, и добавить в мониторинг MON01 проверку `nc -z 10.10.10.35 3142` и `df -h /var/cache/apt-cacher-ng` с порогом 80% — чтобы не повторилось.

**Вариант 2 (подпись).** `sudo mv /usr/share/keyrings/vektor-repo.gpg /root/` на UBU01 → `apt-get update` даёт `NO_PUBKEY`. Диагностика: `ls -l /usr/share/keyrings/`, `sudo gpg --show-keys /root/vektor-repo.gpg`, `cat /etc/apt/sources.list.d/vektor-local.sources`. Решение: вернуть файл на место, `apt-get update`. Причина в проде обычно та же — ключ удалён «при чистке» или истёк срок его действия.

## 6. Ошибки новичков и безопасность

- **«Сразу `apt-get upgrade` на всё»** → обновление ядра и glibc в рабочее время, падение 1С и печати. Правильно: `-s` (симуляция) → пилотная ВМ → окно обслуживания → волны.
- **Отключить проверку подписи, чтобы «прошло»** (`[trusted=yes]`, `--allow-unauthenticated`, `gpgcheck=0`) → в репозиторий можно подсунуть любой пакет, включая бэкдор. Правильно: починить ключ, а не проверку.
- **`apt-mark hold` и забыть** → пакет годами без security-обновлений. Правильно: hold только с датой снятия и записью в тикете.
- **Одна машина-кэш без бэкапа и мониторинга** → падение MIRR01 останавливает патчинг всего офиса. Правильно: мониторить порт, диск и свежесть индекса; держать инструкцию «как обойти кэш на время».
- **Зеркало, которое никто не синхронизирует** → клиенты получают устаревшие метаданные, «404» на уже удалённые версии. Правильно: синхронизация по расписанию + алерт, если `InRelease` старше N дней.
- **Обновление сертифицированной Astra Linux SE «как обычного Ubuntu»** → можно потерять соответствие сертифицированному профилю и поддержку вендора. Правильно: обновляться только из официального репозитория вендора и по его инструкции `[ПРОВЕРИТЬ в документации Astra]`.
- **Автоматический ребут на сервере с БД** → потеря данных и простой. Правильно: `Automatic-Reboot "false"`, ребут руками в окно.
- **Приватный ключ репозитория на веб-сервере с правом чтения** → компрометация всей цепочки поставки пакетов. Правильно: отдельный подписывающий узел, офлайн-ключ, ротация.

### Безопасность

В боевой среде нельзя: запускать репозиторий по HTTP без подписи метаданных; держать в `trusted.gpg.d` ключи «на всякий случай»; раздавать пакеты из непроверенных источников (в том числе «сборки с форумов»); отключать `needrestart`-контроль; ставить обновления без записи, кто и когда это сделал. Для ГИС добавь требование приказа ФСТЭК России № 17 о своевременной установке обновлений безопасности и сверку с БДУ ФСТЭК — это то, что спросят на аудите.

## 7. Вопросы на собеседовании

**1. Чем pull-through кэш отличается от локального зеркала и что вы выберете для 50 серверов?**

Ответ: кэш (apt-cacher-ng, Nexus, Pulp с remote) прозрачно проксирует и наполняется по требованию — экономит канал, но состав версий не контролирует: что вендор выложил, то и прилетит. Зеркало (aptly, debmirror, `reposync`) — фиксированный набор версий, который обновляю я, с моей подписью и моим расписанием. Для 50 серверов обычно гибрид: кэш для всего «длинного хвоста» и зеркало для критичных компонентов, плюс unattended-upgrades только для security.

*Что хочет услышать:* понимание разницы «экономия трафика» vs «контроль версий», готовность к гибридной схеме.
*Красный флаг:* «поставлю apt-cacher-ng и на этом всё» без упоминания контроля версий и подписи.

**2. Как обеспечить доверие к внутреннему репозиторию?**

Ответ: метаданные подписываются GPG-ключом (`InRelease`/`repomd.xml.asc`), на клиентах ключ ставится в `/usr/share/keyrings` и привязывается через `Signed-By` (deb822) или `gpgkey=` + `repo_gpgcheck=1` (RPM). Приватный ключ — не на веб-сервере: отдельный подписывающий узел или офлайн-ключ, ротация, срок действия. Плюс pinning, чтобы версии не подменялись источником с более высоким приоритетом.

*Что хочет услышать:* цепочку «ключ → подпись метаданных → хэши пакетов» и разделение публичной/приватной части.
*Красный флаг:* «положу ключ в `trusted.gpg.d`, там же удобнее» — это доверие всем репозиториям сразу.

**3. Как выстроите процесс управления патчами в компании на 50 серверов?**

Ответ: инвентаризация (какие ОС, какие версии, кто владелец) → классификация (security/bugfix/feature, CVSS, БДУ ФСТЭК) → пилот на 2–3 ВМ и проверка приложений → окна обслуживания и волны (сначала Dev, потом внутренние сервисы, потом прод) → откат (снапшот, `apt install pkg=версия`, `dnf history undo`, etckeeper) → отчётность и метрика «просроченные security-обновления». Регламент письменный, с ответственными и SLA по критичности.

*Что хочет услышать:* процесс, а не команду; пилот, окна, откат, метрики, документ.
*Красный флаг:* «включу unattended-upgrades на всех и всё».

**4. Что такое Foreman/Katello, Content View и Lifecycle Environment и зачем это, если есть apt + Ansible?**

Ответ: Foreman — управление жизненным циклом хостов; Katello добавляет управление контентом и подписками (внутри — Pulp, Candlepin, Qpid). Content View — версионированный срез пакетов, Lifecycle Environment — цепочка окружений (Library → Dev → QA → Production). Хост подписывается на окружение и видит ровно те версии, которые туда продвинули. Это оправдано, когда серверов десятки-сотни, несколько площадок и требования по аудиту; на 10 машинах дешевле aptly + Ansible + Git.

*Что хочет услышать:* понимание, что Katello — про жизненный цикл контента и аудит, а не «обновлятор».
*Красный флаг:* путаница Pulp и Katello или утверждение, что Katello «заменяет Ansible».

**5. Как откатить неудачное обновление на 30 серверах?**

Ответ: до обновления — снапшот ВМ (PVE/VMware) и `etckeeper` для конфигов; после — по ситуации: `apt-get install pkg=предыдущая_версия` вплоть до точного пина, `dnf history undo`, восстановление из снапшота, если поехала база или ядро. Плюс приём «immutable/идемпотентная сборка»: пересобрать сервер из шаблона с зафиксированными версиями. И запись в `stand-log.md`/тикет, что именно откатили.

*Что хочет услышать:* подготовка до изменения + конкретные механизмы отката + понимание, что откат БД — отдельная история.
*Красный флаг:* «сделаю `apt-get install --reinstall` и всё пройдёт».
