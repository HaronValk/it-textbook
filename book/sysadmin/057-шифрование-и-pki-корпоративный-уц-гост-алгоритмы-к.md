# Шифрование и PKI: корпоративный УЦ, ГОСТ-алгоритмы, КриптоПро УЦ, сертификаты TLS

## 1. Введение (зачем это нужно в реальной работе)

Тикет в helpdesk «Вектора»:

> **Пользователь:** ivanov (бухгалтерия, WIN11-CL01)
> **Что написал:** «Открываю https://web01.corp.vektor.lab — браузер пишет "Подключение не защищено, сертификат недействителен". Раньше работало. Завтра сдавать отчётность, почините, пожалуйста.»
> **Срочность:** высокая

Дальше выясняется классика: на WEB01 кто-то переустановил nginx, взял самоподписанный сертификат «на пять минут», а сертификат от корпоративного УЦ остался лежать в `/root/backup`. Пользователь видит предупреждение, бухгалтерия нервничает, а вы полдня объясняете, почему «просто нажать "Всё равно перейти"» — не решение.

Шифрование и PKI (Public Key Infrastructure, инфраструктура открытых ключей) — это тема, которая в работе сисадбина всплывает постоянно: HTTPS на внутреннем портале, RDP с TLS, LDAPS для контроллеров домена, Wi-Fi 802.1X, VPN, почта, 1С с защищённым соединением, электронная подпись для отчётности, ГОСТ-TLS для взаимодействия с госсистемами. Везде одна и та же логика: есть ключи, есть кто-то, кто подтверждает их подлинность, и есть сроки, которые кто-то должен продлевать.

После этой главы вы будете уметь: поднять корпоративный удостоверяющий центр (УЦ, он же CA — Certificate Authority) на AD CS, выпустить через него сертификат для Linux-сервера, настроить автоматическую выдачу сертификатов доменным машинам, проверить TLS-соединение снаружи, отозвать скомпрометированный сертификат и объяснить заказчику, чем ГОСТ-криптография отличается от RSA и почему под неё нужен отдельный криптопровайдер.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Симметрика и асимметрика.** Симметричное шифрование (AES, «Кузнечик», «Магма») — быстрое, но требует, чтобы обе стороны уже имели общий ключ. Асимметричное (RSA, ECDSA, ГОСТ Р 34.10-2012) — медленное, зато решает проблему обмена ключами. TLS использует гибридную схему: асимметрикой стороны договариваются о сессионном ключе, дальше трафик шифруется симметрикой.

**Что такое сертификат X.509.** Это структура данных с полями:

- `Subject` — кому выдан (CN, O, OU);
- `Issuer` — кто выдал (имя CA);
- `Public Key` — открытый ключ владельца;
- `Validity` — `NotBefore`/`NotAfter`;
- `KeyUsage` / `ExtendedKeyUsage (EKU)` — что сертификатом разрешено делать (serverAuth, clientAuth, подпись кода);
- `Subject Alternative Name (SAN)` — список имён (DNS/IP), по которым сертификат валиден. Современные браузеры смотрят **только на SAN**, CN игнорируют;
- `Serial Number`, `CRL Distribution Points`, `Authority Information Access (AIA)` — где взять список отзыва и сертификат издателя;
- `Signature` — подпись CA.

**Цепочка доверия.** Клиент доверяет не сертификату сайта, а корневому сертификату в своём хранилище. Между ними может быть промежуточный (issuing) CA.

```text
                 [ Root CA «VEKTOR-RootCA» ]
                 самоподписан, лежит в Trusted Root
                 ключ в идеале offline / на HSM
                              |
                              | подписывает
                              v
                 [ Issuing CA (выдающий) ]
                 выпускает конечные сертификаты,
                 публикует CRL
                    |                    |
        подписывает |                    | подписывает
                    v                    v
        [web01.corp.vektor.lab]   [WIN11-CL01 (клиент)]
         EKU: serverAuth            EKU: clientAuth

  Проверка на клиенте: цепочка -> срок -> SAN/имя -> EKU -> отзыв (CRL/OCSP)
```

**Кто есть кто в PKI.** CA (выдаёт), RA (Registration Authority — проверяет заявку), VA (Validation Authority — отвечает на запросы статуса), политики и шаблоны (кто и на что имеет право подать заявку), CRL (Certificate Revocation List — подписанный список отозванных серийников, обновляется по расписанию) и OCSP (онлайн-проверка статуса одного сертификата). Плюс ACME — автоматический протокол выпуска (Let's Encrypt, step-ca, внутренние ACME-шлюзы к AD CS).

**Где это в модели OSI и в ОС.** TLS живёт на уровне представления/сеанса (L5–L6) поверх TCP (обычно 443). Сама криптография — в ОС и железе: на Windows это CSP/KSP (Cryptographic Service Provider / Key Storage Provider), на Linux — OpenSSL с провайдерами/engine, на серверах — HSM (аппаратный модуль хранения ключей). В AD PKI встроена через: хранилища сертификатов (`LocalMachine\My`, `Root`, `NTAuth`), групповые политики авто-enrollment и шаблоны сертификатов в AD.

**Windows AD CS: два режима.** *Enterprise CA* интегрирован с AD: шаблоны хранятся в каталоге, есть авто-enrollment через GPO, аутентификация по домену. *Standalone CA* работает без AD и выдаёт вручную — так обычно делают offline-корень. В продакшене правильная схема: offline Root CA + один-два Enterprise Issuing CA, ключи на HSM, CA не на контроллере домена.

**ГОСТ-криптография.** Российские стандарты: ГОСТ Р 34.10-2012 (электронная подпись), ГОСТ Р 34.11-2012 «Стрибог» (хэш), ГОСТ Р 34.12-2015 («Магма» 64 бита, «Кузнечик» 128 бит), ГОСТ Р 34.13-2015 (режимы). Чтобы применять их в TLS/X.509, нужен криптопровайдер: коммерческий «КриптоПро CSP» (и «КриптоПро УЦ» для выпуска сертификатов) либо свободный `gost-engine` для OpenSSL. OID алгоритмов в сертификатах: ГОСТ Р 34.10-2012/256 — `1.2.643.7.1.1.1.1`, /512 — `1.2.643.7.1.1.1.2`, Стрибог-256 — `1.2.643.7.1.1.2.2`, Стрибог-512 — `1.2.643.7.1.1.2.3` `[ПРОВЕРИТЬ по актуальному справочнику OID]`. ГОСТ-TLS описан в RFC (4357, 4491, 7836, 8645, 9215, 9367 — номера сверяйте на rfc-editor.org) `[ПРОВЕРИТЬ]`.

Ключевой практический нюанс: обычный Chrome/Firefox ГОСТ-TLS **не умеет**. Для ГОСТ-сайтов нужен либо браузер с поддержкой ГОСТ-шифров и установленный «КриптоПро CSP», либо доступ через шлюз, терминирующий ГОСТ и отдающий наружу обычный TLS. Именно поэтому в госсегменте часто ставят «КриптоПро» на рабочие места централизованно.

**Сроки жизни сертификатов.** Публичные сертификаты последовательно сокращают: по требованиям CA/Browser Forum максимум уменьшается поэтапно (200 дней с 2026 года, 100 с 2027, 47 с 2029) `[ПРОВЕРИТЬ актуальные даты]`. Вывод для админа: ручное продление не масштабируется, нужна инвентаризация и автоматика.

## 3. Аналогия из жизни

PKI — это паспортная система. Корневой CA — МВД: его печать знают все, а сам он себя удостоверяет (самоподписанный корень). Выдающий CA — паспортный стол района: он не придумывает доверие, а действует по доверенности МВД. Сертификат — паспорт: там фото (открытый ключ), ФИО (Subject/SAN), срок действия и серия (serial), а подпись начальника отдела (подпись CA) подтверждает, что паспорт настоящий. CRL — список украденных и аннулированных паспортов, который регулярно обновляют; OCSP — звонок в паспортный стол с вопросом «этот паспорт ещё действителен?». Клиент — пограничник: он не звонит в МВД, он смотрит, есть ли у паспорта правильная печать и не истёк ли срок.

Аналогия перестаёт работать в одном месте: паспорт нельзя «скопировать», а приватный ключ — можно, если он лежит в открытом виде на сервере, поэтому в PKI компрометация ключа означает отзыв, а не «перевыпуск по заявлению».

## 4. Практика и команды

**1. Посмотреть конфигурацию CA (Windows, DC01).**

```powershell
certutil -CAInfo
certutil -getconfig
```

`-CAInfo` показывает имя CA, тип (Enterprise Root), срок действия сертификата CA, хранилище ключа. `-getconfig` печатает строку конфигурации вида `DC01.corp.vektor.lab\VEKTOR-RootCA` — она нужна для `certreq`. Смотреть: не истекает ли сертификат CA (это катастрофа, а не инцидент) и где лежит ключ.

**2. Опубликовать CRL и посмотреть выпущенные сертификаты.**

```powershell
certutil -crl
certutil -view -restrict "Disposition=20" -out "RequestID,SerialNumber,CommonName,NotAfter"
```

`-crl` публикует новый список отзыва (в лабе — по кнопке, в бою — по расписанию). `Disposition=20` — «выдан». Команда даёт инвентаризацию: что выпущено и когда истекает.

**3. Отозвать сертификат.**

```powershell
certutil -revoke 3a1f...c2 1
certutil -crl
```

Второй аргумент — код причины (1 = keyCompromise). После отзыва обязательно публикуется CRL, иначе клиенты ничего не узнают.

**4. Запустить авто-enrollment на клиенте (WIN11-CL01).**

```powershell
certutil -pulse
Get-ChildItem Cert:\LocalMachine\My | Format-List Subject, NotAfter, Thumbprint
```

`-pulse` заставляет службу Certificate Services Client перечитать GPO и подать заявки по шаблонам. Второй командой проверяем, что сертификат появился в личном хранилище машины.

**5. Проверить, доверяет ли клиент корню.**

```powershell
Get-ChildItem Cert:\LocalMachine\Root | Where-Object {$_.Subject -like "*VEKTOR*"} |
    Format-List Subject, NotAfter, Thumbprint
```

Если корня нет — любая цепочка от вашего CA для клиента недействительна. Отсюда 90% жалоб «сертификат недействителен» на новых машинах.

**6. Сгенерировать ключ и CSR на Linux (UBU01/WEB01).**

```bash
sudo openssl req -new -newkey rsa:3072 -nodes \
  -keyout /etc/nginx/ssl/web01.key \
  -out /root/web01.csr \
  -subj "/C=RU/O=Vektor/CN=web01.corp.vektor.lab" \
  -addext "subjectAltName=DNS:web01.corp.vektor.lab,DNS:web01"
```

`-nodes` — не шифровать приватный ключ паролем (в бою так делать нельзя без защиты файла/HSM). `-addext` добавляет SAN — без него браузер откажется. CSR (Certificate Signing Request) содержит открытый ключ и запрошенные имена, приватный ключ остаётся на сервере.

**7. Отправить CSR в AD CS (DC01).**

```powershell
certreq -submit -config "DC01.corp.vektor.lab\VEKTOR-RootCA" `
  -attrib "CertificateTemplate:VektorWebServer" C:\Temp\web01.csr C:\Temp\web01.cer
```

`-attrib` задаёт шаблон; для этого шаблон должен разрешать subject/SAN из запроса. В бою такое разрешение — предмет строгого контроля: иначе любой, у кого есть право Enroll, выпустит сертификат на чужое имя.

**8. Разобрать сертификат.**

```bash
openssl x509 -in web01.pem -noout -text
openssl x509 -in web01.pem -noout -subject -issuer -dates -ext subjectAltName
```

Смотрим SAN (совпадает с именем в URL), `Not After`, `Extended Key Usage: TLS Web Server Authentication`, AIA/CRL URL (доступны ли они из DMZ).

**9. Проверить цепочку локально.**

```bash
openssl verify -CAfile /etc/ssl/certs/vektor-root.crt web01-fullchain.pem
# web01-fullchain.pem: OK
```

Если «unable to get local issuer certificate» — в файле нет промежуточного сертификата. Типовая ошибка: отдать nginx только leaf.

**10. Проверить боевой TLS снаружи.**

```bash
openssl s_client -connect 10.10.20.10:443 -servername web01.corp.vektor.lab \
  -CAfile /etc/ssl/certs/vektor-root.crt -verify_return_error </dev/null
```

Ключевое в выводе: `Verify return code: 0 (ok)` и строка `subject=` с нужным именем. `-servername` обязателен при SNI, иначе сервер отдаст не тот сертификат.

**11. Проверить доступность AIA/CRL (Windows).**

```powershell
certutil -verify -urlfetch C:\Temp\web01.cer
```

Команда скачивает CRL и цепочку по URL из сертификата. Частая беда: CRL-точка указывает на `http://dc01/…`, а из DMZ этот адрес не резолвится — клиенты в DMZ не могут проверить отзыв.

**12. ГОСТ: ключ и хэш через gost-engine (UBU01).**

```bash
sudo apt install -y libengine-gost-openssl        # имя пакета уточнить [ПРОВЕРИТЬ]
openssl genpkey -algorithm gost2012_256 -pkeyopt paramset:A -out gost-key.pem
openssl req -new -x509 -key gost-key.pem -md_gost12_256 -days 365 \
  -subj "/CN=ubu01.corp.vektor.lab" -out gost-cert.pem
openssl dgst -md_gost12_256 /etc/hostname
```

`paramset:A` — параметры кривой из ТК26. `-md_gost12_256` — Стрибог-256. Проверяем, что подпись и хэш читаются `openssl x509 -text`: в поле `Signature Algorithm` будет ` GOST R 34.10-2012`.

**13. Конфиг nginx с полной цепочкой.**

```nginx
server {
    listen 443 ssl;
    server_name web01.corp.vektor.lab;
    ssl_certificate     /etc/nginx/ssl/web01-fullchain.pem;   # leaf + issuing
    ssl_certificate_key /etc/nginx/ssl/web01.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_prefer_server_ciphers on;
    root /var/www/html;
}
```

`nginx -t` → `systemctl reload nginx`. Полная цепочка снимает половину проблем с проверкой.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

- DC01 (10.10.10.10) — AD DS, DNS, DHCP, домен `corp.vektor.lab`, вы `VEKTOR\adm.student`.
- DC02 (10.10.10.11) — второй контроллер (L2), пригодится как «второй взгляд» на AD.
- WIN11-CL01 — доменный клиент, получает адрес по DHCP.
- WEB01 (10.10.20.10, DMZ, nginx из L2) и GW01 маршрутизатор — маршрут из офисной сети в DMZ уже настроен в L2. Если нет — тестируйте TLS с UBU01 (10.10.10.30) или локально на WEB01.
- UBU01 — Ubuntu 24.04, есть sudo и доступ в интернет через NAT.
- Замечание по безопасности: в лабе мы ставим Enterprise Root CA **на контроллер домена**. В продакшене так не делают: корневой CA должен быть offline, выдающий — на отдельном сервере, ключи — на HSM. Это осознанное упрощение.

### Снапшот

В VMware Workstation на каждой затрагиваемой ВМ: `VM → Snapshot → Take Snapshot`, имя `before-sysadmin-057`. Машины: **DC01, WEB01, UBU01, WIN11-CL01**.

### Шаги

1. **DC01.** Установить роль:

   ```powershell
   Install-WindowsFeature ADCS-Cert-Authority -IncludeManagementTools
   ```
   Ожидаемо: `Success Restart Needed: No`.

2. **DC01.** Развернуть Enterprise Root CA:

   ```powershell
   Install-AdcsCertificationAuthority -CAType EnterpriseRootCA `
     -CACommonName "VEKTOR-RootCA" `
     -CryptoProviderName "RSA#Microsoft Software Key Storage Provider" `
     -KeyLength 4096 -HashAlgorithmName SHA384 `
     -ValidityPeriodYears 15 -Force
   ```
   Ожидаемо: `Certification authority was configured successfully`. Появится предупреждение, что CA установлен на контроллере домена — это нормально для лабы.

3. **DC01.** Проверить CA и опубликовать CRL: `certutil -CAInfo`, затем `certutil -crl`. Ожидаемо: имя `VEKTOR-RootCA`, тип `Enterprise Root`, CRL опубликован, в `C:\Windows\System32\CertLog` есть база.

4. **DC01.** Создать шаблон: `certsrv.msc` → правый клик `Certificate Templates` → `Manage` → дублировать `Web Server` → имя `VektorWebServer` → вкладка `Subject Name`: `Supply in the request` → `Security`: право `Enroll` и `Read` для `Domain Computers` → сохранить. Затем в `certsrv.msc` → `Certificate Templates` → `New` → `Certificate Template to Issue` → `VektorWebServer`. Ожидаемо: шаблон появился в списке.

   > В реальной среде «Supply in the request» без RA-approval = дыра: любой доменный пользователь выпустит сертификат на любое имя. В бою — либо `Build from AD information`, либо менеджер одобрения заявок.

5. **DC01.** Добавить DNS-запись для WEB01:

   ```powershell
   Add-DnsServerResourceRecordA -Name web01 -ZoneName corp.vektor.lab -IPv4Address 10.10.20.10
   Resolve-DnsName web01.corp.vektor.lab
   ```
   Ожидаемо: резолвится в 10.10.20.10.

6. **WEB01.** Сгенерировать ключ и CSR (команда из п.4.6, файлы в `/etc/nginx/ssl/` и `/root/web01.csr`). Ожидаемо: два файла, в CSR видно `Subject: C=RU, O=Vektor, CN=web01.corp.vektor.lab`.

7. **DC01.** Скопировать CSR (через `scp` на DC01 не выйдет — проще `scp` с WEB01 на FS01 и оттуда; либо создать общий ресурс). Отправить заявку: `certreq -submit -config "DC01.corp.vektor.lab\VEKTOR-RootCA" -attrib "CertificateTemplate:VektorWebServer" C:\Temp\web01.csr C:\Temp\web01.cer`. Ожидаемо: `RequestId`, `Disposition: Issued`.

8. **DC01.** Выгрузить корневой сертификат и перекинуть на WEB01:

   ```powershell
   certutil -ca.cert C:\Temp\vektor-root.cer
   ```
   На WEB01: `openssl x509 -inform DER -in vektor-root.cer -out /etc/ssl/certs/vektor-root.crt` и `openssl x509 -inform DER -in web01.cer -out /etc/nginx/ssl/web01.pem`.

9. **WEB01.** Собрать полную цепочку и включить TLS: `cat web01.pem vektor-root.crt > web01-fullchain.pem`, прописать конфиг nginx из п.4.13, выполнить `nginx -t && systemctl reload nginx`. Ожидаемо: `syntax is ok`, `test is successful`.

10. **UBU01.** Проверить TLS:

    ```bash
    openssl s_client -connect 10.10.20.10:443 -servername web01.corp.vektor.lab \
      -CAfile /etc/ssl/certs/vektor-root.crt -verify_return_error </dev/null
    ```
    Ожидаемо: `Verify return code: 0 (ok)`.

11. **DC01.** Включить авто-enrollment: `gpmc.msc` → политика на OU `Компьютеры` (или Default Domain Policy) → `Computer Configuration → Policies → Windows Settings → Security Settings → Public Key Policies → Certificate Services Client - Auto-Enrollment` → `Enabled`, галочки `Renew expired certificates…`, `Update certificates…`. На WIN11-CL01: `gpupdate /force`, `certutil -pulse`, затем `Get-ChildItem Cert:\LocalMachine\Root` — корень `VEKTOR-RootCA` на месте.

12. **UBU01.** ГОСТ-часть: установить `gost-engine`, сгенерировать ключ и самоподписанный сертификат по ГОСТ Р 34.10-2012, посчитать хэш Стрибог (команды п.4.12). Ожидаемо: `openssl x509 -text` показывает `Signature Algorithm: GOST R 34.10-2012`.

13. **DC01.** Проверить отзыв: `certutil -view -restrict "Disposition=20" -out "SerialNumber,CommonName"`, отозвать серийник тестового сертификата `certutil -revoke <serial> 1`, опубликовать CRL `certutil -crl`. Ожидаемо: `certutil -view` показывает `Disposition: 21 (Revoked)` `[ПРОВЕРИТЬ номер]`.

### Проверка

- [ ] `certutil -CAInfo` на DC01 показывает `VEKTOR-RootCA`, тип Enterprise Root.
- [ ] `Resolve-DnsName web01.corp.vektor.lab` возвращает 10.10.20.10.
- [ ] `openssl s_client -verify_return_error` даёт `Verify return code: 0 (ok)`.
- [ ] `openssl x509 -noout -ext subjectAltName` содержит `web01.corp.vektor.lab`.
- [ ] На WIN11-CL01 в `Cert:\LocalMachine\Root` есть `VEKTOR-RootCA`.


**Диагностика по порядку.**
1. С UBU01: `openssl s_client -connect 10.10.20.10:443 -servername web01.corp.vektor.lab -CAfile /etc/ssl/certs/vektor-root.crt` → `Verify return code: 10 (certificate has expired)`.

**Решение.**

```bash
sudo timedatectl set-ntp true
sudo systemctl restart systemd-timesyncd

```

Если NTP недоступен из DMZ (частая история) — разрешить исходящий UDP/123 на GW01 или настроить внутренний источник времени. После синхронизации `openssl s_client` снова даёт `0 (ok)`, перезапуск nginx не требуется.

## 6. Ошибки новичков и безопасность

1. **Самоподписанный сертификат в продакшене** → пользователи тренируются игнорировать предупреждения браузера, это прямой путь к успешному фишингу. Правильно: внутренний CA + распространение корня через GPO, для публичных сайтов — ACME.
2. **Корневой CA на боевом сервере с сетевым доступом** → компрометация корня обнуляет всю PKI: злоумышленник выпустит валидный сертификат на любой домен. Правильно: offline root (или HSM), выдающий CA — отдельно, ключи под M-of-N.
3. **Отдать nginx только leaf-сертификат** → часть клиентов не строит цепочку. Правильно: fullchain, а корень — в хранилище клиента, не в цепочке сервера (лишний корень в цепочке — плохая практика).
4. **Забыть про CRL/AIA, доступные из DMZ** → клиенты не проверяют отзыв, а в строгом режиме — падают. Правильно: публиковать CRL на адресе, доступном из всех сегментов, или отдавать OCSP.
5. **Шаблон «Supply in the request» + Enroll для Domain Users** → любой сотрудник выпускает сертификат на имя `dc01.corp.vektor.lab`. Правильно: ограниченные права, менеджер одобрения, журналирование заявок.
6. **Приватный ключ с правами 644** → любой локальный пользователь читает ключ TLS. Правильно: `chmod 600`, отдельный пользователь, HSM для критичного.
7. **Ручное продление без инвентаризации** → «внезапно истёк» в пятницу вечером. Правильно: реестр сертификатов, мониторинг `NotAfter` (Zabbix «not after» item), календарные напоминания за 30/14/7 дней, автообновление.
8. **Считать, что ГОСТ «просто работает» везде** → Chrome не откроет ГОСТ-TLS, часть ПО не поддерживает ГОСТ-сертификаты. Правильно: проверять совместимость заранее, тестировать на стенде, держать план Б (шлюз-терминатор).

**Безопасность.** В лабе мы поставили CA на контроллер домена, разрешили subject из запроса и использовали незашифрованный приватный ключ (`-nodes`). В боевой среде каждое из этих действий — находка аудитора: CA отделяют, ключи хранят на HSM, шаблоны ограничивают, а все операции с CA логируют и периодически проверяют (кто выпускал, что выпускал, кто имеет право Enroll). Отдельно: сертификаты для электронной подписи по 63-ФЗ выпускают аккредитованные УЦ (сейчас это в основном УЦ ФНС, Банка России, Казначейства и доверенные лица) `[ПРОВЕРИТЬ актуальный перечень]` — самодельный УЦ для сдачи отчётности не подойдёт.

## 7. Вопросы на собеседовании

**1. Что именно проверяет клиент, когда устанавливает TLS-соединение?**

Ответ: строит цепочку от серверного сертификата до доверенного корня в своём хранилище; проверяет подписи на каждом звене, сроки действия всех сертификатов, совпадение имени из URL с SAN (CN устарел), назначение ключа (EKU serverAuth), корректность использования ключа (KeyUsage), статус отзыва через CRL/OCSP, а для публичных сайтов — ещё и ограничения CA/B Forum (срок жизни, алгоритмы). Дальше проверяет, что сервер владеет приватным ключом (подпись в handshake).
*Что хочет услышать интервьюер:* что вы понимаете цепочку, SAN и отзыв, а не «браузер ругается — надо нажать "продолжить"».
*Красный флаг:* «проверяется только срок действия» или «TLS шифрует, сертификат для красоты».

**2. Как бы вы построили корпоративный УЦ с нуля для 500 машин?**

Ответ: offline Root CA (standalone, ключ на HSM или на изолированной ВМ, включён только на время подписи), один-два Enterprise Issuing CA в домене, публикация CRL/AIA на внутреннем веб-сервере с высокой доступностью, шаблоны по назначению (serverAuth для серверов, clientAuth для 802.1X/VPN), авто-enrollment через GPO, регламент: кто имеет право Enroll, как оформляется заявка, как ротируются ключи, где хранится резервная копия CA с ключом и паролем (в сейфе, M-of-N), мониторинг CRL и сроков. Для Linux/сетевого оборудования — либо тот же AD CS через CSR, либо отдельный внутренний CA (step-ca) с ACME, чтобы не плодить ручные процессы.
*Что хочет услышать:* разделение ролей, защита ключа, автоматизация и регламент.
*Красный флаг:* «поставлю AD CS на контроллер домена и всё».

**3. Чем ГОСТ-TLS отличается от обычного и с какими проблемами столкнётесь?**

Ответ: другой набор алгоритмов — ГОСТ Р 34.10-2012 для подписи и обмена, ГОСТ Р 34.11-2012 (Стрибог) для хэша, «Кузнечик»/«Магма» для симметрики, свои OID в X.509 и свои наборы шифров в TLS. Для работы нужен сертифицированный криптопровайдер («КриптоПро CSP») на клиенте и сервере, а браузеры на Chromium/Firefox ГОСТ-TLS не поддерживают — либо специализированный браузер с ГОСТ-поддержкой, либо шлюз, который терминирует ГОСТ внутри и отдаёт обычный TLS наружу. Проблемы: совместимость, стоимость лицензий, аттестация, сложность автоматизации (ACME с ГОСТ практически не встречается), отдельный УЦ («КриптоПро УЦ») `[ПРОВЕРИТЬ актуальную версию продукта]`. Плюс требования регулятора: если работаете с госсистемами или персданными в определённых контурах, ГОСТ — не прихоть, а требование.
*Что хочет услышать:* понимание, что ГОСТ — это про совместимость и сертификацию, а не «ещё одна галочка».
*Красный флаг:* «просто поставлю openssl и всё заработает».

**4. Что делать, если CRL не обновляется или недоступен?**

Ответ: сначала определить режим проверки. Windows по умолчанию использует soft-fail для CRL, часть приложений — hard-fail (например, строгая проверка в .NET, Java keystore). Диагностика: `certutil -verify -urlfetch` на Windows, `openssl verify -crl_check` на Linux — они покажут, какой URL не открывается. Частые причины: истёк срок CRL (по умолчанию публикуется раз в неделю), URL указывает на внутреннее имя, недоступное из сегмента, либо веб-сервер публикации лежит. Лечение: срочно опубликовать CRL, сделать точку публикации доступной из всех зон, поднять срок публикации/мониторинг, а на клиентах — кэш (`CryptnetUrlCache`), который надо очистить. В перспективе — OCSP с fallback на CRL.
*Что хочет услышать:* порядок диагностики и понимание soft/hard-fail.
*Красный флаг:* «отключу проверку отзыва» без оговорок.

**5. Сертификат на балансировщике истекает через неделю, автоматики нет. Ваши действия?**

Ответ: сегодня — продлить вручную (выпустить новый, положить с полной цепочкой, перечитать конфиг без простоя: сначала добавить новый сертификат рядом и переключить, потом проверить `openssl s_client` с внешней точки и изнутри, потом отозвать старый при необходимости). Дальше — системно: завести реестр всех сертификатов (где лежит, кто владелец, дата, как обновляется), включить мониторинг `NotAfter` с алертами за 30/14/7/1 день, перевести на ACME/автообновление, где возможно, и описать runbook «истекает сертификат» с проверкой: цепочка, SAN, reload без downtime, откат. Для внутренних сервисов — шаблоны AD CS с авто-enrollment.
*Что хочет услышать:* срочное решение + устранение корневой причины + мониторинг.
*Красный флаг:* «продлю, когда истечёт».
