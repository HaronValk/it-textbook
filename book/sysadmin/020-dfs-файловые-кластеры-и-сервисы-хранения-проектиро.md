## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Два независимых механизма, которые постоянно путают.**

*DFS Namespaces (DFS-N)* — это **служба referral**, то есть «справочная». Клиент открывает `\\corp.vektor.lab\Shares\Buh`, обращается к контроллеру домена (LDAP 389/636, Kerberos 88) и получает **referral** — список серверов-целей с порядком обхода. Дальше клиент идёт напрямую по SMB (TCP 445) на первую доступную цель. Метаданные доменного неймспейса хранятся в AD (объекты в разделе домена, `System\Dfs-Configuration`), поэтому неймспейс переживает падение любого сервера. DFS-N **не хранит данные и не даёт отказоустойчивости сам по себе** — он даёт стабильное имя и переключение между целями.

*DFS Replication (DFS-R)* — **движок репликации** файлов между серверами. Работает так: сервер читает USN-journal тома, складывает изменения в **staging**-папку, сжимает и передаёт партнёру по RPC (динамические порты, инициируется из SMB-канала), партнёр распаковывает и применяет. Используется **RDC** (Remote Differential Compression) — передаются только изменённые блоки файла, что критично для WAN. Конфликты решаются по принципу «побеждает последняя запись», проигравшая версия уезжает в скрытую папку `DfsrPrivate\ConflictAndDeleted`. DFS-R **не реплицирует открытые файлы** — файл попадает в репликацию после закрытия дескриптора. И DFS-R не предназначен для баз 1С, PST и прочих «живых» файлов с блокировками.

**Файловый кластер** — другой подход: два узла (FS01, FS02) + **общий диск** (LUN по iSCSI, TCP 3260, или SAS/FC). Ресурс «File Server» с сетевым именем и IP живёт на одном узле; при отказе узел-партнёр подхватывает диск и имя. Для Hyper-V/SQL используют **Scale-Out File Server (SOFS)** на CSV с **SMB Transparent Failover** — клиент переподключается к другому узлу без потери хендла, шара помечается *continuously available*. Для обычных пользовательских шар SOFS избыточен: берут «File Server for general use» или вообще DFS.

```text
                 \\corp.vektor.lab\Shares\Buh
                            |
                   [ AD: referral ]
                    /            \
        referral #1            referral #2
            |                       |
        +---------+             +---------+
        |  FS01   |<-- DFS-R --->|  FS02   |   (репликация D:\Buh)
        | 10.10.10.20           10.10.10.21
        +---------+             +---------+
             |                       |
        NTFS + SMB 445          NTFS + SMB 445
             \_______________________/
                        |
              аудит: SACL -> Security.evtx (4663, 5145)
                        |
                 SIEM / Event Forwarding
```

**Где что лежит по слоям:** SMB — прикладной уровень (L7) поверх TCP 445; DFS-N — служба каталога + клиентский редиректор; DFS-R — приложение поверх RPC; iSCSI — L7 поверх TCP 3260; NTFS-права (DACL) — уровень ФС; аудит (SACL) — тоже уровень ФС, но события пишет диспетчер безопасности ядра.

**Сервисы хранения вокруг этого:** DAS/NAS/SAN, Storage Spaces (mirror/parity), ReFS vs NTFS (ReFS даёт integrity streams и быстрее на больших томах, но не поддерживает дедупликацию и часть квот FSRM — проверяй под задачу `[ПРОВЕРИТЬ]`), Data Deduplication (экономия на файлопомойках), VSS (теневые копии → «Предыдущие версии»), FSRM (квоты, экраны файлов, отчёты), Storage Replica (блочная репликация томов, редакция Datacenter `[ПРОВЕРИТЬ]`).

**Аудит доступа.** Права (DACL) отвечают «можно/нельзя», аудит (SACL) — «записать в журнал факт попытки». Чтобы события появились, нужны **три условия**: включена подкатегория аудита (`Object Access` → `File System`, `File Share`, `Detailed File Share`), на объекте стоит SACL, и журнал Security имеет достаточный размер. Ключевые события: **4663** — попытка доступа к объекту (файл/папка), **4656** — запрошен хендл, **5140/5145** — доступ к сетевой шаре и детальная проверка прав на шаре. В РФ это прямо востребовано: 152-ФЗ и приказ ФСТЭК №17 требуют регистрации событий безопасности, и «мы не логируем доступ к папке с персданными» — это находка проверки `[ПРОВЕРИТЬ формулировки]`.

## 3. Аналогия из жизни

DFS-N — это **единый номер телефона приёмной** вместо личных мобильных сотрудников: звонишь всегда один и тот же номер, а диспетчер (referral от AD) говорит «сейчас звонок идёт на Петрова, он недоступен — на Сидорова». DFS-R — это **два секретаря с одинаковыми папками документов**: каждый ведёт свою копию и синхронизирует с коллегой; если оба одновременно правят один лист, побеждает тот, кто положил последним, а черновик второго уходит в ящик «разобранное». Файловый кластер — это **один сейф на рельсах между двумя кабинетами**: сейф физически один, просто при пожаре в первом кабинете его перекатывают во второй, и табличка на двери остаётся та же. Аудит доступа — **журнал вахтёра**: он не мешает входить, но фиксирует, кто, когда и в какую комнату заходил.

Аналогия ломается там, где DFS-R встречается с открытыми базами: секретари-то синхронизируются, но если один правит документ, пока другой его держит в руках, копии разъедутся — и «победа последнего» превратится в потерю данных.

## 4. Практика и команды

Устанавливаем роли (FS01 и FS02):

```powershell
Install-WindowsFeature FS-FileServer,FS-DFS-Namespace,FS-DFS-Replication,FS-Resource-Manager -IncludeManagementTools
Install-WindowsFeature RSAT-DFS-Mgmt-Con -Restart:$false
```

`FS-DFS-Namespace` — неймспейсы, `FS-DFS-Replication` — служба DFSR, `FS-Resource-Manager` — квоты/экраны, `RSAT-DFS-Mgmt-Con` — оснастка DFS Management. Проверка: `Get-WindowsFeature FS-DFS*`.

**1. Создание доменного неймспейса**

```powershell
New-DfsnRoot -Path "\\corp.vektor.lab\Shares" -TargetPath "\\FS01\Shares" -Type DomainV2
Get-DfsnRoot -Path "\\corp.vektor.lab\Shares" | Format-List Path,Type,EnableAccessBasedEnumeration,State
```

`DomainV2` — режим «Windows Server 2008+»: поддержка ABE, >5000 папок, кластеризуемые цели. Пример вывода: `Type : DomainV2`, `State : Online`. Смотрим `State` — если `Offline`, неймспейс не поднялся (нет шары-цели, DNS, права).

**2. Папки и цели**

```powershell
New-DfsnFolder -Path "\\corp.vektor.lab\Shares\Buh" -TargetPath "\\FS01\Buh"
New-DfsnFolderTarget -Path "\\corp.vektor.lab\Shares\Buh" -TargetPath "\\FS02\Buh"
Get-DfsnFolderTarget -Path "\\corp.vektor.lab\Shares\Buh" | ft Path,TargetPath,State
```

Порядок вывода целей = порядок обхода клиентом. `State` цели переключается `Online/Offline` через `Set-DfsnFolderTarget` (параметр состояния `[ПРОВЕРИТЬ]`) — это и есть «выключить сервер из раздачи» без удаления цели.

**3. Группа репликации**

```powershell
New-DfsReplicationGroup -GroupName "RG-Buh"
Add-DfsrMember -GroupName "RG-Buh" -ComputerName FS01,FS02
Add-DfsrConnection -GroupName "RG-Buh" -SourceComputerName FS01 -DestinationComputerName FS02
Add-DfsrConnection -GroupName "RG-Buh" -SourceComputerName FS02 -DestinationComputerName FS01
New-DfsReplicatedFolder -GroupName "RG-Buh" -FolderName "Buh"
```

`Add-DfsrConnection` создаёт **одно направление**; для двунаправленной репликации нужны две связи. `New-DfsReplicatedFolder` регистрирует имя реплицируемой папки — дальше ему назначают путь и staging (п. 4).

**4. Членство в группе и staging**

```powershell
Set-DfsrMembership -GroupName "RG-Buh" -FolderName "Buh" -ComputerName FS01 `
  -ContentPath D:\Buh -StagingPath D:\DfsrStaging -PrimaryMember $true
Set-DfsrMembership -GroupName "RG-Buh" -FolderName "Buh" -ComputerName FS02 `
  -ContentPath D:\Buh -StagingPath D:\DfsrStaging -PrimaryMember $false
Get-DfsrMembership -GroupName "RG-Buh" -ComputerName FS01 | ft ComputerName,FolderName,ContentPath,PrimaryMember,Enabled
```

`-PrimaryMember $true` назначается **на сервере с эталонными данными** — он источник начальной репликации. `StagingPath` держи на отдельном томе/каталоге, не внутри реплицируемой папки. Пример вывода: `PrimaryMember : True`, `Enabled : True`.

**5. Диагностика репликации**

```powershell
Get-DfsrState -ComputerName FS02 | ft ComputerName,Name,State
Get-DfsrBacklog -SourceComputerName FS01 -DestinationComputerName FS02 -RGName "RG-Buh" -RFName "Buh"
dfsrdiag PollAD /Member:FS02
```

`Get-DfsrState` — состояние по партнёрам (`Normal`, `Inbound/Outbound`), `Get-DfsrBacklog` — сколько файлов ещё не доехало (`Number of backlogged files: 0` — норма). `dfsrdiag PollAD` заставляет службу немедленно перечитать конфиг из AD, иначе можно ждать до 60 минут.

**6. Миграция данных robocopy (с сохранением ACL)**

```cmd
robocopy \\FS01\Buh D:\Buh /MIR /COPYALL /DCOPY:DAT /R:2 /W:2 /XD DfsrPrivate /LOG:D:\migrate-buh.log /TEE
```

`/MIR` — зеркало (удаляет в приёмнике то, чего нет в источнике — на первом прогоне это ок, на повторном будь осторожен), `/COPYALL` = `DATSOU` (данные, атрибуты, таймстампы, **ACL (S)**, владелец (O), аудит (U)), `/DCOPY:DAT` — то же для каталогов, `/R:2 /W:2` — не висеть на блокировках по 30 секунд, `/XD` — не тащить служебную папку DFSR. В логе смотреть `Ended :` и счётчики `Copied / Skipped / FAILED`.

**7. Шары, ABE и открытые файлы**

```powershell
New-SmbShare -Name Buh -Path D:\Buh -FullAccess "VEKTOR\adm.student" -ChangeAccess "VEKTOR\GG-Buh"
Set-SmbShare -Name Buh -FolderEnumerationMode AccessBased
Get-SmbOpenFile -CimSession FS01 | Select-Object Path,ClientUserName
Close-SmbOpenFile -CimSession FS01 -FileId 123456789 -Force
```

`-FolderEnumerationMode AccessBased` включает ABE: пользователь видит только те папки, на которые у него есть права (иначе «вижу, но не пускает» — вечная заявка). `Get-SmbOpenFile`/`Close-SmbOpenFile` — инструмент «перевоза на живую»: видно, кто держит файл; `-Force` рвёт хендл (пользователю это ломает сохранение — предупреждать обязательно!).

**8. Квоты FSRM**

```powershell
New-FsrmQuota -Path D:\Buh -Size 5GB -SoftLimit -Description "Buh: soft 5GB"
Get-FsrmQuota -Path D:\Buh | ft Path,Size,SoftLimit,Usage
```

`-SoftLimit` — только предупреждение, запись не блокируется; жёсткая квота — без `-SoftLimit`. `Usage` показывает текущий объём. Квоты удобнее вешать на папки пользователей, а не на общий корень.

**9. Политика аудита**

```cmd
auditpol /get /category:"Object Access"
auditpol /set /subcategory:"File System" /success:enable /failure:enable
auditpol /set /subcategory:"File Share" /success:enable /failure:enable
auditpol /set /subcategory:"Detailed File Share" /success:enable
```

Пример вывода: `File System    Success and Failure`, `Detailed File Share    Success`. В домене это делается **GPO**: `Computer Configuration → Policies → Windows Settings → Security Settings → Advanced Audit Policy Configuration → System Audit Policies → Object Access` — и линкуется на OU `Серверы` (не забудь `gpupdate /force` и `auditpol /get` на сервере для проверки).

**10. SACL на папку (PowerShell)**

```powershell
$acl  = Get-Acl D:\Buh
$rule = New-Object System.Security.AccessControl.FileSystemAuditRule(
  "VEKTOR\GG-Buh","WriteData,Delete,DeleteSubdirectoriesAndFiles",
  "ContainerInherit,ObjectInherit","None","Success,Failure")
$acl.AddAuditRule($rule)
Set-Acl D:\Buh $acl
(Get-Acl D:\Buh).Audit | ft IdentityReference,FileSystemRights,AuditFlags
```

`FileSystemAuditRule` — та же логика, что у `FileSystemAccessRule`, но пишет в SACL. Проверка — колонка `AuditFlags` (`Success, Failure`).

**11. Чтение событий**

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4663,5145} -MaxEvents 20 |
  Select-Object TimeCreated,Id,@{n='User';e={$_.Properties[1].Value}},@{n='Object';e={$_.Properties[6].Value}},@{n='Access';e={$_.Properties[9].Value}}
```

В 4663 смотрим «Имя объекта», «Учётная запись», «Тип доступа» (например `%%1537` = DELETE); в 5145 — доступ к шаре и запрошенные права. Позиции `Properties[N]` зависят от версии ОС `[ПРОВЕРИТЬ]` — надёжнее открывать событие в «Просмотре событий» и мапить поля глазами, а потом закреплять в скрипте/ SIEM.

**12. Кластерный путь (если нужна не DFS-репликация, а HA)**

```powershell
Install-WindowsFeature Failover-Clustering -IncludeManagementTools
Test-Cluster -Node FS01,FS02 -Include "Inventory","Network","Storage"
New-Cluster -Name FS-CL01 -Node FS01,FS02 -StaticAddress 10.10.10.22 -NoStorage
Add-ClusterFileServerRole -Name FS-CLU -Storage "Cluster Disk 1" -StaticAddress 10.10.10.23
Get-ClusterResource | ft Name,State,OwnerNode
```

`Test-Cluster` — валидация до создания (сеть, диски, конфигурация); `New-Cluster` без `-NoStorage` сразу забирает видимые общие LUN; `Add-ClusterFileServerRole` требует **кластерный диск** (`[ПРОВЕРИТЬ]` точный набор параметров в твоей сборке). `SOFS` — `Add-ClusterScaleOutFileServerRole -Name SOFS01` (нужны CSV).

**13. Теневые копии**

```cmd
vssadmin list shadows
vssadmin add shadowstorage /for=D: /on=D: /maxsize=20%
```

20% тома — типовой размер области хранения копий; выше — больше версий, но меньше места под данные. GUI: `Server Manager → File and Storage Services → Shares → правый клик на шаре → Configure Shadow Copies` `[ПРОВЕРИТЬ формулировку меню]`.

## 6. Ошибки новичков и безопасность

1. **Ждать от DFS-N отказоустойчивости.** → Неймспейс даёт только имя и referral; если за ним одна цель на FS01, падение FS01 = простой. → Нужны минимум две цели и репликация (или кластер).
2. **Реплицировать базы 1С/PST через DFS-R.** → Конфликты, «победа последнего», битые базы, потеря данных. → Базы 1С — только на сервере с СУБД и резервным копированием; DFS-R — для документов.
3. **Миграция без `/COPYALL`.** → Пользователи получают «Отказано в доступе» на часть файлов (ровно сценарий выше). → Всегда `/COPYALL /DCOPY:DAT`, а после копирования — дифф ACL и тестовый вход под реальным пользователем.
4. **Переключение трафика, пока файлы открыты.** → Часть записей уйдёт на старый сервер и потеряется при отключении. → `Get-SmbOpenFile`, закрытие в окно обслуживания, повторный прогон robocopy `/MIR` перед cutover.
5. **Staging на том же томе, что и данные, и его чистка руками.** → Замедление репликации, «залипшие» состояния. → Отдельный каталог/том, чистка только штатными средствами `[ПРОВЕРИТЬ]`.
6. **Включить аудит «на всё».** → Security.evtx переполняется за часы, события теряются, сервер начинает тормозить на записи. → Точечные SACL на критичные папки + пересылка событий (WEF) в SIEM/коллектор; отдельно контролировать размер журнала.
7. **Доверять «зелёному» состоянию без теста.** → «Репликация включена» ≠ «данные доехали». → `Get-DfsrBacklog` = 0, тестовый файл в обе стороны, периодический отчёт DFSR.
8. **Квоты и ABE включать после инцидента.** → Пользователи привыкли к «всё видно», а потом «папки исчезли» = шквал заявок. → ABE и квоты вводить с уведомлением заранее, писать в инструкции для сотрудников.

**Безопасность.** В боевой среде нельзя: держать шары с `Everyone:Full` или `Authenticated Users:Change` на корне (`\\FS01\Buh` — не место для «пусть все попробуют»); включать SMB1 ради старого сканера; давать доступ по `IP$`-шарам и скрытым `C$` вне админских задач; хранить теневые копии на том же LUN, что и сами данные (шифровальщик вычистит и копии); запускать аудит без защиты журнала (локальный админ удалит Security.evtx). В лабе мы спокойно включаем ABE и создаём SACL «на всех», потому что стенд учебный — в продакшене SACL на общий корень с `Success+Failure` по `ReadData` гарантированно утопит журнал и создаст нагрузку на диски.

## 7. Вопросы на собеседовании

**1. DFS-N и DFS-R — в чём разница и когда вы выберете файловый кластер вместо DFS?**

*Ответ:* DFS-N — служба пространства имён, хранит в AD список целей и выдаёт клиенту referral; она не хранит данные. DFS-R — движок репликации содержимого между серверами (USN journal, staging, RDC, ConflictAndDeleted), работает асинхронно и не для открытых/транзакционных файлов. Кластер выбирают, когда нужна **синхронная** отказоустойчивость одного и того же набора данных с общей СХД (нет «двух копий», нет конфликтов, единая точка правды, поддержка continuously available SMB для Hyper-V/SQL). DFS — когда серверы географически разнесены, нужен офлайн-доступ к локальной копии и допустима асинхронность.

*Что хочет услышать интервьюер:* понимание, что DFS ≠ HA и что кластер требует shared storage, а DFS — нет.

*Красный флаг:* «DFS-R синхронизирует мгновенно и подходит для баз данных».

**2. Как мигрировать файловый сервер без простоя и что делать с открытыми файлами?**

*Ответ:* ставим второй сервер → robocopy `/MIR /COPYALL /DCOPY:DAT` (предзаполнение) → включаем DFS-R и ждём `backlog = 0` → добавляем второй target в неймспейс → в окно обслуживания `Get-SmbOpenFile`, закрываем хендлы (с предупреждением пользователей), финальный `/MIR` → переключаем цель на новый сервер, старую — в `Offline` → неделя карантина, потом вывод старого. Открытые файлы либо ждут закрытия (DFS-R реплицирует после закрытия хендла), либо их принудительно закрывают в окно.

*Что хочет услышать интервьюер:* наличие cutover-плана, окна обслуживания, проверки ACL и обратного плана.

*Красный флаг:* «скопирую ночью и утром переключу» без упоминания прав, открытых файлов и отката.

**3. Как работает аудит доступа к файлам на Windows и какие события вы будете смотреть?**

*Ответ:* три слоя — подкатегории Advanced Audit Policy (`File System`, `File Share`, `Detailed File Share`) включаются GPO на OU серверов; на объекте ставится SACL (вкладка «Аудит» или `FileSystemAuditRule` + `Set-Acl`); события пишутся в Security: 4663 (доступ к объекту), 4656 (запрошен хендл), 5140/5145 (доступ к шаре / детальная проверка). Читаем `Get-WinEvent` с фильтром по ID или centralized через WEF в SIEM. Обязательно следим за размером журнала и не аудируем `ReadData` на общих корнях.

*Что хочет услышать интервьюер:* что аудит надо планировать заранее и что SACL — отдельная сущность от DACL.

*Красный флаг:* «включу "Аудит объектов" галочку в локальной политике и всё увижу» — без SACL событий не будет.

**4. Как DFS-R разрешает конфликты и что происходит с проигравшей версией?**

*Ответ:* побеждает последняя записанная версия (по времени изменения/приходу), проигравшая уходит в скрытую `DfsrPrivate\ConflictAndDeleted` и живёт там ограниченное время/до переполнения квоты (настраивается). Файлы, удалённые при репликации, тоже попадают в ConflictAndDeleted — это спасает от «зеркало удалило всё». Для больших файлов помогает RDC, для начальной заливки — preseed (robocopy до включения репликации), чтобы не гнать терабайты по WAN.

*Что хочет услышать интервьюер:* понимание асинхронности и того, что «last writer wins» — риск, а не фича.

*Красный флаг:* «конфликтов не бывает» или «DFS-R блокирует файл на втором сервере».

**5. Что такое continuously available share и SMB Transparent Failover?**

*Ответ:* это режим, при котором шара публикуется через Scale-Out File Server на CSV, а SMB3-клиент при отказе узла переподключается к другому узлу, сохраняя открытые хендлы (transparent failover). Нужны: SOFS-роль, CSV, SMB3, клиент с поддержкой (Windows Server 2012+/Windows 8+), корректные права кластера. Применяется для Hyper-V/ SQL/ файлов виртуалок, не для «домашней папки бухгалтера» — там достаточно DFS или обычного файлового кластера.

*Что хочет услышать интервьюер:* границы применимости и понимание, что это про SMB3 + CSV, а не про «магию кластера».

*Красный флаг:* путаница SOFS с DFS и утверждение, что transparent failover работает для любых шар без настройки.
