## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Миграция V2V (Virtual-to-Virtual) — это перенос виртуальной машины с одной платформы на другую. Технически работа идёт **по трём слоям одновременно**:

```text
СЛОЙ 1: Платформа      СЛОЙ 2: Формат ВМ        СЛОЙ 3: Гостевая ОС
ESXi / vCenter    →    .vmx + .vmdk (VMDK)  →   VMware Tools,
                                                  LSI Logic / PVSCSI,
                                                  e1000 / vmxnet3,
                                                  UEFI/BIOS
        │                     │                          │
        ▼                     ▼                          ▼
Proxmox VE          →   .conf + qcow2 (KVM)   →   qemu-guest-agent,
zVirt (KVM+oVirt)   →   OVF/OVA, libvirt XML  →   VirtIO SCSI + VirtIO net,
Базис (KVM)         →   qcow2/raw            →   AHCI + e1000e
Hyper-V             →   VHDX                 →   Integration Services
```

**Слой 2 — формат диска.** У VMware основной формат — `VMDK` (monolithicSparse, thin или thick). В KVM-мирах стандарт — `qcow2`. В Hyper-V — `VHDX`. Инструмент конвертации форматов — `qemu-img`, он понимает все три. Поэтому «переезд» на 80% — это `qemu-img convert` плюс коррекция конфига.

**Слой 3 — гостевая ОС.** Невидимая часть айсберга. Гостевая ОС знает, что живёт на «железе» LSI Logic + сетевая e1000 + VMware Tools. После переезда на VirtIO SCSI и VirtIO net она этих «железок» не находит — на Linux ядро обычно подцепит новые драйверы, на Windows можно получить **BSOD 0x7B (INACCESSIBLE_BOOT_DEVICE)** при старте. Поэтому Windows мигрируют либо с предустановленным `virtio-win`, либо сначала цепляют диск на эмулируемый SATA/IDE, потом ставят VirtIO и переключают.

**Слой 1 — платформа.** Все перечисленные в заголовке цели (кроме Hyper-V) построены на KVM, а три российских (zVirt, Базис, Скала-Р) — это коммерческая обёртка над KVM + управляющая панель (zVirt вырос из oVirt, Базис — KVM + Bacula-совместимая панель, Скала-Р — от Yadro). Proxmox — KVM + Debian + свои LXC/HA/Ceph. Поэтому с практической точки зрения `qemu-img`-конвертация и VirtIO-драйверы применимы почти ко всем целям, кроме Hyper-V (там своя ветка — VHDX и Integration Services).

**Сетевая картина** (L2–L3 по OSI): в VMware VM подключена к portgroup'у vSwitch. В Proxmox — к `vmbr0`/`vmbr1` (Linux-бридж) или Open vSwitch. Имя NIC может поменяться (например, `ens34` → `ens18` после смены контроллера), IP не «приедет», MAC тоже сменится, если явно не задать. Это два самых частых сюрприза после переезда Linux-машины.

**Фазы миграции** — запомни как мантру:

```text
1. ИНВЕНТАРИЗАЦИЯ   списки ВМ, зависимости (БД, DNS, LDAP), окна простоя
        │
2. ПИЛОТ            1–2 неважные ВМ, на них отрабатываем процедуру
        │
3. КОНВЕРТАЦИЯ      по группам сервисов, не по одной ВМ
        │
4. ПЕРЕКЛЮЧЕНИЕ     DNS, LB, IP, backup, клиенты
        │
5. ВАЛИДАЦИЯ        smoke-тесты, мониторинг 72 часа
        │
6. ОТКАТ/PROD       вышли на старт или откат из снапшота
```

Обрати внимание: миграция — это не «техническая операция с диском», это **изменение в production**. Регламент, окно простоя и план отката — обязательная часть.

Детали выбора конкретной целевой платформы и её установки — в уроках 35 (Proxmox) и 36 (zVirt/Базис/Брест/Скала-Р) этого модуля. Здесь мы фокусируемся на плане, конвертации и рисках — они одинаковы для всех KVM-целей.

## 3. Аналогия из жизни

Переезд офиса с Тверской на Кутузовский. Сначала опись — что везём, что выбрасываем, что нельзя отключать дольше, чем на час (сервер 1С, касса). Потом перевозка нескольких коробок в тестовом режиме — проверить, что мебель влезает в новый лифт. Потом основная волна: мебель и бумаги едут по расписанию, электрики переносят щиток, IT — коммутатор. Приёмка — по списку: свет работает, вода идёт, кофеварка включается. И у всех есть обратный билет и запасной офис, если в новом здании прорвало трубу.

Где аналогия ломается: в переезде офиса не бывает, что шкаф при доставке превратился в другой шкаф из-за отсутствия драйвера на дверцу. В миграции ВМ это происходит регулярно — гостевая ОС может «не проснуться» на новом hypervisor'е, и это заранее не всегда видно.

## 4. Практика и команды

Инструменты делятся на три группы: **извлечение из VMware**, **конвертация**, **импорт в цель**. 12 приёмов ниже покрывают полный цикл.

### 4.1. Инвентаризация источника: `govc`

`govc` — CLI к vCenter/ESXi. Устанавливается как один бинарь.

```bash
export GOVC_URL='https://vcenter.corp.local/sdk'
export GOVC_USERNAME='administrator@vsphere.local'
export GOVC_INSECURE=1                 # учебный самоподписанный сертификат; в prod — нет
govc ls /DC1/vm
govc vm.info -json VM-NAME > inventory.json
govc datastore.ls
```

Что смотреть: список ВМ, размеры дисков (`vm.info` даёт `VirtualDisk`), список datastore'ов. Сохрани `inventory.json` — это артефакт для регламента.

### 4.2. Экспорт OVA/OVF: `ovftool`

```bash
ovftool --noSSLVerify \
  vi://adm@vcenter.corp.local/Datacenter/vm/VM-NAME \
  ./export/VM-NAME.ova
```

`--noSSLVerify` — только в лаборатории, в prod используй валидный сертификат. `vi://` — синтаксис vSphere endpoint. Альтернатива в самом govc: `govc export.ovf -vm VM-NAME ./export/`. `[ПРОВЕРИТЬ]` синтаксис govc для OVA в текущей версии.

Экспорт можно делать «на горячую», но для БД — только после graceful shutdown или через snapshot с тишиной ввода-вывода.

### 4.3. Проверка формата источника: `qemu-img info`

```bash
qemu-img info VM-NAME.vmdk
# image: VM-NAME.vmdk
# file format: vmdk
# virtual size: 40 GiB (42949672960 bytes)
# disk size: 32.1 GiB
```

Смотри `file format` (должен быть `vmdk`, не `raw`), `virtual size` (это ёмкость гостевого диска) и `disk size` (реально занято на хосте). Большой разрыв = thin-provisioning.

### 4.4. Конвертация VMDK → qcow2: `qemu-img convert`

```bash
qemu-img convert -p -O qcow2 VM-NAME.vmdk VM-NAME.qcow2
```

`-p` — прогресс. `-O qcow2` — целевой формат. `-c` — сжатие (теряешь производительность, но экономишь место — для архивов). Учти: если VMDK «split» (несколько файлов `-s001.vmdk`), нужен первый файл `VM-NAME.vmdk`, остальные подтянутся.

### 4.5. Проверка целостности: `qemu-img check`

```bash
qemu-img check VM-NAME.qcow2
# No errors were found on the image.
```

Обязательный шаг. Если здесь ошибки — дальше не идти, переделывать.

### 4.6. Создание каркаса ВМ в Proxmox: `qm create`

```bash
qm create 200 --name ubu01-migr \
  --memory 4096 --cores 2 \
  --scsihw virtio-scsi-pci \
  --net0 virtio,bridge=vmbr0 \
  --ostype l26
```

`200` — произвольный свободный VMID. `--ostype l26` — Linux 2.6+. Для Windows: `--ostype win10`.

### 4.7. Импорт диска: `qm importdisk`

```bash
qm importdisk 200 VM-NAME.qcow2 local-lvm
qm set 200 --scsi0 local-lvm:vm-200-disk-0
qm set 200 --boot order=scsi0
qm start 200
```

`importdisk` кладёт диск в storage `local-lvm`, даёт имя `vm-200-disk-0`. Дальше `qm set` его цепляет. Если хочешь сохранить старый MAC (например, чтобы DHCP выдал тот же IP):

```bash
qm set 200 --net0 virtio=AA:BB:CC:DD:EE:FF,bridge=vmbr0
```

### 4.8. Импорт OVA целиком: `qm importovf`

```bash
qm importovf 201 VM-NAME.ovf local-lvm
```

Импортирует OVF, включая параметры VM, но без привязки к сети (сеть задаётся после). В веб-UI Proxmox есть мастер импорта на уровне storage/узла — `[ПРОВЕРИТЬ]` точное расположение меню в твоей версии.

### 4.9. Проверка агента: `qm agent`

```bash
qm agent 200 ping
qm guest cmd 200 network-get-interfaces
```

Нужен установленный и запущенный `qemu-guest-agent` в гостевой ОС. Без него Proxmox не сможет корректно выключать VM и отдавать IP.

### 4.10. Полная миграция на KVM/oVirt: `virt-v2v`

```bash
virt-v2v -ic vpx://administrator%40vsphere.local@vcenter.corp.local/Datacenter/Cluster \
         -o libvirt -os default VM-NAME
```

`virt-v2v` (проект libguestfs) сам снимает диск с vSphere, конвертирует, ставит гостевые драйверы (для Linux — пересобирает initramfs, для Windows — ставит VirtIO). Для zVirt/oVirt — вариант `-o rhv-upload` через API. Мощный, но требовательный: нужен libvirt-хост в качестве приёмника. Для Proxmox — не «из коробки», часто проще `qemu-img` + `qm importdisk`.

### 4.11. Hyper-V-ветка: `Convert-VHD`

```powershell
Convert-VHD -Path C:\export\VM-NAME.vmdk `
            -DestinationPath C:\vhdx\VM-NAME.vhdx `
            -VHDType Dynamic
New-VM -Name VM-NAME -MemoryStartupBytes 4GB -VHDPath C:\vhdx\VM-NAME.vhdx
Add-VMNetworkAdapter -VMName VM-NAME -SwitchName "Default Switch"
```

PowerShell выполняется на Hyper-V-хосте (нужен role Hyper-V). `-VHDType Dynamic` = thin. `-Fixed` = thick.

### 4.12. Финальные штрихи: `qm config`, resize

```bash
qm config 200                    # посмотреть итоговую конфигурацию
qm disk resize 200 scsi0 +20G    # расширить диск (в госте — growpart/resize2fs)
qm set 200 --delete sata0        # после установки VirtIO убрать временный SATA
```

### Сломай и почини

**Пользователь:** ты сам в роли L2-дежурного.
**ВМ:** ubu01-migr на PVE01.
**Что написал:** «Мигрированная ВМ в Proxmox не поднимается: в консоли GRUB, дальше — чёрный экран, в логах PVE ничего. Признаков сети нет».
**Срочность:** высокая (учебная).

**Как воспроизвести поломку.** На шаге 9 поменяй `--boot order=scsi0` на `--boot order=ide2` (без ISO на ide2). Либо оставь `--scsihw lsi` (дефолт в некоторых версиях Proxmox) — тогда Ubuntu может не найти корневой диск.

**Диагностика по шагам.**

1. `qm status 200` — ВМ `running`? Если `stopped` — смотрим `qm start 200`, ловим вывод.
2. `qm config 200` — проверить `boot: order=…`, `scsi0:` (диск прикреплён?), `scsihw:`. Если `scsi0` нет — диск не прицепился на шаге 9.
3. Консоль (noVNC): GRUB есть? Если нет — проблема в диске/загрузчике. Если GRUB есть, но ядро падает — проблема в драйверах контроллера (`lsilogic` vs `virtio-scsi-pci`).
4. Пересоздать конфиг: `qm set 200 --delete scsi0 && qm set 200 --scsi0 local-lvm:vm-200-disk-0 --scsihw virtio-scsi-pci --boot order=scsi0`. Если не грузится — временно переключить на `--scsihw lsi` или диск на `--sata0` и грузиться с него, а уже в госте ставить virtio.
5. Если грузится, но нет сети — `qm config 200` смотреть `net0`. Проверить `bridge=vmbr0`, MAC (`qm guest cmd 200 network-get-interfaces` при работающем агенте).

**Решение.** В 90% случаев — не тот `scsihw` или отсутствие `boot order`. Возвращаем: `qm set 200 --scsihw virtio-scsi-pci --boot order=scsi0` и, если нужно, добавляем ISO `virtio-win` (для Windows) или проверяем `initramfs` (для Linux).

**Что написать пользователю.** «Мигрированная ВМ была запущена с неверным типом контроллера диска, из-за чего ядро не находило корень. Исправил конфигурацию, перезапустил. Сейчас ВМ доступна по SSH, сеть 10.10.10.0/24 отвечает, сервисы в работе. Проверь, пожалуйста, со своей стороны.»

**Закрытие заявки.** Категория «виртуализация / миграция», решение «исправлена конфигурация scsihw и boot order», в `stand-log.md` — запись «причина: несовпадение драйвера контроллера, диагностическая последовательность отработана».

### Откат

1. `qm stop 200 && qm destroy 200` на PVE01 — удалить учебную ВМ целиком.
2. `rm -rf /var/lib/vz/import/*` на PVE01.
3. На хосте: `VM → Snapshot Manager → before-sysadmin-034 → Revert` для PVE01 и UBU01.
4. Записать откат в `stand-log.md`.

## 6. Ошибки новичков и безопасность

1. **«Проверю на боевой ВМ 1С в понедельник утром».** → первая же ошибка = недоступная бухгалтерия и потерянные проводки. Как правильно: пилот на копии (Veeam/Proxmox Backup), никогда на production без бэкапа и окна.
2. **Экспорт «на горячую» без quiesce.** → в образе ВМ консистентность файловой системы не гарантирована, БД может не подняться. Как правильно: graceful stop в госте либо snapshot с VSS/quiesce (`--quiesce` в govc), для SQL/1С — выгрузка БД отдельно.
3. **Забыл про VirtIO на Windows.** → BSOD 0x7B на первом старте. Как правильно: держи `virtio-win.iso`; если гость не грузится — цепляй диск как SATA, устанавливай драйверы, потом переключай на VirtIO SCSI.
4. **Игнорирование MAC/IP.** → Linux после переезда `ens18` вместо `ens160`, systemd-networkd не поднимает интерфейс, сервис недоступен. Как правильно: заранее прописать ожидаемое имя NIC в госте или на PVE задать исходный MAC.
5. **Забыли лицензии.** → Windows Server «отвалилась» после смены hardware (активация привязана к железу, для MAK/KMS может потребоваться реактивация; для OEM — лицензия вообще не переносится). 1С-лицензия на сервер привязана к параметрам сервера (CPU, MAC). Как правильно: собрать лицензии ДО миграции, заложить время на реактивацию, для OEM — покупать новую лицензию.
6. **Не проверен бэкап перед миграцией.** → «переехали, а откатиться некуда». Как правильно: свежий бэкап + тестовое восстановление в изолированной сети перед окном.
7. **Миграция «одной командой, без плана».** → не учтены зависимости (LDAP → приложение, БД → веб) → сервис не работает, хоть ВМ и стартовала. Как правильно: группы по сервисам, а не по одной ВМ.
8. **«Пятница вечер, всё получилось, закрою тикет и уйду».** → на выходных некому починить. Как правильно: окно в рабочий день, дежурный, готовая процедура отката.

**Безопасность.** В реальной работе нельзя: хранить пароль vCenter/root в истории bash или в открытом `~/.bash_history` (используй `read -s` и переменные окружения); отключать `--noSSLVerify` и проверку SSH-ключей «для скорости»; гонять OVA с production по открытому FTP/HTTP — только SCP/SFTP/HTTPS; оставлять после миграции старые VMware-креды и старые snapshot'ы включёнными. Также помни, что экспортированный OVA содержит диск с данными и хэшами паролей гостевой ОС — это конфиденциальная информация, обращаться как с бэкапом.

## 7. Вопросы на собеседовании

**Вопрос 1. Как ты спланируешь миграцию 100 ВМ с vSphere на Proxmox?**
Ответ: инвентаризация (govc) → группировка по сервисам → выбор пилота (2–3 некритичные ВМ) → отработка процедуры на пилоте → бэкапы всех ВМ → окна простоя по группам → переключение DNS/LB → smoke-тесты → мониторинг 72 часа → откат по снапшоту, если что. Отдельно — лицензии (Windows/1С) и зависимости.
*Что хочет услышать:* что ты управляешь проектом, а не только конвертируешь диски; что пилот и бэкап — обязательные фазы.
*Красный флаг:* «ну я просто qemu-img convert, потом qm importdisk».

**Вопрос 2. Чем VMDK отличается от qcow2 и как переходить?**
Ответ: VMDK — формат VMware (thin/thick, split/stream-optimized), qcow2 — формат QEMU/KVM с CoW, снапшотами и сжатием на уровне образа. Переход — `qemu-img convert -O qcow2 → qemu-img check`. Если VMDK split — конвертация по первому файлу, остальные подтянутся.
*Что хочет услышать:* понимание, что конвертация формата ≠ конвертация ОС; что после конвертации обязательна проверка.
*Красный флаг:* «просто переименовать расширение».

**Вопрос 3. Что делать с VMware Tools при переезде Windows на KVM?**
Ответ: VMware Tools удалить в госте, установить `virtio-win` (драйверы VirtIO SCSI / net / balloon) и `qemu-guest-agent`. Если ВМ не грузится на VirtIO SCSI — временно SATA, поставить драйверы, переключить. Проверка: `qm agent <id> ping`.
*Что хочет услышать:* пошаговая процедура «сначала SATA, потом VirtIO», а не героика «сразу VirtIO».
*Красный флаг:* «оставить VMware Tools, оно само заработает».

**Вопрос 4. Какие риски при миграции сервера 1С?**
Ответ: 1С-сервер привязан к параметрам (CPU, MAC, иногда к имени) — лицензия может потребовать перепривязки. SQL/PostgreSQL — критична консистентность, экспорт только с quiesce или через dump базы. Клиенты 1С ходят по имени — проверить DNS и порты (1540/1541/1560). Тестовый запуск на копии БД перед переключением.
*Что хочет услышать:* что ты знаешь специфику 1С (лицензия, БД, порты) — это критично в РФ.
*Красный флаг:* «1С — это ж просто Windows-сервер».

**Вопрос 5. Proxmox, zVirt или Базис — как выбрать?**
Ответ: все три на KVM, разница в управляющей панели, поддержке, сертификации и цене. Proxmox — open-source, огромное комьюнити, нет сертификации ФСТЭК «из коробки»; zVirt/Базис — российские вендоры с реестром, поддержкой и сертификацией (важно для гос/КИИ). Hyper-V — вариант, если уже есть лицензии Microsoft и парк Windows, но с 2026-го доступность легальных лицензий в РФ — вопрос. Итог: смотреть на требования регулятора + бюджет + наличие компетенций.
*Что хочет услышать:* «одинаковое ядро KVM, разница в обёртке, поддержке и сертификации; выбор — по требованиям заказчика».
*Красный флаг:* «Proxmox потому что бесплатный» без анализа требований.
