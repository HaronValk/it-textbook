# SIEM и журналирование: Wazuh, ELK, MaxPatrol SIEM — сбор, нормализация, корреляция, правила

## 1. Введение (зачем это нужно в реальной работе)

Тикет в очередь ИБ:

> **Пользователь:** adm.student (дежурство по ИБ)
> **ВМ:** SIEM01, DC01
> **Что написал:** «В дашборде с 09:20 нет ни одного события с DC01. Last active — вчера 23:12. Остальные агенты на связи. Через час сдавать отчёт по попыткам входа за сутки, а у меня дыра.»
> **Срочность:** Высокая

Пока стенд маленький, кажется, что «логи — это файл, куда лезут руками, когда что-то сломалось». В реальной работе на 50+ серверов и сотни рабочих мест так нельзя: события нужны не задним числом, а в момент атаки, и не по одной машине, а по всей инфраструктуре сразу.

SIEM (Security Information and Event Management — система управления событиями безопасности) решает три задачи: **собрать** события со всех источников, **привести их к одному виду** и **найти в них закономерности**, которые по отдельности выглядят безобидно. Один неудачный вход — ерунда. Двадцать неудачных входов с одного адреса за две минуты, а потом успешный — это уже инцидент.

После этой главы ты должен уметь: развернуть Wazuh в лаборатории, подключить к нему Windows и Linux, написать собственный декодер и правило корреляции, объяснить разницу между SIEM и «просто сбором логов», обосновать retention и рассказать, как требования ФСТЭК закрываются журналированием. И главное — понимать, что SIEM без процесса реагирования превращается в дорогое хранилище JSON.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

SIEM — это конвейер из пяти стадий. Ломается всё обычно на первой и третьей.

```text
ИСТОЧНИКИ          СБОР              НОРМАЛИЗАЦИЯ       КОРРЕЛЯЦИЯ        ХРАНЕНИЕ / UI
                                                                          
DC01 Security  ─┐                                                           
FS01 (агент)   ─┤                  decoder:                                 
UBU01 auditd   ─┼─► agent ───────►  regex → поля ───►  rules:      ────►  indexer ───► dashboard
WEB01 nginx    ─┤   1514/tcp       user, srcip,       if_sid,            (OpenSearch)    443
GW01 nftables  ─┘                  action, result     frequency,          ILM 90 дней
MON01 Zabbix   ──► syslog 514/udp                     timeframe,                 │
                    или TLS 6514                      MITRE ATT&CK               ▼
                                                                              API 55000
                                                                              алерты → почта,
                                                                              Telegram, Jira
```

**Сбор.** Три основных способа: агент на хосте (Wazuh agent, Elastic Agent), безагентный сбор через syslog (RFC 5424, UDP 514 — без шифрования и подтверждения доставки; TLS-вариант — 6514, RFC 5425), и API-опрос (например, читать журнал облака или 1С по REST). На Windows отдельно стоит **WEF** (Windows Event Forwarding) — штатный механизм, который пересылает события в Windows Event Collector по WinRM (5985/5986), без сторонних агентов.

**Нормализация.** Разные системы пишут по-разному: nginx — в access-логах, sshd — в auth.log, Windows — в бинарном EVTX с XML-полями. SIEM нужен общий знаменатель: «источник, пользователь, адрес, действие, результат, время». В Wazuh это делают **декодеры** (парсят строку в поля) и общая схема полей; в Elastic — **ECS** (Elastic Common Schema) и ingest-пайплайны/Logstash grok; в MaxPatrol SIEM — «модель данных» и штатные нормализаторы под конкретные источники.

**Обогащение** — часто путают с нормализацией. Это добавление контекста: чей это IP (актив из инвентаря), критична ли машина, что за учётка (привилегированная или нет), геолокация. Без обогащения все алерты одинаково серые.

**Корреляция.** Правила трёх типов:
- *простые* (сигнатурные) — «событие содержит X»;
- *пороговые* (stateful) — «N событий за T секунд»; в Wazuh это `frequency` + `timeframe`;
- *последовательности* — «A, потом B, потом C от одного субъекта» (в Elastic это EQL sequences, часть функций доступна только в платной подписке `[ПРОВЕРИТЬ актуальный набор по лицензии]`).

**Хранение и выдача.** Индекс с ротацией по времени (ILM — Index Lifecycle Management): горячая фаза, тёплая, удаление. Retention — не «сколько влезет на диск», а требование: типовой компромисс для бизнеса 90–365 дней, для КИИ и по требованиям регуляторов сроки устанавливаются внутренним регламентом и могут быть больше `[ПРОВЕРИТЬ по применимым приказам ФСТЭК для твоего класса]`.

**Сопоставление терминов** — чтобы не потеряться при переходе между системами:

| Задача | Wazuh | Elastic Stack | MaxPatrol SIEM |
|---|---|---|---|
| Хранение | Wazuh indexer (форк OpenSearch) | Elasticsearch | собственное хранилище |
| Парсинг | decoder (XML) | ingest pipeline / grok | нормализатор |
| Правила | rules (XML), id 100000+ для своих | detection rules, EQL | корреляционные правила |
| UI | Wazuh dashboard (443) | Kibana (5601) | веб-консоль |
| API | 55000/tcp, JWT | 9200/tcp | REST `[ПРОВЕРИТЬ]` |

Порты, которые реально понадобятся: **1514/tcp** (события агент→менеджер), **1515/tcp** (регистрация агента), **55000/tcp** (API), **443** (дашборд), **9200** (индексер), **514/udp** и **6514/tcp** (syslog), **5044** (Beats→Logstash), **5601** (Kibana), **5985/5986** (WinRM/WEF).

Уровень модели OSI: всё это прикладной уровень (L7). Но транспорт и шифрование важны — трафик агентов в боевой среде идёт только по TLS, иначе события можно подменить на лету.

## 3. Аналогия из жизни

Представь большой торговый центр. На каждом этаже висят камеры — это **агенты**: они снимают, но сами ничего не решают и не анализируют. В подвале стоит регистратор, который пишет всё на диски — это **индексер**: он хранит, но не думает. А в комнате охраны сидит оператор с папкой инструкций — это **корреляция**. В инструкции написано: «если один и тот же человек дважды прошёл через турникет на входе в 3:00 и один раз через служебную дверь — звони старшему». Камеры видят тысячи событий в час, но оператор реагирует только на совпадение с инструкцией.

Отсюда сразу видно, где всё ломается: если камера на третьем этаже показывает неверное время, оператор никогда не сопоставит её запись с турникетом — и именно поэтому NTP в SIEM не «мелочь», а фундамент. И если инструкция не обновлялась три года, оператор пропустит новый способ кражи.

Где аналогия перестаёт работать: камера фиксирует всё, что попало в объектив, а логи содержат только то, что система решила записать. Если в Windows не включён аудит — события просто нет, и никакой SIEM его не «увидит».

## 4. Практика и команды

**1. Подготовка узла SIEM01 (Linux, базовая гигиена).**

```bash
sudo hostnamectl set-hostname siem01.corp.vektor.lab
timedatectl set-timezone Europe/Moscow
timedatectl status
chronyc sources -v
```

`timedatectl status` показывает, синхронизировано ли время (`System clock synchronized: yes`). `chronyc sources -v` — список источников и звёздочку `*` у текущего. Смотреть: если время уходит — корреляция по `timeframe` начнёт врать, а события будут «прилетать из прошлого». В домене источник времени для Windows — DC01 (эмулятор PDC).

**2. Установка Wazuh all-in-one (менеджер + индексер + дашборд на одной машине).**

```bash
curl -sO https://packages.wazuh.com/4.x/wazuh-install.sh
sudo bash wazuh-install.sh -a -i
```

`-a` — all-in-one, `-i` — игнорировать проверку минимальных требований к железу (для учебного стенда; в бою так не делают). В конце установщик печатает логин `admin` и сгенерированный пароль; они же сохраняются в архиве `wazuh-install-files.tar`. Для 4.9+ вендор рекомендует Wazuh Installation Assistant `[ПРОВЕРИТЬ актуальный установщик для свежей версии]`.

**3. Проверка служб и состояния менеджера.**

```bash
sudo /var/ossec/bin/wazuh-control status
systemctl status wazuh-indexer wazuh-dashboard --no-pager
sudo ss -tlnp | grep -E '1514|1515|55000|443|9200'
```

`wazuh-control status` перечисляет внутренние демоны менеджера (`wazuh-analysisd`, `wazuh-remoted`, `wazuh-db` и др.) и их PID. Если `wazuh-remoted` не поднялся — агенты не подключатся вообще, даже при живом дашборде.

**4. Установка агента на Linux (UBU01).**

```bash
curl -s https://packages.wazuh.com/key/GPG-KEY-WAZUH | sudo gpg --dearmor -o /usr/share/keyrings/wazuh.gpg
echo "deb [signed-by=/usr/share/keyrings/wazuh.gpg] https://packages.wazuh.com/4.x/apt/ stable main" | sudo tee /etc/apt/sources.list.d/wazuh.list
sudo apt update
sudo WAZUH_MANAGER="10.10.10.45" apt install -y wazuh-agent
sudo systemctl daemon-reload && sudo systemctl enable --now wazuh-agent
```

Переменная `WAZUH_MANAGER` подставляется в `ossec.conf` при установке — это штатный способ, ручной правки конфига не требуется.

**5. Установка агента на Windows (DC01) — PowerShell от администратора.**

```powershell
Invoke-WebRequest -Uri https://packages.wazuh.com/4.x/windows/wazuh-agent-4.14.0-1.msi -OutFile $env:TEMP\wazuh-agent.msi
msiexec.exe /i $env:TEMP\wazuh-agent.msi /q WAZUH_MANAGER="10.10.10.45" WAZUH_AGENT_NAME="DC01"
Get-Service WazuhSvc
```

Свойства MSI `WAZUH_MANAGER` и `WAZUH_AGENT_NAME` записывают адрес менеджера и имя агента при тихой установке. Номер версии в имени файла проверь на странице загрузок — он меняется `[ПРОВЕРИТЬ актуальную версию]`.

**6. Sysmon — расширенная телеметрия Windows.**

```powershell
C:\temp\Sysmon\Sysmon64.exe -accepteula -i C:\temp\sysmonconfig.xml
Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" -MaxEvents 5
```

Sysmon (Microsoft Sysinternals, бесплатно) добавляет в журнал события о создании процессов с командной строкой, сетевых соединениях, загрузке драйверов. Конфиг берут готовый (SwiftOnSecurity/sysmon-config, olafhartong/sysmon-modular) и адаптируют. Без Sysmon правило «PowerShell с закодированной командой» писать не из чего.

**7. Список агентов на менеджере.**

```bash
sudo /var/ossec/bin/agent_control -l
```

Вывод — таблица ID, имя, IP, статус (`Active`/`Disconnected`) и время последнего контакта. Это первая команда при любом «нет событий с хоста».

**8. Интерактивная проверка декодера и правила — главный инструмент отладки.**

```bash
sudo /var/ossec/bin/wazuh-logtest
```

Утилита просит строку лога, показывает, какой декодер её разобрал, какие поля извлёк и какое правило сработало (с phase 1/2/3). Пример:

```text
**Phase 2: Completed decoding.
        name: 'vektor-app'
        user: 'ivanov'
        action: 'login'
        result: 'denied'
**Phase 3: Completed filtering (rules).
        id: '100300'
        level: '8'
        description: 'Vektor app: доступ запрещён для пользователя'
```

**9. Своё правило в `/var/ossec/etc/rules/local_rules.xml`.**

```xml
<group name="local,windows,">
  <rule id="100100" level="10">
    <if_group>sysmon_event1</if_group>
    <field name="win.eventdata.commandLine" type="pcre2">(?i)-enc(odedcommand)?\s</field>
    <description>PowerShell с закодированной командой (T1059.001)</description>
    <mitre>
      <id>T1059.001</id>
    </mitre>
  </rule>
</group>
```

`if_group` — «сработай поверх уже сработавшего правила из группы» (здесь: события Sysmon ID 1, создание процесса) `[ПРОВЕРИТЬ имя группы в актуальном ruleset]`. `type="pcre2"` — регулярное выражение Perl-совместимого синтаксиса. `level` от 0 до 15: 0 — не логировать, 3–7 — информационное, 8–11 — требует внимания, 12+ — инцидент. `mitre` привязывает правило к технике ATT&CK — это то, что любят видеть в отчётах и на собеседовании.

**10. Корреляционное (пороговое) правило — брутфорс SSH.**

```xml
<rule id="100201" level="10" frequency="6" timeframe="120">
  <if_matched_group>authentication_failed</if_matched_group>
  <same_source_ip />
  <description>SSH brute force: 6 неудачных входов с одного IP за 120 с</description>
  <mitre>
    <id>T1110</id>
  </mitre>
</rule>
```

`frequency` + `timeframe` (секунды) включают счётчик; `same_source_ip` говорит «считай отдельно по каждому адресу», а не «6 отказов по всей сети». Без `same_source_ip` правило будет стрелять от шести разных пользователей, каждый по разу.

**11. Свой декодер `/var/ossec/etc/decoders/local_decoder.xml`.**

```xml
<decoder name="vektor-app">
  <program_name>^vektor-app$</program_name>
</decoder>

<decoder name="vektor-app-fields">
  <parent>vektor-app</parent>
  <regex offset="after_parent">^user=(\S+) action=(\S+) result=(\S+)$</regex>
  <order>user, action, result</order>
</decoder>
```

`parent` связывает дочерний декодер с родительским (сначала определяем программу, потом разбираем остаток строки), `order` задаёт имена полей по порядку групп regex.

**12. Просмотр сырых алертов и API.**

```bash
sudo tail -f /var/ossec/logs/alerts/alerts.json | jq '{time:."@timestamp", rule:.rule.description, level:.rule.level, agent:.agent.name}'
TOKEN=$(curl -s -k -u admin:"$WAZUH_ADMIN_PASS" -X POST "https://10.10.10.45:55000/security/user/authenticate?raw=true")
curl -s -k -H "Authorization: Bearer $TOKEN" "https://10.10.10.45:55000/agents?select=id,name,status,lastKeepAlive"
```

`alerts.json` — то же, что видно в дашборде, но текстом: удобно для отладки и для выгрузки в другую систему. Пароль по умолчанию для API — `wazuh` на старых версиях, в новых генерируется при установке `[ПРОВЕРИТЬ для своей версии]`.

**13. Где включается аудит на Windows и Linux.**

```powershell
auditpol /get /category:"Logon/Logoff"
auditpol /set /subcategory:"Logon" /success:enable /failure:enable
```

```bash
sudo auditctl -w /etc/passwd -p wa -k passwd_changes
sudo ausearch -k passwd_changes -i | tail -20
```

`-w` — наблюдать за файлом, `-p wa` — write и attribute change, `-k` — метка для поиска. Постоянные правила кладут в `/etc/audit/rules.d/*.rules` и применяют `augenrules --load`. Названия подкатегорий в `auditpol` зависят от локали Windows — на русской системе сверяй через `auditpol /list /subcategory:*`.

**14. Elastic Stack: проверка индексов и политики жизненного цикла.**

```bash
curl -s "localhost:9200/_cat/indices?v&s=index"
curl -s -X PUT "localhost:9200/_ilm/policy/siem-90d" -H 'Content-Type: application/json' -d '
{ "policy": { "phases": {
  "hot":    { "actions": { "rollover": { "max_primary_shard_size": "50gb", "max_age": "7d" } } },
  "warm":   { "min_age": "7d",  "actions": { "forcemerge": { "max_num_segments": 1 } } },
  "delete": { "min_age": "90d", "actions": { "delete": {} } } } } }'
```

`_cat/indices` — размер, число документов, состояние (зелёный/жёлтый/красный). Красный индекс = данные не пишутся, обычно из-за нехватки места или watermark.

**15. Что смотреть в MaxPatrol SIEM (без установки).** Запроси у вендора демо-стенд или документацию `[ПРОВЕРИТЬ доступность учебной/демо-версии]`. В интерфейсе ищи те же четыре сущности: «Источники» (коннекторы), «Нормализация» (модель данных и маппинг полей), «Правила корреляции» (условия + активы + списки исключений), «Инциденты» (результат). Разница с Wazuh — не в идее, а в поставке: вендорская поддержка, сертификация, обновляемые пакеты правил.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

Нужны: DC01 (AD DS, DNS, DHCP, 10.10.10.10), UBU01 (10.10.10.30), FS01 (10.10.10.20) — все в рабочем состоянии после L2. Плюс новая ВМ **SIEM01**, которой в таблице стенда нет: она добавляется на этом уроке как необходимое расширение трека сисадмин. Параметры: Ubuntu Server 24.04 LTS, **10.10.10.45**, 4 vCPU, 8 ГБ RAM, 100 ГБ диск, сеть VMnet8.

Учётная запись для входа в дашборд создаётся установщиком. Пароль всего стенда `Lab#2026-vektor` здесь **не** используется — у Wazuh свои сгенерированные пароли, и это правильно.

### Снапшот

В VMware Workstation: правый клик по ВМ → Snapshot → Take Snapshot. Имя: `before-sysadmin-055`. Сделать на **SIEM01** (после создания ВМ и первичной настройки сети, до установки Wazuh), на **DC01** и на **UBU01**.

### Шаги

1. **SIEM01.** Создать ВМ, поставить Ubuntu Server 24.04, задать статический адрес через netplan:
   ```yaml
   network:
     version: 2
     ethernets:
       ens33:
         dhcp4: false
         addresses: [10.10.10.45/24]
         routes:
           - to: default
             via: 10.10.10.2
         nameservers:
           addresses: [10.10.10.10]
   ```
   Имя интерфейса подставь своё из `ip -br a`. Применить: `sudo netplan apply`.
   *Ожидаемо:* `ping 10.10.10.10` отвечает, `getent hosts dc01.corp.vektor.lab` возвращает адрес.

2. **SIEM01.** Настроить время и проверить синхронизацию (`timedatectl`, `chronyc sources -v`).
   *Ожидаемо:* `System clock synchronized: yes`, расхождение с DC01 — секунды.

3. **SIEM01.** Установить Wazuh all-in-one: `curl -sO https://packages.wazuh.com/4.x/wazuh-install.sh && sudo bash wazuh-install.sh -a -i`.
   *Ожидаемо:* финальное сообщение об успешной установке, логин `admin` и пароль в консоли.

4. **SIEM01.** Проверить службы, открыть `https://10.10.10.45` с хоста.
   *Ожидаемо:* страница входа Wazuh dashboard, после входа — пустые графики и 0 агентов.

5. **UBU01.** Установить агент (команда из п.4 раздела 4). На SIEM01 выполнить `sudo /var/ossec/bin/agent_control -l`.
   *Ожидаемо:* агент `UBU01` со статусом `Active`, время последнего контакта — секунды назад.

6. **DC01.** Установить Sysmon с конфигом, затем агент Wazuh, затем `Start-Service WazuhSvc`.
   *Ожидаемо:* через 1–2 минуты в `agent_control -l` появляется `DC01`, статус `Active`.

**Ответ пользователю:** «Агент DC01 был остановлен, служба стояла в ручном запуске. Запустил, автозапуск вернул, события с 10:05 идут. Отчёт по попыткам входа за сутки соберу к 15:00, данные за простой в 09:20–10:05 с DC01 отсутствуют — за этот интервал собрать не смогу, зафиксирую пробел в отчёте.»

## 6. Ошибки новичков и безопасность

1. **Ставить SIEM и не настраивать NTP** → события с разных хостов не сопоставляются, пороговые правила не срабатывают, таймлайн инцидента врёт. → Один источник времени для всех, проверка `chronyc tracking` и `w32tm /query /status` в чек-листе приёмки.

2. **Собирать всё подряд без фильтра** → десятки гигабайт мусора в день, индексер уходит в read-only, алерты тонут. → Начинать с приоритетных источников (аутентификация, привилегированные действия, изменения учёток, EDR-события), расширять осознанно.

3. **Правила с level 12 на каждое событие** → alert fatigue, дежурный перестаёт открывать SIEM. → Тюнинг, whitelists, suppression, пороги; каждое правило должно иметь владельца и объяснение «что делать при срабатывании».

4. **Хранить логи только на источнике** → атакующий первым делом чистит журнал (`wevtutil cl Security`, `truncate -s0 /var/log/auth.log`). → Централизованный сбор обязателен, на источнике — минимальный буфер.

5. **Логировать пароли и ПДн в открытом виде** → нарушение 152-ФЗ и внутренних политик. → Маскирование полей на этапе ingest, запрет `logall` на чувствительных источниках без фильтра.

6. **Открыть дашборд в общую сеть без TLS и RBAC** → компрометация SIEM = карта всей инфраструктуры у атакующего. → SIEM в отдельном сегменте, доступ по VPN/ bastion, роли, MFA `[ПРОВЕРИТЬ поддержку MFA в выбранной версии]`.

7. **Верить, что SIEM = безопасность** → купили систему, никто не смотрит алерты. → SIEM работает только вместе с процессом: регламент, дежурство, SLA на реакцию, постмортемы (это урок 60).

8. **Править правила сразу в проде без теста** → одно правило с плохим regex кладёт analysisd и останавливает поток событий. → `wazuh-logtest` на реальной выборке, изменения через git и ревью, откат конфигурации.

**Безопасность.** В боевой среде SIEM — критичный актив первого порядка: в нём вся телеметрия и часто инвентарь. Нельзя: держать его в том же VLAN, что рабочие станции; использовать общий пароль администратора без ротации; хранить выгрузки `alerts.json` на общедоступном файловом ресурсе; давать аналитику учётку администратора индекс-кластера. Журналы должны быть защищены от изменения — минимум отдельными правами и бэкапом конфигурации, максимум — WORM-хранилищем (об этом урок 61). В лаборатории мы ставим SIEM01 в общую сеть 10.10.10.0/24 ради простоты — в реальном проекте это отдельный сегмент управления.

## 7. Вопросы на собеседовании

**1. Чем SIEM отличается от централизованного syslog-сервера?**

Ответ: syslog-сервер решает транспорт и хранение — собирает сообщения и складывает в файлы или индекс. SIEM добавляет три слоя: нормализацию (единая схема полей вместо строк), корреляцию (правила, пороги, последовательности с сохранением состояния) и обогащение контекстом (активы, критичность, привилегированность учёток) с выдачей инцидентов и интеграциями (тикеты, SOAR). Практическая разница: syslog отвечает на вопрос «что было», SIEM — «что происходит и на что реагировать сейчас».

*Что хочет услышать:* понимание, что граница проходит по нормализации и корреляции, а не по «красивому интерфейсу».
*Красный флаг:* «SIEM — это просто Kibana над логами».

**2. Что такое нормализация и что вы будете делать с логом самописной 1С-системы?**

Ответ: нормализация — приведение разнородных сообщений к общему набору полей (время, источник, субъект, объект, действие, результат), чтобы правила и отчёты работали одинаково по всем источникам. Для самописной системы: выяснить формат (скорее всего, текстовые строки или JSON), написать парсер (в Wazuh — decoder с `program_name` и regex/`order`, в Elastic — grok или JSON-фильтр), проверить на реальной выборке, замапить поля на общую схему, отдельно обработать многострочные записи и смену формата при обновлении приложения, завести правило и тест.

*Что хочет услышать:* порядок «формат → парсер → маппинг → тест → мониторинг изменений формата».
*Красный флаг:* «настрою grok по первой строке из документации и всё».

**3. Как работает корреляция? Приведите пример и его ложное срабатывание.**

Ответ: корреляция — применение правил к нормализованному потоку, в том числе с состоянием. Пример: 6 неудачных SSH-входов с одного IP за 120 секунд (в Wazuh — `frequency`/`timeframe` + `same_source_ip`). Ложное срабатывание: сканер уязвимостей в регламентном окне или администратор с неверно введённым паролем в цикле проверки. Лечится исключением по источнику (scanner IP в whitelist), окном обслуживания и изменением порога после замеров на реальном объёме.

*Что хочет услышать:* понимание, что порог подбирается по данным, а не «на глаз», и что ложные срабатывания — норма, которую надо управлять.
*Красный флаг:* «поставлю побольше событий — точность вырастет».

**4. Как обеспечить, что логи нельзя подделать или удалить?**

Ответ: цепочка мер. Централизованный сбор с источников (атакующий на хосте не достанет копию в SIEM); ограничение прав на сам SIEM и разделение ролей (администратор платформы ≠ аналитик); TLS на транспорте; неизменяемое хранилище (WORM/object lock, отдельный аккаунт с write-only доступом); криптографическая целостность (хэширование/подпись пачек событий); мониторинг самого SIEM (агент отключился, поток упал — алерт); регулярные проверки восстановления и контроль доступа к резервным копиям. Отдельно — синхронизация времени, иначе подделка «задним числом» становится правдоподобной.

*Что хочет услышать:* defense in depth и мысль «защищаем не только логи, но и систему, которая их собирает».
*Красный флаг:* «включу аудит — и всё».

**5. Какие требования РФ влияют на журналирование и как выбрать SIEM в 2026 году?**

Ответ: 152-ФЗ (ст. 19 — организационные и технические меры, включая регистрацию и учёт событий `[ПРОВЕРИТЬ формулировку]`), 187-ФЗ и приказы ФСТЭК №17, 21, 239 для КИИ и ГИС — там прямо требуется регистрация событий безопасности и их хранение; ГОСТ Р 57580 для финансового сектора задаёт уровни защиты и требования к мониторингу. Практический выбор: если нужна сертифицированная поставка и поддержка вендора — смотреть MaxPatrol SIEM (Positive Technologies, в реестре отечественного ПО), KUMA (Kaspersky), R-Vision SIEM `[ПРОВЕРИТЬ актуальный статус и наличие бесплатных редакций]`. Если задача — внутренний SOC с ограниченным бюджетом и своей экспертизой — Wazuh (open source) или Elastic Stack, но тогда вопросы сертификации и поддержки закрываются самостоятельно. Критерии: покрытие источников, стоимость хранения, наличие правил под российское ПО (1С, КриптоПро, Astra Linux), нагрузка на аналитика, интеграции с SIEM-смежными системами.

*Что хочет услышать:* связку «требование → мера → продукт → стоимость владения», а не «берём самый известный».
*Красный флаг:* «Wazuh бесплатный, значит, всегда лучше» или «сертификация не нужна, мы же не банк».
