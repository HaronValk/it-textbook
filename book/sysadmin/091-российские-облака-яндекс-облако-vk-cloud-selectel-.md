## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Все четыре провайдера построены по одной схеме: физические стойки в дата-центрах → гипервизор (KVM, часто под OpenStack-подобной платформой) → API-слой → консоль и CLI. Отличия в основном в надстройках (PaaS, managed-сервисы, ML) и в юридической обвязке.

**Ресурсная иерархия.** Везде она трёхуровневая, меняются только слова:

```text
Пользователь (аккаунт, он же владелец платёжного аккаунта)
└── Облако / Проект / Аккаунт-проект      ← изоляция ресурсов и биллинга
    └── Каталог / Проект / Подпроект      ← единица, на которую вешаются IAM-роли
        ├── VPC: сеть → подсеть (CIDR) → security group
        ├── Compute: ВМ (vCPU/RAM/диск) + публичный IP
        ├── Object Storage (S3-совместимое)
        └── Managed-сервисы: PostgreSQL/MySQL/ClickHouse, Kubernetes, Redis
```

В Яндекс Облаке это `cloud → folder` (каталог), каталог — основная единица IAM. В VK Cloud — `проект`, внутри которого сети и ВМ. В Selectel — `проект` внутри аккаунта, а права выдаются на проект. В Cloud.ru — `проект` в составе аккаунта, плюс отдельные сегменты Evolution/Advanced. Практический вывод: **никогда не держи прод и дев в одном проекте/каталоге** — иначе одна ошибка в правах или в удалении сети сносит всё.

**Сеть.** У всех: VPC с подсетями в зонах доступности (ЗД/AZ), security groups (stateful firewall на уровне порта ВМ), публичный IP через NAT-шлюз, приватные подсети без выхода в интернет. Порты, которые тебе понадобятся: **443/tcp** — API и консоль всех провайдеров, **22/tcp** — SSH, **5432/3306** — БД, **500/4500/udp + ESP** — IPsec, **51820/udp** — WireGuard (для гибридных схем, урок 92). Зоны доступности у российских провайдеров физически разнесены по разным ДЦ в Москве и СПб — отказ одной ЗД не должен ронять сервис.

**IAM (Identity and Access Management).** Ключевая идея: **никто не логинится в ВМ паролем от аккаунта облака**. Есть три сущности:
- **пользователь** (человек, через федерацию с AD или через Яндекс ID/VK ID) — ему выдаются роли `viewer` (только чтение), `editor`, `admin`;
- **сервисный аккаунт** (service account) — «робот» для приложения, CI, бэкап-скрипта; на него выдаются узкие роли вида «только заливать объекты в этот бакет»;
- **ключи**: авторизованный ключ (для входа по SSH на ВМ), статический ключ доступа (access key + secret для S3/API), API-токен. Секрет показывается **один раз**, восстановить нельзя — только перевыпустить.

**Биллинг.** Платёжный аккаунт привязан к юрлицу или физлицу, работает по предоплате (лицевой счёт) или постоплате для юрлиц, с НДС 20% и закрывающими документами (счёт, акт, УПД). Тарификация почасовая или посекундная. Критично: **остановленная ВМ продолжает стоить** — за диск, публичный IP и иногда за «резерв» вычислительных ресурсов платят, пока ресурс существует. Есть бюджеты и алерты по расходу — их надо включать сразу. Гранты (trial-баллы) дают на старт, но у них есть срок, и после него ресурсы начинают списывать реальные деньги.

**Юридический слой (РФ).** 152-ФЗ, ч. 5 ст. 18 — персональные данные граждан РФ хранятся на серверах в РФ. Реестр операторов ПДн, уведомление РКН. 187-ФЗ (КИИ) — для значимых объектов нужны требования ФСТЭК, приказ № 17 (классы защищённости, УЗ-1…УЗ-3). Аттестация по требованиям безопасности и реестр отечественного ПО — реальный критерий выбора, особенно для госсектора. Все четыре провайдера держат площадки в РФ и предлагают услуги под эти требования, но состав аттестованных сегментов надо уточнять под задачу.

## 3. Аналогия из жизни

Облако — это бизнес-центр класса A. Ты не строишь здание, не меняешь проводку и не покупаешь дизель-генератор: приезжаешь, получаешь помещение нужной площади, платишь за метры, электричество по счётчику, интернет по тарифу и за пропуска сотрудникам. Управляющая компания отвечает за фундамент, лифты и охрану периметра, но **не за то, что ты забыл запереть свою дверь** — за содержимое офиса, за то, кому выписан пропуск, и за то, что твой сотрудник оставил ключ в замке, отвечаешь ты. Счёт приходит по счётчикам, и если ты весь месяц гонял кондиционер на +18 с открытым окном — это твоя проблема, а не УК. Аналогия перестаёт работать в одном: в бизнес-центре нельзя за 40 секунд «достроить» ещё один этаж и через минуту его снести — в облаке это норма.

## 4. Практика и команды

**1. Профиль CLI Яндекс Облака.** `yc` — основной инструмент; профиль хранит OAuth-токен, облако и каталог по умолчанию.

```bash
yc init                       # интерактивно: токен, cloud-id, folder-id, зона
yc config list                # что реально выбрано сейчас
yc config profile list
```

Вывод — список пар `ключ: значение`. Смотреть на `folder-id` и `zone`: 90% «не туда создалось» — это не тот профиль.

**2. Иерархия ресурсов.**

```bash
yc resource-manager cloud list
yc resource-manager folder list --cloud-id b1gxxxxxxxxxxxxxxx
```

Проверяешь, что каталогов ровно столько, сколько проектов, и нет каталога `default` с прод-нагрузкой.

**3. Сервисный аккаунт и ключ.**

```bash
yc iam service-account create --name sa-backup
yc iam key create --service-account-name sa-backup --output sa-backup-key.json
```

`sa-backup-key.json` — приватный ключ для подписи JWT. `chmod 600` и **никогда** в git.

**4. Статический ключ для S3.**

```bash
yc iam access-key create --service-account-name sa-backup
```

В выводе `access_key.key_id` и `secret` — секрет одноразовый. Ключ живёт, пока его не удалят: ротация на тебе.

**5. Сеть и подсеть.**

```bash
yc vpc network create --name vektor-net
yc vpc subnet create --name vektor-subnet-a --network-name vektor-net \
  --range 10.10.40.0/24 --zone ru-central1-a     # зону уточняй в консоли [ПРОВЕРИТЬ]
yc vpc subnet list
```

Диапазон выбирай из своего плана адресации и **не пересекайся с 10.10.10.0/24 и 10.10.20.0/24** — иначе гибридный VPN в уроке 92 не поднимется.

**6. Security group.**

```bash
yc vpc security-group create --name sg-app --network-name vektor-net
yc vpc security-group update-rules sg-app --add-rule \
  "direction=ingress,port=22,protocol=tcp,v4-cidrs=[10.10.10.0/24]"
```

Синтаксис правил проверяй по `yc vpc security-group update-rules --help` [ПРОВЕРИТЬ]. Правило «22 из 10.10.10.0/24» вместо `0.0.0.0/0` — это и есть базовая гигиена.

**7. Создание ВМ и просмотр.**

```bash
yc compute instance create --name cloud-vm01 --zone ru-central1-a \
  --network-interface subnet-name=vektor-subnet-a,nat-ip-version=ipv4 \
  --create-boot-disk image-folder-id=standard-images,image-family=ubuntu-2404-lts,size=20 \
  --ssh-key ~/.ssh/id_ed25519.pub
yc compute instance list
yc compute instance get --name cloud-vm01 --format yaml
```

`image-family` — «последний образ этой линейки», удобнее фиксированного ID [ПРОВЕРИТЬ имя семейства]. `--format yaml` — то, что ты приложишь к заявке на изменение.

**8. S3-совместимое хранилище через aws-cli.** Работает во всех четырёх облаках, меняется только endpoint.

```bash
aws --endpoint-url https://storage.yandexcloud.net s3 ls
aws s3 cp backup.tar.gz s3://vektor-backup/db/backup.tar.gz --endpoint-url https://storage.yandexcloud.net
```

Один инструмент — четыре облака, это главный плюс S3-совместимости (подробно в уроке 93).

**9. OpenStack CLI для VK Cloud и Selectel.** Оба построены на OpenStack, поэтому стандартный клиент видит их ресурсы после загрузки `openrc`.

```bash
openstack server list
openstack network list
openstack token issue
```

Удобно для инвентаризации: `openstack server list -f json` отдаёт всё разом.

**10. Terraform — «инфраструктура как код».** Провайдеры: `yandex`, `vkcs`, `selectel`, для Cloud.ru — `sbercloud`/`cloudru` [ПРОВЕРИТЬ актуальное имя в registry.terraform.io].

```hcl
terraform {
  required_providers {
    yandex = { source = "yandex-cloud/yandex" }
  }
}
provider "yandex" {
  cloud_id  = var.cloud_id
  folder_id = var.folder_id
  zone      = "ru-central1-a"
}
```

Токен — через переменную окружения `YC_TOKEN`, не в файле.

**11. Эмуляция облака на своём стенде (PVE01).** Права, пулы и API-токены Proxmox — прямая аналогия облачного IAM:

```bash
pveum user list
pveum role list
pveum pool add vektor-prod --comment "Прод-нагрузки"
pveum acl modify /pool/vektor-prod --users ivanov@pve --roles PVEVMUser
pveum user permissions ivanov@pve
pveum user token add adm.student@pve cloudru-demo --privsep 0
```

`--privsep 0` означает «токен наследует все права пользователя» — так делать в бою нельзя, только для лабы.

**12. Проверка API руками.**

```bash
curl -s -k -H "Authorization: PVEAPIToken=adm.student@pve!cloudru-demo=<UUID>" \
  https://10.10.10.70:8006/api2/json/nodes
```

Если консоль отвечает, а curl — нет, проблема в токене/правах, а не в «сломалось». `-k` отключает проверку сертификата — на стенде допустимо, в бою нет.

### Сломай и почини

**Заявка INC-91-002**
- **Пользователь:** ivanov (доменная учётка, работает на WIN11-CL01)
- **ВМ:** PVE01 / веб-интерфейс `https://10.10.10.70:8006`
- **Что написал:** «Захожу в Proxmox под своей доменной учёткой, вижу ВМ `tst-cloud01`, но кнопка запуска неактивна, при попытке — "Permission check failed (VM.PowerMgmt)". Вчера всё работало.»
- **Срочность:** высокая.

**Воспроизведение поломки.** На PVE01: `pveum acl modify /pool/vektor-dev --groups <группа> --roles PVEVMUser --delete` (снимаем права).

**Диагностика по шагам:**
1. Кто ты для системы: `pveum user permissions <user>@vektor` — пусто или только `/`-права. Значит, дело не в ВМ.
2. Что вообще выдано: `pveum acl list` — есть ли запись на `/pool/vektor-dev` для нужной группы.
3. Существует ли пользователь и группа: `pveum user list`, `pveum group list`. Если пользователя нет — сломался AD-realm (упал DC01, истёк bind-пароль, истекла учётка).
4. Логи: `journalctl -u pvedaemon -n 50 --no-pager` и `/var/log/pveproxy/access.log` — ищем `permission denied` и `authentication failure`.
5. Проверка снаружи: `curl` с токеном `adm.student@pam` — если админский токен работает, API жив, проблема строго в ACL/ realm.

**Решение.** `pveum acl modify /pool/vektor-dev --groups <группа> --roles PVEVMUser`. Если причина в realm — Datacenter → Permissions → Realms → Sync (и проверить bind-пароль).

## 6. Ошибки новичков и безопасность

1. **Публичный IP + правило `0.0.0.0/0` на 22/3389** → SSH-брутфорс начинается в первые минуты, а через час в логах уже тысячи попыток → открывай только из `10.10.10.0/24` (или адреса офиса) и ставь бастион/VPN.
2. **Статический ключ доступа в скрипте на ВМ или в git** → утечка = чужой доступ к бакету и к API, и никакого следа, кроме счёта → ключи только в переменных окружения / секрет-хранилище, `chmod 600`, ротация по регламенту.
3. **Роль `editor`/`admin` сервисному аккаунту «чтобы работало»** → компромисс робота = компромисс всего проекта → отдельный SA на каждую задачу с минимальной ролью на конкретный ресурс.
4. **Один проект на прод и дев** → случайное удаление сети или квоты в час пик сносит прод → минимум два проекта/каталога, разные бюджеты.
5. **Забыли про исходящий трафик при расчёте** → счёт в разы больше ожидаемого, потому что egress платный, а ingress обычно нет → egress в ТЗ и в бюджете, алерт на 50/80/100% бюджета.
6. **Не удалили тестовые ВМ/диски после эксперимента** → «остановленная ВМ» продолжает тарифицироваться за диск и IP → ревизия ресурсов раз в неделю, теги/пометки, бюджет с жёстким порогом.
7. **Не проверили квоты (лимиты по умолчанию)** → в нужный час ВМ не создаётся, а заявка на квоту рассматривается сутки → заявку на квоты подавать до миграции, а не в день Х.
8. **Считают, что «облако = бэкап»** → отказ зоны или удаление каталога руками уносит данные → собственная резервная копия + межзонная/межрегиональная репликация (уроки 89 и 93).

**Безопасность (что нельзя в боевой среде):** держать ПДн граждан РФ за пределами РФ (нарушение 152-ФЗ, ч. 5 ст. 18) — проверять, в каком регионе создан ресурс; заводить ИТ-доступ без второго фактора — 2FA обязательна везде, где провайдер её даёт; использовать одну общую учётку на нескольких людей — нет персональной ответственности и аудита; включать `--privsep 0` на токенах (как в лабе) — токен должен иметь минимальные права и срок жизни; строить гибридный канал между офисом и облаком на «открытом» IPsec без ГОСТ-криптографии, если объект относится к КИИ — там нужны сертифицированные СКЗИ (КриптоПро, VipNet) и проект по приказу ФСТЭК № 17.

## 7. Вопросы на собеседовании

**1. «Какие российские облака знаешь? Чем Яндекс Облако отличается от Selectel, что бы выбрал под 1С+PostgreSQL?»**
Ответ: «Четыре основных — Яндекс Облако, VK Cloud, Selectel, Cloud.ru. Все дают IaaS, VPC с security groups, S3-совместимое хранилище и managed-БД. Отличия: Яндекс Облако — самая развитая PaaS и управляемые сервисы, свой CLI `yc` и зрелый Terraform; VK Cloud — на OpenStack, удобно мигрировать с OpenStack и с зарубежных облаков, стандартный `openstack` CLI; Selectel — сильный по «железу» (выделенные серверы, colocation) плюс облако, часто дешевле на длинной дистанции и стабильнее по bare metal; Cloud.ru — сильнее в enterprise/гос, у них два сегмента, Evolution и Advanced. Под 1С я бы смотрел на managed PostgreSQL с репликой + зонами доступности, наличие готовых образов 1С и требования по аттестации, а потом уже на цену — сравнив калькуляторы по одинаковому ТЗ.»
*Что хочет услышать:* что ты сравниваешь по критериям, а не «мне нравится это».
*Красный флаг:* «Яндекс круче, потому что он большой» без критериев и без упоминания managed-сервисов, сети и денег.

**2. «Как организуешь сеть в облаке под веб-приложение?»**
Ответ: «Разбиваю на две подсети в разных зонах доступности: публичная — только балансировщик и бастион, приватная — приложение и БД без публичных IP, выход в интернет через NAT-шлюз. Security groups: ingress на 443 только с балансировщика, на 22 — только с бастиона или адреса офиса, БД принимает только с security group приложения, а не по CIDR. Отдельный проект для прода и для дева. Диапазон адресов беру из общего плана адресации, чтобы не конфликтовать с офисными 10.10.10.0/24 и DMZ 10.10.20.0/24 — иначе гибридный VPN не поднимется.»
*Что хочет услышать:* зоны доступности, приватные подсети, SG вместо CIDR там, где можно.
*Красный флаг:* «Всё в одну сеть, всем 0.0.0.0/0, потом разберёмся».

**3. «Как выдать приложению доступ к S3, не храня пароль?»**
Ответ: «Создаю сервисный аккаунт с ролью только на запись в конкретный бакет, выдаю статический ключ доступа, кладу его не в код, а в переменные окружения или секрет-хранилище, файл с ключом — `chmod 600` и вне git. Дальше ротация по регламенту и отдельный ключ на каждую систему. Если ВМ внутри облака — лучше вообще без ключей: роль на инстанс, тогда креды подставляются автоматически.»
*Что хочет услышать:* минимальные права + отсутствие секретов в коде + ротация.
*Красный флаг:* «Захардкожу ключ в скрипте, он же в закрытом репозитории».

**4. «Из чего складывается счёт в облаке и как его уменьшить?»**
Ответ: «Вычисления (vCPU+RAM × часы работы), диски (ГБ × месяц, платятся, даже когда ВМ остановлена), публичные IPv4 (× часы), исходящий трафик в интернет, снапшоты и бэкапы, managed-сервисы по своим тарифам. Уменьшать: остановка и удаление неиспользуемого, резервируемые ресурсы/долгосрочные тарифы вместо pay-as-you-go, автоскейл вместо «всегда 8 vCPU», вынос холодных данных в объектное хранилище с lifecycle-политикой, бюджеты и алерты.»
*Что хочет услышать:* понимание, что остановка ≠ бесплатно, и что трафик считают.
*Красный флаг:* «Облако экономит деньги само по себе».

**5. «Какие требования РФ влияют на выбор облака?»**
Ответ: «Локализация персональных данных в РФ — 152-ФЗ, ч. 5 ст. 18, плюс уведомление РКН как оператора ПДн. Для КИИ — 187-ФЗ и требования ФСТЭК по приказу № 17: классы защищённости, УЗ-1…УЗ-3, сертифицированные СКЗИ для каналов. Для госсектора — реестр отечественного ПО и аттестованные сегменты. На практике проверяю: в каком регионе физически лежат данные, есть ли аттестованный контур, кто оператор и что в договоре про доступ правоохранительных органов и удаление данных.»
*Что хочет услышать:* конкретные номера законов и понимание, что «сервер в Москве» ≠ «соответствие 152-ФЗ».
*Красный флаг:* «У всех всё сертифицировано, это маркетинг».
