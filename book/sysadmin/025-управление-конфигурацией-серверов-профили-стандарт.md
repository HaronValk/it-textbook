# Управление конфигурацией серверов: профили, стандарты, hardening, шаблоны сборки

## 1. Введение (зачем это нужно в реальной работе)

Тикет #2514 в очереди «Вектор-IT»:

> **Пользователь:** ivanov (бухгалтерия), ВМ WIN11-CL01
> **Что написал:** «WinSCP перестал подключаться к UBU01, пишет Access denied. Мне до 15:00 нужно отправить выгрузку в банк. И ещё: аудитор спросил, почему на серверах разные настройки SSH и кто-то до сих пор ходит под root.»
> **Срочность:** высокая

Ты открываешь UBU01, потом ASTRA01, потом вспоминаешь, что WEB01 в DMZ настраивал вообще в другой день — и понимаешь неприятное: три сервера живут по трём разным правилам. Где-то `PermitRootLogin yes`, где-то пароли разрешены, где-то нет. Никто не помнит, кто и зачем это менял, потому что правки шли руками через SSH и нигде не фиксировались.

Это и есть управление конфигурацией: дисциплина, при которой у каждого сервера есть **профиль** (набор настроек под его роль), профиль соответствует **стандарту** (документу с требованиями), настройки применяются автоматически из **шаблона/репозитория**, а любое отклонение видно и объяснимо. После этой главы ты будешь уметь: разложить парк серверов на профили, собрать эталонный профиль в Git, прогнать его через Ansible идемпотентно, замерить уровень защищённости до и после (Lynis, OpenSCAP, `systemd-analyze security`), подготовить шаблон ВМ к клонированию и оформить всё это как внутренний стандарт `STANDARD-LNX-01`, на который можно ссылаться перед аудитором и на собеседовании.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Управление конфигурацией стоит на трёх китах.

**1. Состояние (state), а не скрипт.** Скрипт говорит «сделай шаг» и при повторном запуске сделает его ещё раз. Инструмент управления конфигурацией (Ansible, Puppet, Chef, SaltStack) описывает **желаемое состояние**: «в файле `sshd_config` строка `PermitRootLogin` равна `no`». Повторный прогон ничего не меняет — это называется **идемпотентность**. Idempotent — от лат. «то же самое действие даёт тот же результат».

**2. Эталон и профили.** Эталон (baseline, он же стандарт) — документ: список требований с ID, способом проверки и критичностью. Профиль — техническая реализация эталона для конкретной роли. Профили наследуются: общий `base` → отраслевой `linux-hardening` → ролевой (`webserver`, `fileserver`, `jump`) → `host_vars` для конкретной машины. Важно: **переопределение на уровне хоста — это исключение**, и оно должно быть записано в реестр исключений с фамилией того, кто разрешил. Иначе через полгода никто не скажет, почему на одном сервере иначе.

**3. Контроль дрейфа (configuration drift).** Дрейф — расхождение реального состояния с эталоном. Причины: ручные правки «на минутку», полуприменившиеся патчи, восстановление из старого бэкапа, клонирование ВМ из устаревшего шаблона. Обнаруживается тремя способами: `ansible-playbook --check --diff` (показать, что изменилось бы), сканер соответствия (OpenSCAP, Lynis), сверка с Git-историей.

Схема профилей для стенда «Вектор»:

```text
base  ──┬─ users/sudo, часовой пояс Europe/Moscow, chrony, journald, пакеты, motd
        │
        └─ linux-hardening ──┬─ OpenSSH (порт 22/tcp, key-only, AllowGroups)
                             ├─ sysctl-min (только базовый минимум, глубже — урок 26)
                             ├─ auditd + правила на /etc/passwd, /etc/sudoers, /etc/ssh
                             └─ лимиты ресурсов, umask 027

  profile: webserver   → nginx, TLS, отдельный пользователь, NoNewPrivileges
  profile: monitoring  → zabbix-agent, скрипты, доступ только с MON01
  profile: jump        → только SSH, никаких пакетов сверху

host_vars/astra01.yml → исключения (с записью в реестр)
```

Конвейер применения:

```text
Git (эталон) → lint (ansible-lint) → --check --diff на пилоте (1 хост)
   → канарейка → волна 1 (10%) → волна 2 (остальные)
   → отчёт соответствия (oscap report) → запись в реестр конфигураций
   → при регрессии: git revert + повторный прогон
```

**Откуда берутся стандарты.** Международные: **CIS Benchmarks** (Center for Internet Security — постатейные чек-листы под конкретную ОС и версию, уровни L1/L2), **DISA STIG** (жёстче, военная специфика). Открытая реализация — проект **SCAP Security Guide** (SSG): те же требования в машинночитаемом формате SCAP, который умеет проверять `oscap`. Российские: приказы ФСТЭК России № 17 (ГИС) и № 21 (персональные данные) задают состав мер, «Методика оценки угроз безопасности информации» ФСТЭК (2021) — модель угроз, ГОСТ Р 57580.1 — банковская сфера. Они не дают готовых команд: они дают требования («ограничение числа попыток входа», «журналирование событий безопасности»), а ты сам переводишь их в строки конфига и в проверки. Для Astra Linux SE добавляется мандатный контроль и режим защищённости (урок 31).

Не путать: **профиль конфигурации** (наш набор настроек) и **профиль AppArmor/SELinux** (политика доступа приложения к файлам и сокетам) — разные сущности, хотя слово одно.

## 3. Аналогия из жизни

Типовой проект жилого дома. Есть СНиП и ГОСТ — это **стандарт**, по нему нельзя строить лестницу с шириной 20 см. Есть типовой проект серии — это **профиль**: девятиэтажка с одним подъездом, планировки одинаковые. Есть застройщик, который по этому проекту ставит сразу двадцать домов — это **шаблон сборки**: бетон, арматура, те же чертежи, те же приёмки. Есть служба технадзора, которая приходит на готовый объект с чек-листом и ищет отступления — это **сканер соответствия**. И есть отдельный дом, где жильцы самовольно снесли стену между кухней и комнатой — это **дрейф конфигурации**; он не обязательно катастрофа, но должен быть согласован, задокументирован и внесён в проект.

Аналогия перестаёт работать в одном месте: дом строят один раз, а сервер перестраивают при каждом патче, поэтому чертёж обязан обновляться одновременно со зданием — иначе через месяц по нему уже никто не сможет ничего проверить.

## 4. Практика и команды

**1. Инвентарь и проверка связи.** База любой автоматизации — список хостов с ролями.

```bash
cd /srv/stand-config
ansible-inventory --graph          # дерево групп и хостов
ansible all -m ansible.builtin.ping  # проверка SSH + python на цели
```

```text
@all:
  |--@linux:
  |  |--astra01
  |  |--ubu01
  |--@dmz:
  |  |--web01
```

`--graph` рисует иерархию групп (важно: хост в нескольких группах получит переменные всех). `ping` здесь — не ICMP, а модуль Ansible: подключается по SSH (22/tcp) и запускает Python. `SUCCESS => {"ping": "pong"}` — связь есть.

**2. Факты о системе — основа профилирования.** Один профиль, разные дистрибутивы — значит, решения принимаются по фактам.

```bash
ansible linux -m ansible.builtin.setup \
  -a 'filter=ansible_distribution*,ansible_kernel,ansible_service_mgr'
```

```text
astra01 | SUCCESS => {
  "ansible_distribution": "Astra Linux (Orel)",
  "ansible_distribution_major_version": "1.7",
  "ansible_kernel": "6.1.0-...",
  "ansible_service_mgr": "systemd"
}
```

Смотрим `ansible_distribution` и `ansible_os_family` (`Debian`/`RedHat`) — от них зависят менеджер пакетов и имена сервисов.

**3. Аудит действующего конфига SSH.** `sshd -T` печатает **эффективную** конфигурацию — со всеми `Include`, дефолтами и блоками `Match`. Это главный инструмент аудита: файл на диске и реальность могут отличаться.

```bash
sudo sshd -T | grep -Ei 'permitrootlogin|passwordauthentication|maxauthtries|allowgroups|x11forwarding'
```

```text
permitrootlogin without-password
passwordauthentication yes
maxauthtries 6
x11forwarding yes
```

Читаем: вход root по ключу разрешён (некритично, но в эталоне `no`), пароли разрешены (**это и есть причина тикета**), 6 попыток вместо 3, X11 не нужен на сервере. Проверить конкретного пользователя с учётом `Match`: `sudo sshd -T -C user=ivanov,host=ubu01,addr=10.10.10.100`.

**4. Проверка синтаксиса перед перезапуском.** Классика: сломанный `sshd_config` → сервис не стартует → ты потерял доступ.

```bash
sudo sshd -t && echo OK
sudo sshd -t -f /etc/ssh/sshd_config.d/50-stand-hardening.conf
```

`-t` — только тест, `-f` — тест конкретного файла. Молчание = ошибок нет. В Ansible это делается параметром `validate:` у модуля `lineinfile`/`template` — файл не будет записан, если не прошёл проверку.

**5. Структура репозитория эталона.**

```bash
mkdir -p /srv/stand-config/{group_vars,host_vars,roles/base/tasks,roles/linux_hardening/{tasks,templates,handlers}}
cd /srv/stand-config && git init && printf '*.retry\n*.log\n' > .gitignore
git add -A && git commit -m "init: скелет эталона стенда Вектор"
```

`group_vars/linux.yml` — переменные для всей группы, `host_vars/astra01.yml` — исключения. Правило: **в `host_vars` не бывает «просто так»**, каждая строка — со ссылкой на тикет.

**6. Фрагмент роли: hardening SSH с валидацией.**

```yaml
# roles/linux_hardening/tasks/ssh.yml
- name: Эталонный sshd_config (drop-in)
  ansible.builtin.template:
    src: 50-stand-hardening.conf.j2
    dest: /etc/ssh/sshd_config.d/50-stand-hardening.conf
    owner: root
    group: root
    mode: "0644"
    validate: /usr/sbin/sshd -t -f %s
  notify: restart ssh

- name: Проверить эффективные параметры
  ansible.builtin.command: sshd -T
  register: sshd_effective
  changed_when: false

- name: Зафиксировать факт в логе прогона
  ansible.builtin.debug:
    msg: "{{ sshd_effective.stdout_lines | select('match', 'permitrootlogin|passwordauthentication') | list }}"
```

`validate:` — страховка от синтаксической ошибки. `changed_when: false` — команда только читает, не считается изменением (иначе идемпотентность «сломается» в отчёте).

**7. Сухой прогон и применение.** Основной рабочий цикл.

```bash
ansible-playbook site.yml --check --diff --limit astra01
ansible-playbook site.yml --diff --limit astra01
ansible-playbook site.yml --diff            # повторно — должно быть changed=0
```

```text
TASK [linux_hardening : Эталонный sshd_config (drop-in)] ***
--- before: /etc/ssh/sshd_config.d/50-stand-hardening.conf
+++ after:  /etc/ssh/sshd_config.d/50-stand-hardening.conf
-PasswordAuthentication yes
+PasswordAuthentication no

astra01 : ok=14 changed=3 failed=0
```

`--check` — ничего не менять, `--diff` — показать построчную разницу, `--limit` — сузить до пилота. Второй прогон без `--check` должен дать `changed=0`; если снова `changed>0` — роль неидемпотентна, ищи `command`/`shell` без условий.

**8. Перезапуск SSH на Ubuntu 24.04 — с подвохом.** В 24.04 sshd запускается через сокет-активацию, и `systemctl restart ssh` может не подхватить конфиг.

```bash
sudo systemctl daemon-reload
sudo systemctl restart ssh.socket
systemctl status ssh.socket --no-pager
```

В Ansible это описывается хендлером с двумя задачами (`systemd: name=ssh.socket state=restarted`). Если после правки «ничего не изменилось» — почти всегда дело в этом.

**9. Оценка защищённости юнита systemd.** Показывает, сколько «лишних» возможностей получает сервис.

```bash
systemd-analyze security ssh.service --no-pager
```

```text
→ Overall exposure level for ssh.service: 9.6 UNSAFE 😨
```

9.6 — почти максимум незащищённости: у сервиса нет `ProtectSystem`, `PrivateTmp`, ограничений системных вызовов. Для sshd это частично нормально (он обязан читать многое), но для внутренних сервисов оценка < 5 достижима drop-in'ом с `NoNewPrivileges=yes`, `PrivateTmp=yes`, `ProtectSystem=strict`. Осторожно: `ssh.service` жёстко ограничивать нельзя — сломается аутентификация.

**10. Сканер соответствия: Lynis.** Быстрый аудит без настройки профилей, читает всё локально.

```bash
sudo apt install -y lynis
sudo lynis audit system --quick
```

```text
Hardening index : 62 [############        ]
Suggestions (28):
  * Consider hardening SSH configuration [SSH-7408]
  * Install a malware scanner [HRDN-7230]
```

Смотрим `Hardening index` (растёт после применения профиля), раздел `Suggestions` и `/var/log/lynis-report.dat`. Это не сертификация, а индикатор и подсказки.

**11. Сканер соответствия: OpenSCAP.** Формальная проверка по профилю CIS из SSG, с отчётом для аудитора.

```bash
sudo apt install -y libopenscap8            # контент SSG: пакет ssg-debderived [ПРОВЕРИТЬ]
ls /usr/share/xml/scap/ssg/content/         # ssg-ubuntu2404-ds.xml [ПРОВЕРИТЬ]
sudo oscap xccdf eval \
  --profile xccdf_org.ssgproject.content_profile_cis_level1_server \
  --results /var/log/oscap-results.xml \
  --report /var/log/oscap-report.html \
  /usr/share/xml/scap/ssg/content/ssg-ubuntu2404-ds.xml
```

```text
Title   Ensure SSH root login is disabled
Rule    xccdf_org.ssgproject.content_rule_sshd_disable_root_login
Result  pass
```

Код возврата `2` означает «есть непройденные правила», а не «ошибка запуска» — это важно в CI. HTML-отчёт `oscap-report.html` прикладывается к акту проверки.

**12. Контроль целостности пакетов.** Дрейф бывает не только в конфигах, но и в бинарниках.

```bash
sudo dpkg --verify                      # Debian/Ubuntu/Astra
sudo debsums -c                         # только изменённые файлы (пакет debsums)
sudo rpm -Va                            # ALT Linux и другие RPM-системы
sudo find / -xdev -perm -4000 -type f   # SUID-бинарники: должно быть ровно столько, сколько в стандарте
```

`dpkg --verify` печатает строки вида `??5??????   /usr/bin/passwd` — код `5` в третьей позиции значит «изменилась контрольная сумма». Для SUID: любая находка вне белого списка — разбор.

**13. Подготовка эталона к клонированию (шаблон сборки).** ВМ нельзя клонировать «как есть»: получатся одинаковые machine-id и SSH-ключи хоста.

```bash
sudo cloud-init clean --logs
sudo truncate -s 0 /etc/machine-id
sudo rm -f /etc/ssh/ssh_host_*
sudo rm -rf /var/log/journal/* && sudo journalctl --rotate --vacuum-time=1s
history -c
```

`cloud-init clean` убирает следы первичной инициализации, `machine-id` и host keys создадутся заново при первом запуске клона. `history -c` — гигиена: в истории не должно остаться секретов. Для offline-образов то же делает `virt-sysprep` (пакет `libguestfs-tools`) — `virt-sysprep --list-operations` покажет доступные операции.

**14. Реестр изменений и журнал.** Без этого управление конфигурацией превращается в «ещё один Ansible».

```bash
cd /srv/stand-config && git log --oneline -5
git show --stat HEAD
```

Смотрим автора, дату, затронутые файлы. Правило: изменение попадает в Git **до** применения, а не после; сообщение коммита содержит ID тикета.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

Стенд L2 готов. Нужны: **UBU01** (10.10.10.30, Ubuntu Server 24.04, играет роль control node — машины, откуда запускается Ansible), **ASTRA01** (10.10.10.31, Astra Linux CE — «второй дистрибутив» для проверки универсальности профиля), **PVE01** (10.10.10.70, гипервизор для шаблона), опционально **WEB01** (10.10.20.10, доступен с UBU01 через GW01 10.10.10.3). На UBU01 и ASTRA01 ты работаешь под локальной учёткой `adm.student` с sudo. На UBU01 есть локальный пользователь `ivanov` в группе `sftp-users` (создан в главах про SSH; если нет — `sudo useradd -m -G sftp-users -s /bin/bash ivanov` и задай учебный пароль стенда). Ansible: `sudo apt install -y ansible` на UBU01.

### Снапшот

В VMware Workstation: правый клик по ВМ → **Snapshot → Take Snapshot**, имя `before-sysadmin-025` — на **UBU01**, **ASTRA01**, **PVE01**. В PVE01: выбрать ВМ → **Snapshots → Take snapshot**, имя то же. Записать в `stand-log.md`: «025: снапшоты сняты на UBU01, ASTRA01, PVE01».

### Шаги

1. **UBU01.** Создать репозиторий эталона: команды из п. 4.5. Ожидаемо: `git log` показывает один коммит «init: скелет эталона».
2. **UBU01.** Сгенерировать ключ для автоматизации: `ssh-keygen -t ed25519 -N '' -f ~/.ssh/id_stand` и скопировать публичную часть на ASTRA01 (`ssh-copy-id -i ~/.ssh/id_stand.pub adm.student@10.10.10.31`). Ожидаемо: вход на ASTRA01 без пароля.
3. **UBU01.** Заполнить `inventory.ini` (`[linux]` ubu01, astra01; `[dmz]` web01) и `ansible.cfg` (`inventory`, `host_key_checking = False` **только на стенде**, `stdout_callback = yaml`). Проверить `ansible-inventory --graph` и `ansible all -m ansible.builtin.ping`. Ожидаемо: `pong` от обоих хостов.
4. **UBU01 и ASTRA01.** Зафиксировать «как есть»: `sudo sshd -T | grep -Ei 'permitrootlogin|passwordauthentication|maxauthtries'` на каждой машине. Ожидаемо: значения **различаются** — это и есть дрейф, сохрани вывод в `stand-log.md`.
5. **UBU01.** Написать `roles/linux_hardening/templates/50-stand-hardening.conf.j2` с `PermitRootLogin no`, `PasswordAuthentication no`, `KbdInteractiveAuthentication no`, `MaxAuthTries 3`, `LoginGraceTime 30`, `AllowGroups ssh-users sftp-users sudo`, `X11Forwarding no`, и задачу с `validate:` (п. 4.6). Ожидаемо: файл сохранён, `ansible-lint` не ругается.
6. **UBU01.** Прогнать `ansible-playbook site.yml --check --diff --limit astra01`. Ожидаемо: список `TASK` со статусом `changed`, реальных изменений нет, в diff видно `-PasswordAuthentication yes / +PasswordAuthentication no`.
7. **UBU01.** Применить на пилоте: `ansible-playbook site.yml --diff --limit astra01`. Ожидаемо: `changed=2 failed=0`, хендлер перезапустил `ssh.socket`. **Не закрывая текущую сессию**, открыть вторую и проверить вход по ключу.
8. **UBU01.** Повторить прогон: `ansible-playbook site.yml --diff --limit astra01`. Ожидаемо: `changed=0` — роль идемпотентна.

## 6. Ошибки новичков и безопасность

1. **Правка прода руками мимо Git.** → Через месяц никто не знает, почему конфиг такой; следующий прогон профиля молча затирает правку. → Правильно: изменение только через репозиторий и `--check --diff`, руками — лишь диагностика.
2. **Применение hardening без второго канала доступа.** → `PermitRootLogin no` + `PasswordAuthentication no` при отсутствии ключа у админа = потеря сервера. → Правильно: ключ проверен, вторая сессия открыта, консоль/ILO/VE-консоль PVE01 доступна, снапшот снят.
3. **Копирование профиля CIS Level 2 «как есть».** → На файловом сервере отваливается нужное, на jump-хосте ломается аутентификация. → Правильно: начинать с Level 1, каждое отклонение — в реестр исключений с обоснованием.
4. **`lineinfile` без `validate`.** → Синтаксическая ошибка в `sshd_config`, сервис не поднимается после restart. → Правильно: `validate: /usr/sbin/sshd -t -f %s` и тест на пилоте.
5. **Забыли про сокет-активацию SSH на Ubuntu 24.04.** → Конфиг правильный, поведение старое, «магия». → Правильно: `systemctl restart ssh.socket` в хендлере и проверка через `sshd -T`.
6. **Клонирование ВМ без sysprep-подготовки.** → Два хоста с одинаковыми `machine-id` и SSH host keys: странные логи, конфликты, предупреждения `REMOTE HOST IDENTIFICATION HAS CHANGED`. → Правильно: чистить `machine-id`, host keys, `cloud-init clean` перед превращением в шаблон.
7. **Секреты в репозитории.** → Пароли, токены и приватные ключи в Git-истории навсегда. → Правильно: `ansible-vault`, внешнее хранилище секретов, `.gitignore`, проверка в CI.
8. **Шаблон обновили — парк не пересобрали.** → Новые ВМ по стандарту, старые — нет; «эталон» существует в двух версиях. → Правильно: пересборка по волнам, отчёт соответствия, реестр версий шаблона.

### Безопасность

В боевой среде нельзя: отключать SELinux/AppArmor «чтобы работало» (это снятие целого слоя защиты и почти всегда повод для инцидента), возвращать `PermitRootLogin yes` и `PasswordAuthentication yes` ради удобства одного пользователя, хранить приватные ключи и пароли в Git, применять профили на парк без change-процедуры и окна, отключать `auditd` из-за объёма логов. Любое ослабление — это документированное исключение с владельцем, сроком и компенсирующей мерой, а не «так исторически сложилось».

## 7. Вопросы на собеседовании

**1. Чем управление конфигурацией отличается от автоматизации?**
Ответ: автоматизация выполняет действия (скрипт ставит пакет, правит файл, перезапускает сервис). Управление конфигурацией описывает целевое состояние и приводит систему к нему, обеспечивая идемпотентность: повторный запуск не меняет ничего. Плюс к этому — эталон в репозитории, контроль дрейфа, отчёт соответствия, реестр исключений и прослеживаемость «требование → конфиг → проверка». Автоматизация — инструмент, управление конфигурацией — процесс.
*Что хочет услышать:* слово «идемпотентность», «состояние, а не шаги», «эталон в Git», «контроль дрейфа».
*Красный флаг:* «это одно и то же» или «Ansible и есть управление конфигурацией».

**2. Что такое configuration drift и как вы его обнаруживаете?**
Ответ: расхождение реального состояния с эталоном. Обнаружение: `ansible-playbook --check --diff` по расписанию, сканеры соответствия (OpenSCAP/SSG, Lynis), сверка контрольных сумм пакетов (`dpkg --verify`, `debsums -c`), сверка SUID-списка с белым списком, сравнение `host_vars` с реестром исключений. Причины: ручные правки, неполные патчи, старые бэкапы, клоны из устаревшего шаблона.
*Что хочет услышать:* конкретные команды и понимание, что дрейф бывает и в конфигах, и в бинарниках, и в самом шаблоне.
*Красный флаг:* «дрейфа у нас нет, мы всё делаем руками и одинаково».

**3. Как внедрить hardening на 50 серверов и не положить прод?**
Ответ: эталон в Git, снапшоты и бэкапы, пилот на одном небоевом хосте, `--check --diff`, канарейка, затем волны по 10% с паузой и наблюдением, всегда живой второй канал доступа (консоль гипервизора, out-of-band), заранее согласованное окно и план откатa (`git revert` + повторный прогон). После волны — отчёт OpenSCAP и запись в реестр конфигураций.
*Что хочет услышать:* поэтапность, второй канал, откат, коммуникация с владельцами сервисов.
*Красный флаг:* «запущу на всех сразу ночью».

**4. Golden image или управление конфигурацией — что выбрать?**
Ответ: не «или». Базовый образ даёт предсказуемую отправную точку (ОС, агент, ключи, разметка), управление конфигурацией доводит его до роли и удерживает состояние. Для иммутабельной инфраструктуры (контейнеры, автоскейл) — пересборка образа при каждом изменении; для «домашних животных» (долгоживущие серверы, 1С, AD) — управление конфигурацией поверх образа. Гибрид: пересобираем образ ежемесячно, между пересборками держим состояние плейбуками.
*Что хочет услышать:* pets vs cattle, понимание, что шаблон надо версионировать и пересобирать.
*Красный флаг:* «мы просто клонируем ВМ и правим руками».

**5. Какие требования влияют на ваш стандарт конфигурации в РФ?**
Ответ: приказы ФСТЭК России № 17 (ГИС) и № 21 (персональные данные) задают состав мер — идентификация, управление доступом, регистрация событий, контроль целостности; «Методика оценки угроз безопасности информации» ФСТЭК формирует модель угроз; ГОСТ Р 57580.1 — для финансового сектора; отраслевые требования и уровни защищённости. Практически: каждый пункт стандарта трассируется на меру из документа, проверяется командой и попадает в отчёт. Для Astra Linux SE добавляются режим защищённости и мандатный контроль.
*Что хочет услышать:* трассировка «требование → мера → проверка → отчёт», понимание, что нормативка не даёт готовых команд.
*Красный флаг:* называет несуществующие номера приказов или говорит, что «достаточно поставить антивирус».
