# Межсетевые экраны нового поколения (NGFW): Check Point, FortiGate, UserGate, Ideco — политики, VPN, IPS

## 1. Введение (зачем это нужно в реальной работе)

Тикет в helpdesk «Вектора»: **Пользователь:** ivanov / ВМ WIN11-CL01. **Что написал:** «Не открывается https://portal.vektor.lab из офиса — ERR_CONNECTION_TIMED_OUT. При этом ping до 10.10.20.10 проходит. Из дома через VPN тоже не пускает. Срочность: высокая, закрываем период, бухгалтерия не может сдавать документы». **Статус:** открыт 20 минут назад, до этого портал работал.

Через полчаса выясняется: ночью коллега «навёл порядок» в правилах на периметре и поставил блокирующее правило выше разрешающего, а IPS после обновления баз начал резать запросы портала, приняв длинный POST за атаку. Классическая история: firewall «работает», а бизнес стоит. Эта глава про то, как NGFW устроен внутри, как его настраивать политиками, а не «кнопкой allow any», как включать IPS так, чтобы не убить 1С и портал, как поднимать VPN и — главное — как диагностировать «не работает через фаервол» за 10 минут, а не за три часа. После главы ты должен уметь: прочитать политику сверху вниз, объяснить, почему правило не сработало, поднять VPN-туннель и увидеть в логах, какой именно блок валит трафик.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Классический stateful-фаервол (netfilter/nftables, pf, iptables) смотрит на L3/L4: адрес, порт, флаг TCP и таблицу состояний (`conntrack`). NGFW делает то же самое плюс **DPI** — глубокую инспекцию пакетов до L7: определяет приложение (это точно HTTPS или это SSH, замаскированный под 443), пользователя (через интеграцию с AD), категорию сайта, содержимое и сигнатуры атак.

Типовые модули (их называют blades/профилями/модулями):

- **Stateful inspection** — база, таблица сессий.
- **Application Control** — распознавание приложений по сигнатурам, а не по портам.
- **IPS** (Intrusion Prevention System) — сигнатуры атак (движки Suricata/Snort и вендорские), режим Detect (только логи) или Prevent (дроп).
- **Anti-Virus / Anti-Bot** — файлы и C2-трафик.
- **URL/Web-фильтрация** — категории, репутация, geo-IP.
- **TLS-инспекция (SSLi)** — подмена сертификата, расшифровка, проверка, обратное шифрование.
- **Identity Awareness** — кто именно из AD это делает (LDAP, агенты, Captive Portal, Kerberos).
- **VPN** — site-to-site и remote access.
- **Логирование/SIEM** — syslog, netflow, отчёты.

Архитектурно у вендоров два подхода. **Check Point**: разделение на Security Management Server (SmartConsole, policy) и Security Gateway (data plane, enforcement); между ними защищённый канал SIC [ПРОВЕРИТЬ порт 18184]. **FortiGate** — «всё в одной коробке» FortiOS: firewall policy + UTM-профиль + NAT в одном правиле; для парка машин — FortiManager. **UserGate** — Management Server + NGFW-ноды, кластер с синхронизацией сессий. **Ideco NGFW** — Linux-based шлюз безопасности с модулями (файрвол, IPS, веб-фильтр, VPN) и веб-консолью управления. Общее у всех: **политика читается сверху вниз, первое совпадение выигрывает, в конце — неявный deny**.

Схема стенда после этой лабораторной:

```text
      VMnet8 10.10.10.0/24 (офис)                VMnet10 10.10.20.0/24 (DMZ)
  ┌──────────────────────────────┐           ┌──────────────────────────────┐
  │ DC01 .10 (AD/DNS/DHCP)       │           │                              │
  │ FS01 .20                     │           │   WEB01 .10  nginx           │
  │ WIN11-CL01 DHCP              │           │   gw 10.10.20.2              │
  │ UBU01 .30                    │           │                              │
  │ GW01 .3  (маршрутизатор L2)  │           │                              │
  └───────────┬──────────────────┘           └───────────┬──────────────────┘
              │                                          │
        ┌─────┴──────────────────────────────────────────┴─────┐
        │  NGFW01  WAN 10.10.10.4/24  ──►  LAN 10.10.20.2/24    │
        │  policy → NAT → IPS → log                            │
        └──────────────────────────────────────────────────────┘
   Путь клиента: WIN11-CL01 → route 10.10.20.0/24 via 10.10.10.4 → NGFW01 → WEB01
```

Порты, которые надо помнить инженеру: управление HTTPS 443 / SSH 22; IPsec IKE 500/4500 UDP + ESP (протокол 50); OpenVPN 1194 UDP по умолчанию; WireGuard 51820 UDP по умолчанию; syslog 514 UDP / 6514 TCP+TLS; LDAP 389/636, RADIUS 1812/1813. Остальные служебные порты конкретного вендора — только из его документации, не по памяти.

## 3. Аналогия из жизни

NGFW — это КПП на заводе. Раньше стоял вахтёр со списком «пропускать с улицы только на склад» (stateful: смотрит только на лицо и пропуск). Теперь на КПП: охранник знает всех сотрудников поимённо и по отделу (Identity Awareness), у него список запрещённых предметов и рентген-рамка (IPS/AV), журнал каждого прохода с видеозаписью (логи), отдельный коридор для гостей (DMZ) и служебный вход для развозчиков с пропусками (VPN). И, как на реальном КПП, если охранник поставил новую инструкцию «не пускать никого с сумками» выше старой «бухгалтерию пускать», — бухгалтерия встанет у ворот и будет звонить в техподдержку. Где аналогия ломается: охранник не может вскрыть опечатанную посылку, а NGFW с TLS-инспекцией — может, и именно поэтому её включают не везде.

## 4. Практика и команды

**1. Посмотреть политики pf/OPNsense из шелла (наш учебный NGFW).**

```bash
pfctl -sr            # список правил в порядке применения
pfctl -ss            # таблица состояний (кто куда уже сходил)
pfctl -si | head -20 # статистика: сколько пакетов прошло/заблокировано
```
`-sr` — rules, `-ss` — states, `-si` — info. В выводе `pfctl -ss` смотри адреса и флаги `ESTABLISHED`: если сессии нет вообще, пакет не дошёл или убит на входе.

**2. Живой лог в GUI OPNsense.**
`Firewall → Log Files → Live View`, фильтр по `dst` = `10.10.20.10`. Это первое, что открывают при «не работает через фаервол»: видно `pass`/`block`, правило, интерфейс.

**3. FortiGate: посмотреть политику.**

```text
show firewall policy
config firewall policy
    edit 10
        set srcintf "lan"
        set dstintf "dmz"
        set srcaddr "LAN-NET"
        set dstaddr "WEB01"
        set service "HTTPS"
        set action accept
        set utm-status enable
        set ips-sensor "default"
        set logtraffic all
    next
end
```

Смотри `policyid` (он же порядок), `action`, `nat enable`, `utm-status`. `logtraffic all` — иначе в логах не будет разрешённого трафика и диагностика слепнет.

**4. FortiGate: трассировка пакета по ходу обработки.**

```text
diagnose debug flow filter addr 10.10.20.10
diagnose debug flow filter port 443
diagnose debug flow show iprope enable
diagnose debug enable
diagnose debug flow trace start 20
```
Через 20 пакетов: `diagnose debug disable`. В выводе ищи строки `denied by forward policy check` (правило не разрешает) или `iprope_in_check() check failed` (нет маршрута/обратного пути) — это разные поломки.

**5. FortiGate: перехват трафика.**

```text
diagnose sniffer packet any "host 10.10.20.10 and port 443" 4 20
```
`4` — с заголовками, `20` — сколько пакетов. Показывает, дошли ли пакеты до машины и ушли ли ответы.

**6. Check Point: состояние и трассировка.**

```bash
fw stat                                    # установлена ли политика и когда
fw monitor -e "accept host(10.10.20.10);"  # i/o/O: вход/выход/на выходе после инспекции
fw ctl zdebug + drop                       # временный дебаг дропов (не забыть выключить)
cpview                                     # интерактивный монитор CPU/RAM/трафика
```
`fw monitor` показывает четыре точки конвейера: если пакет виден на `i` и `I`, но не на `o` — его съел IPS/anti-virus. На нагруженной машине снижай SecureXL (`fwaccel off`) на время.

**7. UserGate / Ideco: где искать то же самое.**
Графически: разделы «Политики безопасности / Firewall», «Профили безопасности / IPS», «VPN», «Журнал трафика / События». Точечные пути и порты веб-консоли зависят от версии — сверяйся с документацией вендора [ПРОВЕРИТЬ: порт веб-консоли Ideco и UserGate по умолчанию]. У UserGate есть REST API и IaC-провайдер, у Ideco — резервное копирование конфигурации из веб-консоли; автоматизация через CLI у обоих ограничена [ПРОВЕРИТЬ актуальный набор CLI-команд].

**8. Linux-сторона: эмуляция политики на UBU01/GW01.**

```bash
sudo nft list ruleset
sudo conntrack -L -d 10.10.20.10
sudo tcpdump -ni any 'host 10.10.20.10 and port 443' -c 20
```
`conntrack -L` показывает живые сессии — прямой аналог `pfctl -ss` и таблицы сессий NGFW.

**9. Проверить доступность порта с клиента (PowerShell).**

```powershell
Test-NetConnection -ComputerName 10.10.20.10 -Port 443
tracert -d 10.10.20.10
route print -4 | findstr 10.10.20
```
`TcpTestSucceeded : True/False` — ключевое. `tracert` покажет, где обрывается путь: до NGFW01 или после.

**10. Добавить постоянный маршрут до DMZ.**

```cmd
route -p add 10.10.20.0 mask 255.255.255.0 10.10.10.4
```
`-p` — persistent (переживает перезагрузку). В рабочей среде так не делают: раздают маршрут через DHCP option 121 или GPO.

**11. Проверка веб-сервера в DMZ с самого NGFW.**

```bash
curl -k -I https://10.10.20.10
openssl s_client -connect 10.10.20.10:443 -servername portal.vektor.lab </dev/null
```
Если с NGFW01 открывается, а с клиента нет — проблема в политике, а не в WEB01.

**12. WireGuard на Linux-клиенте (UBU01 как «удалёнщик»).**

```bash
sudo wg-quick up wg0
sudo wg show
ip -4 addr show dev wg0
```
`wg show` — `latest handshake` (давность рукопожатия) и `transfer` (байты). Handshake есть, а байты не растут → политика внутри туннеля не пускает.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

Стенд L2 готов: DC01 (AD/DNS/DHCP), FS01, WIN11-CL01, WIN10-CL02, UBU01, ASTRA01, GW01 (10.10.10.3 / 10.10.20.1), WEB01 (10.10.20.10, nginx). WEB01 сейчас смотрит шлюзом на GW01.

**Добавляем сверх таблицы:** ВМ **NGFW01** — OPNsense 24.x [ПРОВЕРИТЬ актуальную версию на opnsense.org], 2 vCPU, 2 ГБ RAM, 20 ГБ диск, **два адаптера**: `VMnet8` → WAN `10.10.10.4/24`, шлюз `10.10.10.2`, DNS `10.10.10.10`; `VMnet10` → LAN `10.10.20.2/24`, без шлюза, DHCP на LAN выключен. Если нужен именно вендорский продукт — ставь учебный/eval-образ UserGate, Ideco, FortiGate-VM или Check Point Quantum Spark [ПРОВЕРИТЬ доступность и срок eval-лицензии, часть вендоров требует аккаунт и запрос у представителя]; шаги ниже те же, меняются только пункты меню. OPNsense выбран потому, что бесплатен и легально скачивается без ограничений.

### Снапшот

В VMware Workstation на **WEB01, GW01, WIN11-CL01, DC01** — снапшот с именем `before-sysadmin-043`. На NGFW01 снапшот `before-sysadmin-043` сделай сразу после чистой установки, перед настройкой правил. Не забудь: имя одинаковое на всех машинах — так проще откатывать всю лабу целиком.

### Шаги

1. **NGFW01.** Создай ВМ, поставь OPNsense, при присвоении интерфейсов укажи WAN = первый адаптер, LAN = второй. Задай LAN-адрес `10.10.20.2/24`, отключи DHCP-сервер на LAN. **Ожидаемо:** веб-консоль `https://10.10.20.2` открывается из браузера на хосте через VMnet10.
2. **NGFW01.** `System → Settings → General`: DNS `10.10.10.10`, язык/таймзона. Задай админский пароль `Lab#2026-vektor` (только стенд!). **Ожидаемо:** NGFW01 пингует `10.10.10.10` и `10.10.20.10`.
3. **NGFW01.** `Interfaces → [WAN]`: сними галочки **Block private networks** и **Block bogon networks** — иначе OPNsense выбросит весь трафик из `10.10.10.0/24`, потому что это RFC1918. **Ожидаемо:** `ping 10.10.10.30` (UBU01) с NGFW01 проходит.
4. **WEB01.** Поменяй шлюз по умолчанию на `10.10.20.2` (`ip route`/`netplan` — в зависимости от того, как ты её настраивал в L2). **Ожидаемо:** с NGFW01 `curl -I http://10.10.20.10` отдаёт `200 OK`.
5. **WIN11-CL01.** `route -p add 10.10.20.0 mask 255.255.255.0 10.10.10.4`, затем `Test-NetConnection 10.10.20.10 -Port 443`. **Ожидаемо:** сначала `TcpTestSucceeded : False` — политики ещё нет.
6. **NGFW01.** Создай алиасы: `ALIAS-WEB01` = `10.10.20.10`, `ALIAS-WEB-PORTS` = 80, 443. `Firewall → Rules → LAN`: разрешить `LAN net → ALIAS-WEB01` по `ALIAS-WEB-PORTS`, логирование включить. **Ожидаемо:** с WIN11-CL01 `Test-NetConnection` даёт `True`, портал открывается.
7. **NGFW01.** Проверь, что запрещено: с WIN11-CL01 `Test-NetConnection 10.10.20.10 -Port 22` → `False`; в `Firewall → Log Files → Live View` видно `block` с текстом правила. **Ожидаемо:** запрет работает по умолчанию, без твоего «deny»-правила.
8. **NGFW01.** `Services → Intrusion Detection`: включи, скачай ruleset ET open, режим **IPS**, интерфейс LAN, политику — на наше правило. **Ожидаемо:** статус `running`, счётчик правил > 0.
9. **UBU01.** `nmap -sV -p 80,443 10.10.20.10` и `curl -A "Nikto" http://10.10.20.10/`. **Ожидаемо:** в `Services → Intrusion Detection → Alerts` появляются срабатывания ET SCAN; доступ при этом не рвётся (правило разрешает, IPS только логирует по этим сигнатурам).
10. **NGFW01.** `System → Firmware → Plugins` → поставь `os-wireguard`. `VPN → WireGuard → Instances`: создай инстанс, порт `51820`, туннельная сеть `10.10.99.0/24`; добавь Peer для UBU01, сгенерируй ключи. На WAN добавь правило `UDP 51820`. **Ожидаемо:** конфиг пира скачивается, ключи на месте.
11. **UBU01.** Установи `wireguard-tools`, положи `wg0.conf`, `sudo wg-quick up wg0`, `sudo wg show`. На NGFW01 добавь правило `WireGuard net → ALIAS-WEB01 по ALIAS-WEB-PORTS`. **Ожидаемо:** `latest handshake` свежий, `curl http://10.10.20.10` из туннеля работает.
12. **Запись.** Внеси всё в `stand-log.md`: новая ВМ, адреса, изменённый шлюз WEB01, маршрут на клиенте, правила, IPS, туннель.

### Сломай и почини

**Пользователь:** ivanov / **ВМ:** WIN11-CL01 / **Что написал:** «После обеда перестал открываться портал — ERR_CONNECTION_TIMED_OUT. Ping до 10.10.20.10 идёт, а сайт нет. У нас отчётность, умоляю». / **Срочность:** высокая.

**Как воспроизвести:** на NGFW01 в `Firewall → Rules → LAN` добавь **выше** разрешающего правила новое: `block`, `LAN net → ALIAS-WEB01`, протокол TCP, порт 443, логирование включено. Сымитируй «правку ночью».

**Диагностика по порядку:**
1. С клиента `ping 10.10.20.10` — идёт → L3 и маршрут живы, дело не в сети.
2. `Test-NetConnection -Port 443` → `False`, а `-Port 80` → `True`. Значит, режется конкретный порт, а не хост.
3. `route print -4` — маршрут до `10.10.20.0/24` через `10.10.10.4` на месте, исключаем клиента.
4. На NGFW01 `Firewall → Log Files → Live View`, фильтр `dst 10.10.20.10`, `port 443` → видим `block`, номер правила, интерфейс LAN.
5. `Firewall → Rules → LAN` → правило-блок стоит выше разрешающего. Классика.
6. Смотрим в `System → Audit/History` (или свою заметку в stand-log) — кто и когда менял.
7. Удаляем/отключаем блокирующее правило (или, если оно нужно, опускаем ниже разрешающего и сужаем до конкретной подсети), применяем.
8. `Test-NetConnection -Port 443` → `True`, портал открывается, в логе `pass`.

**Ответ пользователю:** «Иван, добрый день. Причина — ошибочное правило на межсетевом экране: блокировался HTTPS до портала для всей офисной сети. Правило убрал, портал открывается, проверьте, пожалуйста. Приносим извинения за простой, разбор причин сделаем, чтобы не повторилось».

**Закрытие заявки:** категория «Сеть / Межсетевой экран», решение — «удалено блокирующее правило policy #N после разбора», привяжи инцидент кchange-записи, добавь в базу знаний заметку «порядок правил NGFW».

## 6. Ошибки новичков и безопасность

- **«allow any any» сверху, чтобы быстрее заработало** → все остальные правила становятся мёртвым грузом (shadowing), логи бесполезны, аудит показывает дыру. Правильно: явные разрешения по конкретным парам «источник→получатель→сервис», запрет по умолчанию, документировать каждое правило.
- **Включил IPS в Prevent на всём трафике без исключений** → ложные срабатывания рвут длинные POST портала, синхронизацию 1С, обновления Windows. Правильно: сначала месяц в Detect, собрать FP, завести bypass/exceptions, потом Prevent.
- **Не включил логирование правила** → инцидент не расследовать, диагностика вслепую. Правильно: логирование для разрешающих правил на периметре обязательно + syslog на MON01.
- **Правка политики днём без окна и бэкапа** → простой бизнеса. Правильно: change-окно, экспорт конфигурации (`Diagnostics → Backup` в OPNsense; в вендорских — своя процедура), план откатa на бумаге.
- **Путают NAT и policy** → «правило разрешает, а не работает» (нет NAT) или наоборот. Правильно: сначала политика, потом NAT, и помнить порядок обработки (на входе/на выходе).
- **TLS-инспекция «на всякий случай» на всё** → ломаются приложения с certificate pinning, растёт нагрузка, а трафик с персональными данными расшифровывается без основания. Правильно: точечно, по категориям, с юридической оценкой (152-ФЗ) и уведомлением сотрудников.
- **NGFW вместо сегментации** → плоская сеть, бухгалтерия и серверы в одном L2-домене. Правильно: NGFW дополняет VLAN/сегменты, а не заменяет (см. урок 47).
- **Слабый admin-доступ** → веб-консоль торчит в WAN, пароль `admin`, нет MFA. Правильно: управление только из выделенного management-сегмента/VPN, MFA, отдельные учётки, регулярная смена паролей.

**Безопасность (боевая среда):** никогда не открывай веб-консоль и SSH фаервола в интернет; не храни приватные ключи IPsec/WireGuard в почте и в git; не отправляй syslog наружу без TLS; не отключай антивирус/IPS «ради скорости 1С» без письменного согласования; не давай подрядчику полный admin — только read-only и временный доступ. На стенде мы используем единый пароль `Lab#2026-vektor` — в реальной работе так делать нельзя, у каждой учётки должен быть свой пароль и MFA.

## 7. Вопросы на собеседовании

**1. Чем NGFW отличается от обычного stateful-файрвола?**
Ответ: stateful смотрит только L3/L4 и таблицу сессий; NGFW добавляет DPI до L7 — распознавание приложений, IPS, антивирус, URL-фильтрацию, привязку к пользователю AD, TLS-инспекцию — и всё это в одном конвейере с логированием и отчётностью. Stateful обычно быстрее и дешевле; NGFW даёт контроль по «кто и что», но требует ресурсов и настройки профилей.
*Что хочет услышать:* понимание, что это не «фаервол с красивее интерфейсом», а разные уровни контроля и разная цена по производительности.
*Красный флаг:* «NGFW — это просто фаервол с антивирусом» без упоминания DPI, identity и профилей.

**2. Как NGFW понимает, что за трафиком стоит конкретный пользователь?**
Ответ: через Identity Awareness — интеграция с AD по LDAP, агенты на контроллерах/клиентах, Kerberos-авторизация, Captive Portal, иногда RSSO/RADIUS. Далее в правилах вместо IP используется группа AD: `GG-Buh → \\FS01\Buh` разрешено, `GG-Sklad` — нет. Ограничения: пользователь должен быть залогинен, при смене IP нужна переавторизация, для сервисных учёток identity не работает — нужны IP-правила.
*Что хочет услышать:* LDAP/агенты/Kerberos + понимание, что identity не бесплатна по сложности.
*Красный флаг:* «фаервол видит, кто зашёл на сайт, по логину в браузере» — так не работает.

**3. Пользователь пишет «не открывается сайт», ping идёт. Твои действия?**
Ответ: по слоям вниз-вверх. 1) порт: `Test-NetConnection`/`nc -vz`; 2) маршрут на клиенте (`route print`, `traceroute`); 3) DNS-резолв; 4) логи фаервола по `dst`+`port` — pass/block; 5) если pass — смотрим IPS/AV-дропы (`fw monitor` на Check Point, `diagnose debug flow` на FortiGate); 6) если block — читаем правило и порядок; 7) проверяем сервер (`curl` с самого фаервола); 8) чиним, проверяем с клиента, пишем пользователю и в тикет.
*Что хочет услышать:* методичный порядок и работа с логами, а не «перезагрузил фаервол — помогло».
*Красный флаг:* «сразу отключил IPS и заработало, заявку закрыл».

**4. Что такое TLS-инспекция, зачем она и какие подводные камни?**
Ответ: NGFW подменяет сертификат сервера своим (клиентам нужно доверять внутреннему CA), расшифровывает, проверяет содержимое (IPS, AV, DLP) и шифрует обратно. Плюс: видно то, что раньше было слепой зоной. Минусы: ломается certificate pinning (мобильные приложения, банки, обновления), кратно растёт нагрузка, появляется юридическая ответственность за расшифровку персональных данных (152-ФЗ), нужен внутренний CA и его защита. Поэтому — точечно и по политике, а не «включить на all».
*Что хочет услышать:* доверие к внутреннему CA, pinning, производительность, комплаенс.
*Красный флаг:* «включаем всем и всё, ничего не сломается».

**5. Как проверить, что HA-кластер NGFW реально переживёт отказ?**
Ответ: убедиться, что синхронизируются политики, таблица сессий и (у части вендоров) состояние VPN; проверить роли Active/Standby и виртуальные IP; затем — плановый тест: отключить один узел в окне, проверить, что сессии не рвутся, `ping`/`curl` не прерываются, логи пишутся, алерты пришли; вернуть узел, убедиться, что ресинхронизация прошла. Обязательно фиксировать результат теста в регламенте и повторять регулярно.
*Что хочет услышать:* «failover проверяется тестом, а не верой в надпись HA».
*Красный флаг:* «у нас HA, значит отказоустойчиво — не проверяли».

## 8. Источники (официальная документация)

- **docs.opnsense.org** — разделы «Firewall», «Intrusion Detection», «VPN → WireGuard». Поиск: `opnsense firewall rules live log`.
- **docs.fortinet.com** — «FortiOS Administration Guide»: Firewall policies, IPS, IPsec VPN; «FortiGate CLI Reference». Поиск: `fortigate diagnose debug flow`.
- **docs.checkpoint.com** [ПРОВЕРИТЬ домен портала документации] — «Security Management Administration Guide», «Security Gateway R81 CLI Reference» (`fw monitor`, `fw stat`). Поиск: `checkpoint fw monitor command`.
- **usergate.com** + портал документации вендора [ПРОВЕРИТЬ адрес docs] — «UserGate NGFW. Руководство администратора»: политики, профили безопасности, VPN. Поиск: `usergate ngfw администратор политика`.
- **ideco.ru** + документация вендора [ПРОВЕРИТЬ адрес docs] — «Ideco NGFW. Настройка межсетевого экрана, IPS, VPN». Поиск: `ideco ngfw настройка правил`.
- **docs.suricata.io** — «Suricata User Guide», разделы Rules и IPS mode (движок, на котором работают IPS у многих NGFW). Поиск: `suricata ips mode ruleset`.
- **csrc.nist.gov** — NIST SP 800-41 Rev.1 «Guidelines on Firewalls and Firewall Policy»: базовый документ по методологии политик. Поиск: `NIST SP 800-41 firewall policy`.
- **datatracker.ietf.org** — RFC 4301 (IPsec architecture), RFC 8446 (TLS 1.3) для понимания, что именно инспектируется. Поиск: `RFC 4301 IPsec architecture`.
- Реестр российского ПО **reestr.digital.gov.ru** [ПРОВЕРИТЬ актуальный адрес реестра] — проверка, входит ли конкретный NGFW (UserGate, Ideco, «Континент», «Гарда» и др.) в реестр отечественного ПО и сертифицирован ли он ФСТЭК для задачи.
