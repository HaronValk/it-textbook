## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**VLAN (Virtual Local Area Network)** — логическая сеть второго уровня (L2, канальный слой OSI). Физически все устройства включены в один коммутатор, логически коммутатор ведёт себя как несколько независимых. Технически это тег **802.1Q**: 4 байта вставляются в Ethernet-кадр после MAC-адреса получателя. Внутри тега 12 бит на VLAN ID → 4094 пригодных номера (0 и 4095 зарезервированы). Кадр без тега — «нетегированный», он уходит в *native VLAN* порта.

Два типа портов:
- **access** — порт для конечного устройства. Получил нетегированный кадр от ПК, повесил тег VLAN 10, отправил в коммутатор. Обратно — снял тег. ПК про VLAN ничего не знает.
- **trunk** — магистраль между коммутаторами и до роутера. Передаёт кадры многих VLAN с тегами. Список разрешённых VLAN ограничивают вручную — это и безопасность, и экономия широковещательного трафика.

Между VLAN нужен маршрутизатор (L3). Его функции выполняет либо отдельный роутер, либо **L3-коммутатор** (SVI — virtual interface на каждом VLAN). Каждый VLAN = своя подсеть = свой шлюз. DHCP для клиентов чужого VLAN поставляется через **DHCP relay** (`ip helper-address` на Cisco, `dhcrelay` в Linux) — потому что широковещательный DHCP Discover не проходит через маршрутизатор.

**Трёхуровневая модель (three-tier):**

| Уровень | Что делает | Пример |
|---|---|---|
| **Core (ядро)** | Только быстрая маршрутизация между блоками. Никаких ACL-простыней и подключаемых рабочих станций | два L3-коммутатора (в лабе — GW01) |
| **Distribution (распределение)** | Политики: ACL между VLAN, маршрутизация, агрегация линков, шлюзы подсетей | L3-коммутатор этажа |
| **Access (доступ)** | Порты для ПК, телефонов, точек доступа. Дешёвый L2 | 24-портовый коммутатор в шкафу |

В офисе на 50–150 человек три уровня — перебор. Стандарт — **collapsed core**: ядро и распределение совмещены в паре L3-коммутаторов, access — этажные L2. Для ЦОД и больших сетей — **spine-leaf**, но это уже DevOps/DC-история.

```text
                    ┌────────────────────────────────────────┐
                    │  CORE / COLLAPSED CORE — GW01 (Debian) │
                    │  ens33 10.10.10.3   ens34 10.10.20.1   │
                    │  ens35 10.10.30.1   ens36 10.10.40.1   │
                    │  ip_forward=1, nftables, NAT           │
                    └───────────────────┬────────────────────┘
                       trunk 802.1Q (в лабе — отдельные VMnet)
      ┌──────────────┬──────────────┬──┴───────────┬────────────────┐
  VLAN 10 SRV   VLAN 20 DMZ    VLAN 30 MGMT  VLAN 40 GUEST    VLAN 50 VOICE
 10.10.10.0/24  10.10.20.0/24  10.10.30.0/24 10.10.40.0/24    (только план)
      │              │               │              │
 DC01 .10        WEB01 .10       PVE01 .70      гости, подрядчики
 FS01 .20                        IPMI, свитчи    (только интернет)
 UBU01 .30
 ASTRA01 .31
 MON01 .40
 PVE01 .70
```

**VLAN-план** — это документ, а не «как получилось». Правила, которые экономят годы:
- номера по назначению, с шагом 10: 10 серверы, 20 DMZ, 30 управление, 40 гость, 50 телефония, 60 принтеры/ IoT, 100+ — пользователи по отделам;
- имя VLAN = имя в мониторинге = имя в схеме, одинаково везде (`SRV`, `DMZ`, `MGMT`, `GUEST`);
- VLAN 1 не используется никогда: это native VLAN по умолчанию, и атака VLAN hopping начинается именно с неё;
- каждая подсеть — /24 с запасом, шлюз — `.1` (или `.254`), первые 50 адресов — под статику (серверы, свитчи), остальное — DHCP;
- любой новый VLAN добавляется в план **до** того, как его создали на железе.

**DMZ (демилитаризованная зона)** — сегмент, куда смотрят снаружи и откуда не видно внутрь. Правило по умолчанию: `LAN → DMZ` разрешено (админы ходят на WEB01), `DMZ → LAN` запрещено всегда, `DMZ → Internet` — только по необходимости (обновления). Наружу публикуется не сам веб-сервер, а reverse proxy / балансировщик, и публикация делается через **DNAT** на периметре.

**Management VLAN** — отдельный сегмент для того, через что ты управляешь инфраструктурой: IPMI/iDRAC, веб-интерфейсы коммутаторов, гипервизор, ИБП. Доступ туда только с bastion-хоста (jump host, в стенде — UBU01) по SSH с ключом. Гостевая сеть к MGMT не имеет доступа вообще никогда.

**Гостевая сеть** — «интернет и ничего больше». Отдельный VLAN, отдельный DHCP (свой пул), отдельный DNS (публичный, не доменный), NAT наружу, ограничение полосы, client isolation на точках доступа (клиенты не видят друг друга), логирование выдачи адресов. В РФ для публичного Wi-Fi действуют требования по идентификации пользователей — уточняй актуальную редакцию нормативки у юриста, не по форумам [ПРОВЕРИТЬ: Постановление Правительства РФ о порядке идентификации пользователей Wi-Fi].

## 3. Аналогия из жизни

Представь Москву. Дворы и подъезды — это **access**: узкие, медленные, но их много и они ведут прямо к нужной двери. Районные улицы — **distribution**: там стоят светофоры (ACL), там решается, кого куда пускать. ТТК и МКАД — **core**: задача одна — быстро провезти поток между районами, никаких магазинов и парковок вдоль дороги. VLAN — это не дороги, это **разметка и пропуска**: физически один асфальт, но по одной полосе едут только жильцы двора, по другой — только курьеры, и шлагбаум между ними открывается лишь на посту с пропуском. DMZ — платная парковка у вокзала: туда пускают посторонних, но из неё нет выхода в жилые кварталы. Гостевая сеть — бесплатная перехватывающая парковка за шлагбаумом: заехал, оставил машину, в город пешком, к твоим дворам доступа нет.

Аналогия перестаёт работать в одном месте: дороги делят физическое пространство, а VLAN — логическая разметка поверх одного кабеля, и цена ошибки здесь другая — «срезать через двор» в сети означает попасть в широковещательный домен целиком.

## 4. Практика и команды

**1. Инвентаризация сетевых интерфейсов на Linux-роутере GW01.**
```bash
ip -br a                    # короткий список интерфейсов и адресов
ip -d link show ens33       # подробно: MTU, тип, состояние
ip route                    # таблица маршрутизации
```
Смотрим: все ожидаемые `ensXX` в состоянии `UP`, адреса совпадают с планом, в `ip route` есть `default` и локальные подсети. Если интерфейс `DOWN` — проблема в адаптере ВМ в VMware, а не в Linux.

**2. Создание VLAN-интерфейса 802.1Q (реальный транк).**
```bash
sudo ip link add link ens33 name ens33.30 type vlan id 30
sudo ip addr add 10.10.30.1/24 dev ens33.30
sudo ip link set ens33.30 up
ip -d link show ens33.30    # видим "vlan protocol 802.1Q id 30"
```
`ip link add ... type vlan id N` создаёт сабинтерфейс; всё, что уйдёт через него, получит тег 30. На VMware Workstation кадры с тегом между ВМ, как правило, не проходят через виртуальный коммутатор — проверяй на своём стенде `[ПРОВЕРИТЬ]`. Поэтому в лабе VLAN моделируются отдельными VMnet, а команды выше нужны для реального железа.

**3. Постоянная конфигурация VLAN через netplan (Ubuntu).**
```yaml
# /etc/netplan/01-netcfg.yaml
network:
  version: 2
  ethernets:
    ens33:
      dhcp4: false
  vlans:
    vlan30:
      id: 30
      link: ens33
      addresses: [10.10.30.1/24]
```
Применить: `sudo netplan try` (с автоматическим откатом через 120 с, если не подтвердить) → `sudo netplan apply`. Ключевое здесь — `netplan try`: страховка от потери SSH.

**4. Включение маршрутизации между VLAN.**
```bash
sudo sysctl -w net.ipv4.ip_forward=1
echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-forward.conf
```
Без этого пакеты между подсетями просто не пойдут, и ты полчаса будешь искать проблему в файрволе.

**5. Политика nftables: гость изолирован, DMZ закрыта.**
```bash
#!/usr/sbin/nft -f
flush ruleset

table inet filter {
  chain input {
    type filter hook input priority filter; policy drop;
    iif lo accept
    ct state established,related accept
    iifname "ens35" ip saddr 10.10.10.0/24 tcp dport 22 accept   # MGMT: ssh только из VLAN 10
    iifname "ens36" udp dport { 53, 67 } accept                  # GUEST: DNS и DHCP
    iifname "ens36" tcp dport 53 accept
    icmp type echo-request ip saddr 10.10.10.0/24 accept
  }
  chain forward {
    type filter hook forward priority filter; policy drop;
    ct state established,related accept
    ip saddr 10.10.40.0/24 ip daddr { 10.10.10.0/24, 10.10.20.0/24, 10.10.30.0/24 } drop
    ip saddr 10.10.20.0/24 ip daddr { 10.10.10.0/24, 10.10.30.0/24, 10.10.40.0/24 } drop
    iifname "ens36" oifname "ens33" accept                       # GUEST -> наружу
    iifname "ens33" oifname "ens34" accept                       # LAN -> DMZ
  }
}
table ip nat {
  chain postrouting {
    type nat hook postrouting priority srcnat; policy accept;
    ip saddr 10.10.40.0/24 oifname "ens33" masquerade
  }
}
```
```bash
sudo nft -f /etc/nftables.conf
sudo nft list ruleset -a      # -a показывает handle'ы для точечного удаления
```
Порядок правил важен: `drop` для гостя стоит **выше** разрешающего. `policy drop` в forward — принцип «запрещено всё, что не разрешено явно».

**6. Публикация сервиса из DMZ через DNAT.**
```bash
sudo nft add table ip nat
sudo nft add chain ip nat prerouting '{ type nat hook prerouting priority dstnat; }'
sudo nft add rule ip nat prerouting tcp dport 443 dnat to 10.10.20.10:443
```
Пришло на внешний адрес GW01:443 → уходит на WEB01. Обратный трафик разруливает conntrack. В бою публикуют через reverse proxy (nginx/HAProxy), а DNAT держат максимально узким.

**7. Проверка изоляции сканированием.**
```bash
nmap -sn 10.10.10.0/24      # из гостевой ВМ: должно быть пусто/ошибка
nmap -Pn -p 445 10.10.10.20 # FS01: filtered
traceroute 10.10.10.20      # видно, что пакет умирает на 10.10.40.1
```
`-sn` — ping-скан без портов. `-Pn` — не пытаться пинговать, сразу проверять порт (полезно, когда ICMP режут). Смотреть в выводе `filtered`, а не `closed`: `filtered` = файрвол молча дропает.

**8. Просмотр дропнутого трафика в реальном времени.**
```bash
sudo tcpdump -ni ens36 icmp            # что прилетает из гостевой сети
sudo nft monitor trace                # если настроен meta nftrace set 1
```
`-n` — без резолва имён, `-i ens36` — только этот интерфейс. Если пакеты видны на входе, но ответа нет — проблема в правилах forward, а не в маршрутизации.

**9. Windows-клиент: проверка того, что видит пользователь.**
```powershell
Get-NetAdapter | Format-Table Name,Status,LinkSpeed
Get-NetIPConfiguration
Test-NetConnection -ComputerName FS01 -Port 445
Resolve-DnsName fs01.corp.vektor.lab
tracert 10.10.20.10
```
`Test-NetConnection` — в PowerShell это правильный способ проверить порт, `ping` проверяет только ICMP, который часто режут. `Resolve-DnsName` покажет, отдаёт ли DC01 запись.

**10. Проверка VLAN на реальном железе (для собеседования и работы).**
```text
# Cisco / Eltex (похожий синтаксис)
show vlan brief
show interfaces trunk
show interfaces status
switchport mode trunk
switchport trunk allowed vlan 10,20,30,40
switchport trunk native vlan 999
```
```text
# Huawei
display vlan
display port vlan
port link-type trunk
port trunk allow-pass vlan 10 20 30 40
```
Смотрим: trunk в состоянии `trunking`, список разрешённых VLAN совпадает с планом, native VLAN — не 1 и не используется никем.

**11. DHCP relay для клиентских VLAN.**
```bash
sudo dhcrelay -i ens36 -i ens33 10.10.10.10
```
Слушает Discover на `ens36`, пересылает на DC01 (`10.10.10.10`) через `ens33`. На Cisco аналог — `ip helper-address 10.10.10.10` на SVI клиентского VLAN.

**12. Проверка полосы и загрузки канала перед вводом QoS для гостей.**
```bash
sudo apt install -y iftop && sudo iftop -i ens36
sudo tc qdisc add dev ens36 root tbf rate 20mbit burst 32kbit latency 400ms
```
`tbf` (token bucket filter) режет гостя до 20 Мбит/с — типичное требование, чтобы гости не съедали канал у 1С.

## 6. Ошибки новичков и безопасность

1. **Всё в VLAN 1 / одна подсеть на офис.** → одна петля или широковещательный шторм кладёт всю сеть, гости видят файловые шары. → Отдельные VLAN по назначению, VLAN 1 не используется и не назначается ни на один access-порт.
2. **VLAN «на бумаге» ≠ VLAN на железе.** → Схема врёт, при инциденте ищешь несуществующую сегментацию. → После каждого изменения `show vlan brief` / `nft list ruleset` и обновление `stand-log.md` в тот же день.
3. **Шлюз для каждого VLAN оставлен на ядре, а ACL — на access.** → Политики не работают, потому что трафик между VLAN не проходит через access-коммутатор. → Шлюзы и ACL — на одном устройстве (collapsed core / SVI на distribution).
4. **`policy accept` в forward-цепочке «чтобы заработало».** → Гостевая сеть получает полный доступ в LAN, и это никто не замечает месяцами. → `policy drop`, затем точечные `accept`; каждая временная поблажка — с датой удаления в задаче.
5. **DMZ в той же подсети, что и серверы, «потому что так проще».** → Уязвимость на WEB01 = прямой путь к DC01, односторонний доступ только на бумаге. → DMZ — отдельный VLAN и отдельная подсеть, `DMZ → LAN` запрещено на уровне периметра.
6. **Гостевой Wi-Fi с доменным DNS и доменным DHCP.** → Гости резолвят внутренние имена, видят структуру домена. → Свой пул, публичный DNS (например, 77.88.8.8), NAT наружу, client isolation на точках.
7. **Management-интерфейсы в общей серверной подсети и с паролем `admin`.** → Компрометация любой ВМ = доступ к гипервизору и коммутаторам. → MGMT VLAN, доступ только с bastion по SSH-ключам, уникальные пароли в хранилище.
8. **Миграция «в один вечер» с изменением адресов всего офиса.** → Утром не работает ничего, и никто не помнит, что меняли. → План миграции по шагам: сначала новые VLAN рядом со старым, потом перенос по отделам, окно и откат на каждом шаге.

**Безопасность (в боевой среде нельзя):**
- Оставлять native VLAN = 1 и разрешать её на trunk — классический VLAN hopping через double tagging.
- Разрешать на trunk «все VLAN» (`switchport trunk allowed vlan all`) — любой лишний VLAN станет доступен с любого порта.
- Ставить гостевую сеть и MGMT на одно физическое устройство без ACL — гость получает L2-соседство с управлением.
- Хранить на порту доступа включённым DHCP-сервер (в том числе VMware DHCP) — «левые» адреса и подмена шлюза. В бою дополнительно: DHCP snooping, Dynamic ARP Inspection, BPDU guard, port-security на access-портах.
- Публиковать сервис из DMZ напрямую в интернет без reverse proxy и обновлений — вопрос дней до взлома.

## 7. Вопросы на собеседовании

**1. Чем access-порт отличается от trunk и как это влияет на дизайн сети?**
Access — один VLAN, кадры нетегированные, для конечных устройств. Trunk — много VLAN с тегом 802.1Q, для линков между коммутаторами и до L3-устройства. В дизайне: trunk идёт только между сетевым оборудованием, список VLAN на нём ограничен планом, native VLAN выделен в отдельный неиспользуемый номер. Один trunk — единая точка отказа, поэтому в бою их пара с LACP.
*Что хочет услышать интервьюер:* что ты понимаешь тег 802.1Q, ограничение VLAN на trunk и отказоустойчивость линков.
*Красный флаг:* «trunk — это когда все VLAN везде разрешены и побольше».

**2. Спроектируй VLAN-план для офиса на 200 человек.**
Отдельные VLAN: серверы, DMZ, управление, гостевая, телефония, принтеры/IoT, пользователи по отделам (бухгалтерия, HR, склад, IT). Номера с шагом 10, имена одинаковые во всех системах. Каждая подсеть /24 с запасом, шлюз `.1`, статика в начале диапазона. Маршрутизация и ACL — на collapsed core (пара L3-коммутаторов), access — L2. Между отделами — разрешено только необходимое (например, бухгалтерии к 1С), гостям — только интернет.
*Что хочет услышать интервьюер:* назначение каждого VLAN и где живут политики.
*Красный флаг:* «пять VLAN, и всё разрешено между ними» или «всё в одной подсети, а VLAN — это для Wi-Fi».

**3. Зачем DMZ и какие правила между DMZ и LAN?**
DMZ — сегмент для сервисов, доступных извне. Правило: LAN → DMZ разрешено (администрирование), DMZ → LAN запрещено, DMZ → Internet только по необходимости. Публикация — через reverse proxy/DNAT на периметре. Смысл: взлом веб-сервера не даёт доступа к AD и файловым серверам. Дополнительно: отдельный сегмент, обновления, минимальные сервисы на хосте, логирование.
*Что хочет услышать интервьюер:* односторонние правила и понимание, что DMZ — не «просто отдельная подсеть».
*Красный флаг:* «в DMZ тот же VLAN, что и у серверов, но мы поставили файрвол на саму ВМ».

**4. Как защитить Management VLAN?**
Отдельный VLAN и подсеть для IPMI/iDRAC, гипервизоров, коммутаторов, ИБП; доступ только с bastion-хоста по SSH-ключам; никакого прямого доступа из пользовательских и гостевых VLAN; отдельные учётки, журналирование входов; по возможности — out-of-band через отдельный физический интерфейс. Внешний доступ — только через VPN с MFA.
*Что хочет услышать интервьюер:* bastion + запрет доступа из пользовательских сегментов + журналирование.
*Красный флаг:* «management в общей подсети, зато пароль сложный».

**5. Что должно быть в гостевой сети и чего там быть не должно?**
Есть: свой VLAN, свой DHCP-пул, публичный DNS, NAT наружу, ограничение полосы, client isolation, логирование MAC/IP, captive portal. Нет: доступа в LAN и DMZ, доменного DNS, доменных учёток, доступа к MGMT, широковещательного соседства с рабочими местами. Плюс требование по идентификации пользователей публичного Wi-Fi в РФ — уточнять актуальную нормативку.
*Что хочет услышать интервьюер:* полная изоляция + управляемость (полоса, логи, портал).
*Красный флаг:* «гостям тот же пароль от Wi-Fi, что и сотрудникам, только VLAN другой».
