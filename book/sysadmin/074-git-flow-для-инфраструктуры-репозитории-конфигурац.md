## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Git — распределённая система контроля версий (DVCS). Внутри — простая объектная модель:

- **blob** — содержимое файла (без имени);
- **tree** — каталог: список «имя → ссылка на blob/tree»;
- **commit** — снимок всего дерева + автор, дата, сообщение и ссылка на родительский коммит;
- **tag** — именованная ссылка на коммит (аннотированный тег — это отдельный объект с автором и сообщением).

Всё это лежит в `.git/objects`, а «ветки» — просто файлы в `.git/refs/heads/`, содержащие SHA-1 (в новых репозиториях — SHA-256) коммита. Поэтому ветка в Git — это указатель, а не копия папки. `HEAD` — указатель на текущую ветку.

История — направленный ациклический граф (DAG). Слияние (`merge`) создаёт коммит с двумя родителями, `rebase` переписывает коммиты на новую базу (меняет их SHA — значит, ломает чужие клоны, если ветка уже опубликована).

**Модели ветвления.** Классический *git-flow* (Винсент Дриссен, 2010) — `main` + `develop` + `feature/*` + `release/*` + `hotfix/*`. Для инфраструктуры он часто избыточен: у конфигов нет «версии для тестирования», зато есть окружения. Поэтому на практике в инфре чаще берут *GitLab Flow*: одна долгоживущая ветка `main` (она же прод), короткие feature-ветки, окружения — ветками (`preprod`, `prod`) или тегами. Для маленькой команды «Вектора» правильный выбор — **trunk-based с защищённой `main` и тегами-релизами**.

```text
                      ┌── feature/nftables-ssh ──┐
main ──●──●───────────●──────────────────────────●──●────────●──●──>
       │  │           (MR + review)              │  │        │
       │  └─ v1.0.0 ──────────────┐              │  └ v1.1.0 │
       │                        (deploy на GW01) │           │
       └─ hotfix/nginx-502 ──────────────────────┘           │
                                                    v1.1.1 ──┘
                              ▲
                     deploy = checkout тега

Компоненты:
  GIT01 (10.10.10.50)  — GitLab CE, харденинг: SSH-ключи, protected main, MR
  GW01  (10.10.10.3)   — /opt/vektor-infra → nftables.conf  (pull-модель)
  WEB01 (10.10.20.10)  — /opt/vektor-infra → nginx sites    (pull-модель)
  DC01  (10.10.10.10)  — DNS A-запись GIT01, учётки людей
```

**Порты и протоколы.** Git поверх SSH — TCP/22 (`git@10.10.10.50:infra/vektor-infra.git`), поверх HTTPS — TCP/443 (`https://...`). Устаревший `git://` — TCP/9418, в продакшене не используется (нет аутентификации). Веб-интерфейс GitLab — TCP/80 или 443. Git не шифрует данные сам — шифрование даёт транспорт (SSH/TLS).

**Три кита, которые нужны сисадмину:**
1. **Источник правды.** Конфиг живёт в репозитории, а не «в голове у Васи» и не только на сервере.
2. **Ревью.** Изменение в `main` попадает только через merge request (MR) с апрувом второго человека — это и защита от опечатки, и формальное доказательство контроля изменений для аудита (в терминах 152-ФЗ и 187-ФЗ такие следы регулярно спрашивают).
3. **Тег = рабочее состояние.** Тег `v1.1.0` — это «конфигурация, которая точно работала 12 марта». Откат = `git checkout v1.1.0`.

## 3. Аналогия из жизни

Конструкторское бюро. Есть архив чертежей, и каждый чертёж существует не в одном экземпляре, а в виде истории правок: «изменение №14, внёс инженер Сидоров, согласовал главный конструктор». Никто не правит чертёж, который уже ушёл в производство, — под него открывают новую версию. Готовое изделие получает штамп «Версия 1.0» и уходит в серию; если в серии всплыл брак — по штампу за пять минут находят, какие именно чертежи в эту версию входили. В Git роль подписи главного конструктора играет approve в merge request, роль штампа — аннотированный тег, роль архива — сервер GIT01. Ломается аналогия в одном месте: в бюро версии чертежей — это целые листы, а Git сливает файлы построчно и умеет автоматически объединять правки двух людей в одном документе.

## 4. Практика и команды

**1. Настройка личности и базовых привычек.** Без этого коммиты будут от «root@ubuntu».

```bash
git config --global user.name "adm.student"
git config --global user.email "adm.student@corp.vektor.lab"
git config --global init.defaultBranch main
git config --global pull.rebase true      # не плодить merge-коммиты при pull
git config --list --show-origin
```

`--show-origin` показывает, из какого файла пришла настройка (`/etc/gitconfig`, `~/.gitconfig`, `.git/config`). Типичный вывод — пары `ключ=значение`; смотреть надо на `user.email` (коммиты «не от того человека» ломают аудит).

**2. Инициализация репозитория и первый коммит.**

```bash
mkdir -p /opt/vektor-infra && cd /opt/vektor-infra
git init
git status
```

`git status` — самая частая команда сисадмина: она показывает расхождение между рабочим каталогом, индексом (staging area) и последним коммитом. Вывод вида `Changes not staged for commit: modified: nginx/web.vektor.lab.conf` — это и есть **дрейф конфигурации** (кто-то поправил файл руками на сервере).

**3. Клонирование и удалённые репозитории.**

```bash
git clone git@10.10.10.50:infra/vektor-infra.git /opt/vektor-infra
git remote -v
```

`remote -v` покажет `origin  git@10.10.10.50:...  (fetch/push)`. Если видишь `https://` вместо `git@` — значит, ключ не настроен и каждый `push` будет спрашивать пароль.

**4. Индекс и коммит.**

```bash
git add nftables/nftables.conf
git add -A                 # всё, включая удаления
git diff --staged
git commit -m "nftables: разрешить SSH с 10.10.20.0/24 на GW01"
```

`git diff` без флагов — рабочий каталог против индекса; `--staged` (`--cached`) — индекс против последнего коммита. Смотреть в диффе надо на строки `-`/`+` и на то, не утекли ли в них пароли.

**5. История и граф.**

```bash
git log --oneline --graph --decorate --all -15
```

```text
* 9c1f0ab (HEAD -> main, tag: v1.1.0, origin/main) nginx: вернуть root на /var/www/web
*   3ab77c1 merge: feature/nftables-ssh
|\
| * 77de012 nftables: правило для DMZ
|/
* 5f0a1c2 (tag: v1.0.0) первичная фиксация конфигов стенда
```

Смотреть: где теги, где слияния, кто последний трогал `main`.

**6. Ветки.**

```bash
git switch -c feature/nftables-ssh
git switch main
git branch -a
```

`switch -c` = создать и перейти (Git ≥ 2.23; старый вариант `git checkout -b`). `branch -a` покажет и локальные, и `remotes/origin/*`.

**7. Слияние.**

```bash
git switch main
git merge --no-ff feature/nftables-ssh -m "merge: nftables-ssh"
```

`--no-ff` запрещает «fast-forward» и всегда создаёт merge-коммит: в истории видно, что была отдельная ветка и MR. Для инфраструктуры это ценно — виден факт ревью.

**8. Теги и релизы.**

```bash
git tag -a v1.1.0 -m "Релиз конфигов: nftables + nginx, проверено на стенде"
git tag -l 'v1.*'
git show v1.1.0 --stat
git push origin v1.1.0
git push --tags        # осторожно: отправит ВСЕ локальные теги
```

`-a` — аннотированный тег (хранит автора, дату, сообщение), `-m` — сообщение. `git show v1.1.0 --stat` покажет, какие файлы вошли в релиз. Легковесный тег (`git tag v1.1.0`) — просто указатель, для релизов не годится.

**9. Откат: revert, а не reset.**

```bash
git revert 9c1f0ab --no-edit     # создать коммит, отменяющий изменения
git log --oneline -3
```

`revert` безопасен: история не переписывается, изменение видно в аудите. `git reset --hard` в общем репозитории недопустим — он рвёт историю у всех, кто уже склонировал.

**10. Кто менял строку.**

```bash
git blame -L 1,15 nginx/web.vektor.lab.conf
git log -p -- nftables/nftables.conf | head -60
```

`blame` показывает для каждой строки коммит, автора и дату. `log -p -- <путь>` — вся история конкретного файла с патчами. Это ответ на тикет «кто это сломал» за 10 секунд.

**11. Что не коммитить.**

```bash
printf '*.key\n*.pem\nsecret*\n*.retry\n' > .gitignore
git rm --cached vault/secrets.yml
git status --short
```

`git rm --cached` убирает файл из индекса, оставляя его на диске. `.gitignore` не защищает уже закоммиченные файлы — их надо удалять из индекса и **менять сам секрет**.

GUI-путь в GitLab: проект → **Code → Branches** (защита веток), **Merge requests → New merge request**, **Code → Tags**, **Deploy → Releases**.

### Сломай и почини

> **Пользователь:** petrova (Мария Петрова, HR)
> **ВМ:** WIN10-CL02
> **Что написала:** «Внутренний портал `http://web.vektor.lab` отдаёт 502 Bad Gateway. Утром работал. Доступ к `\\FS01\HR` тоже пропал. Срочно, у нас отчёт.»
> **Срочность:** высокая

**Воспроизводим поломку.** На WEB01 руками (в обход Git) правим конфиг: в `sites-enabled/web.vektor.lab.conf` меняем `proxy_pass http://10.10.20.10:8080;` на несуществующий порт `8081` (или ломаем `root`), затем `sudo nginx -t` (проверка пройдёт, синтаксис-то валиден) и `sudo systemctl reload nginx`. Портал лёг — а в репозитории ничего не изменилось.

**Диагностика по порядку:**
1. `curl -I http://web.vektor.lab` с UBU01 → `502`, значит nginx жив, а бэкенд за ним недоступен.
2. `sudo systemctl status nginx` на WEB01 → `active (running)`; `sudo tail -50 /var/log/nginx/error.log` → `connect() failed ... 10.10.20.10:8081`.
3. `cd /opt/vektor-infra && sudo git status` → `modified: nginx/web.vektor.lab.conf`. **Вот оно.** Это дрейф: файл на сервере разошёлся с репозиторием.
4. `sudo git diff` → видим `- proxy_pass http://10.10.20.10:8080;` / `+ ...8081`.
5. `sudo git log --oneline -3` → подтверждаем, что последний коммит правильный, изменения в него не входят.

**Решение:**

```bash
cd /opt/vektor-infra
```

## 6. Ошибки новичков и безопасность

1. **Коммит секретов** → пароль навсегда в истории, любой с доступом к репозиторию его прочитает → не коммитить; использовать Ansible Vault (урок 75) или GitLab CI/CD Variables; при утечке — **менять секрет**, а не просто удалять файл.
2. **Работа прямо в `main`** → нет ни ревью, ни возможности сравнить → защищённая ветка + фича-ветки + MR.
3. **`git reset --hard` на общем репозитории** → у коллег расходится история, начинаются «загадочные» конфликты → только `git revert`.
4. **Коммит «fix» на 40 файлов** → по истории невозможно понять, что именно сломалось → один коммит = одно логическое изменение, сообщение формата `область: что и зачем`.
5. **Нет тегов** → некуда откатиться, «прошлая рабочая версия» не существует → тег на каждое состояние, уехавшее на прод.
6. **Репозиторий считают бэкапом** → у GitLab один диск, сервер eсть, бэкапа нет → `gitlab-backup create` по расписанию + вывоз копии за пределы ВМ; репозиторий — не резервная копия, а журнал изменений.
7. **Ревью ради галочки** → approve без чтения диффа → смотреть `git diff` целиком, особенно строки с адресами, путями и правами.
8. **Один огромный репозиторий на всё, включая ISO и дампы БД** → репозиторий распухает до гигабайт, клонирование занимает часы → крупные бинарники в отдельное хранилище, в Git — только текст.

**Безопасность.** Репозиторий конфигураций — это карта сети и инструкция по её обходу. В боевой среде нельзя: давать всем права Maintainer/Owner (достаточно Developer + защищённая `main`); держать GitLab по HTTP без TLS; хранить приватные SSH-ключи в репозитории; оставлять учётку `root` GitLab без смены пароля и без 2FA; пускать веб-интерфейс GitLab в интернет без VPN. В «Векторе» всё это — учебный компромисс, о котором ты пишешь в `stand-log.md`.

## 7. Вопросы на собеседовании

**1. «Как вы организуете хранение конфигураций в Git — один репозиторий на всё или много?»**
Ответ: зависит от масштаба и прав. Монорепо удобен, когда есть общий пайплайн и одна команда: атомарные изменения сквозь несколько сервисов, единая история, проще ревьюить. Много репозиториев оправданы, когда разные команды/подрядчики и разные права доступа, а также когда у компонентов разный жизненный цикл. Для 50 сотрудников — один репозиторий `vektor-infra` с каталогами по узлам (`nftables/`, `nginx/`, `scripts/`), защищённая `main`, релизы тегами.
*Что хочет услышать интервьюер:* понимание trade-off и привязки к правам/командам, а не заученный ответ.
*Красный флаг:* «всегда монорепо, так модно» без обоснования.

**2. «Зачем нужно ревью изменений в инфраструктуре и как вы его вводите, если коллеги сопротивляются?»**
Ответ: ревью ловит опечатки до прода (неверный `root`, лишнее правило nftables), фиксирует автора и согласовавшего для аудита, распределяет знания — второй человек видит конфиг. Вводят мягко: сначала обязательный MR без обязательного апрува, шаблон описания MR, чек-лист («проверил `nginx -t`»), мелкие MR на 5–10 строк, ревью в течение рабочего дня. Защищённая `main` технически заставляет пройти процесс.
*Что хочет услышать:* ревью как процесс и культура, а не как запрет.
*Красный флаг:* «у нас нет времени на ревью, я всё проверяю сам».

**3. «Чем тег отличается от ветки и как вы делаете релиз конфигурации?»**
Ответ: ветка — движущийся указатель, тег — неподвижный указатель на конкретный коммит. Тег не меняется, поэтому это единственный надёжный якорь для отката. Релиз: изменения прошли MR в `main` → проверены на стенде → `git tag -a vX.Y.Z -m "..."` → `git push origin vX.Y.Z` → в GitLab Release с описанием изменений → деплой = checkout этого тега на серверах. Версии — по semver: `PATCH` — исправление, `MINOR` — новое правило/сервис, `MAJOR` — несовместимая переделка (например, смена схемы адресации).
*Что хочет услышать:* аннотированные теги, push тега, семантическое версионирование, деплой по тегу.
*Красный флаг:* «тег — это то же самое, что ветка» или `git push --tags` без понимания, что уйдёт всё.

**4. «В `main` попал файл с паролем. Ваши действия?»**
Ответ: считать пароль скомпрометированным и **немедленно сменить** — история уже разошлась по клонам. Далее: удалить файл из индекса, добавить в `.gitignore`, перенести секрет в Vault/CI-переменные, при необходимости вычистить историю (`git filter-repo`) с предупреждением всех и force-push, что для общего репозитория — крайняя мера. Затем разобрать причину: ревью не заметило, потому что дифф не читали.
*Что хочет услышать:* «меняем секрет, а не просто удаляем файл» и понимание, что история Git публична внутри команды.
*Красный флаг:* «сделаю `git rm` и всё, пароля больше нет».

**5. «Merge или rebase? Можно ли делать force push?»**
Ответ: в общем репозитории — merge (или squash merge через GitLab), история сохраняется, ничего не переписывается. Rebase — для своей локальной ветки до публикации, чтобы подтянуть свежий `main`. Force push запрещён в `main` и вообще в опубликованных ветках, где работают другие; допустим только в личной ветке до MR и лучше в форме `--force-with-lease`, которая не затрёт чужие изменения.
*Что хочет услышать:* «переписывание истории опасно для тех, кто уже склонировал».
*Красный флаг:* «force push — нормально, главное потом всем сказать».
