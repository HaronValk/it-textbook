## 2. Теория «под капотом»

**Нода и кластер.** Proxmox VE — это Debian + KVM/QEMU + LXC + набор собственных демонов. Одиночная нода хранит конфиги в `/etc/pve` — это не обычная папка, а FUSE-файловая система `pmxcfs`, которую обслуживает служба `pve-cluster`. Как только ноды объединяются в кластер, `/etc/pve` становится общим: конфиг виртуалки, созданный на pve01, сразу виден на pve02. Синхронизацию и голосование обеспечивает **Corosync** (UDP 5405–5412).

**Кворум (quorum).** Кластер принимает решения, только если на связи больше половины голосов. Три ноды → нужно 2 голоса. Одна нода упала — кластер жив и работает в режиме read-write. Две упали — кворума нет, `/etc/pve` переходит в режим «только чтение», HA замирает, управление фактически парализовано (но запущенные виртуалки продолжают работать). Кластер из двух нод — плохая идея: при потере связи каждая нода считает себя единственной живой, начинается split-brain. Для двух нод ставится **QDevice** — арбитр на третьей машине (`corosync-qnetd`, TCP 5403).

**HA-стек.** Два демона: `pve-ha-crm` (cluster resource manager — один на кластер, принимает решения) и `pve-ha-lrm` (local resource manager — на каждой ноде, исполняет). Чтобы виртуалка не запустилась дважды, используется **фенсинг через watchdog**: нода, потерявшая связь с CRM, обязана «умереть» (перезагрузиться), чтобы гарантированно освободить свои VM. В виртуалке работает программный `softdog`, в продакшене — аппаратный watchdog (IPMI, i6300esb).

**Ceph.** Распределённая система хранения: данные режутся на объекты, раскладываются по OSD (это диски) согласно карте CRUSH, реплицируются. Компоненты: **MON** (мониторы, кворум хранилища, 3300/6789), **MGR** (менеджер, метрики, dashboard на 8443), **OSD** (диски, 6800–7300), **MDS** (только для CephFS). Данные лежат в **пулах**, пул делится на **PG** (placement groups — единица репликации). Параметры `size` (сколько копий) и `min_size` (минимум копий для записи) определяют, сколько отказов вы переживёте. Proxmox подключает Ceph-пул как storage типа RBD — блочное устройство для диска виртуалки.

**Миграция.** Offline — VM выключена, диск копируется. Online (live) — VM работает, память переносится в цикле pre-copy, в конце короткая остановка (обычно доли секунды — секунды). Если диск на общем хранилище (Ceph, NFS), переносится только память. Если диск локальный — нужен `--with-local-disks` или заранее настроенная репликация ZFS.

```text
        ┌──────────── кластер vektor-cluster (corosync, UDP 5405-5412) ───────────┐
        │                                                                         │
    pve01 10.10.10.70  ◄────►  pve02 10.10.10.71  ◄────►  pve03 10.10.10.72      │
        │  pmxcfs: /etc/pve — общая ФС кластера                                    │
        │  pve-ha-crm (решения) + pve-ha-lrm (исполнение) + watchdog (фенсинг)     │
        └─────────────────────────────────┬───────────────────────────────────────┘
                                          │
                        Ceph, сеть 10.10.10.0/24 (в лабе одна сеть)
             MON x3 (3300/6789)   MGR x3 (8443)   OSD x3 (6800-7300)
                                          │
                            pool labpool (size 2, min_size 1)
                                          │
                          RBD → диск VM 900 (TEST01) → HA-ресурс
```

Управление — веб-интерфейс и API на TCP 8006 (`pveproxy`), консоль SPICE — через прокси 3128, миграция и вход в кластер — по SSH (22). Резервное копирование в Proxmox Backup Server — 8007.

## 3. Аналогия из жизни

Представьте смену на складе логистической компании. Corosync — это рации: пока на связи большинство бригады, решения принимаются (кворум). Если рации замолчали у двоих из трёх, бригадир не имеет права ничего менять — работа идёт по инерции, но новые распоряжения не выдаются. HA-диспетчер следит за заявками: если у кладовщика случился обморок, диспетчер ждёт подтверждения, что тот реально без сознания (watchdog), и только потом передаёт его накладные другому — иначе двое начнут отгружать один и тот же заказ. Ceph — это стеллажи, где каждая паллета лежит в двух-трёх экземплярах в разных концах склада, поэтому потеря одного стеллажа не останавливает отгрузку. А Proxmox Backup Server — архив накладных с описью и периодической сверкой: архив, который ни разу не разбирали, доверия не заслуживает.

Аналогия ломается в одном месте: людям не нужен аппаратный watchdog, чтобы объявить человека нетрудоспособным, — а ноде без фенсинга кластер не поверит, и это принципиально.

## 4. Практика и команды

**1. Создание кластера и вход в него**

```bash
# на pve01
pvecm create vektor-cluster
# на pve02 и pve03
pvecm add 10.10.10.70
```

`create` — инициализирует corosync и pmxcfs; `add <IP>` — подключается к существующей ноде (спросит root-пароль и сверит отпечаток SSH-ключа). Имя кластера — латиница, без пробелов.

**2. Состояние кворума**

```bash
pvecm status
pvecm nodes
```

Сокращённый вывод:

```text
Quorum information
Nodes:            3
Expected votes:   3
Total votes:      3
Quorum:           2
Flags:            Quorate
```

Смотрим: `Quorate: Yes` и все три ноды в списке членов. Если `Flags: No quorum` — дальше можно только читать.

**3. Диагностика кластерных служб**

```bash
systemctl status pve-cluster corosync
journalctl -u corosync -n 50 --no-pager
cat /etc/pve/corosync.conf
```

`pve-cluster` держит `/etc/pve`, `corosync` — связь. Частая причина проблем — рассинхрон времени: `chronyc tracking` на всех нодах должен показывать малый offset.

**4. Аварийное восстановление кворума (временно!)**

```bash
pvecm expected 1
```

Говорит кластеру «считай, что голосов достаточно» — чтобы починить конфиг руками. **Обязательно** вернуть `pvecm expected 3` сразу после ремонта, иначе получите split-brain.

**5. Установка и инициализация Ceph**

```bash
pveceph install --version reef      # версию сверяйте с документацией [ПРОВЕРИТЬ]
pveceph init --network 10.10.10.0/24
pveceph mon create                  # на каждой ноде, по очереди
pveceph mgr create                  # на каждой ноде
```

`init` прописывает `public_network` в `/etc/pve/ceph.conf`. Мониторов ставьте нечётное число и не меньше трёх.

**6. Добавление диска в Ceph**

```bash
ceph-volume lvm zap --destroy /dev/sdb
pveceph osd create /dev/sdb
```

`zap --destroy` стирает старые подписи (в GUI — Disks → Wipe Disk). Без затирания `osd create` откажется.

**7. Проверка здоровья Ceph**

```bash
ceph -s
ceph osd tree
ceph osd df
```

```text
  health: HEALTH_OK
  services:
    mon: 3 daemons, quorum pve01,pve02,pve03
    mgr: pve01(active), standbys: pve02, pve03
    osd: 3 osds: 3 up, 3 in
  data:
    pools:   1 pools, 64 pgs
    usage:   1.2 GiB used
```

Смотрим три вещи: `HEALTH_OK`, все OSD `up/in`, нет `pgs incomplete`.

**8. Пул и подключение его как хранилища**

```bash
pveceph pool create labpool --size 2 --min_size 1
pvesm add rbd ceph-lab --pool labpool --content images,rootdir
pvesm status
```

`--size 2 --min_size 1` — переживает отказ одной ноды, но не двух. В продакшене обычно `size 3`.

**9. Управление HA**

```bash
ha-manager add vm:900 --state started --max_restart 3 --max_relocate 3
ha-manager status
ha-manager config
```

```text
quorum OK
master pve01 (active)
lrm pve02 (active)
service vm:900 (pve02, started)
```

`--max_restart` — сколько раз перезапускать на той же ноде, `--max_relocate` — сколько раз переносить, прежде чем признать ресурс сбойным.

**10. Живая миграция**

```bash
qm migrate 900 pve02 --online
qm status 900
```

`--online` — без выключения. Для локальных дисков добавляется `--with-local-disks`. Время смотрите в `/var/log/pve/tasks/` и в GUI → Tasks.

**11. Бэкап**

```bash
vzdump 900 --storage local --mode snapshot --compress zstd
ls -lh /var/lib/vz/dump/
```

`--mode snapshot` — снять образ без остановки (через QEMU-снапшот), `--compress zstd` — быстрый и плотный. В продакшене хранилище — Proxmox Backup Server: дедупликация, шифрование, verify-задания.

**12. Мониторинг: метрики наружу**

```bash
pveum user add prometheus@pve
pveum user token add prometheus@pve metrics --privsep 0
pveum acl modify / --users prometheus@pve --roles PVEAuditor
pveperf /var/lib/vz
```

Токен даёт доступ к API на 8006 только на чтение (роль `PVEAuditor`), а `pveperf` показывает локальную производительность FS/CPU. Дальше на UBU01 ставится `prometheus-pve-exporter` (порт 9221 по умолчанию) и скармливается Prometheus.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Снапшот

1. Погасите все вложенные виртуалки внутри PVE01 (`qm list`, затем `qm shutdown <id>` для каждой) — снапшот работающей VM с работающим гипервизором внутри снимать не стоит.

3. Для PVE02 и PVE03 снапшот не нужен — они создаются с нуля в этой лабе и при откате просто удаляются.

### Шаги

1. **На PVE01.** Проверьте исходное состояние: `pvecm status` → `no cluster`, `ip -br a` → адрес 10.10.10.70 на `vmbr0`, `chronyc tracking` → малый offset. Ожидаемо: одиночная нода, кворума нет.

Переключите на бесплатный `pve-no-subscription` [ПРОВЕРИТЬ актуальное имя файла в документации], затем `apt update && apt full-upgrade -y`. Ожидаемо: пакеты обновлены, баннер про подписку в GUI остаётся (это нормально, Proxmox бесплатен, подписка — это репозиторий и поддержка).

## 6. Ошибки новичков и безопасность

1. **Кластер из двух нод без QDevice** → при потере связи split-brain, обе ноды считают себя правыми, конфиги расходятся. Правильно: три ноды либо две + QDevice (`pvecm qdevice setup <IP>`).
2. **`pvecm expected 1` как «лекарство»** → маскирует потерю кворума, приводит к расхождению `/etc/pve` и порче конфигов. Правильно: только временно, для ремонта, с немедленным возвратом `expected 3`.
3. **Ceph на одной ноде или с одним монитором** → нет отказоустойчивости, теряется весь пул. Правильно: минимум 3 ноды, 3 MON, OSD на разных физических дисках.
4. **`size 3` при `min_size 3`** → при отказе одной ноды запись встаёт полностью. Правильно: `min_size 2` при `size 3`.
5. **HA без рабочего watchdog** → VM может быть запущена дважды на разных нодах, диск разрушается. В виртуалке это `softdog`, на железе — аппаратный watchdog, проверять `cat /sys/class/watchdog/watchdog0/identity`.
6. **Бэкапы в тот же Ceph, где живут диски VM** → потеря пула = потеря и данных, и бэкапов. Правильно: отдельное хранилище, PBS, правило 3-2-1-1-0 (урок 38).
7. **Обновление всех нод одной командой сразу** → одновременный перезапуск corosync и pve-cluster, потеря кворума и падение HA. Правильно: по одной ноде, с проверкой `pvecm status` между ними.
8. **Игнорирование времени** → рассинхрон chrony рвёт corosync, ноды мигают «no quorum». Правильно: единый NTP-источник, алерт на offset.

**Безопасность.** Никогда не выключайте `cephx` (аутентификацию Ceph) и не открывайте 8006 в интернет — только через VPN или обратный прокси с MFA. Не создавайте API-токены от `root@pam`: отдельный пользователь + `PVEAuditor` только на чтение. Не отключайте проверку TLS-сертификата в интеграциях «чтобы работало». Бэкапы в PBS шифруйте, если они уезжают за пределы контура. Root-SSH по паролю на нодах замените на ключи. И помните: на стенде пароль `Lab#2026-vektor` — учебный; в боевой среде такая практика недопустима.

## 7. Вопросы на собеседовании

**1. «Что такое кворум в кластере Proxmox и что произойдёт, если из трёх нод пропадёт одна? А две?»**

Ответ: кворум — механизм corosync, при котором решения принимаются большинством голосов. В кластере из трёх нод нужно 2 голоса. При потере одной ноды кластер сохраняет кворум, `/etc/pve` остаётся доступным на запись, HA перезапускает VM с упавшей ноды на живые — при условии, что диск доступен (Ceph/NFS). При потере двух нод кворума нет: `/etc/pve` монтируется только для чтения, HA останавливается, но уже запущенные VM продолжают работать. Восстановление — вернуть ноды в сеть; `pvecm expected 1` только как временная мера.

*Что хочет услышать интервьюер:* понимание разницы между «кластер жив» и «VM живы», знание про read-only `/etc/pve` и про то, что кворум не перезапускает виртуалки.
*Красный флаг:* «при потере двух нод виртуалки перезапустятся на третьей» или «поставлю expected 1, и всё заработает».

**2. «Как Proxmox гарантирует, что виртуалка не запустится на двух нодах одновременно?»**

Ответ: через фенсинг и watchdog. `pve-ha-crm` — единственный, кто принимает решения; `pve-ha-lrm` на каждой ноде подтверждает, что держит ресурс, и постоянно «кормит» watchdog. Если нода теряет связь с CRM, watchdog по таймауту её перезагружает — только после этого CRM отдаёт VM другой ноде. На железе нужен аппаратный watchdog (IPMI/i6300esb), в виртуалке — `softdog`, что для продакшена неприемлемо.

*Что хочет услышать интервьюер:* связку fencing → watchdog → отсутствие split-brain, понимание, что HA без фенсинга опаснее, чем без HA.
*Красный флаг:* «HA просто перезапускает VM на другой ноде» без упоминания фенсинга.

**3. «Чем live-миграция отличается от offline и от чего зависит время простоя?»**

Ответ: offline — VM выключена, диск копируется целиком, простой равен времени копирования. Live — VM работает, память переносится циклами pre-copy, в конце короткая пауза (обычно доли секунды — единицы секунд), после чего VM продолжает работу на целевой ноде. Простой зависит от объёма «горячей» памяти, скорости сети и нагрузки: при очень активной записи в память pre-copy может не сойтись, и Proxmox переходит к stop-and-copy. Если диск на общем хранилище, переносится только память; если локальный — нужен `--with-local-disks` (копирование диска, долго) или заранее настроенная репликация ZFS.

*Что хочет услышать интервьюер:* pre-copy, зависимость от dirty pages и сети, разница между общим и локальным хранилищем.
*Красный флаг:* «live-миграция вообще без простоя» — простой есть, просто короткий.

**4. «Расскажите, как устроен Ceph в Proxmox: зачем MON, OSD, PG и что такое size/min_size».**

Ответ: Ceph — распределённое объектное хранилище. MON держат карту кластера и кворум (нужно нечётное число, минимум 3), MGR собирают метрики и dashboard, OSD — это диски, которые хранят данные и участвуют в репликации, CRUSH-карта определяет, на какие OSD попадёт объект. Пул режется на PG — единицы репликации; `size` — число копий, `min_size` — минимум доступных копий, при котором запись ещё возможна. При `size 3 / min_size 2` переживаем отказ одной ноды без остановки записи. Proxmox подключает пул как storage типа RBD и даёт его виртуалкам как блочный диск.

*Что хочет услышать интервьюер:* понимание, что Ceph — не «RAID по сети», а отдельная система со своей логикой отказа, и осознанный выбор size/min_size.
*Красный флаг:* «поставлю size 2, чтобы места больше было» без обсуждения отказоустойчивости.

**5. «Как вы строите резервное копирование виртуалок и как убеждаетесь, что бэкап рабочий?»**

Ответ: vzdump с режимом `snapshot` (без остановки) в отдельное хранилище, лучше в Proxmox Backup Server — там дедупликация, инкрементальные бэкапы, шифрование и verify-задания. Расписание — ночью, retention — по политике (например, 7 daily / 4 weekly / 6 monthly). Правило 3-2-1-1-0: три копии, два носителя, одна вне площадки, одна неизменяемая (иммутабельная) и ноль ошибок при проверке. Раз в квартал — тестовое восстановление конкретной VM на изолированный стенд с замером RTO. Бэкап без проверки восстановлением не считается бэкапом.

*Что хочет услышать интервьюер:* регулярность, изоляция копий, иммутабельность, реальные тесты восстановления и названные RTO/RPO.
*Красный флаг:* «бэкапы делаются, всё настроено» без единого упоминания проверки восстановления.
