# Комплексный проект №4: автоматизация всей инфраструктуры через Ansible + Terraform + Git

## 1. Введение (зачем это нужно в реальной работе)

```text
Тикет #4821 · Сидоров А. (склад) · Срочность: средняя
«Алексей, привет. Запускаем пилот по новой номенклатуре, нужен отдельный
тестовый сервер, чтобы не ломать SRV1C01. Такой же Ubuntu, как UBU01, только
отдельный. Через две недели, наверное, второй. Потом всё это удалим.
И доступ туда нужен только мне и Иванову.»
```

Полгода назад вы бы пошли в VMware Workstation, создали ВМ руками, вспомнили, какие пакеты ставили на UBU01, дописали пользователя, а через две недели честно признались бы, что не помните, какой из пяти пунктов настройки забыли. Именно так выглядит инфраструктура, которая живёт в голове сисадмина, а не в документе. Дальше — три следствия: переустановка сервера всегда «по памяти», однотипные серверы расходятся в конфигурации через месяц, а на вопрос «а что у нас вообще настроено?» ответить нечем.

Тема этой главы — сделать так, чтобы описание инфраструктуры лежало в файлах, лежало в системе контроля версий, применялось одной командой и проверялось до применения. После главы вы будете уметь: описывать ВМ кодом (Terraform), описывать конфигурацию внутри ОС кодом (Ansible), хранить всё это в Git, отделять секреты от кода, проверять изменения в режиме «ничего не применять, только показать» и объяснять коллеге, чем Terraform отличается от Ansible. Это ровно тот набор, который отделяет «админа с руками» от инженера, которому можно отдать парк из 50 серверов.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**IaC (Infrastructure as Code, инфраструктура как код)** — подход, где серверы, сети и настройки описаны текстовыми файлами в репозитории. Файлы проверяются ревью, коммитятся, версионируются и применяются автоматически. Внутри IaC есть два разных инструмента с разными зонами ответственности, и путать их — самая частая ошибка.

**Terraform / OpenTofu — жизненный цикл ресурсов.** Отвечает на вопрос «существует ли ВМ, сколько у неё ядер, какой IP, на каком хранилище диск, из какого шаблона она сделана». Работает не через SSH, а через API гипервизора (в нашем случае Proxmox VE, HTTPS-порт 8006). Конфигурация пишется на языке HCL. Ключевые понятия:

- **Провайдер (provider)** — плагин, который умеет говорить с конкретным API (bpg/proxmox, vsphere, yandex и т.д.).
- **Ресурс (resource)** — единица управления, например `proxmox_virtual_environment_vm`.
- **State (состояние)** — файл, где Terraform помнит, что именно он создал и с какими параметрами. Без state он не знает разницы между «создать» и «уже создано». State — это ещё и секрет: в нём бывают пароли из cloud-init.
- **plan / apply** — сначала Terraform строит план (что добавит, что изменит, что уничтожит), потом применяет.
- **drift (расхождение)** — кто-то поправил ресурс руками; Terraform увидит расхождение только в тех параметрах, которые он же и задавал. Что происходит *внутри* ОС, Terraform не знает и не увидит никогда.

**Ansible — конфигурация внутри ОС.** Отвечает на вопрос «какие пакеты стоят, какие пользователи есть, что в sshd_config, запущен ли chrony». Работает **агентless**: по SSH (порт 22) для Linux и по WinRM (порты 5985 — HTTP, 5986 — HTTPS) для Windows. Никакого демона на целевой машине не нужно — только Python на Linux-хосте. Единица описания — **playbook** (YAML), внутри него **tasks** (задачи), задачи вызывают **modules** (модули, готовые идемпотентные операции: `apt`, `user`, `lineinfile`, `win_service`). Логика раскладывается по **roles** (ролям) с папками `tasks/`, `handlers/`, `templates/`, `files/`, `defaults/`. Инвентарь (**inventory**) — список хостов и групп.

**Идемпотентность** — свойство, при котором повторный запуск приводит систему к тому же состоянию и не делает лишних изменений (`changed=0`). Это главный тест качества плейбука: если второй прогон что-то «меняет», у вас не описание состояния, а скрипт.

**Git — источник правды и история.** Репозиторий хранит не только текущее состояние файлов, но и кто, когда и зачем что поменял. Ветки позволяют готовить изменение отдельно, теги фиксируют «эта версия инфраструктуры работала», а ревью (pull request) — единственная реальная защита от «в пятницу вечером применил и сломал».

Как это стыкуется:

```text
   ┌────────────────┐   git push (SSH 22)   ┌──────────────────────────────┐
   │ ANS01          │ ────────────────────► │ bare-репозиторий             │
   │ control node   │ ◄──────────────────── │ /srv/git/vektor-infra.git    │
   │ (рабочая копия)│        git pull       └──────────────────────────────┘
   │                │
   │ tofu apply ────┼── HTTPS 8006 ──► PVE01 API ──► создать/удалить ВМ UBU02
   │                │                              (CPU, RAM, диск, IP, шаблон)
   │ ansible-       │── SSH 22 ─────► UBU01 / UBU02 / ASTRA01   (что внутри ОС)
   │ playbook ──────┼── WinRM 5985 ─► DC01 / FS01               (что внутри ОС)
   └────────────────┘
```

Порядок в конвейере жёсткий: **Terraform создаёт «железо» → Ansible настраивает ОС → всё это лежит в Git**. Ansible не умеет создавать ВМ, Terraform не умеет ставить пакеты. По модели OSI всё это прикладной уровень (L7): HTTPS, SSH, WS-Management — протоколы приложений поверх TCP.

## 3. Аналогия из жизни

Представьте застройку посёлка. **Terraform** — это генплан и разрешительная документация: сколько домов, где, какой площади, подведено ли электричество, снесён ли барак. Инженер с генпланом приходит на участок и добивается, чтобы реальность совпала с чертежом: нет дома — построить, дом не той площади — снести и построить заново (Terraform по умолчанию пересоздаёт ресурс, а не «подпиливает» его). **Ansible** — прораб внутри каждого дома: развести проводку, повесить замки, поставить бойлер, выдать жильцам ключи. Прораб приходит по расписанию и проверяет: если розетка уже стоит — ничего не делает (идемпотентность), если кто-то её выкрутил — ставит обратно. **Git** — архивная папка с чертежами, где каждый лист подписан и датирован, а старые версии можно достать и сравнить. Аналогия перестаёт работать в одном месте: генплан не знает, что творится внутри дома, ровно как Terraform не знает, что у вас в `sshd_config`.

## 4. Практика и команды

Все команды выполняются на **ANS01** (Ubuntu Server 24.04, control node), если не указано иное.

**1. Установка инструментов и проверка версий**

```bash
sudo apt update
sudo apt install -y ansible-core git pipx
ansible --version
```

В выводе смотрим: версию `core` (2.16.x для Ubuntu 24.04 — норма), путь `config file` (важно: `ansible.cfg` из текущего каталога имеет приоритет — значит, из папки репозитория подхватится именно он) и `collection location`.

**2. Коллекции Ansible**

```bash
ansible-galaxy collection install ansible.posix community.general ansible.windows
ansible-galaxy collection list | head -20
```

`ansible-core` содержит только базовые модули (`ansible.builtin.*`). Всё остальное — коллекции: `ansible.posix` (authorized_key, sysctl), `community.general` (timezone, ufw), `ansible.windows` (модули для Windows). Версии фиксируются в `requirements.yml` — иначе «вчера работало».

**3. Проверка инвентаря**

```bash
ansible-inventory -i inventory/hosts.yml --graph
```

```text
@all:
  |--@linux:
  |  |--@ubuntu:
  |  |  |--UBU01
  |  |  |--UBU02
  |  |--@astra:
  |  |  |--ASTRA01
  |--@windows:
  |  |--DC01
  |  |--FS01
```

Смотреть: все ли хосты на месте, не попали ли они в `ungrouped` (значит, отступы в YAML поехали).

**4. Проверка связи**

```bash
ansible all -m ansible.builtin.ping
ansible UBU01 -m ansible.builtin.setup -a "filter=ansible_distribution*"
```

`ping` здесь — не ICMP, а модуль, который логинится по SSH и возвращает `pong`. Если `UNREACHABLE` — проблема в доступе/сети, а не в плейбуке. Второй командой смотрим собранные **facts** (факты о системе) — их можно использовать в условиях.

**5. Прогон плейбука в разных режимах**

```bash
ansible-playbook playbooks/site.yml --syntax-check
ansible-playbook playbooks/site.yml --check --diff --limit UBU02
ansible-playbook playbooks/site.yml --limit UBU02 -v
ansible-playbook playbooks/site.yml --list-tasks
```

`--syntax-check` — только парсинг YAML. `--check --diff` — «примерка»: показать, что изменилось бы, и diff по файлам. `--limit` — ограничить группу/хост. `-v` (до `-vvv`) — детали подключения. Важно: `--check` не работает для задач с `check_mode: false` и для `command`/`shell` — они либо пропускаются, либо всё равно выполняются.

**6. Секреты через Vault**

```bash
ansible-vault create group_vars/all/vault.yml
ansible-vault encrypt_string 'Lab#2026-vektor' --name 'vault_adm_password'
ansible-playbook playbooks/site.yml --ask-vault-pass
```

`ansible-vault` шифрует файл целиком (AES256). В репозиторий попадает зашифрованный блоб. Пароль vault — отдельно: в менеджере секретов, в переменной CI или в `--vault-password-file` с правами 600.

**7. Terraform/OpenTofu: базовый цикл**

```bash
cd terraform
tofu init -upgrade
tofu fmt -recursive
tofu validate
tofu plan -out=tfplan
tofu show tfplan
tofu apply tfplan
```

```text
Plan: 1 to add, 0 to change, 0 to destroy.
```

`init` скачивает провайдер в `.terraform/`, `fmt` приводит HCL к канону, `validate` проверяет синтаксис, `plan -out` сохраняет план в файл (защита от того, что между plan и apply кто-то поменял код), `apply tfplan` применяет ровно его. Команды `tofu` идентичны `terraform`, разница только в названии бинарника.

**8. Инвентаризация и пересоздание ресурса**

```bash
tofu state list
tofu plan -replace=proxmox_virtual_environment_vm.ubu02
tofu state rm proxmox_virtual_environment_vm.ubu02
```

`state list` — что Terraform считает своим. `-replace` — принудительно пересоздать ресурс (старый `taint` устарел). `state rm` — «забыть» ресурс, не удаляя его (нужно, если ВМ снесли руками и state рассыпался). **Никогда** не редактируйте state руками.

**9. Git: работать, а не «сохранять файлы»**

```bash
git init
git add -A && git commit -m "feat: базовый каркас IaC (inventory, baseline, proxmox)"
git remote add origin git@ANS01:/srv/git/vektor-infra.git
git push -u origin main
git tag -a v1.0 -m "рабочая автоматизация стенда"
git push --tags
git log --oneline --graph --all
```

Смотреть в `log`: короткие атомарные коммиты с осмысленными сообщениями. Один коммит «всё» — признак того, что через месяц вы не найдёте, из-за чего сломалось.

**10. `.gitignore` — граница между кодом и мусором**

```gitignore
.terraform/
*.tfstate
*.tfstate.*
*.tfplan
*.auto.tfvars
vault-password.txt
*.retry
```

Правило простое: в Git — то, что вы написали руками. State, кэш провайдера, планы и пароли — не ваши тексты.

**11. Windows: включить WinRM (на DC01, PowerShell от админа)**

```powershell
Enable-PSRemoting -Force
Test-WSMan DC01
Get-NetFirewallRule -DisplayName "*WS-Management*" | Select DisplayName,Enabled
```

`Enable-PSRemoting` создаёт listeners, правила файрвола и запускает службу WinRM. По умолчанию используется NTLM/Kerberos по HTTP 5985. Проверка с ANS01: `ansible windows -m ansible.windows.win_ping`. Для HTTPS (5986) нужен сертификат на стороне Windows — в продакшене только так.

**12. Хук, который не даёт запушить мусор**

```bash
mkdir -p .githooks
cat > .githooks/pre-commit <<'EOF'
#!/bin/sh
set -e
tofu fmt -check -recursive terraform/
ansible-lint ansible/ || { echo "lint failed"; exit 1; }
EOF
chmod +x .githooks/pre-commit
git config core.hooksPath .githooks
```

`core.hooksPath` заставляет Git искать хуки в папке репозитория — тогда они версионируются вместе с кодом, а не живут только у вас в `.git/hooks`.

## 5. Лабораторная работа (пошаговый сценарий на виртуалке)

### Предусловия

- Стенд L2 развёрнут полностью: **DC01** (10.10.10.10), **FS01** (10.10.10.20), **UBU01** (10.10.10.30), **ASTRA01** (10.10.10.31), домен `corp.vektor.lab`, учётка `adm.student`.
- **PVE01** (10.10.10.70) из урока 102 — работает, в VMware Workstation сетевой адаптер висит на VMnet8, интерфейс `vmbr0` имеет адрес `10.10.10.70/24`.
- Добавляем в этой главе две новые машины: **ANS01** (Ubuntu Server 24.04, 10.10.10.35) — control node и Git-сервер, и **UBU02** (10.10.10.36) — ВМ, которую создаст Terraform.
- Если PVE01 у вас нет — сначала пройдите урок 102, без API гипервизора Terraform не к чему подключаться.
- На ANS01 должен быть выход в интернет (NAT через 10.10.10.2), иначе не скачаются провайдер и коллекции.

### Снапшот

В VMware Workstation: выделить ВМ → **VM → Snapshot → Take Snapshot**, имя `before-sysadmin-104`. Сделать на **PVE01** и **UBU01** (те ВМ, которые мы меняем). ANS01 и UBU02 на момент снапшота ещё не существуют — их «откат» = удаление, об этом в конце.

### Шаги

1. **ANS01, установка.** Создать ВМ в VMware Workstation, поставить Ubuntu Server 24.04, hostname `ANS01`, статический адрес `10.10.10.35/24`, шлюз `10.10.10.2`, DNS `10.10.10.10`, локальная учётка `adm.student` с sudo. Ожидаемо: `ip -br a` показывает `ens33 10.10.10.35/24`, `ping 10.10.10.10` отвечает.
2. **ANS01, инструменты.** `sudo apt update && sudo apt install -y ansible-core git pipx && pipx install ansible-lint && git --version`. Ожидаемо: `ansible [core 2.16.x]`, `git version 2.4x`.
3. **ANS01, ключи.** `ssh-keygen -t ed25519 -a 100 -C "ans01-ansible"`, затем `ssh-copy-id adm.student@10.10.10.30` и `ssh-copy-id adm.student@10.10.10.31`. Ожидаемо: `ssh adm.student@10.10.10.30` пускает без пароля.
4. **ANS01, служебная учётка для автоматизации.** На UBU01 и ASTRA01 создать пользователя `ansible` (это учётка, которую мы вводим в этой главе специально для IaC) и выдать ограниченный sudo:

   ```bash
   sudo adduser --disabled-password --gecos "" ansible
   sudo install -d -m 700 -o ansible -g ansible /home/ansible/.ssh
   sudo sh -c 'cat /home/adm.student/.ssh/authorized_keys > /home/ansible/.ssh/authorized_keys'
   sudo chown ansible:ansible /home/ansible/.ssh/authorized_keys
   echo 'ansible ALL=(ALL) NOPASSWD: /usr/bin/apt, /usr/bin/systemctl' | sudo tee /etc/sudoers.d/ansible
   sudo chmod 440 /etc/sudoers.d/ansible
   ```

   Ожидаемо: `ssh ansible@10.10.10.30 'sudo -n systemctl is-active ssh'` возвращает `active`. В реальной среде NOPASSWD на такой широкий набор — плохая практика, см. раздел 6.
5. **ANS01, Git-сервер.** `sudo adduser --system --group --home /srv/git git`, `sudo -u git git init --bare /srv/git/vektor-infra.git`, `sudo -u git git symbolic-ref HEAD refs/heads/main`. Ожидаемо: каталог `/srv/git/vektor-infra.git` с подкаталогами `objects`, `refs`.
6. **ANS01, каркас репозитория.** `git clone git@ANS01:/srv/git/vektor-infra.git ~/vektor-infra && cd ~/vektor-infra`. Создать структуру:

   ```text
   vektor-infra/
   ├── ansible.cfg
   ├── inventory/hosts.yml
   ├── group_vars/all/main.yml
   ├── group_vars/windows/main.yml
   ├── playbooks/site.yml
   ├── roles/baseline/{tasks,handlers,files}/
   ├── terraform/{main.tf,proxmox.tf,variables.tf,outputs.tf}
   ├── .gitignore
   └── README.md
   ```

   Коммит: `git add -A && git commit -m "feat: каркас IaC"`. Ожидаемо: `git log --oneline` показывает один коммит.
7. **Ansible-инвентарь и первый пинг.** Заполнить `inventory/hosts.yml` группами `linux:children:ubuntu/astra` и `windows`, для Linux указать `ansible_user: ansible`, для Windows — `ansible_connection: winrm`, `ansible_user: VEKTOR\adm.student`. Прогнать `ansible linux -m ansible.builtin.ping`. Ожидаемо: три `pong` (UBU01, UBU02 пока нет — уберите его до шага 10, ASTRA01).
8. **Роль `baseline`.** В `roles/baseline/tasks/main.yml` — пакеты (`chrony`, `vim`, `curl`, `htop`), часовой пояс `Europe/Moscow` (`community.general.timezone`), `PasswordAuthentication no` через `ansible.builtin.lineinfile` с `notify: restart sshd`, и хендлер `ansible.builtin.service: name=ssh state=restarted`. **Перед этим убедитесь, что ключ есть и у `adm.student`** — иначе отключите себе вход паролем. Прогон: `ansible-playbook playbooks/site.yml --limit linux`. Ожидаемо: `changed=N, failed=0`, второй прогон — `changed=0`.
9. **Секреты.** `ansible-vault create group_vars/all/vault.yml` со строкой `vault_adm_password: "Lab#2026-vektor"`, в `group_vars/windows/main.yml` — `ansible_password: "{{ vault_adm_password }}"`. Проверка: `ansible windows -m ansible.windows.win_ping --ask-vault-pass`. Ожидаемо: `pong` от DC01 и FS01. На DC01 предварительно выполнен `Enable-PSRemoting -Force`.
10. **Terraform: токен и шаблон на PVE01.** В веб-интерфейсе PVE01: **Datacenter → Permissions → API Tokens → Add**, пользователь `root@pam`, Token ID `ansible`, снять/оставить Privilege Separation и выдать права на `/` (для стенда — роль `PVEAdmin`; в продакшене — минимальный набор на пул ВМ) `[ПРОВЕРИТЬ точные имена привилегий в вашей версии]`. Затем на PVE01 создать шаблон из cloud-образа:

    ```bash
    cd /var/lib/vz/template/iso
    wget https://cloud-images.ubuntu.com/noble/current/noble-server-cloudimg-amd64.img
    qm create 9000 --name tmpl-ubuntu-2404 --memory 2048 --cores 2 --net0 virtio,bridge=vmbr0
    qm importdisk 9000 noble-server-cloudimg-amd64.img local-lvm
    qm set 9000 --scsihw virtio-scsi-pci --scsi0 local-lvm:vm-9000-disk-0
    qm set 9000 --ide2 local-lvm:cloudinit --boot order=scsi0 --serial0 socket --vga serial0
    qm set 9000 --agent enabled=1
    qm template 9000
    ```

    Имя хранилища проверьте через `pvesm status` (может быть `local-lvm`, `local-zfs` и т.п.) `[ПРОВЕРИТЬ]`.
11. **Terraform: описание UBU02 и apply.** В `terraform/proxmox.tf` — провайдер `bpg/proxmox` (`endpoint = "https://10.10.10.70:8006/"`, `api_token = var.pve_api_token`, `insecure = true`) и ресурс:

    ```hcl
    resource "proxmox_virtual_environment_vm" "ubu02" {
      name      = "UBU02"
      node_name = "pve01"
      vm_id     = 136
      clone { vm_id = 9000 }
      cpu    { cores = 2 }
    ```

1. С ANS01: `ansible UBU02 -m ansible.builtin.ping` → `UNREACHABLE! ... Authentication or permission failure`.

## 6. Ошибки новичков и безопасность

1. **State-файл в Git.** → В репозиторий утекают параметры ВМ, cloud-init пароли и структура инфраструктуры; при работе вдвоём state перетирается и Terraform «теряет» ресурсы. → `.gitignore` + удалённый бэкенд (S3/MinIO, Postgres) с блокировкой; для стенда — просто локально и вне Git.
2. **Пароли в открытом виде в `group_vars`.** → Первый же клон репозитория = компрометация. → `ansible-vault`, CI-переменные, SOPS; пароль vault — отдельно от кода.
3. **`command`/`shell` вместо модулей.** → Задача «выполнена» при каждом прогоне, `changed` всегда > 0, идемпотентность потеряна, `--check` бесполезен. → `apt`, `user`, `lineinfile`, `service`, `template` — они проверяют состояние.
4. **Правки руками «по-быстрому».** → Дрейф: код говорит одно, машина делает другое; следующее `apply` молча затрёт вашу правку. → Любая правка — через плейбук и коммит, даже если это одна строка.
5. **`tofu destroy` без понимания, что в state.** → Снос живой ВМ вместе с диском. → Всегда `plan` и читать секцию `destroy`; для стенда — снапшот до, `-target` для точечных операций.
6. **Отключение `PasswordAuthentication` до проверки ключей.** → Потеря SSH-доступа к серверу, спасает только консоль гипервизора. → Держать открытую сессию, проверять вторым окном, откатывать через ту же консоль.
7. **Незапиненные версии провайдера и коллекций.** → «Вчера работало, сегодня `init` поставил новую мажорную версию и всё сломалось». → `version = "~> 0.x"` в `required_providers`, `requirements.yml` с версиями.
8. **NOPASSWD на всё для `ansible`.** → Компрометация ключа control node = root на всём парке. → Ограничить sudo конкретными командами, ключ с парольной фразой + `ssh-agent`, ограничение `from=` в `authorized_keys`.

**Безопасность (что нельзя в боевой среде).** Хранить state и vault-пароль рядом с кодом; выдавать Terraform-токену `root@pam` с полными правами (нужен отдельный пользователь и минимальные привилегии на конкретный пул); гонять WinRM по HTTP с Basic-аутентификацией (только HTTPS 5986 или Kerberos); коммитить `*.auto.tfvars` с адресами и паролями; пушить в `main` без ревью — включите защиту ветки, иначе автоматизация станет способом сломать всё сразу и легально. Отдельно: репозиторий с описанием инфраструктуры — это документ ограниченного доступа, если в нём адресация и схемы сети реальной компании (152-ФЗ и внутренние регламенты ИБ).

## 7. Вопросы на собеседовании

**1. Чем Terraform отличается от Ansible и почему их используют вместе?**

Ответ: Terraform управляет жизненным циклом ресурсов (создать/изменить/удалить ВМ, сеть, диск) через API провайдера и хранит состояние в state-файле. Ansible управляет конфигурацией внутри уже существующей ОС, работает без агента по SSH/WinRM и не хранит состояние — он каждый раз приводит систему к описанному виду. Вместе: Terraform даёт «есть ли сервер и какой он», Ansible — «что в нём настроено». Плюс разделение ответственности: снос сервера и настройка пакетов — разные риски и разные люди/ревью.
*Что хочет услышать интервьюер:* понимание «state vs stateless», декларативности и границ применимости.
*Красный флаг:* «Ansible тоже может создавать ВМ, значит Terraform не нужен».

**2. Что такое state и почему его нельзя хранить в Git?**

Ответ: это файл соответствия «ресурс в коде ↔ реальный объект у провайдера» с его атрибутами. Без него Terraform не отличит создание от уже созданного и попытается дублировать ресурсы. В Git нельзя, потому что: там секреты (пароли cloud-init, ключи), он меняется при каждом apply (постоянные конфликты), и параллельная работа двух инженеров перетирает состояние. Правильно — удалённый бэкенд с блокировкой (S3/MinIO + DynamoDB-подобный lock, либо state-бэкенд с locking) и шифрованием.
*Что хочет услышать:* бэкенд, блокировка, шифрование.
*Красный флаг:* «state можно не хранить, Terraform сам разберётся».

**3. Что такое идемпотентность и как вы её проверяете на практике?**

Ответ: свойство, при котором повторное применение не вносит изменений. Проверяю вторым прогоном плейбука: `changed=0, failed=0`. Если `changed>0` — либо используется `command`/`shell`, либо шаблон генерирует разный контент (например, дата в файле), либо не выставлены `creates`/`changed_when`. Дополнительно `--check --diff` перед боевым прогоном.
*Что хочет услышать:* «второй прогон должен быть зелёным и без changed», понимание причин ложного changed.
*Красный флаг:* «идемпотентность — это когда скрипт не падает при повторном запуске».

**4. Как управлять секретами в IaC?**

Ответ: несколько уровней. В Ansible — `ansible-vault` (шифрует файл или отдельную строку через `encrypt_string`), пароль vault вне репозитория. Для Terraform — переменные с `sensitive = true` и передача через окружение `TF_VAR_*` или CI-секреты; `*.auto.tfvars` — в `.gitignore`. В CI — защищённые переменные и маскирование в логах. Дополнительно: минимальные права для токенов, ротация, аудит доступа к репозиторию. Для гибридных схем — SOPS с age/KMS.
*Что хочет услышать:* секреты не в Git, отдельный канал доставки пароля, ротация, минимальные привилегии.
*Красный флаг:* «зашифровал паролем в том же репозитории, пароль в README».

**5. Кто-то вручную изменил сервер, который описан в коде. Что делать?**

Ответ: это configuration drift. Сначала выяснить, что именно и зачем изменили (возможно, это была аварийная правка и её надо узаконить). Для конфигурации внутри ОС — прогнать плейбук, он вернёт описанное состояние; правильный финал — внести изменение в роль и закоммитить. Для ресурсов, которыми управляет Terraform, — `tofu plan` покажет расхождение по известным атрибутам; если ресурс правильный, а код устарел — обновить код; если ресурс снесли руками — `state rm` и повторное создание либо `import` существующего объекта в state.
*Что хочет услышать:* «дрейф», «код — источник правды», `plan`/`import`/`state rm`, и что внутри ОС Terraform не видит.
*Красный флаг:* «просто сделаю apply, он всё перезапишет» — без выяснения, что именно сломается.
