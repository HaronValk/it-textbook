## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

Два термина, которые постоянно путают:

- **ITAM (управление активами)** — финансово-учётная сторона: что купили, за сколько, когда, у какого поставщика, до какого числа гарантия, когда списывать. Отвечает на вопрос «сколько это стоит и что с этим будет дальше».
- **CMDB (база конфигурационных единиц)** — техническая сторона: какие **CI** (Configuration Item, конфигурационная единица) есть и **как они связаны**. CI — это не только сервер, но и коммутатор, принтер, лицензия, сервис, иногда даже стойка в серверной. Отвечает на вопрос «что сломается, если упадёт вот это».

В ITIL 4 это две практики: *IT asset management* и *Service configuration management*. На бумаге они разные, в реальной жизни живут в одной системе — и GLPI как раз такая система.

**Из чего состоит запись о CI (на примере компьютера):**

| Блок | Что хранится | Пример для WIN11-CL01 |
|---|---|---|
| Идентификация | имя, инвентарный номер, серийник, UUID | `WIN11-CL01`, `INV-2026-001` |
| Железо | производитель, модель, CPU, RAM, диски | из агента инвентаризации |
| ОС и ПО | версия ОС, пакеты/программы, версии | Windows 11 Enterprise, Edge |
| Привязки | пользователь, расположение, группа | ivanov, «Бухгалтерия, каб. 12» |
| Финансы | дата покупки, стоимость, гарантия | 14.03.2026, гарантия до 14.03.2029 |
| Состояние | новый / в эксплуатации / в ремонте / списан | «в эксплуатации» |
| История | кто и когда менял, тикеты, изменения | журнал GLPI |

**Как данные попадают в систему (это ключевая схема):**

```text
   ИСТОЧНИКИ ДАННЫХ                  CMDB (GLPI на UBU01)            ПОТРЕБИТЕЛИ
 ┌──────────────────────┐        ┌───────────────────────────┐    ┌──────────────────┐
 │ GLPI Agent (Win/Lin) │──HTTP─▶│ Assets: Computer, Printer │───▶│ Helpdesk (заявки)│
 │ сканирование сети    │──SNMP─▶│ Software + Licenses       │───▶│ Аудит, отчёты    │
 │ (discovery, 161/162) │        │ Financial (гарантия)      │───▶│ Бюджет, закупки  │
 │ AD/LDAP (люди, OU)   │──389──▶│ Relations: CI ↔ CI        │───▶│ Мониторинг       │
 │ Ручной ввод / CSV    │        │ Logs (история изменений)  │───▶│ Планирование     │
 │ Закупки / 1С         │        └───────────────────────────┘    └──────────────────┘
 └──────────────────────┘                    ▲
                                             │ HTTP/HTTPS 80/443, БД 3306 (локально)
```

**Что происходит при инвентаризации по шагам:**

1. Агент на машине собирает данные: в Windows — через WMI/CIM (классы `Win32_ComputerSystem`, `Win32_BIOS`, `Win32_Product`/реестр), в Linux — из `/proc`, `dmidecode`, `dpkg`/`rpm`.
2. Формирует инвентарный отчёт (JSON) и отправляет POST-запросом на веб-сервер GLPI.
3. Сервер сопоставляет пришедшее с существующими записями: сначала по идентификатору агента (deviceid), затем по серийному номеру/имени.
4. Если совпадения нет — создаётся новая карточка; если есть — обновляется существующая, в журнал пишется история изменений.
5. Дальше работают **правила** (rules): например, «если ОС содержит "Windows 10" — поставить модель такую-то», «если компьютер в подсети 10.10.10.0/24 — разместить в локации "Офис"».

**Три уровня зрелости учёта**, полезно держать в голове:

- *Уровень 1* — Excel: данные есть, но устаревают за месяц.
- *Уровень 2* — инвентаризация агентом: данные свежие, но без финансов и без связей.
- *Уровень 3* — CMDB: свежие данные + владелец + деньги + связи + процессы (заявка привязана к CI, изменение привязано к CI, списание оформлено).

**Порты и протоколы, которые надо помнить:** 80/443 — веб-интерфейс и приём инвентаря; 389 (LDAP) / 636 (LDAPS) — синхронизация с DC01; 3306 — БД GLPI (наружу не выставляется!); 161/162 — SNMP для сетевого оборудования; 22 — SSH, если собираешь инвентарь Linux-машин без агента.

## 3. Аналогия из жизни

Представь автопарк небольшой логистической компании. Есть гараж, и есть **картотека на каждую машину**: госномер, VIN, марка, дата покупки, срок страховки, кто из водителей закреплён, когда последнее ТО, когда следующее, что сломано и стоит ли в ремонте. Без картотеки диспетчер звонит в гараж и спрашивает «а какая машина свободна?» — и получает ответ «ну, вроде синяя». С картотекой он за десять секунд видит: две машины на ТО, одна в ремонте, три свободны, у одной через месяц кончается страховка — пора продлевать.

Дальше — то, ради чего всё затевается: когда машина ломается, по картотеке видно, **что она везла и какие рейсы встанут**. Это уже связи между CI: не просто «есть грузовик», а «этот грузовик обслуживает склад "Сидоров", у него в рейсе два заказа».

Аналогия ломается на связях: у машины нет «зависимых сервисов» в том смысле, в котором сервер БД зависит от коммутатора, питания и системы хранения. Как только появляются зависимости «А зависит от Б», картотека превращается в граф — и вот это уже настоящая CMDB.

## 4. Практика и команды

### 4.1. Развернуть GLPI на UBU01 (Docker Compose)

```bash
sudo apt update && sudo apt install -y docker.io docker-compose-v2
sudo mkdir -p /opt/glpi && cd /opt/glpi
sudo tee compose.yaml >/dev/null <<'EOF'
services:
  db:
    image: mariadb:11
    environment:
      MARIADB_ROOT_PASSWORD: 'Lab#2026-vektor-root'
      MARIADB_DATABASE: glpi
      MARIADB_USER: glpi
      MARIADB_PASSWORD: 'Lab#2026-vektor'
    volumes: [ "db:/var/lib/mysql" ]
    restart: unless-stopped
  glpi:
    image: glpi/glpi:10.0
    ports: [ "80:80" ]
    volumes: [ "glpi:/var/www/html" ]
    restart: unless-stopped
volumes: { db: {}, glpi: {} }
EOF
sudo docker compose up -d
```

Образ `glpi/glpi:10.0` — официальный `[ПРОВЕРИТЬ актуальный тег, на 2026 может быть 11.x]`. После старта открываешь `http://10.10.10.30/` → мастер установки: host БД `db`, user `glpi`, пароль со стенда, база `glpi`. По окончании GLPI попросит удалить каталог `install`:

```bash
sudo docker compose exec glpi rm -rf /var/www/html/install
```

Заводские учётки GLPI: `glpi/glpi` (супер-админ), `tech/tech`, `normal/normal` — **сразу меняй пароли**, это дефолт, известный всем.

### 4.2. Проверить, что сервис жив и БД доступна

```bash
sudo docker compose ps
sudo docker compose logs --tail=50 glpi
sudo docker compose exec db mariadb -uglpi -p'Lab#2026-vektor' glpi -e "SELECT COUNT(*) FROM glpi_computers;"
```

`ps` — статус контейнеров (`Up`/`Restarting`); `logs` — ошибки подключения к БД; SQL — что база реально отвечает и таблицы на месте.

### 4.3. Проверить LDAP до DC01 (до настройки GLPI)

```bash
sudo apt install -y ldap-utils
ldapsearch -x -H ldap://10.10.10.10 -D "adm.student@corp.vektor.lab" -W \
  -b "dc=corp,dc=vektor,dc=lab" "(objectClass=user)" sAMAccountName cn
```

`-H` — адрес каталога, `-D` — кем биндимся (UPN-формат работает в AD), `-W` — спросить пароль, `-b` — откуда начинать поиск. В выводе ищем `sAMAccountName: ivanov`. Если пусто — проверь base DN и что DC01 резолвится по имени.

### 4.4. Включить REST API и получить сессию

GUI: **Настройка → Общие → вкладка API** `[ПРОВЕРИТЬ название вкладки в твоей версии]`: включить «Enable REST API», «Enable login with credentials» и создать API-клиент (app token).

```bash
APP="<app_token_из_GLPI>"
SESS=$(curl -s -X GET "http://10.10.10.30/apirest.php/initSession" \
  -H "App-Token: $APP" \
  -H "Authorization: user_token <user_token>" | jq -r .session_token)
echo $SESS
```

`initSession` — точка входа, возвращает временный `session_token`. `jq -r` вытаскивает чистое значение.

### 4.5. Выгрузить все компьютеры через API

```bash
curl -s -H "App-Token: $APP" -H "Session-Token: $SESS" \
  "http://10.10.10.30/apirest.php/Computer?range=0-100&expand_dropdowns=true" | jq .
```

`range` — пагинация (GLPI не отдаёт всё сразу, ограничение по умолчанию), `expand_dropdowns=true` — вместо `states_id: 2` покажет `state: "В эксплуатации"`. Это и есть основа регулярной выгрузки для аудита.

### 4.6. Создать CI через API

```bash
curl -s -X POST "http://10.10.10.30/apirest.php/Computer" \
  -H "App-Token: $APP" -H "Session-Token: $SESS" -H "Content-Type: application/json" \
  -d '{"input":{"name":"WIN10-CL02","otherserial":"INV-2026-002","serial":"<серийник>","states_id":2,"users_id":4}}'
```

`otherserial` — инвентарный номер, `states_id`/`users_id` — ID из справочников. ID не угадывай: `curl .../apirest.php/State` и `.../User`.

### 4.7. Агент на Windows: установка и разовый запуск

```cmd
msiexec /i glpi-agent-1.7-x64.msi /qn SERVER=http://10.10.10.30/front/inventory.php RUNNOW=1
```

`/qn` — без интерфейса, `SERVER` — куда отправлять инвентарь (для «родной» инвентаризации GLPI 10 это именно `/front/inventory.php`), `RUNNOW=1` — запустить сразу. Точные имена свойств MSI и версию пакета **проверь в документации агента** `[ПРОВЕРИТЬ]`.

Ручной запуск для отладки:

```cmd
"C:\Program Files\GLPI-Agent\perl\bin\glpi-agent.bat" --server http://10.10.10.30/front/inventory.php --force --debug
```

`--force` — не ждать расписания, `--debug` — подробный лог (видно, что собрал и что ответил сервер). Путь к `glpi-agent.bat` `[ПРОВЕРИТЬ]` под свою версию.

### 4.9. Инвентарь Windows без агента (ручная сверка)

```powershell
Get-CimInstance Win32_ComputerSystem | Select-Object Name, Manufacturer, Model, TotalPhysicalMemory
Get-CimInstance Win32_BIOS | Select-Object SerialNumber
Get-CimInstance Win32_Processor | Select-Object Name, NumberOfCores, NumberOfLogicalProcessors
Get-CimInstance Win32_LogicalDisk -Filter "DriveType=3" | Select-Object DeviceID, VolumeName, Size, FreeSpace
```

`CIM` — современная замена `wmic` (тот объявлен устаревшим). `DriveType=3` — только локальные диски. Серийник из `Win32_BIOS` — это то, по чему обычно сводят дубли.

### 4.10. Список установленного ПО с Windows в CSV

```powershell
New-Item -ItemType Directory -Force C:\temp | Out-Null
$keys = @(
  'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\*',
  'HKLM:\SOFTWARE\WOW6432Node\Microsoft\Windows\CurrentVersion\Uninstall\*'
)
Get-ItemProperty $keys -ErrorAction SilentlyContinue |
  Where-Object DisplayName |
  Select-Object DisplayName, DisplayVersion, Publisher |
  Sort-Object DisplayName |
  Export-Csv C:\temp\software.csv -NoTypeInformation -Encoding UTF8
```

Два пути реестра — потому что 32-битные программы на 64-битной ОС лежат в `WOW6432Node`. Такой CSV — запасной вариант, если агент не проходит по сети.

### 4.11. Инвентарь Linux без агента

```bash
cat /etc/os-release
sudo dmidecode -s system-serial-number
lscpu | head -n 20
lsblk -o NAME,SIZE,TYPE,MOUNTPOINT
free -h
dpkg-query -W -f='${Package}\t${Version}\n' | sort > /tmp/packages.tsv
```

`dmidecode` требует root (читает SMBIOS), `dpkg-query -W` — весь список пакетов с версиями, ровно то, что потом сравнивается с лицензиями.

### 4.12. SQL-сверка: компьютеры, состояния, пользователи

```bash
sudo docker compose exec db mariadb -uglpi -p'Lab#2026-vektor' glpi -e "
SELECT c.id, c.name, c.serial, c.otherserial,
       s.name AS state, u.name AS user
FROM glpi_computers c
LEFT JOIN glpi_states s ON s.id = c.states_id
LEFT JOIN glpi_users  u ON u.id = c.users_id
WHERE c.is_deleted = 0 AND c.is_template = 0
ORDER BY c.id;"
```

Имена таблиц/колонок `[ПРОВЕРИТЬ по своей версии]`. Смысл: `LEFT JOIN` — чтобы машины без пользователя и без состояния тоже попали в отчёт (а они попадут, это закон).

### 4.13. SQL-сверка: установки ПО против лицензий

```bash
sudo docker compose exec db mariadb -uglpi -p'Lab#2026-vektor' glpi -e "
SELECT s.name, COUNT(DISTINCT iv.items_id) AS installs
FROM glpi_softwares s
JOIN glpi_softwareversions v ON v.softwares_id = s.id
JOIN glpi_items_softwareversions iv ON iv.softwareversions_id = v.id
     AND iv.itemtype='Computer' AND iv.is_deleted = 0
GROUP BY s.id ORDER BY installs DESC LIMIT 20;"
```

Это «сколько раз реально стоит». Второй половиной будет сумма мест из `glpi_softwarelicenses` `[ПРОВЕРИТЬ схему лицензий]` — разница и есть твоя лицензионная позиция (в западной терминологии ELP, Effective License Position).

## 6. Ошибки новичков и безопасность

1. **«Заполним CMDB один раз и на этом всё».** → Через два месяца данные врут, доверие к системе нулевое, люди возвращаются в Excel. → Нужен автоматический источник (агент/сканер) + регулярная сверка (раз в квартал) + процесс: новый актив = запись в тот же день.
2. **Два источника правды: Excel и GLPI.** → Рассинхрон, споры «а вот у меня в табличке». → Один источник правды, Excel — только как временный импорт/выгрузка, с датой.
3. **Сваливать в CMDB всё.** → Картриджи, кабели, мышки: система пухнет, никто не заполняет. → Учитывай то, что имеет стоимость, гарантию или влияние на сервис.
4. **Путать ITAM и CMDB.** → Считают деньги, но не знают, что упадёт вместе с сервером; или наоборот. → Держи в одной системе, но разделяй блоки: финансы и связи.
5. **Ручной ввод серийников и моделей.** → Опечатки, дубли, «Windows 10 Pro», «windows 10 pro», «Win10». → Инвентаризация агентом + справочники (dropdowns) вместо свободного текста.
6. **Удаление актива вместо списания.** → Теряется история: чем занимался этот ноутбук, кто виноват в потере лицензии. → Переводи в состояние «Списано», физически удаляй только с обоснованием.
7. **Массовая инвентаризация в рабочее время.** → Сканирование сети и агенты подъедают канал и диск, пользователи жалуются. → Расписание на ночь/обед, лимит одновременных задач.
8. **Импорт CSV без нормализации и без бэкапа базы.** → Кривые записи, которые потом чистят неделю. → Сначала бэкап БД GLPI, импорт в тестовую сущность, потом прод.

**Безопасность (что в бою нельзя):**

- Выставлять GLPI в интернет без HTTPS, без 2FA и со стандартными `glpi/glpi`. Это дыра с полным доступом к карте сети и учётным данным.
- Биндиться в AD доменным администратором (как мы в лабе). Нужна отдельная сервисная учётка только на чтение каталога, желательно LDAPS.
- Хранить API-токены в git, в тикетах или в `bash_history`. Отдельный файл с правами 600, ротация при увольнении админа.
- Тащить в CMDB лишние персональные данные сотрудников (паспорт, адрес). CMDB — это учёт техники, а не кадровое дело; обработка ПДн регулируется 152-ФЗ, и «а давайте ещё телефон и дату рождения» — это уже вопросы к юристу и Роскомнадзору.
- Ставить агент на личные устройства без согласия и без политики — организационный, а не технический провал.

## 7. Вопросы на собеседовании

**1. Чем CMDB отличается от реестра активов (ITAM)?**

Ответ: ITAM — про деньги и жизненный цикл: закупка, стоимость, гарантия, списание, лицензии. CMDB — про конфигурационные единицы и **связи** между ними: что от чего зависит, кто владелец, как это влияет на сервис. На практике живут в одной системе (GLPI), но это разные блоки данных и разные потребители: ITAM нужен бухгалтерии и закупкам, CMDB — эксплуатации и разбору инцидентов.

*Что хочет услышать интервьюер:* что ты понимаешь «связи» и «влияние на сервис», а не просто «список железа».
*Красный флаг:* «это одно и то же, просто названия разные».

**2. Как вы обеспечиваете актуальность данных в CMDB?**

Ответ: три слоя. Первый — автоматика: агент инвентаризации на рабочих станциях и серверах + сетевое сканирование (SNMP) для того, куда агент не поставить. Второй — процесс: любой новый актив заводится в момент выдачи (заявка в ITSM связана с CI), вывод из эксплуатации — смена состояния, а не удаление. Третий — сверка (reconciliation): раз в квартал отчёт «что есть в сети, но нет в CMDB» и наоборот, плюс отчёты по дублям (по серийнику) и по «молчащим» агентам (нет контакта N дней). Метрика зрелости — доля CI с заполненными обязательными полями и датой последней инвентаризации.

*Что хочет услышать интервьюер:* что актуальность — это процесс и метрики, а не «мы стараемся заполнять».
*Красный флаг:* «мы всё вносим вручную, у нас всё точно».

**3. Как посчитать лицензионную позицию по ПО и что делать при недозакупке?**

Ответ: считаю **установки** (данные инвентаризации, а не слова пользователей) и **приобретённые права** (лицензии/подписки с числом мест), сравниваю по версиям и редакциям — это и есть ELP (Effective License Position). Дальше по каждой позиции: излишек — кандидат на отказ от продления; дефицит — сначала легализация (закупка или переход на бесплатный/отечественный аналог из реестра), параллельно удаление нелицензионных копий, чтобы не усугублять. Отдельно фиксирую в учёте, что лицензия привязана к конкретным CI, иначе через полгода снова непонятно.

*Что хочет услышать интервьюер:* понимание разницы «установлено» и «куплено», плюс действия, а не только констатация.
*Красный флаг:* «у нас всё куплено, проблем нет» или предложение «поставить кряк, раз денег не дали».

**4. Опишите жизненный цикл единицы оборудования. Какие данные обязательны на каждом этапе?**

Ответ: заявка на закупку → получение (инвентарный номер, серийник, поставщик, дата, стоимость, гарантия) → подготовка (образ, домен, ПО, привязка к пользователю и месту) → эксплуатация (инвентаризация, обновления, тикеты, перемещения между сотрудниками и кабинетами) → ремонт (состояние «в ремонте», подмена техники пользователю) → списание (акт, физическая утилизация/передача, снятие лицензий, состояние «списано», история сохраняется). Обязательный минимум в любой момент: инвентарный номер, серийник, владелец, место, состояние.

*Что хочет услышать интервьюер:* что ты доводишь цикл до конца, включая списание и утилизацию, и не теряешь данные по пути.
*Красный флаг:* жизненный цикл заканчивается на «выдали и забыли».

**5. Как CMDB связана с ITSM и что это даёт в реальной работе?**

Ответ: заявка привязывается к CI, поэтому видно историю по конкретной машине и её «болезненность» (сколько инцидентов, что чаще ломается, когда пора менять). Изменение (RFC) привязывается к CI, поэтому можно оценить влияние: «обновляем прошивку коммутатора — эти три сервиса затронуты». При массовом инциденте CMDB отвечает на вопрос «кого ещё это касается» за секунды, а не за час обзвона.

*Что хочет услышать интервьюер:* связь учёта с процессами и оценкой влияния.
*Красный флаг:* «CMDB — это отдельная база для отчётов, с заявками не связана».
