# Объектное хранилище S3: бэкапы, архивы, статические сайты, политики жизненного цикла

## 1. Введение (зачем это нужно в реальной работе)

Тикет в helpdesk «Вектора»:

> **Пользователь:** petrova (Мария Петрова, HR)
> **ВМ:** WIN10-CL02
> **Что написала:** «Нужно отдать в проверку архив кадровых документов за 2023 год. На `\\FS01\HR` это ~180 ГБ, на флешку копировать нельзя — там персональные данные. Сделайте, пожалуйста, ссылку, которую можно отправить проверяющему, и чтобы через две недели она перестала работать».
> **Срочность:** плановая, до пятницы.

Заявка учебная, а ситуация — абсолютно рабочая. Файловый сервер для такого плох: 180 ГБ по SMB через VPN проверяющий будет качать сутки, права на папку придётся выдавать доменной учётке, а «ссылка, которая умирает через две недели» в SMB просто не существует. Ровно эту задачу решает объектное хранилище: положить архив в бакет, ограничить срок жизни объектов политикой, выдать одноразовую ссылку.

S3 — это не «папка в интернете», а отдельная модель хранения со своим API, и она давно стала стандартом де-факто: её поддерживают Яндекс Облако, VK Cloud, Selectel, Cloud.ru, AWS; из неё едят бэкапы (Veeam, restic, `pg_basebackup` через прослойки), реестры контейнеров (Harbor), логи, статические сайты и дистрибутивы. После этой главы вы должны уметь: поднять S3-совместимое хранилище на стенде, организовать бэкап и архив с версионированием и жизненным циклом, защитить данные от удаления и шифровальщиков через Object Lock, опубликовать статический сайт и выдать пользователю временную ссылку — и всё это задокументировать в runbook.

## 2. Теория «под капотом» (как это работает: архитектура, протоколы)

**Модель данных.** Три сущности: *бакет* (bucket, контейнер верхнего уровня, имя глобально уникальное в пределах хранилища), *объект* (object) и *ключ* (key). Ключ — это просто строка, например `fs01/obshchee/otchet-2026.xlsx`. Никаких настоящих каталогов внутри нет: `fs01/obshchee/` — это префикс ключа, а «папки» в веб-консоли рисует клиент. Объект = данные + метаданные (`Content-Type`, `x-amz-meta-*`, ETag, дата) + версия. Изменить объект нельзя: можно только целиком заменить новым (PUT). Переименования тоже нет — это копирование + удаление.

**Протокол.** S3 — это REST API поверх HTTP/HTTPS (7-й уровень OSI), порт 443 в облаке и, например, 9000 у MinIO в лабе. Методы: `PUT` (положить), `GET` (забрать), `HEAD` (метаданные), `DELETE`, `POST` (multipart). Аутентификация — подпись AWS Signature V4: каждый запрос подписывается секретным ключом, в заголовке `Authorization` едет access key, дата, хэш тела. Авторизация — bucket policy (JSON-политика на бакет) и IAM-политики пользователя. Ключевая деталь: **права проверяются на стороне сервиса, а не на клиенте**, поэтому «дать доступ на папку» здесь означает «написать политику на префикс ключей».

**Согласованность.** С конца 2020 года AWS S3 даёт strong read-after-write consistency: после успешного PUT любой GET сразу видит объект. MinIO ведёт себя так же. Это важно для бэкапов: скрипт может сразу проверять, что объект лёг.

**Большие файлы.** Объект до 5 ТБ, но загружается частями (multipart upload): клиент режет файл на части по 5–5120 МБ, сервер собирает. Недособранные загрузки остаются мусором и занимают место — их надо чистить правилом жизненного цикла `AbortIncompleteMultipartUpload`.

**Фичи, которые дают «взрослую» эксплуатацию:**
- *Versioning* — каждая перезапись/удаление создаёт версию; удаление ставит delete-маркер, данные остаются.
- *Lifecycle (ILM)* — правила: через N дней удалить, через N дней перевести в дешёвый класс/тир, через N дней удалить неактуальные версии, абортить недособранные multipart'ы. Правила применяются асинхронно (в AWS — раз в сутки, около полуночи UTC), то есть «удалить ровно в 00:00:01» никто не обещает.
- *Object Lock (WORM)* — объект нельзя удалить/перезаписать до истечения срока хранения. Режимы: `GOVERNANCE` (можно снять при наличии прав `s3:BypassGovernanceRetention`) и `COMPLIANCE` (не может снять вообще никто, включая root, пока срок не вышел).
- *Pre-signed URL* — временная ссылка с подписью в query-строке; даёт доступ, не раскрывая ключей.
- *Static website hosting* — бакет отдаёт `index.html` как документ по умолчанию и публично читается.
- *Tiering / storage classes* — «горячие» данные на локальных дисках, «холодные» — во внешнем S3 (например, в Яндекс Облаке), переход по расписанию.

Схема стенда после этой главы:

```text
 FS01 \\FS01\Obshchee        UBU01 (скрипты, mc)
        |                          |
        | CIFS-монтирование        | S3 API
        v                          v
 +-------------------------------------------------------------+
 | MINIO01 10.10.10.60  — S3-совместимый сервер (HTTP :9000)    |
 |   SigV4 -> bucket policy / IAM -> проверка прав              |
 +-------------------------------------------------------------+
      |                        |                         |
      v                        v                         v
 vektor-backup           vektor-archive             vektor-site
 versioning + ILM        Object Lock (WORM)         public read,
 + abort MPU             + expire 365d              статический сайт
      |
 /srv/minio/data (диски ВМ, erasure coding)
```

**Где это в РФ 2026.** Облачные S3: Яндекс Объектное хранилище (Object Storage), VK Cloud Object Storage, Selectel S3, Cloud.ru. On-premise: MinIO (AGPLv3, community-сборка бесплатна), Ceph RGW (LGPL), Garage, SeaweedFS. Про AWS: сервис доступен, но оплата и доступность из РФ нестабильны [ПРОВЕРИТЬ] — для рабочего проекта смотрите на российские площадки. Одна строка про дистрибутивы: скачивание с `dl.min.io` из РФ иногда медленное — легальная альтернатива — Ceph RGW из репозиториев вашего дистрибутива.

## 3. Аналогия из жизни

Представьте склад самообслуживания. Вы арендуете **секцию** (бакет), кладёте туда **коробки** (объекты), на каждой — **штрихкод** (ключ) и наклейка с описанием (метаданные). Внутрь коробки залезть и подправить одну бумажку нельзя — только привезти новую коробку с тем же штрихкодом и выбросить старую; поэтому у каждой коробки может быть **история версий** на стеллаже. Кладовщик по расписанию обходит склад и выносит всё, что пролежало больше года (**lifecycle**). На некоторые коробки ставится **пломба на 30 дней** — вскрыть нельзя даже директору (**Object Lock COMPLIANCE**). А проверяющему вы выдаёте **разовый пропуск на два часа** (pre-signed URL), а не свой ключ от склада.

Где аналогия ломается: на складе коробку можно переставить в другой стеллаж и она останется той же коробкой, а в S3 «перемещение» — это физическая перезапись объекта под новым ключом.

## 4. Практика и команды

Работаем клиентом `mc` (MinIO Client, работает с любым S3-совместимым сервисом) и `aws cli`. Алиас стенда-хранилища — `s3` (`http://10.10.10.60:9000`), креды лабораторные.

**1. Настройка подключения.**
```bash
mc alias set s3 http://10.10.10.60:9000 vektor-admin 'Lab#2026-vektor' --api S3v4
# Added `s3` successfully.
mc admin info s3
```
`--api S3v4` — версия подписи (S3v4 = Signature V4). `admin info` показывает состояние сервера, объём, версию. Смотреть: доступен ли сервер, свободное место.

**2. Создание бакетов.**
```bash
mc mb --with-versioning s3/vektor-backup
mc mb --with-lock       s3/vektor-archive
mc mb                   s3/vektor-site
mc ls s3
```
`--with-versioning` — сразу включить версии, `--with-lock` — включить Object Lock (он **требует** версионирования, поэтому создать «лок» на уже готовом бакете нельзя, только включить версии и потом настраивать правила). Имена: строчные буквы, цифры, дефисы, 3–63 символа, без подчёркиваний.

**3. Копирование и синхронизация.**
```bash
mc cp --recursive /mnt/fs01-obshchee/ s3/vektor-backup/fs01/obshchee/
mc mirror --overwrite --remove /mnt/fs01-obshchee/ s3/vektor-backup/fs01/obshchee/
```
`mc cp` — разовая копия, `mc mirror` — синхронизация (как `rsync`): `--overwrite` перезаписывает, `--remove` удаляет в приёмнике то, чего нет в источнике (**опасно**: с включённым версионированием это delete-маркеры, без него — реальное удаление).

**4. Просмотр объектов и метаданных.**
```bash
mc ls --recursive s3/vektor-backup | head
mc stat s3/vektor-site/index.html
# Name      : index.html
# Size      : 1.2 KiB
# Metadata  :
#   Content-Type: text/html
mc du s3/vektor-backup
```
`mc stat` — главный инструмент диагностики статических сайтов: почти всегда проблема в `Content-Type: application/octet-stream` вместо `text/html`. `mc du` — занятый объём.

**5. Версионирование.**
```bash
mc version enable s3/vektor-backup
mc ls --versions s3/vektor-backup/fs01/obshchee/
mc version suspend s3/vektor-backup     # приостановить, старые версии остаются
```
Смотреть: появился ли `version-id`, не создаётся ли delete-маркер там, где его не ждут.

**6. Публичный доступ (и как его отобрать).**
```bash
mc anonymous set download s3/vektor-site     # публичное чтение
mc anonymous get s3/vektor-site              # текущая политика
mc anonymous set none s3/vektor-site         # только по подписи
```
В старых версиях `mc` та же команда называлась `mc policy set download`. Ошибка «нажал download на бакет с бэкапами» — классический способ утечь.

**7. Политики жизненного цикла.**
```bash
mc ilm rule add s3/vektor-backup --expire-delete-marker --noncurrent-expire-days 30
mc ilm rule add s3/vektor-backup --expire-days 7 --prefix "tmp/"
mc ilm rule add s3/vektor-backup --transition-days 90 --transition-tier YANDEX-COLD
mc ilm rule ls s3/vektor-backup
mc ilm rule export s3/vektor-backup > ilm-backup.json
```
`--noncurrent-expire-days` — удалить неактуальные версии; `--prefix` — применить правило к префиксу (никогда не задавайте правило на весь бакет бэкапов «на глаз»); `--transition-*` требует заранее настроенного тира (`mc admin tier add`). `export` — чтобы положить правило в git и не собирать руками.

**8. Object Lock (WORM).**
```bash
mc retention set --default governance 30d s3/vektor-archive
mc retention set --default compliance 30d s3/vektor-archive/legal/
mc legalhold set s3/vektor-archive/legal/delo-2023.zip
mc retention info s3/vektor-archive/legal/delo-2023.zip
```
`compliance` снять нельзя до истечения срока — ни админом, ни поддержкой вендора. `legalhold` — бессрочная пломба, снимается отдельной командой `mc legalhold clear`. Ставьте `compliance` только осознанно: ошибочно применённый срок исправить невозможно.

**9. Временная ссылка (pre-signed URL).**
```bash
mc share download --expire 14d s3/vektor-archive/legal/delo-2023.zip
# Share: http://10.10.10.60:9000/vektor-archive/legal/delo-2023.zip?X-Amz-Algorithm=...&X-Amz-Expires=1209600&X-Amz-Signature=...
```
Срок задаётся в `s`/`m`/`h`/`d`. Ссылка = подпись + срок; кто её получил, тот и скачает, поэтому это «одноразовый пропуск», а не «права пользователя».

**10. Проверка через `aws cli` (то же самое, другой клиент).**
```bash
export AWS_ACCESS_KEY_ID=vektor-admin
export AWS_SECRET_ACCESS_KEY='Lab#2026-vektor'
aws --endpoint-url http://10.10.10.60:9000 s3api list-object-versions --bucket vektor-backup --max-items 5
aws --endpoint-url http://10.10.10.60:9000 s3api get-bucket-lifecycle-configuration --bucket vektor-backup
aws --endpoint-url http://10.10.10.60:9000 s3 presign s3://vektor-archive/legal/delo-2023.zip --expires-in 3600
```
`--endpoint-url` — потому что клиент по умолчанию идёт в AWS; регион для MinIO любой (`us-east-1`). Это важно знать: любой S3-совместимый сервис = endpoint + ключи.

**11. Bucket policy для сервисной учётки.**
```bash
mc admin user add s3 svc-backup 'Svcb#2026-vektor'
mc admin policy create s3 vektor-backup-rw backup-policy.json
mc admin policy attach s3 vektor-backup-rw --user svc-backup
```
`backup-policy.json` — JSON с `Resource: ["arn:aws:s3:::vektor-backup", "arn:aws:s3:::vektor-backup/*"]`, `Action: ["s3:PutObject","s3:GetObject","s3:ListBucket","s3:DeleteObject","s3:AbortMultipartUpload"]`. Синтаксис `attach` зависит от версии `mc` [ПРОВЕРИТЬ]; в старых — `mc admin policy set`.

**12. Проверка отдачей по HTTP.**
```bash
curl -I http://10.10.10.60:9000/vektor-site/index.html
# HTTP/1.1 200 OK
# Content-Type: text/html
curl -I "http://10.10.10.60:9000/vektor-archive/legal/delo-2023.zip"
# HTTP/1.1 403 Forbidden   <- приватный бакет, так и должно быть
```
`curl -I` — быстрый способ проверить, что видит пользователь, не открывая браузер. В GUI MinIO Console (если она есть в вашей сборке — в новых community-релизах её урезали [ПРОВЕРИТЬ]) те же действия: Buckets → бакет → Lifecycle / Anonymous / Object Lock.

### Шаги

1. **MINIO01, установка.** Обновите систему и скачайте бинарники сервера и клиента.
   ```bash
   sudo apt update && sudo apt install -y curl wget cifs-utils
   wget https://dl.min.io/server/minio/release/linux-amd64/minio -O /tmp/minio
   wget https://dl.min.io/client/mc/release/linux-amd64/mc -O /tmp/mc

   sudo install -m 0755 /tmp/mc /usr/local/bin/mc
   minio --version
   ```
   Ожидаемо: печатается версия и лицензия AGPLv3.

2. **MINIO01, служба.** Создайте пользователя, каталог данных и unit.
   ```bash
   sudo useradd -r -s /sbin/nologin minio-user
   sudo mkdir -p /srv/minio/data && sudo chown -R minio-user: /srv/minio
   sudo tee /etc/default/minio >/dev/null <<'EOF'
   MINIO_ROOT_USER=vektor-admin
   MINIO_ROOT_PASSWORD=Lab#2026-vektor
   MINIO_VOLUMES=/srv/minio/data
   MINIO_OPTS="--address :9000"
   EOF
   sudo tee /etc/systemd/system/minio.service >/dev/null <<'EOF'
   [Unit]
   Description=MinIO
   After=network-online.target
   [Service]
   User=minio-user
   EnvironmentFile=/etc/default/minio
   ExecStart=/usr/local/bin/minio server $MINIO_OPTS $MINIO_VOLUMES
   Restart=always
   [Install]
   WantedBy=multi-user.target
   EOF
   sudo systemctl daemon-reload && sudo systemctl enable --now minio
   ```
   Ожидаемо: `systemctl status minio` — `active (running)`.

3. **MINIO01, проверка порта и API.** Откройте 9000 в файрволе (в лабе — упрощение, в бою так нельзя) и проверьте health-эндпоинт.
   ```bash
   sudo ufw allow 9000/tcp
   curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:9000/minio/health/live
   ```
   Ожидаемо: `200`.

4. **MINIO01, алиас и бакеты.** Выполните команды 1–2 из раздела 4. Ожидаемо: `mc ls s3` показывает три бакета; `mc mb` не ругается.

5. **MINIO01, сервисная учётка.** Создайте `backup-policy.json` (см. п. 11 раздела 4), пользователя `svc-backup` и привяжите политику. Затем проверьте от его имени:
   ```bash
   mc alias set s3svc http://10.10.10.60:9000 svc-backup 'Svcb#2026-vektor'
   mc ls s3svc
   ```
   Ожидаемо: `s3svc` видит только `vektor-backup` (или получает отказ на листинг остальных бакетов) — это и есть проверка принципа минимальных прав.

6. **MINIO01, монтирование шары FS01 и первый бэкап.**
   ```bash
   sudo tee /etc/smb-fs01.cred >/dev/null <<'EOF'
   username=VEKTOR\adm.student
   password=Lab#2026-vektor
   EOF
   sudo chmod 600 /etc/smb-fs01.cred
   sudo mkdir -p /mnt/fs01-obshchee
   sudo mount -t cifs //10.10.10.20/Obshchee /mnt/fs01-obshchee -o credentials=/etc/smb-fs01.cred,domain=VEKTOR,ro
   ls /mnt/fs01-obshchee
   mc mirror --overwrite /mnt/fs01-obshchee/ s3/vektor-backup/fs01/obshchee/
   mc du s3/vektor-backup
   ```
   Ожидаемо: файлы появились в бакете, `mc du` показывает ненулевой объём. `ro` — монтируем только на чтение, чтобы бэкап-джоб физически не мог испортить источник.

7. **MINIO01, проверка версионирования.** Перезапишите один объект и посмотрите историю.
   ```bash
   mc cp /etc/hostname s3/vektor-backup/fs01/obshchee/test-version.txt
   echo "second run" > /tmp/h.txt && mc cp /tmp/h.txt s3/vektor-backup/fs01/obshchee/test-version.txt
   mc ls --versions s3/vektor-backup/fs01/obshchee/test-version.txt
   ```
   Ожидаемо: две строки с разными `version-id`.

8. **MINIO01, жизненный цикл.** Добавьте правила как в п. 7 раздела 4 и выгрузите их в файл для регламента.

   ```bash
   mc ilm rule add s3/vektor-backup --expire-days 90 --prefix "tmp/"
   mc ilm rule export s3/vektor-backup | tee ~/ilm-backup.json
   ```
   Ожидаемо: `mc ilm rule ls` показывает два правила с корректными префиксами и сроками.

9. **MINIO01, архив с пломбой.** Загрузите тестовый файл в `vektor-archive/legal/` и поставьте `compliance 30d`. Попробуйте удалить.

## 6. Ошибки новичков и безопасность

- **«Сделаю бакет и подключу как сетевой диск»** → S3 не POSIX: нет блокировок, rename, дозаписи в конец файла → база 1С или файл `.mdb` на S3 будут битыми. Правильно: S3 — для бэкапов, архивов, статики и медиа; для БД — снапшоты/дампы, а не «файл базы в бакете».
- **`mc anonymous set download` на все бакеты «чтобы быстрее проверить»** → публичная утечка персональных данных и бэкапов, а через поисковики — ещё и индексируемая. Правильно: публичный доступ — только точечно на бакет статики, всё остальное — по подписи или через политику.
- **Нет версионирования + правило `--expire-days` на весь бакет** → единственная копия бэкапа удаляется по расписанию, восстановить нечего. Правильно: версионирование + правило только на конкретный префикс + отдельный бакет для «вечного» архива.
- **Правило ILM без `--prefix`, «на глаз»** → за ночь удаляется продакшн-бэкап или файлы сайта. Правильно: сначала `mc ilm rule export` и ревью по процедуре change management (урок 86), потом применение.
- **Ключи доступа в скрипте/репозитории/тикете** → компрометация всего хранилища. Правильно: сервисные учётки с политикой на один бакет, ротация ключей, секреты — в хранилище секретов, root-ключи не используются приложениями.
- **Не настроен `AbortIncompleteMultipartUpload`** → прерванные загрузки лежат мусором, место кончается незаметно, ругань на «бэкапы занимают втрое больше». Правильно: правило автоочистки + контроль через `mc du` и метрики.
- **Порт 9000 открыт в мир без TLS** → в логи попадают ключи и данные в открытом виде. Правильно: только HTTPS (nginx/reverse proxy с сертификатом внутреннего УЦ), доступ по VPN/белому списку, отдельный сервисный VLAN.
- **Вера в «удалил — значит уничтожено»** → версии, delete-маркеры, реплики и Object Lock оставляют данные живыми. Правильно: для реального уничтожения — политика истечения версий + проверка на копиях, для ПДн — процедура, согласованная с ИБ.

**Безопасность (в бою так нельзя):** в лабе мы открываем порт 9000 без TLS, храним пароль стенда в `/etc/smb-fs01.cred` и используем предсказуемые креды — это допустимо только на изолированном стенде. В рабочей среде: TLS обязателен (bucket policy с `Deny` при `aws:SecureTransport=false`), root-ключи только в сейфе, сервисные учётки — под конкретный бакет и префикс, включён аудит доступа к объектам, бэкапы защищены Object Lock (это же и защита от шифровальщиков), а проверка восстановления из объектного хранилища проводится по графику из урока 89. Отдельно: `compliance`-ретеншн — инструмент, а не «на всякий случай»; ошибочно выставленный срок на ПДн может нарушить сроки хранения по закону, поэтому согласуйте его с юристами.

## 7. Вопросы на собеседовании

**1. Чем объектное хранилище отличается от файлового и блочного и когда вы выберете S3?**
Ответ: блочное (iSCSI, RBD) — диски для ФС и БД, минимум семантики; файловое (SMB/NFS) — дерево каталогов, блокировки, права на уровне файлов; объектное — плоское пространство ключей, каждый объект меняется целиком, доступ по HTTP API с подписью, горизонтальное масштабирование, дешёвая репликация и политики жизненного цикла. S3 выбираю для бэкапов, архивов, статики, логов, медиа, дистрибутивов и как backend для Harbor/Veeam/restic. Не выбираю для БД, для «сетевого диска» пользователям и для сценариев с частой модификацией маленьких файлов.
*Что хочет услышать интервьюер:* понимание модели (ключ-значение, замена объекта целиком, HTTP API) и границ применимости.
*Красный флаг:* «S3 — это просто папка в облаке, туда можно базу положить».

**2. Как вы защитите бэкапы в объектном хранилище от ransomware и от собственных ошибок?**
Ответ: версионирование включено всегда; Object Lock в режиме `compliance` на срок, превышающий окно обнаружения атаки (например, 30–60 дней); отдельные сервисные учётки только на запись с ограничением по префиксу; жизненный цикл, который не удаляет неактуальные версии раньше срока ретеншна; MFA/строгий доступ к root-ключам; регулярная проверка восстановления (иначе это не бэкап, а надежда).
*Что хочет услышать интервьюер:* WORM + минимум прав + проверка восстановления как система, а не «мы делаем снапшоты».
*Красный флаг:* «включим версионирование, этого достаточно» или «у нас 3-2-1, но восстанавливать не пробовали».

**3. Что такое pre-signed URL, какие у него ограничения и риски?**
Ответ: ссылка, в которой подпись SigV4 и срок действия передаются в query-параметрах; даёт доступ к конкретному объекту без выдачи ключей; срок ограничен, но ссылку можно передать дальше, и до истечения она работает у любого. Риски: утечка ссылки = утечка объекта, логирование URL в прокси/браузере, слишком длинный срок. Практика: короткий TTL, ссылка на конкретный объект, не на бакет; для чувствительных данных — дополнительная аутентификация на уровне приложения.
*Что хочет услышать интервьюер:* понимание, что это делегирование доступа, а не аутентификация пользователя.
*Красный флаг:* «pre-signed URL — это безопасная авторизация пользователей».

**4. Как сделать статический сайт на S3 и почему иногда так делать не стоит?**
Ответ: включить публичное чтение бакета, загрузить `index.html` и ресурсы с корректным `Content-Type`, при необходимости настроить error document и кэширование, надеть сверху CDN и TLS (в облаке — через CDN-домен, on-premise — nginx перед MinIO). Ограничения: нет серверной логики, нет нормальной обработки форм, SPA требует fallback на `index.html`, публичный бакет — это осознанный риск, а приватный контент так публиковать нельзя.
*Что хочет услышать интервьюер:* знание Content-Type и разницы между «сайт из бакета» и «сайт за CDN».
*Красный флаг:* «просто открываю бакет наружу, там же всё равно статика» — без упоминания CDN, TLS и чувствительности данных.

**5. Как контролировать стоимость и рост объектного хранилища?**
Ответ: видеть, что занимает место — `mc du`, метрики по бакетам и префиксам, отчёт по количеству версий и недособранных multipart-загрузок; правила жизненного цикла (истечение неактуальных версий, аборт multipart, переход в холодный тир); классы хранения по сроку доступа; разделение бакетов по политике (бэкап ≠ архив); алерты на аномальный рост; и выгрузка правил в git, чтобы «кто-то поменял lifecycle» не выяснялось по факту удаления данных.
*Что хочет услышать интервьюер:* связка «наблюдаемость + политики + классы хранения», а не «закупим ещё дисков».
*Красный флаг:* «объектное хранилище дешёвое, считать не надо» или отсутствие упоминания неактуальных версий и multipart-мусора.
